# 跨任务记忆与跨平台同人识别

## 为什么需要

跨关键词、跨产品、跨时间，同一个博主会反复出现。重复推荐浪费用户时间，重复发信显得不专业。

前一版只记录"每次运行批次"，不记录人 —— 这是个真实缺口。

---

## 文件

`memory/creators.json`，单文件，本地。**不做多人共享** —— 单人使用足够，团队场景需要另行设计。

```json
{
  "version": 1,
  "updated_at": "2026-08-25T14:30:00Z",
  "creators": {
    "tiktok:techwithsarah": {
      "platform": "tiktok",
      "handle": "techwithsarah",
      "nickname": "Sarah | Tech Reviews",
      "followers": 82000,
      "first_seen": "2026-08-25",
      "linked_to": "instagram:techwithsarah",

      "recommendations": [
        {
          "date": "2026-08-25",
          "product": "anker-powerbank",
          "keyword": "anker power bank",
          "task": "anker-powerbank-202608251430",
          "tier": "A",
          "fit_reason": "数码测评方向，最近在测氮化镓充电头"
        }
      ],

      "contacted": false,
      "replied": false,
      "blocked": false,
      "note": ""
    }
  }
}
```

主键格式：`{platform}:{handle}`。

## 规则

**任务开始时先读**，任务结束时写回。**「文件不存在」与「文件读不出来」是两件事**：

| | 含义 | 怎么做 |
|---|---|---|
| 文件不存在 | 第一次跑，记忆里确实没有人 | 创建，正常往下走 |
| 文件读不出来 | 可能记着一百个人，**我读不出来** | `collect` 以退出码 2 结束，**不产出名单**；你也停下 |

「读不出来」有五种，**第四种更常见也更阴**：

1. **读不到** —— 权限不足、父路径不是目录、磁盘 IO 错。文件本身可能好好的，
   是**拿不到它**。报错里会带上真实原因，**照着那句去查，别默认是 JSON 坏了**（ADR-26）
2. **解析失败** —— 少个逗号、写到一半被打断，一眼看得出坏了
3. **同一层出现两次的键** —— 解析只会留下最后一条，另一条说了什么无从得知，
   而它们可能正好相反（ADR-36）
4. **结构不对** —— 合法 JSON，但形状错了。最典型的是把 `creators` 的花括号
   改成方括号，或者删掉某个人的 `contacted`。它**能解析**，于是旧版本会
   若无其事地报「读到了」，然后一个人都不过滤（ADR-19）
5. **键不能用** —— 键必须是 `platform:handle`：平台得是支持的那几个，handle 只能有
   字母、数字、下划线、点。少个冒号、平台拼错、handle 前面带了 `@`，或者两个键
   （比如 `tiktok:Alice` 和 `tiktok:alice`）指向同一个人、各有一条记录，都算读不出来
   （ADR-25 · ADR-37）

> 键的**大小写不用管**：读进来时按 D1 统一小写化，写回去也是规范形式。
> 手改时不小心把首字母打成大写，脚本会就地纠正，不会因此漏掉这个人。

读不出来时不产出名单，是因为 `contacted` / `blocked` 全靠这个文件，
读不出来就无法保证不重复打扰（P4），而**名单没有第三态** —— CSV 里每一行
就是「这个人可以发信」，没有地方写「我不确定该不该发」。见 ADR-15。

**这也是为什么续跑时不能拿上一轮的 `creators.json` 将就**：那份名单是按上一轮
读到的记忆过滤的，用户这一轮手改过的 `contacted` 它一个都不知道。

**这时候要跟用户说的话**，按顺序：

1. `memory/creators.json` 读不出来了。**报错会直接说是哪里不对**（哪个人的哪个字段），
   原样转给用户 —— 修它的是人，越具体越好
2. 采集结果和已花的预算都在，**已抓到的不会重抓**。但续跑要不要花钱，
   **照 stderr 说的转述**：剩余关键词和待补 profile 都为零才是零请求。
   修好之后按 stderr 给的那条命令续跑（预算用尽时它会带上 `--budget`）：
   `npm run collect -- --resume output/{task}`
3. 如果实在修不了、又必须现在拿到名单：加 `--ignore-memory`。
   但要**说清代价** —— 这一批不会做已联系去重，名单里可能有他打扰过、
   甚至已经拉黑的人，发信前得自己核对

**不要自作主张替用户选第 3 条。** 前两条是标准答案，第 3 条是他的取舍。

| 状态 | 处理 |
|------|------|
| 已推荐过（`recommendations` 非空） | **默认不进新名单** |
| 推荐记录来自**同一个任务**（`task` 相同） | **不过滤**。续跑要推荐的就是这批人；滤掉会让 render 之后的每次 `--resume` 都产出空名单 |
| 换了产品且契合度更高 | 可以再推，但必须标注「曾为 {product} 推荐过（{date}）」，让用户自己判断 |
| `contacted: true` | 排除 |
| `blocked: true` | 排除，且不再出现在任何名单 |

交付时给用户一行统计：

```
本次发现 187 人，其中 23 人此前推荐过已过滤，2 人已标记联系过。
```

**先看 `memory_status` 再报这一行。** 它是 `unreadable_ignored` 时那两个数都是 0，
而这个 0 和「确实没人需要过滤」长得一模一样 —— 这时候要报的是
「**本次没有做去重**，名单里可能有你联系过的人」，不是「0 人已过滤」。

它是 `unknown` 时，报的是「**不知道有没有去重**，重跑一次采集就有确定答案」——
说不知道，不要说没问题。**不要替它编一个原因**：`unknown` 有两个来源
（早期版本采集的任务目录、名单与去重状态没能一起落成），事后分不出是哪一个。

## 关于 `contacted`

**Skill 不发信，因此只能知道"推荐过"，无法知道"联系过"。**

`contacted` / `replied` / `blocked` 是**用户手动标记位**：

- 直接改 JSON
- 或者跟你说一声，由你写入（"@techwithsarah 已经联系过了" → 标记）

> **手改 JSON 是这个文件最常见的损坏来源**，而它是唯一一份副本（`memory/` 不进 git）。
> 用户说要自己改的时候，提一句「改完让我跑一下就知道有没有改坏」比事后补救便宜 ——
> 尤其是**形状改错**这种：它能解析，肉眼也不容易看出来。
> 脚本这边已经做到：读不出来（含结构不对）不会被当成空记忆，也**不会被覆盖**，
> 而且报错会指名哪个人的哪个字段（ADR-15 · ADR-19）。

**不要主动追问上批结果。** 让运营回填数据这件事历史成功率极低，追问只会在每次任务开头插入一段用户想跳过的对话。

## 跨平台同人识别

做双平台之后新增。同一个人在 TikTok 和 IG 都有号，**价值高于任一单平台账号** —— 触达更广，且愿意跨平台经营的创作者通常更认真对待商务合作。评分里给 +15。

### 识别信号（按可靠度排序）

**1. bio 外链互指 —— 最可靠**

```
TikTok  data.userInfo.user.bioLink.link  →  含 instagram.com/{handle}
IG      bio_links[].url                  →  含 tiktok.com/@{handle}
```

Linktree / beacons.ai 这类聚合页也算 —— 但要真去看页面内容才能确认，成本较高，可以只在其他信号也吻合时才验证。

**2. handle 完全相同或高度相似**

```
tiktok:techwithsarah  ↔  instagram:techwithsarah      完全相同，强信号
tiktok:sarah.tech     ↔  instagram:sarahtech          去标点后相同，较强
tiktok:sarahtech      ↔  instagram:sarah_tech_real    相似但不确定，弱
```

**3. 昵称 + 头像同时接近 —— 最弱**

单独出现时不足以判定。只作为前两条的佐证。

### 合并规则

满足信号 1，或信号 2 的强档，才合并。

合并后：
- 按"人"而非"账号"计入名单，避免同一个人占两个名额
- `followers` 取两平台之和
- 输出标注 `cross_platform: true`，并在 CSV 里列出两个 handle
- 记忆里双向写 `linked_to`

**不确定时不合并。** 错误合并两个人的代价（发错信、张冠李戴）比漏合并同一个人（多推荐一次）大得多。

不确定但有嫌疑时，在 `note` 里记一句"疑似与 instagram:xxx 为同一人"，留给下次或用户判断。

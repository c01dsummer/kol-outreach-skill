# 3 · 生成:代码与 UI

界面和代码是两种不同的产物,但它们受**同一类约束**,所以放在一份文档里:

> **生成环节不许发明。**
> 每一处产出都要能指回上游 —— 指回一条需求编号,或者指回设计里的一个 token。
> 指不回去的东西,就是这一环节自己发明出来的,而发明出来的东西没有人验收得了。

> 第三种产物是**架构文档**,它受的约束不同(它管的是零件之间,不是零件本身),
> 单独在 `5-DESIGN.md`。**动手改模块边界或调用顺序之前先读那一份。**

---

## 通用纪律

### 1. 一个任务 = 一个需求编号 = 一个能一次读完的 diff

超出就拆。**一个需要略读的 diff 等于没被审查过。**

### 2. 禁止顺手重构

改 A 就只改 A。想重构 B,单开一个任务。

顺手重构最大的问题不是风险,是**它让 diff 变得读不完**,
于是真正的改动藏在格式变动里,审不出来。

评审者要的也算顺手：评审中提出的重构、新行为、新跑法、新触发、新模块,另开一条 PR,
不在正被评审的那条改动里做,本 PR 里最多把它降级 —— 开关或删入口(`6-INTEGRATE.md`「评审中的发现」)。
唯一的例外：同一处连着两轮被挑出毛病、需求所有者定了改设计(`6-INTEGRATE.md`「同一处连着两轮被挑出毛病」)。

### 3. 非平凡改动先出计划再写代码

改哪些文件、为什么、影响哪条需求。
**计划阶段发现错误的成本,比代码阶段低一个数量级。**

### 4. 审 diff 时,重点看它删了什么

**遗漏比错误更常见,删除比新增更难发现。**

新增的错代码会报错、会跑不通、会被测试抓到。
删掉的一个空值分支、一条校验、一句纪律注释,**什么都不会发生** ——
直到有一天它本该拦住的东西过去了。

规则:**diff 里每一处删除,都要能说清为什么可以删。**说不清就是不能删。
最好把它做成一个工具:自动列出 diff 里删掉的校验、空值分支、异常处理,逐条要求解释。

### 5. 通用最佳实践,有一部分在具体项目里是反的

这一条最容易出事,因为违反它的代码看起来**特别专业**。

典型的几条:

| 通用做法 | 什么时候是错的 |
|---|---|
| 防御性默认值 `x \|\| "未知"` | 信息类产品里,这是把"不知道"伪装成"知道" |
| 优雅降级 | 拿不到数据时降级显示,等于用旧的/假的数据冒充新的 |
| DRY 到底 | 两处相似但语义不同的规则合并后,改一处会误伤另一处 |
| 封装内部细节 | 需要可追溯性的产品里,来源信息必须能穿透到界面 |

每个项目要在自己的业务层文档里列出**「哪些通用最佳实践在这里是错的」**,
并且**尽量让它们在这个项目里写不出来** —— 因为默认会遵循它们的不只是人,
还有所有把最佳实践当先验的代码生成器。

按这个顺序挑材料,越靠前越好:

1. **结构性**(「写不出来」)—— 改数据形状或调用形状,让那个坏状态表达不出来
2. **验证性**(「查得出来」)—— 直接断言**结果**:坏的写法会让产出物变成什么样,就断言那个
3. **指令性**(「别这么写」)—— 扫源码的 lint、文档里的告诫。**最后一档**

第三档为什么垫底:它每次都在和激励梯度竞争,而且**必须先列举**你要防的东西 ——
列漏了就静默放行,而没人知道漏了。比如一条扫写法的 lint 靠一张手写的字段表,
判据正文说的是哪儿都不许,真正盖住的却只是表上那几个名字。
梯度指向捷径时,**拆掉那条捷径**,不要再加一条规则去劝阻它。

散文里的纪律是期望,**能报错的检查才是保证**。

### 6. 名字说内容,不说来历

目录、文件、测试组、命令的名字,写**它装的是什么、测的是什么**,
不写它是从哪张工单、哪条决策记录、哪一片、哪一组来的。

工单号、记录编号、分片代号只在派活的那几天有意义:工单关了、片合了,
名字还留在树上,后来的人(和每次从零开始的 Agent)只看得到一串码,
得先去查码才知道里面是什么。来历写进文件头注释或决策记录,那里能写清楚,也不挡路 ——
写的是那件事本身,不是外部工具里的工单号(第 7 条)。

例外只有一种:**编号本身就是这份东西的身份**,而且后面跟着说内容的标题 ——
例如一条一个文件、文件名是「编号-标题」的决策记录。表示阅读顺序的序号也不算来历。

### 7. 仓库只往里指,不往外指

外部任务工具(看板、工单系统)里的一张卡,可以写它对应仓库里的哪条决策记录、哪条需求、哪个 PR;
**反过来不行**:仓库里的文字 —— 决策记录、需求登记、文档、代码注释、检查用的数据 —— 不写外部工具的工单号,
也不放指向某一张卡的链接。

仓库是这个产品唯一会被完整交接、完整复制的东西。工单号要开着那个工具才说得出意思,
工具换了、权限没了、卡改了标题,号就成了一串没人认得的码;而它往往正写在决定为什么这么做的那一句里。
要说的是哪件事,就写那件事本身:说内容的名字、决策记录编号、需求编号、PR 号。
决定是在卡上做的,把谁、什么时候、选了什么、原话抄进决策记录 —— 记录要自己读得懂。

指向那个工具里整个项目的入口链接不算(它是路由,不是依据)。仓库之外的协作痕迹 —— PR 标题与正文、分支名 ——
可以带工单号,工具靠它们把 PR 挂到卡上。提交信息也不在这条里:它是改动的来历,不是仓库里的文字,
工具同样靠它挂卡;但别把只有开着那个工具才读得懂的东西当成提交信息的全部。
新写的文字里引一个分支名时,分支名里的工单号就成了仓库里的文字,照这一条撤掉。

这一条最好有检查守着:决策记录追加不删改,旧记录里已有的号删不掉,检查就按文件数号、只许减不许加,
新文件一个都不许有。

### 8. 要用到的事实,先写清楚找谁要;能问权威的,不从给人看的文字里推

很多功能要先知道一些事实才能干活:这次改了哪些文件、改了哪几行,代码里一个名字指的是哪个声明,
某个行为有没有测试守着。**动手写代码之前,在第 3 条的计划里先列一张表**(计划写进决策记录的,表也写在那里;
不用出计划的平凡改动不用列):

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|

项目可以把这一节的标题和表头定成固定写法、不用列的写一句固定开头的理由,再建一道检查看着新记录里
这一节在不在、每格填没填;检查只看得到格式,填得对不对仍靠下面那次独立复核。

**能让权威给确切答案的,就问权威。** 权威指的是本来就负责回答这件事的那个工具:编译器和它的语言服务、
版本管理工具专门给机器读的输出(空字符分隔、不加引号、固定格式的行号)、真跑一遍得到的结果。
**不许从给人看的文字里自己推**:名字、注释、排好版的报告、给人读的差异正文。

两处别读歪:

- 项目自己规定了格式、并且有检查校验那个格式的标记(比如写在注释或提交信息里的具名豁免),
  不算「给人看的文字」—— 它本来就是写给机器读的契约。
- 「真跑一遍的结果」是拿来回答「事实是什么」的,不是拿来当测试期望值的;期望值不许来自运行结果
  (`4-VERIFY.md`)。

为什么:给人看的文字为了好读,会加引号、转义、截断、换行、用同一个名字指不同的东西。
从它推出来的规则,每遇到一种没想到的写法就错一次;评审每轮挑出一种,补一种又冒出一种,永远收不住。
权威给的答案一次就是对的,剩下的只是用对它。

这张表**在写代码之前过一次独立复核**。复核者只问一件事:每一行的「找谁要」是不是那件事真正的权威。
这是设计复核,不是代码评审,不算评审轮次(`6-INTEGRATE.md`「先定义『一轮』」)。
实在找不到权威、只能推的那几行,写明推法在什么情况下会错,错的时候是多报还是漏报 —— **选多报**:
多报的会当场红,有人看;漏报的报绿,没人看。

写到一半发现某件事要靠推,停下来回到这张表,不要先推着写、以后再换。

### 9. 存下来的数据加字段、删字段、改名:先定缺着怎么读,读不清就升版本

管的是**存下来、以后还会被程序读回来的数据**:状态文件、交付物、登记表、台账、跨次运行的记忆、检查链自己存的记录。
只给人看一眼的页面、只在一次运行里传递的输出不在此列。
总纲那一句(`README.md`「这套东西的一条总纲」)说旧数据缺字段只能读作「我不知道」;这一条把它落到五件事上,
并写清三种不按那一句读的情形:字段加入之前那件事不可能发生的可选字段(第一件)、派生字段(第一件末)、带版本标记且从那一版起写明每次都写的字段(第三件)。

**一、一个字段缺着,只许有一种意思。** 加字段时先问:新代码写这份数据时,会不会也有不写它的时候?

- 不会(每次都写):缺着只可能是旧数据,照总纲读作「我不知道」,写明哪些结论因此是「我不知道」、哪些照旧。
- 会(它本来就是可选的,比如作废标记只在作废时才写):缺着既可能是「旧数据还不知道这件事」,也可能是「新数据没填」。
  只有一种情况可以把缺着读成默认值:**这件事在字段加入之前不可能发生**(不只是「那时没记下来」)。
  例:作废标记跟作废这个动作同一天加进来,之前没有作废这回事,旧条目缺着确实是「没作废」;
  反过来,「是否联系过」在加字段之前就可能发生过、只是没记,旧数据缺着就只能是「我不知道」。
  走这个口子的,在那条改动里写明「缺着读作某某,对旧数据也成立,因为……」,并拿一份真的旧数据断言它读成了那个默认值;
  说不清「之前不可能发生」的,不许这么读,给数据升版本(第三件),读的一侧按版本分开读。

由工具算出来写回的**派生字段**(比如内容指纹)不归这一件:缺着就是没回写,当场红,不读作「我不知道」
(`1-REQUIREMENTS.md`「登记表里的元数据要么是派生的,要么删掉」)。

**二、删字段、改名、改类型、改意思,都要升版本。** 旧代码读新数据,会把改了名的字段当成缺着;
新代码读旧数据,会把旧名字当成不认识的东西 —— 两头都不报错,结论悄悄变了。所以:

- 删掉、改名、改类型、同一个名字改装别的意思,都给数据升版本;
- 删掉的字段名不再拿来装别的东西;
- 新代码读到旧版本,要么明着换算成新版本(换算本身有测试),要么拒收并说出是哪个文件、哪一版、该怎么办;
  不许当成新版本照读。

只加一个按第一件读得清的字段,不用升版本。

**三、版本标记。** 程序会读回来的数据,带一个读得出「哪种格式、第几版」的标记(格式名加版本号,或一个版本号字段)。

- 读的一侧只认它认得的版本,不认得的拒收,不猜。
- 读进来先整份对照这一版的格式说明判过(形状、版本、该有的字段),判过的才交给后面用;不要每个用到它的地方各判各的。
- 一个字段**是随升版本一起加的**、从那一版起写明每次都写,那一版的数据缺着它就是坏数据,照坏数据拒收 ——
  标记说明写它的那一版知道这个字段,缺着不再是「旧数据不知道」。没升版本就加进来的字段,同一版里新旧数据都有,
  缺着照第一件读,不能事后改口说「这一版每次都写」。
- 还没有标记的数据不用回头补。第一条需要分开新旧的改动(第一件里结论不一样的,或第二件)顺手加上。
  没有标记的当作最早那一版,前提是能确认它写于加标记之前:加标记那一版起,写的一侧每次都写标记、有测试守着,
  而且写下以后没有别的程序或手工去改它(改的时候可能把标记弄丢),没标记就只可能是更早写的。
  确认不了的(比如还有别的程序或手工写、改这份数据,不保证留着标记),没有标记的拒收,
  说出是哪个文件、为什么、该怎么办,不按最早那一版的意思硬读 —— 新数据丢了标记被当成旧版读,意思不同的字段会悄悄换算错。

**四、读法写在哪、测试核什么。**

- 每个字段缺着怎么读、各版之间怎么换算,写在架构文档里这份数据的对外契约旁边(`5-DESIGN.md`「必须装下的五类」第四类);
  改变用户看到的结论的,同时写进验收判据(那是改需求,照 `2-CHANGE.md` 走)。只写在 PR 正文或评审回复里不算:给测试上下文的准入读物清单
  (`4-VERIFY.md`)里没有它们,测试的期望推不出来。
- 测试拿一份按旧写法写的数据喂进去(拿得到旧版真写出来的样本最好),**逐条核**那条改动里写下的结论:
  哪些变成「我不知道」、哪些照旧。只核「没报错」不算 —— 那是一条从来不会失败的检查(`4-VERIFY.md`「判据的失效方式」)。
  再配一条变异,把「缺着」读成与写下的读法不同的那一档(写的是「我不知道」就改成「否」或零;写的是默认值就改成「我不知道」),看它红。
- 读的一侧拒收旧版本(或拒收没有标记的数据)时,测试拿一份那样的数据喂进去,核对拒收说出了哪个文件、哪一版(或为什么)、该怎么办;
  再配一条变异,让它不拒收或少说其中一样,看它红。

**五、靠什么守。** 字段缺着读成什么对不对、理由站不站得住,机器判不了,靠评审问一句:
**「这次加的、删的、改名的字段,旧数据里缺着时读成什么,写在哪,测了什么?」**(`README.md` 第三层那张表)。
「改了形状却没想到这一条」机器认得出:把这类数据的形状由类型生成一份快照放进仓库,检查拿当前类型生成的与快照比,
不一样就红,直到同一条改动里更新快照 —— 有的数据格式比对工具就是这么拦不兼容改动的。
快照由类型生成,只看得到类型说了的形状:不经类型、手拼出来写盘的字段,它看不到。
项目建没建这道检查、建到哪,写在项目自己的决策记录里;没建的,只靠评审那一问。

## UI 设计

### 设计的产物是什么

设计交付的不是一张图,是**一套可继承的东西**,分三层:

| 层 | 形态 | 怎么交到代码 |
|---|---|---|
| **token** —— 配色、字号、间距、圆角、阴影 | 一段 CSS 变量声明 | **原样复制**,不是照着调 |
| **构图** —— 布局、元素顺序、信息层级 | 画板 | 人看着实现,需要判断 |
| **行为** —— 交互、状态、数据 | 不在设计里 | 看需求文档 |

### 设计必须先于代码

如果先写代码再出设计,实现者会先发明一套配色,拿到设计后再换一遍。
**那一轮是纯返工,而且换色这类改动最容易换漏** —— 漏掉的那处会一直存在,
因为它看起来也不难看。

### token 靠结构保证,不靠事后对比

给实现的硬约束:

> **所有颜色、字号、间距、圆角只能取自设计的 token 变量。
> 代码里不允许出现字面的颜色值和魔法数字。**

这一条成立的话,实现和设计在 token 层**天生一致**,没有可以对不上的空间。

**能靠结构保证的,就别靠对比保证。**
对比是一次性的,做完就过期;结构是永久的,新写的代码自动服从。
这条原则不只适用于 UI —— 它是这整套方法的通用形状。

### 设计画板永远告诉不了你的一件事

**画板是用挑好的假数据摆出来的。**

真实数据是残缺的、长短不一的、有大量空字段的。
一个只在信息完整时好看的设计,在真实产品里是废的 ——
而这件事在设计评审时**完全看不出来**,因为评审看的就是画板。

所以:**每一套设计交付里,必须包含至少一张"信息最贫乏的那个实例"的画板。**
不是补充,是必需项。验收时**先看那一张**。

## UI 验收

token 层不需要验收(结构已保证)。真正要看的只有两样:

1. **构图与信息顺序** —— 在目标尺寸的真机上打开实现,和画板并排看。
   这一层没法机器判,也不该机器判
2. **真实数据下的样子** —— 用最残缺的那条真实数据渲染,和"信息贫乏"那张画板对比

对比时区分两种差异:

- **真差异** —— 顺序错了、该显眼的不显眼、空状态没按设计处理 → 改代码
- **假差异** —— 文字长度不同、条目数量不同、真实内容比示意文本长 → 不是问题,
  除非它把布局撑坏了

> ⚠️ **不要做像素级 diff。**设计画板和真实响应式页面之间,内容不同、高度不同、
> 数据长度不同,像素 diff 会产生大量假阳性,然后所有人开始忽略它 ——
> **一个被忽略的检查比没有检查更糟,因为它让人以为检查过了。**

## 给自动化实现者的额外提醒

如果代码由 AI 生成,下面几条是它最容易绕过纪律的路,值得预先堵上:

1. **它会在拿不到数据时生成"合理"的默认值。**因为训练数据里到处都是防御性编程。
   → 让那个默认值**写不出来**(改形状),或者直接断言产出物里「没查」「查过为空」「值就是零」还分得出来;
     扫写法是最后一档
2. **它会把"我做不到"表达成一个正常返回。**空数组、0、`null` 被当作"结果就是没有"。
   → 区分"没查到"和"查到了,答案是空",在类型层面就分开
3. **它会在汇报里把"工具修好了"说成"任务推进了"。**两件事必须分开说
4. **它提的变更请求,默认按「实现方便」处理**(见 `2-CHANGE.md`)
5. **它说"我跑过了"的时候,大概率没跑到那条最长的路径。**
   见 `4-VERIFY.md` 的「未执行的路径」
6. **它在记录、评审回复、提交信息里写的数字和「没有／全部／唯一／还剩」,
   来自扫了一眼的搜索,却用"我查过了"的语气写出来。** 第 5 条是路径没跑到,
   这一条是**关于工作的陈述**没查证:严谨用在了交付物上,没用在关于交付物的记账上 ——
   而后者往往是接手的人唯一的依据。一份少了一族的清单,会让照它开工的下一个人
   把那一族整个漏掉,直到更后面才重新"发现"它。
   → 句子里带数字或这类量词的,要来自一条**跑过、并把输出贴出来**的命令;
   贴不出输出,就把那句话删掉,或者改成"没查"。
   → 不像数的也算。**凡是列举就是清单,凡是清单就回去数正本**:并列的几样东西、
   「A 还是 B」、「N 处／N 种／N 类」、一个指向别处的行号,落纸之前回去对一遍它说的那份原文。
   只盯数字,「结论是采纳还是驳回」这种二选一的句子会漏过去 —— 而它说的那份原文里,结论可能
   不止两种。这两条都没有判据守着(第三层)

数据/结构校验 · 需求测试 · 变异测试 · 可执行文件的离线执行(`4-VERIFY.md`「未执行的路径」)· 链路审计

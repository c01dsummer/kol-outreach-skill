# 3 · 生成:代码与 UI

界面和代码是两种不同的产物,但它们受**同一类约束**,所以放在一份文档里:

> **生成环节不许发明。**
> 每一处产出都要能指回上游 —— 指回一条需求编号,或者指回设计里的一个 token。
> 指不回去的东西,就是这一环节自己发明出来的,而发明出来的东西没有人验收得了。

> 第三种产物是**架构文档**,它受的约束不同(它管的是零件之间,不是零件本身),
> 单独在 `5-DESIGN.md`。**动手改模块边界或调用顺序之前先读那一份。**

---

## 通用纪律

### 1. 一个任务 = 一个需求编号 = 一个能一次读完的 diff

超出就拆。**一个需要略读的 diff 等于没被审查过。**

### 2. 禁止顺手重构

改 A 就只改 A。想重构 B,单开一个任务。

顺手重构最大的问题不是风险,是**它让 diff 变得读不完**,
于是真正的改动藏在格式变动里,审不出来。

评审者要的也算顺手：评审中提出的重构、新行为、新跑法、新触发、新模块,另开一条 PR,
不在正被评审的那条改动里做,本 PR 里最多把它降级 —— 开关或删入口(`6-INTEGRATE.md`「评审中的发现」)。

### 3. 非平凡改动先出计划再写代码

改哪些文件、为什么、影响哪条需求。
**计划阶段发现错误的成本,比代码阶段低一个数量级。**

### 4. 审 diff 时,重点看它删了什么

**遗漏比错误更常见,删除比新增更难发现。**

新增的错代码会报错、会跑不通、会被测试抓到。
删掉的一个空值分支、一条校验、一句纪律注释,**什么都不会发生** ——
直到有一天它本该拦住的东西过去了。

规则:**diff 里每一处删除,都要能说清为什么可以删。**说不清就是不能删。
最好把它做成一个工具:自动列出 diff 里删掉的校验、空值分支、异常处理,逐条要求解释。

### 5. 通用最佳实践,有一部分在具体项目里是反的

这一条最容易出事,因为违反它的代码看起来**特别专业**。

典型的几条:

| 通用做法 | 什么时候是错的 |
|---|---|
| 防御性默认值 `x \|\| "未知"` | 信息类产品里,这是把"不知道"伪装成"知道" |
| 优雅降级 | 拿不到数据时降级显示,等于用旧的/假的数据冒充新的 |
| DRY 到底 | 两处相似但语义不同的规则合并后,改一处会误伤另一处 |
| 封装内部细节 | 需要可追溯性的产品里,来源信息必须能穿透到界面 |

每个项目要在自己的业务层文档里列出**「哪些通用最佳实践在这里是错的」**,
并且**尽量把它们变成 lint 规则** —— 因为默认会遵循它们的不只是人,
还有所有把最佳实践当先验的代码生成器。

散文里的纪律是期望,**能报错的检查才是保证**。

## UI 设计

### 设计的产物是什么

设计交付的不是一张图,是**一套可继承的东西**,分三层:

| 层 | 形态 | 怎么交到代码 |
|---|---|---|
| **token** —— 配色、字号、间距、圆角、阴影 | 一段 CSS 变量声明 | **原样复制**,不是照着调 |
| **构图** —— 布局、元素顺序、信息层级 | 画板 | 人看着实现,需要判断 |
| **行为** —— 交互、状态、数据 | 不在设计里 | 看需求文档 |

### 设计必须先于代码

如果先写代码再出设计,实现者会先发明一套配色,拿到设计后再换一遍。
**那一轮是纯返工,而且换色这类改动最容易换漏** —— 漏掉的那处会一直存在,
因为它看起来也不难看。

### token 靠结构保证,不靠事后对比

给实现的硬约束:

> **所有颜色、字号、间距、圆角只能取自设计的 token 变量。
> 代码里不允许出现字面的颜色值和魔法数字。**

这一条成立的话,实现和设计在 token 层**天生一致**,没有可以对不上的空间。

**能靠结构保证的,就别靠对比保证。**
对比是一次性的,做完就过期;结构是永久的,新写的代码自动服从。
这条原则不只适用于 UI —— 它是这整套方法的通用形状。

### 设计画板永远告诉不了你的一件事

**画板是用挑好的假数据摆出来的。**

真实数据是残缺的、长短不一的、有大量空字段的。
一个只在信息完整时好看的设计,在真实产品里是废的 ——
而这件事在设计评审时**完全看不出来**,因为评审看的就是画板。

所以:**每一套设计交付里,必须包含至少一张"信息最贫乏的那个实例"的画板。**
不是补充,是必需项。验收时**先看那一张**。

## UI 验收

token 层不需要验收(结构已保证)。真正要看的只有两样:

1. **构图与信息顺序** —— 在目标尺寸的真机上打开实现,和画板并排看。
   这一层没法机器判,也不该机器判
2. **真实数据下的样子** —— 用最残缺的那条真实数据渲染,和"信息贫乏"那张画板对比

对比时区分两种差异:

- **真差异** —— 顺序错了、该显眼的不显眼、空状态没按设计处理 → 改代码
- **假差异** —— 文字长度不同、条目数量不同、真实内容比示意文本长 → 不是问题,
  除非它把布局撑坏了

> ⚠️ **不要做像素级 diff。**设计画板和真实响应式页面之间,内容不同、高度不同、
> 数据长度不同,像素 diff 会产生大量假阳性,然后所有人开始忽略它 ——
> **一个被忽略的检查比没有检查更糟,因为它让人以为检查过了。**

## 给自动化实现者的额外提醒

如果代码由 AI 生成,下面几条是它最容易绕过纪律的路,值得预先堵上:

1. **它会在拿不到数据时生成"合理"的默认值。**因为训练数据里到处都是防御性编程。
   → 变成 lint 规则,而不是靠提醒
2. **它会把"我做不到"表达成一个正常返回。**空数组、0、`null` 被当作"结果就是没有"。
   → 区分"没查到"和"查到了,答案是空",在类型层面就分开
3. **它会在汇报里把"工具修好了"说成"任务推进了"。**两件事必须分开说
4. **它提的变更请求,默认按「实现方便」处理**(见 `2-CHANGE.md`)
5. **它说"我跑过了"的时候,大概率没跑到那条最长的路径。**
   见 `4-VERIFY.md` 的「未执行的路径」

## 提交前

跑项目自己的 `check`,红了自己修。检查链至少要包含:

纪律 lint · 数据/结构校验 · 需求测试 · 变异测试 · 脚本自检 · 链路审计

**这些必须能一条命令跑完,而且必须跑在 CI 上。**
只在本地靠自觉跑的检查,执行率会随时间趋近于零。

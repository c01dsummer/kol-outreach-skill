# 1 · 需求怎么定义

**需求文档是唯一来源。**架构、UI、代码、测试、验收全都依赖它,并且**引用它的编号**。

散文负责解释为什么,编号负责定义是什么。
没有编号,「代码是否实现了需求」这个问题无法回答 —— 只能靠印象,而印象会变。

---

## 编号

每条需求有一个**稳定编号**。编号一旦发出去就不再改含义;
需求作废时保留编号并标记作废,**不要回收复用** —— 复用会让历史记录指向错误的东西。

编号分类由项目自己定,但**必须至少有一类是红线**。常见的分法:

| 前缀 | 类别 | 特征 |
|---|---|---|
| `P` | 红线 | 不参与任何取舍 |
| `S` | 范围 | 明确不做什么 |
| `D` | 数据 | 结构、取值、约束 |
| `U` | 展示 | 界面与交互 |

> **编号命名空间不许撞车。**决策记录用 `ADR-01`,数据需求用 `D1` ——
> 如果决策记录也用 `D-01`,读者会读不清 "D2" 指的是哪个。开头就把前缀分开。

**编号的前缀就是它的分类,两者必须一致,而且要能被机器检查。**
下游(渲染、审计、覆盖统计)全都按分类分流:一条需求的分类填错 ——
哪怕填的是另一个**合法**分类 —— 它就被当成另一类需求。
最坏的情况是一条红线被挪出红线组:强制「每条红线都要有测试和变异」的那道检查
从此不管它,而报告里的红线条数会比你声明的少一条,然后全绿通过。

### 一条需求长什么样

```json
{
  "id": "D3",
  "cat": "D",
  "pri": "P0",
  "text": "一句话说清要什么。不解释为什么。",
  "accept": [
    { "id": "D3.a", "text": "怎么算满足了 —— 必须是可以被判定的,不是形容词" },
    { "id": "D3.b", "text": "另一件能被独立判定、也能被独立弄坏的事" }
  ],

  "adr": ["ADR-07"],
  "tension": [
    { "with": "P2", "ruling": "撞上时以谁为准,写结论", "adr": "ADR-07" }
  ],
  "deprecated": { "since": "2026-01-01", "why": "为什么不做了", "superseded_by": "D9" }
}
```

**`accept` 写不出来,说明需求没想清楚。**"体验流畅"不是验收标准,
"从打开到看到结果不超过四次交互"是。

### 验收标准是**一组判据**,不是一段话

一段话里的「与」「且」「同时」,**在计量上是一条,在事实上是两条**。

后果不是"记录不够细",是**覆盖率会虚报**:一条需求报「有测试」,而它验收标准的
后半句可以从来没有实现过 —— 那半句还可能是一条红线的承重结构。
这不是假想,是踩出来的(见项目的决策记录)。

所以:

- `accept` 是一个**列表**,每项一条可独立判定的判据
- 每条判据有自己的**稳定编号**(`{需求编号}.{字母}`),规矩与需求编号一样:
  **不改含义、不回收复用** —— 下游按它认领覆盖,含义一变认领就指向了别的东西
- **计量单位是判据,不是需求。**红线的每一条判据都要能被单独指认;
  指认不了的,按缺口显式登记(连同"那它靠什么守着"),不要靠整条需求的✓ 蒙混过去

**拆到多细?判据只有一条:**

> **这两半会不会被不同的代码路径独立满足、或者独立弄坏?**

会 → 拆成两条。不会(同一个函数同一个分支产出的)→ 留成一条。

机械地按标点切会造出一堆没有独立含义的碎片,那和不拆一样没用 ——
**拆分的目的是让"漏掉一半"变得看得见,不是让条目变多。**

后三个字段是可选的,各解决一个具体问题:

| 字段 | 回答什么问题 |
|---|---|
| `adr` | **这句话是哪次决策的结果。**决策记录里的「冲击的需求」是正向链接,回答不了这个 —— 只列**塑造了这条文本**的,不列所有提到它的 |
| `tension` | **这条与哪条在某个交点上互相拉扯,撞上时以谁为准。**见下 |
| `deprecated` | **作废,但编号保留。**回收复用会让历史记录指向错误的东西 |

### 交点要写进登记表,不能只写在散文里

两条需求各自都对、各自都有测试、各自都通过检查,而它们**在交点上不能同时成立** ——
这是最难发现的一类错,因为**交点不属于任何一条需求**:

> 检查是逐条来的("每条需求有没有测试"),所以交点上的测试**写了不加分,
> 不写不扣分**。计量决定行为 —— 靠提醒守不住,只能让交点在计量里有位置。

所以:

- 交点**声明在让步的那一方**(通常是非红线那条)。两边各写一遍,迟早出现两种说法
- `ruling` 写**结论**,不写"需要讨论"。红线在场时结论已经确定,只是把它写下来
- 裁决落在哪条决策记录里就填 `adr`;裁决写在别处(比如约定文档)的可以不填,
  但 `ruling` 里要说清楚在哪
- **交点里有红线的,必须有测试** —— 这是红线第 2 条硬要求的自然延伸。
  测试怎么认领一个交点,由项目自己定一个机器查得到的标记

裁决怎么做、什么时候要找人拍板,在 `2-CHANGE.md`。

### 机器可读是硬要求

需求登记表必须有一份**机器可读的版本**(json / yaml 均可),它是编号的唯一真相来源。
人类可读的需求文档是它的渲染。**两者不一致时以机器版为准,并当场修文档。**

理由:审计要能自动回答"每条需求在下游被引用了吗"。人读文档做不到这件事,
而做不到的结果不是"漏一点",是**没人知道完成度是多少**。

### 登记表里的元数据要么是派生的,要么删掉

版本号、最后修改时间这类字段,**手工维护的一律会烂**:改需求时忘记改它不会报错,
而症状与"需求没改过"一模一样。

两条路,没有第三条:

- **派生** —— 由回写工具写、由检查校验(比如一个覆盖需求内容的指纹)。
  没有任何人需要记得改它,手改需求而不回写当场变红
- **删掉** —— 一个没有消费者、也没人维护的字段是纯负债:
  它唯一的作用是提供一个出错的地方,而且出错时不报警

> 判据和整套方法的第二层原则是同一条:**散文里的纪律是期望,能报错的检查才是保证。**

## 红线机制

每个项目必须定义自己的红线。**红线不是"很重要的需求",判据是这两条同时成立**:

1. **违反的代价由用户承担**,不是由团队承担
2. **不可逆** —— 用户不会给第二次机会

举例这个判据怎么用:性能差是重要需求,但用户会再试一次,不是红线;
给用户一条错误信息导致他白跑一趟,是红线。

### 红线的四条硬要求

1. **不参与 trade-off。**任何变更请求只要触碰红线,直接驳回,不进入权衡
2. **每条红线至少一个测试**
3. **每条红线至少一个变异** —— 一个"故意违反它"的代码改动,
   必须能让对应的测试失败。做不到的话,那个测试不能证明任何事(见 `4-VERIFY.md`)
4. **新增红线时,测试和变异同时加**,不能留到下次
5. **红线不许作废。**作废机制会把一条需求挡在现行需求表与审计之外 —— 于是红线条数
   静静少一条,它的测试、变异、交点要求全部随之消失,而检查报「全部通过」。
   作废一条红线的意思是「这个代价用户不再承担了」,那是**产品定义变了**,
   该走变更评定并留下决策记录,不是给一条需求加个字段

> 红线的数量应该很少 —— 一只手数得过来。
> 如果红线有十几条,那说明其中大部分不是红线,是重要需求。
> **红线多到需要查表,它就失去了"不用想就知道不能碰"的作用。**

### 新增或修改一条需求时,只查它与红线的交点

两条需求可以各自都对,却在某个交点上不能同时成立。全部两两查是 n²,
没人做得到,做了也会流于形式。

**但和红线的交点必须查,而且很便宜** —— 红线只有几条,这是常数次检查。
而且红线是全序最高的,交点的结论**已经确定**,不需要讨论,只需要把它写下来。

写法:在这条需求的验收标准里点名它跟哪条红线相接、相接时以谁为准。
写不出来,说明这条需求还没想清楚它在极端情况下要什么。

> 剩下那一半(非红线之间的交点)提前想不出来,也不该硬想 ——
> 等它在实现或评审时撞出来,按 `2-CHANGE.md` 评定。

## 验收标准

每条需求的验收标准,必须满足:

- **可判定** —— 两个人分别看,结论一样
- **可失败** —— 存在一种明确的情况会让它不通过。永远通不过和永远通得过一样没用
- **指名编号** —— 验收清单上每一项后面标着它验的是哪条**判据**(不是哪条需求)
- **可独立** —— 一条判据里不该藏着两件能分别成立、分别失败的事(见上一节)

### 允许写"做不到",不允许写"应该可以"

调研、探测、可行性验证这类环节,产物是**结论**,不是"进展"。

- ✅「做不到,原因是 X」—— 这是结论,下游可以据此决策
- ✅「能做到,证据是 Y」—— 这是结论
- ❌「应该可以」「看起来没问题」「理论上支持」—— **这不是结论,是把不确定伪装成确定**

一条"应该可以"混进结论,下游会按"可以"去做架构决策,
而这类决策的成本往往差一个数量级。

## 需求文档里不该有什么

- **不要有实现方式。**"用 Redis 缓存"是架构决策,不是需求。需求是"重复查询不应重复计算"。
  **这条不是洁癖** —— 需求里夹带的实现方式,会替下游把一个本来有几种解法的问题
  锁死成一种。万一锁死的那种恰好和红线冲突,下游是照着需求写的,**没有人会觉得
  自己写错了**,而检查也不会红:两条需求各自都被满足,冲突只在它们的交点上
- **不要有通用工程纪律。**"要写单元测试"属于通用层,写在需求里是噪音
- **不要有分期与排期。**那是计划,不是需求。计划变得比需求快得多,混在一起会让需求看起来也不稳定
- **不要有"暂定""待确认"而不标出来。**不确定的需求要么标明不确定并给出确定它的办法,
  要么先不写进登记表。**登记表里的每一条都是已经决定的**

---

## 什么时候需求算写完了

不是写满了页数,是下面四条同时成立:

- [ ] 每条需求有编号、优先级、一句话描述、可判定的验收标准
- [ ] 红线单独成组,且每条都通过了上面那两条判据
- [ ] 机器可读版本存在,且和文档一致
- [ ] 明确写出了**不做什么**(范围边界)—— 只写做什么的需求文档,
      会在实现时被一点点扩大,而每扩一点都是新的错误来源

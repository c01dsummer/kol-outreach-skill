# 6 · 改动怎么合回主干

前面五份管的是「一个需求怎么走到可验收的成品」。这一份管**最后一步**：
那个成品怎么回到主干,以及在这条路上不许做什么。

它以前不存在,代价是可见的：整个流程可以每一步都合规,最后堆成一个
没人读得完的合并单元 —— 而所有的检查都是绿的。

---

## 一条长期分支

主干只有一条,它**必须永远处于可发布状态**。其余分支都是短命的：
开出来,过检查,合回去,删掉。

**一个任务可以开多条分支、多个 PR。** 会话或工具给的「指定分支」是起点,不是上限：
一个证据问题一条分支一个 PR(见下面「怎么切」),对主干开,合了再开下一条。
把两个证据不同的改动捆在一条分支上,理由不能是「任务只给了一条分支」——
在指定分支名后面加个后缀开出去就是了(本仓库：ADR-64)。

**叠分支:直接叠在一条没合的分支上开出去。** 下面那条分支的提交就在这条的第一父链上,
它那些新增行会算进这条的体量,它那句 `size-ok:` 也会被这条捡到 —— 提交图分不出
「叠上去」和「这些提交本来就是我写的」。叠分支本来就是这条纪律要劝退的东西 ——
先把下面那条合了。

**分支活得越短越好,但这件事不再有闸门看着**(2026-09-18 撤掉,见 ADR-76)。
下面那几条理由仍然成立,它们现在靠人执行:

分支的寿命是这套方法里唯一一个「越短越好、没有下限」的量。理由不是洁癖：

- **长命分支真正的成本不是解冲突,是延迟发现的冲突。** 语义上的冲突要等
  两周后合并才暴露,而那时两边都已经在错误的假设上又盖了十几层
- **评审线程会随着分支老化而作废。** 见下面「只追加」那一节
- **主干停滞本身就是告警。** 主干几天不动、外面挂着几条大分支,
  说明集成已经不是流程的一部分了

---

## 怎么切：按验收证据切,不按逻辑依次加强切

一个改动常常长成「三层依次加强的保证」：第二层比第一层更强,第三层又比
第二层更强。于是它看起来必须捆在一起走。

**判据不在这里。判据是证据：**

> **一个改动只回答一个「怎么证明它对了」的问题。
> 两段代码要写两种不同的证据来证明它们对,它们就是两个改动。**

一段靠单元断言证明、一段靠崩溃点注入证明、一段靠端到端产出物证明 ——
这是三个改动,哪怕它们在逻辑上依次加强。依次加强只说明**合并顺序**,
不说明它们该在同一个合并单元里。

判据好用的地方在于它当场就能问出口,不必等到事后清点。而事后清点是有代价的：
一个装了三件事的改动,其中一件「声称做到了、其实没做到」时,
另外两件的正确性会替它背书 —— **一句假话搭着两句真话一起合入**,
是这类改动最典型也最贵的失效方式。

### 未完成的东西靠开关,不靠分支

「还没做完所以不能合」几乎总是假的。可以合的做法有三种,都比拖着分支便宜：

| 做法 | 怎么用 |
|---|---|
| **开关** | 新路径挂在一个默认关闭的开关后面,合进主干;翻默认值是另一个改动,通常一行 |
| **抽象层** | 先把调用点收敛到一个接口,再在接口后面换实现 |
| **最后一块砖** | 实现先进主干,**入口最后接上**。没有入口的代码不改变任何行为 |

判别一句话：**「代码合进去了」和「功能对用户可见了」是两件事。**
把这两件事绑在一起,就只剩下拖分支这一个选项。

## 体量：有阈值,不靠自觉

「一个改动 = 一个能一次读完的 diff」这条纪律,长期写在 `README.md` 的
**第三层**(只能靠自觉),理由是「『能一次读完』没有阈值」。

现在有了。阈值分类计,超线即红,豁免必须具名：

- **分类分开算**,不合并成总数 —— 否则源码的超标会被大段文档稀释掉,
  而那正是最该被拆开的情形
- **只数新增行** —— 删除便宜,而且按删除量收费会惩罚重构
- **量的是分支相对主干的全部新增**,不是单个提交。评审、冲突、线程失效
  都按合并单元结算;按提交结算会得到一个永远合格的漂亮数字
- **豁免写在提交信息的最后一段**(trailer 块,和 `Co-Authored-By:` 同一段),
  格式 `size-ok: <类别> <理由>`:必须指名类别(不指名会把所有类一起放行),
  理由必填。它进历史、进评审视野,不会被忘记删

  > 只认最后一段,是为了让正文能**放心讨论这个语法** —— 举例、贴反例、写围栏块,
  > 怎么写都不会被当成指令。反过来扫整个正文的话,就得没完没了地枚举
  > 「什么不是指令」,而那条路走不到头。

阈值定在哪不重要,**有阈值才重要**。它的作用不是拦住谁,是让「这该不该是
第二个改动」这个问题在写第 301 行时被问出来,而不是三天后由一条事后的
决策记录来拆。

> **提交之前跑的那次检查,量的是上一次提交。** 闸门只数已提交的东西
> (工作区不计),所以 `git add && npm run check && git commit` 这个顺序里,
> 闸门看到的是**这次改动还没进去**的状态 —— 全绿地提交,推上去 CI 才红。
> 想先知道数,提交完再跑一次 `npm run size`,再决定要不要补一条豁免。
> 这不是闸门的毛病:未提交的工作区随时会变,量它得到的数没有意义。

> 阈值该按**本项目已合并的改动**校准,不是拍脑袋 —— 满屏假阳性的检查会被忽略,
> 而被忽略的检查比没有检查更糟。

---

## 评审中的分支：只追加提交

**不要 rebase、amend、force-push 一条正在被评审的分支。**
要同步主干就 merge 进来。合并时 squash,最终历史一样干净。

> squash 发生在**合并那一刻**,不是在分支上。在分支上压成一个提交,
> 等于把历史整个替换掉 —— 线程照样失效,而且体量闸门的 `size-ok:` 行
> 也会跟着丢掉,那条改动一旦被重新量就会红。

理由是可量化的：评审线程锚在提交与行号上,历史被替换之后它们集体失效 ——
指向的提交不再存在,意见得重新提一遍、重新答一遍。一次这样的失效,
成本是整轮评审重来。

同理,**不要在别人的分支上改写历史**：merge 保住对方的检出,rebase 不会。

---

## 评审中的发现：分档路由,从第三轮起只登记

上一节定下的是怎么改历史,却隐含地把每条评审发现都定成了「修在这条 PR 里」。
没有别的出口时,一条开出来在线内的 PR 会在评审里长到开 PR 时的几倍：每一条修补都合规,
每一次 push 都换来下一轮评审,而机器评审永远不会说「可以合了」。事实与数字在本项目
关于评审膨胀的那条决策记录里(本仓库：ADR-64)。

**出口要写出来,否则默认就是唯一出口。**

### 先定义「一轮」

**一轮 = 锚在 PR 同一个 head 上的全部评审意见**,不分机器或人、不分几个评审者;
按意见锚定的 head 算,不按它提交的时间算。开 PR 时那个 head 上的是第一轮。
同步主干的合并提交、只为换 head 的空提交,不起轮 —— 锚在这种 head 上的意见算进上一轮。

**一轮里有哪些意见,按评审者给的清单点,不按自己看到的那几条点。** 有的评审工具会把一部分
发现「抑制」掉:它们只出现在评审正文里,**不生成可回复的讨论串**(本仓库:机器评审的
suppressed comments 就是这样,连着两条 PR 漏在这里)。按讨论串列意见,漏掉的那部分
**看起来根本不存在**,而下一节「每条都要回、都要 resolve」照样显示执行完毕 ——
一条纪律只覆盖了你收得到的那一部分,却报告成覆盖了全部。

**没有讨论串的那些,用一条普通 PR 评论当替身。** 一条发现一条评论,开头点名它在评审正文里的
位置(文件 ＋ 行),第一行照样按下一节写档与去向。评审工具不认这条评论,所以它永远不会被
标成 resolved —— 它的作用是让这条发现在 PR 上留下**可检索的去向**,合并者按评审正文里那份
清单逐条去对。**只数清单不留替身,等于把这条发现记在了没人会去翻的地方。**

### 五档路由

每条评审发现,作者在回复的**第一行**按固定写法写档和去向(没有讨论串的那些,「回复」就是
上一节说的那条替身评论,格式一样)：

```
档：本改动 · 去向：<修它的提交或反向提交>
档：本改动(第 N 轮,不阻塞) · 去向：登记 · 重启条件：<条件>
档：扩范围 · 去向：<另开的 PR,或「合入后开」>
档：既有缺陷 · 去向：<另开的 PR,或「合入后开」>
档：登记 · 重启条件：<条件>
档：驳回 · 理由：<为什么不成立>
```

| 档 | 判据 | 去向 |
|---|---|---|
| **本改动** | 指向的是这条 PR 自己写的内容,不限于正确性错。修法要碰开 PR 时 diff 里没有的文件(补一条测试、改一处工作流、改一句契约文档)照样是本改动;本 PR 让一个老错从不可达变可达、从无害变有害的,也算 | 前两轮：本 PR 追加提交修,修完、线程指向那个提交后 resolve。第三轮起且不阻塞：登记 |
| **扩范围** | 要求新行为、新跑法、新触发、新模块,或重构 —— 以提交信息声称做到了什么为准,PR 描述能改、不起轮 | 那个行为不在本 PR 做。本 PR 只允许一种改动：用开关或删入口把它**降级**(这条提交让 diff 变小,不受轮次限制);行为本身另开 PR,写清去向后 resolve |
| **既有缺陷** | 不是本 PR 引入的正确性错,主干上不合这条 PR 也一样坏 | 另开 PR。会让检查说假话或让主干不可发布的,走「主干红了」：立刻从主干开、就地修或回滚、立刻合,不受下面并行三条的限制,当前 PR 等它合了再把主干合进来;其余当前 PR 合入后排最前。写清去向后 resolve |
| **登记** | 不在本 PR diff 里的措辞、文档、判断力收紧,且不是正确性错 | 写下重启条件,resolve;欠条进仓库见下 |
| **驳回** | 发现不成立 | 回复里写为什么不成立,然后 resolve。同一条之前驳回过的,指向那次;涉及规则本身的,档改写为登记,走欠条 |

档按「错是谁引入的」分,不按「修法碰了哪些文件」分。沾边时按 本改动 > 扩范围 > 既有缺陷 > 登记
取靠前的;唯一的例外是本改动与扩范围都沾边 —— 本 PR 引入的错,正确的修法却要一个新模块 ——
那按阻塞项的两种处理：最小修补或 revert,扩出来的那部分另开。

评审工具给的严重级别不等于档 —— 一条标着「普通」的发现也可能是正确性错,分档按内容。
**合入之后才到的意见没有本改动档**：正确性错按「主干红了」或既有缺陷另开,其余按登记,不成立的按驳回。

**「禁止顺手重构」(`3-BUILD.md`)从这里起也管评审回应。** 评审者要的重构和作者顺手的重构,
对 diff 来说是同一件事：都让它变得读不完。

### 从第三轮起只登记,阻塞项除外

从第三轮起到达的新发现,分档照旧;**本改动档里不阻塞的那些不再修,改走登记。**
PR 停在当时的 head,检查绿就合。前两轮在 PR 里修完的是健康的;这条只拦没有出口的回路。

**阻塞项不受轮次限制**：本改动档里的正确性错、触碰红线的、安全问题,不论第几轮都要处理完才能合 ——
评审发现常常指向检查链没覆盖的行为,「检查绿」不等于「没有已知的坏」。处理只有两种：

- **最小修补**
- **revert**：用 `git revert <sha>` 追加一条反向提交把引入它的那个提交撤掉(评审中不改写历史,
  见上一节);反向提交不写 `size-ok:`。引入它的就是开 PR 那个提交时,revert 等于
  关掉这条 PR —— 那就关掉,另开一条更小的,把 PR 描述末尾那份索引原样搬过去,被关掉那条的
  推迟项由新 PR 的合入触发

不许借阻塞项扩范围。回路的出口在这里：revert 让 diff 变小,登记让 diff 不变,只有扩范围会让它变大。

### 合并者核对去向

**合并者不能是写档的那一方。** 作者自己合的 PR 只能含前两轮修在本 PR 的本改动档(扩范围的降级算在内);
有别的档就得等第二个人读完。

合并前展开全部已 resolve 的线程;**再按每一轮评审正文里的「被抑制」清单逐条找到对应的那条
替身评论** —— 那一类发现只在那里留痕,漏看它等于漏掉一整类,而线程全绿照样成立。
(作者在 PR 描述末尾维护一份「不修在本 PR 的发现」索引,含驳回;那只是目录,不是登记处。)按档核：

| 档 | 合并者核什么 |
|---|---|
| 本改动,前两轮 | 线程指向修它的提交或反向提交。**阻塞项没指向提交的不合** |
| 本改动,第三轮起写了「不阻塞」 | **是不是阻塞项由合并者判,不由作者判** |
| 扩范围 | 它要的确实不在这条 PR 的提交信息声称的范围内 |
| 既有缺陷 | 主干上不合这条 PR 也一样坏 |
| 登记 | 不在本 PR diff 里,不改行为,不是正确性错 |
| 驳回 | 理由成立 |
| 上一条合入的 PR | 它若有推迟项,欠条已在主干上(见下) |

不认可就**打回**：把那条线程 unresolve,回一句合并者判的档。判为阻塞的按上面两种处理;
判为扩范围或既有缺陷的,作者改写去向后再 resolve;判为不阻塞的本改动,按当时的轮次走。
打回之后作者不再驳回,异议走决策记录。

第二个人只读被推迟的那些。豁免自批的价格为零,正是因为理由没有第二个人读;只核「有没有档」
会把同一个漏洞原样搬到路由上。推迟得越多,合并前要读得越多,这个代价是故意的。

### 登记怎么做：欠条 PR

登记不是「留个线程」。合并闸要求线程全部 resolve 时,留着不 resolve 的线程挡的是自己;
**resolve 表示「已有去向」,不表示「修了」。**

1. 回复第一行写档、去向和重启条件,然后 resolve
2. **本 PR 不为登记再 push** —— 为登记换 head 会再起一轮,回路就又开了。本来就要为阻塞项或
   降级 push 的,欠条可以搭在那次提交里;搭进去的那些欠条 PR 里不再重复,全部搭进去了就不必开
   欠条 PR,下一条 PR 的合并者按「欠条已在主干上」核
3. **合入后作者开的第一条 PR 是欠条 PR**：只追加 `⚠️` 块或新开一条只装欠条的记录,不改既有内容,走「什么不走这套」直接合。
   不修在本 PR 的每一条发现(驳回除外)各一行：

   ```
   > ⚠️ 欠条：<缺的是什么> · 重启条件：<条件>
   ```

   落在主干上已有的哪条决策记录,按顺序：被指出的那件事已有记录的,追加进那条;本 PR 自带记录的,
   写进那条;都没有的,按 `2-CHANGE.md`「接受为已知缺口」开一条,同一条 PR 的多条合在一条里。
   扩范围与既有缺陷的重启条件就是「本 PR 已合入」;还上时在下面再追加一块。
   「定期清点」清点的就是这个标记,接手的会话读的也是它,不必翻线程
4. 重启条件通常是三种之一：下次有改动碰到那个文件、同一缺口再被点名、定期清点

项目路由文件里若有一张「已知缺口,不要试图消灭」的表,它**不是**登记处 —— 表头就写着不要消灭,
放进去的东西天然没有重启条件。写不出重启条件的登记不是登记,是免责声明。

### 另开 PR 的,合入就做

扩范围与既有缺陷两档由当前 PR 合入触发：欠条 PR 先,然后串行做 —— 开一条、检查绿、合、再开下一条。
顺序：既有缺陷在扩范围前;各自里面,会让检查静默给出错误结论的在前(比如输入读不到时退回一个
看起来正常的值)。

合并前**不从这条 PR 的 head 上开**：那是叠分支,下面那条的提交会跟着进来,体量和它那句 `size-ok:` 也跟着进来
(见上「叠分支」)。从主干开出的(第一父链上没有当前 PR 的提交)只在三条都满足时才开：
不碰当前 PR diff 里的文件(防冲突)、在主干上自己就能全绿(防依赖)、开它的人说得出为什么等不到合入
(防绕过串行)。合并者核它的 head 不含当前 PR 的提交,以及文件清单。
让主干不可发布的既有缺陷不在这三条之内 —— 那是「主干红了」,红灯优先于任何进行中的工作。

### 闸门自身走「最后一块砖」

入口已经接进检查链的闸门,每个洞都是主干上一条在说假话的检查。入口已在主干上的,按「主干红了」
就地修;入口还在本 PR 里没合的,处理就是扩范围档那一种降级 —— **把入口拆下来**,跑法、触发另开 PR,
最后一条再接回去。本仓库那两道闸门(体量,以及已经撤掉的分支寿命)出生时都没这么做,各长到两倍多,事实见同一条决策记录。
所以新加一道闸门,判定模块、测试、变异先合,最后一条 PR 才把它接进检查链。

---

## 主干红了

主干必须永远可发布,所以红灯优先于任何进行中的工作。**就地修,或者回滚。**

- 回滚不是失败,是把主干还给所有人的最快手段
- 「先红着,我下午修」等于让所有人在一个坏掉的基线上工作
- **跳过、禁用、隔离一个测试,永远不是让检查变绿的办法**

前提是检查本身要快而可信。检查跑一次要十几分钟,攒着一起提就成了理性选择 ——
那时该修的是检查,不是纪律。

---

## 决策记录先于实现合

决策记录只追加、彼此独立、不依赖任何代码,所以它**可以单独先合进主干**。

这不是省事,是把一个改动里最大的一块从关键路径上挪走：论证、裁决、驳回
往往比实现本身长得多,而它们一行也不需要等实现。

先合的另一个好处是编号早点固定下来 —— 编号不复用,**允许有空号**,
包括那些还活在别的分支上、没合进来的号。

---

## 什么不走这套

一次提交就能说清、检查全绿、且不触及需求登记表的改动,直接合。
这一份和前面五份一样,防的是悄悄侵蚀,不是给每次提交加手续。

---

## 这一层里,什么是机器保证的

按 `README.md` 的三层分法：

| 纪律 | 哪一层 |
|---|---|
| 体量不超阈值、豁免必须具名 | **第二层**(`size` 检查) |
| 决策记录编号唯一、不装回整册 | **第二层**(`adr` 检查) |
| 主干可发布 | **第二层**(检查链 + CI) |
| 一个改动只回答一个证据问题 | 第三层 —— 「同一个证据」没有判据 |
| 评审中不改写历史 | 第三层 —— 可以查,但正当的改写也存在 |
| 评审发现的档与去向 | 第三层 —— 档由作者自填,没有判据 |
| 合并者读了被推迟的发现、判了阻塞 | 第三层 —— 读没读、判没判,没有检查看着 |
| 从第三轮起只登记 | 第三层 —— 轮次没有检查在数;把一批修补拆成几次 push 就能把轮次数快,靠合并者看 |
| 欠条 PR 带上了每一条推迟项 | 第三层 —— 线程与欠条之间没有检查对账 |

**第三层的这几条不要假装被保证了。** 体量闸门能挡住 400 行的改动,
挡不住一个 340 行、同时改了三件互不相干的事的改动 ——
它保证的是上限,不是内聚。

**分支寿命这一条走完了一个来回**:先写在第三层,理由是「该不该红是人的判断」;
后来提到第二层,理由是「闸门本来就有一条给判断用的通道:具名豁免」(ADR-59);
2026-09-18 整个撤掉,理由是它一次真红都没抓到过,而它的豁免有一半是别的规矩
制造的等待(ADR-76)。**具名豁免那条通道成立,但它只能保证理由被写下来,
保证不了那条理由值一次红。**

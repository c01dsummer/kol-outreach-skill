# 全流程约束 · 总则

**这一套文档和任何具体产品无关。**它规定的是:一个需求怎么从想法走到可验收的成品,
以及在这条路上,每一步各自不许做什么。

把整个 `process/` 目录复制进任何新项目就能用。项目自己的需求写在别处(见「两层」)。

---

## 为什么要分两层

一份文档里如果既写着「变更请求怎么评定」,又写着「步行时间禁止估算」,会出两个问题:

1. **复用不了** —— 下一个项目想用这套方法,得先把业务规则一条条剔出去
2. **更糟:读的人分不清哪条可以商量** —— 通用纪律是方法论,可以随经验演进;
   业务红线是这个产品的生死线,不能碰。混在一起,两种都会被当成"建议"

所以:

| 层 | 装什么 | 谁写 | 变动频率 |
|---|---|---|---|
| **通用层** `process/` | 流程、纪律、评定办法、验证手段 | 一次写好,跨项目复用 | 很低 |
| **业务层** `docs/` | 这个产品要什么、红线是哪几条、验收怎么算 | 每个项目自己写 | 高 |

**业务层引用通用层的规则,不复述它。**业务层里出现的每一条规则,都必须是只属于这个产品的。
如果一条规则换个产品也成立,它写错地方了。

## 环节与依赖

```
        ┌──────────────────────────────────────────────┐
        │                  需求文档                      │  ← 唯一来源
        │        编号 · 优先级 · 验收标准 · 红线          │
        └──────────────────────────────────────────────┘
             │            │           │           │
      ┌──────┘      ┌─────┘     ┌─────┘     ┌─────┘
      ▼             ▼           ▼           ▼
  ┌───────┐    ┌────────┐  ┌────────┐  ┌────────┐
  │架构设计│    │ UI 设计 │  │测试用例│  │验收标准│
  └───────┘    └────────┘  └────────┘  └────────┘
      │             │           │           │
      └──────┬──────┘           │           │
             ▼                  │           │
       ┌──────────┐             │           │
       │ 代码实现  │◄────────────┘           │
       └──────────┘      测试先于/独立于实现   │
             │                               │
             └───────────────────────────────┘
                          验收
```

**依赖方向只有一个:向下。**下游引用需求编号,上游不知道下游存在。

**唯一的例外是反向输入** —— 下游在干活时撞见需求文档有错或代价远超假设。
这种情况不允许在下游被悄悄消化掉,必须走 `2-CHANGE.md` 的评定。

> 这张图保证的是**纵向**不漂移,它对**横向**什么也没说。
> 同一层的两条需求可以各自都对,却在某个交点上不能同时成立 ——
> 而那个交点**不属于任何一条需求**,所以逐条来的检查(测试、变异、审计覆盖率)
> 全都看不见它:写了不加分,不写不扣分。
>
> 提前挡住一半的办法在 `1-REQUIREMENTS.md`(只查与红线的交点),
> 撞出来之后怎么办在 `2-CHANGE.md`。

### 每个环节的输入与产物

| 环节 | 输入 | 产物 | 约束在哪 |
|---|---|---|---|
| 需求设计 | 调研、观察、决策 | 编号化的需求文档 + 机器可读登记表 | `1-REQUIREMENTS.md` |
| 架构设计 | 需求编号 | 架构文档,每处实现标注服务哪条需求 | `5-DESIGN.md` |
| UI 设计 | 需求编号 + 界面需求 | 设计画板(HTML/CSS)+ 可继承的 token | `3-BUILD.md` |
| 代码实现 | 需求编号 + 架构文档 + 设计 + token | 代码 | `3-BUILD.md` |
| 测试实现 | **只有需求编号和验收标准** | 测试 | `4-VERIFY.md` |
| 测试覆盖 | 测试 + 红线清单 | 变异集 | `4-VERIFY.md` |
| 需求验收 | 全部 | 审计报告 | `4-VERIFY.md` |
| UI 验收 | 设计画板 + 实现 | 差异清单 | `3-BUILD.md` |
| **集成** | 通过验收的改动 | 合进主干的提交 | `6-INTEGRATE.md` |

注意测试那一行:**输入里没有代码。**这不是疏忽,理由见 `4-VERIFY.md` 的「同源污染」。

## 六份文档

| 文件 | 管什么 | 什么时候读 |
|---|---|---|
| `1-REQUIREMENTS.md` | 需求怎么定义、编号、红线机制、验收标准怎么写 | 写需求文档前 |
| `2-CHANGE.md` | 反向输入与需求冲突怎么评定、**哪些必须找人拍板**、决策怎么记、文档怎么同步 | 想改需求时,撞见两条需求打架时,以及每次想说"这个太麻烦"时 |
| `3-BUILD.md` | 代码和 UI 怎么生成、生成者的已知失效模式 | 动手写之前 |
| `4-VERIFY.md` | 测试、覆盖、审计、验收 | 写测试前必读 |
| `5-DESIGN.md` | 架构文档写什么、必须先于代码、靠锚点不漂移 | 改模块边界或调用顺序前 |
| `6-INTEGRATE.md` | 改动怎么切、怎么合回主干、体量闸门、评审发现怎么路由 | **开分支时、回应评审时,以及每次想把一个改动做大时** |

还有 `AGENTS.md.tpl` —— 复制到新项目根目录改成 `AGENTS.md`(再放一个转发过去的
`CLAUDE.md`),它负责把上面那几份接进去。

## 这套东西的一条总纲

六份文档里的具体条款可以忘,这一句不能:

> **任何一个会产出结论的东西 —— 需求、检查、测试、探针、界面 ——
> 都必须能够说「我没有资格回答」。**

它必须能表达三档,不是两档:

| | 含义 |
|---|---|
| **是** | 查过,结论是肯定 |
| **否** | 查过,结论是否定 |
| **我不知道** | **没查到,或没资格回答** |

把第三档压进前两档,是这套方法要防的头号事故。压进"是"就是编造;
压进"否"就是把"没测量"说成"测量结果是零"。这两种错误在输出上长得和正确答案一模一样,
所以不会自己暴露 —— 只会在下游被当成事实引用,然后由用户承担代价。

后面几份文档里的绝大多数具体条款,都是这一句在不同环节的展开。

## 跨工具:什么是真的可移植,什么不是

这套文档是纯 Markdown + JSON,任何能读文件的工具都读得懂。但"读得懂"只是第一层,
真正的可移植性分三层,**保证强度依次递减**:

### 第一层 · 入口 —— 靠约定,要显式处理

不同工具自动加载的文件名不一样(`AGENTS.md` / `CLAUDE.md` / 各家自己的)。

**做法:选一个当正本,其余做转发或符号链接。**
`AGENTS.md` 是目前跨工具采用面最广的,建议它当正本。

> 转发文件里**永远不要写内容**。一旦写了,不同工具看到两套约定,
> 而且没有任何东西会提醒你 —— 这是最典型的"悄悄漂移"。

### 第二层 · 可执行的部分 —— 真正的保证

```
check 链 · 审计 · CI
```

这一层**和工具完全无关**。谁跑都一样红,人跑也一样红。

「一个任务 = 一个能一次读完的 diff」以前在第三层,理由是「没有阈值」。
现在它有阈值了(`6-INTEGRATE.md` 的体量闸门),所以搬到了这一层 ——
给一条纪律找到判据,就把它搬下来。**这是三层之间往下那个方向。**

**所以:每一条你真正在乎的纪律,能变成检查就变成检查。**
散文里的纪律是期望,能报错的检查才是保证 —— 换个工具、换个模型、换个人,期望会变,检查不会。

这条原则的另一个说法在 `3-BUILD.md`:**能靠结构保证的,就别靠对比保证。**
两句是同一件事。

#### 但上面那句有一整类例外:替代「读」的那些不要建

「能变成检查就变成检查」没有限定,而它有一整类例外。少了这条限定,
一个真心想守住某条纪律的人会被它直接推向一张**会过时的表**。

判据一句话:

> **这道闸门替代的是「跑」,还是「读」?**

- **替代跑的** —— 跑一条命令、比一个哈希、数一个数、看两处对不对得上。
  **建。** 这类事模型再强也还是要跑,而且跑出来的结果不随模型变。
- **替代读的** —— 判断这段话算不算一条条件、这个改动是不是碰了那件事、
  这个名字起得好不好。**不要建。** 你写的会是一张手写的名单、映射或正则,
  它今天盖住八成,明天多出来的那一成它不知道;而「读」那一侧每一代都在变强。

分不清的时候再问一句:**判据写不写得成一条命令?**
写不成、要靠一张手写的表去逼近,那就是「读」。

**两种失败不对称,所以拿不准时不建。** 一道替代「跑」的闸门坏了,它当场报错;
一张替代「读」的表漏了,它**报绿**。而后者的漏会随时间变多 ——
表是写下它那一天的仓库的样子,仓库不会停在那一天。

**「不建」不等于不管。** 管的办法是把**原料**交给会读的那一侧:抽出来、列清楚、
指过去,但不替它下判断。抽取本身是机械的,仍然属于这一层 ——
只是它产出的不是一个「通过/不通过」,而是一份让人一眼看得完的东西。

#### 往上撤那个方向也正当,而且今天没有机制

这一节原先写着「这就是这三层之间**唯一**正当的移动方向」(出处 ADR-58 末尾)。**那句话不成立。**

ADR-58 想到过反方向,但只想到一种形状:一条检查**因为太吵**而被降级成「大家注意一下」,
并且正确地把它叫作「同一件事的失败版本」。它没想到另一种:**拿判据量过之后撤掉。**

2026-09-18 这一天,主干上按后一种形状撤掉了分支寿命闸门(ADR-76)、纪律 lint(ADR-77)、
架构锚点检查(ADR-78)、决策记录闸门里走 git 的那一半(ADR-79)、体量豁免的过期机器(ADR-80)。
每一道撤的时候都摆出了判据:边际价值的斜率、它守的失败响不响、它抓到过真问题没有、
它的主要工作是不是在消化另一条规则的后果。同一套判据也驳回过判决表里的判撤
(ADR-81) —— 量出来那几样不是闸门,是关系钩,不在那把尺子的量程里。

**区分这两种的不是方向,是撤的时候说不说得出判据。** 说不出的那种仍然是失败版本,
ADR-58 那句话在那个范围内一直成立。

**而两个方向都该有机制,今天只有一个有。** 往下搬有:给一条纪律找到判据就搬,`2-CHANGE.md` 管它。
往上撤**没有** —— 没有任何东西会提醒人去问「这道闸门还值吗」,上面那几道全是人在某一天
想起来才去问的。补这个缺口的东西叫**死亡条件**:一道闸门立起来的时候就写下
「什么条件下它该退成只报数、什么条件下该整个撤」,下一个人不必重新论证,
只需要去核那个条件成立了没有。形状见 ADR-80 末尾那一节,**逐道的账记在 ADR-85** ——
包括哪几道判过、结论是「不该有」。**「不该有」也要写下来**:一个没被判过的闸门
和一个判过说不该有的闸门,在文件里长得一模一样。

### 第三层 · 只能靠自觉的部分 —— 会因工具而异,要承认

下面这些**没法机器检查**,不同的工具、模型、人会执行到不同程度:

| 纪律 | 为什么机器查不了 |
|---|---|
| 写测试时不许读实现 | 证据在提交树之外 —— 人看不见,留痕的执行者事后翻得出来,检查够不着。**但后果削弱得了**:一处没有任何测试约束住的行为,点着它的变异会存活。这是**套件级**的 —— 单条断言写空了看不出来,套件里别的测试照样把那条变异杀掉。缺的不是一道闸门,是变异盖得住 —— 而变异集常常也出自同一上下文,所以是削弱不是消除 |
| **架构文档写的是不是真的** | 锚点检查 ADR-78 撤了 —— 今天连覆盖与绑定都没有机器核,更不用说散文为真 |
| 非平凡改动先出计划 | 无法验证计划是真想过还是补写的 |
| 变更请求的分类是否诚实 | 分类由提出者自己给 |
| UI 构图与信息顺序 | 也不该机器查 |
| 汇报时分开"你让我做的"和"我顺手做的" | 汇报在仓库之外 |
| **「怎么核这件事」被读成「建什么闸门」** | 比下一行更早的一步 —— 等你问得出「该不该建」,「要建一道闸门」这个框已经套上了。一次自动的联想,没有任何判据拦得住 |
| **一道闸门该不该建** | 「它替代的是跑还是读」要人判。判错的症状是一张表**报绿**,而报绿不会自己暴露 —— 建错一道闸门比不建更糟 |
| 评审发现的档、是不是阻塞、合并者是否读了被推迟的、第几轮 | 档由作者自填,阻塞由合并者判;读没读、第几轮,仓库里都没有判据 |

**不要假装这一层是被保证的。**它靠的是每次开工前真的把对应那份文档读进去,
以及一个会追问的人 —— 这两样都不是文件能提供的。

**而「一个会追问的人」不可执行,所以把那句话本身写下来。**
这一层能被拦住的时候,拦住它的通常是一句人问的话,不是哪份文档:

> **我们还在原则上吗?**
> **这一条违反原则吗?**

两句都不指名任何一条纪律,对着上面表里任何一行都问得出口。
**问的人不必先看出哪里错了** —— 它把「你自己说说看」交回给动手的那一方,
而上下文全在那一方手里。在代码写出来之前问,比在评审里问便宜一个数量级。

这也是这一层唯一便宜的干预:**它不建任何闸门**,所以不会多出一张替谁报绿的表。
而这一层没有闸门这件事,不是欠账 —— 给「该不该建闸门」建一道闸门,
会当场违反它自己说的话。

> 结论:**换工具时,第二层原样迁移,第一层改个文件名,第三层需要重新验证。**
> 第一次用一个新工具做完一轮,回头看它有没有在第三层上偷工 ——
> 尤其看 diff 删了什么,和测试是不是长得像实现的镜子。

## 什么时候不走流程

改文案、调间距、重命名变量、修 bug、补测试 —— **直接做**。

流程只在**改动触及需求登记表任何一条**时启动。
一个尚未验证需求的小项目,流程过重会先杀死动能;
它存在的目的是防止红线被悄悄侵蚀,不是给每次提交加手续。

---

## 一条给人看的提醒

这套文档里的分期、编号、环节名,是**执行者的脚手架**。
向决策者汇报时不要用它们 —— 说"还差什么、卡在哪、下一步谁做",
不要说"我们在第几阶段"。

**脚手架是给盖楼的人用的,不该出现在住进来的人眼前。**

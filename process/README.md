# 全流程约束 · 总则

**这一套文档和任何具体产品无关。**它规定的是:一个需求怎么从想法走到可验收的成品,
以及在这条路上,每一步各自不许做什么。

把整个 `process/` 目录复制进任何新项目就能用。项目自己的需求写在别处(见「两层」)。

---

## 为什么要分两层

一份文档里如果既写着「变更请求怎么评定」,又写着「步行时间禁止估算」,会出两个问题:

1. **复用不了** —— 下一个项目想用这套方法,得先把业务规则一条条剔出去
2. **更糟:读的人分不清哪条可以商量** —— 通用纪律是方法论,可以随经验演进;
   业务红线是这个产品的生死线,不能碰。混在一起,两种都会被当成"建议"

所以:

| 层 | 装什么 | 谁写 | 变动频率 |
|---|---|---|---|
| **通用层** `process/` | 流程、纪律、评定办法、验证手段 | 一次写好,跨项目复用 | 很低 |
| **业务层** `docs/` | 这个产品要什么、红线是哪几条、验收怎么算 | 每个项目自己写 | 高 |

**业务层引用通用层的规则,不复述它。**业务层里出现的每一条规则,都必须是只属于这个产品的。
如果一条规则换个产品也成立,它写错地方了。

## 环节与依赖

```
        ┌──────────────────────────────────────────────┐
        │                  需求文档                      │  ← 唯一来源
        │        编号 · 优先级 · 验收标准 · 红线          │
        └──────────────────────────────────────────────┘
             │            │           │           │
      ┌──────┘      ┌─────┘     ┌─────┘     ┌─────┘
      ▼             ▼           ▼           ▼
  ┌───────┐    ┌────────┐  ┌────────┐  ┌────────┐
  │架构设计│    │ UI 设计 │  │测试用例│  │验收标准│
  └───────┘    └────────┘  └────────┘  └────────┘
      │             │           │           │
      └──────┬──────┘           │           │
             ▼                  │           │
       ┌──────────┐             │           │
       │ 代码实现  │◄────────────┘           │
       └──────────┘      测试先于/独立于实现   │
             │                               │
             └───────────────────────────────┘
                          验收
```

**依赖方向只有一个:向下。**下游引用需求编号,上游不知道下游存在。

**唯一的例外是反向输入** —— 下游在干活时撞见需求文档有错或代价远超假设。
这种情况不允许在下游被悄悄消化掉,必须走 `2-CHANGE.md` 的评定。

### 每个环节的输入与产物

| 环节 | 输入 | 产物 | 约束在哪 |
|---|---|---|---|
| 需求设计 | 调研、观察、决策 | 编号化的需求文档 + 机器可读登记表 | `1-REQUIREMENTS.md` |
| 架构设计 | 需求编号 | 架构文档,每处实现标注服务哪条需求 | `5-DESIGN.md` |
| UI 设计 | 需求编号 + 界面需求 | 设计画板(HTML/CSS)+ 可继承的 token | `3-BUILD.md` |
| 代码实现 | 需求编号 + 架构文档 + 设计 + token | 代码 | `3-BUILD.md` |
| 测试实现 | **只有需求编号和验收标准** | 测试 | `4-VERIFY.md` |
| 测试覆盖 | 测试 + 红线清单 | 变异集 | `4-VERIFY.md` |
| 需求验收 | 全部 | 审计报告 | `4-VERIFY.md` |
| UI 验收 | 设计画板 + 实现 | 差异清单 | `3-BUILD.md` |

注意测试那一行:**输入里没有代码。**这不是疏忽,理由见 `4-VERIFY.md` 的「同源污染」。

## 五份文档

| 文件 | 管什么 | 什么时候读 |
|---|---|---|
| `1-REQUIREMENTS.md` | 需求怎么定义、编号、红线机制、验收标准怎么写 | 写需求文档前 |
| `2-CHANGE.md` | 反向输入与需求冲突怎么评定、**哪些必须找人拍板**、决策怎么记、文档怎么同步 | 想改需求时,撞见两条需求打架时,以及每次想说"这个太麻烦"时 |
| `3-BUILD.md` | 代码和 UI 怎么生成、生成者的已知失效模式 | 动手写之前 |
| `4-VERIFY.md` | 测试、覆盖、审计、验收 | 写测试前必读 |
| `5-DESIGN.md` | 架构文档写什么、必须先于代码、靠锚点不漂移 | 改模块边界或调用顺序前 |

还有 `AGENTS.md.tpl` —— 复制到新项目根目录改成 `AGENTS.md`(再放一个转发过去的
`CLAUDE.md`),它负责把上面五份接进去。

## 这套东西的一条总纲

五份文档里的具体条款可以忘,这一句不能:

> **任何一个会产出结论的东西 —— 需求、检查、测试、探针、界面 ——
> 都必须能够说「我没有资格回答」。**

它必须能表达三档,不是两档:

| | 含义 |
|---|---|
| **是** | 查过,结论是肯定 |
| **否** | 查过,结论是否定 |
| **我不知道** | **没查到,或没资格回答** |

把第三档压进前两档,是这套方法要防的头号事故。压进"是"就是编造;
压进"否"就是把"没测量"说成"测量结果是零"。这两种错误在输出上长得和正确答案一模一样,
所以不会自己暴露 —— 只会在下游被当成事实引用,然后由用户承担代价。

后面几份文档里的绝大多数具体条款,都是这一句在不同环节的展开。

## 跨工具:什么是真的可移植,什么不是

这套文档是纯 Markdown + JSON,任何能读文件的工具都读得懂。但"读得懂"只是第一层,
真正的可移植性分三层,**保证强度依次递减**:

### 第一层 · 入口 —— 靠约定,要显式处理

不同工具自动加载的文件名不一样(`AGENTS.md` / `CLAUDE.md` / 各家自己的)。

**做法:选一个当正本,其余做转发或符号链接。**
`AGENTS.md` 是目前跨工具采用面最广的,建议它当正本。

> 转发文件里**永远不要写内容**。一旦写了,不同工具看到两套约定,
> 而且没有任何东西会提醒你 —— 这是最典型的"悄悄漂移"。

### 第二层 · 可执行的部分 —— 真正的保证

```
check 链 · 审计 · CI
```

这一层**和工具完全无关**。谁跑都一样红,人跑也一样红。

**所以:每一条你真正在乎的纪律,能变成检查就变成检查。**
散文里的纪律是期望,能报错的检查才是保证 —— 换个工具、换个模型、换个人,期望会变,检查不会。

这条原则的另一个说法在 `3-BUILD.md`:**能靠结构保证的,就别靠对比保证。**
两句是同一件事。

### 第三层 · 只能靠自觉的部分 —— 会因工具而异,要承认

下面这些**没法机器检查**,不同的工具、模型、人会执行到不同程度:

| 纪律 | 为什么机器查不了 |
|---|---|
| 写测试时不许读实现 | 无法观测它读了什么 |
| **架构文档写的是不是真的** | 锚点检查只保证**覆盖与绑定** —— 一份把目录树抄进去、每行胡写一句话的文档也能通过 |
| 一个任务 = 一个能一次读完的 diff | "能一次读完"没有阈值 |
| 非平凡改动先出计划 | 无法验证计划是真想过还是补写的 |
| 变更请求的分类是否诚实 | 分类由提出者自己给 |
| UI 构图与信息顺序 | 也不该机器查 |
| 汇报时分开"你让我做的"和"我顺手做的" | 汇报在仓库之外 |

**不要假装这一层是被保证的。**它靠的是每次开工前真的把对应那份文档读进去,
以及一个会追问的人 —— 这两样都不是文件能提供的。

> 结论:**换工具时,第二层原样迁移,第一层改个文件名,第三层需要重新验证。**
> 第一次用一个新工具做完一轮,回头看它有没有在第三层上偷工 ——
> 尤其看 diff 删了什么,和测试是不是长得像实现的镜子。

## 什么时候不走流程

改文案、调间距、重命名变量、修 bug、补测试 —— **直接做**。

流程只在**改动触及需求登记表任何一条**时启动。
一个尚未验证需求的小项目,流程过重会先杀死动能;
它存在的目的是防止红线被悄悄侵蚀,不是给每次提交加手续。

---

## 一条给人看的提醒

这套文档里的分期、编号、环节名,是**执行者的脚手架**。
向决策者汇报时不要用它们 —— 说"还差什么、卡在哪、下一步谁做",
不要说"我们在第几阶段"。

**脚手架是给盖楼的人用的,不该出现在住进来的人眼前。**

## 一件新工作放哪边

仓库有两种代码，**加功能之前先决定它属于哪边**：

| | 位置 | 谁执行 | 装什么 |
|---|---|---|---|
| **判断** | `skill/` | Agent 读了照做 | 读懂产品、推关键词、判断内容匹配、写草稿 |
| **机械** | `scripts/` | Node 执行 | API 调用、分页、去重、评分、落盘 |

判据一句话：

> **同样的输入，两次跑出来必须一模一样吗？**
> 必须 → `scripts/`。允许不一样、且不一样才有价值 → `skill/`。

- 基础分层规则（待重评先 B；其余明确 ❌ 为 C，有非空邮箱且明确 ✅ 为 A，缺 fit 为 B）**必须**每次一样
  → `scripts/lib/score.ts`
- 「这个做露营装备测评的博主适不适合卖充电宝」，也就是那个 `fit` 从哪来，
  **不该**每次一样 → `skill/references/semantic-fit.md`

反过来用最容易出事：把判断写进脚本会得到一个僵硬的规则引擎（关键词表越写越长，
永远差一个 case）；把机械劳动交给 Agent 会又慢又贵，而且**不可复现**——
同一份数据两次跑出两份名单，用户无法知道哪一份是对的。

## 新东西落在哪个目录

仓库只有下面这些目录。**新建目录之前先看这张表**：多数东西都有现成的落点。

| 目录 | 进仓库 | 装什么 |
|---|---|---|
| `skill/` | 是 | Agent 读了照做的执行指令（`SKILL.md` 与 `references/`） |
| `scripts/` | 是 | Node 执行的脚本：入口与需求测试 `test.ts` 在顶层，产品逻辑在 `lib/`，数据源在 `providers/`，检查链在 `check/`；逐个模块见下面的锚点表 |
| `docs/` | 是 | 业务文档与决策记录（`adr/`）；逐个文件管什么见 `docs/SYNC.md` 的文档地图 |
| `process/` | 是 | 跨项目通用的流程与纪律 |
| `.github/` | 是 | CI，以及给评审器的转发（`copilot-instructions.md`） |
| `output/` | 否 | 本机运行产物。现状：collect 建的采集任务目录 `output/<产品>-<时间戳>/`。本节另立的规矩：核实工具与调查的原始响应、诊断快照、价目快照也放这里，`output/<名字>/`，带清单与 SHA256 |
| `memory/` | 否 | 跨任务记忆（`memory/creators.json`，已推荐过的人） |
| `.check-cache/` | 否 | 检查链的缓存：编译缓存（`compile-cache`）、变异派工的 worker 目录（`mutate-jobs`）、测试与自检的覆盖记录 |
| `node_modules/` | 否 | 依赖 |

根目录只放入口文档（`AGENTS.md`、`README.md` 等）与配置文件。

三条规矩：

1. **不新建顶层目录，也不在 `docs/` 下新建子目录。** 真需要时，在同一条改动里把它登记进这张表，写明装什么、进不进仓库；
   不进仓库的，同一条改动里加进 `.gitignore`，并同步 `scripts/check/jobs-rule.ts` 的 `SKIP`
   （`.gitignore` 的手抄本，决定变异 worker 复制哪些东西）。
2. **运行时产生的东西一律放 `output/<名字>/`**：接口响应原件、诊断快照、价目快照、日志。它们不进仓库；
   决策记录要引用时，写本机路径与 SHA256，不把文件搬进 `docs/`。
3. 这张表和下面的锚点表一样**没有机器核**：改目录结构时，靠 `docs/SYNC.md` 触发表那一行提醒回来改。

这张表只列顶层目录与落点，不逐个文件列（逐文件的目录树仍然不写，`process/5-DESIGN.md`）。
来历：仓库里曾有过一个 `docs/evidence/`，是为给决策记录留原始证据建的，需求所有者要求删掉；
根子是没有一处把顶层目录连同进不进仓库列全、也没说运行产物该放哪（ADR-114）。

## 模块锚点表

层的含义：**入口**只做读参数、落盘、打印、退出码；**逻辑**装有语义的决策；
**适配**把外部响应翻译成内部类型；**检查**是检查链自身。

> 入口层不许放决策逻辑 —— 判据是「这段代码的顺序错了会不会出错」。
> 会，它就有语义，就该搬进 `lib/`（`docs/CONVENTIONS.md` 第 10 条 —— 那条自己数着踩过几次，这儿不抄）。

### 变异维护的输入与执行边界（ADR-120）

`mutate.ts` 负责 Git 与文件读取；`mutate-rule.ts` 决定可信基线与版本间维护判定，
依赖 `size-rule.ts` 复用本地 Git 基线判定、依赖 `group-rule.ts` 复用分组依赖闭包；不新增模块。
CI 从 GitHub 提供的 `GITHUB_EVENT_PATH` 与 `GITHUB_EVENT_NAME` 取得事件自身的基线；事件缺失或不合规时失败，不改用本地起点。
显式 `MUTATE_BASE_SHA` 优先用于固定对照与独立 Git 夹具；提交格式及真实祖先资格仍由 Git 判定核实。
旧变异目录与旧验证者分组配置都从可信提交读取，当前配置从待验源码读取。
两侧的 `kills` 都经同一套实际归组路径推导路由；不另外保存一份变异到组的映射。
维护比较先于隔离正常基线与施变，读取旧内容失败不能进入「无变化」分支。

解释形状与变化判定由检查代码负责，解释语义由评审负责，公开判据见 `process/4-VERIFY.md`。
维护结果只增加变化清单，不接管验证者的断言归因、进程收尾或认领写入；
正常基线复用与完整运行的审计认领仍由原执行路径负责。

完整需求测试认领 `.check-cache/test-claims.json` 的恢复沿既有退出处理执行。
正常字节未变时应保留文件原件，不重写同一内容；认领遭施变清除或改写时仍须恢复开跑前原字节。
开跑前没有认领时，只删除运行中产生的认领；两头都缺席时不作文件操作。空文件属于存在的原件，
JSON 语义相同、长度相同都不能代替原字节相同。
该动作判定放在既有 `mutate-restore.ts`，入口负责读取和执行；先独立验证判定，再以真实入口证明接线。
入口在既有退出恢复中读取当前字节并执行该动作；相同原件不产生写入或删除，异常改写仍须还原。
真实恢复入口归独立自检组 `claims-restoration-entry`，完整检查执行一次；纯判定断言和 M-H50 仍归需求测试。
入口夹具的认领字节仅作恢复输入，不冒充完整需求测试的认领；自有子进程结束后由该组回收临时仓库，
夹具或进程资格故障须单独失败，不能当作指定断言抓到错误。该组不新增业务判据认领，
也不解除 `mutate.ts` 等验证基础设施的自我施变限制；既有源码恢复和信号收尾顺序继续由原负片守住。

`full_run: { reason: string, recheck_when: string }`：两个值均须为非空白字符串，

## 缝隙契约：Agent ↔ scripts

各入口都是**一次性进程**，彼此之间只通过磁盘上的文件交接。
Agent 是编排者，它读 stdout 做决策。

| 入口 | 读 | 写 | 退出码 |
|---|---|---|---|
| `probe` | `--config probe.json` | **不落盘** | 0 · 1 · 2 |
| `collect` | `--config task.json` 或 `--resume <dir>` `[--ignore-memory]`；旧名单、采集原件、评审正本及已有人工表 | `task.json` `creators.raw.json` `creators.json` · 内容变化时 `agent-review.json` | 0 · 1 · 2 · **3** |
| `enrich` | `--dir <dir>`（`task.json` `creators.json` `creators.raw.json` `agent-review.json` · 已有 `manual-feedback.csv`） | `enrichment.json` `task.json` | 0 · 1 · 2 · **3** |
| `render` | `--dir <dir>` `[--ignore-memory]`（`task.json` `creators.json` `creators.raw.json` `agent-review.json` · 已有 `manual-feedback.csv` · `enrichment.json` · 当前 `memory/creators.json`） | 内容变化时 `agent-review.json` · `task.json` 的去重状态 · `creators.json` `kol.csv` `kol.xlsx` `meta.json` `report.html` · **`memory/creators.json`** | 0 · 1 · 2 |
| `feedback-template` | 必填一次 `--dir <dir>`、可选一次 `--append`；既有 `task.json`、已保存 `agent-review.json`、完整 `creators.json`、存在时的 `creators.raw.json` 及人工目标 | 仅 `manual-feedback.csv` 的创建或显式追加；unchanged 不写 | 0 · 1 · 2 |

**stdout 是结构化 JSON，stderr 是进度。** 这个分工是硬约束 —— Agent 解析 stdout，
往里混进度信息会让解析在最需要它的时候（长任务、预算告急）失败。

`npm run --silent feedback-template -- --dir <dir> [--append]` 提供 D26 的机械 JSON 出口；普通 `npm run` 自身可打印脚本 banner。相对目录按调用 cwd 解析，空白路径、缺值、未知／重复参数或位置参数在任务读写前以 2 拒绝并给用法，不建目录。输入读取、结构、冻结来源或人工表问题均退出 2，stderr 点名实际文件及问题，人工行带物理行；保存失败退出 1 并带目标及真实原因，两者均无成功 JSON。实际保存成功或合法 unchanged 退出 0，只输出 `{file:absolute_path,status:'create'|'append'|'unchanged',added_accounts:number}`；账号行数不是独立人数，unchanged 的新增数为 0（D26）。

`probe` 的 `sample[].top_post` 供 Agent 判断方向：作品字段缺席或空数组写 `（未查询）`，
有作品则给第一条文案的前 120 字符，空串照留（P1.i）。它不是最高播放量，也不是主页近期样本；
空串不能证明作者没写文案，适配层目前也会把未取到的文案归为空串（ADR-103）。

搜索任务身份（U8、ADR-106）：`meta.keywords[]` 与 `probe.results[]` 的成功/普通错误行
由脚本写入原 `tasks` 零起始 `task_index`，Agent 只读。人读序号为下标加一；筛选不得重编号。
`pending_keywords`、续跑判定用的关键词列表、probe 进度和 collect 完成/达上限提示共用任务标签，
包含原序号、维度、平台、原词；续跑成本提示仍只使用列表长度报告数量。HTML 使用行的下标；旧行缺失或非法下标显示「无从确认」。
`as_hashtag` 保留为配置元数据，当前不切换 TikHub 搜索端点，不能作已执行路径声明。
IG 路线只由任务的 `ig_route` 决定：缺席走 Reels；`"hashtag"` 走话题搜索，在 `TikHub.search()` 最前面分派，probe 与 collect 共用。
probe 的成功与普通错误行照配置带出 `ig_route`：写了才有这个键，不补成 Reels，也不由 `as_hashtag` 推断（D15.l、D15.m）。
`ig_route` 不合规时 collect（新建与续跑）与 probe 在建目录、预留与请求之前以退出码 2 结束（D15.j）。
任务列表及三个必填字段由共同的 `taskListProblems` 原样校验（D16）：至少一个任务，`keyword` 是非空白字符串，
`dimension` 与 `platform` 按各自枚举原值匹配，不修剪、不补值。collect 新建、整份旧任务续跑（含改预算）与 probe
都在任何预留、请求和任务写入之前拒绝坏列表；续跑不改原文件。任务问题与路线问题合并报告，带输入文件路径，
不跳过坏项，也不只校验未完成项；collect 的进度行在此后才读取列表长度。
查询状态、计数及任务列表重排的既有边界不变。

collect 恢复已有任务还要校验原始进度（D19、ADR-117）：`done` 为不重复且在任务范围内的安全整数数组；
四张可选统计表存在时必须以标准十进制任务索引为键，值为非负安全整数，仅 `found` 的项允许 null。
进度数字使用 JSON source context 取得原 token 并按精确十进制值判定，允许 `1.0`、`1e0`，
拒绝经 Number 舍入或下溢后才成为整数的原文；错误显示非法 token，不把溢出数写成 null。
整表缺席仍表示历史未知，不回填；已记录页数可高于当前页数上限，不作跨表推算。
任务列表有效后、首次读取进度行与预算构造前拒绝坏进度；普通续跑和改额续跑都退出 2，
stderr 点名任务文件及坏字段，任务原字节不变、零预留和请求。

enrich 与 render 同样使用 `taskListProblems` 校验原样任务列表；与品牌输入同时有问题时两类均报，先于改额、预留、请求和任务／交付写入。render 空数组也拒绝（D16.n–q、ADR-115 第十一节）。
任务文件读不到、JSON 或根对象形状不合规、列表不合规时，在读名单及任何写入前退出 2；stderr 写任务文件路径及实际问题，
任务列表问题一次报全，不带内部异常类名或堆栈。已有任务文件、名单、交付物和记忆保持原字节，原本不存在的输出不创建。
输入读取的异常处理只包任务读取，后续保存与运行错误不改报输入问题。此入口不套新任务缺省，也不接搜索路线或市场/人数校验。

市场与目标人数使用同一份原字段判定（D17）：collect 新建允许字段缺席，续跑（含改额）要求两字段齐全；probe 只查 market。
已提供的 market 必须是非空白字符串，collect 的 target_count 必须是有限数，合规原值不修剪、不转换；不增加国家或人数范围限制。
字段问题与任务/路线问题一起报告；collect 在输入可读且 CLI 预算及新建预算合规时保证报全，probe 在配置可读时保证报全。
坏输入退出 2，先于建目录、任务写入、改额、任何预留和请求；续跑 task.json 逐字不变。probe 的输入诊断仍无内部异常类名与堆栈。
合规后仅为新 collect / probe 缺席的 market 采用 US，并在 stderr 说明默认；仅为新 collect 缺席的 target_count 采用 50。
显式 null 不是缺席，旧任务不套这些缺省；人数为 0 仍受 F9 第一页保证及其预算边界约束。

退出码按可行动的原因区分：

| | 含义 | Agent 该做什么 |
|---|---|---|
| `0` | 正常；probe 预算不足也保留部分输出 | 读 stdout 与停止提示 |
| `2` | 输入/初始费用状态、实际请求缺 key，或记忆读不出来 | 报具体原因，不能仅建议加钱 |
| `3` | collect/enrich 已知额度不足且断点保存成功 | 用户确认新总上限后续跑，或用已有数据收尾 |
| `1` | 运行中费用内部错误、保存失败或其他失败 | 读 stderr；不得声称断点已保存 |

恢复 pending 拒绝付费/改额为 2，运行中意外 pending/receipt 错为 1。直接分页探针非 200 仍中止，不输出成功结果 JSON。
零请求 collect、缓存/私密 enrich 与 render 不要求 key 或可付费账；坏的整份 JSON 仍无法读取。

collect/enrich 的任务费用先保存预留才发请求，结算保存成功后才读正文或进入下一尝试（D14、ADR-109）。费用检查点只更新盘上 task 的账目与次数，不能提前保存内存业务进度或去重声明。检查点失败锁定本运行并退出 1；尽力保存成功也不产出常规成功提示或被记忆错误改成 2。process 探针不接此回调。强杀后 pending 仍占额度；终态已存但业务响应未存时仍可能重查，不承诺断电或多个写者安全。

续跑提示分别计算待查关键词与待补 profile；两者皆零才声明无新请求。有待查项但费用不可用时同时报告阻止原因，不能承诺续跑即花钱（D6.q/r）。记忆读不出来仍按 P4 停止产出，只有用户显式 `--ignore-memory` 才跳过，并保留未去重声明。

### 字段所有权

Agent 判断、人工作答与采集证据各有正本；`creators.json` 的判断只由脚本重建投影：

| 写者 | 所有权 |
|---|---|
| `collect`（脚本） | 采集与 profile 原始字段、`source_keyword`、`source_dimension`、`discovery_sources` 及 raw 累加器；保全旧评审、冻结候选并保存当前名单投影 |
| **Agent** | 只编辑 `agent-review.json` 对应平台账号的原判断、四项证据、兼容 fit／理由／草稿及实际校准版本；保留冻结轮次、来源与其他评审 |
| **人工** | `manual-feedback.csv` 的原作答；Agent 不代填，collect/enrich/render 只读 |
| `feedback-template`（脚本） | 只创建模板结构或显式追加冻结池缺席账号的空白七字段，不改已有人工字节、轮次、判断或源文件 |
| `enrich`（脚本） | 只写 `enrichment.json` 与任务状态，不碰评审正本、人工表、raw 或名单 |
| `render`（脚本） | 当前 Agent／人工投影、`score`、`tier`、`tier_adjustments`、公开指标摘要及交付；正本仅保存迁移或冻结变化，不重写原判断 |

名单中的旧评审字段不是新判断的来源；直接修改投影，下次运行会被正本重建覆盖。新采集证据也不授予补写人工结论的权利。


**搜索作品的身份与合并归脚本管理（D11、ADR-105）。** 适配器只从对应作品字段生成
可选 `RecentPost.id`，使用 `平台:原始id`；外部标识缺失就不生成键，Agent 不补写它。
采集首次收页与后续合页都经 `scripts/lib/posts.ts`，同人合并也复用这一契约：
已有记录在先、后页在后；同人合并则主记录在先、关联记录在后，主记录选择规则不变。
同平台同 id 保留第一次记录及其字段，后到的新作品按原顺序追加，缺 id 的作品逐条保留，
因此旧任务的条目数不保证等于不同作品数。合并不修改输入；两侧都无非空作品时保持未查询。
这只汇集关键词命中的证据，不替代 `enrich` 的独立主页样本，也不改变评分或同人识别规则。
Instagram V2 Reels 与话题搜索共用逐条视频判定，只对有肯定视频信号的作品写搜索
`RecentPost.plays`；图文、轮播和类型未知的作品仍保留，播放数缺席。适配层不凭端点名
或源播放字段存在与否推断媒体类型（D18.a–d、P1、ADR-102 第九节）。

### IG 主页样本的媒体范围与交付

主页公开样本与上面的关键词命中作品分开。IG 适配器先保留提供方本次返回的前最多 12 条作品，
再逐条带出 `video_confirmed`：只有肯定视频信号才为 true；false 是“没有肯定信号”，
不宣称已证明为图文。播放字段只对确认视频取来源值；赞评与发布时间的真实证据不因媒体未知被丢弃。
`assessment` 给新样本写 `media_scope='provider_returned_first12'`；这句话只说明本次端点返回的窗口，
不保证端点已返回账号所有图文。TikTok 的媒体类型仍按原契约，不由 IG 字段推断。

旧 IG 缓存没有逐条媒体资格。只有原样保留的来源是 `public_api/tikhub`、端点是
`/api/v1/instagram/v2/fetch_user_posts`，且旧 `basis` **精确匹配**已知视频筛后生产记录时，
`assessment` 才认作 `media_scope='legacy_video_filtered_first12'`；其余旧样本经重核显式记为
`media_scope='unknown'`，而非缺字段后由交付侧猜测。
不能从 `views` 是否存在、是否为 0 或缓存时间反推视频，也不能零请求复原此前过滤掉的图文。
缓存重算保留原 `source`/`observed_at`，已证实的旧视频窗口绩效与 Reels 报价可以继续作为**历史视频窗口**测量，
但旧窗口不能证明账号最近一次发布，活跃状态不可用；未知范围的作品依赖指标和报价不可用。
补取新窗口只经显式刷新和既有费用检查。

新 IG 播放类指标只读确认视频，全媒体互动、发帖间隔与活跃度只读窗口内可用作品证据；
Reels 报价的 eCPE 另用同窗口的确认视频互动分母，不借全媒体 `median_engagements`。
同行风险仅在同平台、同粉丝档、同 `media_scope` 的可比账号之间建立基线，范围未知者不被凑入。
`enrich` 写回与 `render` 直接读取旧目录时都经同一范围判定；`render` 在名单、表格、报告或记忆写入前
先在内存中重核旧公开指标及其风险，随后才投影交付，不把旧的无范围数值原样透传。
JSON 摘要、CSV/XLSX 与 HTML 都带出范围状态，使历史视频窗口与本次返回窗口在用户眼前可分；
这些展示不能把“旧版仅视频”或“范围未知”写成当前全媒体结论（D8、D9、D10、F8、P1、P5）。

### 两个 creators 文件

实际发现来源归脚本管理（D15、ADR-110）：适配器将返回账号的实际端点与原任务词/维度写入 `discovery_sources`，合页及同人合并稳定取并集；旧缺席不妨碍追加新观察。它不同于完整归属用的 `source_tasks`，不从后者倒推，也不改变后者的未知规则。来源在现有业务保存点落盘；profile、费用检查点及 Agent 不补写它。probe 透传集合；表格与 HTML 使用纯格式化投影，HTML 在输出处转义。集合只代表已记录的账号发现来源，不保证完整历史，不对应某条作品或请求费用次数。

| 文件 | 是什么 | 规则 |
|---|---|---|
| `creators.raw.json` | 采集**累加器** | **只增不减**（D6）。collect 的续跑输入；enrich/render 只读完整直接关联，不覆盖它 |
| `creators.json` | 交付物 | 累加器的过滤视图与当前正本投影。过滤只作用于它 |

三个入口只有确认 raw 路径真缺席才从旧名单回退；已存在的坏 JSON、非列表、读失败或悬空软链均带实际文件拒绝，不当作没有原件。collect 的兼容 seed 是独立克隆，去除 Agent／人工／有效建议、评分分层、公开评估摘要和记忆标记等派生字段，先迁移旧判断再重建；旧原件存在时保持原值。旧任务已经丢掉的被过滤账号或来源无法从回退名单恢复，不补造历史完整性。

早先两者共用一个文件：collect 结尾把过滤后的名单写回 `creators.json`，
而 `--resume` 又拿它当输入 —— render 写回记忆之后再续跑，全员被判成「已推荐过」，
已付费采集的数据被清成空数组。见 ADR-08。

## 三态在类型层的落点

总纲那句「任何会产出结论的东西都必须能说『我没有资格回答』」，在代码里长这样：

| 形态 | 含义 |
|---|---|
| `undefined` | **没查过** |
| `null` | 查过，确实没有 |
| 有值 | 查过，就是它 |
| `recent_posts` 的空数组 | **例外：读作没查过**，与缺席同一态。今天没有生产者，全是盘上旧数据里 IG 那条兜底路径凭空写的（ADR-102） |
| `Measurement<T>` | `measured`（带 source / observed_at / sample_size / basis）· `unavailable`（带 reason）· **字段整个缺席 = 未查询** |
| `meta.json` 的 `capabilities` | 每种能力分别统计 `measured` / `unavailable` / `unqueried`，三个数不合并 |

这三档为什么不能压成两档、以及压掉之后会发生什么，在 `docs/CONVENTIONS.md`
第 1、6 条 —— **不在这里复述**。这一页只说它落在哪：`scripts/lib/types.ts`。

### 费用账与付费接线的边界（D12–D14、ADR-107/108/109）

金额模型不依赖供应商、文件或网络；报价提供固定版本表，budget 包装持有与 task 保存共享的同一 state。新建与恢复分开，旧费用缺失不能产生零账；原 ledger 可独立核验，根预算冲突的整体输出诊断不阻止合规的显式改额。

原预算 token → 精确金额 → 本端点预留 → 保存任务 pending → fetch → 按 HTTP 状态结算 → 保存任务终态 → 正文解析，先后不可交换：解析失败不能改变已知 HTTP 的费用类别。retry/fallback 各走一遍，费用错误不触发后继请求。费用检查点只保存 ledger/requests，业务仍由原保存点处理；显式改额先保存两处一致上限，再请求。process 探针不保存任务。接线由独立进程假网络与 M-D14-a…j 验收，业务保存另由 M-P3-f、M-D6-o 守住。

费用投影的唯一字段契约见 ADR-108；各入口及 render 共用，金额文本只在 JSON 出口转精确 number。render 不创建或修复费用账；保留原账的本地写回不把未知金额变零。

请求前持久预留按 ADR-109 的目标契约实现，必须另用强制中断与保存故障验证，不能由纯模型测试推定通过。保留边界是断电、多写者以及未保存的业务响应；费用终态已存不证明业务进度已存。


### 人工审核汇总边界（U11、ADR-130）

任务评审协调器保留初始已校验人工行的只读副本，当前完整关系重验与投影仍按原顺序；统计只读这份作答和待保存的完整冻结池。render 在联系过滤后的名单之外，从同一评审上下文取得汇总和完整轮次，写入 metadata，再交报告呈现；冻结池不随联系过滤、筛选或当前候选缩减。统计不授予模板写入、memory 更改或修改 Agent 判断的能力。HTML 只格式化调用方提供的统计，不读盘重算；formatter 未提供统计时保留未知出口。


关键词归因（U11.c/k–m）沿既有 `pipeline.keywordRows` 边界：两参公共调用保持兼容；生产 render 提供 `{document,feedback}` 已校验上下文，语义通过读取对应平台原 fit，人工已审读取全部冻结来源与自身原人工行。当前入围来源的全表未知、冻结人工来源的同平台未知分别判断，不互相覆盖，未查询行不带人工测量数。`keywords[].manual_reviewed` 交给 HTML 只做格式化，缺席/未知/真零分开；不改变协调器顺序、feedback_summary 或完整 review_rounds，不增加写入权限。

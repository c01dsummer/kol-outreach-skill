# 海外 KOL 建联 Skill — 业务需求

> 状态：v1 · 2026-08-25 定稿，2026-08-26 按首轮真实运行修订
> 这份文档只谈业务需求，不谈实现。编号定义见 `docs/SPEC.md`（唯一来源），技术选型见 `docs/data-source-strategy.md`。

---

## 0. 为什么重做

前一版（`tikhub-kol-sourcing`）跑通了完整链路，也验证了需求真实存在。重做不是因为它不能用，而是因为**复杂度花错了地方**：

| 现状 | 问题 |
|------|------|
| Phase 03 让用户"确认 TikHub 接口" | README 承诺"不需要懂 API"，却把接口选择暴露给非技术运营。实现细节泄漏到了用户界面 |
| 静态评分表（bio 含关键词 +15） | 用字符串匹配近似"内容相关性"。这恰好是 LLM 最擅长、正则最差的地方 —— 做了一个不如 SaaS 筛选器的东西 |
| 已抓取 `best_video_desc` 却只做参考 | 判断博主契合度最有价值的原料已经在手里，没被真正使用 |
| 产出停在 CSV | 运营拿到名单后的下一个动作是写信，而这一步的信息（博主在做什么内容）Agent 已经读过了，白白丢弃 |
| 历史索引记录"每次任务" | 记的是运行批次，不是人。同一博主跨关键词、跨产品重复出现，没有"已联系过"的记忆 |
| 与 TikHub 硬绑定 | 数据源是可替换的商品层，不该锁死 |

**核心判断：这个 Skill 的护城河是判断力，不是数据获取能力。**

任何人都能包一层采集 API。Modash、Heepsy 这些 SaaS 在筛选和导出上做得比我们好。Agent 唯一不可替代的是语义判断 —— 读懂产品、推导搜索策略、判断内容调性是否匹配、写出有针对性的第一封信。新版本的复杂度必须集中在这四件事上。

---

## 1. 产品定义

一个 AI Agent Skill。运营用自然语言描述自己卖什么，Agent 完成从产品理解到可发信名单的全过程，产出带个性化开发信草稿的分层名单。

**不是**采集工具，**不是** SaaS 的命令行版本。是一个替运营做完"找谁、为什么是他、第一句话说什么"的助手。

---

## 2. 用户

### 主用户：出海运营 / 独立卖家

- 不写代码，可能没听说过 API
- 手上有 1–N 个 SKU 要推
- 当前做法：在 TikTok/IG 手工搜索，逐个点开主页看粉丝数，把 bio 里的邮箱复制进表格
- 现状产能：一天 30–50 人，且质量全凭手感
- 判断标准：这批人靠谱吗、我该先联系谁、信怎么写

### 次用户：clone 这个 Skill 的开发者

- 会改 prompt 和脚本，但不想重写架构
- 需要能换数据源、调评分权重、改输出格式
- 对他们的承诺：改配置就能换供应商，不用动编排逻辑

### 明确不服务

- 需要团队协作、审批流、合同与付款管理的中大型团队 —— 那是 CreatorIQ / Aspire 的领域
- 需要投放效果归因的 —— 需要接店铺和广告数据，是另一个产品

---

## 3. 待解决的问题

按对结果的影响排序。这个排序决定了复杂度该往哪儿投。

### P0 — 不知道该搜什么词

最前置也最致命。搜错词，后面每一步都在浪费。

运营知道自己卖便携榨汁机，但不知道该搜 `juicer`（一堆商家号）、`smoothie recipe`（场景对但可能是美食博主不测评产品）、还是 `kitchen gadgets`（泛但精准度低）。

**这是 Agent 相对人类运营的最大优势** —— 它能从产品推导出四个维度的候选词，并且能在小样验证后调整。

### P1 — 拿到名单不知道信怎么写

群发模板回复率通常 <2%。有针对性的第一句话能到两位数。

差距全在"你是否真的看过他的内容"。而 Agent 在筛选阶段本来就读过了 —— 不用这个信息是纯浪费。

### P2 — 肉眼筛选无法规模化

粉丝量、互动率这些硬指标好办。难的是"这个人的内容调性适合我的产品吗"。

一个健身博主，粉丝 8 万、互动率 5%，看起来完美 —— 但他最近十条全在带减脂代餐，和你的蛋白粉直接冲突。这种判断只能靠读内容。

### P3 — 发了信才发现人选不对

受众地域不符（你卖美国，他 80% 粉丝在巴西）、刷粉号、邮箱是死的。样品和时间都白花。

这一层需要外部数据（受众画像、邮箱验证），是**可选增强**而非核心，因为它有成本门槛。

### P4 — 重复联系同一个人

跨关键词、跨产品、跨时间，同一个博主会反复出现。重复发信显得不专业，也浪费额度。

现有实现完全没有这层记忆。

## 4. 成功指标

| 指标 | 目标 | 怎么测 |
|------|------|--------|
| 单次任务耗时（说一句话 → 拿到名单） | < 15 分钟 | 人工计时 |
| 单次任务 API 成本 | < $2 | 运行日志累计 |
| 名单中"值得发信"的比例（人工复核） | > 60% | 抽样 50 人盲评 |
| A 级候选邮箱有效率 | > 90% | 发信后退信率反推 |
| 零配置跑通率（只有一个 key） | 100% | 新环境验证 |

**关于回复率**：这是业务上最关键的指标，但 Skill 测不到 —— 它不发信，也不该向用户索要回填数据（见 §6 关于回访的决定）。因此回复率**不列为 Skill 的成功指标**，由使用者在自己的发信工具里衡量。

代价要说清楚：没有反馈回路，评分权重只能靠人工调整，不会随使用自动变好。这是接受的取舍。

## 5. 范围边界

### 做

- 产品理解与搜索策略推导
- **TikTok + Instagram** 双平台创作者发现，含跨平台同人识别（YouTube 待定）
- 语义契合度判断 + 分层
- 可选的邮箱验证与受众画像增强
- 个性化开发信草稿（仅英语）
- 结构化产出（CSV 单表 + xlsx 分层 sheet + HTML 报告）
- 跨任务的创作者记忆（本地 JSON）

### 不做（及原因）

| 不做 | 原因 |
|------|------|
| **实际发送邮件** | 送达率、SPF/DKIM、退信处理、发信域名预热是另一个量级的复杂度，且必须用用户自己的邮箱服务。Skill 产出草稿，发信交给用户现有工具 |
| CRM / 跟进管理 | 变成长期状态管理，超出 Skill 形态 |
| 合同、付款、寄样物流 | 平台方（TikTok Shop / TCM）和专业 SaaS 做得更好 |
| 投放效果归因 | 需要接店铺和广告数据 |
| 多语言开发信 | 见 §6 Phase 06。首版仅英语 |
| 回访 / 效果回填 | 见 §6。用户回填成功率太低，做了大概率是死代码 |
| 中国大陆平台（抖音/小红书/快手） | 本产品定位出海。技术上数据源支持，将来可扩展，但账号体系、合规要求、建联方式完全不同，不应混在同一个流程里 |

## 6. 核心工作流

设计原则：**便宜的步骤先跑，贵的步骤只对幸存者跑。**

```
01 产品理解      能从链接推的绝不问用户
02 策略 + 试探   ★ 小样验证搜索方向，不对就重来
03 规模采集      TikTok + Instagram 双平台，策略验证过了才放量
04 语义筛选      ★ 读内容判断契合度，输出理由而非分数
05 增强（可选）  只对入围者做邮箱验证 + 受众画像
06 交付          分层名单 + 每人一封开发信草稿
```

**不做回访环节。** 曾考虑加一个 Phase 07，下次运行时询问上批的发信/回复结果，用来回填指标并调整评分权重。放弃了 —— 让运营回填数据这件事历史成功率极低，做了大概率是死代码，还会在每次任务开头插入一段用户想跳过的对话。宁可接受权重靠人工调。

### Phase 01 — 产品理解

给一个商品链接（亚马逊 / 独立站）就应该能推出大部分信息：品类、卖点、价位、目标人群。

**只问推不出来的**：目标市场、本次预算上限、要找多少人。三个都无法从商品链接推导，且都直接影响后续每一步。

反模式：把七个维度做成问卷让用户逐个填。运营会在第三个问题时放弃。

### Phase 02 — 策略 + 试探 ★

四个维度生成候选关键词：

| 维度 | 例（便携充电宝） | 特点 |
|------|------------------|------|
| 品类词 | `power bank review` | 精准但商家号多 |
| 场景词 | `travel essentials tech` | 找到真实使用场景的内容创作者 |
| 竞品词 | `anker power bank` | 已经在测评同类产品，转化意愿最高 —— 但见下方实测警告 |
| 人群词 | `iphone accessories` | 覆盖面广，精准度低 |

**两个平台分别出词。** IG 走 Reels 搜索，对多词词组匹配很差 —— 实测 `smoothie recipe` 返回 0 条、`smoothie` 返回 12 条，所以 IG 用单词或去空格的 token（`portableblender`），TikTok 才用 2–3 词短语。同一维度在两个平台可能要用不同的词，试探要分平台看。

⚠️ **竞品词有个实测反直觉的结果。** 首轮（便携榨汁机，2026-08-26）竞品词语义命中率
**30%，低于品类词的 38%** —— 因为它把品牌官方号、已签约的合作方（内容带
`#blendjetpartner`）、经销商都搜了进来，而这些恰恰是最不能联系的人。
设计时给竞品词 +15 的最高权重，**可能给高了**。需再跑 2–3 个品类确认是否普遍，
记在 `docs/SPEC.md` 的待验证清单里。

**然后必须小样试探**：每词每平台抓 1 页，把真实抓到的人摆给用户看，问"这批对吗"。

这是新版最重要的增量。现有实现一口气抓完才发现方向错了，钱和时间都已经花掉。试探成本约 20 次请求（两个平台，不到 3 美分），能避免整轮返工。

试探结果明显不相关时，Agent 应主动换词重试，而不是硬着头皮往下跑。若某个平台整体召回都差（例如该品类在 IG 上就是没人做内容），应如实告知用户并建议单平台推进，而不是硬凑数量。

### Phase 03 — 规模采集（TikTok + Instagram）

策略确认后才放量。自动分页、全局去重、多关键词并行。

**双平台首发。** 两个平台的发现路径不同，关键词策略不能照搬：

| | TikTok | Instagram |
|---|---|---|
| 主路径 | 视频搜索 | **Reels 搜索** —— 两者都是按内容匹配，能过滤商家号 |
| 分页 | 有 | **无游标，一词封顶约 12 条** |
| 关键词长度 | 2–3 词短语 | **单词** —— 词组返回 0 条 |
| bio 完整度 | 搜索结果里没有，必须补 profile | 同样没有，同样要补 |
| 粉丝数 | 搜索结果里有 | **搜索结果里没有**，补 profile 才知道 |

**采集必须轮转，不能顺序执行。** 实测竞品词一个词就够 50 人，顺序跑会让场景词、
人群词、整个 IG 一条都跑不到 —— 四维策略作废。做法是先给每个关键词各抓一页，
再回头抓第二页。

**达标判断数的是「能进名单的人」**，不是采集总数 —— 两者差很多（实测 64 采集 → 36 入围），
用错会提前停止且未达标。

**成本闸门由用户在运行前设定。** 不预置默认数字 —— 不同人的预算和任务规模差异太大，任何拍脑袋的值都会误伤。Phase 01 收集，运行中主动提醒。

| 时机 | 行为 |
|------|------|
| Phase 01 | 询问本次预算上限（美元）。用户不给就按 $2 走，并明确告知这是假设值 |
| 每个 Phase 结束 | 报告累计花费与占预算比例 |
| 达 50% | 提醒一次，说明当前进度与预计总消耗 |
| 达 80% | 再次提醒，给出「继续 / 缩小目标人数 / 就此收尾」三个选项 |
| 达 100% | **暂停并保存断点**，给出「追加预算续跑 / 用已有数据收尾 / 缩小目标」三选项。追加后从断点继续，不重复已完成的关键词 |

估算按 **请求数 × 单价**。默认源单价 $0.001/请求，因此估算是**上限** —— 日请求量大时有阶梯折扣，实际只会更低。报告时说明这一点，不要让用户以为花超了。

另设一道与花费无关的护栏：**单关键词页数上限**（参考前一版实测值 4 页）。防的是单个关键词无限翻页，与预算闸门相互独立。

### Phase 04 — 语义筛选 ★

硬指标（粉丝区间、活跃度、有无邮箱、商务合作信号）照旧计分 —— 这部分是客观的，规则能做好。

**内容相关性交给判断**：Agent 读 bio + 最近若干条视频文案，回答"这个人适合推我的产品吗"，并给出**理由**。

产出形如：

- ✅ 做 5 分钟早餐内容，出镜频繁，厨房场景多 —— 强相关
- ⚠️ 标榜健身，但最近十条都在带减脂代餐 —— 与我方蛋白粉品类冲突
- ❌ 账号名含品类词但内容是搬运合集，无真人出镜 —— 疑似机构号

理由比分数重要。运营看得懂"为什么这人排在前面"，才会信任这份名单。

### Phase 05 — 增强（可选）

只对入围者做。500 人全量增强和 50 人精选增强，成本差一个数量级，而后者覆盖了几乎全部决策价值。

**缺少配置时必须优雅降级** —— 跳过这一步，流程照常走完。

### Phase 06 — 交付

- 分层名单（见 §7）
- 每人一封开发信草稿，基于 Phase 04 实际读到的内容
- `kol.csv` 单表（给脚本读）+ `kol.xlsx` 按 A/B/C 分 sheet（给人看）+ HTML 报告
- 成本与召回统计（花了多少、抓了多少、命中率）

**开发信只写英语。** 首版不做多语言。

这不只是省事 —— 多语言意味着 Agent 要判断每个创作者的母语、要保证非英语文案的地道程度（写得生硬比写英语更伤），还要处理日语敬语这类文化规约。收益不确定，风险明确。

**派生影响**：目标市场默认按英语区理解（美/英/加/澳）。做增强时如果拿到受众地域，英语区占比低的创作者应降权 —— 给一个西语区博主发英文信，命中率本来就低。

## 7. 关键业务规则

### 创作者准入

| 规则 | 值 | 依据 |
|------|-----|------|
| 粉丝下限 | 5,000 | 低于此互动数据噪声太大，且多为素人 |
| 粉丝上限 | 5,000,000 | 高于此基本走 MCN，个人建联无效 |
| 活跃度 | 视频数 > 30 | 低于此可能是弃号 |

上下限应可按预算和品类调整，不写死。

### 分层与对应动作

分层的意义在于**对应不同的建联动作**，不是给个好看的标签。

| 层级 | 含义 | 建议动作 |
|------|------|----------|
| **A** | 有可用联系方式 + 内容强相关 | 直接发个性化开发信 |
| **B** | 内容相关但联系方式缺失或存疑 | 先在其内容下互动，或走站内私信 |
| **C** | 有潜力但当前不匹配 | 存入观察池，下次任务复用 |

### 跨平台同人识别

做双平台之后新增的规则。同一个人在 TikTok 和 IG 都有号，价值高于任一单平台账号 —— 触达更广，且愿意跨平台经营的创作者通常更认真对待商务合作。

识别信号（按可靠度排序）：

1. bio 里互挂链接 —— IG bio 挂 TikTok 链接、TikTok `bio_link` 指向 IG，最可靠
2. handle 完全相同或高度相似
3. 昵称 + 头像同时接近

合并后按"人"而非"账号"计入名单，粉丝数取两平台之和，并在输出中标注 `cross_platform: true`。这一条**加分**，因为前一版（BrightData 那套）就把"平台覆盖"给了 15% 权重，方向是对的。

识别不确定时**不合并** —— 错误合并两个人比漏合并同一个人代价大得多。

### 跨任务记忆

存本地 JSON，单文件 `memory/creators.json`，以 `platform:handle` 为主键。同人合并后额外记一条 `linked_to` 指向另一平台身份。

每条记录：

- 首次发现时间、来源关键词、来源产品
- 被推荐过几次、分别为哪个产品
- 人工标记位：`contacted`、`replied`、`blocked`

**关于"已联系"**：Skill 只生成草稿、不发信，因此**它只能知道"推荐过"，无法知道"联系过"**。`contacted` 是给用户手动标记的字段 —— 直接改 JSON，或跟 Agent 说一声由它写入。不主动追问（见 §6 关于回访的决定）。

规则：

- **已推荐过的人默认不再进新名单**，除非换了产品且契合度更高，此时标注"曾为 X 产品推荐过"让用户自己判断
- 标了 `contacted` 或 `blocked` 的人一律排除
- 记忆是本地文件，不做多人共享。单人使用足够；团队场景需要另行设计，当前不在范围内

## 8. 非功能需求

| 需求 | 说明 | 为什么是硬约束 |
|------|------|----------------|
| **零配置可跑** | 只需一个数据源 key，其余全部可选 | 这是发布给别人用的 Skill。任何"再去注册一个服务"的要求都会劝退绝大多数人 |
| **优雅降级** | 可选依赖缺失时跳过对应能力，不阻塞主流程 | 同上 |
| **成本可预测** | 用户运行前设定预算，运行中按阈值提醒，超限即停 | Agent 天然倾向发散探索，且用户看不到请求在烧钱。必须让花费全程可见（见 §6 Phase 03） |
| **数据源可替换** | 定义适配接口，换供应商不动编排逻辑 | 数据源是商品层，不该锁死 |
| **跨 Agent 兼容** | Claude Code / Codex / OpenCode 等 | 扩大可用人群 |
| **产出可离线查看** | 本地 CSV + HTML，不依赖在线服务 | 运营要发给同事、要存档 |

---

## 9. 数据源策略

详见 `docs/data-source-strategy.md`。此处只记业务侧的结论：

**"发布给别人用"这一条约束，直接决定了数据源只能在自助注册的几家里选。** CreatorDB、Modash API、Phyllo 数据更好，但都是申请制或销售报价 —— 别人 clone 下来卡在等审批，Skill 就废了。这不是数据质量问题，是分发问题。

因此：

- **默认源**必须支持即时注册、同步返回、按次计费
- **增强源**可以更贵更好，但必须是可选的

## 10. 已定决策

| # | 问题 | 决定 |
|---|------|------|
| 1 | 首发平台 | **TikTok + Instagram 同时**。派生出跨平台同人识别规则，见 §7 |
| 2 | 记忆存储 | **本地 JSON**，单文件 `memory/creators.json`。不做多人共享 |
| 3 | 开发信语言 | **仅英语**。目标市场默认英语区，非英语区受众降权 |
| 4 | 成本闸门上限 | **运行前由用户设定**，不预置默认值。50%/80% 提醒，100% 暂停并允许追加预算从断点续跑。另有独立的单关键词页数上限 |
| 5 | 回访环节 | **不做**。用户回填成功率太低，回复率因此不列为 Skill 指标 |

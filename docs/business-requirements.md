# 海外 KOL 建联 Skill — 业务需求

> 状态：草稿 v1 · 2026-08-25
> 这份文档只谈业务需求，不谈实现。技术选型见 `docs/data-source-strategy.md`。

---

## 0. 为什么重做

前一版（`tikhub-kol-sourcing`）跑通了完整链路，也验证了需求真实存在。重做不是因为它不能用，而是因为**复杂度花错了地方**：

| 现状 | 问题 |
|------|------|
| Phase 03 让用户"确认 TikHub 接口" | README 承诺"不需要懂 API"，却把接口选择暴露给非技术运营。实现细节泄漏到了用户界面 |
| 静态评分表（bio 含关键词 +15） | 用字符串匹配近似"内容相关性"。这恰好是 LLM 最擅长、正则最差的地方 —— 做了一个不如 SaaS 筛选器的东西 |
| 已抓取 `best_video_desc` 却只做参考 | 判断博主契合度最有价值的原料已经在手里，没被真正使用 |
| 产出停在 CSV | 运营拿到名单后的下一个动作是写信，而这一步的信息（博主在做什么内容）Agent 已经读过了，白白丢弃 |
| 历史索引记录"每次任务" | 记的是运行批次，不是人。同一博主跨关键词、跨产品重复出现，没有"已联系过"的记忆 |
| 与 TikHub 硬绑定 | 数据源是可替换的商品层，不该锁死 |

**核心判断：这个 Skill 的护城河是判断力，不是数据获取能力。**

任何人都能包一层采集 API。Modash、Heepsy 这些 SaaS 在筛选和导出上做得比我们好。Agent 唯一不可替代的是语义判断 —— 读懂产品、推导搜索策略、判断内容调性是否匹配、写出有针对性的第一封信。新版本的复杂度必须集中在这四件事上。

---

## 1. 产品定义

一个 AI Agent Skill。运营用自然语言描述自己卖什么，Agent 完成从产品理解到可发信名单的全过程，产出带个性化开发信草稿的分层名单。

**不是**采集工具，**不是** SaaS 的命令行版本。是一个替运营做完"找谁、为什么是他、第一句话说什么"的助手。

---

## 2. 用户

### 主用户：出海运营 / 独立卖家

- 不写代码，可能没听说过 API
- 手上有 1–N 个 SKU 要推
- 当前做法：在 TikTok/IG 手工搜索，逐个点开主页看粉丝数，把 bio 里的邮箱复制进表格
- 现状产能：一天 30–50 人，且质量全凭手感
- 判断标准：这批人靠谱吗、我该先联系谁、信怎么写

### 次用户：clone 这个 Skill 的开发者

- 会改 prompt 和脚本，但不想重写架构
- 需要能换数据源、调评分权重、改输出格式
- 对他们的承诺：改配置就能换供应商，不用动编排逻辑

### 明确不服务

- 需要团队协作、审批流、合同与付款管理的中大型团队 —— 那是 CreatorIQ / Aspire 的领域
- 需要投放效果归因的 —— 需要接店铺和广告数据，是另一个产品

---

## 3. 待解决的问题

按对结果的影响排序。这个排序决定了复杂度该往哪儿投。

### P0 — 不知道该搜什么词

最前置也最致命。搜错词，后面每一步都在浪费。

运营知道自己卖便携榨汁机，但不知道该搜 `juicer`（一堆商家号）、`smoothie recipe`（场景对但可能是美食博主不测评产品）、还是 `kitchen gadgets`（泛但精准度低）。

**这是 Agent 相对人类运营的最大优势** —— 它能从产品推导出四个维度的候选词，并且能在小样验证后调整。

### P1 — 拿到名单不知道信怎么写

群发模板回复率通常 <2%。有针对性的第一句话能到两位数。

差距全在"你是否真的看过他的内容"。而 Agent 在筛选阶段本来就读过了 —— 不用这个信息是纯浪费。

### P2 — 肉眼筛选无法规模化

粉丝量、互动率这些硬指标好办。难的是"这个人的内容调性适合我的产品吗"。

一个健身博主，粉丝 8 万、互动率 5%，看起来完美 —— 但他最近十条全在带减脂代餐，和你的蛋白粉直接冲突。这种判断只能靠读内容。

### P3 — 发了信才发现人选不对

受众地域不符（你卖美国，他 80% 粉丝在巴西）、刷粉号、邮箱是死的。样品和时间都白花。

这一层需要外部数据（受众画像、邮箱验证），是**可选增强**而非核心，因为它有成本门槛。

### P4 — 重复联系同一个人

跨关键词、跨产品、跨时间，同一个博主会反复出现。重复发信显得不专业，也浪费额度。

现有实现完全没有这层记忆。

## 4. 成功指标

| 指标 | 目标 | 怎么测 |
|------|------|--------|
| 单次任务耗时（说一句话 → 拿到名单） | < 15 分钟 | 人工计时 |
| 单次任务 API 成本 | < $2 | 运行日志累计 |
| 名单中"值得发信"的比例（人工复核） | > 60% | 抽样 50 人盲评 |
| A 级候选邮箱有效率 | > 90% | 发信后退信率反推 |
| 开发信回复率 | > 8% | 用户回填 |
| 零配置跑通率（只有一个 key） | 100% | 新环境验证 |

**关于回复率**：Skill 本身测不到，必须靠用户回填。这反过来是个设计要求 —— 见 §6 Phase 07。

## 5. 范围边界

### 做

- 产品理解与搜索策略推导
- 多平台创作者发现（TikTok 起步，IG / YouTube 随后）
- 语义契合度判断 + 分层
- 可选的邮箱验证与受众画像增强
- 个性化开发信草稿
- 结构化产出（CSV + 可读报告）
- 跨任务的创作者记忆

### 不做（及原因）

| 不做 | 原因 |
|------|------|
| **实际发送邮件** | 送达率、SPF/DKIM、退信处理、发信域名预热是另一个量级的复杂度，且必须用用户自己的邮箱服务。Skill 产出草稿，发信交给用户现有工具 |
| CRM / 跟进管理 | 变成长期状态管理，超出 Skill 形态 |
| 合同、付款、寄样物流 | 平台方（TikTok Shop / TCM）和专业 SaaS 做得更好 |
| 投放效果归因 | 需要接店铺和广告数据 |
| 中国大陆平台（抖音/小红书/快手） | 本产品定位出海。技术上数据源支持，将来可扩展，但账号体系、合规要求、建联方式完全不同，不应混在同一个流程里 |

## 6. 核心工作流

设计原则：**便宜的步骤先跑，贵的步骤只对幸存者跑。**

```
01 产品理解      能从链接推的绝不问用户
02 策略 + 试探   ★ 小样验证搜索方向，不对就重来
03 规模采集      策略验证过了才放量
04 语义筛选      ★ 读内容判断契合度，输出理由而非分数
05 增强（可选）  只对入围者做邮箱验证 + 受众画像
06 交付          分层名单 + 每人一封开发信草稿
07 回访          ★ 下次运行时询问上批结果，回填记忆
```

### Phase 01 — 产品理解

给一个商品链接（亚马逊 / 独立站）就应该能推出大部分信息：品类、卖点、价位、目标人群。

**只问推不出来的**：目标市场（美国？欧洲？东南亚？）、预算档位、这次要找多少人。

反模式：把七个维度做成问卷让用户逐个填。运营会在第三个问题时放弃。

### Phase 02 — 策略 + 试探 ★

四个维度生成候选关键词：

| 维度 | 例（便携充电宝） | 特点 |
|------|------------------|------|
| 品类词 | `power bank review` | 精准但商家号多 |
| 场景词 | `travel essentials tech` | 找到真实使用场景的内容创作者 |
| 竞品词 | `anker power bank` | 已经在测评同类产品，转化意愿最高 |
| 人群词 | `iphone accessories` | 覆盖面广，精准度低 |

**然后必须小样试探**：每词抓 1 页，把真实抓到的人摆给用户看，问"这批对吗"。

这是新版最重要的增量。现有实现一口气抓完才发现方向错了，钱和时间都已经花掉。试探的成本约 10 次请求（不到 1 美分），能避免整轮返工。

试探结果明显不相关时，Agent 应主动换词重试，而不是硬着头皮往下跑。

### Phase 03 — 规模采集

策略确认后才放量。自动分页、全局去重、多关键词并行。

**必须有成本闸门**：单次任务的请求数上限、目标人数达标即停。Agent 不能失控烧钱。

### Phase 04 — 语义筛选 ★

硬指标（粉丝区间、活跃度、有无邮箱、商务合作信号）照旧计分 —— 这部分是客观的，规则能做好。

**内容相关性交给判断**：Agent 读 bio + 最近若干条视频文案，回答"这个人适合推我的产品吗"，并给出**理由**。

产出形如：

- ✅ 做 5 分钟早餐内容，出镜频繁，厨房场景多 —— 强相关
- ⚠️ 标榜健身，但最近十条都在带减脂代餐 —— 与我方蛋白粉品类冲突
- ❌ 账号名含品类词但内容是搬运合集，无真人出镜 —— 疑似机构号

理由比分数重要。运营看得懂"为什么这人排在前面"，才会信任这份名单。

### Phase 05 — 增强（可选）

只对入围者做。500 人全量增强和 50 人精选增强，成本差一个数量级，而后者覆盖了几乎全部决策价值。

**缺少配置时必须优雅降级** —— 跳过这一步，流程照常走完。

### Phase 06 — 交付

- 分层名单（见 §7）
- 每人一封开发信草稿，基于 Phase 04 实际读到的内容
- CSV + 可读报告
- 成本与召回统计（花了多少、抓了多少、命中率）

### Phase 07 — 回访 ★

下次运行时，Agent 应主动问上一批的结果：发了多少、回了多少、成交几个。

两个作用：填上 §4 里 Skill 自己测不到的指标；让评分权重能基于真实反馈调整，而不是永远用拍脑袋的初始值。

## 7. 关键业务规则

### 创作者准入

| 规则 | 值 | 依据 |
|------|-----|------|
| 粉丝下限 | 5,000 | 低于此互动数据噪声太大，且多为素人 |
| 粉丝上限 | 5,000,000 | 高于此基本走 MCN，个人建联无效 |
| 活跃度 | 视频数 > 30 | 低于此可能是弃号 |

上下限应可按预算和品类调整，不写死。

### 分层与对应动作

分层的意义在于**对应不同的建联动作**，不是给个好看的标签。

| 层级 | 含义 | 建议动作 |
|------|------|----------|
| **A** | 有可用联系方式 + 内容强相关 | 直接发个性化开发信 |
| **B** | 内容相关但联系方式缺失或存疑 | 先在其内容下互动，或走站内私信 |
| **C** | 有潜力但当前不匹配 | 存入观察池，下次任务复用 |

### 跨任务记忆

以创作者身份（平台 + handle）为主键，持久化记录：

- 首次发现时间、来源关键词
- 被推荐过几次、分别为哪个产品
- 是否已联系、联系结果

**规则：已联系过的人不再出现在新名单的 A 级中**，除非用户明确要求复联。

## 8. 非功能需求

| 需求 | 说明 | 为什么是硬约束 |
|------|------|----------------|
| **零配置可跑** | 只需一个数据源 key，其余全部可选 | 这是发布给别人用的 Skill。任何"再去注册一个服务"的要求都会劝退绝大多数人 |
| **优雅降级** | 可选依赖缺失时跳过对应能力，不阻塞主流程 | 同上 |
| **成本可预测** | 每个 Phase 有请求上限，运行结束报告实际花费 | Agent 天然倾向发散探索，必须有闸门 |
| **数据源可替换** | 定义适配接口，换供应商不动编排逻辑 | 数据源是商品层，不该锁死 |
| **跨 Agent 兼容** | Claude Code / Codex / OpenCode 等 | 扩大可用人群 |
| **产出可离线查看** | 本地 CSV + HTML，不依赖在线服务 | 运营要发给同事、要存档 |

## 9. 数据源策略

详见 `docs/data-source-strategy.md`。此处只记业务侧的结论：

**"发布给别人用"这一条约束，直接决定了数据源只能在自助注册的几家里选。** CreatorDB、Modash API、Phyllo 数据更好，但都是申请制或销售报价 —— 别人 clone 下来卡在等审批，Skill 就废了。这不是数据质量问题，是分发问题。

因此：

- **默认源**必须支持即时注册、同步返回、按次计费
- **增强源**可以更贵更好，但必须是可选的

## 10. 开放问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | 首发平台只做 TikTok，还是 TikTok + IG 同时？ | 影响 Phase 03 复杂度和首版交付时间 |
| 2 | 跨任务记忆存哪里 —— 本地 JSON 够用，还是要考虑多人共享？ | 单人用本地足够；团队用需要另想 |
| 3 | 开发信草稿要不要多语言（英/日/西）？ | 目标市场如果不止英语区，这是必需项 |
| 4 | 成本闸门的默认上限设多少？ | 需要跑几轮真实任务才能定出合理值 |
| 5 | Phase 07 回访的数据，用户真的会填吗？ | 如果不填，评分权重就只能靠人工调 |

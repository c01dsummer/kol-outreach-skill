# ADR-17 需求登记表的元数据要么派生要么删；交点在计量里有了位置

> ⚠️ **本条落地的内容指纹当时只覆盖顶层字段** —— 交点的裁决改成相反的意思，
> 指纹纹丝不动。已由 ADR-18 修好。本条声称的「手改需求不回写当场变红」，
> 在修好之前只对顶层字段成立。

- 日期 · 2026-08-28 · ADR-15 边界里留下的待决项
- 类型：**流程补缺**（登记表缺三样东西：可校验的元数据、指回决策的链接、交点的归属）
- 冲击的需求：**无**。不改任何一条需求的文本，只改登记表的结构与检查链
- 结论：**采纳**

### 触发它的事实

四件事凑成同一个形状 —— **写在纸上但没人查，于是慢慢变成假的**：

1. `docs/requirements.json` 第 3 行的 `"version": 1`，2026-08-25 写下之后
   经历 5 次需求改动（新增 D8/D9/D10/F8/U7，重写 U5/U6/P5/D6/D8 的验收标准）
   **一次都没有递增过，也没有任何检查发现**。这正是 ADR-13 驳回缓存版本号时
   说过的话：「版本号把一次性的问题换成永久的问题 —— 忘记递增不报错」
2. 决策记录里有「冲击的需求：编号」，那是**正向**链接。审计据它能回答
   「这条需求被引用了吗」，却回答不了「**这句话是哪次决策的结果**」。
   U5/U6 在 `34ff0ea` 里被就地改写，旧文本只活在 commit message 里
3. `process/1-REQUIREMENTS.md` 早就规定「作废时保留编号并标记作废」，
   而登记表**没有这个字段**。第一次作废发生时才补，一定是赶在最忙的时候补
4. 交点没有归属。审计的计量单位是「每条需求有没有测试」，于是
   **交点上的测试写了不加分，不写不扣分** —— D4 × P4 那个红线失效就是这么活下来的

### 结论与边界

**一、元数据：派生，或者删掉，没有第三条路**

- `version` 删除，换成 `content_hash`（需求内容的 sha256 前 12 位）
- `content_hash` 与 `updated_at` 都由 `spec-sync --write` 写，**没有人需要记得改**
- 手改需求不回写 → `npm run spec` 当场变红，并打印实际指纹
- 指纹只覆盖需求本身，不含它自己和 `updated_at`（否则自我循环）；
  比较用键序无关的序列化 —— 磁盘上的键序由写下它的那一版代码决定（ADR-13 同一个坑）

**二、`adr` 反向链接**

每条需求可以列出**塑造了这条文本**的决策记录 —— 不列所有提到它的（ADR-04 那种
横切的已知缺口不算）。双向都校验：登记表里的 ADR 编号必须存在，
决策记录「冲击的需求」里的编号也必须存在。后者是「编号不回收复用」
唯一查得了的那一半。

14 条需求补上了链接。**U5/U6 没有** —— 它们当初就是在一条 commit 里就地改的，
没有决策记录可指。这个空缺现在是显式的。

**三、`deprecated`**

字段 + 渲染（单独成节，不混进现行表）+ 审计（不计入覆盖率，编号仍然列出）。
目前**没有任何一条需求作废**，所以这条路径靠 harness 测试和 M-H3-a 撑着，
不是靠真实数据。

**四、交点在计量里有了位置**

- 登记表的 `tension`：声明在**让步的那一方**，双向声明会被当场拦下
  （两处各写一遍迟早出现两种说法）
- 裁决渲染进 `SPEC.md` —— 只躺在 json 里等于没写
- 测试里用 `tension('A', 'B')` 认领一个交点，审计逐个找
- **交点里有红线的，没有测试认领就是硬失败** —— 红线第 2 条硬要求的自然延伸

登记了三处交点：**D4 × P4**（ADR-15）、**D4 × D6**（ADR-08）、
**F5 × P1**（裁决在 `docs/CONVENTIONS.md` 第 2 条，没有 ADR）。
第三处此前完全没有测试，这次补上：缺增强层时主流程走完（F5）不等于
给缺失字段填值（P1）。

**边界：**

- 判定抽进 `scripts/check/spec-rule.ts`，`spec-sync.ts` 只剩读写、打印、退出码 ——
  与 `lint-rule.ts` / `why-rule.ts` 同一个理由，也是同一条踩过五次的坑
  （`docs/CONVENTIONS.md` 第 10 条）
- 决策记录里的编号形状**从分类前缀派生**，不写死成「一个大写字母加数字」。
  写死的话，换一个用长前缀的项目，这条检查会安静地一条都匹配不到 ——
  一个永远通得过的检查等于没有检查。这一条是被自己的测试抓出来的：
  fixture 用了两字母编号，检查没反应
- **`tension` 挡不住「该声明而没声明」。** 它只保证已声明的交点有裁决、
  有测试；一个从没被人想到的交点，登记表里不会有它。能提前挡住的只有
  与红线的交点（`process/1-REQUIREMENTS.md` 新增那一节），
  剩下的仍然只能等实现或评审时撞出来

### 教训

**「以后记得改」不是一种机制，是一种许愿。**

`version: 1` 躺了三天、五次改动、无人发现，而它长得和一个正常工作的字段一模一样。
所有手工维护的元数据都会走到这一步 —— 区别只在于多久，以及是谁在什么时候
为它付代价。

判据只有一条，`process/README.md` 第二层早就写了：
**散文里的纪律是期望，能报错的检查才是保证。** 一个字段如果既不派生、
又没有检查盯着，它的正确性就等于最后一个改它的人的记性。

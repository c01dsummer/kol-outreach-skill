# ADR-58 把体量与集成纪律从第三层提到第二层

- 2026-08-31 · 复盘三条在途分支时发现
- 类型：**不属于反向输入的五类** —— 它改的是 `process/`，不触及需求登记表。
  按 `2-CHANGE.md`，这类改动本不必走评定；记下来是因为它动了通用层，
  而通用层的变动频率应当很低，每一次都该说得出理由
- 冲击的需求：无
- 结论：**采纳**

## 触发它的事实

三条在途分支，相对主干各自新增 4000+ 行：

| 分支 | 源码 | 测试 | 文档 |
|---|---|---|---|
| requirement-conflict-perspective | 926 | 880 | 2247 |
| durable-persistence-machinery | 1010 | 862 | 2250 |
| requirements-registry-machinery | 1179 | 863 | 2318 |

前两条之间只差 **366 行**（8 个文件），其余约 3700 行完全相同；
27 个文件里 **23 个被三条分支同时改过**。也就是说那次「拆成三个分支」
在 diff 层面没有拆掉任何东西，只是把同一坨复制成了三份。
主干在这三天里一次没动。

其中一条的描述里写着代价：「此前 29 条评审线程指向的是被替换掉的提交」。

## 为什么这不是纪律问题

`process/README.md` 把「一个任务 = 一个能一次读完的 diff」列在
**第三层（只能靠自觉）**，理由写得很清楚：「『能一次读完』没有阈值」。

而同一份文档的总纲是：

> 每一条你真正在乎的纪律，能变成检查就变成检查。
> 散文里的纪律是期望，能报错的检查才是保证。

所以这条纪律不是被违反了 —— 它**从来就没有被保证过**，
第三层的东西长期会怎样，这三条分支已经演示完了。

## 结论与连带改动

- 给它一个阈值：`npm run size`，分类计、只数新增、豁免必须具名（ADR 无，见提交）
- 决策记录拆成一条一个文件：`docs/adr/`，`npm run adr` 守着
- 新增 `process/6-INTEGRATE.md` —— 前五份管「需求怎么走到成品」，
  最后一步「成品怎么回到主干」以前没有正本
- `README.md` 的第三层删掉那一行，第二层补上它

## 教训

**三层之间只有一个正当的移动方向：给一条纪律找到判据，把它从第三层搬到第二层。**

反过来的移动（一条检查因为太吵而被降级成「大家注意一下」）是同一件事的失败版本，
而它在当下看起来总是合理的。

判据找不到时，第三层是诚实的落点，不是失败 —— 但「找不到判据」要每隔一段时间
重新问一次。这条纪律在第三层待了很久，而它的判据其实只是一个数字。

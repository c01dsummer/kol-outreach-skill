# ADR-26 存在性判断吞掉了权限错误；审计自己的判定抽出来交给变异守

- 日期 · 2026-08-28 · PR #5 第八轮自动评审，三条都成立
- 类型：**事实证伪**（三条都落在我这几轮刚建的东西上）
- 冲击的需求：**P4**（红线）· D4 · 审计的计量机制
- 结论：**采纳**，三条都改，并把审计的判定抽进可被变异守住的模块

### 一、`existsSync` 把「读不到」说成了「不存在」

`readMemory` 用 `if (!existsSync(FILE))` 分出 `absent`。而 **`existsSync`
对权限不足、父路径不是目录、IO 错误统统返回 `false`** —— 于是：

```
读不到（非 ENOENT）→ status=absent，名单照出=true
```

名单照常产出，`memory_status` 报的是「查过，记忆里确实没人」。
**刚刚拆开的三档，被一个存在性判断压回了两档**，而这一压正好压在 P4 上。

修法：直接读，**只有 `ENOENT` 才是 `absent`**，其余都是「没查到」。

### 二、同一个方向的交点声明两次

`validateRegistry` 只查了反向重复（A 声明 B、B 又声明 A），
没查同方向重复。一条需求把同一个 `with` 写两次、两条裁决互相矛盾，
校验放行；审计渲染两行，而运行时**一次** `tension('A','B')` 认领
同时算到两行头上 —— **一个测试证明了两条相反的裁决。**

### 三、一条判据都没认领，反而干干净净

判据缺口的条件写的是 `claimed.length && claimed.length < r.accept.length` ——
**只报「认领了一部分」那种**。于是一条判据都没认领的需求拿到 `✓` 和
`判据 0/N`，一条待办都没有。更糟的是它的激励方向：

> **把仅有的那条认领删掉，缺口就消失了 —— 这个检查在奖励删证据。**

修法：任何未认领且未豁免的判据都是缺口，按需求聚合成一行报出来。
改完之后审计如实多出几十条待办，红线仍然全绿。

### 四、顺带：审计自己的判定抽进 `spec-rule.ts`

这已经是**第三条落在 `audit.ts` 里的问题**（前两条是 ADR-20 的
「注释掉的认领照样算数」和上面第三条），而 `audit.ts` 的判定
**没有任何测试或变异守得住** —— 变异只跑 `scripts/test.ts`。

按 `docs/CONVENTIONS.md` 第 10 条（这条路已经踩过三次）把每条需求的裁定
抽成 `requirementVerdict(r, evidence)`：输入全是算好的事实，不读盘、不扫源码，
因而可被测、可被变异。`audit.ts` 只剩读盘、拼接、打印、退出码。
新增 M-H6-a / M-H6-b 守它。

### 五、一个存活的变异，抓出了一条已经失效的测试

改完第一条之后，`M-D4-e`（写不进去时把整个交付一起丢掉）**存活了**。
原因：那条测试用「父路径是文件」构造写失败，而第一条修完之后
`readMemory` 会在更早的地方就判定读不出来，`saveMemory` 根本没跑到 ——
**测试还在，绿着，但它已经不测那件事了。**

重建成真正「读得出来但写不进去」的场景：在写回用的临时文件名上放一个目录。
这正是 `4-VERIFY.md` 说的变异测试的价值：它抓的是「什么都没断言的测试」，
而一条因为上游改动而悄悄失效的测试，就是这种。

### 教训

**一个检查的激励方向，比它当下抓到了什么更要紧。**

第三条最值得记：它不是「漏报」，是**报得越少越干净**。
一条测试删掉之后审计更绿，那这个检查就在教人删测试 ——
而且删的人不会觉得自己在作弊，因为报告确实变好看了。

所以给检查写完判据之后，还要问一句：
**有没有哪种「什么都不做」或者「删掉一点东西」，会让这个检查更满意？**
有，就是这条判据写反了方向。

### 追记 · `onDisk` 又把「读不到」当成了「没有」—— 判断只留一份

- 拆分后第十三轮自动评审 · 类型：**事实证伪**（打的是 ADR-47 刚加的代码）· 冲击 P4 · D4

```ts
function onDisk(): string {
  try { return readFileSync(FILE, 'utf8') } catch { return ABSENT }
}
```

一行 `catch` 吞掉全部读失败。于是记忆文件在读与比对之间变得读不到时
（运营刚建了一个权限收紧的文件），比对拿「看不到」当「没有」放行，
改名把一份**从没读到过**的记忆盖掉，里面的 contacted 与 blocked 跟着消失。

**这正是本条第一节在 `readMemory` 里修过的那个塌陷** —— 它就在同一个文件、
隔几十行的地方，而我写这个新函数时一个字都没想起来。

修法是**让判断只有一份**：抽出 `isAbsence(e)`，`readMemory` 与 `onDisk` 共用 ——
因为上一次出事（ADR-46）正是同一个判断有两份副本、只修好了一份。
合并之后，原先守 `readMemory` 那条 `M-P4-i` 与新加的那条指向了同一行，
又是一次「两条变异在重复守一件事」，合并成一条。

**「隔壁函数刚记过的教训」不会自动作用到我下一个函数上。** 到这一轮为止，
同一个形状出现了三次：ADR-42（权限收得太晚）、ADR-46（新写的原子写没带上权限处理）、
本节（新写的函数重犯旧账）。三次都是**新代码重犯旧教训**，而不是旧代码没修好。
写下教训防不住这件事 —— 教训在决策记录里，而我写新函数时看的是代码。
唯一有效的是**让那个判断只存在一份**：一份的时候，新调用方自动继承它；
两份的时候，继承靠的是我记得，而我不记得。

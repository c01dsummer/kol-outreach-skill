# ADR-03 成本闸门不预置默认值，超限后允许追加预算续跑

- 2026-08-25 · 需求评审时由用户提出
- 类型：**发现更优解**
- 触发它的事实：初稿设计的是「达到预算上限即停止采集，用已有数据收尾」。
  用户指出应当允许追加额度后重新继续。
- 冲击的需求：P3 · F7 · D6
- 结论：**采纳**
- 理由：硬停会在两种常见情况下造成纯浪费 —— 预算估低了、或者关键词比预期多。
  两种情况下用户都愿意多花几毛钱跑完，而硬停逼他从头再来一遍（**已经花掉的钱白花**）。
  采纳的前提是采集必须可断点续跑（D6）：`task.json` 记录已完成的关键词索引与
  累计请求数，`--resume` 重入时跳过已完成项、以已有 requests 初始化 Budget，
  因此**不重复跑也不重复计费**。
  检查了这不是「降标准」：用户得到的信息没有变少或变模糊，
  相反他多拿到了一个明确的选择点。
- 连带改动：`skill/SKILL.md`（超限后的续跑一节）· `docs/business-requirements.md` ·
  `scripts/collect.ts`（退出码 3 + `--resume`）· `scripts/lib/budget.ts`（跨运行累加）
- 教训：**「达到上限就停」是个看起来安全实则昂贵的默认。**
  闸门的目的是让用户知情并做选择，不是替他做决定。
  凡是设计成「到点即停」的地方，都该问一句：停下来之后，他还能不能接着走？

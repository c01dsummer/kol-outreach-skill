### 事实

给 ADR-33 加变异时，我写了 `req: "H4"`。`H4` 不是任何一条需求的编号 ——
`H` 开头是检查链给自己留的名下，而它真正的写法是 `harness`，
另外十五条 `M-H*` 全都写对了。

`npm run check` 全绿。变异照样跑、照样被抓到，控制台打出 `✓ M-H4-f [H4] 被抓到`。

而 `audit.ts` 拿 `req` 去回答「这条需求有没有变异守着」—— 那条变异
**对任何一条需求都不算数**，记在了一个空名下。没有人被告知。

### 吵的那一半早就有人管了

写成**另一条真实存在**的编号是吵的：被顶替的那条会报「缺变异」。
写成**不存在**的编号是静默的 —— 而这一半没有任何检查。

### 连带改动

`scripts/check/attribution-rule.ts`（新模块）· `scripts/check/mutate.ts` ·
`docs/ARCHITECTURE.md` · `scripts/test.ts` ·
`scripts/check/mutations.json`（M-H7-a）

名下可以是一条需求，也可以是一条**验收判据** —— 豁免常常只豁免其中一条判据
（`P2.a`、`P3.b`）。第一版只认需求编号，当场被现有的三条豁免证伪。

### 教训

**这一条不是评审找出来的，是我自己在修上一条的时候踩进去的**，
而且是在一条「检查报绿不等于没问题」的记录正下方踩的。

值得记的是它怎么被发现的：不是靠检查（检查是绿的），是靠**看见输出里
`[H4]` 和旁边十五个 `[harness]` 不一样**。这一轮我一直在核对
「对面实际读的是什么」，恰好也就看了一眼那一列。

**绿色的检查链证明不了它自己的口径是对的。**

## 续：检查链第一步也读变异编号（2026-11-12）

ADR-70 末尾「变异残留」第三片给检查链加了第一步 `anchors.ts`，它按编号报锚点，又多了一处读变异编号的地方。它自己先拒重复编号，用的是 `mutate.ts` 那道检查同一个 `duplicateIds`（判定 `anchorVerdict`，配断言与变异）。另有一处早已在自己拒：`mutate-rule.ts` 的 `executionRoutes` 用自己的一个集合拒重复编号、抛错，`mutate.ts` 与启动数闸门 `launches.ts` 都经它读目录；本片没动它。整条 `npm run check` 跑时它恰好排在所有消费者之前；单跑 `npm run mutate` 或别的入口时不是，「所有消费者之前的一个统一阶段」照旧没做。第 5 行那张的条件响了，不带重新起算，所以在这里续挂。

> ⚠️ 已重挂：ADR-34 第 5 行 · 现行的是 ADR-34 第 57 行

> ⚠️ 欠条：变异编号的唯一性仍由每个读编号的地方各自先拒（`mutate.ts` 与检查链第一步共用 `duplicateIds`，`executionRoutes` 自己拒），没有一个所有消费者之前都经过的统一阶段 · 来源：ADR-34 第 5 行续挂 · 档：登记 · 重启条件：再出现一处新的读变异编号的消费者，或在 `executionRoutes` 之外又有一处读编号的地方不经 `duplicateIds` 自己拒，或定期清点

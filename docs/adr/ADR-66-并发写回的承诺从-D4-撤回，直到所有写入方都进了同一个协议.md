# ADR-66 并发写回的承诺从 D4 撤回，直到所有写入方都进了同一个协议

- 日期 · 2026-09-02 · 用户裁决（把一个大改动拆成多个时，对 D4 里这一句的去留）
- 类型：**产品取舍**（不是事实证伪 —— 事实 ADR-55 已经记过，这一条决定的是
  承诺该不该继续挂在需求上）。主干上 `2-CHANGE.md` 的五类里没有这一类，
  按 ADR-50 的先例标；ADR-16 把它补进分类表，那条与流程改动一起另行合入
- 冲击的需求：D4
- 结论：**D4 里「并发的两个写入方不得静默互相盖掉」整句撤回，改写成明确不保证**；
  代码里已有的比对保留

### 起因

D4 曾写：并发的两个写入方各自读改写时，不得让后写的把先写的静默盖掉 ——
不做串行化，但改名前要再确认一次盘上还是读到的那份，发现变过就报未写回。

拆分时按「谁在写」清点写入方（ADR-54），发现两个文件一共**五个**写入方：
`task.json` 有三步协议、采集途中的断点保存、`enrich`；`creators.json` 有三步协议的
第二步、`render`。参与改名前比对的只有三步协议的第一步和第三步，其余三个都是
无条件写（ADR-55）。不需要任何外部写入方，两个三步协议交错就能复现
「`memory_status = ok` 配一份未去重的名单」—— 那正是这句话说不会发生的事。

所以这句话是需求登记表里唯一一处**「声称做到了、其实没做到」**。

### 裁决

三条路摆给用户：

1. 把五个写入方全部纳入同一个协议，做到了再合 —— 那是一整条分支的工作量
2. 收窄成「以下 N 个写入方之间互不静默覆盖」，把 N 个逐个列出来
3. **整句撤回**，改写成明确不保证

用户选第三条。

- **代码保留** —— 改名前的比对已经写好也验过，留着有益无害。它现在的身份是
  「检测到撞车就响地失败」，不是一条要被追着查的承诺
- **D4 改成**：并发的两个写入方之间不作任何保证 —— 后写的可能把先写的盖掉，
  两个任务目录写入方交错时盘上也可能留下名单与声明不符；
  要把它变成保证，先把它变成一条需求
- **什么时候能回来**：五个写入方都参与同一个协议，且验收能写成
  「以下五个写入方之间互不静默覆盖」并逐个列出 —— 另一条需求，另一个改动

### 为什么不选收窄

按 ADR-55 的教训，收窄是最诚实的写法。但 N 现在等于 2，而那两个是**同一个进程里
的两步**（三步协议的第一步和第三步）—— 它们之间的比对保护的是一次运行内部的
顺序，不是两个进程。写成「以下两个写入方之间互不覆盖」对用户没有任何意义，
挂在需求上只是一句为了让检查通过的话。

ADR-50 那条原则在这里同样成立：**文档说少了不要紧，说多了才是问题。**

### 教训

ADR-55 写过「检测到了不等于挡住了」。这一条补的是它在需求侧的那半：

**一条承诺能挂在需求上的条件，是它的验收当下就能写成可失败的判据并且跑得过。**
做不到的先撤下来 —— 撤回是响的（读需求的人知道这里没有保证），
挂着是静默的（读需求的人以为有）。前者的代价是少一句话，后者的代价是
一份看起来完整、其中最要紧的那句是假的需求文档。

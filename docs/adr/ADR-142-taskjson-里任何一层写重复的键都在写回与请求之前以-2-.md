## 一、决定

1. **整份判，不逐字段判。** 读入只留最后一处，在哪个字段都是同一件事：盘上有几处，命令只看见一处，整份写回时其余几处消失。按名单逐个判（`tasks`、`requests`、`cost_ledger`、`budget_usd`、`brand_calibration`）要先猜哪些字段要紧，名单外的键与更深的位置（`tasks[0]` 里的 `keyword`、`cost_ledger` 里的项、进度值里的对象）照样被吞，以后新加的字段还得记着往名单里添。整份判一句话说得清，ADR-141 第四节那张（进度值里更深一层）也一并还掉。
2. **D19.k 那几处不动。** 根上五个进度键与四张表里的键照 D19.k–n 报，措辞与时机都不变；D27 只报其余位置，同一处不报两遍。人工反馈模板命令过去不判进度，这次两类一起判。
3. **其余位置的重复先写出，不遮住别的问题。** `tasks` 写重复时，任务列表按最后那份判；要是只在进度那一道报重复，用户会先照最后那份改任务，改完再撞上「写重复」。反过来也一样：只在任务列表那一道报、在那里就退出，同一份里 D19.k 的重复与坏进度这一轮都看不到（复核发现 2）。所以 collect 续跑与 render 先写出其余位置的重复，再照常判任务列表；任务列表有效时进度那一道照判，两类在同一次里报，再以 2 退出。enrich 与模板命令本来就只有一道。
4. **`calibration version` 照 D19.n。** 缺席与已一致都不写盘，盘上的几处原样留着，照旧以 0 结束；要写盘时与进度键的重复一起拒绝。
5. **只管 task.json。** collect --config 与 probe 读的是用户写的配置，见第四节。

## 二、逐条评定

1. **触碰红线吗？** 撞的是 P1（替用户挑一处、写回时抹掉其余几处）与 P3（`requests`、`cost_ledger`、`budget_usd` 按最后一处的计数或上限花钱）。拒绝不违反任何红线；两个交点都写了裁决。
2. **缩范围还是降标准？** 都不是。没有写重复的文件，五个命令的行为一字未改（D27.e）。
3. **可逆吗？** 可逆：五处调用删掉即回到原样。

## 四、边界

- collect --config 与 probe 读的配置文件不由本条判。那份文件是用户写的输入，不被整份写回；它写重复时 collect 按最后一处建任务，新建的 task.json 里只有那一处。
  P3 那一面同样在：配置里 `"budget_usd":1,"budget_usd":100` 读出来是 100 美元，collect --config 与 probe 按后一处开账（复核实测 `readCostLimit` 交回 `100000000`）。D27 × P3 的理由（不按最后一处的上限花钱）在这里一样成立；本条照需求所有者选的「整份判 task.json」划界，没有替他把配置文件一起划进来。

> ⚠️ 欠条（既有缺陷）：collect --config 与 probe 读的配置文件写重复的键时按最后一处读，`budget_usd` 写两次按后一处开账；主干上就这样 · 重启条件：本 PR 已合入（按 `process/6-INTEGRATE.md`「既有缺陷」排在下一条之前，由需求所有者定修不修）

- 上一层的键本身写重复时，下层的位置有歧义：`{"x":{"k":1,"k":2},"x":{"k":3}}` 报 `x["k"]`（`1`、`2`）与 `x`（`{…}`、`{…}`）两条，用户打开留下来的那份 `x` 只看得到一个 `k`。D27.a 没要求分出是第几处的 `x`；两条合起来已够人找到，只是要多看一眼（复核发现 5）。

> ⚠️ 欠条（登记）：上一层的键写重复时，下层那一条的位置没写明在第几处 · 重启条件：下一条改 D27.a 的位置写法或 `lib/duplicate-keys.ts` 问题文本的改动，或有人因此找错地方
- 同一目录的并发写入按 D4 当前不保证（ADR-66）：命令跑到一半时有人手改 task.json 写出重复，费用检查点重读后只留最后一处，不在本条。

## 五、独立复核的发现与去向

复核对 `a822ea6`，在副本里以非 root 用户实跑。复核自己写了一个递归下降的参照解析器，随机生成六万份合法文档比对重复的位置与每一处原文，0 处不符；同一批文档上新的 `sourceDuplicateKeys` 与 `7214352` 上的旧实现逐字节一致。转义、反斜杠结尾、数组套数组、`__proto__`、2400 层嵌套、九百万字的字符串都试过。五个入口的拒绝都在改额、预留、请求与任何写入之前。

1. **档：本改动 · 阻塞 · 去向：本 PR 修。** D27.e 只由自检认领，没有一条 `by: selfcheck` 的负片，`audit` 硬失败。补 M-D27-aa（同一个数组里的几个对象共用一份键表，两个任务各有 `keyword` 就算写重复）。它先写成 `by: selfcheck`、点名自检两组的「不多拒」，单独施变时点名的两条红了，但自检里带费用账条目的阳性对照也跟着失败、带上夹具记号 —— 任何一种多拒的扫描都会这样，自检那边的负片按规矩记不上功。所以改由 `test.ts` 里判据一层那条「不多拒」认领 D27.e（复核提的第二种修法），M-D27-aa 改 `by: test`、点名那一条；入口那一半照旧由自检认领。
2. **档：本改动 · 阻塞 · 去向：本 PR 修。** collect 续跑与 render 把其余位置的重复放进任务列表那一道，在那里就退出；同一份里 `found` 的 D19.k 重复或坏进度值（`{"0":-1}`）这一轮都不报，本 PR 之前会报。违反 D19.l 与第一节第 2、3 条自己的理由。改成先写出其余位置的重复（另起一句「里写重复的键」，不再顶着「任务配置不合规」的标题），再照常判任务列表与进度，在两道的末尾以 2 退出（第一节第 3 条已改写）。D27.b 补半句「任务列表有效时也与进度问题一起」。
3. **档：本改动 · 去向：本 PR 修。** 测试缺口：「不报两遍」在 collect、render 上够不着（同一份里进度那一道根本没跑），在 `calibration version` 上没断言，三处各去掉一个 `true` 都不红，`calibration version` 那个实测把同一行打两遍。自检那条「进度键与别处同时写重复」改成三个入口两处都恰好一次，另加一份坏进度值 `-9.25e2` 与 `requests` 重复同在的 collect、render 用例；`test.ts` 的 `d20-content-version` 加一条 `calibration version` 两处各一遍。配 M-D27-t、u、v（去掉 `true`）与 M-D27-w、x（见到其余位置的重复就先退出）。另：`tasks-root` 用例的前一处原文 `zq-first-tasks` 自己就含位置 `tasks`，位置那一半是空转的，原文改成 `zq-first-list`。这几处测试是复核之后由写实现的上下文补的，不是先于实现写成。
4. **档：本改动 · 去向：本 PR 修。** 根上的键原样写出：空键位置是空的，控制字符原样进终端，根上的 `x["y"]` 与 `x` 里的 `y` 写出来一样；下层键名里带引号、反斜杠没有测试。根上的键为空、或含字母、数字与 `_ . -` 以外的字符时也写成 `["键"]`，D27.a 补这一句；`test.ts` 加一条，配 M-D27-y、z。
5. **档：登记 · 去向：第四节欠条。** 上一层的键本身写重复时，下层那一条的位置没写明是第几处。
6. **档：本改动（本记录措辞）· 去向：第四节补 P3 那一面，配置文件写重复记为既有缺陷，由需求所有者定。** 第四节只从 P1 论证配置文件不在范围内，没提 `budget_usd` 写两次按后一处开账。
7. **档：本改动 · 去向：本 PR 改。** 文首「冲击的需求」漏了 D19.k 的措辞改动。

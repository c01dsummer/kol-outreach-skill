# ADR-68 钱不是在 charge() 里花掉的：预算协议做成能穷举的模型

- 日期 · 2026-09-05 · 形式化验证试点，从静态盘点走到第一份可执行的模型
- 类型：**反向输入**（撞见几处需求没有决定的行为）＋ **事实证伪**（两处实现违反已有的红线）
- 触发它的事实：`Budget.charge()` 早有单元测试证明超限会抛，但**钱不是在那里花掉的** ——
  是在 `scripts/providers/tikhub.ts` 那一行 `fetch`。过闸门、发请求、把请求数写进
  `task.json` 是三步，步与步之间可以崩溃、可以续跑，而那两个窗口不在任何一个单元里
- 冲击的需求：P3 · P3.a · P3.b · F7.a · D6.a
- 结论：**采纳**（加一份可执行的模型与检查）＋ **接受为已知缺口**（崩溃窗口等四条，各带重启条件）

---

## 做了什么

`formal/budget/BudgetProtocol.tla` 与 `scripts/check/formal-rule.ts` 是**同一个转移系统的
两种写法**，`npm run formal -- --tla` 把两边的可达状态集逐个字符比一遍。

`npm run formal` 进了检查链，三件事买到的东西不一样，报告里必须分开说：

| 跑什么 | 保证到哪 |
|---|---|
| 抽象模型的全部可达状态（五个场景，56–2236 个状态）| 只对模型成立 |
| 真实的 `Budget` 与真实的 `TikHub.get()`，588 个响应序列、555 次真实提交 | 真实实现，但输入有界 |
| 两个钱字段的取值全域 | 真实实现，输入域有限所以是穷举 |

逐条的等级、边界、假设与人工核对表在 `formal/budget/IMPLEMENTATION-MAP.md`。

## 修了什么（实现违反已有的红线）

两处同一形状：**闸门那句比较的两边都是外部输入，而没有人查过它们是不是数。**

1. `--budget 3.0.0` 这样一个手误让上限变成 `NaN`，比较恒为假 —— 闸门不是宽了一点，
   是整条不存在；百分比同时恒为 0，连 50%／80% 的提醒都不出现（**P3 · F7**）
2. `task.json` 的 `requests` 是 `null` 时整本账退回零；是字符串时下一次请求让计数变成
   拼接（`"4"` → `"41"`），一次请求把账面翻十倍（**D6.a**）

判定写进 `scripts/lib/budget.ts`，`collect` / `enrich` / `probe` 三条入口共用一份。
`enrich.ts` 本来就查过 `--budget` 的有限性 —— 同一个判定有两份副本时，
**没查的那一份不会报错**（ADR-46 的形状，第三次）。

## 接受为已知缺口

### ⚠️ 欠条：崩溃与续跑之后，供应商收的钱可以超过已确认的上限

`npm run formal -- --trace SpendIsRecorded` 给的 5 步反例：过闸门、发请求、供应商收钱、
落盘之前进程死掉。再续跑一次就成了 12 步的 `NoOverspend` 反例 —— 少记的那一段，
下一轮被当成没花过。

**这不是一处写错，是这个架构的性质**：任何把落盘和发请求分成两步的实现都有这个窗口。
P3 的两条判据只说了 `charge()` 与退出码，D6.a 说「spent 连续不归零」也没说崩溃 ——
**登记表没有决定崩溃时该怎样**，所以这里不替它裁决。

代价随落盘节奏放大：关键词循环每抓一页落一次盘（窗口 1 次请求），
补 profile 那个循环**一次都不落盘**（窗口是整份候选名单），`enrich` 每个账号落一次。

· **重启条件**：有人要把崩溃安全变成保证（那要改协议：先写「打算发一次请求」再发，
或者按供应商账单对账），或者补 profile 那个循环的落盘节奏被改动时。

### ⚠️ 欠条：F7.a 的「一次」是每个进程一次还是每个任务一次，没有定义

提醒集合是进程内的，续跑新建一个实例就空了。跑到 85% 之后续跑，第一次请求会同时
打出「已用 50%」和「已用 80%」。按任务算的话，F7.a 与 D6.a 在这一点上就是一条交点，
而 `docs/requirements.json` 里没有它。

· **重启条件**：下次有人碰 `scripts/lib/budget.ts` 的提醒逻辑，或者用户反馈提醒刷屏。

### ⚠️ 欠条：预算用尽且记忆读不出来时退的是 2，不是 3

那条路径先 `persist()` 保住断点，再因为 P4 无法保证而中止（ADR-15 的裁决），
所以退 2 是**有意的**；但 P3.b 的措辞是无条件的「以退出码 3 结束」，
而 `docs/requirements.json` 里没有 P3 × D4 这条交点。两侧都是红线 ——
按 `process/2-CHANGE.md`，**实现者不许自选一条违反，退回需求所有者消解**。
建议的裁决是把 P3.b 的措辞收成「没有更高优先的中止理由时」，交点写在 P3 一侧。

· **重启条件**：下次改 `collect.ts` 的收尾分支，或者有人按 P3.b 的字面写检查。

### ⚠️ 欠条：「非 200 供应商不计费」是承重的假设，而它只活在一行注释里

把它取反，`NoOverspend` 立刻被 10 步反例违反。没有需求、没有决策记录、没有测试。
429 重试把它放大：一次调用最多向供应商提交 4 次（`attempt` 从 0 数到 3），本地最多记 1 次；
IG profile 的 V3→V2 回退再乘一次 —— 最多 8 次提交、1 次计数。

· **重启条件**：拿到一份真实账单可以核对时，或者供应商改计费口径时。

### ⚠️ 欠条：`probe` 的花销不写盘；两个进程同时对着一个任务目录跑时后写的会盖掉先写的

前者是 `docs/ARCHITECTURE.md` 写明的「probe 不落盘」的代价：F1 向用户要的是**一个**
预算上限，而 probe 那 20 次请求不进任何账。后者是 `collect` 与 `enrich` 都把计数
**整体赋值**回 `task.json`；D4 已经就记忆文件撤回过并发承诺（ADR-66），`requests`
不在那条撤回里，也不在任何保证里。

· **重启条件**：Agent 被允许并行跑 `collect` 与 `enrich` 时，或者有人要把 P3 的上限
说成「整个任务的」而不是「每个进程的」。

## 教训

**「这个函数验过了」和「这条红线守住了」之间，隔着一个没有人建模的协议。**

`charge()` 有测试、有变异、有验收判据认领，报告上 P3.a 是绿的。而 P3 说的是
「未经用户确认不得超出预算上限」—— 那句话的主语是**供应商真正收的钱**，
代码里没有任何变量装着它，所以也没有任何一条断言在看它。

判据落在能观测到的量上是对的；错在**没有人问过「这个量和红线说的是不是同一个量」**。
形式化在这里买到的不是「更多测试」，是把那个没有变量装着的量**显式写进状态**，
于是它和红线之间的差第一次可以被计算。

第二条：**负例要和正例一起进仓库。** `broken-charge` 那个场景不是演示，
它是这套资产的自检 —— 抓不到它就说明检查器坏了。同理，
每个场景**预期的最短反例长度**也记下来了：模型被改松、反例变长，一样红。
一条只会因为「变绿」报警的检查，在模型被改松时是哑的。

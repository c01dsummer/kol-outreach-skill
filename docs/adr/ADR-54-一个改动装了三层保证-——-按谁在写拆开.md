# ADR-54 一个改动装了三层保证 —— 按「谁在写」拆开

- 日期 · 2026-08-31 · 用户：「现在这个 PR 太大了，split it」
- 类型：**范围失控**（第二次。第一次是 ADR-35）
- 冲击的需求：D4
- 结论：**拆成三个改动**，本改动只留最里面那一层

### 事实

ADR-35 拆过一次，把「需求登记表的机器」拿走了。之后又跑了十六轮评审，
这一半自己重新长回 4609 行。

拆开看，它装的其实是**三层不同的保证**，一层比一层强：

| 层 | 保证什么 | 坏了会怎样 |
|---|---|---|
| 一、读侧红线 | 记忆读不出来时不产出名单、绝不覆盖那份记忆 | **静默地重复打扰已拉黑的人** |
| 二、一个写入方 | 写到一半被打断，盘上留下的不会是一份骗人的东西 | 被打断时留下截断的文件 / 说谎的状态 |
| 三、多个写入方 | 两个进程同时写时不互相盖掉 | 并发时静默丢记录 / 名单与声明不符 |

三层是**依次加强**的，所以之前一直在同一个改动里往上加。
但它们的**证据要求完全不同**：第一层用普通用例就能验；第二层要构造中断；
第三层要构造交错 —— 而第三层的正确性，这一轮自查证明**它并没有做到**。

### 为什么正好切在二和三之间

不是按文件切，是按**「谁在写」**切：

- 第二层的每一句话，在「只有一个写入方」这个前提下都是真的
- 第三层的每一句话，都需要「所有写入方都参与同一个协议」，而**现在只有两个参与了**：
  `task.json` 有三个写入方（三步协议、采集途中的断点保存、`enrich`），
  `creators.json` 有两个（三步协议第二步、`render`），
  其中只有三步协议的第一步和第三步带了改名前的比对。第二步压根没带。

也就是说：**第三层是这个改动里唯一一处「声称做到了、其实没做到」的地方。**
把它留在本改动里，等于让一句假话搭着两句真话一起合入。

### 怎么拆的

- **本改动**：第一层 + 第二层 —— 三档状态、形状校验、重复键、键的规范化、
  `--ignore-memory` 与 `memory_status` 的声明、整体替换（临时文件 + 改名 +
  权限位）、孤儿临时文件清理、三步落盘。**并发和刷盘明写成不保证。**
- **`claude/durable-persistence-machinery-z23u9v`**：第三层 + 崩溃持久性 ——
  改名前的比对、五个写入方全部入事务、刷盘。自查查出的两条 P1 在那里修。
- **`claude/requirements-registry-machinery-z23u9v`**：需求登记表的机器（ADR-35 拆走的那半）。

**决策记录跟着它讲的东西走。** ADR-16/17/23/24/27/28/31/33/34（登记表机器）
与 ADR-49/50（刷盘）已经从本改动移走 —— 编号**留空不复用**，
它们活在各自的分支上。

### 教训

**「一层比一层强」不是「该放在同一个改动里」的理由，反而常常是相反的信号。**

依次加强意味着**每一层的前提都比上一层多一个**。前提越多，能证明它的场景越窄；
而一个改动的可评审性，取决于**最窄的那一层**能不能被证明。这一轮的第三层，
证不了 —— 而它被两层证得动的东西驮着，一路走到了第十六轮。

ADR-35 的教训是「每轮多做三件事会复利」。这一条是它的另一面：
**范围不只从「多做」长出来，也从「往上再加一层保证」长出来** ——
而后者看起来一直像是在把同一件事做得更对。

判据：**问「这一层需要几个前提才成立」，前提变了就该是另一个改动。**

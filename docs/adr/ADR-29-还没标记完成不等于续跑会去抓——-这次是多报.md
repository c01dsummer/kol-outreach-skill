# ADR-29 「还没标记完成」不等于「续跑会去抓」—— 这次是多报

- 日期 · 2026-08-28 · PR #5 第十一轮自动评审
- 类型：**事实证伪**（同一句承诺的第五轮，但方向相反）
- 冲击的需求：**D6** · P3
- 结论：**采纳**

### 触发它的事实

达标提前停下时（`qualified() >= target_count`），`run()` 直接 `break`，
**剩下的关键词一个都没被碰过，也不会被写进 `state.done`**
（末尾那轮只把「跑满页数上限」的标记为完成）。

于是 `pendingKeywords(state)` 把它们算成待办，我的消息说
「还有 N 个关键词没跑完，续跑会继续发请求、继续花钱」。

而实际上：续跑先把累加器读回 `creators`，`run()` 的第一件事就是再查一次达标 ——
**同一个数、同一个门槛，立刻 `break`，一个请求都不发。**

### 方向相反，危害不同

前四轮那句承诺都是**少报**：告诉用户不花钱，实际要花。这一轮是**多报**。

多报看起来是「安全的那一侧」，但它有自己的代价：

> 用户被告知「续跑要花钱」，可能因此**不敢续跑** ——
> 而不续跑就永远拿不到那份已经付过费的名单。

一句不准的话，往哪边不准都会让人做错决定。**「保守」不是准确的替代品。**

### 结论

新增 `keywordsResumeWillRun(state, qualified)`：达标了就返回空，
否则才是 `pendingKeywords`。消息用它，进度汇报仍然用 `pendingKeywords`
（那是「还没跑完」的口径，服务的是进度不是花钱）。

D6.c 的验收判据改写成：**剩余工作量按「续跑真正会执行的路径」算** ——
关键词按「续跑会去抓的」，profile 按补全循环用的同一个判定。

### 教训

**同一个集合，服务两个问题时口径可能不同 —— 别让它们共用一个函数名。**

`pendingKeywords` 回答的是「还有多少活没干完」（进度）。
我拿它去回答「续跑要花多少钱」（成本），而这两个问题在**达标提前停下**
这一种情况下答案不一样。名字里的 "pending" 掩盖了这一点：
它听起来像个通用事实，实际上是一个特定口径。

判据仍然是 ADR-25、ADR-28 那一句 —— **问「对面实际会执行什么」，
不要问「我这边还剩什么」** —— 只是这次它指向的是同一句话的另一侧：
上几轮我漏掉了对面会执行的东西，这一轮我算进了对面不会执行的东西。

## 一、决定

- 新命令 `npm run jargon`：这条分支在 Markdown 里新加的行，列出三种多半要配白话的写法，**永远以 0 退出**，不挡合并。
  - **生词**：加粗或打书名号的短词（2 到 8 个字，不含空格和断句的标点），术语表里没有、任何一份 Markdown 的标题里也没出现过。只认这两种写法是需求所有者选的：自造的词几乎都是加粗或打书名号引进来的；不靠分词去猜哪段话是新词。
  - **行号引用**：`ADR-数字:行号`。术语表说这是旧写法、不再新写。
  - **没配白话的需求编号**：需求清单里真有的编号（`P2`、`P2.c` 这种），后面没紧跟括号或书名号说明的。
- 围栏代码块、HTML 注释、行内代码里的不算 —— 那是在演示写法。
- CI 每跑都列一次：在检查链那个 job 里、欠条点名提醒之后单列一步，汇总一句进通知，全文进那一跑的 Summary，红绿都照跑。与欠条点名提醒同一种出法（ADR-196）。
- 判定与入口分开：判定是纯函数、由测试与变异守；入口只起 git、读文件、打印，在玩具仓库里由需求测试真起。

## 二、量出来的

- 入口在本机跑一次约 0.4 秒（三次 0.37–0.41 秒），与欠条点名提醒（约 0.45 秒）同一量级。CI 上它是检查链那个 job 末尾多出的一步，不进 `npm run check`。
- 在本分支上跑（叠在白话目录那条上，量的是相对主干新加的行）：白话目录里新加的那些行报出几十处「生词」，多数是书名号引的原文短句或白话说法（「故意改坏」「压成一个提交」）。这类不是自造词，提示照列，读的人一眼跳过；要不要收窄等用一段时间再看（第三节那张欠条）。

## 三、仍然按不住的

> ⚠️ 欠条「生词提示的提示太多会没人看」：书名号也常用来引原文、引标题，这些短句照样会被列成「生词」；白话目录那一回就报了几十处。提示一多，真生词淹在里面 · 还法：数一段时间里各条 PR 的提示里真生词占几成，占得太少就收窄认法（比如书名号只认后面紧跟解释的、或加一张「引原文不算」的写法），收窄要需求所有者再选一次 · 档：登记 · 重启条件：周回访第一次有人说提示太多看不过来；或本条合入满四周（2026-12-21）

> ⚠️ 欠条「生词提示只看 Markdown」：代码注释、提交信息、PR 正文里的生词不看。注释里书名号多用来引断言名、提示文案，一并看会更吵 · 还法：先按上一张欠条把噪声压下去，再决定要不要把注释纳进来 · 档：登记 · 重启条件：上一张「生词提示的提示太多会没人看」还上时

- **需求编号「配了白话」只认紧跟括号或书名号**：「`P2` 这条红线是说……」这种把白话放在前后句里的，照样会被列出来。它只是提醒，多列不挡合并。
- **「已有标题里出现过」按包含算**：一个短词只要是任何一份文档某个标题的一部分就不报；标题里碰巧含了这几个字的，也就不报了（只会少报）。

# ADR-228 读写任务文件不再逐层递归：能读多深不再看机器栈大小

- 日期 · 2026-11-20
- 类型：实现缺陷（检查结果随机器变），不改需求原文
- 触发它的事实：`scripts/test.ts` 里「任一层写重复的键：读得进来的深层嵌套……照常判」那条断言拿 2400 层嵌套的任务文本（测试里现拼，不存进仓库）去读、去查重复的键。同一版 Node 22.23.5，CI 上绿，在一台云端容器里（默认栈）读任务那一步就抛「Maximum call stack size exceeded」，把栈调大一倍又绿。量下来：读任务时用的带回调的 `JSON.parse`（为了在回调里拿到每个数字的原文）在 V8 里逐层递归，这台机器上约 2237 层就用完栈；不带回调的 `JSON.parse` 不递归，同一台机器上一千九百多万层都读得进来。查重复的键那一步（`scanDuplicateKeys`）本来就不递归，卡住的是它前面这一步
- 决定人与时间：需求所有者丸子 2026-11-20 16:42（UTC）在项目对话里答「试试吧」，同意把这一步改成不靠递归的写法
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 理由：见下面几节
- 连带改动：`scripts/lib/cost-json.ts`（读入改用不带回调的 `JSON.parse` 加一遍不递归的扫描找回数字原文；费用子树换精确金额改用待办列表；整份写出改用不递归、与内置逐字节相同的写法；认键名的那几行抽成一个函数两处共用）· `scripts/test.ts`（深层嵌套的断言从 2400 层改到十万层，新加两条：深处的数字原文与费用子树、一万层整份写回）· `scripts/check/mutations.json`（新变异 M-D27-ac、M-D13-av、M-D19-bd；M-D19-y 的锚点跟到抽出的函数上）· `scripts/check/launches.json` 重写

## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 哪一步在深嵌套时栈溢出、各在多少层 | 在出事的容器里逐个深度真跑：带回调与不带回调的 `JSON.parse`、带写出回调与不带的 `JSON.stringify`、`structuredClone` | 机器 |
| 新的读法记下的数字原文与旧的带回调读法是否一致 | 两种读法对同一批随机 JSON 逐个位置比对（含重复键、转义的键、各种数字写法） | 机器 |
| 新的写法与内置 `JSON.stringify(值, 回调, 2)` 是否逐字节相同 | 两种写法对同一批随机值逐字节比对（含 `toJSON`、包装对象、`JSON.rawJSON`、写不出的值、成环） | 机器 |
| 改了以后入口在深嵌套时怎么结束 | 真起 collect、render（假供应商），根上与任务条目里各挂一个深键，逐个深度看退出码、请求次数、task.json 变没变，主干同样跑一遍对照 | 机器 |
| 这一步该不该改 | 需求所有者，2026-11-20 答「试试吧」 | 人 |

## 一、读：不带回调的解析，加一遍不递归的扫描

`readCostDocument` 原先在 `JSON.parse` 的回调里拿每个数字的原文（JSON.parse 的 source 上下文），按「所在的对象或数组 → 键」记下，供费用字段精确换算（D13）与整份写回照原文写数字（D19.g、ADR-138）用。带回调的那条路在 V8 里是递归的，能读多深取决于这台机器的栈。

现在先用不带回调的 `JSON.parse` 读出对象，再逐个记号扫一遍原文（与查重复键同一种走法：找下一个引号、看前面紧挨着几个反斜杠认出字符串结尾，不用正则，ADR-140 第五节），每层记下各键最后一处的值：数字记原文，容器记下一层。同一个键再写一次就盖掉前一处，与 `JSON.parse` 只留最后一处一致，被盖掉的容器不在读出的对象里，里面的数字也就不记。扫完再对着读出的对象逐层配上。两步都用列表代替递归，读得进来多深都走得完。

这是标准做法里最稳的一种：解析本身仍交给内置的 `JSON.parse`（它先接受了这份文本，扫描只在它接受过的文本上走），我们只补它不交出来的那一样（数字的原文），不自己判 JSON 合不合法。

一致性的证据：两种读法对 6 万份随机 JSON 逐个位置比对，375 万处位置（其中数字 168 万个）一处不差（比对脚本放在项目共享文件夹 `stack-depth/fuzz-sources.ts`，不进仓库）。

读入后把费用子树里的数字换成精确金额那一步原先也是递归函数，改成待办列表，同样不看深度。

## 二、写：不递归、与内置逐字节相同的写出

只改读会带出一个新问题，所以同一条改动一起改写。原先读那一步在约两千两百层处先溢出，入口以 2 拒绝、什么都不写；读不再受限以后，深的任务能读进来，却在整份写回时被内置的 `JSON.stringify`（带写出回调时这台机器上约一千八百层就溢出）拦下：collect 以 6（保存失败）结束，render 打出堆栈 —— 比改之前还糟。

`stringifyCostJson` 改用 `stringifyDeep`：按 ECMAScript 规定的写出步骤（`toJSON`、写出回调、拆包装对象、`JSON.rawJSON` 的原文、数组里写不出的值写 `null`、对象里的跳过、成环抛 `TypeError`）一层层用列表走，标量与键名的写法仍交给内置的 `JSON.stringify`。写出回调本身一个字没改。

一致性的证据：与内置 `JSON.stringify(值, 回调, 2)` 对 15 万个随机值逐字节比对，一字不差，成环两边都抛 `TypeError`（比对脚本 `stack-depth/fuzz-stringify.ts`，同上）。独立复核另拿主干的整个模块对 10 万份随机任务（读入后随机改动、带与不带费用视图、共享对象）比写出文本，0 处不同；它也找出五种刻意造的怪值两边不同（原型换成包装类的普通对象、回调交回自带 `toJSON` 的包装对象、装了 `BigInt.prototype.toJSON` 时的 BigInt、成环的报错文字），`JSON.parse` 读出的任务数据到不了这几处，所以「逐字节相同」说的是任务数据，不是任意值；带 `toJSON` 的函数那一处已照内置改了。

## 三、测试与变异

深层嵌套那条断言从 2400 层改到十万层。2400 层原意是「读得进来、但很深」，可「读得进来」本身随机器变；十万层远超任何机器栈上逐层递归能走的深度，这条断言于是在哪台机器上都量的是「读与查重复键不递归」。夹具仍在测试里现拼，不存进仓库。

新加三条断言：同一深度上最里层的数字原文记得下来、费用子树最里层读不出精确值的数字照样换成「读不出」的占位（与浅处读出的相同）；一万层的任务整份写回不抛异常、读回来层数与原文不变；新读法与新写法和内置的一致 —— 同一个键写两次时原文取最后一处、转义的键按解码后的名字记，写出与内置 `JSON.stringify(值, null, 2)` 逐字节相同（夹具挑的是内置写法的各条岔路：自带转换写法的值、包装对象、数组里与对象里写不出的值、不可枚举的属性、`-0` 与 `NaN`、空容器），成环同样抛 `TypeError`。随机比对不进仓库，这一条是仓库里留下的、能被变异抓住的对照。

新变异，逐条施变都抓到：

- 不递归这件事本身：M-D27-ac（读任务又改用带回调的解析）、M-D13-av（费用子树换精确金额又改成递归）、M-D19-bd（整份写回又改用内置的 `JSON.stringify`）。
- 新写的两个函数里面：M-D19-be（同一个键写两次时原文取了前一处）、M-D19-bf（不按值自带的转换写法写出）、M-D19-bg（数组里写不出的值被丢掉而不是写 null）、M-D19-bh（包装对象写成空对象）、M-D19-bi（按原文写出的数字写成一个对象）。成环那一支没有变异：去掉判断后写出会一直走下去不停，变异跑不出结果。

M-D19-y 原先锚在扫描里认键名的那一行，那一行抽成两处共用的函数后锚点跟过去，施变后照样抓到。

## 四、改了以后入口怎么结束（实测）

在出事的容器上真起 collect、render，task.json 根上挂一个未列出的深键：

| 深度 | 主干 | 本条 |
|---|---|---|
| 3000 | 两个入口都以 2 拒绝（读任务时栈溢出） | 照常跑完，collect 照常请求、写回 |
| 两万、十万 | 同上 | 以 6 结束，零请求，task.json 不变（见下面第一张欠条） |

深键挂在任务条目 `tasks[i]` 里时，两边都在 5000 层以 2 结束、零请求、task.json 不变；溢出点从读任务挪到了评审准备整份复制任务条目那一步（ADR-136 那张欠条记的同一处），render 的 stderr 因此不再写出 task.json 路径（见下面第二张欠条）。

> ⚠️ 欠条「上万层的任务写回超出字符串上限」：根上挂的深键超过约一万六千层时，整份写回的缩进总长超出 V8 字符串上限（两万层约八亿字），collect 以 6 结束（stderr 说「收尾保存也失败」），render 以 6 结束并打出堆栈；都在任何请求之前，task.json 不变。这与栈无关：缩进两格的写法下层数一多，总长按层数的平方涨，在哪台机器上都一样（随 Node 版本的字符串上限变）。一万到一万六千层之间写得出但慢：独立复核实测一万层 42 秒、一万五千层 83 秒，每次保存写两到五亿字（主干在这些深度读任务时就以 2 拒绝）。现实里没有哪份任务会这样嵌；要修得先定这种文件算输入问题（退 2）还是另起写法 · 重启条件：有人在真实任务里遇到，或改整份写回的格式

> ⚠️ 欠条「读入之后几处深拷贝仍会栈溢出」（重挂 ADR-136 第 137 行、ADR-192 第 61 行）：读任务不再在深处失败以后，同一类栈溢出只剩在读入之后的几处深拷贝 —— 评审准备整份复制任务条目（`task-reviews.ts`）、读名单后的深拷贝（`task.ts` 的 `structuredClone`、`pipeline.ts` 去重前）、`agent-review.json` 读入后的深拷贝（`review.ts`）。任务条目或名单里嵌到几千层以上时，collect、render 以 2 结束，stderr 只有一句「Maximum call stack size exceeded」，不点名文件；render 原先在读任务时就以 2 拒绝并写出 task.json 路径，现在到复制那一步才结束，少了路径。退出码、零请求、task.json 不变都与主干相同。现实里没有哪份会这样嵌，失败都在预留、请求与写入之前；需求所有者 2026-10-10 定的「接受为已知缺口」照旧 · 重启条件：下一条改这几处深拷贝，或同一缺口再被点名

## 五、碰到的欠条

三份独立的清点把台账逐条按字面读过，结果如下。

- ADR-136 第 137 行与 ADR-192 第 61 行（同一张欠条与它的重挂，条件含「同一缺口再被点名」）：本条改的是读任务本身，读不再在深处失败，失败点挪到了它们点名的深拷贝，并在第四节点了这个名，响了。本条不改那几处深拷贝，还不了：重挂到第四节「读入之后几处深拷贝仍会栈溢出」（原条件不带重新起算，照原样），两处原文末尾各加一行「已重挂」。陈述随之收窄：「读任务超过解析上限时不点名文件」那半句已够不着，换成读入之后那几处。
- ADR-141 第 45 行（D19.k「同一个任务索引键」措辞比实现窄，条件含「改 `cost-json.ts` 重复键扫描」）：本条改了扫描的函数体（认键名那几行抽成两处共用的函数），响了。实质早已还清：D19.k 现在的原文是「同一个键出现不止一次」，与实现一致。在它末尾补一行「已还」。
- ADR-89 第 92 行（加变异时看一眼盖的是不是没人盖过的地方）：每条加变异的 PR 都要做的一步。核过：新锚点在主干上都不存在，盖的是新地方；新写的两个函数里面原先一条变异都没有，已补上第三节那五条和那条对照断言。
- ADR-99 第 145 行（开 PR 前按文件清单核在途 PR）：每条 PR 的一步，核的结果写在 PR 正文。
- ADR-138 第 60 行（改入口写回 task.json 的方式，括号里写「重建根或 holder」）与 ADR-94 第 197 行（进度三张表靠字段在不在表达三态，「任何一次 JSON 往返都会毁掉它」）：宽读响 —— 写出器整个换了，数字原文的读法也换了。实质不响：写出回调一字未改、仍不重建根或 holder，新写法与内置逐字节相同（随机比对加第三节那条仓库内的对照），字段在不在照原样写出。
- ADR-72 第 675 行（断言没验到它声称守的事）：费用子树那条断言起初的名字写「换成精确金额」，夹具走的却是「读不出」占位那一支；开 PR 前已把名字改成说实话，不计一次。
- ADR-140 第三节「读不进来的深度（`JSON.parse` 自己栈溢出）是读取错误」：不是欠条。那时读任务用的是带回调的解析，这句话是对的；现在读不进来的深度由不带回调的 `JSON.parse` 决定（一千多万层），这句话描述的界线由本条取代，旧文不改。

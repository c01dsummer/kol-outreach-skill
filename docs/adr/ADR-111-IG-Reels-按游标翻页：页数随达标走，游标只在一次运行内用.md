# ADR-111 IG Reels 按游标翻页：页数随达标走，游标只在一次运行内用

- 日期 · 2026-09-24 · 交接清单「IG 真正按游标翻页」；ADR-100 第六节与末节的重开条件（IG 搜索有了可用游标）在这里被触发
- 类型：**产品取舍**（需求所有者裁决）；实现与需求改动另开 PR
- 触发它的事实：固定官方规范声明 `search_reels` 接受 `pagination_token`，历史单次运行内的链式请求取得了更多去重作者（ADR-101 第十二、十三节）；
  生产采集器仍只取 Reels 首页（`search()` 见 offset > 0 直接返回空，reels 页恒 `has_more: false`）
- 冲击的需求：D6（新增 IG 续页判据；D6.k 正文里「reels 页恒 `has_more: false`」的前提句要改写，判据本身不变）；F9、F9 × P1 **不变**（见第一节）
- 结论：**采纳，按下面的裁决实现。** 本条不改代码；需求登记表在实现那条 PR 里随代码一起改，不先写一句还没做到的话

---

## 一、需求所有者的裁决（2026-09-24）

1. **页数「根据总量定」。** IG 与 TikTok 用同一套轮转调度与停止条件：没达标就继续翻、达标即停（F9.d），
   额度不足按 P3 停，单个任务的页数上限仍是现有的 `MAX_PAGES`（D6.h）。**不设按平台的默认页数或配额**，
   所以 F9 × P1「不设任何默认的平台配额」原样成立，ADR-100 末节「把 `MAX_PAGES` 变成按平台的值」那条重开条件不触发。
2. **游标只在同一次运行内沿用**，放内存，不写进 `task.json`。续跑时，已经抓过页、还没进 `done` 的 IG 任务不再翻页。
   理由：游标跨运行（几小时到几天）还能不能用，没有任何样本；持久化续用的失败会让每次续跑卡在同一个任务上。
3. **保存顺序的既有缺陷单独修**（先写作者累加器、再推进进度），不作为翻页的前置，也不混进翻页那条 PR。

## 二、已由现有需求定死、不需要拍板的

- **第一页保证**照旧（F9.a/c）：旧目录里一页都没抓过的 IG 任务照常抓第一页（含账号名兜底），这一页之后不再翻。
  「抓过没有」按分页记录表 `offsets` 有没有这个键判，与 `firstPagePending` 同一份判定。
- **兜底只在第一页**（D6.k 的形状）：第一页走了账号名兜底的任务，当页进 `done`，不再翻 Reels，更不取账号名响应里的任何值作游标。
  带游标的续页不走兜底，不看解析结果。
- **续页停止**，一律在拿回那一页的同一次迭代里判定、记进 `done`、随同一次落盘：
  响应里没有游标或游标为空白；本页 0 条（按供应商返回的条目数，同现有判法）；本页有条目却一个作者都解析不出；
  达到页数上限；达标之后不再翻（F9.d）。措辞只说「本次没有可继续的游标」「达到上限」，**不说服务端已经没有更多**。
- **续页失败**照现有错误路径处理（保存断点、如实报错），不退回首页、不触发兜底。
- **「这个任务还能不能再翻」只有一份判定**，放在 `scripts/lib/pipeline.ts`，调度与「续跑要不要花钱」那句话共用（ADR-25 的形状）。
- **费用**：每一页一次 `search_reels` 请求，走现有逐次预留与结算（D13、D14）；不新增端点。
- **术语**：需求与代码里的「分页游标」一直指 `offsets` 表（D6.l、D6.m、D6.s）。IG 的 `pagination_token` 称「IG 续页令牌」，不与它混名。

## 三、代价，写明

- **新任务的默认行为会变**：今天 IG 每个关键词只抓一页；合入后没达标就会继续翻，每页 $0.002（固定价目），
  与 TikTok 的续页在同一轮转、同一预算里竞争。预算有限时，排在后面的 TikTok 第 2–4 页可能被 IG 续页挤掉，反之亦然。
- **跨词人群重叠没有量过**，续页买到的新作者数只有一个关键词、一次运行的历史记录（ADR-101）。页数随达标走是需求所有者的取舍，
  不是证据证明的最优。
- 预算中断后续跑时，已抓过页的 IG 任务不再翻页 —— 覆盖比持久化续用少，换来不依赖未验证的前提。

## 四、未验证的前提

- Reels 续页令牌的位置按历史样本取 `data.pagination_token`（与 `data.data` 同级）；只在一个关键词、一次运行里观察过。
- 同一次运行内相邻请求之间令牌有效，也只有那一次运行的链式记录支持。

## 五、施工顺序（每步一条 PR）

1. provider：Reels 带令牌请求、从响应读出下一个令牌放进搜索结果的新字段；`has_more` 仍为 false、入口不用它。行为不变。
2. 判定：`pipeline.ts` 里「还能不能再翻」的唯一判定与测试、变异；不接入口。
3. 入口（最后一块砖）：`collect.ts` 在同一次运行内沿用令牌、按第二节停止；同一条 PR 改 D6（新增续页判据、改写 D6.k 前提句），
   按 `docs/SYNC.md` 同步 `skill/SKILL.md`、`skill/references/providers/tikhub.md`、`docs/SPEC.md` 手写两节、
   `docs/data-source-strategy.md` 里「只取一页」的说法，并在 ADR-100、ADR-101 末尾追加指向本条的更正。

## 六、实现追记（第五节第 3 步）

- 入口接上后，「续跑时已经抓过页、还没进 `done` 的 IG 任务不再翻页」按 D6.h 的先例落成 **记进 `done`**（D6.v）：
  一次运行结束时（跑完、达标、预算不足、出错）手里还握着令牌的 IG 任务当场记进 `done`；
  续跑时遇到抓过页、不在 `done`、手里没令牌的（例如进程被硬杀留下的），同样记进 `done`、不发请求。
  不这样做的话，调度不抓，而「续跑还剩多少关键词」（D6.g）仍把它算进要花钱的那一半（ADR-25）。

> ⚠️ 更正第二节：「措辞只说『本次没有可继续的游标』」里的「游标」应作「续页令牌」。
> 同一份记录的术语一条规定 IG 的 `pagination_token` 称「IG 续页令牌」，「分页游标」专指 `offsets`；
> D6.u 与实现的提示用的都是「令牌」。独立写自检夹具的上下文指出了这处自相矛盾。


- 第二节说「这个任务还能不能再翻」只有一份判定、调度与「续跑要不要花钱」那句话共用。第 3 步第一版只接了调度那一侧，
  那句话（`keywordsResumeWillRun`）仍只看 `done`：正常收尾时两边一致（握着令牌的任务已进 `done`），
  进程被硬杀、续跑又在调度走到那个 IG 任务之前撞上预算时，那句话会把它算进要花钱的一半。独立审阅指出，
  同一条 PR 里改成共用 `canRequestPage`，D6.g 补上这个例外。
- D6.t「累加器保存失败时续跑重新请求这一页」对 IG 第二页起做不到（令牌已不在），例外写进 D6.v，ADR-113 末尾追记更正。

> ⚠️ 更正第三节「跨词人群重叠没有量过」：2026-09-24 在 `selfcare`／`journaling` 两个词的 IG 首页上零成本量过一次，
> 两个词搜到的作者没有交集（按用户名认，没有粉丝数，不是能进名单的人；ADR-101 第十五节）。只有两个词的首页，
> 不能换算成名单人数，也不能外推到别的词、近义词或更深的页；续页买到多少新作者仍只有 `smoothie` 那一次记录，
> 本节的取舍和「不是证据证明的最优」不变。

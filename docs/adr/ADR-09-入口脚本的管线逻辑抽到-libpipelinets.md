# ADR-09 入口脚本的管线逻辑抽到 lib/pipeline.ts

- 日期 · 2026-08-26 · 复查后的整改
- 类型：**发现更优解**（结构调整，不改需求、不改行为）
- 冲击的需求：无。P1/P4/D6/F5/U1 的既有验收标准不变，只是从此有了测试
- 结论：**采纳**

### 触发它的事实

ADR-08 的第三条教训写着「同一个坑第四次：教训被记下来了，却没有被应用到最大的
那个入口」。这条 ADR 就是去把它应用掉。

`collect.ts` 的 `main()` 与 `render.ts` 的顶层各有一段裸露的管线：

```
collect:  同人识别 → 合并 → 粉丝闸门 → 记忆过滤
render:   算分 → 分层 → 受众降权 → 排序
```

八个步骤全部有顺序约束，但顺序本身没有任何测试守着 —— 因为它们不在函数里，
测试拿不到它们。

### 抽出后新增的保证

`lib/pipeline.ts` 的 `finalize` / `rankCreators` / `pendingKeywords` /
`keywordStats` / `tierCounts`，配 5 个变异：

| 变异 | 违反什么 |
|---|---|
| `M-P1-g` | 先闸门后合并 → 「两平台各 3000、合起来 6000」的人被提前丢掉 |
| `M-D6-c` | `finalize` 就地修改累加器 → 退回 ADR-08 那个 bug 的形状 |
| `M-P4-b` | 记忆过滤跑在闸门之前 → `filtered_contacted` 虚报打扰规模 |
| `M-F5-a` | 降权跑在分层之前 → 降完被 `tierOf` 覆盖，地域不达标的人留在 A 级 |
| `M-U1-b` | 管线不排序 → A 级混在几百行里 |

`finalize` 顺手改成 `structuredClone` 输入：「累加器只增不减」从此是**结构性**
保证，不再依赖调用方记得先落盘再调用。

需求覆盖 19 → 21 条（F3、F5 此前没有任何测试）。

### 行为未变的证据

拿重构前的 commit 建 worktree，两边跑同一份真实数据（48 人的产出目录）：

```
✓ kol.csv        逐字节一致
✓ report.html    逐字节一致
✓ creators.json  逐字节一致
✓ memory         只差写入时间戳
· meta.json      仅 keywords[] 内的键顺序不同，值全等
```

### 教训

**判断一段代码该不该从入口搬进 `lib/`，只问一句：它的顺序错了会不会出错。**

会，它就有语义；有语义就该能被测；能被测就不该待在入口脚本里。
比「这段有多长」「看起来乱不乱」都好用 —— 后两个判据会把
`main()` 里那种「一行一步、读起来很顺」的管线判成不需要动，而那恰恰是最危险的地方。
已写入 `docs/CONVENTIONS.md` 第 10 条。

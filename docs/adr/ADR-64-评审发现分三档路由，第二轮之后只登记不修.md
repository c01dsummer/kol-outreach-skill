# ADR-64 评审发现分三档路由，第二轮之后只登记不修

- 2026-09-02 · 复盘 PR #1–#15 的体量、寿命与评审时发现
- 类型：不属于反向输入的五类 —— 改的是 `process/`，不触及需求登记表。
  记下来是因为它动了通用层，而通用层的每一次变动都该说得出理由
- 冲击的需求：无
- 结论：**采纳**

## 触发它的事实

15 条 PR 全部按 `size-rule.ts` 的分类口径重新量过（base 按合并方式取，不按本地主干）：

| PR | 源码新增 开→合 | 打开后提交 | size-ok | 打开到合入 | Codex 线程 | 处理方式 |
|---|---|---|---|---|---|---|
| #6 | 393 → 1079 | 29 / 34 | 52 | 22.6 h | 39 条，P1 2 条 | 36 条在 PR 内修 |
| #7 | 263 → 738 | 27 / 29 | 15 | 5.0 h | 27 条，P1 6 条 | 26 条在 PR 内修 |
| #13 | 0 | 1 / 2 | 0 | 15 min | 1 条 | PR 内修 |
| #14 | 43 → 76 | 3 / 4 | 0 | 37 min | 4 条，P1 1 条 | PR 内修 |
| #8 #9 #11 #15 | 0 | 0 | 0 | 2–5 min | 0 条 | 直接合 |
| #10 #12 | 112 / 133 | 0 | 0 | 2–3 min | 各 1 条 | 合并之后才到，另开 #14 / #13 |
| #5 | 938，未合 | 24 / 24 | 4 | 5 天后关闭 | 64 条 | 历史改写，50 条线程失效 |

从这张表和评审线程里能站住的事实：

- **#7 开 PR 时在线内。** 源码 263 行。之后 Codex 每次 push 评一轮，共 19 轮；作者每条都在
  PR 内追加提交修；5 小时后 738 行，写了 15 条 `size-ok:`。#6 同形。
- **膨胀的主体不是「修复引出修复」。** #7 的 27 条里严格意义上「上一轮修复引入」的只有 6 条。
  大头是评审要求的范围扩张（定时跑法、逐 PR 贴检查、PR 事件触发，约 320 行毛增），其次是
  原始缺陷的修补（约 620 行，含最后那次 250 行的重构）；打开后新增的源码里一半是注释。
- **体量闸门没有失灵，是出口太便宜。** 它在 #7 上问了 15 次「能不能拆」，15 次都由写代码的
  同一方自己写一句理由放行。Codex 的 27 条线程没有一条涉及体量。
- **寿命闸门把 #6 定义成了健康分支。** `age-rule.ts` 头部的校准表写着「已合并 PR #6，22.9 小时」
  属于健康组，48 小时是按它留一倍余量定的。用户要的健康是一两小时合入。
- **「评审后一两小时合入」这个形态其实没真正出现过。** #10 合并时间比 Codex 第一条评论早
  6 分钟，#12 早 1 分半 —— 它们是先合再审，发现落到已合并的 PR 上，另开 PR 是唯一选项。
  真正走完「评审、修、合」的只有 #13 和 #14，各在 PR 内修了 1–3 个提交。
- **Codex 的 P2 被当成了 P1。** 第三方转载的 Codex 评审提示词里 P2 的定义是「Normal. To be fixed
  eventually」（官方文档在本环境被拦，未核对原文）。#6 的 37 条 P2、#7 的 20 条 P2 几乎全部
  在 PR 内修掉。
- **两条闸门 PR 都是一边建闸门、一边被自己建的闸门评。** 第一个提交就把闸门接进了
  `npm run check`，于是每条「闸门堵不住洞」的 P1 按「主干必须可发布」只能在本 PR 修。
  `6-INTEGRATE.md` 自己写了「最后一块砖：实现先进主干，入口最后接上」，#9→#11 也用过
  （「先补齐再接检查，检查接上的那一刻就是绿的」），两条闸门 PR 都没用。
- **#6 的 22 条豁免引用「受单一指定分支约束」。** 那是会话的启动指令（「在指定分支上开发，
  未经许可不推到别的分支」），不是仓库规则；同一形态的会话 2e97m1 在指定分支名后加后缀
  开了 8 条分支。用户已明确解除这条约束。

## 为什么不是体量阈值的问题

#7 开 PR 时 263 行在 350 以内，超出的 475 行全在评审期间长出来。只把 350 降到 150 而不改
「发现修在哪」和「豁免谁批」，同一条 PR 照样会长到 738。

小 PR 的收益也要说准：按 PR 数算，小 PR 的发现确实少（0–4 条对 27–39 条）；按每百行源码
算，密度不稳定（#14 每百行 5 条，高于 #6 的 3.6）。#8–#15 八条合计约 3.2 小时、432 行，
和 #7 的 5 小时、738 行吞吐相当。**拆小换来的是合入粒度、线程不失效、可单独回滚，不是总工作量
变少。** 这是对的目标，但要按它本来的样子写。

## 裁决

五条，都进 `process/6-INTEGRATE.md`（规则文本在下一条 PR）：

1. **评审发现分三档路由，档号由作者写在每条回复的第一行，合并者只核「每条有档号和去向」。**
   - **本改动**：错在开 PR 时的 diff 已有的行里 —— 本 PR 追加提交修
   - **扩范围**：要求新跑法、新触发、新模块、重构，或修法要碰开 PR 时 diff 里没有的文件 ——
     不在本 PR 做；能降级的用开关或删入口降级后合入，另开 PR。`3-BUILD.md` 的「禁止顺手重构」
     从此也管评审回应：评审者要的重构和作者顺手的重构，对 diff 来说是同一件事
   - **措辞 / 文档 / 判断力收紧**：登记

   徽章不等于档。P2 里有正确性错（#10 那条「锚读不出来就静默退回作者时间」），分档按内容，
   不按 P 级。
2. **轮次出口。** 第二轮之后到达的新发现一律登记不修，PR 停在当时的 head，检查绿就合。
   #14 三轮 37 分钟是健康的，这条只拦没有出口的回路。机器评审永远不会说「可以合了」，
   评审结束只能由规则定义。
3. **触发。** 另开 PR 的事项由当前 PR 合入触发：合完立刻在同一个会话里串行做，开一条、
   检查绿、合、再开下一条，让闸门静默错判的排最前。合并前不开 —— 那是叠分支，ADR-63 已经
   说过它会继承下面那条的豁免。登记的事项由登记时写下的重启条件触发（下次有 PR 碰到那个
   文件、同一缺口再被点名、定期清点）；登记落在 ADR 的欠条或 `AGENTS.md` 的已知缺口表，
   不另造 PR 描述清单 —— squash 之后它会丢。写不出重启条件的登记不是登记，是免责声明。
4. **闸门自身走「最后一块砖」。** 判定模块、测试、变异先合，最后一条 PR 才把它接进检查链。
   这是让新闸门的 P1 不必在本 PR 修的唯一办法。
5. **一个任务可以开多条分支、多个 PR。** 一个证据问题一个 PR，对主干开，合了再开下一条。
   会话启动指令里的「指定分支」是起点，不是上限。

## 没有做的，以及为什么

- **不加新闸门**（打开后提交数、打开后增量、轮次、打开后时长）。三个独立校准从同一张表给出
  2 / 3 / 6 / 10 四个数，说明健康样本太少，数字是拍的。而每道新闸门都要判定模块、测试、
  变异、架构锚点、selfcheck、SYNC、ADR 一整套 —— 正是 #6、#7 出生时的形状。先用上面五条跑
  几周攒数据，届时另立记录校准。
- **不降体量阈值。** 外部数据都站在「350 太大」这边（Google 100 行合理、GitLab 约 200、
  六个工业项目中位 25–78 行），但它们量的是改动行，本仓库只数新增行，口径不同；且阈值不是
  约束所在。另立记录校准。
- **不把 P2 一律定为不阻塞。** 见裁决第 1 条的最后一句：#10 那条 P2 让主干带着一个静默错
  跑了 68 分钟。

## 明确不保证的

五条全在第三层：档号由作者自填，没有检查能验证一条发现是不是「本改动」；合并者的核对靠人，
而数据显示人合并只用 8–15 分钟；轮次数没有检查在数。**不要假装这一层被保证了。** 它们的
判据要等数据攒够再找 —— 和 ADR-58 走过的路一样。

## 教训

- **出口是一行文字的闸门，挡的是无意。** 写代码和批豁免是同一方时，出口的价格是零。
  ADR-59 说「说不出理由的长命分支和说得出理由的不是一回事」—— 成立的前提是理由有第二个人读。
- **一条只规定了「怎么改历史」的规则，会隐含地规定「改在哪」。** 「评审中只追加提交」定下的是
  不许 rebase，却让每条发现默认都落在本 PR。规则要把出口写出来，否则默认就是唯一出口。
- **阈值按历史校准之前，先问历史里哪些算健康。** 校准表把 22.9 小时列为健康，闸门就永远
  看不见 22.9 小时。
- **AI 作者在 PR 上的默认姿态是「每条意见要么修要么回复理由」。** 回复「另开 PR」在它的规则里
  是合格回应，但没有明写的出口，它每次都会选修。这不是纪律问题，是没给第二个选项。

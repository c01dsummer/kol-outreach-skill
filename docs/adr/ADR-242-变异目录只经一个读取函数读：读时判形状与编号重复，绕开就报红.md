## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 哪些地方在读变异目录 | 语法树：非测试源码里字符串字面量、模板串各段带着目录文件名的地方，与引用了读取函数所在模块的文件（`catalogDoorFaults`） | 机器 |
| 读到的目录能不能用 | 读取函数 `readCatalog` 自己判：读得出 JSON、`mutations` 是数组、每条带字符串 `id`、编号不重复、豁免缺着或是数组 | 机器 |
| 各入口原先怎么报错、以几退出 | 各入口的自检夹具（`mutation-duplicate-ids`、`anchor-residue-entry`、`admission-entry`、`shard-load-entry`、`audit-entry`、`mutation-reds-entry`、`launch-count-entry`）与需求测试 `h-field-use-entry-inputs` | 机器 |
| 不读编号、只碰到文件名的那几处算不算读者 | 人读那几处代码：指纹只算字节、体量只按路径归类、负载闸门只核工作流那一行写没写对 | 人 |

## 一、做了什么

1. **一个读取函数。** `readCatalog(text)` 收读到的文字（读不到交 `undefined`），按「读不出 → 形状不对 → 编号重复」的先后判，交回一份可以按编号用的目录，或者一个拒收原因（`unreadable`、`shape`、`duplicate`）。只判所有读者都用得上的那一层：各读者自己要的字段（`file`、`find`、`req`、`why`、`kills`……）仍由各自的判定核，读取函数不替它们核。`catalogFaultText` 把拒收原因说成一句话，入口照抄。
2. **八处读者都先经它。** 每处入口拿到拒收就照自己原来的规矩报、退出：变异一步与锚点那一步编号重复时仍打原来那段点名（「N 个编号重复」「某某 出现不止一次」），准入读物包仍以 2 拒收、不建包目录，负载闸门把它记成算不出秒数，启动数那一行把它记成数不出，审计抛出去以 1 退出（原先 JSON 坏了也是抛出去的；不另加硬退出，免得碰 ADR-70「硬退出收口只到 mutate.ts」）。原先 `never-red.ts`、`admission.ts` 各自调的 `duplicateIds` 撤了，统一到读取函数里。 改了措辞的几处：维护比较读不成基线时说「基线的变异目录……」，准入读物包拒收时前面带目录的位置，`never-red.ts` 读不出时改说读取函数那一句，锚点那一步读不出时括号里带上原因；写成 `"exemptions": null` 的目录原先在变异一步与审计里当空放过，现在拒（缺着才当空）。维护比较读基线目录也经读取函数，基线是 null 时同样拒、不应用变异：主干的变异目录从没写过 null 豁免（按 git 历史查过，一次都没有），本条合入后主干上每条改动的当前目录都先经读取函数判过，null 进不了主干，所以基线不会是这种形状；万一出现，照坏目录报，修法是先修主干那份。入口这一半由各自的自检组守：变异一步、锚点、准入读物包原有编号重复的例；审计、负载闸门、从没红过的断言各加了一例，字段断言闸门在需求测试里加了一例。启动数那一行没加：它读不成时与纯判定自己拒重复时打的是同一句，拿掉读取函数也看不出差别。
3. **绕开就报红。** 需求测试组 `h-catalog-door` 扫 `scripts/` 下所有 TypeScript 与 JavaScript 源码（测试文件不扫），交 `catalogDoorFaults` 判两件事：目录的文件名只许以字面量写在 `catalog-rule.ts`；引用了读取函数所在模块的文件（按名字导入、整个模块导入、只为副作用导入、`import()`、`require`、转出都算；整句只带类型、或每个名字都只带类型的不算），同一个文件里要真调用那个模块里的 `readCatalog`（调的是不是它不按名字认，交 TypeScript 编译器问：把这批文件放进一个只在内存里的编译，读取函数所在模块的导入一律指到 `catalog-rule.ts`，每个调用问编译器「这一调落到哪个声明上」，落到 `catalog-rule.ts` 里那个 `readCatalog` 函数声明上才算 —— 改了名、经模块对象调、从动态导入或模块对象解构出来的都认；同名的本地函数、同名的参数、别的对象上的同名方法、从别的模块导入的同名函数都不认。这是 CONVENTIONS 第十三节「名字指向哪个声明问语言服务」的做法。CodeRabbit 第一轮指出原先只按名字认，第二轮指出改成跟踪名字之后仍不分作用域，同一处连着两轮，按规矩换成问编译器，不再补名字规则。已知漏的一种：参数的类型写成 `typeof readCatalog` 再调那个参数，编译器说落到读取函数上，会当成调了；要这么写得先导入读取函数本身，绕开的意图写在明处，不另堵）。不读编号、只碰到文件名的三处（算指纹的 `claims.ts`、按路径归类的 `size-rule.ts`、核工作流那一行的 `shard-load-rule.ts`）和这道检查自己，写在放行名单 `NOT_READERS` 里、各带理由；名单里列了却不在仓库里的也报。
4. **纯判定里原有的拒法没撤。** `anchorVerdict` 先报编号重复、`executionRoutes` 遇重复就抛、`attributionFault` 先报重复再报记错名下 —— 它们是纯函数，测试里也拿任意输入调，留着各自的拒法；从入口走到它们时，编号已经在读取函数那一道拒过了。

## 二、为什么是这个分法

想过的三种：

- **甲（本条）：一个读取函数，加按语法树查绕开的检查。** 新读者照常写的几种（直接写文件名、拿了位置不调读取函数）在需求测试里当场红；认不出的写法列在第五节。
- **乙：只加一个读取函数，不查绕开。** 今天八处都改好了，下一处新读者照样可以忘 —— 欠条要的统一阶段就只是今天碰巧统一。
- **丙：把各纯判定里的拒法都撤了，只留读取函数。** 纯函数会被测试与别的调用者拿任意输入调，撤了以后它们对重复编号的行为就成了未定义；而且撤掉会动 ADR-34、ADR-70 那几组已有断言和变异，收益只是少几行。

查绕开按文件、按字面量与导入认，不按「这一处调用读的是不是目录」认：后者要猜实参，前者语法树上能确切回答（与 ADR-217 起子进程那道闸门同一个理由）。

## 五、证不了的

- 绕开的检查认不出拆开拼的文件名（`'mutations' + '.json'`）、从环境变量或参数传进来的路径、`shell` 与工作流里读目录的命令（`check.yml` 里那一行 `jq` 只数条数、不读编号）、拆开拼的模块名；一个文件里调了 `readCatalog`、另一处又拿位置自己读的，它也认不出 —— 要看数据怎么流，语法树答不了。这几种仍靠评审。
- 测试文件不扫：需求测试与脚本自检里有十几处写夹具目录、一处拿真目录做测试输入，它们不是检查链读目录拿去判的地方。
- 放行名单里那几处不读编号，是人读代码判的，没有机器核它们以后会不会开始读。

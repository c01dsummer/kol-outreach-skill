# ADR-190 草稿拿去就能放进邮箱：主题单列，发件人可选，只存不发

- 日期 · 2026-11-09 · 「Zoho 发开发信」那条线：运营方要用自己的 Zoho 邮箱发开发信，需求所有者问一个具体的邮件平台该怎么放进这个通用 Skill
- 类型：产品取舍（四件事都不违反需求，选哪种决定用户看到什么），需求所有者 2026-11-09 14:19Z 在决策卡上选「全按推荐」
- 触发它的事实：评审 CSV/XLSX/HTML 里开发信草稿是一整格，第一行是 `Subject: …`（`skill/references/outreach-draft.md` 的模板），主题和正文混在一起，放进任何邮箱工具或邮件合并之前都要人手拆；模板署名处有 `{name}`（同一文件的「我是谁」那一行与结尾署名），而流程里没有任何一项输入能填它，它只能原样留在草稿里
- 冲击的需求：S1（解释，不改字面）、U9.d（退役，由 U9 下一个新字母接替）；主题列、发件人姓名各新增一条需求，编号在实现那一片登记时定
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR；依据是他 2026-11-09 在项目线程决策卡上的选择。本条第三节那三处细节是实现者替他选的默认，合入即认
- 理由：草稿拿去要能直接放进任何邮箱工具，又不能让这个通用 Skill 绑上某一家邮箱、碰上发信。主题从草稿首行导出时拆，正本不多一份会漂的真相；发件人姓名是用户给的输入，放在任务根上，不碰品牌校准的版本。每一件的细节见第一、二节
- 连带改动：本条只有决策记录与索引一行；实现分三片串行，见第四节

## 一、决定

**1. 把审好的信放进用户自己邮箱的草稿箱，算 S1 说的「只产出草稿」。** 条件是只能经用户自己接上的邮箱工具，并且是本次对话里用户自己明说要放；Skill 自己的代码不调用任何邮箱接口，S1.a「代码中不存在任何 SMTP / 邮件发送 API 调用」字面不变。Agent 只调用「建草稿」一类的工具，绝不调用「发送」；发不发由人在邮箱里点。

**2. 具体邮件平台的代码不进本仓库。** 本仓库是发布给别人用、零配置的通用 Skill（`docs/business-requirements.md` 的「零配置可跑」与「发布给别人用」两条约束）；只有某一家邮箱的用户用得上的代码，对别人是死代码，凭据还会进 Agent 读得到的环境。连某一家邮箱的那一小段放在仓库外：先试该平台官方的 MCP、只挑「存草稿」那一个工具；没有，再另开一个小仓库做。`.agents/skills/`、`.claude/skills/` 里照旧只放那一条软链（`docs/ARCHITECTURE.md`「新东西落在哪个目录」）。

**3. 主题单独成一列（新增一条 U 类需求，退役 U9.d 换新字母）。** 导出时从草稿首个非空行的 `Subject:` 拆出来，不在 `agent-review.json` 里加字段：正本只留一份真相，字段里的主题和草稿首行不会各自漂。原来那格 `outreach_draft` 一个字节都不改，下游可能已经在读它。主题里的 `{…}` 照原样保留（P2.b）。

**4. 发件人姓名作可选输入（新增一条 D 类需求）。** 存进 `task.json` 根上的新字段 `sender_name`，由 collect 原样透传；不加第四个必问项，不进 `brand_calibration` —— 后者按内容算出版本号，一改并重算版本，所有已评账号都变成「待重评」。Agent 写草稿时拿它署名；脚本没有任何一处拿它去填 `{name}`。缺席就是用户没给：不读作默认值，脚本不补，草稿照旧留 `{name}`。

**5. 不导出 `.eml`。** 零凭据、不联网，但各邮件客户端把它打开成草稿的行为不统一，以后再看。

## 二、按改需求逐条评定

- 红线：P1、P2、P4、P5 都不碰。P3 要分开说：四片里 Skill 的代码都不调邮箱接口，也不新增按单价记账的请求；但第 4 片让宿主替用户调的邮箱工具会发 HTTP 请求，可能产生费用，现行 P3.c 的字面也没有把它排除。本条的解释是它不在 P3 的账上：P3.c 的「所有实际 HTTP 尝试」说的是 Skill 的 collect、enrich 按已核端点单价记账的那些请求，存草稿是宿主替用户调用的工具，Skill 的代码不经手、也没有它的单价可记；它花不花钱、花多少，由用户和那家邮箱之间的套餐决定，不由本仓库担保（以 Zoho 为例，官方说明 MCP 不单独收费、走账户现有的接口配额）。本仓库能管的只是 Skill 文字：只在用户本次对话里明说时才调、每次调用前把收件人和正文给用户看（第四节第 4 片）；宿主的审批若被用户设成自动放行，那一步就不再经人，这一点写进第 4 片的提醒。这条边界现在只是本条的解释，登记表里还没有字面；第 4 片按改需求的流程把它写成判据（见第四节第 4 片），在那之前以现行 P3 判据为准，下游不得引用本段当 P3 的依据；主题列里的占位符原样输出（P2.b）；「拆不出主题」和「没有草稿」写得不一样（P1：不同含义不共用一个空白）。
- 缩范围还是降标准：都不是。S1 的意思收窄成一条明确的边界（只经用户自己的工具、只存草稿），原先它对「放进草稿箱」没表态。
- 覆盖还是可信：覆盖上升 —— 草稿拿去就能放进邮箱，不用人手拆。
- 可逆：可逆。新列只追加在末尾，旧列与列序不变；`sender_name` 缺席照旧能跑。

**做了什么。**

- 新入口 `scripts/sender.ts`（`npm run sender -- --dir <任务目录> --name <姓名>`）：参数判定 → 姓名过 `textProblem`（与 D30.b/c 同一道）→ `readCostDocument` 读盘上原文（坏 JSON、根不是对象都拒）→ `duplicateKeyProblems` 不带第二个实参，任一层写重复的键都拒（进度键也在内）→ 只换根上 `sender_name`，走 `saveTask` 整份写回（`updated_at` 刷新，数字照原文）。不开账、不请求、不读写记忆。
- 测试 `d30-set`（`scripts/test.ts`）：手写夹具，合规三种（首尾空白、中文与重音、旧值不是字符串）与被拒七种（空串、只有空白、没有 `task.json`、根是数组、根是 null、坏 JSON、写重复的键）。自检 `sender-entry`（`scripts/check/selfcheck.ts`）：十一种用法错误、写进时的 stdout、拒绝时 stdout 为空、`task.json` 只读时以 1 结束且原字节。
- 负片 M-D30-i 至 o 七条，逐条手动施加，点名的断言都红。i、j、k、l 由 `d30-set` 抓（姓名校验、重复键、整份写回丢键、写前修剪），m、n、o 由 `sender-entry` 抓（`--` 开头的值、stdout 的 `replaced`、保存失败的退出码）。
- 文档：`README.md` 目录树、快速上手与 D30 那一段；`skill/SKILL.md`、`skill/references/outreach-draft.md`、`skill/references/product-intake.md` 各一句；`docs/ARCHITECTURE.md` 模块表、命令表、顺序契约表、缝隙契约、「整份写回 task.json」那一段与字段所有权表各一行。

**合入即认的几处。**

1. **已有署名照换，不先问。** 用户说了新名字就是要换；stdout 的 `replaced` 带出旧值，Agent 可以转述。
2. **`updated_at` 照例刷新。** 走 `saveTask`，与 `calibration version` 一样。
3. **任一层写重复的键都拒，不只进度键。** 整份写回会悄悄只留最后一处，等于替用户改了别的键（D27）。
4. **不查任务形状。** 根是任何 JSON 对象都当成任务写（`{}` 也写），同 `calibration version`。
5. **不要与同一任务的 collect、enrich、render、`calibration version` 或另一条 sender 同时运行。** sender 是 `task.json` 第三个整份写回的入口，后写的会盖掉先写的；没有锁，只在 `README.md` 与 `outreach-draft.md` 写了一句。

**与第四节计划不同的几处（ADR-81 第 98 行）。** 计划只说「一个只改这一个字段的入口」；本片多了 D30.h 与自检一组（独立复核指出入口没进自检，`audit.ts` 第二项与自检末尾的「每个可执行文件都有出处」都会红），以及 D30.g 里「数字照原文」半句。

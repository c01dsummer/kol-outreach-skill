# ADR-37 只堵了空白，剩下的字符还开着 —— 第六扇门

### 一、handle 的形状（P1）

`tiktok:@alice`、`tiktok:alice/`、`tiktok:alice?x`、`tiktok:ali%63e` ——
四个都过得了分隔符、空白、平台三关，四个都 `status=ok kept=1 filtered_contacted=0`。

**ADR-32 里我明确拒绝过这件事**，理由写着：按用户名校验可能吃掉一份
我们自己写出来的合法记忆，而「用户名不允许空白」是外部事实、代码里推不出来。

**那句话是错的。** 这个仓库自己就编码了 handle 的形状：

| 证据 | 推出什么 |
|---|---|
| `report.ts` 渲染 `@${handle}` | handle 自己带 `@` 会显示成 `@@alice` |
| `profile_url` 拼 `.../@${handle}` 与 `.../${handle}/` | handle 是**裸的 URL 路径段** |

我没去看，就断言推不出来 —— 于是只堵了想得到的那一个字符。

取两家平台都允许的字符集（字母、数字、下划线、点；连字符留着是因为
现有数据里有 `active-kol`）。方向仍然选错得起的那边：误判大声中止，
漏判静默破红线。

### 二、类型对不等于能用（P2）

`"product": ""` 类型是字符串，检查放行。而 `filterByMemory` 拿 product
去匹配「这个人是不是已经为这个产品推过了」—— 空字符串永远匹配不上任何产品，
**这条去重记录等于不存在**，人会被重新推荐，名单上那句「上次推的是什么」
也渲染成 `" @ 2026-01-01"`。

`date` 同一类（渲染成 `"p @ "`）。`task` 不在此列：空字符串与缺省在过滤里
行为完全一致，那不是坏数据。

### 教训

**「我判断不出来」之前，先去问一遍这个仓库。**

ADR-32 那句「这是外部事实，代码里推不出来」听上去很严谨 —— 承认边界、
标明限度、还给了失败方向。它唯一的问题是**没去查**。而查的成本是两个 grep。

一个自称谦虚的结论，和一个偷懒的结论，写出来长得一模一样。
分辨它们的办法不是看措辞，是看**有没有去找过证据**。

# ADR-138 整份写回 task.json 时读入后没改动的数字照原文写回，坏断点不再被洗成合法值

- 日期 · 2026-10-11 · 还 ADR-136 末尾那张既有缺陷的欠条（「task.json 写回时，费用字段以外的数字可能丢值或丢精度」），需求所有者 2026-10-11 定为修
- 类型：既有缺陷；按 `process/2-CHANGE.md` 属「需求有歧义」的补充 —— D19 只说坏断点不许晚暴露，没说经别的命令写回后不许消失
- 触发它的事实：主干 `b890781` 上，手改坏的续跑进度（`offsets` 写 `2.0000000000000001`、`found` 写 `1e400`）先让 `collect --resume` 以 2 拒绝；
  经 render、enrich、`calibration version` 或费用检查点写回一次后变成 `2` 与 `null`，再续跑以 0 通过，坏断点再也看不出来。
  `found` 里的 `null` 恰是 D6.l「注定不全」那一态。同样被改写的还有任务条目里未列出的键（`1e-400` → `0`）与未列出的顶层键（`9007199254740993` → `…992`）。
  `scripts/lib/task.ts` 的 `saveTask` 经 `scripts/lib/cost-json.ts` 的 `stringifyCostJson` 整份写出，读入时只有费用字段保留原文 token，其余数字只经 `JSON.parse` 成 number；自 2026-08-25 第一版读写任务起就是这样
- 冲击的需求：D19（正文补半句、新增 D19.g、新增 D19 × P1 交点）；D14.g（正文不改，今天在业务字段上不成立，补测试）。D13、D20.q 不改
- 结论：采纳。整份写回时，读入根上没被程序改动的非费用数字照读入时的原文写回；费用三棵子树（`requests`、`cost_ledger`、`budget_usd`）仍只走 D13 的专用路径
- 连带改动：`docs/requirements.json` 与 `docs/SPEC.md`；本记录与索引；ADR-136、ADR-94 末尾追加；README、`docs/ARCHITECTURE.md` 里说到写回数字的几句

## 一、决定

1. **只在写出时多查一次原文。** `readCostDocument` 读入时本来就按「根 → holder → 键」记下了每个数字的原文（供 D19 按原文判进度）。
   `stringifyCostJson` 写出时按同一张表查：读入根上某个数字的当前值仍等于它原文解析出的值（没被程序改动），就照原文写回；改过的照新值写。
   读入时一点不多算，写出时不另起递归（避开 ADR-136 记过的深键栈溢出）。
2. **只按读入的根查。** 查表的键是传给 `stringifyCostJson` 的那个根；meta.json、stdout 与 `collect --config` 新建任务时重建的根都查不到原文，行为与今天相同。
   根被浅拷贝（`{ ...value }`）之后，顶层键要回到读入的根去查，嵌套对象与根共用。
3. **费用三棵子树排除在外。** 它们由 `preserveCostNumbers`、根预算 token 与费用视图精确保存（D13）；通用回写若也进去，会把 D13 专用路径弄丢的原文从别处补回来，
   M-D13-i、M-D13-t 这类变异会存活（设计时实测）。所以排除由变异闸门间接守着：谁拿掉它，那两条变异立刻存活、闸门变红。不许拿改写那两条变异来换掉排除。
4. **没改动的数字一律照原文写回，不只是会变值的那些。** 只写回会变值的原文需要一个十进制比较函数，它买来的只是「`1.0` 被规范成 `1`」，没有判据要它；
   去掉以后「当前值仍等于原文的值」这道守卫就是承重的 —— collect 合法推进 `pages`、`offsets` 时没有它就会写回旧原文，跨运行页数上限失守。
5. 判据只保证值，不保证写法（D19.g「数字的写法不在本条保证之内」）。脚本自己写出的 task.json 原文本来就是规范写法，写回逐字节不变。

## 二、理由（四条判据依次问）

1. **触碰红线吗？** 碰 P1，按红线优先写进交点 D19 × P1（见第三节）：读不出精确值的进度不再被改写成 `null`、`0` 或舍入后的合法值，坏断点留给 collect 按原文拒绝。不碰 P3：费用输出逐字节不变。
2. **缩范围还是降标准？** 都不是。修的是整张欠条（所有非费用位置），不只是 D19 管的五张表。
3. **覆盖还是可信？** 可信：一个检查（D19.e）不再在别的命令之后静默给出错误结论。
4. **可逆吗？** 可逆。撤掉这一段，写回退回今天的有损写法；已写回的原文在旧代码下照旧解析。

**考虑过、没选的。** 收窄到五张进度表：是缩范围，D14.g 在其他业务字段上仍不成立，同一缺陷在别的按原文校验的字段上会复发。
拒绝式（enrich、render、`calibration version` 写回前先按 D19.a、D19.b 校验进度，坏了就以 2 拒绝）：新增产品行为 —— 进度坏了 render 就不能导出已付费的数据；值丢失的机制原样留着，进度以外的数字照丢，以后新加的写入方会再洗一次。

- **D19.g**：enrich（普通、改额，含其费用检查点）、render 与 `calibration version` 整份写回后，进度五张表里每个数字的十进制值与写回前盘上的原文相同；手改坏的进度写回后 collect 续跑仍按 D19.e、D19.f 拒绝并显示原文。test.ts 与自检两边认领。
- **D19 × P1**（写在 D19 一侧）：「P1 优先：读不出精确值的续跑进度数字……不由任何命令修补或补成合法值。」test.ts 认领；碰红线，合并前过一次独立复核（`process/4-VERIFY.md`）。
- **D14.g** 正文不改：「其他业务字段保持盘上版本」今天在读不出精确值的数字上不成立，补一条按原文比较的测试。

## 四、测试与变异

测试由没读实现的上下文按判据先写，对着主干跑红（`process/4-VERIFY.md`「测试先于实现」）。`scripts/test.ts` 里 `d20-content-version` 组那条「写出时 `1e400` 不再是原写法」的断言钉的正是本条要修的有损写回，只删那一半，留下「整数形的键排到前面」作夹具有效的证明（`docs/CONVENTIONS.md` 第 8 条）。

刻意不登记的两种变异：拿掉费用子树排除（值层面等价，由 M-D13-i、M-D13-t 间接守着，见第一节第 3 条）；改回只写会变值的原文（没有判据要求，等价）。

## 五、边界与欠条

> ⚠️ 欠条：`collect --config` 新建任务时写的是重建出来的根，只与读入的配置共用 `tasks` 与 `brand_calibration` 两个 holder；那里未列出键上读不出精确值的数字（`1e-400`、`1e400`）仍按今天的写法写成 `0`、`null`。这不是写回既有任务，不在本条之内，设计时读者实测发现，是既有缺陷 · 重启条件：本 PR 已合入（按 `process/6-INTEGRATE.md`「既有缺陷」排在下一条之前，由需求所有者定修不修）

> ⚠️ 欠条：render 不校验续跑进度，手写坏的 `found` 写成 `1e400` 时，meta.json 印 `null`、report.html 印 `Infinity`，与 task.json 不一致；meta.json 与 stdout 的根是新建的，本条的写回查不到原文。设计时读者实测发现，是既有缺陷 · 重启条件：本 PR 已合入（同上，由需求所有者定修不修）

> ⚠️ 欠条：「当前值仍等于原文的值」这道守卫有个前提 —— 没有入口把读入的位置改成与旧值同一个 double，也没有入口原地重排读入后的数组（`shift`、`splice`、`sort`、删除下标）；否则旧原文会复活，或跟着下标迁移到别的元素上。今天的入口都不这样做 · 重启条件：下一条对读入后的进度数组或任务列表做重排、删除，或把同值写回已读入位置的改动

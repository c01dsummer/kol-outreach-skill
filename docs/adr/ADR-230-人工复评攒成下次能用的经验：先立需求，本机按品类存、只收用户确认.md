## 一、这次只把规矩写下来，Agent 的行为不变

经验写错了会带偏后面每一个同品类任务，所以先把边界写成需求、由需求所有者合入来批，再动手实现。
本条只加 D31 这条需求、这份记录和一组测试；Agent 读的 `skill/` 文字、`scripts/` 下的产品代码都不改，合入后跑任务的行为与合入前一样。

让 Agent 真正起草经验、写进经验库、下一个任务读它，是另一条改动（末尾那张欠条）。真实任务的手工回归（拿以前跑过的任务对比改前改后的产出）照 ADR-159 那套办法做，要需求所有者指定任务目录和机器，不在本条。

## 二、D31 写了什么（对照选择题第 2–10 题，外加两处）

选择题第 1 题定的是这次做多大（见第一节），第 11 题定的是工单怎么关，都不进需求正文。

1. **存在哪**（第 2 题）：本机 `memory/` 目录下，与 `memory/creators.json` 同一目录，每个品类一个文件（D31.a）；仓库的忽略规则把这些文件挡在 git 之外（D31.b）；不放进 `skill/`、不随 Skill 发布（D31.c）。共享与否跟着 D4（跨任务记忆那一条）走，本条不另写 —— D4 以后改成多人共享时，不用连带改 D31。D4 若改成把 `memory/` 做成一条指向共享目录的符号链接，D31.b 那组测试只抄忽略规则、不建链接，要跟着补一种造法：今天的忽略规则写的是 `memory/`（带斜杠只挡目录），挡不住同名的符号链接（ADR-72 有一张欠条专管这件事）。
2. **一条经验长什么样**（第 4 题）：五项缺一不收 —— 局面、教训、证据、归因、规则版本（D31.d）。局面写形状不写事实、归因可以写「混杂」，借的是 harness2 经验库的做法（ADR-157 第一节引过）：一个偶然的例子不能当规律。
3. **只记局面和判断**（第 7 题）：不收能直接照抄进开发信或评审理由的现成句子（D31.e）。Agent 会照着现成句子抄，下一个任务的产出就成了模板。
4. **谁批**（第 5 题）：只收用户在对话里明确确认的；Agent 只起草（D31.f）。
5. **规则版本三种状态**（第 6 题，来自 2026-10-22 pstack 研究页那条「值得做」的建议）：写入时记下 Skill 规则文字的版本标识，取不到记「未知」（D31.g）；读的时候每条落在且只落在「同一版本」「写于规则改动之前」「版本未知」三种之一（D31.h）；后两种照常参考、不停下问用户，在数据边界里列出来（D31.i）。版本标识具体取什么（比如 `skill/` 目录在仓库里的那棵树的指纹），留给实现那一条定；判据只要求两边相同、不同、取不到这三种能分开。
6. **同品类怎么认**（第 3 题）：只读与本任务品类名同名那一份，新品类照常跑（D31.j）；起名前先看已有名字能沿用就沿用（D31.k），不为此追问用户（D31.l）。不多问一句，是因为开工前要问的事正在另一件需求里压到三件以内。
7. **什么时候起草**（第 9 题）：用户填好复评表、且人工作答与 Agent 判断不一致时，下一次重出报告附一段草稿（D31.m）；不为攒经验去要复评表或回填（D31.n，与 S3 相接）。
8. **管到哪**（第 8 题）：不改评分、分层与采用建议的规则，只经由语义筛选的判断起作用（D31.o）；不读写已联系、拉黑、已回复三个标记，人工复评表对名单的作用仍只属于那个任务（D31.p）。分层由语义判断决定（F6），经验改了判断，分层结果当然会跟着变；D31.o 禁的是绕过判断直接动规则。
9. **读不出来怎么办**（第 10 题）：照常跑、写明没读到及原因、不当成空的（D31.q）；不覆盖、不改写原文件（D31.r）。这与「已联系名单读不出来就不出名单」（D4.e）不同：经验库只是参考，缺了不会让已联系过的人再进名单；已联系名单缺了会。

另外两处不在选择题里：

- **共享跟着 D4 走**（第 1 条末句）：执行稿原有的一句，免得两条需求各写一遍「不共享」，D4 一改就要连带改。
- **交付时说清读了哪几条**（D31.s）：执行稿原有的一项，「读了」指读进来的全部，不只是用上的。「没有这一品类的经验库」与「有这一份但一条经验都没有」分开写，是红线 P1（「没查」与「查了为空」要分得开）推出来的，复核时补上（D31.t）。

### 一条判据装几件事

每条判据按 `process/1-REQUIREMENTS.md`「拆到多细」核过：会被不同代码路径分别做到、分别弄坏的，都拆开了（存放位置、不进仓库、不进 `skill/` 三条；写入记版本与读时分三态两条；读同名一份、起名沿用、不追问三条；起草与不索要两条；不改规则与不碰标记两条；读不出照常跑与不覆盖两条；写明读了哪几条与「没有」「零条」分开写两条）。留成一条的：D31.d 五项缺一不收是同一道「收不收」的关，D31.i 照常参考与列进数据边界是读到那一条时的同一步，D31.p 不碰标记与复评表只属于那个任务说的是同一件「经验不进去重」；D31.j 只读同名一份与没有同名时照常跑是同一次「挑哪一份」的两个结果；D31.q 照常跑与写明没读到的原因是读失败那一个分支里的同一步。D31.e「可以直接照抄的现成句子」与 D31.d「不写某一次的具体事实」要靠人读，两个人判未必一样，实现时随回归办法（ADR-159）由人看。

## 三、不要什么

- **经验库不进 `skill/`、不进仓库。** 三个理由：
  - 经验里有用户自己的客户、品类和账号，装了这个 Skill 的别人不该读到；
  - `skill/` 是发给所有用户的规则文字，改它要走 ADR-159 的回归办法、由需求所有者合入；经验库是每个用户自己攒、自己批的，节奏完全不同，混在一起，每收一条经验就成了一次 Skill 改动；
  - 经验写的是「上次这样判错了」，它的证据（哪个任务、哪个账号）只在用户本机的任务目录里，进了仓库就成了指不回证据的孤句。
- **不自动写入**：理由同第二节第 4 条。
- **不改打分**：经验一旦能调权重，打分规则就随库悄悄漂移，规则版本记录也对不上（第 8 题放弃的那一项）。
- **不存现成句子**：见第二节第 3 条。

## 四、与红线、范围的交点

只查与红线的交点（`process/1-REQUIREMENTS.md`「和红线的交点必须查」），结论写进 D31 的判据文字，不登记成两条需求之间的交点：这几处都是 D31 单方面让步，没有哪两条需求在同一处要相反的东西。

- **P1（缺失的数据不得用默认值填充）**：经验库读不出来不当成空的（D31.q），也不覆盖原文件（D31.r）；没有那一份（新品类）就是没有，照常跑（D31.j）；「没有这一份」与「有这一份但零条」分开写（D31.t）。
- **P4（已联系、已拉黑的不得再进名单）**：经验不读写这两个标记，用户在复评表里填「采纳」也不让已联系的人回到名单（D31.p；后一半本来就由 `memory.md` 那一段管着）。
- **P5（交付必须声明数据边界）**：读了哪几条、哪几条版本对不上、没读到的原因，都写进数据边界（D31.i、D31.q、D31.s）。
- **S3（不主动索要回填）**：不为攒经验去要复评表或回填（D31.n）。
- P2（开发信不得有未证实信息）、P3（不超预算）不相接：经验不进开发信原句（D31.e），读经验不发请求。

## 五、测试认领

本条不改 `skill/` 与产品代码，D31 的二十条判据里，这次能拿机器确证的只有 D31.b（经验库文件不进仓库）：需求测试新组 `d31-store-outside-repo` 把本仓库的忽略规则原样抄进一个玩具仓库，在 `memory/` 下放几份经验库文件（含中文、带空格的品类名）、在别处放同名对照文件，问 git 哪些文件算已跟踪或没被忽略的新文件，由 git 答；经验库文件一个都不能在里面，对照文件必须都在。不读忽略规则的文字去猜。问的时候把 `HOME`、`XDG_CONFIG_HOME` 指进临时目录、不读系统与用户级配置：不然本机另有一份挡 `memory/` 的用户级忽略文件时，仓库那一行删了这条照样绿（复核实测过）。核过它会红：把 `.gitignore` 里的 `memory/` 注释掉，同时在用户级忽略文件里写上 `memory/`，这一条红。

其余十九条要等 Agent 真正起草、读写经验库时才有东西可测，由实现那一条改动在写代码时一起认领（末尾欠条），`npm run audit` 在那之前把它们列为「未被测」（只报不红）。这样分是否成立，待需求所有者在选择卡「这次只定规矩，工单要求的『有测试认领』怎么算？」上定（TODO-待选择卡回复后改写）。

## 八、当时的十一道选择题（2026-11-21，需求所有者回「全按推荐」）

原工单写过「另有 24 个候选点和 10 个没定的选择」，那份清单出自交接时另一个工具里的页面，仓库、项目共享文件夹与任务系统里都找不到原文。下面这组题是照 2026-10-22 执行稿里这件事的写法和 pstack 研究页那条建议重新整理的；第 11 题请需求所有者确认按这组题算。每题只抄推荐项和被放弃的选项各一句。

1. 这次做多大 —— 推荐：只写需求和决策记录，Agent 行为不变，实现另开一件。放弃：规矩和实现一起做；不做。
2. 经验库存在哪 —— 推荐：本机 `memory/` 下按品类各一份，不进仓库。放弃：每个任务文件夹各一份（任务一删就没了）；进仓库随 Skill 发布（别人会读到你的客户和品类）。
3. 同品类怎么认 —— 推荐：按开工时定下的品类名，先沿用旧名。放弃：不分品类共用一份；每次开工问一句。
4. 一条经验写哪几项 —— 推荐：局面、教训、证据、归因、规则版本五项缺一不收。放弃：只要前三项。
5. 谁批 —— 推荐：只收用户明确确认的，Agent 只起草。放弃：Agent 自动写、用户事后删。
6. 规则改了以后旧经验怎么办 —— 推荐：记规则版本，后两种状态照用但在数据边界标出，不停下问。放弃：规则一改全部停用等重新确认；不记版本。
7. 能不能存可照抄的句子 —— 推荐：不能，只记局面和判断。放弃：可以存例句。
8. 经验能管到哪 —— 推荐：只管语义筛选前读什么，不改打分、不碰已联系和拉黑。放弃：也允许按经验调打分。
9. 什么时候起草 —— 推荐：复评表与 Agent 判断有分歧时，下次重出报告附草稿，不追问。放弃：只在用户明说时起草。
10. 读不出来怎么办 —— 推荐：照常跑、写明没读到、不当空不覆盖。放弃：停下不跑。
11. 工单的关单标准怎么写 —— 推荐：改成「这组 11 道题逐项有裁决」。放弃：先去找原清单。

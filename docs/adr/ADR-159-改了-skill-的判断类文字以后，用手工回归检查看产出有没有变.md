## 一、它是什么，不是什么

**是**：改了 `skill/` 的判断类文字以后，在几个固定的真实任务上比一比新旧两版，看产出有没有变差的一套手工流程。机器只管产出；读和判由人做，判的是需求所有者。九项（能答什么、冻结集、重跑什么、新旧两版、先量噪声、盲比、判词、什么时候跑、成本）都在 `docs/REGRESSION.md`，一项一节。

**不是**：

- 不是闸门，不进 CI。跑不跑由需求所有者逐次定（`docs/REGRESSION.md`「h」）。
- 答不了「变好了没有」（第三节），也答不了开发信的真实效果：`AGENTS.md`「目前已知的缺口」第三行照旧留着，不消灭。
- 不是跨运行的记录。每次的结果只进那条改 `skill/` 的 PR 正文（第四节）。

**第一次跑要需求所有者指定 3–5 个任务目录。** 真实任务目录只在他的机器上（`output/` 不进仓库）。

## 二、为什么先写办法，不先跑

1. 真比对要用真实任务目录，只在需求所有者的机器上；本条那条 PR 在拿不到它们的地方写成，不跑真比对，也不提交任何真实任务数据（执行稿 P1 验收第 4 条照旧）。
2. 先写办法、不急着写脚本（拍板栏 1-1 选 A）：办法里哪几步值得交给机器，要真跑过一两次才看得出；先写成脚本，等于先把还没跑过的步骤钉死。执行稿举的外部例子：harness2 论文里，没有经验库时不实跑就直接改，三个域里两个掉分。这说明「改之前要有证据」，不说明「必须实跑」，所以办法可以先于第一次真跑写下来，而改 `skill/` 之前要有证据这一层，由这套办法给。
3. 办法里能不靠真实数据核的那几步，开 PR 前用假候选机械走了一遍（第五节）。

## 三、为什么叫「回归检查」，为什么「看着更好」不当证据

3–5 个固定任务只够发现退步。任务是改文字这一方挑的、又这么少，新版在它们上面看着更好，分不出是改对了还是改得正好合这几个任务。执行稿举的外部例子（都不在仓库里）：SkillOpt 在任务太少、训练集和验证集分不开时会自己标 `holdout_leaked`；RRSI 论文里，训练任务上分数最高的版本，换一批任务几乎没涨。

所以判词四档里「看着更好」只记录、不当证据。冻结集还偏着挑人工复评与 Agent 判断对不上的任务（`docs/REGRESSION.md`「b」），挑的正是旧版被人判得不对的地方，新版更容易显得好：这一偏向在文档里写在判词「看着更好」旁边。

## 四、它在回路里是哪一段

照 `process/README.md`「让机器照运行的反馈自己改:先画回路,没有传感器就不动」那一节画：目标是判断类产出不退步；控制者是改 `skill/` 的人或 Agent；被控对象是 `skill/` 里给 Agent 的判断类指令；输出是评审与草稿；这套回归检查是传感器。

它是**半开**的：机器产出，人读、人判，不跨运行累积，不驱动任何自动改动。所以结果只进 PR 正文，不建跨运行记录；以后要改成跨运行记录（比如攒下每次的噪声范围与判词，看同一处是不是在来回改），另提一条。

传感器怎么失效，失效了怎么办：

- **读不到**：没有指定任务目录，或冻结时第 4 步（搜旧判断原文）搜到了东西。不跑，或这一次不下判词，照实写进 PR 正文。
- **样本不足**：一直如此，本来就只有 3–5 个任务（第三节），所以只答有没有退步；新旧对的差别不超出噪声对量出的范围时，判「没看出差别」。
- **口径变了**：几跑用的不是同一个 Agent、同一个模型版本，差别里就混着模型那一份。这一次不下判词，照实写进 PR 正文。

## 五、冻结集里冻什么：读脚本与文字定的，再用假候选走了一遍

冻什么、不冻什么，是读 `skill/SKILL.md` Phase 04–06、`skill/references/semantic-fit.md`「判断保存在哪里」、`skill/references/output-format.md`「文件」与 `scripts/render.ts`、`scripts/lib/memory.ts`、`scripts/lib/review-projection.ts` 后列的，表在 `docs/REGRESSION.md`「b」。要点是三处会把旧判断漏给重跑的一方：名单 `creators.json` 里的旧判断投影、只给旧判断为 ✅、⚠️ 的候选取过数的 `enrichment.json`、人工作答 `manual-feedback.csv`。

列完以后，在 `902e63e` 的几个临时 worktree 里拿三个假候选，把「b」的冻法、「d」的四跑与「f」的改名、密封、开封机械走了一遍：不调模型（Phase 04 的判断由一段固定写法代替），不发请求，环境里没有 `TIKHUB_API_KEY`，worktree 根下没有 `.env`；假数据不进仓库，逐步结果在本条那条 PR 的正文里，是演示，不是证据。走出来的几件，都写进了文档：

1. 名单不重建，旧判断就漏过去：清空 `reviews` 以后，冻结集的 `creators.json` 里还搜得到旧理由；离线 render 一次重建以后搜不到了，候选都成了「未评」。
2. 整份删掉 `agent-review.json` 不行：render 重新冻结一轮候选，`rounds` 的时间变成那一跑的时间。名单里只存着旧式 `fit`、理由和草稿的老任务，render 还会把它们当判断迁回来：演练里造原任务那一步就是这样迁进来的（`scripts/lib/review-projection.ts` 第 36–56 行，只在正本缺席时迁）。
3. 真记忆不能拷进 worktree：把原任务那一跑写下的 `memory/creators.json` 拷过去，冻结集又改了名，候选全被当成「这个产品在别的任务里推荐过」滤掉，交付里一个不剩（`scripts/lib/memory.ts` 第 423–428 行）。几跑各在自己的 worktree 里写自己的 `memory/`，原任务那份目录里的记忆前后 SHA256 不变。
4. 时间漏先后：两跑旧版之间，除了草稿措辞，`task.json` 的 `updated_at` 也不同。所以几跑的先后随机排，盲比只拷交付物。
5. 费用账那一行命令每一跑都打「费用账没变」（假任务没有费用账，两边都缺席，只核了命令走得通）；密封文件判前、开封时两次算的 SHA256 相同。

和执行稿不一样的一处：执行稿写的是旧版两跑、新版一跑。独立复核指出，判的人先看过噪声对，新旧对里要是又出现噪声对里的一跑，草稿逐字认得出，就知道另一边是新版，新旧对其实不盲。所以旧版跑三次：前两次量噪声，第三次进新旧对；每个任务多一次 Agent 会话，API 费仍是零（文档「d」「i」）。

## 六、不要什么

- **不写盲评配对脚本**（拍板栏 1-1 选 A）：等真跑过一两次再说（第二节第 2 条）。选 B 的那种（随机改名、写密封文件、并排渲染的脚本放 `scripts/` 下，带测试与变异，照「新增可执行文件」接线）另开一条。文档里改名与密封那几行是给跑的人照抄的命令，不是检查链的一部分。
- **不进 CI，不做闸门**：判的是「读」，判据写不成一条命令（`process/README.md`「但上面那句有一整类例外:替代「读」的那些不要建」）。
- **不建跨运行记录**（第四节）。
- **不改 `skill/`、`scripts/`**，不动 `AGENTS.md`「目前已知的缺口」。

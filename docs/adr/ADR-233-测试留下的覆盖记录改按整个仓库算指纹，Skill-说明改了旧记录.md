## 一、决定

认领记录（需求测试写的单元认领、自检写的入口认领）的指纹，从「`scripts/` 下的 `.ts` 加 CI 工作流」改成**整个仓库**：git 列出的受控文件加上没被忽略的新文件，去掉 `.check-cache`、`node_modules` 与 `.env` 一类 —— 与变异派工带进 worker 副本的是同一份清单，用同一个函数筛。每个文件按字节算 sha256（不按 UTF-8 读，两份不同的二进制文件可能读出同一串替换字符），符号链接算它指向哪里、不跟进去（git 存链接也是这样），已经不在的、目录、子模块不算。

为什么是整份清单，不是「测试读到的那几个目录」：哪些文件被读今天能实测出来（第二节），加一条测试就变了；手写一份目录名单迟早漏，漏了没有东西提醒。整份清单是上界，而且有现成的证据说它够用：变异测试就是在只带这份清单的副本里把整套测试跑通的。多算的代价只是改一份没被读的文件（比如一份决策记录）也要重跑一次测试，才能单跑审计。这也是构建缓存的通行做法：Turborepo、Nx 默认都按包里 git 认得的全部文件算输入的哈希，不靠人列。

为什么不改 `sourceFiles`：变异那一步的源码身份（成本报告与启动数那份文件认它）仍只认 `scripts/` 与工作流。改一份说明不该要人重跑半小时的变异；那份身份防的是另一件事（变异清单与源码对不对得上），不是「测试证据新不新鲜」。

问不到 git（不是仓库、不在顶层、清单是空的）就抛错，不退回只算 `scripts/` 那棵树：退回去就是又一次「旧记录照样算数」，只是这回没人知道。不写记录的那几种跑（需求测试的子集、自检的子集、变异 worker 的副本，副本里没有 `.git`）不算指纹，所以不受影响。

## 三、测试与负片

- 需求测试 `h-infra-rules` 组，在临时目录建玩具 git 仓库（经 git 夹具）验：Skill 说明、需求表、代码都在指纹里；覆盖记录自己、依赖目录不在；改一份 Skill 说明指纹就变、改回去就回来；重写覆盖记录、被忽略的运行产物不改指纹；按字节算；符号链接改了指向指纹就变；已经不在的文件不进指纹；不在仓库顶层就抛错。不拿本仓库验：变异 worker 的副本里没有 `.git`，那样这几条在每一跑变异里都起不来。
- 变异：M-H14-au（指纹又只算 `scripts/`）、M-H14-av（不看链接指向）、M-H14-aw（按文字读文件）由需求测试抓；M-H14-ax（审计那一侧只拿 `scripts/` 比）由自检 `audit-entry` 组抓 —— 玩具树的记录按整个玩具仓库写，审计那一侧范围不同就说「记录是旧的」、以 1 退出。
- 自检 `audit-entry` 组：玩具树建成 git 仓库，两份记录在别的文件写好之后按现算的指纹写；第二跑往树里加了一份决策记录，记录跟着重写，否则审计先说「记录是旧的」、走不到欠条那一段。

## 四、没做的

- 写记录的那一侧（需求测试、自检）要是又改回只算 `scripts/`，审计那一侧算整个仓库，两边对不上，完整检查的审计一步当场红 —— 由检查链自己守，没有单独的变异。
- `claimInputEntry` 跳过的那几种（目录、管道、已删）与 `mutate.ts` 建副本时跳过的是同一套，各写了一份，没有抽成一个函数：本条不动变异入口。两份哪天不一致，后果是指纹多算或少算一个 worker 副本里本来就没有的特殊文件，不会让旧记录冒充新鲜。

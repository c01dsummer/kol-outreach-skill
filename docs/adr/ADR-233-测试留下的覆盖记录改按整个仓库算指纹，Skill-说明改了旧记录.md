## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 一次完整的需求测试真读了仓库里哪些文件 | `strace` 跟着整套需求测试（含它起的子进程）记下每一次打开文件，取落在本仓库里的那些（第二节） | 机器 |
| 「仓库里的文件」是哪些 | git：`ls-files -z --cached --others --exclude-standard`（受控的加上没被忽略的新文件），经 git 入口问；变异派工建 worker 副本用的是同一问、同一个筛法（`workerCopyList`） | 机器 |
| 整套测试只靠这份清单就跑得通 | 变异那一步：每条变异都在只带这份清单的副本里把验证者整个跑一遍，基线跑不绿就不施加变异 | 机器 |
| 改了一份 Skill 说明，审计认不认得出记录是旧的 | 需求测试里的玩具 git 仓库：改前改后各算一次指纹；自检 `audit-entry` 组在玩具仓库上真起审计 | 机器 |

## 一、决定

认领记录（需求测试写的单元认领、自检写的入口认领）的指纹，从「`scripts/` 下的 `.ts` 加 CI 工作流」改成**整个仓库**：git 列出的受控文件加上没被忽略的新文件，去掉 `.check-cache`、`node_modules` 与 `.env` 一类 —— 与变异派工带进 worker 副本的是同一份清单，用同一个函数筛。每个文件按字节算 sha256（不按 UTF-8 读，两份不同的二进制文件可能读出同一串替换字符），符号链接算它指向哪里、不跟进去（git 存链接也是这样），已经不在的、目录、子模块不算。

为什么是整份清单，不是「测试读到的那几个目录」：哪些文件被读今天能实测出来（第二节），加一条测试就变了；手写一份目录名单迟早漏，漏了没有东西提醒。整份清单是上界，而且有现成的证据说它够用：变异测试就是在只带这份清单的副本里把整套测试跑通的。多算的代价只是改一份没被读的文件（比如一份决策记录）也要重跑一次测试，才能单跑审计。这也是构建缓存的通行做法：Turborepo、Nx 默认都按包里 git 认得的全部文件算输入的哈希，不靠人列。

为什么不改 `sourceFiles`：变异那一步的源码身份（成本报告与启动数那份文件认它）仍只认 `scripts/` 与工作流。改一份说明不该要人重跑半小时的变异；那份身份防的是另一件事（变异清单与源码对不对得上），不是「测试证据新不新鲜」。

问不到 git（不是仓库、不在顶层、清单是空的）就抛错，不退回只算 `scripts/` 那棵树：退回去就是又一次「旧记录照样算数」，只是这回没人知道。不写记录的那几种跑（需求测试的子集、自检的子集、变异 worker 的副本，副本里没有 `.git`）不算指纹，所以不受影响。

## 二、实测：一次完整的需求测试读了哪些仓库文件

在主干 `c6e7c03` 的一份副本上，以 nobody 身份用 `strace -f -y` 跟着一次完整的需求测试（含它起的全部子进程），记下每一次成功打开的文件，按解析后的真实路径取落在副本里的普通文件（去掉 `node_modules`、`.git`、`.check-cache`、`output` 与测试运行时的 npm 缓存）：

| | 文件数 |
|---|---|
| git 列出的仓库文件（受控加没被忽略的新文件，去掉 `.check-cache`、`node_modules`、`.env` 一类） | 425（另有两份是 npm 把缓存写进了当时的家目录，那是这次实测的布置，不是仓库文件） |
| 其中这一跑真打开过的 | 423 |
| 打开过、却不在上面那份清单里的 | 0 |
| 原先的指纹算的（`scripts/` 下的 `.ts` 加 CI 工作流） | 154 |

真打开过的按目录：`docs/` 228 份（需求表、规矩、全部决策记录与历史文件）、`scripts/` 160 份（含 `.ts` 以外的 7 份，如变异清单 `mutations.json`，原先也不在指纹里）、`skill/` 11 份、`process/` 8 份、`.github/` 4 份、根目录 11 份、`proposals/` 1 份。没打开的两份是 `.agents/skills/` 与 `.claude/skills/` 底下指回 `skill/` 的符号链接。

结论：一次完整的需求测试几乎把整个仓库读了一遍；原先的指纹只盖住了其中三分之一多一点。整份清单与真读的只差两条符号链接，按整份算没有多算多少。

## 三、测试与负片

- 需求测试 `h-infra-rules` 组，在临时目录建玩具 git 仓库（经 git 夹具）验：Skill 说明、需求表、代码都在指纹里；覆盖记录自己、依赖目录不在；改一份 Skill 说明指纹就变、改回去就回来；重写覆盖记录、被忽略的运行产物不改指纹；按字节算；符号链接改了指向指纹就变；已经不在的文件不进指纹；不在仓库顶层就抛错。不拿本仓库验：变异 worker 的副本里没有 `.git`，那样这几条在每一跑变异里都起不来。
- 变异：M-H14-au（指纹又只算 `scripts/`）、M-H14-av（不看链接指向）、M-H14-aw（按文字读文件）由需求测试抓；M-H14-ax（审计那一侧只拿 `scripts/` 比）由自检 `audit-entry` 组抓 —— 玩具树的记录按整个玩具仓库写，审计那一侧范围不同就说「记录是旧的」、以 1 退出。
- 自检 `audit-entry` 组：玩具树建成 git 仓库，两份记录在别的文件写好之后按现算的指纹写；第二跑往树里加了一份决策记录，记录跟着重写，否则审计先说「记录是旧的」、走不到欠条那一段。

## 四、没做的

- 写记录的那一侧（需求测试、自检）要是又改回只算 `scripts/`，审计那一侧算整个仓库，两边对不上，完整检查的审计一步当场红 —— 由检查链自己守，没有单独的变异。
- `claimInputEntry` 跳过的那几种（目录、管道、已删）与 `mutate.ts` 建副本时跳过的是同一套，各写了一份，没有抽成一个函数：本条不动变异入口。两份哪天不一致，后果是指纹多算或少算一个 worker 副本里本来就没有的特殊文件，不会让旧记录冒充新鲜。

## 五、欠条清点

三个独立上下文按台账（864 条）分段按字面判过，本条上响了的：

- ADR-231「认领记录的指纹不含测试读的 Skill 文档」：本条就是还它，ADR-231 末尾补了「已还」。
- ADR-158「覆盖记录过期诊断没提工作流正文」：本条改了那句诊断；顺手把「CI 工作流」写进括号，ADR-158 末尾补了「已还」。
- ADR-70「审计读入口认领那处接线没有负片」：两支条件都中（改了 `audit-entry` 的玩具树、改了审计算指纹那一行），没还：要还得在玩具树里造只由自检认领的判据再配一条变异，与本条要修的事无关。在原块上写明这次又响、从本条合入起重数，照拆 ADR-151 那次的写法。
- ADR-89 第 92 行（加变异时看盖的是不是没人盖过）：核过，四条变异的锚点都在本条新写的代码上，主干上一处也没有；仍没有变异守的是第四节那几处。
- ADR-99「性能那轮流程失误待收尾，开 PR 前核在途 PR」：每条 PR 都做的一步，结果写在 PR 正文。

拿不准、按窄读不响的（两种读法都写在清点回报里）：往入口脚本加判定那几张（ADR-231 第 176 行一类：本条在 `test.ts`、`selfcheck.ts` 里只是给原有的「拥有记录」条件起了名字，判定仍在 `claims.ts`）；硬退出收口那张（ADR-70：审计那处 `process.exit(1)` 没动，只改了它前面那句话的字）；自检夹具引用判定模块先核变异路由那张（ADR-155：`selfcheck.ts` 原本就引 `claims.ts`，`claims.ts` 新引了 git 入口与派工判定两份模块，路由若有变化在启动数那份文件的写回里看得见）。

另外，ADR-231 第十节同时到期的扩范围那张「增强结果读入时整份校验」不归本条，另一条线程在做（读入增强结果时整份对照格式说明）。

# ADR-140 进度键在 task.json 里写重复时按每一处原文拒绝，不再只按读入后留下的最后一处放行

- 日期 · 2026-10-11 · 还 ADR-139 第五节第一张既有缺陷的欠条（重复键 `"found":{"0":1e400,"0":3}` 按后一个值判为合规），需求所有者 2026-10-11 定为修（「开 PR 修」）

- 触发它的事实：主干 `0423c3e` 上（接口桩 `8546ec8` 行为相同），`task.json` 里写 `"found":{"0":1e400,"0":3.000}`：
  collect 续跑与 `--budget 2` 改额都以 0 结束，预留 6 次、请求 6 次，task.json 被整份写回；render 以 0 结束，新建 kol.csv、kol.xlsx。
  整份写回后 `found` 只剩 `{"0":3}`（`stringifyCostJson(readCostDocument(…))` 实测），`1e400` 从盘上消失。反过来的顺序 `{"0":3,"0":1e400}` 被拒，但诊断只显示 `1e400`，看不出文件里还有一处 `3`
- 冲击的需求：D19（正文补半句，新增 D19.k、D19.l）；D19.g 与 D19 × P1 裁决的措辞（还 ADR-139 第五节第二张，见第二节第 4 条）；P1（交点 D19 × P1 已在，裁决含义不改）

## 一、决定

1. **回到源文本找，不在解析结果上找。** `JSON.parse`（连同 reviver 与 source context）只交出最后一处，前几处在解析结果里没有任何痕迹，reviver 也只被叫到留下的那一处。
   能看见它们的只有源文本。扫描只跑在 `JSON.parse` 已经接受的文本上，所以只认记号、不做语法校验；键按解码后的名字比，`"0"` 与 `"\u0030"` 是同一个键，与 `JSON.parse` 判「同一个键」的口径一致。
2. **放在 `readCostDocument` 旁边，用到时才扫。** 它是读 task.json 的唯一入口，本来就按读入的根留着原文证据（`sourceNumberToken`）；重复键是同一类证据。
   读入时只留住源文本，扫描推迟到有人问 —— 只有 collect 续跑与 render 判进度时问，enrich、probe、`calibration version`、collect 新建任务不付这份时间。
   一开始写成读入时就扫（那时还用正则认字符串），3.9 MB 的任务文件读入的墙钟时间从约 140–190 ms 变成约 300–400 ms，才改成用到时扫；改后不问的读入方与主干同速。
   用到时的扫描（逐字符那一版）在 7.8 MB 的任务文件上另花约 120–360 ms CPU 时间（`process.cpuUsage`，7 次），同一份文件读入本身的 CPU 时间与主干同在约 330–560 ms。
3. **只记根与根下一层的对象，逐字符走。** 五个进度键在根上，四张表在下一层。更深的层只记层数、不记键；扫描不递归，字符串靠找下一个引号、看前面紧挨着几个反斜杠认出结尾，不用正则。
   ADR-136 记过的深键（读得进来的两千多层）与很长的字符串（九百万字、三千万字都试过）都扫得完。第一版用正则认字符串，九百万字的字符串就让正则引擎栈溢出（第五节第 1 条）。
4. **判为不合规、整份拒绝，不替用户挑一处。** 按最后一处放行就是替用户挑了一处；改成按第一处同样是挑。哪一处是真的只有改文件的人知道，诊断按文件里的先后把每一处原文列出来让他定。
   拒绝的出口沿用 D19.e、D19.h（ADR-117、ADR-139）：collect 在预留与请求之前、render 在任何写入之前以 2 退出。
5. **诊断的形状。** 表里的重复点名 `found["0"]`，根上的重复点名 `found`；写出出现次数；数字与字符串照原文 token，对象与数组记作 `{…}`、`[…]`。
   整张表的原文可能很长、跨很多行，整段印出来不比「去文件里找第二个 `found`」更好用，也会把别处的数字混进这一行。重复与值本身的问题各报各的（D19.c）：`{"0":3,"0":1e400}` 既报重复、也报留下的 `1e400` 不合规。

## 二、逐条评定

1. **触碰红线吗？** 撞的就是 P1：按最后一处放行，前几处原文在整份写回时被悄悄抹掉，留下的那个数看起来像测量值。拒绝不违反任何红线。
2. **缩范围还是降标准？** 都不是。没有重复键的文件判据一字未改，collect 收的 render 都收；新拒的只有本来就靠 `JSON.parse` 的实现细节挑了一处的那部分。
3. **可逆吗？** 可逆：判据里多一类问题，删掉即回到原样。
4. **D19.g 与 D19 × P1 裁决的措辞。** 本条改了 D19 正文，响了 ADR-139 第五节第二张欠条，顺手还上：D19.g 末句写明「render 见到坏进度按 D19.h 在写回前拒绝，经它写回的只有合规进度」，
   裁决写明坏断点留给「collect 续跑与 render 导出（D19.h）」按原文拒绝。两处含义不变，只把 ADR-139 之后 render 那一层写出来；D19.g 的认领与断言不动。
5. **D19.g 对写重复的输入不成立，本条不改它的正文。** D19.g 要 enrich、`calibration version` 整份写回后每个进度数字与盘上原文逐字相同；写重复的进度经它们写回，前几处照样消失。
   这是主干上就有的既有缺陷，需求所有者这次定的范围是 collect 与 render，见第四节的欠条。

## 四、边界

- 只管 collect 续跑与 render，只管根上的五个进度键与四张表里的任务索引键。D19.k 以外位置的重复键照旧按最后一处读，见下面欠条。
- 读不进来的深度（`JSON.parse` 自己栈溢出）是读取错误（D16.n），到不了这一步；扫描本身不递归。
- 读入的根活多久，它的源文本就跟着活多久（enrich 一整轮都留着）。任务文件是 MB 量级，这份内存不另计。

> ⚠️ 欠条：enrich（普通、改额）与 `calibration version` 不判进度（ADR-138 第二节否决过拒绝式），整份写回写重复的进度时只留最后一处，前几处原文消失；之后 collect 续跑照常预留与请求（复核实测：先跑 `calibration version` 以 0 结束、`found` 写成 `{"0":3}`，再续跑预留 6 次、请求 6 次）。D19 正文、D19.g 与 D19 × P1 裁决已写明这个例外，SKILL 与 README 提醒修好重复之前别跑这两个命令。主干上就这样，是既有缺陷；需求所有者 2026-10-11 定为下一条 PR 修：两个写回方在写回前遇到 D19.k 的重复以 2 拒绝 · 重启条件：本 PR 已合入（按 `process/6-INTEGRATE.md`「既有缺陷」排在下一条之前，修不修已定）

> ⚠️ 欠条：根上其他键写重复时任何入口都不判，读入后只剩最后一处，整份写回时前几处消失。最要紧的两类：`tasks`（进度索引的依据 —— `"tasks":[A,B],"tasks":[C]` 时进度按最后那份列表判，前一份写回时消失，collect 续跑以 0 继续，复核实测）与费用计数 `requests`、`cost_ledger`（P3 —— `"requests":7,"requests":0` 被收下、写回时抹掉）；另有 `budget_usd`、`brand_calibration` 等。主干上就这样，是既有缺陷；修法要先定是对整份 task.json 判重复、还是逐个字段判 · 重启条件：本 PR 已合入（按 `process/6-INTEGRATE.md`「既有缺陷」排在下一条之前，由需求所有者定修不修）

## 五、独立复核的发现与去向

复核者没写过这段代码，只读判据与 diff，自己造输入跑判据与两个入口（`6243a2c`）；另拿 14 万份随机合法文档与它自己写的递归下降参照做差分（重复集合、所在对象、原文与先后），0 处不符。

   render 与 collect 续跑带着 `RangeError` 与堆栈以 1 退出，合规的进度也导不出来（D19.j、D19.i）；主干以 0 结束。第一节第 3 条原先说「扫得完」也就不成立。

2. **档：本改动 · 去向：本 PR 修。** D19.k「不由本条判」那一半没有测试：根上白名单换成任意键、去掉表的白名单、记键的层数放到三层，三个自然的改法都存活，各自让 render 拒绝合规的进度。

   改成交回 `null`，判据报「无从核对」；先写的断言对着旧代码红，配 M-D19-ak、al。今天的调用方都传读入的根，够不到。
4. **档：既有缺陷（行为）与本改动（措辞） · 去向：行为下一条 PR 修（需求所有者 2026-10-11 定），措辞本 PR 修。** enrich 与 `calibration version` 写回时照样只留最后一处，之后 collect 续跑照常花钱；
   D19 正文、D19.g 与 D19 × P1 裁决读起来都是无条件的。三处写明这个例外并指向第四节的欠条；SKILL 与 README 提醒修好重复之前别在该目录跑这两个命令。
5. **档：既有缺陷 · 去向：登记，见第四节第二张欠条。** `tasks` 写重复时进度按最后那份列表判、前一份写回时消失；`requests` 写重复同样被收下、抹掉（P3）。欠条点名这两类，便于排先后。
6. **档：本改动 · 去向：本 PR 修。** M-D19-ag 的 why 写的是机制（「读入时不留源文本」），`mutate --brief` 会把它交给写测试的上下文；改成需求语言。
7. **档：本改动 · 去向：本 PR 修。** 自检 D19.l 的 collect 一半只比 task.json，D19.l 说的是「任何文件或跨任务记忆写入之前」。改成任务目录与记忆整棵比（行为本来就成立，复核另行实测过），断言名跟着改，配 M-D19-ap。
8. **档：本改动 · 去向：本 PR 修。** 几处措辞：README 与 output-format 写「统计键」，`done` 不是统计表；`cost-json.ts` 文件头写「读入时记下」，实际是用到时才扫；
   本记录第一节第 1 条的 `"\u0030"` 丢了反斜杠；第一节第 2 条的时间没说是墙钟还是 CPU。
9. **档：驳回。** 三条规格选择：
   - 根上重复时前几处只标 `{…}`／`[…]`，里面的坏值要等用户挑完一处才报：理由在第一节第 5 条，挑完之后下一次判进度照常逐项判。
   - `done` 写重复时只显示 `[…]、[…]`，两处分不出来：同上，去文件里找第二个 `done` 就能看到。
   - 两处一模一样（`"1":1,"1":1`）也拒：D19.k 说的是「出现不止一次」；按值相同放行得先定按原文还是按数（`1` 与 `1.0` 按数相同、按原文不同，写回后后者就没了）。手改留下的重复本身就值得人看一眼。

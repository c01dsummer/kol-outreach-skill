# ADR-92 粉丝数三档排序：未查询压得过 0，压不过已查到的非 0

## 裁决

需求所有者 2026-09-19：**粉丝数未查询的人，排在粉丝数确实是 0 的人前面。**

落成判据 `P1.h`：同一层、同一分数时，粉丝数分三档 ——
**已查到且不是 0 → 未查询 → 确实是 0**。
**只改先后，不改分数也不改分层。**

## 一、这句话有两种落地，选了哪一种

| | 做法 | 后果 |
|---|---|---|
| 加分 | 给「未查询」一个分值 | 他整体上移，**可能跨档** —— C 变 B |
| **排序** | 分数不动，打平时让他站前面 | 同档同分内部换位，**档位不动** |

**选了排序。** 给分等于替他编一个他可能并没有的实力：那个分值从哪来？
没有依据，只能拍一个，而拍出来的数会把人推进他不该进的档。
「不知道」的正确待遇不是「当他强」，是**「让人先看见他」** —— 排序正好只做这件事。

顺带：这也保住了 `scoreCreator` 的一条既有性质 —— 未查询的维度**不折算成任何具体值**。
加分会当场破掉它。

## 二、我先把规则写宽了，需求所有者不认 —— 记在这里

裁决的原话是拿 0 说的。我落地时写成了「未查询 vs **已查到**」，
理由是只跟 0 比在比较器上像个特例，而「已查到的那位量过了仍然不够」听着更一般。

**推广出去的东西我自己报了**：同层同分、一个未查询一个已查到 5 万，
按那个写法未查询的也会排前面。需求所有者的答复是 **不认** ——

> 排已知粉丝数后面，0 粉前面。

所以收窄成三档：**已查到且不是 0 → 未查询 → 确实是 0。**

**收窄之后的理由比原来那版硬**：

> 「未查询」只压得过一个确认为 0 的人，压不过任何一个真查到了数的人。
> 查到了数的那位**有据可依**；未查询的那位只是**可能**够 ——
> 凭一个还没量过的可能越过量过的事实，是拿「不知道」当本钱。
> 而确实是 0 的那位已经量过、就是 0，「不知道」比他多一分指望，所以在他前面。

**这一节记的是一次实现者的越权被纠回来。** 裁决说的是 0，我推广到了「已查到」，
推广的那一步没有人授权 —— 我报了，但报了不等于被批准。
负片 `M-P1-n` 就是守这一条的：把三档压回两档（也就是我原来那个写法）当场红。

## 三、测试：正序逆序各排一次，三档还要两两各钉一次

打平时排序是稳定的：比较器返回 0，结果就跟着输入顺序走。
**只写一个方向的断言，一半的错误实现照样绿** —— 包括「这一条根本没生效」。
所以同一组输入正序逆序各排一次，两次都要求同一个结论。

这个手法不是本条发明的：ADR-88 里那个隔离上下文独立用了同一招，
理由一字不差。

**三档还要两两各钉一次。** 三个一起排的时候，只要有一档放对了，
另一档错位也可能被挤回正确的位置 —— 那样一条错的实现能让整串看着是对的。

还有一条管另一个方向：**这一条只在打平时说话**，不许越过分数插队 ——
越得过去就等于偷偷加了分，而那正是第一节判掉的做法。

## 四、动了哪几处

| | |
|---|---|
| `scripts/lib/rows.ts` | 排序比较器加第三级。全仓只有这一处排序，名单与分 sheet 都走它 |

| `scripts/check/mutations.json` | 两条负片：`M-P1-m` 把第三级整个去掉，`M-P1-n` 把三档压回两档（第二节那个被驳回的写法）|

**`U1` 没动。** 它的判据说「行序满足 A→B→C 且同层分数递减」——
加一条打平时的次序，这句话仍然成立，不是改它的含义。

## 五、ADR-88 那张「评分侧与采集解析侧没有判据」的欠条

重启条件是「下一条要动 `docs/requirements.json` 里 P1 的改动」，本条踩到了。
**只还了一部分，把账说清楚：**

- **排序侧**：本条新增 `P1.h`，有认领、有负片。
- **评分侧**：仍然没有自己的判据编号。但**行为本身有变异守着** ——
  `M-P1-b` 指的就是评分里那行「粉丝数未查询时不给分、也不当作 0」，
  它记在 `P1` 名下而不是某条判据名下。隔离上下文要的是给它一个编号，本条没给：
  裁决把出口改在了排序侧，评分侧一个字没动。
- **采集解析侧**：ADR-90 补了测试，**不是判据**。

⚠️ 欠条：**评分侧「未查询不折算成具体值」只有变异守着，没有自己的判据编号。**
重启条件：下一条要动 `scripts/lib/score.ts` 里那几条「未查询不给分」的改动，
或者下一次有人要给这条性质做拆分计量时。

## 六、没做的

- **没有回头看别的排序键有没有同一个毛病。** 本条只处理了粉丝数这一个字段。
  作品数、播放数同样是三态，它们在排序上有没有被压平，本条没查。
  ⚠️ 欠条：**只审了粉丝数这一个排序字段。**
  重启条件：下一条要动排序比较器的改动。
- **没有给这条规则做端到端验证。** 它在单元层有三条断言和一条负片，
  但「产出的 CSV／xlsx 里真的是这个顺序」没有在自检里跑过一遍。
  ⚠️ 欠条：**排序的新规则没有端到端跑过。**
  重启条件：下一条要动交付物产出那一段的改动。

> ⚠️ 上文第六节第一条那张欠条（「只审了粉丝数这一个排序字段」）已还：`scripts/lib/rows.ts` 里每个排序比较器的每个键都过了一遍，基线 `367393e`，结论记在这里。
>
> 那张欠条挂的条件第一次明确成立是 #250（`59d14c4`，2026-10-01）：它在 `rows.ts` 加了 `sortForReviewOutput`，在原排序外面再按 `effective_priority` 排一层，当时没回来审。之前 #146（`16c3abf`）和 #147（`e4565cc`）碰过 `bestPost` 那几行，一个改了外面的空数组判断，一个把注释改准，比较器的表达式都没动。
>
> **先更正第四节一句话。** 「全仓只有这一处排序」在本条合入时（#127，`825fd2d`）就不准：`rows.ts` 里另有两处排序，`topGeo` 挑受众占比最高的国家，`bestPost` 挑播放最高的那条作品；`scripts/probe.ts` 也已经有一处按粉丝数排的取样（当时在第 64 行，见文末）。这三处排的都不是名单：前两处挑一个格子里印什么，后一处挑试探样本。所以那句话按「名单排序」读是对的；但欠条问的「作品数、播放数……在排序上有没有被压平」，播放数那一半的答案恰好在 `bestPost` 里。
>
> 逐个比较器、逐个键：
>
> | 比较器 | 键 | 怎么排 | 三态压平了没有 |
> |---|---|---|---|
> | `sortForOutput` | `tier` | A → B → C → 缺席 | 没有，缺席单独排末位 |
> | `sortForOutput` | `score` | 有分的按分降序 → 没算过分 | 没有，0 分与没算过分分得开（`P1.f`，负片 `M-U1-d`；`M-U1-c` 记在 `U9.a` 名下，点的是同一条断言） |
> | `sortForOutput` | `followers` | 已查到且不是 0 → 未查询 → 确实是 0 | 没有，就是本条的 `P1.h`（负片 `M-P1-m` `M-P1-n`）。同一档内不按数的大小排，5 万和 8 千谁在前看输入顺序；`P1.h` 本来就只分三档 |
> | `sortForReviewOutput` | `effective_priority` | 优先联系 → 备选 → 待核实（缺席也排在这里）→ 暂不采用 | 排序位置上缺席与「待核实」并列，这是需求写定的，见下 |
> | `bestPost` | 作品的 `plays` | 播放降序，缺播放数按 0 排 | **压平了**：缺播放数与真实 0 并列，谁在前看输入顺序。已有记录，见下 |
> | `topGeo` | 各国受众占比 | 降序取第一 | 不涉及三态：值都是数，整份缺席在上一行已经挡掉 |
>
> `post_count`（作品数）不是任何一个比较器的键。
>
> **`effective_priority` 缺席排在待核实的位置，是有意的。** `U9.b` 逐字写「effective_priority 缺席只在排序上落在待核实位置，不写回建议」，`U9.c` 对 XLSX 各表照搬；`docs/requirements.json` 里 `U9` 对 `P1` 的 tension 裁决（出处 ADR-130）写「有效建议缺席的排序位置不制造字段值」。展示上两者仍分得开：表格里缺席是空白，HTML 标「未提供」（`U9.h`，ADR-130 第 50、164 行）。压的只是先后，不是取值，和本文第一节判掉加分、只动先后是同一个分寸。
>
> 实测（在仓库外的副本上跑的）：同层同分同粉丝数的两个人，一个缺席、一个待核实，正序输入时缺席在前，倒序输入时待核实在前，谁先看输入顺序。外面那层是稳定排序，原排序的三态照旧当次级键用；`M-U9-b` 把里面那层原排序换成原样输入，点名弄红的是「U9.b 180组冲突键按优先级层级分数粉丝三态稳定排列」。那条断言的输入里带着缺席：把 `? 2` 改成 `? 3`，按它的期望函数逐位比，180 个位置里有 107 个对不上。这只是在副本上算的，没跑变异；`scripts/check/mutations.json` 里也没有一条变异指着这个 `? 2`。
>
> **`bestPost` 那一处不是新发现。** ADR-102 第六节第 4 条早就写了「挑播放最高那一条时，缺播放数的按 0 排」，归在 `P1.b` 的全称豁免底下（ADR-77），那份文件第 128 行登了欠条，等用户要求区分、或者有人改最佳作品的选择规则时再动。它只决定 `best_post_desc` 印哪一条的文案，不动名单先后。要不要也按本条的三档来挑（真查到的非 0 → 缺播放数 → 真 0），等于把需求所有者对粉丝数的裁决推广到播放数，正是本文第二节记下的那种越权；留给 ADR-102 那张欠条，不在这里自己定。
>
> **`null`。** 上面这几个键的类型里都没有 `null`，比较器只按类型里的那几态排。拿 `null` 在 `sortForOutput` 的三个键上试过：`followers` 为 `null` 会排进「已查到且不是 0」那一档，`score` 为 `null` 会和 0 分并列，`tier` 为 `null` 和缺席一样排末位；`effective_priority` 与播放数没拿 `null` 试。走管线的名单里，前两个到不了这一步：`score` 只在 `scripts/lib/pipeline.ts:407` 写，值来自 `scoreCreator`，是数；`followers` 为 `null` 的人先在入池闸门（`scripts/lib/score.ts:62` 的 `passesFollowerGate`）被当成不在区间挡掉，轮不到排序。
>
> 名单之外还有两处按粉丝数比先后：`scripts/probe.ts:86` 小样试探取样，`scripts/lib/identity.ts:102` 跨平台合并时挑哪条当主记录。两处都把缺粉丝数当 -1，比真 0 还低一格。没有压平（-1 与 0 分得开），先后和 `P1.h` 相反；`P1.h` 管的是名单排序，这两处不在它的范围里。

# ADR-92 粉丝数三档排序：未查询压得过 0，压不过已查到的非 0

## 裁决

需求所有者 2026-09-19：**粉丝数未查询的人，排在粉丝数确实是 0 的人前面。**

落成判据 `P1.h`：同一层、同一分数时，粉丝数分三档 ——
**已查到且不是 0 → 未查询 → 确实是 0**。
**只改先后，不改分数也不改分层。**

## 一、这句话有两种落地，选了哪一种

| | 做法 | 后果 |
|---|---|---|
| 加分 | 给「未查询」一个分值 | 他整体上移，**可能跨档** —— C 变 B |
| **排序** | 分数不动，打平时让他站前面 | 同档同分内部换位，**档位不动** |

**选了排序。** 给分等于替他编一个他可能并没有的实力：那个分值从哪来？
没有依据，只能拍一个，而拍出来的数会把人推进他不该进的档。
「不知道」的正确待遇不是「当他强」，是**「让人先看见他」** —— 排序正好只做这件事。

顺带：这也保住了 `scoreCreator` 的一条既有性质 —— 未查询的维度**不折算成任何具体值**。
加分会当场破掉它。

## 二、我先把规则写宽了，需求所有者不认 —— 记在这里

裁决的原话是拿 0 说的。我落地时写成了「未查询 vs **已查到**」，
理由是只跟 0 比在比较器上像个特例，而「已查到的那位量过了仍然不够」听着更一般。

**推广出去的东西我自己报了**：同层同分、一个未查询一个已查到 5 万，
按那个写法未查询的也会排前面。需求所有者的答复是 **不认** ——

> 排已知粉丝数后面，0 粉前面。

所以收窄成三档：**已查到且不是 0 → 未查询 → 确实是 0。**

**收窄之后的理由比原来那版硬**：

> 「未查询」只压得过一个确认为 0 的人，压不过任何一个真查到了数的人。
> 查到了数的那位**有据可依**；未查询的那位只是**可能**够 ——
> 凭一个还没量过的可能越过量过的事实，是拿「不知道」当本钱。
> 而确实是 0 的那位已经量过、就是 0，「不知道」比他多一分指望，所以在他前面。

**这一节记的是一次实现者的越权被纠回来。** 裁决说的是 0，我推广到了「已查到」，
推广的那一步没有人授权 —— 我报了，但报了不等于被批准。
负片 `M-P1-n` 就是守这一条的：把三档压回两档（也就是我原来那个写法）当场红。

## 三、测试：正序逆序各排一次，三档还要两两各钉一次

打平时排序是稳定的：比较器返回 0，结果就跟着输入顺序走。
**只写一个方向的断言，一半的错误实现照样绿** —— 包括「这一条根本没生效」。
所以同一组输入正序逆序各排一次，两次都要求同一个结论。

这个手法不是本条发明的：ADR-88 里那个隔离上下文独立用了同一招，
理由一字不差。

**三档还要两两各钉一次。** 三个一起排的时候，只要有一档放对了，
另一档错位也可能被挤回正确的位置 —— 那样一条错的实现能让整串看着是对的。

还有一条管另一个方向：**这一条只在打平时说话**，不许越过分数插队 ——
越得过去就等于偷偷加了分，而那正是第一节判掉的做法。

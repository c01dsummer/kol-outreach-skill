## 一、判据原文

`P1.p`：搜索结果里供应商没给的粉丝数、作品数（字段没有，或者是空值），记成「未查询」，不记成 0。搜索接口对所有人一律回 0 的作品数只是占位，不当成真实的作品数，也记成「未查询」。

原文由执行者照现有做法起草，需求所有者在选择卡上照这句选定，一字未改。

## 二、怎么认领、谁守着

- 新组 `p1-search-counts` 认领 `P1.p`，断言由没读过实现的会话写（第三节）。四条搜索路各造一页：TikTok 视频搜索、Instagram 短视频搜索、短视频搜不到人时改搜账号名、Instagram 话题搜索；再直接喂一次话题页解析函数。每页里一个账号两个数都不给、一个都给空值、一个作品数给 0；TikTok 那页再加一个两个数都是真值的正对照，免得「一律记未查询」也过得去。每个账号都核了不带「给了怪值」那个记号（那是 `P1.m` 的「已查询但未取得有效值」，与「没给」是两个态）。
- 取值先转成字符串再比：本仓库的 `eq` 走 JSON.stringify，数组里的 undefined 与 null 比不出差别；人没解析出来时得「查无此人」，不会被读成「未查询」而空过。
- 原来 `p1-provider` 组里那两条（搜索没给粉丝数仍是未查询、占位的 0 不成为真实的 0）不动，也不认领 `P1.p`。
- 判据级负片，逐条施上、只跑新组，都被抓到：
  - 原有的 `M-P1-j`（没给的粉丝数记成 0）、`M-P1-k`（占位的 0 当真值）改记在 `P1.p` 名下，多点名新组里抓到它们的断言。
  - `M-P1-bj`：空值当成给了怪值。`M-P1-bk`：没给的作品数记成 0。
  - `M-P1-bl`、`M-P1-bm`：搜索结果里的粉丝数、作品数一律不读，正对照那几条抓它们。
  - `M-P1-bn`、`M-P1-bo`、`M-P1-bq`：Instagram 三条搜索路把没给或空值的两个数补成 0。
- 没有负片点名的断言共 19 条：
  - 各页「不记怪值」那几条，除了 TikTok 两个字段都是空值那条（`M-P1-bj` 抓）。Instagram 四处今天根本不碰这个记号，TikTok 那三个账号（没给、占位 0、正对照）走的是已经滤掉空值与占位 0 之后的读数，造不出一个说得通的错法只让它们单独变红；它们守的是以后有人改读数时别把「没给」读成怪值。
  - 四条「确实请求了某个端点」：它们只证明素材真的走到了那条路，免得后面的断言在别的路上空过，本身不守判据。
  - 每周整跑的「从没红过的断言」清单会列出这 19 条，读法照上面。
- Instagram 那几条「零作品数记成未查询」守的是今天「这几条路不读作品数」。哪天这几条路开始读作品数，先问清 Instagram 搜索给的 0 是不是占位，再改这几条；测试文件里那组开头写了同样的提醒。

## 三、断言由没读实现的会话写

`P1.p` 是红线判据，照 `process/4-VERIFY.md`「给测试上下文一张准入读物清单」做，与 ADR-226 第四节同一做法：

1. 在本条的工作树上（需求与变异已写好、实现没改）跑 `npm run admission -- P1 <仓库外目录>`，出一个 69 个文件的包。包头写着出自提交 7ef4cb11、工作区还有没提交的改动（那时只差一条变异说明的措辞）。
2. 一个只拿到这个包路径的会话，被告知只读这个目录、不碰仓库、不跑程序、不发网络请求，写出一份测试文件和一份说明。产出在项目文件 `iou-ledger-tooling/parse-criterion-isolated/`（`tests.ts` SHA256 `b389f9ec204ac8ad64f4cede6f3b9b96dfc737910404f899245fde12f102afd4`，`说明.md` SHA256 `b13f21eba777581c9c2c6562cf76b33aaa9a24413b7c20abb95766da1dbfcf94`），不随提交走；会话记录在仓库外，这里只能说作者核过它只读了这个包。
3. 它写了 56 条断言，其中 17 条在名字里标了「假设」。原样跑一遍：48 条过，8 条不过。不过的全是 Instagram 三条搜索路与话题页解析的「正对照：真给了的粉丝数、作品数照留」。它假设这几条路会读这两个数；实际上这几条路从来不读，等主页补全那一步再填（对外文档只含糊写了一句「仍待 profile 补全」），所以给了真值也是「未查询」。这对 `P1.p` 是对的。
4. 搬进 `scripts/test.ts` 新组 `p1-search-counts`，改了这几处：
   - 删掉那 8 条，Instagram 素材里随之去掉正对照那个账号。
   - 自带的 `eq`、`ok`、假 fetch、开预算换成本文件的；断言名里的「〔假设〕」去掉。
   - 隔离稿里 Instagram 三条搜索路本来就是逐条写的；搬入时把三条路的请求素材收进一张小表，每条路的断言仍逐条写字面名字（变异点名要在源码里找得到字面的断言名）。
   - 其余断言名、素材、期望值一字未改。搬入后 48 条在没改的实现上全过。
5. 这次找出了原测试漏掉的错法：原来只有 TikTok 一条路有断言，Instagram 三条路把两个数补成 0（`M-P1-bn`、`M-P1-bo`、`M-P1-bq`）原测试一条都抓不到；搜索结果的数一律不读（`M-P1-bl`、`M-P1-bm`）原测试也抓不到。
6. 它列的「判据或文档没说清」13 条，去向：
   - Instagram 搜索条目上粉丝数、作品数叫什么、这几条路读不读：照第 3 步，判据对它们成立；对外文档那句含糊，并进第四节交给需求所有者的那张。
   - 占位的 0 只在 TikTok 实测过，它把 Instagram 作品数给 0 也写成「未查询」：Instagram 这几条路两个数都不读，0 与别的值一样是「未查询」，与判据不冲突，留着。
   - TikTok 搜索给了非零作品数照留：对，留着，由 `M-P1-bm` 守。
   - 搜索给了真实的粉丝数 0：判据没说，它也没写断言；现行代码照收 0，不在本条范围。
   - 怎么替换请求层、响应外壳长什么样、预算怎么开、`eq` 从哪来、条目至少要哪几个字段：都是准入读物包本身缺的，并进第四节那张。
   - 请求间隔 150 毫秒关不掉、包与提交对不上：只影响跑得快慢与可追溯，不改断言。

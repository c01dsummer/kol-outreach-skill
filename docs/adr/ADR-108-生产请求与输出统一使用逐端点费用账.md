# ADR-108 生产请求与输出统一使用逐端点费用账

- 日期：2026-09-23
- 类型：事实证伪与需求补充
- 触发事实：现有付费入口与 render 仍按请求总数乘统一单价；ADR-107 已建立固定八端点价目及纯费用账，但尚未接入请求。普通 JSON.parse 会把 `0.00499999999999999999999999999999999999999` 舍入为 0.005，Number 往返会把 `9007199254.740991` 变为更大数值。旧 task 的请求总数不足以恢复分端点历史金额。
- 冲击的需求：P3、D6、F7；新增 D13，承接 D12；P1、P3、P5 交点写入 D13。
- 结论：采纳
- 理由：请求额度与持久费用必须依据同一已核金额，不能把旧估算继续当剩余额度；费用无从确认只限制新增付费，不抹掉可用业务数据。
- 连带改动：生产请求、任务读取/保存、费用 JSON/HTML 出口、独立进程验证与负片；需求、架构、Skill 及公开成本说明同步。

## 决定与范围

现有八条生产端点及直接 Reels 探针使用固定价目，不增加端点、页数、关键词或重试。每次实际 HTTP 独立报价与预留；取得状态立即按 200/非 200 结算，再读正文；仅 fetch 没有返回状态才记结果不明。费用类错误穿透普通词错误、profile fallback 与重试分支。200 保留、非 200 同额撤销、无状态保守留存，均不是实付账单断言。

根预算保留原 JSON 数值 token，CLI 保留原文本。业务与 HTML 用十进制文本，统一 JSON 写出边界保留数值 token；不能 Number 往返。原生 JSON.parse source context / JSON.rawJSON 可作为小边界实现，本机 Node 24 已验证；名为 node@22 的本地路径实际也报告 v24.10.0，不能据路径声称已验 Node 22，须由 CI 真运行或确认真实 22 二进制。能力检测不足时可以保留只读业务与费用未知诊断，但精确写回或新增付费必须阻止，不能悄悄回退到有损 number。这里只处理任务/配置与费用字段，不建立通用 JSON 框架。

只有新配置且目标 task.json 不存在才开新账。恢复旧账先只读诊断，真正发请求前才要求有效账与供应商凭证；不能在启动时挡住零请求 collect、缓存/私密 enrich 和 render。旧费用写回保持原件语义，任务 JSON 语法错误仍是输入错误，不能凭空恢复业务数据。

纯费用模块只增加改额接口 `CostBudget.setLimit(limit: MicroUsd): void`：有效无 pending 的账可设总上限，新值不得小于占用，只改 limit，失败不变。显式 --budget 可替换不一致的根预算与有效 ledger 上限；无 --budget 时不一致阻止付费。改额必须先保存两处一致快照，保存失败不发新请求。缺账、坏价、未知版本或未结项不能靠改额修复。不提供迁移服务、增量加钱命令或任意改写历史账目接口。

默认金额只适用于新输入中预算字段缺席：collect 2、probe 0.5、直接探针沿用进程上限 1，并明示默认与作用范围；显式 null/字符串等非法值不视为缺席。已有任务不借默认值补零账。新预算全部表示总额度。

提醒仅按每个运行实例记忆 50%/80% 各一次。每次成功预留后判断，恢复时已达线也须在首个成功预留时分别提醒；退款不重置，拒绝预留与 settle 不另提醒。它没有跨进程去重承诺，不新增持久化通知字段。

## 固定对外费用与退出契约

所有费用 JSON 出口固定包含以下字段。内部 view 的金额为精确十进制 string 或 null；最终 serializer 输出精确 JSON number 或 null。`cost_estimate_usd` 保持“预算占用估算”用途，包含保守留存及 pending，不改成只有 200 小计。

| 字段 | 取值 |
|---|---|
| requests | number 或 null；有效账取终态净次数。旧费用未知但原计数仍为非负安全整数可保留，计数本身坏则 null，不因此推算费用。 |
| cost_estimate_usd / budget_usd | 精确 JSON number 或 null；已知占用 / 可解释总上限。根预算冲突且未成功显式改额时两项均为 null。 |
| cost_status | known / unknown-history / unavailable-evidence / invalid-ledger。known 可有 pending，不等于可新增付费。 |
| cost_scope | task / process / null。 |
| cost_http_200_usd / cost_unknown_result_usd / cost_pending_usd | 已知账三项精确 JSON number，其和为占用；费用不可用时均为 null。 |
| cost_basis | 固定 string：`按固定公开基础价、不计优惠的估算；不是实际账单，也不保证供应商未来价格上限。` |
| cost_price_versions | string[]；已知账实际 entries 与 pending 的版本去重，空账 []。费用不可用时 [] 表示没有可确认版本，不表示无历史费用。 |
| cost_problems | `{path:string, reason:string}[]`；无诊断 []，未知/坏账给具体原因。 |

根预算与有效 ledger 上限冲突、尚无成功显式 --budget 替换时，整体 CostView 为 `invalid-ledger`：`cost_estimate_usd`、`budget_usd`、三类金额和 `cost_scope` 均为 null，`cost_price_versions=[]`；`requests` 保留可验证的非负安全整数，否则 null，`cost_problems` 给出根 `budget_usd` 与 ledger 上限冲突的具体诊断。原 ledger 本身仍可单独校验，因此此整体输出状态不阻止以有效且无 pending 的原 ledger 为依据执行显式改额；成功后两处上限同时替换。

价目来源见 [TikHub 官方定价资产](https://tikhub.io/_next/static/chunks/16hcexj0jth19.js) 与 ADR-107 末尾的观察时刻、哈希及固定版本；版本 registry 保留已核单价，不往每份 stdout 复制整份 provenance。HTML 从同一诊断投影；CSV/XLSX 本次不加任务费用列。

| 情形 | 退出与产物 |
|---|---|
| collect/enrich 已知预算不足 | 保存成功后 3；保存失败 1，不能称已保存。 |
| 配置/金额/初始费用状态或实际请求所需 key 缺失 | 2；初始 pending 的付费/改额拒绝亦为 2。纯本地路径不因缺 key 或费用不可用失败。 |
| 运行中未知端点、意外 pending、receipt/结算或费用保存内部错误 | 1，停止后续请求；按既有约定尝试保存已完成部分。 |
| probe 已知预算不足 | 保持 0 与部分结果输出；配置/初始费用/key 问题 2，运行中费用内部错误 1。 |
| 直接分页探针的非 200 | 沿用中止且不输出成功结果 JSON 的契约；不借计价修改其请求或停止规则。 |

collect 正常和错误收尾、enrich 每账号/最终保存，以及任务状态声明保存，都携带同一 ledger/requests 快照。render 只读费用，不创建或修复账。费用不足与费用不可用文案分开；待查集合和页数/条目数算法不改。Reels→users 在总额度 0.003 时，第一次 0.002 留存后第二次零 fetch，任务不进 done，首次次数与未知 found 仍按既有断点规则保存。

## 验证与保留边界

独立测试以需求、此对外契约、ADR-107 末尾的固定价目来源、公开类型/签名和假网络协议为输入，不读待改生产函数体。用进程级假网络观察真正 fetch 的端点/次数、stdout/stderr、退出码及前后文件；纯金额单测不能替代生产接线证据。

关键反例：原始超精度 token、最大安全微美元与嵌套同名预算；旧未知账 requests=0；三个离线入口缺 key 仍零 fetch；根预算冲突整体 invalid-ledger、金额与 scope 全 null、versions=[]、保留合法 requests 并给具体诊断，显式总额度仍可单独核验原 ledger 后替换两处；恢复 pending 与运行中 receipt 错的退出区别；200 坏正文、非 200 坏正文、201/204、fetch 无状态；混合单价 fallback 卡预算；恢复已过两阈值与退款后不重复提醒；保存失败不报 3。

不在本项实现或宣称每请求前的持久预留。可捕获错误与现有保存点的连续性，不等于硬杀后的费用连续性，也不保证已付费业务响应可恢复。ADR-107 的硬中断欠条继续有效，接线合入后立即以单独的请求前持久预留与硬中断注入处理；单写者、断电与并发边界仍依 D4。不改调度、分页、发现路径或探针因果措辞。

本记录是实现前契约，不声称生产接线已通过验证；验证完成后在 ADR-107 末尾追加结果指针，历史正文不改写。用户要求不提交 evidence 文件，不创建该目录或替代归档。

## 供独立测试使用的小接口边界

`cost-json.ts` 只管理根预算的原 token 与精确写出；`budget.ts` 持有调用方同一 state，成功记账后同步 ledger/requests，但不自动写盘。初始化包装允许离线诊断，付费资格在 reserve 才检查。完整费用字段以上表为准，不另建输出协议。

```ts
type CostState = { budget_usd?: unknown; cost_ledger?: unknown; requests?: unknown }
readCostDocument<T extends object = CostState>(text: string): T
readCostLimit(state: CostState): MicroUsd
setCostLimitField(state: CostState, limit: MicroUsd): void
stringifyCostJson(value: object, view?: CostView): string

type NotifyCost = (threshold: 0.5 | 0.8, view: CostView) => void
class BudgetInputError extends Error {}
class Budget {
  constructor(state: CostState, notify?: NotifyCost)
  get count(): number | null
  reserve(endpoint: string): AttemptReceipt
  settle(receipt: AttemptReceipt, outcome: AttemptOutcome): void
  setLimit(limit: MicroUsd): void
  view(): CostView
  summary(): string
}
startBudget(state: CostState, limit: MicroUsd, scope: 'task' | 'process', notify?: NotifyCost): Budget
costView(state: CostState): CostView
```

readCostLimit 只解释载入时保存的根 numeric token 或 setCostLimitField 写入的已验证精确上限；普通无 token 的内存 number 不算已核。stringifyCostJson 无 view 时保留根预算原字段，有 view 时合并投影并把金额文本写成精确 JSON number。startBudget 只用于调用方已确认的新账，更新同一 state 的 ledger、requests 与根上限。

初始缺账、坏账、未知版本和恢复 pending 在付费/改额时抛 BudgetInputError；根预算冲突阻止 reserve，但显式 setLimit 可独立核验有效无 pending 的原 ledger 后替换两处。纯模型运行中 CostError 原样穿透，只有 budget-exceeded 表示额度不足。count 为 null 时不补零计算搜索增量。setLimit 成功后由入口保存，再允许下一请求。

D13 交点及入口判据由独立进程假网络验证；只由 selfcheck 认领的判据配对应负片。具体负片编号与验证结果在实际完成后登记，不能先宣称通过。本项触发 ADR-95 输入接线负片及 ADR-96 提醒/批量计价欠条，完成情况随验证明确记录。

费用表中的“可解释总上限”单独判断：历史费用缺失、价目不可用或 ledger 损坏时，若根预算原 token 仍可精确解释，`budget_usd` 可保留该总上限；占用与三类费用仍为 null，范围为 null、已核版本为空。根预算也不可解释时才将上限置 null。根预算与有效 ledger 冲突仍按前文例外处理，两项金额均为 null；这不赋予任何新增付费资格。

首轮验证发现独立夹具额度不足以走完两次各 2000 微美元的 IG 回退；补 4000 总额场景，计费 oracle 不变。既有 D4 持久化测试直接构造内存 budget_usd，缺少新契约要求的原始 token；将其与故障写入副本按公开读取边界载入，保留名单、状态、权限与原子写断言，不把预算输入拒绝当文件故障证据。

实现复核指出同一精度问题也影响 requests 与 cost_ledger 数字：非法小数可被舍入为已核整数，溢出数可在本地保存时变成 null。独立公开接口反例先复现，故精确边界同时保留这两个费用字段里的原 numeric token；不能解释为非负安全整数的值保持不可用，并在离线保存时写回原数值。这是 D13.i 保留费用输入和付费资格校验的实现范围，不扩展到普通业务 JSON 字段。

既有入口自检的两处逐字提示断言也随已确定的费用口径调整：直接探针非 200 中止仍必须分别报告真实发出 1 次、净次数 0 与零占用，不再要求“0 次计费”的实付表述；记忆错误的恢复命令仍与余额不足提示同进同出，但不把不足以支付下一端点说成额度完全用尽。调整由仅阅读需求和公开契约的测试上下文完成，具名断言保留，运行验证仍单独报告。

独立复核发现 D13.i 的原根预算保留还包括非法对象或数组形式：其中数字不应在新增的零请求保存路径里舍入或变为 null。独立公开接口反例先确认该损失；精确保存边界因此覆盖根预算容器内的原数字，但容器本身仍是不合法预算，不授予付费或改额资格。

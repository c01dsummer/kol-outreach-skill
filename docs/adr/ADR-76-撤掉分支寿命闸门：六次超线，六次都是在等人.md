# ADR-76 撤掉分支寿命闸门：六次超线，六次都是在等人

- 2026-09-18 · 按 Bitter Lesson 原则重整检查链，逐道评定里的第二道
- 类型：缩范围（撤一道闸门）
- 冲击的需求：无 —— `docs/requirements.json` 里没有任何判据认领它
- 结论：**撤**。删 `age.ts`、`age-rule.ts`、`age.yml` 及其十处接线。
  **不撤**「合并者不能是写档的那一方」，理由见末节

## 判据是斜率，不是松紧

对每个部件问一句：**模型再强一档，它的边际价值涨、跌，还是不动？**
涨的（验证、工具、规格）留；跌的（编排、步骤协议、路由表）标死亡条件；
不动的（沙箱、权限、预算上限 —— 约束的是世界不是模型）永远留。

分支寿命闸门量的是「这条分支分叉了多久」。它约束的既不是世界，也不是正确性 ——
它约束的是**人什么时候来合**。而下面这六条说清了那个人为什么没来。

## 六条豁免，六条都是「我在等人」

主干上真正写成顶格 trailer 的 `age-ok:` 一共六条：

```
git log 26375fb --format=%B | grep -c '^age-ok:'   → 6
```

逐条读它们的理由，分成三类，**没有一类是「我把分支放烂了」**：

| 条数 | 理由 | 等的是谁 |
|---|---|---|
| 2 | 「等的是合并者不是我 —— 本条绿且可合，而 `6-INTEGRATE.md:268` 不许作者合……」 | 第二个读的人 |
| 3 | 「等的是评审不是我 —— PR #82 已开、评审在跑」 | 评审 |
| 1 | 「串行链的第二条 —— 内容自 2026-09-09 起就在，等第一条合入主干才能开」 | 上一条 PR |

**六条全部是队列延迟，一条都不是疏忽。** 闸门量的是分叉时长，
而分叉时长在这个仓库里主要由「等人」构成 —— 那是它看不见、也管不着的东西。
有两条甚至逐字点着另一条纪律的行号：这条闸门的一部分工作，是消化另一条纪律的后果。

⚠️ **数这个数的命令要挑对。** `git log --all --format=%B | grep -c 'age-ok:'` 数出 **21**，
多出来的十几条是**正文里提到 `age-ok:` 的句子**被当成了用过一次。
真豁免是顶格 trailer（`^age-ok:`），所以要带上锚。这个坑本仓库早就撞过 ——
主干提交信息里有一句「HTML 注释里的 `size-ok:` 也会被当成真豁免。成立。」

## 每日聚合连续十四天红，没有人动

`age.yml` 每天 UTC 早上跑一次全仓聚合。定时触发的 17 次运行里：

```
GET /repos/c01dsummer/kol-outreach-skill/actions/workflows/age.yml/runs?event=schedule
```

| 日期 | 结论 |
|---|---|
| 2026-09-02 ～ 09-04 | 绿（3 次） |
| **2026-09-05 ～ 09-18** | **红（14 次，连续）** |

从 09-05 起没有再绿过一次。**一个永远红的信号没有信息量** ——
它不再区分「今天有问题」和「今天没问题」，于是没有人再看它，
而没有人看的红灯和没有红灯是同一回事。

## 它守的失败是响亮的，不是静默的

**强度放在失败静默的地方，自由放在失败响亮的地方。**

分支停在那里没合，是**响亮的**：PR 开着，列表里看得见，评审在等，作者自己知道。
这类失败在循环里会自愈 —— 人或者 agent 看见了就去推它。
harness 要守的是那种**不看就永远发现不了**的失败。

这道闸门把强度放在了响亮的那一头，所以它交出来的东西只能是噪音：
一个所有人都已经知道的事实，每天重复一遍，外加六次要人手写一行理由的摩擦。

## 它自己的账

- **901 行**（`age.ts` 500 ＋ `age-rule.ts` 401），是检查链里第二大的一套，
  仅次于 `selfcheck.ts` 的 1324 行
- **23 条变异**（`M-H2-a` 到 `M-H2-w`）守着它，随它一起删
- `scripts/test.ts` 里 **138 行**夹具，随它一起删
- 抓到过的真问题：**0**。它自己出过两次 bug，各留了一条记录（ADR-61 校准漏了一条路、
  ADR-63 叠分支继承豁免）

  ⚠️ 「零真红」这一条**我没有复核** —— 它要读 1087 次 CI 运行的日志，
  出处是 2026-09-18 那次逐道归因。上面别的数都是这次自己跑命令核的。

## 不撤的那一条，以及为什么

「**合并者不能是写档的那一方**」（`6-INTEGRATE.md`）**留着，一个字不动。**

六条豁免里有两条逐字点着它，按「一条规则的主要工作是消化另一条规则的后果，
至少删一条」，它是候选之一。**但它不能删**，因为它不在斜率判据的管辖范围内：

> **验证者独立于生成者是结构性质，不是编排。模型越强，越会把自己的误解
> 原样复制进它写的测试里 —— 独立的第二个上下文是唯一读得出这种误解的东西。**

这不是推测，是这个仓库自己的账：63 条记录里，闸门合计抓到 **8** 个真问题，
而「另一个没写过这段代码的上下文读一遍」抓到约 **30** 个。
删掉第二个读的人，等于删掉这个仓库里最有效的那个验证机制。

所以这一对矛盾从**另一头**解开：撤掉那个会因为等人而变红的闸门，
等人就不再有代价。规则只删了一条，而删的是没有价值的那条。

## 什么条件下重开这个讨论

- **分支寿命重新变成会咬人的东西时** —— 具体是：出现一条超过 48 小时、
  且理由**不是**「在等评审／等合并者／等上一条 PR」的分支。那说明队列延迟
  不再是主要成因，这个量重新量得出东西了
- **合并不再需要等人时** —— 如果哪天评审与合并都由独立上下文的 agent 承担、
  延迟降到分钟级，那「分叉时长」就重新等于「作者拖了多久」，可以重装
- **主干停滞本身成为问题时** —— `6-INTEGRATE.md` 里那三条理由（延迟发现的冲突、
  评审线程作废、主干停滞是告警）仍然成立，它们现在靠人执行。
  如果因为没有闸门而真的出现了一次「两周后合并才暴露的语义冲突」，
  那是重装的证据，把那次冲突记下来

**谁去数**：下一条因为等人而超过 48 小时的分支出现时，开它的人自己判属于哪一类。
没有机器在数了 —— 这是有意的，也是这条记录要说的事。

## 顺带清掉的十处接线

`package.json`（脚本行 ＋ check 链）、`.github/workflows/check.yml`
（`prbase` 那一步、`AGE_PR_HEAD`／`AGE_PR_BASE`、为它加的 `pull-requests: read` 权限）、
`.github/workflows/age.yml`、`AGENTS.md` 的检查链描述、`docs/ARCHITECTURE.md` 两行锚点、
`process/README.md` 的索引行、`process/6-INTEGRATE.md`（48 小时那条规矩、`age-ok` 语法、
三种跑法那张表、required status checks 的告诫、出生时间取锚、叠分支继承豁免那一段、
三层表里那一行，共 68 行）、`scripts/check/selfcheck.ts` 与 `scripts/check/trailer.ts` 的注释。

`trailer.ts` 当初抽出来是因为有两道闸门要读提交信息里的指令，现在只剩体量一道。
**没有把它并回 `size-rule.ts`** —— 那属于顺手重构。

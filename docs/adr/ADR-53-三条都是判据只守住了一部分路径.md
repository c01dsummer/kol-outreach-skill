# ADR-53 三条都是「判据只守住了一部分路径」

- 日期 · 2026-08-28
- 类型：**事实证伪**（外部评审第十六轮）
- 冲击的需求：D4
- 结论：**采纳全部三条**

### 事实

三条各自独立，但根子是同一个：**一条判据只在它被写下来的那条路径上生效。**

**一、`--resume` 那条路上没有产品名校验。**
上一轮给 `collect` 加了「产品名为空就别开跑」，加在了 `--config` 分支里。
而续跑读的是盘上的旧 `task.json` —— 它可能被手改过（S3 明确允许），
也可能来自还没有这条校验的旧版本。于是续跑能带着一个空产品名一路采集、
补 profile、**把钱花完**，最后停在写回被拒。校验的整个意义是「在花钱之前说」，
而它只对两条入口里的一条说了。

顺带查出一个更硬的：产品名**不是字符串**时（手改成数字、null、对象），
写回那一步 `product.trim()` 直接抛 TypeError，而 `render` 没有接它 ——
交付物在钱已经花完之后整个丢掉，报错还是一句没人看得懂的类型错误。
本该走的是「报为未写回，照常完成交付」。

**二、刷目录关不上描述符时，会把一次已经成功的写回报成失败。**
`fsyncDirBestEffort` 吞掉了 open 和 fsync 的错，却把 `closeSync` 留在
`finally` 里裸奔。它跑在 `renameSync` **之后** —— 替换已经生效了。
一个关描述符的错逃出去，`writeFileAtomic` 就报失败，调用方照着这个失败
告诉用户「未写回，原文件一个字节没动」。**那是假话**：推荐记录已经落进去了。

这个 PR 的整条主线是「宁可响地失败，不要静默地成功」。这一处是它的镜像：
**响地报了一个假的失败**。而假的失败比假的成功更难查 —— 用户会照着它去修
一个没坏的东西。

**三、`output-format.md` 把 `unknown` 和 `unreadable_ignored` 合成一句话。**
`report.ts` 与 `memory.md` 都写着「`unknown` 只说不知道，**不要替它编一个原因**」
（ADR-22 · ADR-43），而 Agent 照着输出格式那份说的时候，会告诉用户
「记忆文件读不出来，你让我跳过了」—— 一个编造的诊断。
同一句话的第三份副本，而它是唯一一份错的。

### 修法

**一和三的修法是同一个：让判据只存在一份。**

「一个必填的文字字段能不能用」这条判据，在仓库里原有三份手写副本
（结构校验里两份、写回前一份），而最该有的第四处一份都没有。
抽成 `types.ts` 里的一个函数，四处都调它。非字符串于是顺带被四处一起挡住了。

`output-format.md` 的 `unknown` 那句不再自己发明措辞，改成写明
「措辞的规矩以 `memory.md` 为准」—— 三份副本降成两份，而剩下那两份
一份是代码、一份是它的说明。

**二**：把 `closeSync` 也包进 try。刷目录整件事要么全是尽力而为，
要么全不是；一半吞一半抛，就是这次这个结果。

### 连带改动

- `M-D4-u`：变异掉「去掉首尾空白之后还剩东西」这半条判据。它现在一处失守
  就是四处一起失守 —— 这正是合并副本换来的：**一条变异守住了四个调用点**。
- 测试补上「全是空白」与「不是字符串」两种入参。
- `dir` 从 `let` 变成 `const`：目录名就是产品名，只能在产品名过关之后才算得出来。
  这个顺序原先靠分支里的语句排列维持，现在是靠它算不出来。

### 自查时顺手撞见的第四处（同一类）

写这一轮的修法时，我自己往 `collect` 里又加了一句 `` `${resume}/task.json` `` ——
而 ADR-52 刚把这个名字收成 `task.ts` 里的一份常量，注释上写着「**只此一份**」。
去数了一下：`collect` 两处、`enrich` 一处，加上我新添的一处，
那句「只此一份」在仓库范围内从来就没成立过 —— 它只在 `task.ts` **这个文件里**成立。

导出 `taskFile(dir)`，四处都改成调它，注释改成「全仓库只此一份」。

**这件事本身就是这条教训的样本**：我刚写完「判据要只存在一份」，
下一段代码就手拼了一次路径。合并副本之所以有效，正是因为它不依赖我记得。

### 教训

**加一道校验的时候，要问的不是「这里对不对」，是「还有几条路绕得过去」。**

前十五轮里第 2 类（校验只做到一层）说的是纵向：能解析不等于形状对。
这一轮是横向：**同一层上有两条入口，校验只站在其中一条上。**
两种都是「守住了一部分就以为守住了」。

而横向那种更难自查 —— 纵向的漏洞在同一个函数里看得见，
横向的漏洞在**另一个分支**里，你读代码时根本不会读到它。
所以判据必须是个函数：函数有调用点，调用点数得清；
写在分支里的 `if`，数不清。

**另外：吞异常要么全吞要么全不吞。** 一个「尽力而为」的操作里留一条会抛的路，
它迟早会在最不该抛的时刻抛出来 —— 这一次是在替换已经生效之后。

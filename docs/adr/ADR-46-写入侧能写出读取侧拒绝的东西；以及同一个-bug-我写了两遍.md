# ADR-46 写入侧能写出读取侧拒绝的东西；以及同一个 bug 我写了两遍

- 日期 · 2026-08-28 · PR #5 拆分后第十一轮自动评审，两条都成立
- 类型：**事实证伪**
- 冲击的需求：D4
- 结论：**采纳**，并把原子写入合并成**唯一一份**

### 一、一次写回就能毒掉整份记忆

任务配置里 `product` 是空白时：

```
写回报告: {"written":true}
盘上存的 product = ""
下次读:   记忆文件 ... 不可用：结构不对 —— tiktok:alice 的第 1 条推荐记录的 product 不是非空字符串
```

**这是我自己造的循环。** ADR-37 加了读取侧的「product 必须非空」，写入侧没跟着加 ——
于是一次正常的写回就把一份好好的记忆变成读不出来的，此后每一次采集
都被挡在门外，直到有人手工去修。

判据是**读取侧实际会拒绝什么**，不是「这个值看起来合不合理」。
写入侧现在拒收并报 `written:false`，另外 `collect` 在**花钱之前**就检查配置 ——
空产品名走不到最后，早说比晚说好。

### 二、同一个权限位的 bug，我在两个文件里各写了一遍

上一轮（ADR-45）我给任务目录写了个新的 `writeAtomic`。两轮前（ADR-40 · ADR-42）
刚在 `memory.ts` 里修好的权限位处理，**新写的这份一个字都没带过来** ——
`saveTask` 又是 600 进、644 出。

根因不是我粗心，是**这段例程有两份副本**。所以这次不是「把第二份也修好」，
是抽成 `lib/atomic.ts` 里**唯一一份**，两边共用。

合并的直接好处当场就看见了：原先守这两份的四条变异，合并后有两条
指向了同一行 —— 说明它们本来就在重复地守同一件事，只是分散在两处看不出来。

**留在调用方的**：孤儿临时文件清不清。记忆文件要清（长期存在、孤儿是一份
完整的联系历史副本），一次性的任务目录不用。这一条按各自处境不同，
不该合进公共函数。

### 教训

**「我刚修过这个」是最不该信的一句话。**

我修过 `memory.ts` 的权限位，两轮之后写一个新函数时，那次修复没有以任何形式
出现在我脑子里 —— 因为它属于**另一个文件**。

真正的问题从来不是「记不记得」，是**同一段逻辑有几份副本**。
一份副本的时候不需要记得，两份的时候记性就成了唯一的保障，而它不可靠。

### 追记二 · `--resume` 那条路上没有产品名校验 —— 判据只守住了一部分路径

- 拆分后第十六轮评审 · 类型：**事实证伪** · 冲击 D4

第一节给 `collect` 加的「产品名为空就别开跑」，加在了 `--config` 分支里。
而续跑读的是盘上的旧 `task.json` —— 它可能被手改过（S3 明确允许），
也可能来自还没有这条校验的旧版本。于是续跑能带着一个空产品名一路采集、
补 profile、**把钱花完**，最后停在写回被拒。校验的整个意义是「在花钱之前说」，
而它只对两条入口里的一条说了。

顺带查出一个更硬的：产品名**不是字符串**时（手改成数字、null、对象），
写回那一步 `product.trim()` 直接抛 TypeError，而 `render` 没有接它 ——
交付物在钱已经花完之后整个丢掉，报错还是一句没人看得懂的类型错误。
本该走的是「报为未写回，照常完成交付」。

修法：「一个必填的文字字段能不能用」这条判据，在仓库里原有三份手写副本
（结构校验里两份、写回前一份），而最该有的第四处一份都没有。
抽成 `types.ts` 里的 `textProblem`，四处都调它。非字符串于是顺带被四处一起挡住了。

- `M-D4-u`：变异掉「去掉首尾空白之后还剩东西」这半条判据。它现在一处失守
  就是四处一起失守 —— 这正是合并副本换来的：**一条变异守住了四个调用点**。
- 测试补上「全是空白」与「不是字符串」两种入参。
- `dir` 从 `let` 变成 `const`：目录名就是产品名，只能在产品名过关之后才算得出来。
  这个顺序原先靠分支里的语句排列维持，现在是靠它算不出来。

**加一道校验的时候，要问的不是「这里对不对」，是「还有几条路绕得过去」。**
纵向的漏洞（能解析不等于形状对）在同一个函数里看得见，横向的漏洞
（同一层上有两条入口，校验只站在其中一条上）在**另一个分支**里，
你读代码时根本不会读到它。所以判据必须是个函数：函数有调用点，调用点数得清；
写在分支里的 `if`，数不清。

### 追记三 · 整体替换顺手弄坏了一件原来是对的事：目标是软链时，改名换掉的是链接本身

- 2026-08-31 外部评审 · 类型：**事实证伪** · 冲击 D4（打在上面第二节合出来的那份 `atomic.ts` 上）

`memory/creators.json` 是一条指向别处的软链时（用户把它放在同步目录、
或者多个工作副本共用一份），`statSync` 跟着链接看到了终点的权限位，
而 `renameSync(tmp, file)` 换掉的是**链接**。第一次写回之后：

| | 换成整体替换之前 | 之后 |
|---|---|---|
| 链接还在吗 | ✅ 还是链接 | ❌ 变成普通文件 |
| 真正那份 | ✅ 写进去了 | ❌ 停在旧内容 |
| 交付物怎么说 | 已记入 | **也说已记入** |

真正那份记忆从此不再更新，而每一次都报成功。**静默地停止记录**，
正是这条需求存在的理由要防的那一种 —— 由它自己引入。
改成整体替换之前，这里是一次普通的 `writeFileSync`，它跟着链接写到终点。
**所以这不是补一个新能力，是把顺手弄坏的行为还回去。**

修法：写之前顺着软链找到终点（`followLinks`），临时文件建在终点那一层，
改名也改在那一层。不用 `realpathSync` —— 它要求终点存在，
而**终点不存在时该写的正是那个终点**，不是把链接换掉。
解不出来时（不是 EINVAL / ENOENT）**抛，不猜** —— 和 `isAbsence` 同一条规矩。
配一条变异 `M-D4-x`。同一轮的另一件（新文件的权限位）追记在 ADR-42。

**「换一个更强的实现」和「保持原有行为」是两件事，而后者没人会替你检查。**
从 `writeFileSync` 换到「临时文件 + 改名」，收益是原子性，代价是这个操作的
**每一个副作用都变了**。需求、测试、变异守的都是「新实现该做到什么」，
**没有一条守着「旧实现已经做到、不该丢的那些」**。
判据，写给下一次换实现的人：**先列出旧实现的语义清单，逐条问新的还成不成立。**
对文件写入至少是这四条：写在哪个 inode、权限从哪来、目标是链接时怎么办、
中途失败留下什么。

### 追记四 · 修好「写在哪」，没修「扫在哪」

- 2026-08-31 外部评审（追记三的直接后果，同一轮） · 类型：**事实证伪** · 冲击 D4

追记三让 `writeFileAtomic` 顺着软链写到终点。临时文件也就跟着落到了
**终点旁边**（`/别处/real.json.<pid>.tmp`）。而 `sweepStaleTemps` 还照着配置里
那个路径扫：`dirname(FILE)`、`basename(FILE)` —— 链接那一侧。两边对不上。
硬杀留下的孤儿 —— **一份完整的联系历史** —— 落在终点旁边，而清理程序在链接
那一侧找一个永远不会出现的名字。实跑复现：写回成功，孤儿原封不动。
D4 写着「目录列得出来时清掉」。目录列得出来，只是列错了目录。

修法：把「一次整体替换真正落在哪个文件上」变成一份**导出的**判据 `writeTarget`，
三处都调它：写（`writeFileAtomic`）、扫（`sweepStaleTemps`）、
建目录（`saveMemory` 里那次 `mkdirDurable`）。第三处是数出来的，不是评审提的：
`FILE` 在 `memory.ts` 里出现六次，逐个问「这一处要的是配置里那个路径，
还是真正写到的那个文件」—— 读盘和报错要前者，另外三处要后者。

**加一层间接之后，所有「同一个东西在哪」的问题都得重问一遍。**
追记三的清单四条我都对着 `writeFileAtomic` 问过了，漏掉的是：
**那四条不只 `writeFileAtomic` 一个人在回答。** 判据，比追记三那条更靠前一步：
**新加一个解析/间接层时，先 grep 那个被解析的东西在模块里的每一次出现，
逐个判它要的是解析前还是解析后。** 这是本条第二节那件事的第 N 次复发，
只是这次的副本不是「同一段代码写了两遍」，而是「同一个问题有两处在各自回答」——
**前者 grep 得到，后者只有数调用点才看得见**。

# ADR-60 修好「写在哪」，没修「扫在哪」

- 日期 · 2026-08-31 · 外部评审（ADR-57 的直接后果，同一轮）
- 类型：**事实证伪**
- 冲击的需求：D4
- 结论：**采纳**

### 事实

ADR-57 让 `writeFileAtomic` 顺着软链写到终点。临时文件也就跟着落到了
**终点旁边**（`/别处/real.json.<pid>.tmp`）。

而 `sweepStaleTemps` 还照着配置里那个路径扫：

```ts
const dir = dirname(FILE)                 // 链接那一侧
const prefix = `${basename(FILE)}.`       // 链接的文件名
```

两边对不上。硬杀留下的孤儿 —— **一份完整的联系历史** —— 落在终点旁边，
而清理程序在链接那一侧找一个永远不会出现的名字。实跑复现：写回成功，
孤儿原封不动。它会一直躺在那里，没有任何人知道。

D4 写着「下一次写回在目录列得出来时清掉已死进程留下的临时文件」。
目录列得出来，只是列错了目录。

### 修法

把「一次整体替换真正落在哪个文件上」变成一份**导出的**判据 `writeTarget`，
三处都调它：写（`writeFileAtomic`）、扫（`sweepStaleTemps`）、
建目录（`saveMemory` 里那次 `mkdirDurable`）。

第三处是数出来的，不是评审提的：`FILE` 在 `memory.ts` 里出现六次，
逐个问「这一处要的是配置里那个路径，还是真正写到的那个文件」——
读盘和报错要前者（用户配的是哪条路径，就该看到哪条），另外三处要后者。

### 教训

**加一层间接之后，所有「同一个东西在哪」的问题都得重问一遍。**

ADR-57 的教训是「换实现时要列出旧语义清单逐条问」，我照做了，
清单上四条（写在哪个 inode、权限从哪来、目标是链接时怎么办、
中途失败留下什么）都对着 `writeFileAtomic` 问过了。

漏掉的是：**那四条不只 `writeFileAtomic` 一个人在回答。**
「写在哪个文件上」原先是一句所有人都默认知道的常识（就是 `FILE`），
`writeTarget` 一出现，它就变成了一个需要问的问题 —— 而只有我改的那个
函数被问到了。

判据，比 ADR-57 那条更靠前一步：**新加一个解析/间接层时，先 grep 那个
被解析的东西（这里是 `FILE`）在模块里的每一次出现，逐个判它要的是解析前
还是解析后。** 这件事有确定的做法、数得清的次数，不该靠想起来。

这也是 ADR-52 那条的第 N 次复发，只是这次的副本不是「同一段代码写了两遍」，
而是「同一个问题有两处在各自回答」——**前者 grep 得到，后者只有数调用点
才看得见**。

# ADR-75 验证者那几百个进程共用一份 V8 编译缓存

- 2026-09-18 · 正文写于 2026-09-09（`claude/perf-3-compile-cache`），接着 ADR-72 往下量，
  同一次「check 太慢」的请求
- 类型：扩范围（新跑法）—— 不改任何一条判定
- 冲击的需求：无
- 结论：**采用**。指一个绝对路径给 Node 自己的编译缓存，让几百次验证者跑共用一份

## 为什么这条记录是 75 而不是 73

`age-ok:` 逐字写着「**等前两条合入主干才能开**」。前两条是 #108、#109，都在 2026-09-13 合了；
**第三条从来没开过 PR**。

```

git log -1 --format=%ad --date=short origin/claude/perf-3-compile-cache  → 2026-09-11

```

分支尖端停在 2026-09-11，落后主干 119 个提交。这期间主干把 73 和 74 都发出去了
（73 是「一条讲『写数要核正本』的提交，自己带了个没核过的数」）。

**编号不可回收**，所以这一条改用 75 重新开。原分支上那份 ADR-73 不再作数 ——
它从来没进过主干，主干上的 73 是另一条决定。

## 为什么它不是「用过期结果」

这是采用一份缓存时唯一要回答的问题，先答它。

缓存里装的是 **V8 把一段源文本编译出来的字节码**，条目由 Node 按
「源文本 ＋ Node 版本 ＋ V8 参数」自校验，对不上当场重编。里面**没有任何
「上一次的结论」** —— 不是「这条变异上次被抓到了」，是「这段字节码是这段源码编出来的」。

于是那个最要紧的问题（「一条变异改过的文件，会不会命中未改之前的缓存」）答案是不会：
源文本变了，键就变了。**这个坏法有负片，不需要另立断言** —— 缓存要是替旧源码作了证，
那批变异会集体「存活」，而存活是硬失败。

隔离机制：路径指的是主仓库的 `.check-cache/compile-cache`（`.gitignore` 第 5 行）。
跑在隔离目录里的那几个 worker 各有各的 cwd，**所以必须是绝对路径** ——
不指绝对路径就成了几份互不相通的缓存，白建。已经有人在外面指了一份的，用人家那份。

## 验收证据

**树钉不成一个 hash，钉的是「基线 ＋ 本条的改动」。** 本条自己的 hash 写不进本条正文
（写进去它就又变了）—— 这正是 ADR-73 那个自指问题的同一个形状，所以这里不假装钉得住：
基线是 `26375fb`，改动是本条对 `scripts/check/mutate.ts` 的三处（一个常量、两处 spawn 的 env）。

```
# 冷缓存：先把缓存整个删掉再跑
rm -rf .check-cache/compile-cache && npm run -s mutate    → 364 个变异全部被抓到，退出码 0
# 热缓存：紧接着原样再跑一次
npm run -s mutate                                          → 364 个变异全部被抓到，退出码 0
```

两跑的「存活／红错了地方／跑不起来／锚点失效／没有结论」**都是 0**：

```
grep -cE '存活 ——|红错了地方|跑不起来 ——|锚点失效|没有结论 ——' <各自的输出>  → 0 和 0
```

⚠️ **这一跑不是 ADR-72 欠着的那次「逐条比对」。** 它证明的是「开着缓存、走派工那条路，
364 条一条不漏地被抓到」，**没有**把派工跑和串行跑的结论逐条摆在一起比。
ADR-72 正文里那句「逐条比对那一条尤其要重来」仍然欠着，且它至今不是一张带重启条件的欠条。

## 收益与代价

⚠️ **本机这三个数都是在有其他负载的机器上量的**（同一会话里另有两个后台任务在读仓库，
4 核），**只能当「没变慢」的旁证，不能当基准**：

| 树 | mutate 墙钟 |
|---|---|
| `26375fb`（没有本条） | 235.9s |
| 基线＋本条，冷缓存 | 210.6s |
| 基线＋本条，热缓存 | 209.4s |

作者在一台干净的 4 核 Linux 上量过（出处是 `6a45ea0` 的提交信息，那棵树上 302 条变异）：
mutate 227.823s → 205.538s，每条变异的 CPU（user＋sys）2.539s → 2.262s，**−10.9%**。
**墙钟与 CPU 要分开看**：派工那一条（ADR-72）没省 CPU，它换的是墙钟；本条是真的少干了活。

**一处作者那份没写、这次量出来的事**：冷跑和热跑几乎一样快（210.6s vs 209.4s，差 0.6%）。
收益**几乎全部发生在同一跑之内** —— 一跑里有 364 次验证者 spawn，头几次之后缓存就热了，
跨跑再省的那一点淹在噪声里。所以「冷缓存慢、热缓存快」这个直觉在这里不成立，
删掉 `.check-cache/compile-cache` 的代价约等于零。

代价是磁盘，而且**它只增不减**：一次完整跑之后 14 MiB，跑第二次涨到 18 MiB。
Node 不替我们收，删掉就重新长出来。

```
du -sh .check-cache/compile-cache   # 一跑之后 → 14M；两跑之后 → 18M
```

## 没验过的边界

- `NODE_COMPILE_CACHE` 是 Node 22.1 起才认的环境变量。更老的 Node 会**当它不存在**，
  于是这一条静默地什么也不做 —— 不是坏，是没有收益。本仓库钉的是 v22
- 只在 Linux 上量过
- 没有量过「缓存目录只读／盘满」时会怎样。Node 的文档说写不进去就退化成不缓存，没实测

> ⚠️ 欠条：**本条加的东西没有任何检查守着。** 把那两处 `NODE_COMPILE_CACHE` 从 spawn 的
> env 里删掉，364 条变异、全部单测、整条 `npm run check` 一条都不会红 —— 因为退化的后果
> 是「慢」，而这条链里**没有一步与时间有关**。同一个洞更大的那一半：`jobsWanted` 哪天被改成

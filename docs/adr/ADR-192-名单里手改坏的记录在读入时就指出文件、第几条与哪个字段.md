# ADR-192 名单里手改坏的记录在读入时就指出文件、第几条与哪个字段

- 日期 · 2026-11-10
- 类型：既有缺陷。`creators.json` 或 `creators.raw.json` 被手改坏一条（条目不是对象、handle 写成数字、bio_links 删掉、recent_posts 写成字符串等），render、collect、enrich 不在读入时说哪里坏，而是到后面的同人识别、打分里崩掉，报的是 `Cannot read properties of undefined (reading 'toLowerCase')`、`c.bio_links is not iterable` 这类话，不说是哪个文件、哪一条；recent_posts 写坏时 render 以 1 结束，看上去像程序坏了。新增判据 D21.t，按改需求逐条评定，见第二节
- 触发它的事实：ADR-191 那条 PR 开工前的试探。需求所有者 2026-11-10 15:29Z 在项目线程的决策卡上选了「另开 PR」（卡上写的是「让缺字段或类型不对的记录报出文件、第几条和原因」）
- 冲击的需求：D21（新增 D21.t）
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 理由：这几种坏法都出在用户自己手改名单之后，报错得让用户知道改哪儿。读入是四个入口（render、collect、enrich、人工反馈模板）共用的一步，在这里查一次就都管到；它在任何写入、预留与请求之前，拒绝时什么都没动
- 连带改动：`scripts/lib/task.ts`（`readOptionalReviewCreators` 读完数组后逐条查形状；`loadReviewCreatorInputs` 两个文件都读完再一起报）· `docs/requirements.json` 新增 D21.t、D21 的 adr 加 ADR-192，`docs/SPEC.md` 照它生成 · `scripts/test.ts` 组 `d21-task-reviews` 加一个用例块；组 `feedback-template-crossings` 的夹具补上 `bio_links: []`（见第三节）· `scripts/check/mutations.json` 新增 M-D21-ar–bf · `scripts/check/launches.json` 里 `d21-task-reviews` 那一行的 running 由 13 改成 28 · `skill/SKILL.md` 三个命令以 2 拒绝的原因清单补上这一种

## 一、决定

`creators.json` 或 `creators.raw.json` 读成数组之后，逐条查下面四种形状，有一处不对就以 `ReviewInputError` 拒绝，入口照它们对评审输入错误的原有处理以 2 结束（D21.t）：

- 条目不是对象（字符串、数字、null、数组）；
- platform 或 handle 不是字符串（含缺席）；
- bio_links 缺席，或不是字符串数组；
- recent_posts 出现且不为 null，却不是对象数组。

每一处一行：文件路径、第几条、平台与账号（两样都读得到时）、哪个字段、读到的值（按 JSON 写法，超过 80 个字符截短；缺席就写缺席）、应是什么。两个文件都读完、每一条都查完再一起报，用户改一次就能把所有坏处改对。

只查这四种，是因为对 render 逐字段试探时只有它们会崩：作品、粉丝数、作品数、昵称、来源这几样写成别的类型或删掉，render 照样以 0 结束；平台写成 `youtube` 也不崩。所以这是一张手写的清单，守的不是「名单里任何类型不对都拒绝」这一整类 —— 决策卡上那句「缺字段或类型不对」比本条宽，合入即认可收窄到会崩的这四种。其余字段的类型、平台名认不认得，仍在 ADR-180 第 28 行那张欠条里等需求所有者定（见第四节）。

## 二、按改需求逐条评定

- 红线：P1–P5 都不涉及。拒绝在读入那一步，排在任何写入、开账与请求之前；不改任何字段的值
- 缩范围还是降标准：收窄的是能跑通的任务 —— 试探过的 render 上，原先以 1 结束或以 2 带一句看不懂的话结束的，现在以 2 带一句看得懂的话结束（collect、enrich 没有逐个试探，它们读入走同一步，拒绝的位置在开账与请求之前）；已知原先以 0 结束、现在被拒的只有一种：人工反馈模板读到缺 bio_links 的名单（它不做同人识别，不会崩）。这一种现在也拒绝，四个入口一个口径
- 覆盖还是可信：可信上升 —— 报错说的是用户能照着改的事
- 可逆：可逆。拒绝时盘上文件原样不动，改了那几条重跑即可

## 三、怎么验

- 先红：`13155c4` 只加了判据与测试，读入照旧。改之前那一版断言名由模板拼出（变异的 `kills` 是静态扫出来的，拼出来的名字扫不到），之后改成逐字写死，并把每种坏法的「拒绝、指出、不动盘」三件合成一条断言。
- 试探（本条清单的来历）：对主干 `053f2ac` 的 render 喂一份两条的 `creators.json`，第 2 条逐个字段删掉或换成数字、字符串、对象、`[null]`、`[5]`。崩的就是第一节那四种；recent_posts 为字符串或 `[null]` 时崩在打分里、以 1 结束，其余崩在同人识别、以 2 结束。改后同样的输入都以 2 结束，stderr 是第一节那样的一行。
- 不多拒：形状对的记录原样读入；recent_posts 缺席、为 null、为空数组都放行；粉丝数写成字符串、昵称写成数字、平台写成 `youtube` 也放行（本条之外）。
- 旧夹具：组 `feedback-template-crossings` 的名单没有 bio_links，本条让它的人工反馈模板入口以 2 拒绝、整组崩掉；补上 `bio_links: []`，它守的是模板与正本，不靠缺这个字段。
- 变异（新加的都由 `d21-task-reviews` 抓）：M-D21-ar 放行非对象条目；as、at 不查 handle、platform；au 只查 bio_links 是不是数组；av 放行 bio_links 缺席；aw 只查 recent_posts 是不是数组；ax 把 recent_posts 为 null 也拒（多拒）；ay 多查昵称（多拒）；az 不说第几条；ba 不写原值；bb 不带平台与账号；bc 不截短；bd 碰到第一条就停；be 一个文件坏了就停；bf 不查累加器。
- 启动数：本机没有 bwrap，完整变异一步的自检基线起不来，`launches.json` 不能整跑写回。照 ADR-191 第三节的办法，对本条提交的 `scripts/check/mutations.json` 调 `executionRoutes`，数 `executes` 只有 `d21-task-reviews` 的条数：28（主干 `053f2ac` 上 13），其余配置条数两边相同。

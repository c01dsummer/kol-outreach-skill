## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 增强结果里每一格该是什么类型、哪几格必有、能写哪几个值 | `scripts/lib/types.ts` 的 `EnrichmentState`，由生成器读成 JSON Schema | 机器 |

## 一、做法：格式说明从类型生成，读入时整份对照

不再逐项手写「这一格该是什么」。增强结果本来就有一份完整的类型定义（`EnrichmentState` 及它用到的那些），enrich 写文件、render 读文件都照它；把它交给 ts-json-schema-generator（把 TypeScript 类型转成 JSON Schema 的常用工具）生成一份格式说明，读入时交给 Ajv（JSON Schema 的常用校验器）整份对照。规则只有一处来源，就是类型；手写的判断一条都不留。

生成时定的几样：

- **类型里没写的键一律不认**（生成器的 `additionalProperties: false`）。拼错一个可选格（例如把 `followers` 写成 `follower`）不会被悄悄当成没写；报错说「多了格式说明里没有的一格」。
- **三态包装按 status 分支**（类型上标 `@discriminator status`）。status 是 measured 就按「已测」那一支查，是 unavailable 就按「不可用」那一支查，报错只说那一支缺了什么，不把另一支的要求也列出来。
- **格式说明存成 `.ts` 模块**（`scripts/lib/enrichment-schema.ts`），不存 `.json`：读它的代码不必按自己所在的位置找文件，检查链预编到别处的那份 JS 也照样认得（预编不复制 `.json`）。
- 作品样本的类型单起名字（`ProfileSample`、`NormalizedPublicPosts`）：泛型参数直接写成数组时，生成器给的定义名里带源码位置，类型文件挪一行就变，核对就会无故变红。

改了类型没回写，需求测试「入库的格式说明与按当前类型现生成的一份逐字相同」那条变红；回写命令 `npm run enrichment-schema -- --write`，`docs/SYNC.md` 触发表加了一行。

## 二、读入时怎么拒、报什么

enrich 与 render 读增强结果都走同一个读入函数。不是合法 JSON，或有一处不合格式说明，以 2 拒收（与名单手改坏同一种拒法），逐处一句：

- 哪个文件、哪个账号（JSON 路径里的 `~1` 还原成 `/`）、哪一格（点连起来的路径，例如 `metrics.view_rate.value`）；
- 类型不对：应是什么（数字、文字……）、读到什么（按 JSON 写法）；
- 取值不对：能写哪几个、读到什么；
- 缺了：同一格缺的几项合成一句（「缺了 value、source、observed_at、sample_size、basis」），免得一个漏写的三态包装刷出五六句；
- 多了：哪个键。
- 粉丝数、关注数类型不对时多一句：这个数可能是 enrich 从名单抄来的，名单里同一个账号的这一格也要一起改。

enrich 原先在改额（`--budget` 会写 task.json）之后才读增强结果，现在挪进读入阶段，与名单、任务的检查一起，在改额、写任何文件、发任何请求之前。render 照旧在写任何文件之前。

原先 D21.v 那一段（只查没有作品样本、又不是 Instagram 的账号的活跃状态与风险等级）删掉：它查的两样都是格式说明里的取值列表，整份对照覆盖它；D21.v 原文不改，仍然成立。

## 三、老文件：逐个发布版本实测

格式说明管的是今后，也管用户机器上已有的任务目录。按类型逐版比对：自首版 enrich（`5ab044e2`，2026-08-26）以来，增强结果用到的类型只有一次新加必有的格（`a033f02c` 给公开指标加了最后发布时间、距今天数、活跃状态三格），与首版相隔 26 分钟，中间没有发布 tag；其余改动只加了可选的格、只给取值列表加了值。

比对只能说明类型，说明不了 enrich 实际写出什么，所以又真跑了一遍：在 2.0.0、3.0.0、4.0.0、5.0.0 四个发布 tag 与本条的树上，各跑那一版自己的 enrich（假供应商，罐头主页作品：作品足、只有三条、零条、没有日期、没有粉丝数、账号不存在、Instagram 视频与图文混着、全是图文、全是视频、空、私密、关联账号，加十个凑够同行组的 TikTok 账号），每版跑三遍（首跑、缓存重算、强制刷新）。十五份结果按新格式说明全部通过；四个老版本的任务目录直接交给本条的 render 也都以 0 结束、报告里没有 NaN，2.0.0 到 4.0.0 的交给本条的 enrich 缓存重算同样以 0 结束。跑法与罐头在项目共享文件夹 `enrichment-schema/release-check/`。

这些结果按「键的结构加上 status、reason、media_scope、source.kind 的取值」去重，留下 17 个账号（作品样本只留前两条，形状不变），存进 `scripts/enrichment-released-samples-data.ts`。需求测试拿当前格式说明逐个校验：以后谁改类型把一个老版本照常会写的形状判成不合规，那条测试变红（D21.y）。

文档里给 Agent 的手写报价示例（`public-metrics.md`）也拿来校验，文档列的报价取值（平台、形式、来源、外层来源种类、外层状态）与格式说明逐个比 —— ADR-231 第二轮复核挑出的「来源只认两个词、其中一个文档里从没出现」那一类，取值以类型为准、文档照抄、测试核两边一致。

## 四、enrich 不再抄不是数的关注数（D21.x）

名单读入时只查粉丝数、作品数（D21.u），关注数不查（ADR-227）。enrich 原先把名单里的这两样原样抄进增强结果：关注数是文字时，增强结果里留下文字，算出的关注／粉丝比不是数。现在抄之前不是有限数字的一律当没给；缓存命中回填时用的也是这份当过没给的值。

关注数是从供应商主页资料来的：TikTok、Instagram 主页资料那两处原先不验类型，现在不是有限数字就当没给（作品样本接口那两处原来就这样）。供应商线上会不会真给非数字没有核（不发付费请求）；不给的话只有名单被手改才碰得上。

用户机器上要是已经有 enrich 抄进去的文字关注数，读入时会被拒，报错那句「名单里同一个账号的这一格也要一起改」就是为这种情况写的：只删增强结果里那一格、不改名单的话，下次 enrich 不会再抄（本条已修），但名单里那个坏值还在。

## 五、测试与变异

新组 `d21w-enrichment-schema`（作者写）：格式说明与类型同步；发布版本样本全过；文档示例与取值；各种不合规各报什么；真起 render（粉丝数写成文字、带样本：以前印 NaN%，现在以 2 拒、一个交付文件都没写）；真起 enrich（拼错的键：以 2 拒，task.json 与增强结果原字节不变、一个请求都没发）；名单关注数写成文字时 enrich 写出的账号没有关注数；主页资料的关注数。

改了的旧断言：

- 「D21.v 没有样本的 Instagram 账号存着的指标报告本就不用所以不因本条拒绝」（ADR-227 那次隔离会话写的）：整份对照不管报告用不用那一格，存着的活跃状态不是那三个之一就拒，改成断言拒收（D21.w）。这是需求变了，不是那条测试写错。
- 「D21.v 已测活跃状态／风险等级缺了值时报一条」（作者写）：改成看同一格缺的几项合成一句。
- 「P1.n 入口：合作报价缺币种时 stderr 点名增强结果、账号与币种」（作者写）：缺币种现在在读入时就拦下，点名的是文件、账号与 `collaboration_quote.value 缺了 currency`；拼报告那一道的白话格名（「合作报价币种」）改由直接调拼报告函数的一条守，M-P1-bf 跟着改认那条。
- 那组入口测试的报价夹具外层来源原先没写 `kind`，按类型是必有的，补上。

新变异 M-D21-bp 至 M-D21-by（同一格缺的几项分开报、取值不对不列能写的、类型不对不印读到的值、多出的键不报、账号路径不还原、enrich 不拒、enrich 抄文字关注数、两处主页资料不验关注数、生成时放过类型里没写的键）；M-D21-bl、M-D21-bm、M-D21-bo、M-D8-s 跟着代码挪了锚点，施的刀含义不变；M-D21-bn 跟着改名。逐条施上、只跑相关的组，点名的断言都红。

## 六、没做的、碰到的欠条

- 格式说明只管类型能说清的：类型说「数字」，它就不管负数、小数、日期写得对不对。粉丝数写成 -5、`observed_at` 写成乱码，读入照样放行。要管得在类型上加注解（生成器认 `@minimum`、`@format` 这类），每加一条都要先拿发布版本样本验老文件读不读得进。

> ⚠️ 欠条「格式说明不管取值范围」（档：登记）：增强结果的格式说明只按类型查，数字的正负与整不整、日期字符串的写法不查；手写成 -5 或乱码的日期照样读入 · 重启条件：有人碰上一次这类值进了报告，或者下一条改增强结果类型的改动

- 账号键与账号里写的平台、账号名对不对得上，格式说明管不了（JSON Schema 不比两处的值）；render 照键找账号，对不上就是找不到，表现为未查询。没改。

> ⚠️ 欠条「增强结果的账号键与内容对不上时当未查询」（档：登记）：`accounts` 里键写的是 `tiktok:a`、内容里 handle 写的是 `b` 时读入不拒，render 照键找人，这个人显示成未查询 · 重启条件：有人碰上一次，或下一条改增强结果读入的改动

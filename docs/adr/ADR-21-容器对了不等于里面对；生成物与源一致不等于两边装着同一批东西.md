# ADR-21 容器对了不等于里面对；生成物与源一致不等于两边装着同一批东西

- 日期 · 2026-08-28 · PR #5 第四轮自动评审，两条都成立
- 类型：**事实证伪**（两条都是「校验只做到了一层」）
- 冲击的需求：**D4** · 登记表与 `SPEC.md` 的一致性机制
- 结论：**采纳**，两条都改

### 一、推荐记录只校验了容器，没校验元素

ADR-19 加了结构校验，但 `recommendations` 只查到 `Array.isArray` 为止。
而 `filterByMemory` 会**逐条**读元素的 `task` / `product` / `date`：

| 文件内容 | 修之前 | 修之后 |
|---|---|---|
| `"recommendations": [{}]` | `status: ok`，「已推荐过」这件事悄悄消失，名单上留下一个 `undefined @ undefined` | 拦下：第 1 条推荐记录的 product 不是字符串 |
| `"recommendations": [null]` | **抛 `TypeError`** —— 绕开整条「退出码 2 + 一句人照做得了的报错」的流程 | 拦下 |

第二行尤其要紧：ADR-19 建的那条可操作报错路径，被一个 `null` 直接跳过，
用户拿到的是一句读不懂的 `Cannot read properties of null`。

修法：逐条校验元素 —— 必须是对象，`product` 与 `date` 必须是字符串，
`task` 若存在必须是字符串。仍然不做全量 schema（运营在推荐记录里自己加的
批注不该被判成损坏，有用例守着）。

### 二、分类表里没有的 `cat`，那条需求从渲染里凭空消失

`renderTables` 按分类表逐个分类挑需求。一条 `cat` 拼错、或用了没声明的前缀，
**整条被跳过**——而：

- 内容指纹**包含**它（它确实在登记表里）
- SPEC 一致性检查**全绿**

因为那条检查比的是**生成结果和生成结果**：漏掉的那条与它自己完全一致。
于是「`SPEC.md` 是 `requirements.json` 的渲染」这句承诺失效，
而两道检查都说没问题。

修法：`validateRegistry` 收下分类前缀，`cat` 不在表里当场报错。

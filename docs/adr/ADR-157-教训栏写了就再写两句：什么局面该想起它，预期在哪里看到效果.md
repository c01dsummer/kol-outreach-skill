## 一、为什么改

ADR-153 那 28 条说的是同一件事：一条早先记下的教训，后来又被犯了一次，不少是写它的人自己犯的，有的就在同一个文件、同一条记录里。它们缺的不是「知道」：犯的人读过、甚至写过那条教训。缺的是到了那个局面能想起它。模板的「教训」一栏只要求写「是哪一类」，没要求写「什么局面该想起它」。

另一半是没有回头对账的地方：一条教训写下以后起没起作用，没人看。要看得先知道该看哪里，所以第二句写「预期在哪里看到效果」：下次同类出现时，哪一步、哪种改动或检查会因为它而不同。

同一节第 197 行那半句（`4b36935` 上）说写清了「这是哪一类错」的记录「能防住以后所有同类」，与 ADR-153 那 28 条对不上。ADR-153 第 19 行写了要两句一起改：那半句改小，候选句接在后面，不然同一节里两句话打架。

## 二、借的两处

都只借做法，没装、没跑，也没搬代码。

- harness2 的经验库：每做完一个任务存一条教训，必须有三项 —— 适用的情境形状（不是这次的事实）、要做什么、引用哪几行判词作证据，缺一项就不收。本仓库的记录本来就有「触发它的事实」等几栏，相当于证据；缺的是情境，就是第一句。
- RRSI：每处改动写预计会影响哪些任务，事后把命中和落空摆回来。第二句只借前一半，写下预期；事后对账本条不做，也没有机器去做（第四节）。

## 三、改了什么

`process/2-CHANGE.md`「决策记录格式」两处，标点照 `process/` 那边（半角逗号、冒号、括号）：

```
- 教训(可选):如果这条记录揭示的是一类问题而不是一个实例,把那一类写下来。写了就再写两句:
  什么局面该想起它(局面的形状,不是这一次的事实);预期在哪里看到效果(下次同类出现时,哪一步、哪种改动或检查会因为它而不同)
```

```
**最后一栏是这套东西里回报最高的部分。**
一条只记了"这次怎么处理"的记录,只能防住这一次;
一条写清了"这是哪一类错"的记录,才有可能防住以后的同类。
但写清了的教训,单靠写下来防不住下一次同类:下一次多半出在别的文件、新写的代码里,犯它的人往往读过、甚至写过它。
所以记的同时把已有的同形之处找全,改掉或逐处登记;能变成结构(只留一份实现)或替代「跑」的检查的,当场变过去;只剩散文的,按还没落实算。
```

与 ADR-153 的候选句比，只改了一处：第一句开头的「写清了「这是哪一类错」的教训」改成「但写清了的教训」，因为上一行刚说过「这是哪一类错」，前面加「但」接住改小的那半句。第二句一字没改。

每一句都过了「换个项目也成立吗」（`process/README.md`「为什么要分两层」，本仓库的字眼见 `docs/SYNC.md`「一条判别规则」）：没有记录编号、文件、命令、字段名、需求编号、业务词，没有「以前」「今天」这类钉在本仓库时间线上的词。「替代「跑」」是 `process/README.md` 第二层自己的说法（第 168–187 行），「只留一份实现」是 `process/3-BUILD.md` 第 105 行那句「能靠结构保证的,就别靠对比保证」的意思。

- **不混代码**：这条 PR 没有代码改动（`process/2-CHANGE.md` 同步表「改本目录里的任何一份」）。

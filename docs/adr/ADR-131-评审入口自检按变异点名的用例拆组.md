# ADR-131 评审入口自检按变异点名的用例拆组

- 日期：2026-10-02 · 核对 main 上 `npm run check` 时长增长时发现
- 类型：成本超预期
- 触发它的事实：检查代码相同、只有机器快慢不同的两次 main CI 里，`selfcheck --only=review-cli-entry`
  这一种组合的正常基线为 17.5 秒／21.4 秒，13 条变异逐条经过时间合计 261.0 秒／371.3 秒，
  每条约 20.1 秒／28.6 秒（[run 36990274512](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/36990274512)
  `1a4038a`、[run 36990329444](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/36990329444) `8df080a`，
  取自两跑的 `MUTATION_COST_JSON`）。同两跑需求测试一侧的变异平均每条约 1–1.4 秒。
  这一组串着 39 次 CLI 启动：先 2 次阳性对照，接着 24 次拒绝矩阵，本机约占整组一半多；
  13 条变异里只有 2 条点名矩阵那条断言，另外 11 条点名的断言都在矩阵之后，却每次都要先把矩阵跑完。
- 冲击的需求：无。断言判定、标签原文、失败文案、变异施变正文与 `by/kills` 一个字不改；
  U9.j 仍只在整组全部跑完时认领。
- 结论：采纳，把 `review-cli-entry` 拆成六组，旧组名保留为完整入口。
  同形状的 `feedback-template` 与 `task-list-collect-invalid` 只测量，结论是**不拆**（见下文）。
- 理由：变异按 `kills` 自动选组（ADR-99），组切得越贴近「这条变异实际需要哪些用例」，
  它付的启动次数就越少。拆组不改任何判定，只改每条变异被迫多跑的部分；
  代价是正常基线从一种组合变成七种，下文的实测已经把这部分算在里面。
- 连带改动：`scripts/check/selfcheck.ts`；本记录及生成的索引；ADR-130 末尾追加一块欠条
  （它的两条欠条被本次触发，见末节）。`process/` 与 `docs/ARCHITECTURE.md` 只写通用的分组与基线规则，
  不列具体组名和配置数，本次不用改。

## 切法与依赖边

| 组 | 依赖 | 内容 | CLI 启动 | 点名其中断言的变异 |
|---|---|---|---:|---|
| `review-cli-entry-positive` | — | collect／enrich 阳性请求、「观察器同接线阳性」 | 2 | 无（只作依赖） |
| `review-cli-entry-reject` | positive | 三入口 × 8 种坏输入矩阵、新任务输入拒绝、坏断点 | 26 | M-U9-q、M-U9-x |
| `review-cli-entry-collect` | — | 旧兼容判断及其重复运行、缺 raw 旧目录、正本空 reviews | 4 | M-U9-o、M-U9-p |
| `review-cli-entry-enrich` | — | enrich 按正本 fit 与合法关联决定付费范围 | 1 | M-U9-o、M-U9-y、M-U9-z |
| `review-cli-entry-collect-exit` | positive | 新发现关联冲突（退出 2）、正本保存失败（退出 1）、预算不足（退出 3） | 3 | M-U9-r、M-U9-w |
| `review-cli-entry-render` | — | 独立读回器机械控制、三格式交付、空层、待重评高风险 | 3 | M-U9-o、s、t、u、v、y、aa |
| `review-cli-entry`（旧名） | 以上六组 | 六组都跑完才认领 U9.j | 0 | — |

**零事件类断言仍以阳性对照为前提。** 用到「阳性已证明观察器接线」的断言在 reject 和
collect-exit 两组里。这两组声明依赖 positive，选跑时由 `wanted` 的闭包先跑它；
它们读的是 positive 组跑完后写进模块变量的真实结果，只认 `true`。
positive 组没跑或没跑完时这个值是 `undefined`，那些断言照原判定变红，不会把缺席当成已证明。

**文件系统上的依赖边。** ADR-99 第二节记过跨组有 `tsc` 看不见的边。这里每组各自调用
同一个造夹具函数：它重建本组根目录和观察器预加载文件。每个用例的目录按用例名分开，
没有一组读另一组写下的文件。七种实际配置都单独跑过正常代码，全部通过。

**认领。** 新组名各自完成时打标记；旧组名只在六个标记都在时调用 `criterion('U9.j')`。
render 组的读回器机械控制失败会提前返回，这时它不打标记，U9.j 不认领。这与拆分前
「提前返回就走不到末尾的认领」一致。

## 本机成对计时

固定旧版 `8df080a` 与拆组版 `8a2a4fb`，各建一份独立克隆，依赖从同一份锁文件安装，
Node `v22.22.0`、Linux x64、4 个 CPU、4 个 worker。两边各加一个相同的本地提交，
`mutations.json` 只保留 M-U9-o…aa 这 13 条（对象原文不变），以各自的版本为维护比较基线，
运行 `MUTATE_BASE_SHA=<该版本> tsx scripts/check/mutate.ts`。正常基线计入耗时：旧版每次一种，新版每次七种。
按旧→新→旧→新→旧→新各跑三次，六次都自然成功，没有追加择快样本。

**用 uid 65534 跑，不用 root。** root 无视文件权限，`feedback-template` 组的保存屏障阳性对照会按夹具失败报红。
本机先以 root 跑时实际撞到了这一点。这与本改动无关，但 root 下的完整自检不能作数。

| | 旧版（1 种配置） | 拆组版（7 种配置） |
|---|---:|---:|
| 墙钟 | 117.95、115.71、115.45 秒；中位 **115.71**，范围 115.45–117.95 | 45.71、43.11、44.06 秒；中位 **44.06**，范围 43.11–45.71 |
| 已回收子进程 user+sys | 336.19、333.58、333.57 秒；中位 **333.58** | 120.35、114.40、115.80 秒；中位 **115.80** |
| 正常基线逐个相加 | 21.5、20.6、20.6 秒 | 47.2、43.1、42.5 秒 |
| 13 条变异逐条相加 | 324.2、319.9、319.2 秒 | 67.7、62.0、65.2 秒 |

后两行取自 mutator 自己的成本报告。新版里两条仍点名矩阵的变异（M-U9-q、M-U9-x）合计
32.6–35.4 秒，其余 11 条合计 29.4–33.6 秒。CPU 用 Python `RUSAGE_CHILDREN` 取增量，
不保证覆盖所有后代进程。

每次 13 条都由预定的全部具名断言抓到，没有存活、崩溃，也没有进程或夹具记号。
新版七种配置的正常基线都在施变前通过，各只跑一次。
这是本机 13 条短集合的结果，不是整条 CI 的节省量；CI 的对照见下一节。

临时资源：6 次短集合加 1 次正常子集运行之后，`/tmp` 下观察到 75 个属于 uid 65534 的 `kol-selfcheck` 临时根，
没有逐条归因。提前停止的变异会留下随机目录，这是 ADR-99 第十九节已记的既有情况，本改动没有改那条路径。
这些目录都是实验自己产生的，测完已删。

## 本机完整检查

拆组提交 `8a2a4fb` 在本机以 uid 65534 跑完整 `npm run check`（`MUTATE_BASE_SHA` 为 `8df080a` 的完整 SHA）。
体量、规格、决策记录、类型检查、需求测试全部通过。变异一步的维护比较 `8df080a..8a2a4fb` 报 0 条路由／正文变化、
13 条执行配置变化；108 种配置的正常基线各通过一次，984 条全部被抓到。
完整自检里本改动的六组和旧组名入口全部通过，只有 `mutation-cost-entry` 一组的进程树资格判红；
检查链在这一步停下，审计没有跑到。

这一组判红是本机容器的问题，与本改动无关：同样的失败在拆组前的 `8df080a` 上单独跑这一组，原样复现。
留下的进程是 tsx 的 `esbuild` 子进程。它成了孤儿后被这个容器的 1 号进程（`process_api`）收养，
而后者不及时回收，于是以僵尸状态留在进程表里（运行中实际观察到 `Z` 状态、父进程为 1）。
夹具用 `kill(pid, 0)` 判断存活，僵尸也算存活，`SIGKILL` 又清不掉僵尸。
GitHub 的 runner 有正常的 init，同一提交 `8df080a` 在 main 上的 CI 是绿的。
在一个只做「登记为子进程收割者、及时回收孤儿」的包装进程下，旧树单独跑这一组即通过；
用同一包装重跑完整检查的结果，在本 PR 的后续提交里补上。

## CI 对照

本 PR 的 CI 跑完后在此补上：用 PR 那一跑与 base（main `8df080a`）那一跑的 `MUTATION_COST_JSON`，
先用两边都没变的配置估出机器快慢（取耗时比的中位数），扣掉之后再报拆出来的七种配置合计的增减。
不拿两个墙钟直接相减。

## 另外两组：只测量，不拆

两组都用同一个方法量：本机 uid 65534 跑一次正常子集并记录每行输出的时刻，
找出每条变异点名的断言**最早**在什么时候全部出过一遍，那就是它最早能停的地方。
CI 数据取自上面两跑的成本行。

### `feedback-template`：不拆

CI 上 17 条，正常基线 10.0／13.6 秒，变异合计 102.4／144.1 秒，平均每条 6.0／8.5 秒，约为基线的 0.6。
本机整组约 9.1 秒、33 次启动；17 条最早能停的位置平均在整组的 63%，与 CI 的比例对得上。

- 开头约 0.6 秒是「观察器合法阳性」和「未处理异常合法阳性」，后面所有用例都以它们为前提，拆出的每一组都得带上。
- M-D26-m、n、o、p、q 这 5 条点名的断言在组尾（≥ 97%）。其中 p、q 点名的「所有源文件原字节」「零外部请求」
  汇总的是全组每个用例的观察结果：拆开以后它们仍要跑全组，而且汇总状态会变成跨组的模块变量，
  正是 ADR-99 第二节说的那种 `tsc` 看不见的边。
- 其余 12 条若各自只跑阳性加本用例，按本机时间线估算（阳性约 0.6 秒，每个用例约 0.3 秒），逐条墙钟合计最多约省 40 秒。
  这还没扣新增配置的正常基线；4 个 worker 分摊之后，墙钟在十秒以内的量级。

收益太小，换来的是跨组汇总状态的风险，不值得单开一个 PR。

### `task-list-collect-invalid`：不拆

CI 上 6 条，执行本组与依赖组 `task-list-good`，正常基线 32.9／45.0 秒，变异合计 116.8／168.3 秒，
平均每条 19.5／28.0 秒。本机整跑 28.2 秒：collect 坏输入按 new（0.9 秒起）、resume（6.7 秒起）、
resume-budget（12.7 秒起）三种方式各跑一遍，18.8 秒之后是依赖组（约 9.4 秒）。
被点名的标签在每种方式里每个坏输入各出现一次，所以一条变异最早能在它点名的最后一种方式的第一个用例处停：
M-D16-ad 在 11.75 秒，其余 5 条在 12.72 秒。

- 依赖组登记在后、执行也在后，提前停的变异本来就跑不到它，也跑不到 collect 段最后约 6 秒。
  这部分只有正常基线在付。
- 按方式拆：x、z、ag 点名全部三种方式，ad 在第三种方式之前就停了，这 4 条都省不了；
  只有 ab（只点 resume-budget）约省 11.8 秒、ac（resume 与 resume-budget）约省 5.8 秒，合计约 18 秒逐条墙钟。
  新增的两种配置各要带上依赖组跑正常基线，约 2 ×（6 + 9.4）≈ 30 秒，比省下的还多。

## 两条欠条的重启条件被本次触发

ADR-130 有两条欠条，把「下一次修改 `review-cli-entry` 自检组」写成了重启条件：

1. 「CLI render 阳性合法关联字段按账号契约规范化」的稳定验收编号与入口认领还没补；
2. D21.b（续跑保全已有 Agent 评审）与 D21.c（重复交付以正本重建投影）既没有需求测试或入口认领，
   也没有各自名下的负片。

本次拆的正是这个组，两条的条件都触发了，但这次都没还。需求所有者给本改动定的范围是
「不改任何断言的判定、标签和失败文案，入口认领不变」；还这两条要新增认领，可能还要加断言或负片，
属于扩范围（`process/3-BUILD.md`「禁止顺手重构」）。拆组也没有改变它们缺的东西：
相关的行为观察原样留在 collect 组和 render 组里，判定一字未动。

> ⚠️ 欠条：ADR-130 中「CLI render 阳性合法关联字段」的验收归属与入口认领、D21.b／D21.c 的认领与负片，
> 在本次拆组时触发重启条件而未还，缺口内容不变 · 重启条件：本 PR 已合入

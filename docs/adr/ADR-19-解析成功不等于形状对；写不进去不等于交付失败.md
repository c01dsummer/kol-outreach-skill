# ADR-19 解析成功不等于形状对；写不进去不等于交付失败

- 日期 · 2026-08-28 · PR #5 第二轮自动评审，两条都成立
- 类型：**事实证伪**（一条是旧实现一直有的洞，一条是我这次改动**新引入**的回归）
- 冲击的需求：**P4**（红线）· D4
- 结论：**采纳**，两条都改

### 一、合法 JSON、错误结构 —— 同一条红线的另一扇门

`JSON.parse` 成功，不等于拿到的是一份记忆。而这个文件是产品**明确要求运营手改**的
（S3 → `business-requirements.md` 写着「直接改 JSON」），手改最容易改出的恰恰是
**能解析但形状错**的东西。实测：

| 文件内容 | 修之前 | 修之后 |
|---|---|---|
| `{"version":1,"creators":[]}` | `status: ok`，**所有人进名单** | 拦下：creators 不是键值对象（是数组） |
| 条目缺 `contacted` | `status: ok`，**该人进名单** | 拦下：tiktok:alice 的 contacted 不是 true 或 false |
| `contacted: "true"`（字符串） | `status: ok`，**该人进名单** | 同上 |
| `recommendations: null` | `status: ok` | 拦下 |

第一行最典型：花括号改成方括号。字符串取键在数组上一个都取不到，于是
**打扰过、已拉黑的人全部重新进名单，而报告会说去重成功了** —— 与 ADR-15
修的是同一个红线失效，只是走的另一扇门。ADR-15 只堵住了「解析不了」那一扇。

修法：解析后过一道结构校验，不合格归入 `unreadable`。

- **只校验过滤真正会读的字段**：`contacted`、`blocked`（决定 P4）、
  `recommendations`（决定跨任务去重）。不做全量 schema —— 运营自己加的备注字段
  不该被判成损坏（有用例守着）
- **报错指名哪个人的哪个字段**。修它的是人，「结构不对」四个字帮不上忙

### 二、写不进去时，整个交付被一起丢掉 —— 我自己引入的回归

ADR-15 把写回从 render 末尾挪到了报告之前，**为的是让报告能声明写回的结果**。
代价没想到：`saveMemory` 在目录不可写、磁盘满、路径被占时会抛，而它现在跑在
`meta.json` 与 `report.html` 之前 —— 于是 CSV/XLSX 已经落盘，报告却没了。

挪之前，写回在最末尾，抛出来只损失记录，交付物完好。**我把一个局部失败改成了
全局失败，而且是在一次以「交付要说实话」为目的的改动里。**

修法：写回失败与读不出来走同一条路 —— 返回 `written: false` 加原因，交付照常
完成，报告上照常声明。判据是 `2-CHANGE.md` 的第 2 条：交付不出来是**降标准**
（用户什么都拿不到），少记一轮推荐是**缩范围**（东西少了但剩下的是对的）。
顺带：`saveMemory` 失败时清掉临时文件，不在盘上留半成品。

### 教训

**「同一个失效，还有没有别的门」是一个该单独问出口的问题。**

ADR-15 找到的是「文件读不出来 → P4 静默失效」。我修好了那扇门，写了测试、
写了变异、写了 ADR，然后**没有回头问一句：这个红线还能怎么失效？**
`JSON.parse` 成功这条路一直敞着，而它比我修的那扇门更好走 ——
坏成解析不了需要运气，坏成形状不对只需要按错一个键。

第二条的形状不一样，值得单记：**为了让交付说实话而做的改动，让交付变得做不出来。**
挪动一次调用的位置是最不像改动的改动，所以那一步没有被当作改动来审
—— 它改的不是行为，是**失败的作用域**。

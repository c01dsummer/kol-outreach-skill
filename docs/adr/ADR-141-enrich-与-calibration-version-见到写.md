# ADR-141 enrich 与 calibration version 见到写重复的进度键时在写回前以 2 拒绝，不再整份写回成只剩最后一处

- 日期 · 2026-10-11 · 还 ADR-140 第四节第一张既有缺陷的欠条（enrich 与 `calibration version` 写回写重复的进度时只留最后一处），需求所有者 2026-10-11 定为下一条 PR 修（「下一条 PR」）
- 类型：既有缺陷。D19.g 要这两个写回方整份写回后每个进度数字与盘上原文逐字相同，而写重复的进度键读入后只剩最后一处，前几处无从照原文写回；本条改 D19 正文、D19.g 与 D19 × P1 裁决的措辞，新增 D19.m、D19.n，按改需求逐条评定，见第二节
- 触发它的事实：对着 `16a13d9`（判据已从 `resumeProgressProblems` 抽出，两个写回方还没调它）跑新测试。task.json 里写 `"found":{"0":1e400,"0":3.000}`、或根上 `"pages":7.25e1,"pages":"zz-mid","pages":{"0":1}` 时，enrich 普通与 `--budget 2` 四跑都以 0 结束，各预留 1 次、请求 1 次，task.json 整份写回成只剩最后一处；`calibration version` 要写盘时以 0 报 `written`，同样整份写回。brand_calibration 同时不合 D20.a 时两者都以 2 拒绝，stderr 却只写品牌那一类，不提重复

- 结论：采纳。enrich 在任何改额、预留、请求与写入之前，`calibration version` 在要写盘时，按 D19.k 判写重复的进度键，有就以 2 拒绝、按先后列出每一处原文；两者都不判进度的值

## 一、决定

1. **两个写回方只判重复，不判进度的值。** ADR-138 第二节否决过让 enrich 与 `calibration version` 按 D19.a–b 拒绝坏进度：它们不读也不写续跑进度，坏断点留给 collect 续跑与 render 按原文拒绝，写回方只负责照原文留下。
   写重复的进度键不一样 —— 它们没法照原文留下：读入后只剩最后一处，整份写回就是替用户挑了那一处。所以只把 D19.k 这一半接过去，`duplicateProgressProblems` 从 `resumeProgressProblems` 里抽出来，两个写回方只调它。
2. **enrich 在最前面拒绝。** 它的第一次写盘可能是改额、可能是费用检查点、可能是跑完后的 `persist`，都在预留与请求之后或之间。拒绝放在读入任务、与任务列表和品牌输入的校验同一处：任何改额、预留、请求与写入之前以 2 退出，三类问题同时存在时一起报。
3. **`calibration version` 只在要写盘时拒绝。** 缺席（D20.m）与已一致（D20.r）都不写盘，盘上的几处原文原样留着，没有东西会丢，照旧以 0 结束；要写盘（D20.q）时有重复就以 2 拒绝、不写盘。
   brand_calibration 同时不合 D20.a 时本来就以 2 拒绝（D20.n），两类问题一起写出，免得用户改完一类再撞上另一类。
4. **诊断与 collect、render 同一份。** 同一句「`found["0"]` 在文件里写了 2 次，依次是 …」，前面带 task.json 路径；四个入口说的是同一件事，用户在哪个命令上撞见都按同一个办法改。

## 二、逐条评定

1. **触碰红线吗？** 撞的就是 P1：写回方把前几处原文悄悄抹掉，留下的那个数看起来像测量值，之后 collect 续跑照常花钱。拒绝不违反任何红线。
2. **缩范围还是降标准？** 都不是。没有重复键的文件，两个命令的行为一字未改：enrich 照旧不判进度的值，坏进度照 D19.g 原样写回（D19.g 的写回段就是这里的阳性对照）。
3. **D20 多一种拒绝。** `calibration version` 以 2 拒绝的输入原先只有参数、读不到任务与校准不合 D20.a（D20.k–n）；现在多一种：要写盘而进度键写重复。D20.m、D20.r 不受影响（不写盘就不拒绝），D20.q 的「保留续跑进度」从此对写重复的输入也成立 —— 不写，就不丢。
4. **可逆吗？** 可逆：两处调用删掉即回到原样。

## 三、测试与变异

1. **测试先于实现、由另一个上下文写成**：只读需求原文、函数签名、夹具与 `mutate --brief`，不读实现。自检 `resume-progress` 组新增九条断言（enrich 四条、`calibration version` 五条），`scripts/test.ts` 的 `d20-content-version` 组末尾新增五条（库层，不另认领判据）。每个拒绝用例都配同一模式下只留最后一处的阳性对照：enrich 要以 0 结束、预留与请求都大于 0、写回 task.json；`calibration version` 要报 `written` 或 `unchanged`；对照不过就带夹具记号、跳过该例。
2. **对着接口看红**：自检六条红、test.ts 三条红，都是新断言，原有断言一条没变色。观测值见文首「触发它的事实」。自检绿着的三条是「enrich 不因此判进度的值」（没有重复的 `1e400` 照常预留、请求、照原文写回）与 `calibration version` 缺席、已一致两条，test.ts 绿着的两条是夹具有效性与缺席、已一致那条 —— 它们断的是现状本来就对的那一半。接上实现（`e33c1c7`）后全绿。
3. **变异 M-D19-as 至 M-D19-ba，九条**（四条 `by: selfcheck`、五条 `by: test`）：去掉 enrich 的判定、拒绝时不写重复那一类、拒绝前先写回；`calibration version` 去掉判定、D20.a 不合时丢掉重复那一类、缺席与已一致也拒、拒绝前先写回、诊断换成一句不点名的话。每条在副本里单独施变后只跑点名的组：点名的断言都红，没有夹具或进程记号。
4. **没写成变异的一条**：「enrich 判了进度的值」（照 collect 那样按 D19.a–b 拒绝坏进度）会同时弄红 D19.g 写回那一段的阳性对照，那一条带夹具记号，`mutate` 按规矩把这条变异记成「崩了」而不是「被抓到」。守它的是第 1 条里「enrich 不因此判进度的值」那条断言与 D19.g 的写回段；`calibration version` 那一侧有 M-D19-ax、ay 守着过拒。

## 四、边界

- 只管 D19.k 那几处：根上五个进度键与四张表里的任务索引键。根上其他键写重复（`tasks`、`requests`、`cost_ledger`、`budget_usd` 等）仍是 ADR-140 第四节第二张欠条，需求所有者 2026-10-11 另有一张卡在定。
- enrich 跑到一半时有人手改 task.json 写出重复，费用检查点重读盘上的文件后只留最后一处：同一目录的并发写入按 D4 当前不保证（ADR-66），不在本条。

# ADR-36 同一个键出现两次 —— 解析已经把证据吃掉了

- 日期 · 2026-08-28 · PR #5 拆分后第一轮自动评审，成立
- 类型：**事实证伪**（P1，静默破红线）
- 冲击的需求：P4（不重复打扰）· D4（记忆不可用的分档）
- 结论：**采纳**，重复键判为读不出来

### 事实

手改的文件里把同一个人贴了两遍：

```json
"tiktok:alice": { "contacted": true,  "blocked": true,  ... },
"tiktok:alice": { "contacted": false, "blocked": false, ... }
```

`JSON.parse` 静默保留**最后一条**。跑出来 `status=ok kept=1 filtered_contacted=0` ——
一个已联系、已拉黑的人重新进名单，而状态报「读到了」。

### 为什么前四道关一道都没拦住

`normalizeKeys` 里有一条撞车检测（ADR-22 加的），专门管「两个键指同一个人」。
它拦得住 `tiktok:Alice` 与 `tiktok:alice`，**拦不住两个一模一样的键** ——
因为等它拿到 `Object.entries` 的时候，重复**已经不存在了**。

我在同一个函数里写下「两个键规范化后撞在一起 —— 该用哪一条无从判断」，
却没想到还有一种撞车是**解析器替我选了一条**，而且不告诉我。

### 修法

在**文本上**查，不在解析结果上查。`duplicateKey` 扫一遍原文，
按对象层记键，同层出现两次就报。只在已经解析成功的文本上跑，不必处理非法 JSON。

借 `JSON.parse` 还原单个键的转义 —— 手写反转义会把 `\u0062` 和 `b` 看成两个键。

### 教训

**检查要放在证据还在的地方。**

前四扇门都是「值不对」，查解析结果就够。这一扇是「证据在解析时被消灭了」——
再严的下游检查也查不到一件已经不存在的事。判断一个检查放得对不对，
要问的是「我要找的那个东西，走到这一步时还在不在」。

# ADR-101 IG 没有分页游标那句话从来没试过请求侧：先造验它的工具

- 日期 · 2026-09-21 · 接着 ADR-100 那句「**这条改动不改善 IG 的召回量**」往下做。
  用户最初报的问题是「TikTok 结果多、每次占满配额，Instagram 召回很小或为零」——
  ADR-100 修的是「为零」那一半，这一条冲的是「**很小**」那一半的第一块挡路石
- 类型：**既有缺陷**（一条承重事实的证据不成立），**不新增需求判据**
- 触发它的事实：ADR-94 那张欠条的重启条件（「下一次有网络与 key 的人碰
  `skill/references/providers/tikhub.md` 的 Instagram 一节」）这次踩到了
- 冲击的需求：**一条都没有。**「IG 只有一页」从来没写进 `docs/requirements.json` ——
  它只活在参考文档和代码注释里，而下游的上限论证全压在它上面
- 结论：**① 新增 `scripts/probe-ig-paging.ts`，拿真 key 去问请求侧；
  ② 它的判词里没有「不支持」这一句，只有「认了／这一次没多给／作废」（⚠️ **这一条 2026-09-22 退役了** —— 那套判词是为「试猜来的参数名」服务的，而参数名不再靠猜；现在的形状见第十一节，那条「不确定不许伪装成确定」的纪律原样搬了过去）；
  ③ 每一处副本改成说我们**实际做了什么**（只取一页），不再替 TikHub 断言它有没有游标（逐处见第四节那张表，别在这里数个数 —— 手数的数会烂）；
  ④ 结论本身这次不动 —— 没跑过就没有结论**

## 一、这句话的证据是什么

`skill/references/providers/tikhub.md` 写着（2026-08-25 那轮真实调用留下的）：

> 1. **没有分页游标。** 响应只有 `count` 和 `items`，一个关键词只能拿一页（约 12 条）。

`scripts/providers/tikhub.ts` 的块注释、`docs/data-source-strategy.md` 第 2 条、
`docs/business-requirements.md` 的双平台对比表、`skill/SKILL.md` 三处，说的是同一句话。

**证据只有前半句：「响应只有 `count` 和 `items`」。** 那是**响应**那一侧的观测。
结论「没有分页游标」是**请求**那一侧的断言 —— 两件事不是一回事，而我们的请求从头到尾
只发过 `keyword` 一个参数：

```
git grep -n "search_reels" scripts/providers/tikhub.ts
```

`has_more: false` 也不是观测来的，是代码里写死的字面量；`search()` 见到 `offset > 0`
直接返回空，压根不发请求。**所以「第 2 页是空的」这个现象，是我们自己造的。**

TikHub 的 OpenAPI 又不描述响应体（`docs/data-source-strategy.md` 第 3 条：196 个 schema
没有一个描述响应内容），ADR-94 那次还拉不到 `openapi.json`（代理 403）。
**文档那条路也走不通，只剩真打一次。**

## 二、这次**不**改结论，只造验它的工具

按 `process/1-REQUIREMENTS.md`：调研的产物是**结论**，「做不到，原因是 X」和
「能做到，证据是 Y」都算，「应该可以」不算。**「大概能翻页」同样不算** ——
这次一个真实请求都没发（IG 端点不吃免费额度，恒 402），所以这条记录里
没有关于 TikHub 行为的任何新结论，只有一条关于**证据**的结论：

> 那句话的证据不支持那句话。

工具是 `scripts/probe-ig-paging.ts`，跑法：

```
npm run probe:ig-paging -- --keyword smoothie
```

每跑一次：基线 2 次 ＋ `VARIANTS` 里每个参数各 1 次。**这里不写总数、也不写总价** ——
两者都是 `VARIANTS` 与 `lib/budget.ts` 单价的函数，而 `VARIANTS` 的注释逐字写着
「只加不改」，也就是它**注定会长**：写死的数必烂（`REVIEW.md`、ADR-73／ADR-82）。
跑完之后脚本在输出里打出 `requests`（真发出去几次）与 `cost_estimate_usd`。
⚠️ **后者是估算，不是账单**：它等于请求数乘以 `lib/budget.ts` 里**我们自己写死的**
`UNIT_PRICE`，对面到底怎么扣费这个脚本看不见，也从来没验过（402 只说明余额不足，
并不证明这一次扣了钱）。字段名就叫 estimate，散文别把它说成实际支出。
**要一把充过值的 key** —— 没充值时 IG 端点恒 402，脚本会直说是余额问题，不含糊。

## 三、这个工具最危险的一支，就是它最可能跑出来的那一支

传 `count=50`，还是 12 条。**这能读成「不支持 count」吗？不能。**
未知的查询参数常被服务端静默忽略 —— 那一次观测里，「这个参数不存在」与
「这个参数存在、但这一次没多给」**不可区分**。

把它读成「不支持分页」，方向是最坏的那一侧：**下一个人看了就不再试。**
这句承重话上一次正是这么活下来的 —— 一句合理的推论穿上了实测的衣服（原文逐字写着
「⚠️ **两个实测限制**」），此后一路被抄进参考文档、论证文档和代码注释，没人回头问它的证据是什么。

所以判词只有三句，**「不支持」不在其中**：

| 判词 | 什么时候打 | 它说了什么 |
|---|---|---|
| **认了** | 拿到了基线里没有的条目，而基线自己两次一致 | 服务端确实按这个参数多给了 —— 肯定结论 |
| **这一次没多给** | 一个新条目都没多拿到 | **只有这么多**，与「没这个参数」不可区分 |
| **作废** | 基线自己两次就不一样 | 端点在漂，这一跑一个参数也别判 |

量的是**比基线多拿到几个新条目**，不是「两张列表一不一样」。按顺序比整张列表的话，
服务端只要把同一批换个次序返回就会被判成「认了」—— 而那是这个工具最重的一句结论，
不该由一次重排买到。

**基线重跑那一次请求是地基，不是冗余。** 少了它，「带上 `offset` 拿到了另一批」
既可能是参数被认了、也可能只是这个端点本来就在漂，而两种读法的结论正好相反。
`M-H44-b` 就是把它省掉的那条变异。

顺带还打一样便宜的东西：**整份响应的键路径**。原来的证据「响应只有 `count` 和 `items`」
是从 `pickList` 的视角看的 —— 它只取 `data.data.items`，别的一律扔掉。
真有一个 `next_max_id` 藏在别处，今天没有任何一行代码看得见它。

## 五、它自己怎么被守着

`scripts/probe-ig-paging.ts` 带 shebang，属于「每个可执行文件都要有出处」那条
（`scripts/check/selfcheck.ts` 的末节）。出处是自检里的 `ig-paging-probe` 一组，
三句判词各造一次 —— 后两句靠 `scripts/check/fake-fetch.ts` 新增的两个旋钮：
关键词带 `force-paged` 就按 `offset` 换一批，带 `force-drift` 就每次都换一批。

**不造这两个旋钮的话，夹具只会走「这一次没多给」那一支** —— 而那恰好是最容易
被读成假结论的一支，于是「跑通了」买到的东西最少。

两条负片钉着（`req: "harness"`，验证者是自检）：

- `M-H44-a`：把「这一次没多给」改口说成「不支持分页」
- `M-H44-b`：省掉基线重跑，拿第一次的结果顶替

```
npx tsx scripts/check/mutate.ts --only=M-H44-a,M-H44-b
npx tsx scripts/check/selfcheck.ts --only=ig-paging-probe
```

## 六、跑出来是「都没多给」怎么办 —— 现在就把话说死

这是最可能的结果，也是最容易在半年后变回「不支持分页」的结果。所以：

> **「四个参数这一次都没多给」不是一条结论，是一次没有结论的观测。**
> 它只允许两种下一步：换参数名再试、或拿到接口文档。**不允许**据此写任何
> 「IG 结构性上限」的论证 —— ADR-94 第十五节那套论证就是这么来的。

⚠️ 欠条：**这个工具至今一次真实请求都没发过。** 罐头响应是我按 2026-08-25 那份
实测结构捏的，所以「自检全绿」只证明三条路径走得完，**不证明真实端点上的任何事**；
`identify()` 在真实条目上走哪一支（有没有 `id`／`pk`）也还没见过真的
· 重启条件：下一个**同时有网络与充过值 key** 的人跑一次 `npm run probe:ig-paging`
>
> ⚠️ 就地更正（2026-09-22）：**上面这条原先只写了「有 key」，漏掉了「有网络」**——
> 而 ADR-94 那张欠条逐字写的是「下一次有**网络与 key** 的人」。实测：在本仓库的
> 沙箱环境里，出网代理**按策略拒掉 `api.tikhub.io`**，`curl` 报
> `CONNECT tunnel failed, response 403`，代理自己的状态里也记着
> `connect_rejected · gateway answered 403 to CONNECT · host api.tikhub.io:443`。
> **所以在那种环境里配上 key 也跑不了**，而脚本会在缺 key 那一步就退 2、
> 读的人只看见「缺 key」、看不见后面还有一堵墙。这跟 ADR-94 拉不到
> `openapi.json` 是同一堵。两个条件缺一不可，分开写出来。
> 怎么复现：`curl -sS "$HTTPS_PROXY/__agentproxy/status"` 看 `recentRelayFailures`。

## 七、欠条还了一半：跑出来了，而结果比「没验过」更难看

2026-09-22，用户在一台能出网、带充过值 key 的机器上跑了一次。**上面第一张欠条的
重启条件就此触发**，结果分两半 —— 一半是确定的结论，一半仍然没有。

### 确定的：那句话不是「没验过」，是**错的**

探针顺带打的那份**整份响应键路径**里有：

```
data.pagination_token
```

它是 `data.data` 的**兄弟**，就在 items 上面一层。而 `pickList` 只取 `data.data.items`，
**所以在这一跑之前，没有任何一行代码看得见它**。

也就是说，原文那句证据 ——「响应只有 `count` 和 `items`」—— 是**透过我们自己那个窄窗口
看出来的**。同一份响应的键路径远不止两条（数目别写进这儿，跑一次看 `all_key_paths`）。
第一节里我写的是「那是**响应**那一侧的观测，而请求侧没人试过」，这个说法**太客气了**：
连响应那一侧的观测本身都不成立。

⚠️ **但「有游标」不等于「能翻页」。** 把那个值回传给服务端管不管用，仍然没人试过。
有键、值是 null、回传被忽略，这三种都可能。

### 仍然没有的：四个候选参数一条都没判成

`count`／`offset`／`page`／`max_id` 全判「**作废**」，因为**基线自己两次就不一样** ——
两次完全相同的请求返回了不同的条目集。第三节那道地基在这一跑里真的起作用了：
没有它，`offset` 那一行「多出几个基线没有的条目」会被读成「offset 被认了」。

**端点会漂**这件事本身也是这一跑才知道的，而它比参数问题更根本：它意味着
「一个关键词固定返回那一批人」这个隐含前提也不成立。

### 这一跑暴露了探针自己的三个毛病，当场修了

1. **`reading` 那句话把最大的发现漏掉了。** 它只说「一个参数都没判，换个时段再跑」——
   而游标就躺在同一份输出的另一个字段里。游标那一条**与对比无关**（是对一份响应的
   直接观测），所以现在它**不分支**地排在结论第一句。负片 `M-H44-c` 守着
2. **只打键名不打值。** 「那个 token 是 null 还是真有个值」是现在最该问的，而原版答不了。
   现在连值一起打（截断）
3. **「作废」不给漂移量。** 基线漂 1 条和漂 7 条，对「某个参数多给 7 条」的读法完全不同。
   现在报 `baseline_drift_items`，并在结论里教怎么跟每一行的「基线没有的」比。负片 `M-H44-d`

> **这三条是同一个毛病的三种形状：工具把话说到一半就停了。** 判词表是为了不让人
> 得出假结论 —— 但一个**把真结论藏起来**的工具，代价一样大。

## 八、第二跑：token 是真的，而漂移量让那四个猜的参数全成了噪音

同一天又跑了一次（探针已带上第七节那三处修复）。两件事：

**一、那个 token 不是 null，是一个真的不透明串。** 「有键」升级成「有值」——
下一步从「要不要试」变成了「怎么试」。

**二、漂移量一摆出来，那四个猜的参数就全没戏了。** 基线自己漂了 5 条（12 条里），
而 `count`／`offset`／`page`／`max_id` 的「基线没有的」分别是 8／6／5／7 ——
**全在漂移量级里**。上一跑的「作废」只是「没信息」，这一跑的「作废」是
「而且这四个看着都没戏」。顺带：`count=50` 两跑都返回同样条数，它显然不是页大小。

**这就是漂移量那三行代码买到的东西**：把一个「不知道」变成了「知道这几个不用再试」。

### 于是把 token 回传接进了探针

`VARIANTS` 装不下它 —— 那是一张常量表，而 token 是从**基线响应里挖出来的**。
所以多了一条动态候选：拿观测到的值，按最可能的两个参数名各发一次。输出里
**猜的排前、挖回来的排后**，因为两类的证据强度不一样（值是观测到的，名字仍然是猜的）。

三处配套：

- **原值与给人看的值分开**（`rawAt` / `show`）。显示要截断，**回传必须用原值** ——
  拿截断过的串去试，是一次注定失败、且失败原因看不出来的试探。第二跑的输出里
  那个 token 连收尾引号都被截掉了，差一点就这么塞回去
- **「作废」那一支点名高出漂移量的行**，措辞钉死「这是线索，不是结论」——
  判词仍然全是作废。**严格大于，不设阈值**：阈值是凭空造的确定性
- **中止时报出已花的请求数** —— 非 200 直接抛，前面那几次已付的观测一起丢了，
  读的人至少要知道这一跑赔了多少

### 顺带修掉一个定位式的夹具触发器

假 fetch 里「第 7 次调用回 429」是给 `TikHub.get()` 的退避重试用的。探针**不走那条路**
（自己的 `ask()`，非 200 直接抛），而候选一多就跨过第 7 次 —— 整跑当场中止。
**按「第几次」定位的触发器，调用数一变就会误伤。**

给探针的夹具加了个显式关门旋钮（`FAKE_FETCH_NO_429`），没有改那条触发器本身：
改成关键词触发的话，`collect` 那几条轨迹就不再顺带走到重试分支，**而那条分支今天
没有任何变异守着** —— 减了覆盖也不会有人报错。

## 九、第三跑：游标回传试过了 —— 没被忽略，也没翻页

同一天第三次（探针已带上第八节接进去的游标回传）。**上面那张「还没人跑过带它的那一版」
的欠条，重启条件就此触发。**

两件事是判词表管不着的 —— 它们都不依赖基线对比，所以「作废」不影响它们成立：

**一、拿响应里的游标当 `max_id` 发那一次，返回的条数与基线不同。** 那一跑其余几次观测、
以及第二跑的每一次，回的都是同样条数，只有它不是。而 `ask()` 非 200 直接抛、`pickList`
也不截断，所以那是一个 200。**服务端没有忽略这个参数。**

**二、但回传之后拿到的是同一批人的子集，不是下一批。** 两条游标候选的「基线没有的」
都**低于基线自己的漂移量** —— 也就是说，**回传游标之后的结果，比什么都不传、原样重跑
一次更像基线**。真的翻页该给的是一整页全新的。

顺带两条：token 的值第二跑与第三跑**不一样**（同一个关键词），所以它是每份响应各一个的
状态串，不是「第 2 页」的钥匙；漂移量本身两跑也不一样，见上面那张欠条的就地更正。

### 于是：问错了问题

六条候选（四个猜的参数名 ＋ 两种游标回传）全落在漂移量级里。而**端点会漂**这件事本身
给出了另一种解释：这个端点可能根本不是「一页一页翻」，而是**每次抽一把**。那样的话
召回上限就不是单次条数，而是**重复调用的累计去重人数** —— 而这条路**不需要服务端
支持任何分页参数**。

## 十、接口文档拿到了：那几个参数名不是猜的，而**文档里写明的那个照样没翻页**

`api.tikhub.io` 与 `docs.tikhub.io` 在这台机器上**整个域被出网代理挡着**（curl 与抓取
都是 CONNECT 403），官网文档页打不开。绕道：TikHub 自己的 Python SDK 是**按 OpenAPI
spec 机械生成**的（自述端点全覆盖），路径与请求参数名从它的源码里读得出来。
**GitHub 从来没被挡** —— 这一点是整件事的关键。

⚠️ **它对路径与请求参数是权威的，对响应体一个字都答不了** —— 那正是
`docs/data-source-strategy.md` 第 3 条早就记下的事：TikHub 的 OpenAPI 不描述响应内容。
而且那份 SDK 的提交日期比我们上一轮真实核实还早，所以它是**证据，不是正本**。

| 端点 | 官方请求参数 |
|---|---|
| `v2/search_reels` | `keyword`、**`pagination_token`** |
| `v2/search_users` | 只有 `keyword` —— **一个分页参数都没有** |
| `v3/search_users` | `query`、`rank_token` |
| `v1/fetch_hashtag_posts` | `hashtag`、`end_cursor` |
| `v2/fetch_hashtag_posts` | `keyword`、`feed_type`、`pagination_token` |
| `v2/general_search` | `keyword`、`pagination_token` |
| `v1`／`v2` `user_id_to_username` | `user_id` |

三件事就此定下来：

**一、`VARIANTS` 那四个名字确实是凭空猜的，而且 spec 里一个都没有。** 于是第八节那句
「那四个看着都没戏」升级成「**那四个本来就不该试**」—— 第三节判词表里「未知参数常被
服务端静默忽略」这句话，现在有出处了。

**二、而 `pagination_token` 不是猜的：它就是 `search_reels` 官方声明的分页参数。**
第九节那次回传用的是**文档里写明的那个名字**，而服务端仍然没给出下一页。

**三、`v3/get_hashtag_posts` 这个端点不存在。** 参考文档那张参数名表里那一行是假的
（v3 只有 `search_hashtags`，那是搜话题，不是取话题下的帖子）。

### 真正的教训不在「猜错了」，在顺序

这张欠条自己写着重启条件是「拿到接口文档，或 `openapi.json` 能拉下来（上次代理 403）」。
把「代理挡了 `api.tikhub.io`」读成「正本拿不到」，于是三跑一共十几次付费请求花在了
**spec 里根本不存在的参数名**上。**先拿真 key 试，才去找正本 —— 顺序反了。**
某个域被出网代理挡住，不等于正本拿不到。

这条不另写一份规矩：真正挡住它的是代码 —— `VARIANTS` 已经不在了，而探针头上那段
注释就写着这件事。（散文规矩会有两份副本，而先改的那边不会报错，ADR-46。）

## 十一、于是探针整个换掉：删掉猜参数，收成 `--chain` ＋ `--repeat`

**第九节那次回传只试了一步，而 `pagination_token` 的正经用法是顺着链一直翻。**
所以「翻页这条路死了」这个判断本身是用错方法得出来的 —— 它没死。

探针收成两个模式，共用一条曲线：

| 模式 | 每一次带什么 | 回答什么 | 发几次请求 |
|---|---|---|---|
| 默认 | 只有 `keyword` | 响应长什么样、有没有像游标的键 | 1 |
| `--chain N` | 上一次响应里的 `pagination_token` | **翻页**能拿到多少人 | 2N |
| `--repeat N` | 什么都不带，原样再发 | **漂移**能刷出多少人 | N |

**`--chain` 一定同时跑对照组** —— 这就是 2N 的来源，也是第三节那条「基线重跑是整个
对比的地基」的升级版：从一次对照变成一条对照曲线。这个端点会漂，少了对照，
链上多出来的人分不清是翻页给的还是漂给的，**而这两种读法的结论正好相反**。
负片 `M-H44-a` 把对照组删掉、`M-H44-b` 把那个比较松一格，两条都被
「端点在漂，链和对照涨得一样多」那条断言杀掉 —— 夹具 `force-drift` 每次换一批人
**而且每次都照给游标**，正是为这一条造的。

**数的是人，不是条目。** 同一个人连发三条 Reels，翻页能多拿视频却一个新达人都没多给 ——
「条目在涨、人没涨」是这里最贵的误读（`M-H44-f`、`M-H44-h`，夹具 `force-onecreator`）。

**认不出作者的条目单独计数：既不折成一个人，也不当成零个。** 折成一个桶凭空多出一个
达人，当成零个又把「有人、但没认出来」说成「没有人」。人数只当**下限**（P1）。

**唯一不靠推断的终止条件：服务端不再给下一个游标。** 那是它自己说的「没有下一页」，
与「这 N 次之内没再涨」不是一回事 —— 后者是我们的推断，混成一句就等于把推断说成了
对方的原话（`M-H44-d`，夹具 `force-paged` 翻到第三页就不再给游标）。

⚠️ 一条写不出来的负片：**「缺操作数时退出码该是 2」守不住**。把退出码改掉的变异会让
`run(..., {status: 2})` 那条进程级期望本身失败，而本仓库的变异判定见了「（进程）」记号
一律判 `crashed`（`mutate-rule.ts` 的判据表与 `:42-43`，那是刻意的保守假阴性）。
于是那条负片改成守**诊断措辞**，退出码那一半只由断言守着 —— 手工验过它会红，
但没有负片替它作证。说在明处，别以为那一格是满的。

⚠️ 顺带记下：**这一版没有省下多少行**（删掉猜参数那一套 ≈ 加上链式翻页与对照组）。
省下的是**每跑一次少发四次付费请求**，以及问的是对的问题。行数那个数别再拿来当成绩。

## 十二、第四跑：链式翻页**有效**，而且两条杠杆是叠加的

2026-09-22，关键词 `smoothie`，`--chain 10`（10 次链 ＋ 10 次对照，共 20 次请求）。

| 怎么问 | 10 次之后累计去重达人 |
|---|---|
| 一次请求 | 11–12 |
| 原样重发 10 次（只吃漂移） | 36 |
| 顺着 `pagination_token` 翻 10 次 | **58** |

**一、翻页是真的有效。** 58 对 36，而对照组同样是十次独立采样 —— 这不是噪音，
第三节那条「基线重跑是地基」的纪律在这一跑上第一次给出了**肯定**结论。

**二、漂移也独立有效，两者叠加。** 对照组光靠原样重发就从一次的 12 涨到 36。
所以第九节末尾那句「问错了问题」只对了一半：漂移确实是一条杠杆，但它不是**唯一**
那条，而翻页被判死是因为只试了一步。

**三、完全没到头。** 链的最后一次还多出十个没见过的人，而对照组那边已经明显衰减
（有两次一个新人都没多给）。58 不是上限，是我们只翻了十页。

**四、但它不是干净的分页。** 链上每一次的「新条目」在满页与个位数之间来回跳 ——
真分页每一页该几乎全新。所以**不许按「翻 N 页 = N × 单页条数」去估**，重叠很重；
能说的只有「十次换来五十几个人」。

### ⚠️ 但「五倍」是只看累计的说法 —— 按每次请求算，翻页是在**变贵**

用户当天指出成本视角后，把那一跑的**边际**产出算了出来：

| | 每次请求买到几个去重达人 |
|---|---|
| 新关键词的第一页 | 11–12 |
| 同一关键词头两次 | 10.5 |
| 同一关键词第 3–10 次 | **4.6** |
| 原样重发（只吃漂移） | 3.6 |

累计确实是五倍，**而代价是十倍请求**。同一关键词翻到第十页，每次请求的产出只有
新开一个关键词首页的四成。**所以在预算固定时，广度大概率打败深度** ——
十次请求分给十个关键词的首页，胜过押在一个关键词的十页上。

⚠️ 这条边际曲线**不是干净衰减的**（第十次又蹦出十个新人），所以「翻到第二页就该停」
从一次跑里得不出来；能得出的只有「第 3–10 次的平均明显低于首页」。

⚠️ **决定这件事的那个数还没量：关键词之间的人群重叠。** 若两个关键词返回的大半是
同一批人，广度的优势会被吃掉。它很便宜（几个关键词各发一次），而且**应当排在
把游标接进采集之前** —— 有可能结论是页数上限该设成一。

于是 `D6.h`（单关键词页数上限，跨运行有效 · ADR-100）那道闸门找到了它真正的用处：
它一直管着一个恒为一页的东西，而现在它是**按边际产出决定翻几页**的那个旋钮。
**别把它默认设成「不限」。**

### 于是「IG 只能拿一页」这句话彻底完了

它经历了三个阶段：先是「没有分页游标」（假的，响应里就有）；再是「有游标不等于能
翻页」（真的，但只试了一步）；现在是**能翻页，而且一次跑就把召回拉到五倍左右**。
下一步落在 `providers/tikhub.ts`：`search()` 今天见到 `offset > 0` 直接返回空，
`has_more: false` 是写死的字面量 —— 那两处是「IG 只有一页」这个现象的**真正来源**。

⚠️ 这是**一个关键词、一次跑**。别把它写成「IG 每个关键词能拿五十几个人」——
换关键词、换时段都没验过，而这正是这条 ADR 从头到尾在防的那种写法。

### 顺带修掉一处「换了方案、旧写法跟着漏过来」

`readCurve()` 里报「跑了几次」用的是**要求的次数**，不是曲线上实际有几行。旧设计里
那个数是待试参数的个数，必然等于实际跑数；换成链式翻页之后不再成立 —— 链一旦提前
断掉（服务端不给游标了），它就会把没发生过的几次算进结论。自检当时没抓到，因为
夹具恰好断在第三次、而那条断言要的就是三次。现在要五次、断在第三次（负片 `M-H44-i`）。

⚠️ 欠条：**`pagination_token` 回传管不管用，工具现在会试，但还没人跑过带它的那一版。**
参数名仍然是猜的（响应里叫 `pagination_token`，请求里未必）· 重启条件：下一个同时有
网络与充过值 key 的人跑一次，看那两行的「基线没有的」有没有明显高过漂移量

> ⚠️ 就地更正（2026-09-22，第三跑）：**这张欠条还完了。** 重启条件踩到了，逐字要的那个
> 对比有了答案 —— 那两行的「基线没有的」不但没高过漂移量，还**明显低于**它。结果见第九节。
> ⚠️ 同日再更正：**参数名不是猜的** —— `pagination_token` 就是 `search_reels` 官方声明的
> 分页参数（第十一节）。所以这一跑的份量比原先记的更重。

⚠️ 欠条：**429 撞上就整跑作废，已付的观测全丢。** 探针刻意不重试（那是 `requests`
等于真实发出次数这个性质的来源），代价是限速一碰就赔掉整跑。现在至少会报出赔了多少 ·
重启条件：有人真的在跑探针时撞上 429

⚠️ 欠条：**这个端点在相同请求下会漂，而漂多少没有量过。** 只知道 2026-09-22 那一跑
基线两次不一致。这件事对「一个关键词能拿到多少人」的影响完全没算过 —— 如果重复调用
能稳定刷出新人，那本身就是一条召回杠杆，而且不需要任何新参数 · 重启条件：同一个关键词
连跑若干次，量累计去重人数的增长曲线

> ⚠️ 就地更正（2026-09-22）：**「漂多少没有量过」这句话已经不成立** —— 第二跑与第三跑
> 各量了一次，而且两次不一样：**漂移量自己也在漂**。于是「高过漂移量就值得再试」那条
> 线索的地基本身在动，两跑里被点名的那一行都只高出一点点。
> 这张欠条剩下的那一半仍然欠着：**累计去重人数的增长曲线没人跑过**。第十节把量它的
> 工具造出来了（`--repeat N`），所以重启条件收紧成：下一个有网络与充过值 key 的人
> 跑一次 `--chain`（它自带 `--repeat` 那条对照曲线）。

⚠️ 欠条：**`VARIANTS` 那四个参数名是猜的。** `count`／`offset`／`page`／`max_id` 取自
TikTok 侧的命名与 IG 私有 API 的常见写法，没有任何东西保证 TikHub 用的是这几个；
「四个都没多给」因此连「常见参数名都不认」都证不出来 · 重启条件：拿到
`search_reels` 的接口文档，或 TikHub 的 `openapi.json` 能拉下来（上次代理 403）

## 十三、2026-09-23 追记：固定规范能证明什么，历史样本不能外推什么

- 日期：2026-09-23；类型：事实证伪与证据边界补充。
- 触发事实：直接读到固定版本的官方 OpenAPI，发现第十节把目标业务 `data` 无结构
  外推成整个规范没有响应 schema，把路径未列出写成端点不存在；第十二节又把一个词的首页
  当成新关键词首页，未量跨词重叠便推出广度更好。
- 冲击的需求：不修改登记表；更正支撑判断的事实，保持 P1/P5 的未知边界。
- 结论：采纳事实更正；历史正文不删改。此追记不接入新发现路径、分页或缓存，不改页数上限。

### 可追溯的规范范围

正本为 [TikHub 官方 SDK 中固定提交的 `spec/openapi.json`](https://github.com/TikHub/TikHub-API-Python-SDK/blob/2d92927332e1ff0fdc2d05b46381218a0f5a3511/spec/openapi.json)，
提交 `2d92927332e1ff0fdc2d05b46381218a0f5a3511`；本次只读 GitHub，未发 TikHub 请求。
文件 SHA-256 为 `dbdb9776f1cb44b50c3ac0276a6d69697719f8dfaa4fa0bb8a9cc027af15a51a`。

该快照的 `components.schemas` 有 **114 项**。本次核对的 IG V2 Reels/users/general、
V3 users、V1/V2 hashtag、V1/V2 id 转用户名端点，其 `get.responses.200` JSON schema
均引用 `ResponseModel`。该模型有响应外壳字段，而 `properties.data.anyOf` 是
`[{}, {"type":"null"}]`。因此第一、十节的“整个 OpenAPI 不描述响应”及“196 个 schema”
不能用于描述这份固定快照；也未核出“所有端点都返回同一模型”这个全称断言。
规范未以类型化 schema 约束这些目标端点的业务 `data`；`get.description` 确有返回字段
说明，例如 Reels/hashtag/general 的 `data.items`、`pagination_token`，以及 V3 users 的
`data.users`、`data.rank_token`。这些是官方文字说明，不能略去，也不证明实际字段值、
每条记录的覆盖率或完整响应中的包装层级；这些问题仍需对应响应样本核验。

第十节参数表经逐项重核仍可用于这份快照：Reels 是 `keyword` + `pagination_token`；
V2 users 只声明 `keyword`，V3 users 是 `query` + `rank_token`；V1 hashtag 是
`hashtag` + `end_cursor`，V2 hashtag 是 `keyword` + `feed_type` + `pagination_token`；
general 是 `keyword` + `pagination_token`；两版 id 转用户名均为 `user_id`。
**V2 users 未声明分页参数，不等于它返回全部匹配用户。** `v3/get_hashtag_posts` 只是在
这份快照中没有该路径，不能据此宣告所有版本或当前在线服务都不存在。
同理，候选参数未被这份规范声明，不等于已经通过运行时验证证明服务端必然拒绝或忽略它。

撤回由接口名称推导的全称边界：Reels 搜索是否包含图文、轮播或 PhotoMode，是否覆盖仅发
这些媒体的作者，以及具体匹配排序，都没有被本稿引用的固定规范或原批首条摘要证明；`play_count` 的媒体
适用范围同样未定。历史某一短词优于某一词组，也不能证明所有词组都为零或自动过滤商家号。

第十一节将缺少下一游标说成“服务端自己说没有下一页”同样过强：缺 token 至多表明本次
无可追的链，不能证明匹配结果已穷尽。探针当前运行时仍输出这个更强断言，此事实修订不改
执行代码；调用者不能把它转述为供应商的完整性保证。

⚠️ 欠条：探针运行时及其说明副本仍把缺 token 写成服务端明确没有下一页；`beatsDrift`
又仅凭一次链与重发的作者数差异就作因果归因，两支分别说“翻页确实多拿到人”或“是漂给的，
不是翻页给的”，超出了观测。重启条件：本次 API 事实修订合入；随后最小修正
`scripts/probe-ig-paging.ts`：缺 token 只说“本次没有可继续传递的 token，不能证明结果集
已耗尽”；链/对照比较只报告当次差异，不直接归因、推统计显著性或据此建议接入。
同步架构、探针注释与夹具说明并核对相关断言，不在本次事实修订修改运行代码。

`ResponseModel.cache_url` 允许 string/null，且无必填声明；`cache_message_zh` 的默认
文案声明缓存结果直链有效 24 小时，访问不另收费。此前“缓存不能省下重取费用”的全称判断
因此撤回。这里说的是那次结果的直链访问，**不等于普通 API 重发免费**，也不等于每次响应
都含可用直链；本次未访问真实缓存 URL。当前 `--resume` 未使用该机制，请求与续跑实现不变；
其费用估算与下面新核到的端点标价存在差异。

### 三路发现端点规范价不是工具旧的统一估算

该固定快照中 IG V2 `search_reels`、`fetch_hashtag_posts`、`general_search` 的
`get.description` 各自声明 **0.002 USD/请求**。真实账单未核，其他端点不能据此类推；
但仓库旧的统一 `$0.001/请求` 不能继续称为这些接口的可靠费用上界，历史阶梯折扣描述
也不能证明“实际只会更低”。文档收回此承诺，本次不改预算计算代码。

⚠️ 欠条：现有 `UNIT_PRICE=0.001` 与上述三路规范标价不同，预算估算和探针“至多”费用
提示尚未核对。重启条件：本次 API 事实修订合入；逐端点核定计价依据并修正预算实现、
输出承诺及对应验证，真实账单未核时仍须区分规范声明、工具估算与实际支出。

### `smoothie` 历史观测与策略推断分开

第十二节保留的是用户提供的 2026-09-22 一次 `smoothie` 记录：10 次链得到 58 个累计
去重作者，同次数原样重发得到 36 个，单请求为 11–12 个作者。这些单位都是**作者**，
不是 `items` 条目；此处转述历史记录，未用原始响应重新核算，也未新增实测。

这份记录支持“那次链式请求比等次数重发观察到更多作者”，不能证明统计显著性或因果可加性；
第十二节的“不是噪音”“独立且叠加”应收窄到该观测。重复请求有重叠，不能按页数乘首页人数
估算总量。历史记录中末次仍新增作者，也不证明服务端结果集有多大。

**撤回“固定预算下广度大概率打败深度”。** 第十二节的“新关键词的第一页”实际仍来自
同一个 `smoothie`；没有不同关键词的累计并集与重叠，不能把它当成每个新词的边际产出。
“翻两页就停”“通用上限设一页/四页/不限”均不能由这次记录决定。现有页数上限继续是
当前实现与需求约束，尚未通过跨关键词的成本收益比较证明最优。

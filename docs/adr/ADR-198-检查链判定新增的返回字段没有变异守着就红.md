## 一、判什么

PR 上，`scripts/check/` 下非验证者文件里，导出函数的返回值这次新加的字段，变异登记表里没有一条改到它、被测试打红的变异，也没写具名豁免，就红。基线与体量闸门同一个起点（`size-rule.ts` 的 `resolveBaseline`）：PR 上是与主干的共同祖先，HEAD 在主干上时是上一版。主干上只报数、退 0，理由同体量闸门。

字段**按位置认，不按名字认**：名字会撞（判别值相同的联合成员、重载、同名的属性……写法列不完），位置不会。第二十一轮以前按名字认，同名的几处怎么对，前后改了五回，见历史文件第五节末「第二十一轮后改设计」。

1. **字段**：每个导出函数的返回类型逐层展开 —— 数组、元组、联合、交叉、索引签名（`Record`）、`Readonly`／`Partial`／`Pick` 这类映射；类型参数按它的约束；`Promise`、`Map`、`Set` 这类库里的泛型取类型参数 —— 展开到的、声明在 `scripts/check/` 直属非验证者文件里的每一个属性，**一处声明一个字段**。函数类型的属性本身算一个字段，它的返回值不展开。
2. **新增**：字段声明里属性名所在的那一行，是这次相对基线新加的行。新加了哪几行由 git 说，不比名字、不数处数：文件名由 git 列出（空字符分隔，不加引号、不转义），每个文件一份 `git diff -U0`，`addedLines` 只读块头写的新文件那一边的行号范围，不解析文件名、不逐行数正文。只挪了位置、改了格式、改了类型的旧字段，那一行也是新加的，算新增（多报红，在安全的一边）。
3. **赋值处**：给这个字段赋值的那几处源码 —— 对象字面量里写它的那一项（`{ n: 1 }`，简写 `{ n }` 也算）、`x.n = …`、`x['n'] += …`。哪一处是给哪个字段赋值，问 TypeScript 语言服务的「跳到定义」（编辑器里同名的那个功能）：它按类型认，同名的不同字段在它眼里是不同的东西。「跳到定义」交回的（简写去掉变量自己那一个）**恰好一个、而且是字段**才算；交回几个的（没有判别值、分不开的联合，或一个字段加一个不归闸门管的成员）不算任何一个的 —— 先数个数、后看是不是字段。推断出来的对象字面量里，那一项自己就是字段声明，也就是它的赋值处。验证者文件里写的不算（那是测试造的期望值）。
4. **测到了**：变异登记表（`scripts/check/mutations.json`）里有一条变异，它**真正改动的那一段**和这个字段的某一处赋值重叠（有公共的字；只是挨着不算）。一条变异的 `find` 在它的文件里只出现一次（变异跑本来就这样要求），所以位置是确定的；`find` 与 `replace` 相同的开头和结尾不算改动，去掉（`markSite`）—— 否则 `find` 为了定位多带的那几个字，会替旁边的字段作保。只插入、不删字的变异剩一个空段，插入点落在赋值处里面才算。变异跑（`npm run mutate`）要求每条变异都被测试打红，所以重叠就是「把给这个字段赋值的那段改坏，有测试会红」—— 这是真跑出来的，不是读测试源码推出来的。
5. **不读测试源码**：测试里读没读、比没比这个字段，一律不看。第十九轮以前这里是一整段「读测试源码、推断测试碰没碰到这个字段」的判定，十九轮 CodeRabbit 里一多半的意见落在它身上，见历史文件第五节末「第十九轮后改设计」。
6. **豁免**：字段声明前面独占几行的注释里、或那一行行尾的注释里（行注释、块注释都认）写 `字段不入断言：<理由>`。理由去掉多行注释行首的 `*` 与首尾空白后必须非空，写了标记没写理由的新增字段照样红（有没有变异都算）。上一个字段行尾的注释不算下一个字段的；字符串里的标记不算。豁免只管写了它的那一处声明。给只能从子进程输出验到的、从文件或 JSON 读进来没有赋值处的字段用。

## 三、证不了的

- **变异改坏的是不是这个字段的值**，只核到它改的那段和一处赋值重叠为止。赋值那一项里改的是右边算值的一小段，大多就是改了这个字段的值；但改到的也可能是同一个表达式里别的东西（右边嵌着的另一个对象字面量、顺手调用的函数），测试为那个红了，也算守住了它 —— 这一步靠评审看变异的 `why`。
- **没有赋值处的字段，变异守不了，只能写豁免**：从文件或 JSON 读进来、`as` 断言出来、`satisfies` 套着写的、展开 `{ ...x }` 带进来、方法简写 `{ run() {…} }` 写的，以及没有判别值、TypeScript 自己分不开是哪个成员的联合（`{ rule; index } | { refused; rule }` 里的 `rule`）。都在多报红的一边。
- 看不见的新增：一个函数的返回类型改成仓库里已有的、更大的类型，或新加一个函数返回已有的类型，多出来的字段声明那一行没动，不算新增；`Record<某个联合, …>`、`{ [K in 某个联合]: … }` 给联合加一个成员，不算新增；声明成 `unknown`／`any` 的字段里装的新结构看不见。
- 打印出来的文字不是字段。检查链靠 stdout 行与退出码对外说话的那一大半（入口打的行、机器段里拼出来的 JSON 串）不在这道闸门里。
- 看不见的出口：不导出的函数、返回 `any` 的函数、返回值类型声明在 `scripts/check/` 以外（`scripts/lib/`）的、导出类的方法、导出对象上的方法（`export const api = { run() {…} }`）、`namespace` 里的函数、返回函数的函数、回调参数。今天 `scripts/check/` 下没有导出类。
- 按行认新增：只挪了位置、改了格式、改了类型、同一行上改了别的字段的旧字段也算新增，可能误红 —— 补一条变异或写豁免。一行里写了几个字段（`{ a: number; b: number }`），动了其中一个，同一行的几个都算新增。
- 本机 `git update-index --assume-unchanged`／`--skip-worktree` 标过的文件，git 不列它的改动，这道闸门也看不见；只影响本机，CI 上没有这种标记。
- 现在这一边用的是工作区，基线用的是提交；没提交的改动算进「现在」。还没 `git add` 的新文件 `git diff` 不列，入口另用 `git ls-files --others --exclude-standard` 把它们整份算作新加（第四节）。

> ⚠️ 欠条「新字段的变异改坏的是不是它的值没人核」：字段断言闸门只核「有一条被测试打红的变异，改的那段和这个字段的一处赋值重叠」，不核那条变异改坏的确实是这个字段的值，也看不见本节列的那几种出口（打印的行、不导出的、类方法、对象方法、返回 `any` 的）与「看不见的新增」 · 档：登记 · 重启条件：下一次发现一个过了这道闸门、那条变异却没改到它的值的新字段；或定期清点

## 四、入口（第二片）

### 要用到的事实，各找谁要（第二片动手前写下，过独立复核；`process/3-BUILD.md` 第 8 条）

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 仓库根在哪 | `git rev-parse --show-toplevel`（git 入口里已有）。`fieldsOf` 的 `root`、`tsconfig.json`、变异登记表都从它找；下面每一问的路径与输出都写成按仓库根算（`:(top)`、`--full-name`、`--no-relative`）：不这样写，列文件那几问跟着当前目录走，在子目录里跑会悄悄少列 | 给机器读的 |
| 和哪个提交比、HEAD 在不在主干上 | git，经体量闸门的 `resolveBaseline`（`rev-parse`、`merge-base`、`rev-list`，git 入口里已有这几问） | 给机器读的（提交号、`true`/`false`） |
| 相对基线改过的、受 git 跟踪的文件 | `git diff --name-only --no-renames --no-relative -z <基线>`（git 入口加这一问；`--no-relative` 压住本机配置里的 `diff.relative`）：空字符分隔、不加引号不转义，名字原样当键；只留 `isJudgedFile` 认的那几份 | 给机器读的 |
| 还没加进 git 的新文件 | `git ls-files -z --full-name --others --exclude-standard -- ':(top)scripts/check/'`（git 入口加这一问） | 给机器读的 |
| 受跟踪的文件新加了哪几行 | 每个文件一问 `git diff --no-renames --no-relative --no-color --no-ext-diff --no-textconv --text --diff-algorithm=myers --indent-heuristic -U0 --inter-hunk-context=0 <基线> -- ':(top,literal)<文件>'`（git 入口加这一问；起 git 时环境里去掉 `GIT_DIFF_OPTS` 与四个 `GIT_*_PATHSPECS`：前者会盖掉 `-U0`，`GIT_LITERAL_PATHSPECS` 会让带魔法的路径一个也对不上、git 答空、照样退 0）。`addedLines` 只读块头里新文件那一边的起止，不读正文。**列文件那一问列出来的文件，这一问答空就是「无从判断」**：真改过的文件至少有一行文件头（只改权限的也有），删掉的文件有一个只删的块 | 给机器读的（块头是固定格式） |
| 没加进 git 的新文件新加了哪几行 | 整份都是新加的（上一行的 `ls-files` 说的）。标成 1 到「换行符个数 + 1」的每一行：字段那一边的行号也只数换行符（第一片的 `fieldsOf`），同一个算法，整份里每个字段的行号都落在里面；多出来的行号不对应任何字段，不影响判 | 给机器读的（git 说「整份新」，行号由同一算法覆盖，不另推） |
| 字段所在的文件都在 git 的视野里 | `git ls-files -z --full-name --cached --others --exclude-standard -- ':(top)'`（git 入口里已有）。语言服务里每一份 `isJudgedFile` 认的文件都得在这张单子里，不在（被 `.gitignore` 挡掉的、名字的大小写或 Unicode 写法两边不一样的）就是「无从判断」：git 看不见它的改动，里面的字段就永远不算新。是符号链接的（问文件系统 `lstat`）也是「无从判断」：git 的行号是链接本身的 | 给机器读的 |
| 现在有哪些字段、各在哪一行、赋值处在哪 | TypeScript 语言服务，拿仓库根的 `tsconfig.json` 建（第一片的 `fieldsOf`） | 给机器读的（编译器） |
| 每条变异改的是哪一段 | 变异登记表 `scripts/check/mutations.json`（项目定的格式，`anchors` 闸门校验 `find` 在文件里正好出现一次）的 `file`、`find`、`replace`，交 `markSite`。文件正文取语言服务那个程序里的同一份（`getSourceFile(…).text`），不另读：TypeScript 读文件时去掉 BOM，另读一遍位置会差一个字。不在程序里的文件没有赋值处，不用算；`markSite` 给不出位置的变异不算守着任何字段（多报红那一边） | 给机器读的（项目自己的契约） |
| 那条变异真被测试打红 | 同一条检查链里的变异跑：本地是 `npm run check` 里的 `npm run mutate`，CI 上是同一个工作流里分三份跑的变异作业（工作流与 `package.json` 的 `check` 对不对得上，由变异负载闸门钉着）。登记表里每一条都必须被打红，有一条没被打红整条检查就红。本闸门排在变异跑前面、不重跑变异：单跑 `npm run fields` 绿，只说明「登记了」，「打红了」要等整条链 | 给机器读的（真跑） |
| 类型检查过了 | 排在 `npm run typecheck` 之后：类型检查不过的树上，字段与赋值处都认不准 | 给机器读的（编译器） |
| 哪个字段写了豁免 | 注释里的 `字段不入断言：<理由>` 标记（项目定的格式，由第一片的判定校验），注释的位置由 TypeScript 给 | 给机器读的（项目自己的契约） |
| 闸门真接在检查链上、判红时真的非 0 退出 | `package.json` 的 `scripts.check`（JSON 读出来比；CI 那边由变异负载闸门钉着与它一致）；独立验证者在 git 夹具建的玩具仓库里真起入口、看退出码 | 给机器读的（JSON、真跑） |

`scripts/check/field-use.ts`：照 `resolveBaseline` 定基线；上表那几问都经 git 入口问（ADR-220），git 入口表里加三问：列改过的文件（带 `--no-relative`）、列没加进 git 的新文件、单个文件的 `-U0`。单个文件用 `:(top,literal)` 写路径：从仓库根算、`?.ts` 这种名字不当通配符；`--no-renames` 让改了名的文件整份算新加（与列文件那一问一致，见下面「改名不认」）；`--text` 让被当成二进制的 `.ts` 也给出块，仍给不出就由 `addedLines` 抛错；`--diff-algorithm`、`--indent-heuristic` 钉死，本机配置换了算法，同样几行里算哪一行「新加」不跟着变。「文件 → 输出」交给 `addedLines`（输出不以文件头开头——列出来的文件答空也算——、块头读不懂，它抛错，不悄悄当成没改）；没加进 git 的新文件交给 `wholeFile` 整份算新加；判定文件 git 看不见或是符号链接由 `outOfSight` 说原因；入口只问、只读、只打印，这些判断都在判定文件里；拿仓库根的 `tsconfig.json` 建一个语言服务交给 `fieldsOf`（只建现在这一边，基线那一版不用建）；读变异登记表，每条用 `markSite` 定位置；三样交给 `fieldVerdict` 照打。PR 上有没有变异守着的新字段或空理由的豁免以 1 退出；HEAD 在主干上只报数、退 0；基线算不出来、`git diff` 失败或读不懂、列出来的文件 diff 答空、字段所在的文件 git 看不见或是符号链接、`tsconfig.json` 读不出或有错、一个字段都没取到，都说「无从判断」以 1 退出。

这张表的独立复核（2026-11-20，写代码之前）：认可每一行找的都是权威；挑出两处会悄悄报绿的 —— 环境变量 `GIT_LITERAL_PATHSPECS` 让单个文件那一问答空、退 0，在子目录里跑时列新文件那一问答空、本机配置 `diff.relative` 让列出来的名字少一截 —— 和四处要写清的（变异「打红」在 CI 上是哪一步、变异位置用哪一份正文、被忽略的文件 git 看不见、diff 算法没钉死）。都已改进上表：仓库根一行、空答案判无从判断、去掉那几个环境变量、`--no-relative`、`--full-name` 与 `:(top)`、正文取程序里那一份、「git 视野」一行、钉死算法。复核在临时仓库里真跑 git 2.43 核过各条（`-z` 原样、`--no-renames` 盖过钉死的改名检测、`GIT_DIFF_OPTS` 真会盖掉 `-U0`、`--no-ext-diff`／`--no-color`／`--text` 各盖过对应配置、删掉的文件是只删的块、改名的新文件整份新加）。

**这道闸门替代的是什么。** 替代的是「读」：这件事原先由每条 PR 的复核逐个字段读出来（触发它的事实那一串）；判据是一条命令（`npm run fields`）。它不另造一套「测没测到」的办法，用的是仓库已有的变异：变异问「每条负片都被抓到」，这道问「每个新字段都有一条负片」，两边合起来就是 ADR-70 第二节第①条那段原话要的。

> **什么条件下退成只报数**：连续 20 条改过 `scripts/check/` 的 PR 里，它红过的每一次都是误红（补的是豁免，或一条改不到这个字段的变异）时。那说明它挡下的不是漏测，是写法。

> **什么条件下整个撤掉**：变异测试改成按断言逐条记账（ADR-70 第二节第②条说的那张具名断言清册落地），新字段的变异能自动生成、不必手登时。

**已知边界，照实记。**
- 入口有真起它的独立验证者：需求测试组 `h-field-use-entry`、`h-field-use-entry-git`、`h-field-use-entry-inputs`，用 git 夹具建玩具仓库，起入口看退出码与打出来的行（没守着的新字段、补了变异、有理由与空理由的豁免、没加进 git 的新文件、主干上、只有一个提交；在子目录里跑、环境里开着按字面读路径、改了 diff 上下文、git 单问一个文件答空、git 出错退出、找不到主干；被忽略的文件、符号链接、`tsconfig.json` 读不出与选项有错、变异表读不出、一个字段都没有、不是仓库 —— 上面那串「无从判断」每一种都有一例），并核 `package.json` 的 `check` 里紧跟类型检查接着 `npm run fields`。只有规则模块的单测与变异证不了这两件 —— 把判红那一支的 `return 1` 改掉、或把 `npm run fields` 从 `check` 里拿掉，单测一条也不会红 —— 所以入口与 `package.json` 各有变异（`M-H198-ij`…`ja`），由这几组打红。CI 那一边的接线（`check.yml` 那一行）由变异负载闸门钉着与 `package.json` 的 `check` 一致。
- 递归类型（`next?: Chain<T[]>`，或 `type Loop<T> = Loop<T[]>[]`、`type Tup<T> = [Tup<T[]>]` 这种直接递归的数组、元组别名）每展开一层都是新的类型实例，按实例去重拦不住。找字段按这一条停：**数层数，不认类型是谁** —— 往下每走一步（属性、数组元素、联合成员、类型实参……）算一层，到 `DEPTH` 层（16）这一层整个不展开；另外一次从头走（一个导出函数的一个签名）总共展开超过 `BUDGET` 步（2000）也停 —— 一个泛型同时往几路递归（`a: N<T[]>; b: N<[T]>`）时每层分叉，层数没到就指数爆，光靠层数停不住。两条都有限，所以必停、也停得快。上限按仓库里实际的返回类型定：在提交 `9e1fd00` 的树上，拿 `tsconfig.json` 建程序，给本文件的 `enter` 临时加上记最大层数与步数，跑一遍 `fieldsOf` —— 509 处字段，最深 7 层，一次从头走最多 77 步，没有一条「没展开完」；步数上限降到 200 再跑，找到的字段一条不差，2000 留十倍。层数是一步一算，不是「套了几层」：`x?: Y[]` 走过去算三步（联合、数组、元素）。先判层数再记「走过」，在深处被停下的类型从浅处走到照样展开。**停下不悄悄少找**：找字段这一路一停，那个导出函数就记一条标着「没展开完」的「字段」（行号是函数名那一行），它没有赋值处，变异守不了，照新增字段报红；确认里面没有要验的字段，就在函数前写 `字段不入断言：<理由>` 放行。这一条**不论哪一行改没改、每次都判**：停下的地方里面后来加了字段，找不到，新加的那一行也对不上它；所以它一直要有豁免才绿，删了豁免就红。今天 `scripts/check/` 下没有会停下的返回类型；哪天真有返回类型深过 16 层或大过 2000 步，它会以「没展开完」报红，到时再看是加豁免还是调上限。按路径数层数有两处会多报红，都在安全的一边：一圈互相引用的类型从一头走进去，路径长过上限也会停，哪怕每个类型离根都很近（记「没展开完」）；上限那一层正好是数字、字符串这种没有字段的类型，也照样记「没展开完」。
- 改名不认：整份文件改了名，按新文件名问 git，整份都是新加的，里面的字段全算新增（多报红，在安全的一边；要绿就补变异或写豁免）。列文件、单个文件那两问都带 `--no-renames`，不跟本机配置、也不跟 git 入口钉死的「改名检测开着」走。判定文件改名少见，换来的是不必在改动文本里认改名的那几行。

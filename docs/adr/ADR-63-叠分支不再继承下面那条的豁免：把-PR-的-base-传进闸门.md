# ADR-63 叠分支不再继承下面那条的豁免：把 PR 的 base 传进闸门

- 2026-09-02 · 还 ADR-59 的另一张欠条
- 类型：不属于反向输入的五类 —— 改的是检查链自己
- 冲击的需求：无
- 结论：**采纳**

## 触发它的事实

分支寿命的豁免只认第一父链（合进来的旁支的 `age-ok:` 不算）。但 B 直接从没合的 A 上
开出去时，A 的提交就在 B 的第一父链上，B 于是继承 A 那句豁免，自己一句话没说过。
ADR-59 只做到「看得见」（报告里点名那句理由写在哪个提交上），把「挡得住」记成欠条：
提交图分不出「叠上去」和「这些提交本来就是我写的」，分得出的事实只有「这条 PR 的
base 是谁」，而它只在调用方手里。

## 改了什么

和 `AGE_PR_HEAD` 同一个形状：让调用方把 base 也传进来，传事实、不传推断。

- 三条跑法各接一个口：`AGE_PR_BASE`（check.yml：pull_request 事件填
  `github.event.pull_request.base.sha`；push 事件查一次这条分支开着的 PR，取最早那个的
  base，没有就空着）、`--base`（age.yml 贴 PR 那一步，从 PR 清单的 `baseRefOid` 或事件里取）、
  `--prs` 清单里的 `baseRefOid`（`--all`；这一列成了必填，少了整份清单不算）
- 判定在 `age-rule.ts` 的 `ownSince`：**base 里已经有的提交不算这条分支自己的**，判据是
  祖先关系（`merge-base --is-ancestor`），一条一问。base 是主干时第一父链上没有它的提交，
  一条都不去 —— 普通 PR 的行为一点没变
- 给了 base 却找不到、或与这条分支没有共同祖先 → 拒答，不退化成扫整条：那正是叠分支
  继承豁免的那条路
- 报告在豁免下面多一行说清楚扫了哪些：有 base 时「base 里已有的 N 条不算」，**N 是 0 也照说**；
  没有 base 时「没给 base，豁免扫的是整条第一父链」
- `age.yml` 的 `pull_request_target` 加 `edited`：改 base 分支不换 head，而 base 现在是判定的输入

## 量出来的

在一个临时仓库里复现（这个仓库造不出叠分支这个形状）。主干 `228f60b`；A 从主干开出，
两个提交作者时间都在 2026-08-27（量的那一刻分叉 149.9 小时），第二个 `a30154d` 写着
`age-ok: A 在等上游接口定稿`；B 从 A 的头开出一个提交，没有任何豁免。

| 跑法 | 结果 |
|---|---|
| `--ref B` | `⊘ B:分叉 149.9 / 48 小时` · `豁免(写在 a30154d 上):A 在等上游接口定稿` · `没给 base(…),豁免扫的是整条第一父链` —— **继承，但说了** |
| `--ref B --base <A 的头>` | `✗ B:分叉 149.9 / 48 小时` · `先合一次` —— **拦下** |
| A 又长了 a3，B 把 A 合进来，`--ref B --base <a3>` | `✗`，同上 —— 第一版按「链上碰到分叉点就截」在这里一刀不切（分叉点在 B 的第二父那边），评审举出来的，改成按祖先关系后拦下 |
| `--ref B --base <主干>`（叠分支对着主干开的 PR） | `⊘` · `豁免(写在 a30154d 上)` · `豁免只认这条分支自己的提交:base 228f60b 里已有的 0 条不算` —— **继承，如实报 0** |
| `--ref B --base <无共同祖先的提交>` | `✗ 分支寿命:无从判断 —— --base 给的 … 与 B 没有共同祖先` |
| 对照：从主干开出、自己写了豁免的 B2，`--ref B2 --base <主干>` | `⊘` · `base 228f60b 里已有的 0 条不算` —— 普通 PR 一点没变 |
| HEAD 在 B 上、没有 `AGE_PR_BASE`（push 事件上没有 PR 的分支） | `⊘` · `没给 base(…)` |
| HEAD 在 B 上、`AGE_PR_BASE=<A 的头>` | `✗` |

## 仍然按不住的

三处，都在报告里点名那句理由写在哪个提交上，靠人看：

- **没有 base 的跑法**：本地跑、push 事件上没有开着 PR 的分支、`--all` 里没有 PR 的分支。
  报告明说这一路没收窄
- **叠分支对着主干开的 PR**：`gh pr create` 默认就对着主干。那时 base 是主干，下面那条的提交
  就是这条 PR 要合的内容，它的豁免跟着进来 —— 检查看到的和一条自己写了那些提交的分支
  没有区别。要挡这一种，得再拿一个事实：链上哪个提交是**别的开着的 PR 的头**（PR 清单里有
  `headRefOid`）。这次没接，记在这里
- **下面那条分支里带豁免的那个提交被改写过**（哪怕只 amend 一次）：新的 base 不再包含它，
  它留在链上

## 教训

第一版把「base 之后」写成「第一父链上碰到与 base 的分叉点就停」。评审举了一个最普通的形状：
叠上去之后下面那条又长了一个提交，上面那条把它合进来 —— GitHub 的 Update branch 按钮做的
就是这个。分叉点跑到第二父那边去了，链上碰不到，一刀不切，而报告还说「只认 base 之后」。

判据要按**语义**写（这个提交是不是 base 的祖先），不按**形状**写（链上有没有碰到某个点）。
形状是语义在一种提交图里的投影，换一种图它就不对了 —— 和 ADR-59 里「判据不在提交图里」
是同一件事的另一面。

另一条：欠条的价值在于**它写下了缺的是什么**（base 在调用方手里），于是这一次不必再论证，
只要接线。写不出「缺的是什么」的欠条，不是欠条，是免责声明。

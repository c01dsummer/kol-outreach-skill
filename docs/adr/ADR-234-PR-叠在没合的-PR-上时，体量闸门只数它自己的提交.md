# ADR-234 PR 叠在没合的 PR 上时，体量闸门只数它自己的提交

- 日期 · 2026-11-22
- 类型：不属于反向输入的五类 —— 改的是检查链自己
- 触发它的事实：体量闸门（一个 PR 新增行数的上限，超线要在提交信息里写 `size-ok:` 具名豁免）量的是「分支相对主干的全部新增行」。一条 PR 开在另一条还没合的 PR 上面时，下面那条的新增行算进这条，下面那条写的 `size-ok:` 豁免也被这条捡到。分支寿命闸门在 ADR-63（叠分支不再继承下面那条的豁免）修过一模一样的洞，体量闸门没跟着修。需求所有者 2026-11-15 在「要不要采用堆叠 PR」的选择卡上选了「暂不采用，但先补体量闸门这个洞」
- 冲击的需求：无
- 决定人与时间：需求所有者 2026-11-15 的选择（见上），做法照 ADR-63 的形状，不需要再选
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 理由：见第一节
- 连带改动：`scripts/check/size-rule.ts`（`resolveBaseline` 多一个可选参数、说明加第 7 步、`Baseline` 多一个可选的 `prBase`、新加 `prBaseFrom`）· `scripts/check/size.ts`（读环境变量 `SIZE_PR_BASE`，报告多一行说清用没用 base）· `.github/workflows/check.yml` 检查链那一步加 `SIZE_PR_BASE` · 新加 `.github/workflows/size-base.yml`（改 PR 信息时也重量） · `scripts/check/shard-load-rule.ts` 钉死的工作流跟着加几行 · `scripts/check/git-fixture.ts` 玩具仓库多认一个 `merge` · `scripts/test.ts` 体量闸门起点那组加第 7 步的假应答用例与一个真 git 玩具仓库 · `scripts/check/mutations.json` 新加 M-H234-a 到 q，M-H9-t 的锚点跟上新写法 · `process/6-INTEGRATE.md`「叠分支」两处说法改准 · `docs/ARCHITECTURE.md` 体量闸门两行 · ADR-145 一张欠条补状态行 · `docs/adr/README.md` 索引

## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 这条 PR 的 base 是哪条分支 | GitHub 的 pull_request 事件：`github.event.pull_request.base.ref`，CI 拼成 `origin/<分支名>` 经环境变量 `SIZE_PR_BASE` 交给闸门 | 机器 |
| 那条分支此刻的头是哪个提交 | git：`rev-parse --verify <origin/分支名>^{commit}`（CI 取完整历史，远端分支都在） | 机器 |
| 哪些提交已经在 base 里 | git：`rev-list <base 的头>..HEAD` 列出不在 base 里的；按主干列出的提交里，不在这一份里的就是 base 里已有的（按祖先关系，不按提交图的形状） | 机器 |
| 起点挪不挪 | git：`merge-base <base 的头> HEAD` 取与 base 的共同祖先，再问它与「与主干的共同祖先」的共同祖先是不是后者 | 机器 |
| 两个提交之间新增了多少行 | git：与原先同一组 `diff --numstat` 问法 | 机器 |

## 一、决定

照 ADR-63 的形状：**传事实、不传推断**。提交图分不出「叠上去」和「这些提交本来就是我写的」，分得出的事实只有「这条 PR 的 base 是谁」，而它只在调用方手里。

- 入口读环境变量 `SIZE_PR_BASE`，经 `prBaseFrom` 去掉首尾空白；没设、空串、全是空白都算「没给」，照旧按主干量。CI 上 pull_request 事件填 `origin/<base 分支名>`；推 main 的那一跑这个表达式落成空串；本地不设。
- 判定在 `resolveBaseline` 第 7 步，**只减不加**：给了 base、而且 HEAD 不在主干上时，这条分支自己的提交 = 第 6 步按主干列出的、又不在 `rev-list <base 的头>..HEAD` 里的那些；其余记成 `inherited`，报告里说「base 里已有的 N 个提交不算」，**N 是 0 也照说**。起点**只往后挪**：与主干的共同祖先是与 base 的共同祖先的祖先（叠在下面那条上）时，才改从后者量；否则不动。
- 给了 base 却找不到、与 HEAD 没有共同祖先、比两个起点答不上来、按 base 列提交答不上来 → 无从判断、退出 1，**不退回按主干量**：退回去，叠分支就又把下面那条的行数和豁免算成自己的。以 `-` 开头的不拿去问 git（那是开关，不是提交名），直接无从判断。
- base 就是主干那一头、或者是主干上更旧的一处时，量出来的数、找豁免的提交与没给 base 时一点不变。
- HEAD 在主干上时不用 base：主干上本来就只报数、不判定，报告说一句「给了 base，但 HEAD 就在主干上，没用它」。
- 起点挪没挪记在 `prBase.moved`。没挪时（这条与 base 的分叉点不在与主干的分叉点之后，比如叠着的这条直接合过更新的主干），base 里那几个提交的 `size-ok:` 照样不认，但它们的新增行照样数，报告照实说「多算、不少算」，不说「新增行不数」。
- **改 base 也要重量**：base 现在是判定的输入，而改 PR 的 base 不换 head、不触发 `check.yml`（第二轮独立复核指出：B 对着没合的 A 开、绿了，再把 base 改成主干，旧绿灯留在同一个 head 上，B 带着 A 的全部行数）。ADR-63 那次是给分支寿命闸门的工作流加改 PR 信息（`edited`）这种触发。这里另起一份 `size-base.yml`：开 PR、推新提交、重开、改 PR 信息都跑，只装依赖、跑体量闸门，按事件里此刻的 base 量；改标题也照跑、**不按「base 变没变」跳过** —— 跳过的任务在 PR 上算通过，会把同一个 head 上更早的红灯盖掉。检出 PR 的头而不是合并结果：改 base 时 GitHub 重算合并结果是异步的。没往 `check.yml` 加这种触发：那样改个标题就要重跑整条链。

**为什么传分支名、不传 `base.sha`**：第一版传的是事件里的 `base.sha`，并把起点直接换成与它的共同祖先。独立复核指出这会漏拦：`base.sha` 是开 PR（或上一次改 base）那一刻的快照，之后主干又合了别人带豁免的大改动、这条 PR 把主干合了进来，起点就被往回拉到旧主干头，别人的行数和那句 `size-ok:` 都算成这条的，超线的改动被放行。改成两处：传分支名（CI 每一跑取那条分支此刻的头），判定只减不加、起点只往后挪 —— 给的 base 再旧，最多是少减，不会多算别人的。

判据是祖先关系（git 列提交按的就是它），不是「链上碰到某个点就截」—— 那是 ADR-63 第一版栽过的：下面那条又长了一个提交、上面那条把它合进来之后，分叉点跑到第二父那边，按形状截一刀不切。

## 二、量出来的

真 git 玩具仓库（`scripts/test.ts` 体量闸门起点那组）：主干一个提交；A 从主干开出，加 400 行源码，提交信息最后一段写 `size-ok: 源码 A 首次落地，拆不开`；B 从 A 的头开出，加 10 行源码，没有豁免。

| 跑法 | 结果 |
|---|---|
| B 上，给 base = A 的头 | 源码 10 行；豁免一条也没捡到；base 里已有的 1 个提交不算 |
| B 上，不给 base | 源码 410 行；捡到 A 的豁免、放行 —— 这是没给 base 时明写的旧行为 |
| B 上，给 base = 主干 | 与不给时量出同一组数、同样的豁免 |
| A 又长了 100 行带豁免的一块，B 把 A 合进来，给 base = 分支 a | 源码 10 行；A 新长的那句豁免不算 B 的 |
| 同上，给的是 A 的旧头（开 PR 时的快照） | 源码 110 行 —— 明写的缺口（第三节），所以 CI 传分支名 |
| 再让 B 直接合更新的主干（A 仍没合），给 base = 分支 a | 源码 510 行（A 那 500 行照样数）、A 的豁免不认、`moved` 为假 —— 多拦不漏拦（第三节） |
| 另一条 P 从旧主干开出、加 360 行；主干后来合了 400 行带豁免的 M；P 把主干合进来；给 base = 旧主干头 | 源码 360 行、主干上那句豁免不算 P 的、超线拦下，与不给 base 量出同一组数（独立复核举的形状） |

假应答那一组另外钉住：base 找不到、没有共同祖先、比两个起点答不上来、按 base 列不出提交，四种都无从判断；以 `-` 开头的不拿去问 git；base 比主干那一头旧时起点不往回拉；HEAD 在主干上时根本不去解析 base；环境变量的空串、空白与首尾空白。十七条变异（M-H234-a 到 q：找不到 base 退回按主干量、没有共同祖先退回按主干量、豁免照旧从按主干列出的提交里找、行数照旧从与主干的共同祖先量起、「不算」的那几个一律报 0、主干上也去用 base、报告里的 base 写成共同祖先、叠分支被当成在主干上、「给的是哪个 base」写成解析出来的提交、起点直接换成与 base 的共同祖先、自己的提交改成按 base 列出的那些、以 `-` 开头的也去问 git、比两个起点答不上来照旧往下量、按 base 列不出提交当成没有提交、空串当成给了 base、不去首尾空白、起点没挪也报「新增行不数」）都被点名的那条断言抓到。

## 三、仍然按不住的

- **没给 base 的跑法**：本地跑（除非手设 `SIZE_PR_BASE`）、推主干。报告里明说「没给 PR 的 base，按主干量」。这是设计如此，不挂欠条。

> ⚠️ 欠条「叠分支对着主干开时体量闸门仍算下面那条」：叠上去却仍对着主干开的 PR，base 是主干，下面那条的提交就是这条要合的内容，它的行数和豁免照样算进来。要挡这一种得再拿一个事实（链上哪个提交是别的开着的 PR 的头），这次没接，同 ADR-63「仍然按不住的」第二条 · 还法：CI 多拿一份「开着的 PR 的头」清单交给判定 · 档：登记 · 重启条件：需求所有者改主意采用堆叠 PR 时；或第一次在真 PR 上见到这一种

> ⚠️ 欠条「给的 base 是旧快照时体量闸门少减」：给的 base 比那条分支此刻的头旧（手设成某个提交号、或哪天 CI 又改回传 `base.sha`），下面那条后来长的提交照样算进这条（玩具仓库里钉成 110 行）。只会多算、不会少算；CI 传分支名时碰不到 · 还法：无（传分支名就是还法），钉住它的断言防有人改回去 · 档：登记 · 重启条件：下一条改 `check.yml` 或 `size-base.yml` 里 `SIZE_PR_BASE` 那一行的改动

> ⚠️ 欠条「base 与 HEAD 同一处时体量闸门量出 0 行」：base 分支的头就是这条 PR 的头（同一个提交开了两条 PR，或下面那条把上面那条快进合了），这条自己的提交一个不剩，量出 0 行、不判红。比按主干量更松，但这时这条 PR 要合的内容确实已经在 base 里 · 还法：要不要把这种形状单独报出来，等真碰到再定 · 档：登记 · 重启条件：第一次在真 PR 上见到「base 里已有的 N 个提交不算」且自己的提交为 0

> ⚠️ 欠条「下面那条被压扁合入或改写后体量闸门认不出」：下面那条用 squash 合进主干后，上面那条若对着主干、却没把新主干合进来，它链上那几个原提交不在主干里，照旧算成自己的；下面那条被改写（rebase 后强推）、上面那条没跟时，上面那条带着的旧副本不在 base 里，那些旧提交的行数和 `size-ok:` 照旧算成自己的（第二轮独立复核在玩具仓库里跑出「已具名豁免」、放行）。都是改前就有的（按主干量也一样），本条没让它更糟 · 还法：上面那条把主干或新的下面那条合进来即可；闸门这边要认得出得拿改写前后的对应，git 给不了确切答案 · 档：登记 · 重启条件：下一条碰 `resolveBaseline` 的改动（重新起算）

> ⚠️ 欠条「叠着的这条直接合了更新的主干时体量闸门多拦」：B 叠在没合的 A 上、对着 A 开，B 直接合了更新的主干（A 没合），与 A 的分叉点不在与主干的分叉点之后，起点挪不了，A 的行数照样数（玩具仓库里 510 行、红），A 的豁免不认。多拦、不漏拦，报告照实说 · 还法：改从「主干与 base 合起来的那棵树」量起（`git merge-tree` 能给出，有冲突时另说），本条没接 · 档：登记 · 重启条件：第一次在真 PR 上被这一种挡住

> ⚠️ 欠条「改 base 重量那一份要设成必须通过才拦得住」：`size-base.yml` 红了只在 PR 上显示，要它真能拦住合入，需求所有者要在 main 的分支保护里把「体量闸门（按此刻的 base）」加成必须通过（这项设置不在仓库里，同「同一处连着两轮」那次）。没设之前，改 base 后变红的那一跑只是提醒。设上之后仍有三处缝（第三轮独立复核指出）：对改 base 之前那一跑点「重跑」，GitHub 用的是旧事件、按旧 base 再量一遍，可能盖住新红灯；改 base 后与新 base 有冲突时 GitHub 不起 PR 工作流，旧结果留着；从别人复刻的仓库开来的 PR，按提交号检出可能拉不到头提交而红（不漏） · 还法：需求所有者在设置里加上；前两处要在运行时现查这条 PR 此刻的 base，第三处改按 `refs/pull/<号>/head` 检出 · 档：登记 · 重启条件：需求所有者设上时收尾；或第一次有人改了 PR 的 base

> ⚠️ 欠条「体量闸门入口读没读 base 没有测试守着」：`size.ts` 入口本来就没有入口测试（判定都在 `size-rule.ts`）。环境变量怎么算「没给」挪进了 `prBaseFrom` 有单测与变异；入口拿到之后有没有交给判定、报告那几种说法（起点挪了、给了但没有一个提交已在 base 里、起点没挪、在主干上、没给）打的是哪一种，只有读 diff 的人看。CI 有没有把 base 传进来：`check.yml` 由变异负载闸门钉死的那份守着（`shard-load-rule.ts` 那份逐行比），`size-base.yml` 由体量闸门起点那组的两条断言守着（触发、传法、检出、不跳过） · 还法：给 `size.ts` 加一组真起入口的测试 · 档：登记 · 重启条件：下一条改 `size.ts` 的改动（重新起算）

> ⚠️ 欠条「同一个起点的另外几道检查没传 base」：欠条点名提醒、字段断言闸门、起子进程接口闸门、启动数闸门、外部工单号闸门也用 `resolveBaseline` 定起点，这次都没传 base。叠分支上它们会多算下面那条的改动 —— 多报、不会少报，所以没顺手改 · 还法：各自入口照 `size.ts` 读 `SIZE_PR_BASE`（到时可改个通用的名字）并在 CI 那几步传进来 · 档：登记 · 重启条件：需求所有者改主意采用堆叠 PR 时；或第一次有人在叠分支上被这几道多报挡住

## 四、给后来者的提醒

`process/6-INTEGRATE.md`「叠分支」那一段原先说「下面那条的新增行会算进这条、`size-ok:` 也会被捡到」，现在只在没给 base 或对着主干开时才这样，两处说法已改准。叠分支仍是这条纪律要劝退的东西：先把下面那条合了。

## 五、欠条清点

三个独立上下文按台账（868 条）分段按字面判过，本条上响了的：

- ADR-145「启动数闸门入口的映射与吞错没有变异」（下一条碰 `launches.ts` 或 `resolveBaseline` 的改动，重新起算）：响了，没还。本条只给 `resolveBaseline` 加了一个可选参数，`launches.ts` 不传、映射与吞错一行没动；还法仍是把映射挪进 `launch-rule.ts`，与体量闸门无关。在 ADR-145 原块下补了「已重挂」状态行，从本条合入起重数。
- ADR-89 第 92 行（加变异时看盖的是不是没人盖过）：核过，M-H234-a 到 q 全落在新写的第 7 步与 `prBaseFrom` 上，主干上没有变异盖它们；M-H9-t 只换锚点。
- ADR-99「开 PR 前核在途 PR」：每条 PR 都做的一步，结果写在 PR 正文。
- ADR-80 第 87–88 行（下一个碰 `size-rule.ts` 的人顺手看一眼 `size-ok:` 的数）：主干提交信息里按字面数约 277 处，最近合入的三条（报告缺值、复评经验、增强结果整份校验）都带豁免，远不到死亡条件「四周 20 跑为 0」；本条自己没写 `size-ok:`。CI 红史那一半这里看不到，没核。

拿不准、按窄读不响的：往入口脚本里加判定那一串（现行的是 ADR-232「入口判定仍在入口脚本里」）—— 窄读说的是产品那几个入口（ADR-197 第 96 行取过），本条改的是检查链入口；宽读那一半（`size.ts` 报告那三行只有读 diff 的人看）已挂成本条自己的欠条「体量闸门入口读没读 base 没有测试守着」，不另重挂。给检查链判定的返回值加新字段那一串（ADR-70、ADR-145、ADR-158，现行的是 ADR-198「新字段的变异改坏的是不是它的值没人核」）：`prBase` 的四个字段各有一条改坏它的值的变异（M-H234-e、g、i、q）且字段断言闸门绿，那张余下的是机器核不核，本条没碰它的判法。

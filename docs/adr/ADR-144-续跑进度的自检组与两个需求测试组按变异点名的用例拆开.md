# ADR-144 续跑进度的自检组与两个需求测试组按变异点名的用例拆开

- 日期 · 2026-10-12 · 核对 main 上 `npm run check` 时长又劣化时发现（#296 合入后 16:37，#300 合入后 23:04，#301 合入后 30:42）
- 类型：成本超预期
- 触发它的事实：取各次 main CI 变异一步末尾的配置成本行（「配置成本观测」）。#296 合入的 run 1702（数字转引 2026-10-12 的交接文档）、#300 合入的 [run 1709](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/38202852936)、#301 合入的 [run 1711](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/38218193816)：
  - 自检 `resume-progress` 这一种配置：变异 16 → 31 → 31 条，正常基线 28.2 → 71.7 → 94.4 秒，变异逐条合计 362 → 1283 → 1662 秒，三跑都占全部变异逐条合计的约三成；
  - 需求测试 `d19-resume`：变异 8 → 39 → 39 条，正常基线 0.8 → 6.8 → 8.5 秒，变异逐条合计 7 → 296 → 379 秒；
  - 需求测试 `d28-config-duplicates`（#301 新建）：15 条，正常基线 22.3 秒，变异逐条合计 323 秒。
  1711 那台 runner 比 1709 慢（两跑都没变的配置，耗时比的中位数约 1.27），所以 1709 → 1711 里旧配置跟着涨，这一跳里真新增的只有 `d28-config-duplicates`。
- 冲击的需求：无。断言判定、标签原文、失败文案、`mutations.json` 与每条的 `by/kills` 一个字不改；认领照旧只在完整运行时落下。另加一条阳性对照（见第一节），它不认领任何判据、没有变异指向它

- 理由：变异按 `kills` 自动选组（ADR-99）。自检变异在点名的断言都出结果后提前停，组里排在它前面的用例都要先付；需求测试选组从不提前停（`mutate.ts` 的 `stopIfSeen`），组里每多一次启动就乘以这组的变异条数。#294 到 #301 这条功能线每条 PR 都把新用例追加在同一组的末尾、把新变异指到整组，两个因子一起长。拆组不改任何判定，只改每条变异被迫多跑的那一段
- 连带改动：`scripts/check/selfcheck.ts`、`scripts/test.ts`；本记录及生成的索引。`process/` 与 `docs/ARCHITECTURE.md` 不列具体组名，本次不改

「付费启动」是这条变异点名的断言末次打印 ✓ 时，验证者进程已经直接起了多少个子进程（不含 git），在未施变的正常基线里数；数法见第三节。

**必须做对的几处：**

- **跨组读的结果都有 `needs` 边、写方都登记在前。** 由一组写、另一组读的模块变量只有这几个：`renderControlOk`（render-control 写，render-reject、dup-render 读）；`writebackHeld`、`renderKeptLegal`、`collectDup`、`renderDup`、`d27MainDone`、`d27MixedRan`、`d27BothRan`（各自那一组写，旧组名读）。原来是同一个函数里的局部变量，现在提到顶层；判定式一个字不改，`c.ok && c.status === 0` 换成读 `renderControlOk`，值相同。
- **夹具目录名保持唯一。** `d27Run` 原来用一个计数器给目录编号。拆开后每组各拿一个 `d27Runner(前缀)`：主循环的前缀是空串（目录名与拆前完全相同），mixed、twice、same-names 各是 `mixed-`、`twice-`、`same-`。不分前缀的话，各组各自从 1 数起，`costFixture` 撞名会静默复用目录，残留的 `armed.txt` 会让「预留观测已装上」在没有证据时成立。
- **`d27-mixed` 指向 `d27-entries`。** mixed 那一段不读主循环的对照结果，但它的判定含零预留、零请求，要以各入口的阳性对照先跑过为前提，道理同下面「阳性对照」一段。两组本来就在同一族里（旧组名把十五组连成一族），这条边不并族、不降拆进程的并行度；ADR-134 第二节说的假依赖是会把两族并成一族的那种。今天没有变异指向 mixed，代价为零；将来有了，它前面要先付 `d27-entries` 的 34 次。初稿写的是不加边，被独立复核纠正（第八节第 2 条）。
- **oracle 的提前返回只结束自己那一组。** writeback 的「普通 JSON 往返改掉了坏数字」与 dup-calibration 的内容哈希 oracle，原来坏了会把整组后面全部跳过；现在只跳过本组，失败数照样加一，认领照样落不下。d27-calibration 用的 `calSame` 只由那条 oracle 证，所以这一组开头另抄一份：`--only` 只点它时，dup-calibration 不跑。两份 oracle 都跑的那几种配置里，oracle 坏了会各打一行相同的 ✗，无害。

**阳性对照（新加的那一组）。** A、C 两段（D19.e、D19.f、D19.g 的 collect 一半）断言的是「零预留、零请求」，它们以「观测确实接上」为前提。拆组之前，这件事只靠同一进程里碰巧排在后面的 D19.l、D27 两段对照：观测坏了，整组的正常基线会红。拆开后，collect-bad、writeback 两种配置的正常基线里没有那两段，观测坏了也会是绿的。所以照 ADR-131「零事件类断言仍以阳性对照为前提」加一组，两组都 `needs` 它；它不过就以夹具记号失败，那一跑整个红。与 ADR-131 不同的是，依赖方不读它的结果：A、C 的判定式原来就不读任何对照，这次也不改。代价是这两种配置各多一次正常 collect 启动（约 1.5–2 秒），5 条变异各付一次。

### 需求测试 `d19-resume`（`test.ts`）

D27 × P3 的入口一侧（collect `--resume --budget 2` 与 enrich `--budget 2` 各一次阳性对照、各四种写重复，共 10 次 `spawnSync`）移进新组 `d27-p3-entry`，登记在 `d19-resume` 之后。这 10 次启动是 `d19-resume` 里唯一起子进程的地方，39 条变异里只有 M-D27-h 点名它的断言；M-D27-h 另点名一条库层断言，留在 `d19-resume`，所以它自动落到 `d19-resume, d27-p3-entry` 两组的配置。两组共用的 `LEDGER`、`costText`、`P3` 提到顶层（只读，只改缩进）。`d27-p3-entry` needs `d19-resume`：「费用字段写重复夹具有效」（P3 那几份读回来确实是最后一处的值）留在 `d19-resume`，入口以 2 退出要以它为前提，不然拒绝可能是因为最后一处本身不合规。`d19-resume` 不起子进程，这条边不加启动；M-D27-h 本来就两组都跑，`d19-resume` 的 38 条路由不受影响（边是单向的）。初稿没有这条边（第八节第 3 条）。

# ADR-48 两个新函数，各自重犯了一条隔壁函数早就记过的教训

- 日期 · 2026-08-28 · PR #5 拆分后第十三轮自动评审，两条都成立
- 类型：**事实证伪**（两条打的都是**上一轮刚加的代码**）
- 冲击的需求：P4 · D4
- 结论：**采纳**

### 一、`onDisk` 把「读不到」当成了「没有」

```ts
function onDisk(): string {
  try { return readFileSync(FILE, 'utf8') } catch { return ABSENT }
}
```

一行 `catch` 吞掉全部读失败。于是记忆文件在读与比对之间变得读不到时
（运营刚建了一个权限收紧的文件），比对拿「看不到」当「没有」放行，
改名把一份**从没读到过**的记忆盖掉，里面的 contacted 与 blocked 跟着消失。

**这正是 ADR-26 在 `readMemory` 里修过的那个塌陷** —— 它就在同一个文件、
隔几十行的地方，而我写这个新函数时一个字都没想起来。

### 二、`fsync` 把文件的刷盘失败也吞了

上一轮我为「刷不动目录」写了一个吞异常的 `fsync`，**它同时被用来刷文件**。
于是磁盘满、IO 错这类**恰恰在刷盘那一刻才浮出来**的失败被吞掉，改名照做，
成功照报 —— 把这个函数存在的理由整个抵消掉。

拆成两个：`fsyncFile` 抛，`fsyncDirBestEffort` 吞。**能吞的只有目录那一个。**

### 修法都是「让判断只有一份」

第一条抽出 `isAbsence(e)`，`readMemory` 与 `onDisk` 共用 —— 因为
**上一次出事（ADR-46）正是同一个判断有两份副本、只修好了一份**。
合并之后，原先守 `readMemory` 那条 `M-P4-i` 与新加的那条指向了同一行，
又是一次「两条变异在重复守一件事」，合并成一条。

第二条不是合并而是**拆分**：原先一个函数吞两种失败，而这两种失败该不该吞
是相反的。**该合的合、该拆的拆，判据都是「它们是不是同一件事」。**

### 教训

**「隔壁函数刚记过的教训」不会自动作用到我下一个函数上。**

到这一轮为止，同一个形状出现了三次：ADR-42（权限收得太晚）、
ADR-46（新写的原子写没带上权限处理）、本条（新写的两个函数各犯一条旧账）。
三次都是**新代码重犯旧教训**，而不是旧代码没修好。

写下教训防不住这件事 —— 教训在决策记录里，而我写新函数时看的是代码。
唯一有效的是**让那个判断只存在一份**：一份的时候，新调用方自动继承它；
两份的时候，继承靠的是我记得，而我不记得。

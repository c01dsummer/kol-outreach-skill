- 冲击的需求:无编号需求。冲击的是**记录本身的可信度**

## 触发它的事实

`bc64d93` 的提交信息里写着：

> 同一份文件往上 **32 行**的小节标题逐字就是「第四步：结论只有三种，都要落纸」

真实距离是 **49 行**。改之前那棵树上，`## 第四步` 在 152 行，我那句在 201 行：

```
git show 604925d:process/2-CHANGE.md \
  | awk '/^## 第四步/{a=NR} /结论是采纳还是驳回/{b=NR} END{print a, b, b-a}'
→ 152 201 49
```

那个 32 没有任何来源 —— 我没有数，是看着像。

## 难看的地方不在偏了 17 行

那条提交的标题逐字是《**在一份写着「结论只有三种」的文件里，我把结论写成了两种**》，
整条提交的主旨就是「写下一个数的时候，没去核紧挨着它的那份正本」。

**它自己就带着一个没核过的数，而且那个数指的正是那份正本在哪。**

同一个错误还被复述了两遍：#114 的评审线程里一遍，跟人的对话里一遍。三处都写 32。

## 同一形状这一轮出现过几次

六条都是**列举或计数**，六条都有一份正本躺在**够得着的地方**，六条都没去够。

## 为什么已有的规矩没拦住

这一轮中途给自己定过一条：「记录里出现的每个**数**，旁边必须带上产出它的那条命令」。
它没拦住上面第四条和第五条 —— **「采纳还是驳回」看着不像一个数，「32 行之上」看着像个修饰语**。

规矩定在「数」上，漏掉的是**形状**：凡是列举（清单、枚举、「A 还是 B」、「N 处／N 种／N 类」、
一个指向别处的行号），都是清单；凡是清单，就得回去数那份正本。

## 教训

**一条讲判据的记录，最容易在自己身上破那条判据** —— 因为写它的时候，注意力全在被讲的那件事上。
所以判据落纸那一刻，要拿它先量一遍**这条记录自己**。

本条就是这么被逮到的：#114 合入后的清点拿「凡是列举就回去数正本」去量这一轮的产出，
第一个撞上的是写这条规矩的那条提交。

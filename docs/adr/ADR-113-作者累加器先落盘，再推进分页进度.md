# ADR-113 作者累加器先落盘，再推进分页进度

- 日期 · 2026-09-24 · 设计 IG 翻页时读 `collect.ts` 的 `persist()` 撞见（ADR-111 第一节第 3 条）
- 类型：**既有缺陷**；修不修由需求所有者 2026-09-24 裁决：单独一条 PR 修
- 触发它的事实：`persist()` 先写 `task.json`（分页进度 offsets、pages、done，以及 answered、found），
  再写作者累加器 `creators.raw.json`。两次写之间进程被打断、或第二次写失败时，盘上的进度已经前进而这一页的作者没有保存：
  TikTok 续跑从下一页接着翻，这一页被跳过；IG 首页与 `done` 在同一次写里，丢的是这个任务唯一的一页，续跑不再碰它
- 冲击的需求：D6（新增 D6.t）
- 结论：**采纳。** 对调顺序：先写作者累加器，再写 `task.json`

## 代价，写明

- 两次写之间被打断时，续跑在预算允许时会**重新请求这一页**，预算不足时照 P3 停下；重抓实际发出的每一次请求都由费用账如实记录
  （IG 首页走账号名兜底时是两次；费用终态在 `persist()` 之前已由检查点保存）；
  这一页的 answered、found 停在更早的断点，被重抓的那一次不计入。这落在 ADR-109「保留的边界」原文之内
  （「页数、answered 与 found 等业务进度可能停在更早断点……不保证任意强杀后绝不重复请求」），不另立新边界。
- 累加器保存失败时（盘满、只读、IO 错），这一页的分页进度不落盘，本次运行以错误退出；续跑同样重抓这一页。
- 同一个作者被重抓一次时按现有合并规则入库（D11、D15），不会变成两个人。
- 不承诺主机断电的持久性，不承诺多写者 —— 同 ADR-109、D4。

## 验证

自检用预加载只拦截对 `creators.raw.json` 的最终改名写入、使它失败，断言：这次运行以错误退出、恰好发出一次搜索请求，
而 `task.json` 里这个任务的 offsets、pages、done 都没有前进。对调回原顺序的变异由这条自检抓到。

# ADR-147 bio 里有几个邮箱就列出几个：不替人挑，合并同人时两边都留

- 日期 · 2026-10-12 · 需求挖掘「在 Codex 里经 Zoho 发开发信」第 8 节第 1 条顺手发现。需求所有者 2026-10-12 在决定卡上选了「全部列出」
- 类型：产品取舍（几种取法都不违反 D7 原文，选哪种决定交付表上看到什么），需求所有者已拍板
- 触发它的事实：邮箱提取在 bio 里找到第一个合规地址就返回。`'biz: agency@mgmt.com / personal: jane@gmail.com'` 交付表里只有 `agency@mgmt.com`，个人邮箱一字不见；跨平台同人合并时，主记录有邮箱就整个丢掉另一个平台 bio 里的邮箱。两处都是在替人挑，而挑掉的那个常常正是该联系的
- 冲击的需求：D7（新增 D7.d）；P1.a 不变（三态照旧，只是「有值」那一态可以装几个地址）
- 结论：采纳。几个邮箱列几个：按在 bio 里出现的先后、地址写成小写、同一地址只列一次，用 `, ` 连成 `email` 的一个值；跨平台同人合并时两边的邮箱都留下，主记录的在前、去掉重复
- 连带改动：`scripts/lib/email.ts`（提取全部、按位置排序、去重）、`scripts/lib/identity.ts`（合并取并集）、`scripts/lib/types.ts` 字段注释、`docs/requirements.json` D7.d 与 `docs/SPEC.md`、`docs/ARCHITECTURE.md` 锚点表两行、`skill/references/output-format.md` 的 `email` 列、`skill/references/providers/_interface.md` 字段注释；测试 `d7-email` 组；变异 M-D7-d 至 M-D7-i

## 一、为什么连成一个值，不改成数组

`email` 是落盘字段：`creators.raw.json`、`creators.json`、续跑的目录里都存着字符串。改成数组，旧目录读回来要么类型不对，要么得写一层迁移；而续跑与重新渲染恰恰是会读旧目录的。连成一个字符串，旧目录照样读，下游判「有没有邮箱」的地方（评分 +30、A 层、同人取主、`email_count`）全是判真值，一处不用改。

代价是下游想按地址逐个处理时要按 `, ` 拆开（`EMAIL_SEP`）。今天没有这样的下游；以后接发信或邮箱验证时再看要不要拆成数组。

## 二、逐条评定

1. **触碰红线吗？** 不碰。P1.a 的三态不变：未查询仍是 `undefined`，查过没有仍是 `null`；合并时一边未查询、另一边没有邮箱，结果仍是未查询。
2. **缩范围还是降标准？** 都不是，是多给：原先丢掉的地址现在列出来。
3. **覆盖还是可信？** 覆盖变多。每个地址照旧未经验证（P5.f 的声明不变）。
4. **可逆吗？** 可逆：交付物是每次渲染出来的，退回只取第一个就是改回两处代码。

## 三、测试与变异

1. **测试先于实现、由另一个上下文写成**：只读需求原文、类型与测试文件，不读 `email.ts`、`identity.ts` 的函数体。主记录是谁不由 D7.d 规定，合并的用例按合并结果里的主记录推出期望顺序。
2. **对着未改的实现看红**：十五条里九条红（几个地址只出一个、合并只留主记录的）；绿着的六条是只有一个邮箱、大小写不同的同一地址（原来本就只出一个），以及合并时有一边未查询或没有邮箱的四条三态用例 —— 断的是现状本来就对的那一半。之后又补了一条「拼写写法在前、符号写法在后」，因为两条模式分开扫，不按位置排序的话拼写写法总排在后面，原来那几条用例守不住这一点。
3. **变异 M-D7-d 至 M-D7-i，六条，都是 `by: test`**：只取第一个、不按出现先后排、不去重、合并只留主记录、合并不去重、合并时另一边排前。每一条都手工施加过，点名的断言全在红的里面。

## 四、教训

「找到一个就返回」在提取函数里很自然，但它在替人做选择。凡是从自由文本里提取联系方式，先问一句：有好几个的时候，挑哪个是不是人的判断？

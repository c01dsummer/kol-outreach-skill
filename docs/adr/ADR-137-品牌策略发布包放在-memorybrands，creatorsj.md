# ADR-137 品牌策略发布包放在 memory/brands/，creators.json 仍是唯一的创作者记忆

- 日期 · 2026-10-09 · 语义复评批次 A 开工前的设计审计（批次 A 的范围见 ADR-135）
- 类型：**产品取舍**（需求所有者 2026-10-09 在本次任务中采纳修订后的设计并按暂定方案开工）
- 触发它的事实：批次 A 要跨任务保存品牌策略发布包（ADR-135 第二节）。现行决定只有单文件的创作者记忆：
  决定表第 2 条「本地 JSON，单文件 `memory/creators.json`。不做多人共享」（`docs/business-requirements.md:380`），
  `skill/references/memory.md:13` 写的是同一个决定，目录表的 `memory/` 一行也只列了 `memory/creators.json`（`docs/ARCHITECTURE.md:53`）。
  `output/` 下是 collect 一次建一个的任务目录 `output/<产品>-<时间戳>/`（`docs/ARCHITECTURE.md:52`）；
  发布包要被以后的任务按 `policy_ref` 引用，建它的那个任务目录删掉之后也必须仍可读
- 冲击的需求：D4（不变：创作者记忆仍是 `memory/creators.json`，D4.a 原样）；`docs/business-requirements.md` 决定表第 2 条的含义收窄为「创作者记忆」；品牌发布与激活的新需求见 ADR-135 第三节
- 结论：采纳。本条不改代码、目录与需求登记表；目录随 ADR-135 施工顺序第 3、4 步的实现 PR 落地（第 3 步 `staging/`、`authorizations/`，第 4 步其余）
- 理由：不碰红线；不缩范围、不降标准；补的是可信（任务目录删掉后，已绑定的发布包仍可读）；落盘位置不易逆，所以由需求所有者定。逐条见第三节
- 连带改动：本记录；`docs/adr/README.md` 索引（`npm run adr -- --write`）。目录表、Skill 与业务文档的同步在实现 PR 里做，清单见第五节

## 一、决定

下文的 D27–D31 是 ADR-135 第三节的需求草案编号，尚未登记。

1. **新增 `memory/brands/<brand-id>/`，一个品牌一个目录。** 布局如下（`qualifications/` 只预留名字）：
   - `releases/<policy-hash>/`：一版发布包，发布后不可变（D29.a）。内含 `policy.json`（策略内容）、`manifest.json`（文件清单与来源闭包）、
     规则实际引用的最小摘录（D29.b）、被采用的提案与验证记录、案例。
     目录名只取 64 位十六进制，不带 `sha256:` 前缀（冒号在 Windows 上不能作文件名）；JSON 内仍写完整的 `policy_hash`。
   - `registry/`：发布、激活、退役事件，一个事件一个文件，写下不改。
   - `current.json`：按范围保存的默认指针（D29.e），新任务从这里解析（D29.g）；原子整体替换（中途打断时要么是旧的、要么是新的，同 D4.i 的口径），先写事件再替换指针。
   - `authorizations/`：品牌级授权记录（D28.e）。不放进任务目录，删任务目录不连带删授权。
     发布只接受 `staging/` 里按品牌级授权签发的验证记录；在任务目录里、按任务级授权签发的验证须先在 `staging/` 重新验证 ——
     任务级授权随任务目录保存，删任务目录会断开发布包的闭包（与 D29.b 不读 `output/` 同理）。
   - `staging/`：发布前的品牌级原件、提案与验证（D27、D28）；没有发布的不生效。
   - `qualifications/`：归纳规则的资格记录，留给批次 C。批次 A 的发布包不收归纳规则（D29.h）；开放时机见 ADR-135 第一节 Q4。
2. **brand_id 规则。** 小写字母开头，只含小写字母、数字和连字符，最长 63 位；
   另拒绝 Windows 的保留设备名 `con`、`prn`、`aux`、`nul`、`com1`–`com9`、`lpt1`–`lpt9`。
   它直接作目录名；只用小写，是为了两个只差大小写的品牌不会在不分大小写的文件系统上落进同一个目录。
   不合规就拒绝，不替运营转小写、删字符或截断；任务的品牌一项缺席时，不按名称相近补出品牌（ADR-135 D29 × P1）。
3. **只存品牌资料与派生摘录。** 供应商接口的响应原件不进品牌目录，仍只放 `output/<名字>/`（`docs/ARCHITECTURE.md:64` 规矩 2）；
   保存品牌原件时，从本地导入 `output/` 下的文件一律拒绝（D27.a）；发布只从 D27 的原件库复制摘录，不读 `output/`（D29.b）。
4. **creators.json 仍是唯一的创作者记忆。** 它的路径、结构与 D4 的全部判据不变。品牌目录不保存任何创作者的推荐、联系或屏蔽状态；
   案例只作 Agent 可读的示例。已联系去重（P4）照旧只读 `memory/creators.json`。
5. **单机、单人。** 不做多人共享（同决定表第 2 条）。`memory/` 已被 `.gitignore:9` 忽略，也已在变异 worker 不复制的 `SKIP` 里
   （`scripts/check/jobs-rule.ts:255`），实现 PR 不用改这两处。品牌目录不进仓库，也没有备份保证。
6. **不加锁。** 品牌发布与激活由运营串行执行，并发写入不保证，与 D4、ADR-66 同口径；理由见 ADR-135 第二节「批次 A 不加锁」一段；要变成保证，按该段与 D29 主句另开 ADR 引入锁。

**判据草案。** 下面三条在 ADR-135 第三节的 D29、D30 里没有对应判据，随实现 PR 登记（字母按登记时的空号）：

- （i）brand_id 须匹配 `^[a-z][a-z0-9-]{0,62}$`，且不是第 2 条列的保留设备名；不合规时，在写品牌目录之前以退出码 2 拒绝并指出字段，
  不转小写、不删字符、不截断。D30.a 引的 brand_id 格式即此条。随第 3 步（首次写品牌目录，D27、D28 的品牌级入口）登记。
- （ii）发布包、注册事件、默认指针与品牌级授权都存于 `memory/brands/<brand_id>/`；删掉任一任务目录后，
  已发布的发布包仍可按 `policy_ref` 解析，并通过内容哈希核对。随第 4 步（D29）登记。
- （iii）默认指针原子整体替换，先写事件后替换。随第 4 步（D29）登记。

## 二、为什么是 memory/，不是 output/，也不是仓库

- **不放进建它的任务目录。** `output/<产品>-<时间戳>/` 只属于一个任务（`docs/ARCHITECTURE.md:52`）。发布包放在那里，
  运营删掉那个任务目录，别的任务的 `policy_ref` 就指向不存在的东西。
- **不另开 `output/<名字>/`。** 规矩 2（`docs/ARCHITECTURE.md:64`）说运行时产生的东西一律放 `output/<名字>/`，
  列的是接口响应原件、诊断快照、价目快照、日志 —— 一次运行留下的证据，没有哪个流程按默认指针回头去读。
  跨任务、默认要回头读的状态今天已有例外 `memory/creators.json`（`:53`）；发布包是以后的新任务默认要读的跨任务状态，与它同一类，
  规矩 2 的字句在实现 PR 里补（第五节）。供应商原件照旧守规矩 2（第一节第 3 条）。
- **不进仓库。** 品牌资料是运营的业务资料，含产品页摘录与品牌偏好；仓库只放 Skill、代码与文档。
  通用基线是仓库里受控的 Skill 指令，不在 `memory/brands/` 下（D29.g）。
- **不算新建顶层目录。** 规矩 1（`docs/ARCHITECTURE.md:61`）管的是顶层目录与 `docs/` 下的子目录，`memory/brands/` 是已有顶层目录下的子目录。
  但 `memory/` 一行的「装什么」变了，目录表要在实现 PR 里改（`docs/ARCHITECTURE.md:66` 规矩 3：改目录结构靠 `docs/SYNC.md:30` 那一行提醒，本条按同类处理，清单见第五节）。

## 三、理由（四条判据依次问）

1. **触碰红线吗？** 不碰。P1：brand_id 不合规就拒绝，不转写、不按名称相近合并（第一节第 2 条）。
   P2：发布包里的产品事实只说明运营确认过出处，草稿仍以产品页出处为准（ADR-135 D29 × P2）。
   P3：只是本地文件，不新增付费请求。P4：去重仍只读 `memory/creators.json`（第一节第 4 条）。
   P5：发布包读不到时停下汇报，不在交付里装作用过品牌策略（本节第 4 条）。
2. **缩范围还是降标准？** 都不是。多了一处存储，没有放宽任何现有校验；保留期与清理没定就不做（第四节），不默认一个期限。
3. **覆盖还是可信？** 可信。发布包脱离单个任务目录，任务目录删掉后，已绑定的版本仍可读、可核对内容哈希。
4. **可逆吗？** 不易逆。运营积累了发布包、任务写下了 `policy_ref` 之后，换位置就要迁移；
   把品牌目录删掉，已绑定的任务还留着各自 `task.json` 里的 `brand_calibration`，但读不到发布包里的其余内容（`memory/creators.json` 不受影响）；
   读不到所指发布包时，该任务停下汇报，不得不带品牌准则照常评审、交付。
   不可逆是三个必须问人的条件之一（`process/2-CHANGE.md:108` 起「第三步」那一节），所以这一处由需求所有者 2026-10-09 定，不由实现者选。

## 四、没定的

批次 A 不做自动清理，也不提供删除命令。手删 `memory/brands/` 下的文件没有任何保证；
当前指针所指的内容缺了或对不上时，新任务按 D29.g 的「指针坏」拒绝自动套用。
`current.json` 或整个品牌目录被删掉时，新任务解析只读 `current.json`，与从未激活过的品牌看起来一样，按 D29.g 走通用基线；这属于手删没有保证的一部分，不算指针坏。
品牌锁及其恢复记录不在批次 A；要引入，按 ADR-135 第二节「批次 A 不加锁」一段与 D29 主句另开 ADR，逐条回应 ADR-39、ADR-44、ADR-47。删除后的占位做法随下面的欠条。

> ⚠️ 欠条：品牌存储的保留期、删除合规（含案例里的个人资料）、归档介质与删除后的占位做法未定，批次 A 不做自动清理 · 重启条件：保留期或删除合规参数由业务确定时

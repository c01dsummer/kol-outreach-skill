# ADR-56 一个只写在注释里的契约，只兑现了一半

- 日期 · 2026-08-31 · 外部评审（缺陷属实，**它给的后果不成立**）
- 类型：**事实证伪**
- 冲击的需求：D4
- 结论：**采纳缺陷，不采纳修法的理由，也不采纳它描述的后果**

### 事实

`recordRecommendations` 的契约是**绝不抛**。这句话不在签名里，在它自己
catch 块的注释里：「这一步跑在报告之前，让它抛会把已经算好的名单连同报告
一起丢掉」。D4 也写着同一件事：写回失败「报为未写回并照常完成交付，
**不得中断产出**」。

而它只包住了**落盘**那一条路。生成键之前的那道校验 `keyProblem`
第一句就是 `platform.toLowerCase()` —— 手改过的 `creators.json` 里
`handle: null` 或数字 platform，校验自己先抛。实跑复现：

```
{"platform":"tiktok","handle":null} → TypeError: Cannot read properties of null
{"platform":7,"handle":"zed"}       → TypeError: platform.toLowerCase is not a function
```

**评审说的后果不成立。** 它说交付物因此产不出来 —— 我拿真实的手改文件跑了
`render`，两种取值都死在 `identity.ts`（`render.ts:32`），比写回
（`render.ts:81`）早了 49 行。只修这一处，它描述的场景一个字都不会变。

所以真正成立的是另一句：**这个函数今天违反了 D4 明写的一条**，
只是暂时被上游一个更早的崩溃挡着，看不出来。

### 修法

`keyProblem` 改收 `unknown`，先用 `textProblem`（types.ts 里那一份判据）
确认两个值是文字，再往下走。**没有**顺手去修 `identity.ts` 或给
`loadCreators` 加运行时校验 —— 那是另一件事，范围也大得多。

### 为什么没有像上一轮那样「先记在待办里」

第一版回复写的是「记在待办里，和 `creators.json` 的运行时校验一起提」。
那是错的，理由很简单：**这一处在本改动自己的文件里，几行就修得干净，
而且修完那句写在注释里的契约才第一次为真。**

「今天不可达」不是把一条已知的需求违反留在盘上的理由。不可达是**上游一个
bug 的副作用**，而上游那个 bug 迟早会被修 —— 到那天，这一处就直接可达了，
而没有任何人会记得回来看它。

### 教训

**契约写在注释里，就只会兑现在写注释的那个人当时看着的那条路上。**

这个函数的作者（我）知道「绝不抛」，所以在落盘那里写了 try/catch。
同一个函数里另一条会抛的路，隔了三十行，就没被想起来 ——
不是因为难，是因为**注释不会去数还有几条路**。

和 ADR-46 追记二是同一件事的两种形态：那次是「判据只守住了一部分路径」，
这次是「契约只兑现在一部分路径」。判据可以抽成函数让调用点数得清，
而契约要变成结构上的保证，得让**函数没有别的出口** ——
要么把整个函数体包起来，要么把每一处可能抛的调用都换成返回值。
这次选了后者，因为它同时把错误原因带给了用户。

**另外：评审提的「缺陷」和它推的「后果」要分开评定。** 这一条的缺陷是真的，
后果是假的。只看后果会把它整条驳掉，只看缺陷会照着一个错的理由去改
——两次都会错。

## 一、按条数分配不平秒数

ADR-200 按条数分：主干 `d153df5` 上 2,179 条变异（自检 339、需求测试 1,840）三份各 726～727 条。可一条变异的代价差得很多。取主干最近 5 跑（run 43599870587、43602914312、43606643519、43611515154、43677636843）三份变异 job 日志里的成本报告（`MUTATION_COST_JSON` 那一行，每种配置的基线与各条变异实测毫秒）：

- 自检一条变异平均约 7.9 验证者秒，需求测试一条约 1.5 秒；一种配置跑一次正常基线，自检的中位约 7.6 秒，需求测试的中位不到 1 秒；最慢的几种自检配置一次基线三四十秒。
- 三份条数一样，变异那一步的墙钟却差得多：`92ef770` 那一跑三份是 516、426、223 秒。

## 二、量什么、怎么分

**一种配置的秒数 = 一次正常基线 + 条数 × 一条的秒数**，两个数都取自树内的 `scripts/check/shard-weights.json`。那份文件由 `npm run shard-weights -- <日志>…` 从 CI 日志里的成本报告算出来：同一个 headSha 的几份报告算一跑，每种配置每跑的基线秒数与一条的平均秒数，取各跑的中位数（偶数跑取较小的那个），两位小数；文件里没有的配置（新加或改了名的组）按验证者取默认值（基线取各配置的中位数，一条取全部毫秒 ÷ 全部样本）；闸门每跑报出有几条落在默认值上。**整跑的变异**（没有点名断言、每一条都要把整个验证者跑一遍）每一条按那个验证者各配置的基线之和算（需求测试约 320 秒、自检约 610 秒），不按一条的平均算 —— 它们是最贵的一种，称轻了涨幅与上限两道就静默放行（第二轮复核 B3）；树上现在没有整跑的。这一版取自上面那 5 跑，206 种配置；同一份报告传两遍只收一次，同一个提交重跑的两次尝试分不开，不要一起传。

先试过的是「自检一条算 6、需求测试一条算 1」的估重。复核发现原稿那张回放表用的不是这个比例，拿真的 `shardPlan` 重放（5 跑各自的实测秒数不变，只换分法；回放脚本没进仓库，第二轮复核用 `weightsFromReports` 另写一份重放，各格差在 1 个点内）：

| 分法 | 5 跑里最重一份比平均高 |
|---|---|
| 按条数（ADR-200） | 10%～33% |
| 估重 自检 6、需求测试 1 | 11%～27% |
| **每种配置的实测秒数（取前一跑的）** | **3%～7%** |
| 每种配置的实测秒数（取另外 4 跑的中位数） | 2%～8% |

估重分不平，是因为一摞的代价大半在那一次基线和这一组的用例多慢，不在条数。需求所有者 06:06Z 选了秒数文件。

**用文件里的数，不用这一跑的秒数**：秒数随 runner 型号与并发变（同一份代码在不同 runner 上差到 ×1.6，ADR-145 第三十一节），拿它判红，同一个提交重跑就可能换结论；文件进了仓库，同一棵树永远算出同一个数。文件旧了，只影响分得平不平、估得准不准，不影响哪条变异被抓到。

分法照 ADR-200，只把「条数」换成「这一摞的秒数」：同配置成摞，摞按秒数从重到轻发给眼下最轻的那一份（`shardPlan`）。变异一步与闸门共用 `shardKey`、`shardPlan`、`pileWeigher` 与同一份文件，闸门量的就是变异一步实际的分法。只跑一份（本地）时不读这个文件。

**秒数折墙钟：× 0.19**。一份里验证者秒数合计与那一份变异一步的墙钟之比，5 跑 15 份实测 0.180～0.191（6 个 worker 跑在 4 核上，几个验证者同时跑）。

## 三、三道线

需求所有者 05:41Z 选的（选择卡原文：最重一份超平均 25% 红；一个 PR 让变异总量涨超 5% 红，提交信息写理由可豁免；最重一份预计超 14 分钟红，无豁免）。06:06Z 改了量法，线没改：

1. **三份均衡**：最重一份比平均高过 25% 就红，不设豁免。判的是三份各自的总秒数，不是哪一摞够不够重：一摞接近平均值（三份总量的三分之一）时最容易越线，但几摞差不多重、摞数又不凑巧时也会（例如七摞 5、5、5、4、4、4、4 按「重的先放、放进最轻那份」分成 13、9、9，最重一份比平均高约 26%）。改法是把重的那组用例拆成两组，或删重复的变异。
2. **一次涨幅**：一个 PR 让总秒数比 PR 基线涨过 5% 就红。基线与体量闸门同一个（`resolveBaseline`：PR 上是合并用的主干头，主干上是上一版）；基线那份清单与它那时的源码，按**这棵树的**秒数文件算，量的是变异变了多少，不是秒数文件换了多少。可在这条分支自己的提交信息末段写 `mutation-growth-ok: <理由>` 豁免（只认 trailer 块，见 `trailer.ts`；键用 ASCII，因为 trailer 的键只认 `[\w.-]`）。最近 45 个主干提交按条数涨得最多的一次 +2.8%（#483，2,110 → 2,170 条），十月 #360 一次加 91 条按条数约 +6%；按秒数要看加的是哪几组，自检的一条顶需求测试的五条。
3. **上限**：最重一份预计超过 14 分钟就红，不设豁免。折算：14 × 60 ÷ 0.19 ≈ **4,421 验证者秒**。`87830f0` 那棵树上 `npm run shard-load` 报三份约各 2,152 秒，约 6.8 分钟。这一道守的是一次涨一点、涨很多次：十月（16 → 24 分钟）和这一周都是这么涨的，跟上一次比永远过不了第 2 道线。到线时要么删变异，要么由需求所有者决定加一台 runner（改 `SHARD_COUNT` 与 `check.yml`）。

PR 上越线就红；**主干上只报数**，同体量闸门与启动数闸门：CI 跑在推送之后，主干上判红只会让主干变红。问不出在不在主干上、接线对不上（第四节，下一条 PR 接上）、秒数文件认不得是数据错，主干上也红；PR 基线那份清单读不出来，PR 上红，不当成没涨。

每跑都先打一行报数：每份秒数、最重一份比平均高多少、预计几分钟、总秒数与比基线涨了多少。

要放的位置是检查链第三步、紧跟体量闸门：两道都只看这次改了什么，不起验证者，几秒钟。本地 `npm run check` 越线时后面那半小时不白跑；CI 上变异那几份不等 `chain`，省不了时间，只是红得早。**入口分两条 PR 接**：评审里第四节的接线核对一连几轮出同类的洞，照 `process/6-INTEGRATE.md`「闸门自身走最后一块砖」，需求所有者 2026-11-15 09:40Z 在选择卡上选「拆入口，新设计另开 PR」—— 第一条 PR 只合判定、入口脚本、测试、变异与按秒数分份；入口连同重新设计的接线核对由第二条 PR 接进检查链。

## 四、接线核对

`check.yml` 里有几处与代码对不上不会红（ADR-200 第 92 行那张欠条）：份数（矩阵、`MUTATE_SHARD`、上传的启动数文件名）、`chain` 那一串与 `package.json` 的 `check`、变异那一步的 `MUTATE_JOBS: '6'`，还有让变异那几份或检查链不跑、跑红了也不算红的写法。由闸门入口一起核（`workflowWiringFaults`），对不上就红，主干上也红。

- **前两版都是从文字猜 YAML 的结构，都被找出洞。** 第一版逐行找几行关键的字、再猜它落在哪个 job，CodeRabbit 三轮各找到一种写法让它猜错（`exclude:` 认到别的 job 的矩阵、两行一起挪到另一步、前面别的 job 写了同样的行）。第二版改成「几行记号整份里各恰好一次、紧挨着写、只报数的步骤以外不许 `if:`／`continue-on-error:`」，独立评审又找到六类 GitHub 认的写法让它放行：引号括起来的键、接到下一行写的命令、紧贴命令的 `#`、块里放一段假的记号、流式写法、判 `CHAIN` 与 `MUTATE` 那句之前先 `exit 0`。猜错时都是悄悄放行。
- **现在整份钉死**（需求所有者 2026-11-15 18:42Z 在选择卡上选的）：`check.yml` 去掉整行注释与空行之后，逐行、逐字（行尾空白也算）与 `shard-load-rule.ts` 里钉死的那份（`WORKFLOW_PIN`）相同；份数、worker 数与 chain 那一串不写死，按 `SHARD_COUNT`、`CI_MUTATE_JOBS` 与 `package.json` 的 `check` 填。`check` 那一串原样填进 chain 那一行，所以它只许是几步 `npm test`／`npm run 某名字` 用 ` && ` 连起来（`CHECK_SHAPE`），别的样子红 —— 里面夹 `\ #` 时本地 shell 照跑全链，YAML 却把 `#` 后面当注释、CI 只跑前几步。chain 那一行是 `check` 去掉恰好是 `npm run mutate`、`npm run launches` 的那两步。不猜任何结构：留下来比的行改了哪怕一个字，闸门都红在第一处不一样的那一行，报出应为什么。
- **「整行注释」「空行」只认最窄的样子**，因为去掉的行若其实起作用，就是悄悄放行。整行注释是空格缩进、`#` 起头的行；空行是空的或全是空格的行。换行只认 `\n` 与 `\r\n`（`\r\n` 先折成 `\n`），空白只认空格与 tab：文件里出现别的空白或换行（单独的 `\r`、U+0085、U+2028、全角空格、不换行空格……）一律红，因为 YAML 或 shell 可能把它当换行或当内容，把一行「注释」的后半截变成真内容。tab 起头的注释行也拿去比（YAML 不许 tab 作缩进）。接在行尾 `\` 后面的注释行或空行红 —— shell 会把它连进上一行的命令。宁可误红。
- 代价是改工作流的人要在同一条 PR 里改钉死的那份。改得对不对 —— 例如有人把 `continue-on-error` 同时写进两边 —— 只有评审看得见；闸门保证的是这种改动躲不开评审，不保证它对。不比的整行注释与空行不改变 YAML 解析出的结构 —— 落在 `run: |` 块里、缩进又比块里的内容浅时，整份解析失败，GitHub 上报工作流无效，看得见但本地闸门是绿的；落在块里、缩进够时是块里的内容，在 shell 里是注释或空行，除了接在行尾 `\` 后面的那种（上面已红）都不起作用。

## 五、它替代什么、什么时候撤

**替代的是「跑」**（`process/README.md` 第二层「一道闸门该不该建」）：此前要知道变异一步会不会慢，只能推上去跑一次 CI、看墙钟；现在判据是一条命令，量取自树内的文件，同一棵树永远同一个结论。它不替代读：秒数文件准不准、线定得对不对，仍要人看报数行与 CI 的实际墙钟。

**什么时候重写秒数文件**：报数行说「其中 N 条变异的配置不在秒数文件里」那个数涨到几百条；主干上连续 3 跑，变异最重那一份的实际墙钟与报数行的预计差过 25%；或改了验证者本身的成本（加了一批慢用例、改了 worker 数、换了 runner 型号）。下载那几跑三份变异 job 的日志，`npm run shard-weights -- <日志>…`，与别的改动分开提交。重写文件本身会让下一个 PR 的基线跟着换（第三节第 2 条按这棵树的文件算两边），不会被算成涨幅。反过来，秒数文件本身没有东西核：把某种配置手改小就能过无豁免的上限线 —— 这一条只靠「只由命令写、分开提交」与评审看 diff。

**死亡条件**：

- **退成只报数**：连续 8 周里，PR 上三道线变红的每一次，改法都只是重写秒数文件、或写了涨幅豁免（即它一次真问题都没拦到）；
- **整个撤**：变异一步不再分份（`SHARD_COUNT` 回到 1），或主干上连续 10 跑最重那一份变异都不是 CI 最慢的那一段（拖住整跑的换成了别的 job），那时守它就不再守 CI 的墙钟。

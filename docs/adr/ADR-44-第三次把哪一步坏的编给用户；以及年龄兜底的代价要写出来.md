### 一、`MemoryUnreadable` 把 I/O 失败说成「解析失败」

```
记忆文件 .../creators.json/x.json 解析失败：ENOTDIR: not a directory
```

一个纯粹的路径问题，用户读到的是「解析失败」，然后去查一份完好的 JSON。

`collect.ts` 原样打印这句话，skill 的说明还叫 Agent 照着转述 ——
**一句编造的诊断会一路传到操作的人手里。**

`readMemory` 早在 ADR-26 就把「读不到」并进了 `unreadable`（因为 `existsSync`
分不清权限错误和文件不存在）。**状态改对了，包装它的那句话没跟着改。**

改成中性：`记忆文件 X 不可用：<detail>`。真实原因在 detail 里，它自己会说。

**这是同一条规矩第三次出现：**

| | 编的是什么 | 记在 |
|---|---|---|
| 一 | 把「写不进去」说成「文件坏了」 | ADR-20 |
| 二 | 替 `unknown` 编一个来源 | ADR-43 |
| 三 | 替失败编一个阶段 | 本条 |

三次的形状一模一样：**一个笼统的状态，配一句具体的解释，而那句解释是我
从最常见的那种情况里顺手抄来的。**

### 二、年龄兜底的代价，要写在需求里

第二条意见说：被 `SIGSTOP` 或调试器按住超过一小时的写入方，它的临时文件
会被年龄兜底当成孤儿清掉，恢复后 rename 失败。

**成立。而这次不改代码，改的是 D4 里那句话。**

D4 原先写着「不得动还活着的进程正在写的那些」—— 加了年龄兜底之后，
这句话已经不再为真。两种失败都罕见，但坏法不同：

| | 后果 |
|---|---|
| 不做年龄兜底 | pid 被回收后，一份完整的联系历史**永远**留在盘上，没人知道 —— **静默** |
| 做年龄兜底 | 被按住的写入方那一次写回失败，交付照常完成并带出原因 —— **响的** |

静默与响之间选响的。取舍本身不变，**但需求不能继续写着它没做到的事** ——
改成「不得动还活着的进程**刚写下**的那些」，并把代价写进去。

没有走「加锁」那条路：锁文件自己就会留下陈旧锁，那正是这里在解决的问题。

### 追记 · 残留清理只认系统发得出的 pid，上限是通用常量，不是本机的

- 日期 · 2026-09-03 · PR #34 评审四轮，同一条判据每轮收一格，第四轮起登记（ADR-64）

第二条的年龄兜底落地在 #34 的 `sweepStaleTemps`：只认 `process.pid` 写得出来的名字，
别的名字是别人的文件，再老也不动。四轮评审把「写得出来」一格一格收窄：正规十进制
（`1e3`、`007` 不算）、转成数字不丢精度（长过 2^53 的不算）、落在系统发得出的范围里
（先是 `process.kill` 收得下的 int32，再收到 Linux 硬上限 4194304）。第四轮指出 macOS 的
上限是 99999、`pid_max` 也能调低 —— 剩下的那一格只能靠读本机上限（Linux 读 `/proc`、
macOS 走 sysctl、Windows 没有，而且文件可能是别的主机或改过 sysctl 之前写的），或换一套
能证明出处的命名。那是设计改动，不是最小修补；判严了的代价只是那份残留留着不清，
丢不了数据，常量落在安全的那一侧。按 ADR-64 从第三轮起只登记，欠条见文首。


### 追记 · 承接本机 PID 上界欠条（实施前设计，2026-10-27）

本轮只承接文首残留识别这一格，依据 D4.k 与原交接 A，不改权限、写回错误、软链终点或一小时年龄取舍；旧正文和未证边界保留。Linux 每次清扫依据当前 `/proc/sys/kernel/pid_max`，上界不包含；值在运行中调整，下一次清扫结果要跟上，不把某一读取次数当需求。正规临时名还要满足 `0 < PID < 上界`。

延续原方案：只有 Linux 使用其 proc 来源；读失败／坏文本退至 4194304，Darwin 用 99999，其余平台仍用 4194304。proc 文本去首尾空白后要求 ASCII 正规十进制正整数；纯数字过大值收至 4194304。非 Linux 不读取同名挂载文件。数值是有限识别条件，不是来源认证；BSD、Windows、别的主机或改上界前的旧文件仍可能超出该识别保证。

Linux v6.6 文档明示该上界及以上不会分配（[pid_max](https://www.kernel.org/doc/html/v6.6/admin-guide/sysctl/kernel.html#pid-max)）；4194304 是项目保留硬界，不说成所有 Linux 的当前值。Apple [XNU 11215.1.10](https://github.com/apple-oss-distributions/xnu/blob/8d741a5de7ff4191bf97d57b9f54c2f6d4a15585/bsd/kern/kern_fork.c#L960)与 [12377.121.6](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/kern/kern_fork.c#L954)普通分配路径均在达到 99999 时回绕。项目延续 Darwin 兜底，但尚未验证本机较新 XNU 13432.1.9 的端点，不能宣称全版本或真机上界已证。

独立上下文只用先行合同、需求、平台主源与公开 `writeFileAtomic` 签名编写测试，先冻结、看未修树的合格语义红，再实现；不借旧作者的16条／9红7控制／238绿／10负片／启动54当当前实测。新增断言用最窄组；四处旧越界死号夹具只在保留原断言含义的前提下换成上界内合格号，实际启动摘要须真实 mutate 后派生。原实现、清点和整链均待执行，此设计不表示欠条已还。


> ⚠️ 欠条（档：登记；来源：2026-10-23原交接A的BSD续挂提案；适用轮次：本轮原余额承接，不是新评审付款）：FreeBSD、OpenBSD仍沿用项目通用兜底4194304，尚未取得并采用各自运行时PID上界；名字落在本机实际上界与该兜底之间的文件仍可能被误作残留。本轮不声称4194304是BSD真实上界，不消除Windows及历史／跨主机来源边界 · 重启条件：下一条改 `scripts/lib/atomic.ts` 本机PID上界段的改动，或有人在BSD上运行本仓库

# ADR-18 指纹要看得见嵌套字段；查不到的去重状态记为不知道

- 日期 · 2026-08-28 · PR #5 的自动评审提出两条，都成立
- 类型：**事实证伪**（两处，都是「我以为它在守着，其实它没有」）
- 冲击的需求：**D4**（补 `unknown` 一档）· P5（多一条声明）
- 结论：**采纳**，两条都改

### 一、内容指纹看不见嵌套字段

`JSON.stringify(value, keys)` 的白名单参数是**逐层生效**的。ADR-17 里拿顶层键
当白名单，于是每一个嵌套对象都被同一张表过滤：

```
{"accept":"a","cat":"D","id":"D4","pri":"P1","tension":[{}],"text":"t"}
                                              ^^^^^^^^^^^^
```

**交点整个被序列化成一个空对象。** 实测：把 `tension.ruling` 改成意思完全相反的
一句话、把 `tension.with` 改成指向另一条需求、把 `deprecated` 的理由整段换掉 ——
指纹三次都纹丝不动。

讽刺的地方在于：**这些恰恰是 ADR-17 那一轮新加的、最需要被守住的内容。**
我加了一道检查、加了测试、加了变异，然后让它对我新加的字段全盲 ——
而它看起来在工作，因为改 `accept`（顶层字段）确实会让它变红。

我的 harness 测试也没抓到，因为那条用例改的正好是顶层的 `accept`。
**一个用例只覆盖了判据成立的那一半，看起来和覆盖全了一模一样。**

修法：递归排序键的规范化，不用白名单参数。新增用例分别改嵌套的
裁决、指向、作废理由，M-H8-b 守着。

### 二、旧任务目录的去重状态被当成「没问题」

ADR-15 的边界写着：`memory_status` 缺失时按 `ok` 处理，理由是
「那时去重是无条件跑的」。

**这个理由是假的,而且假在一个我本该最清楚的地方**：过滤这一步确实无条件跑，
但 ADR-15 修的正是它**遇到读不出来的记忆会静默失效**。所以对一份早期版本
产出的任务目录，「跑过」和「生效了」之间隔着的正是那个 bug ——
到底去没去重，事后查不出来。

把它读成 `ok`，就是拿一个查不到的事实当肯定答案 —— 这个仓库总纲里
排第一位的事故形态，而我在修这个事故的同一次改动里又犯了一遍。

修法：`MemoryStatus` 加第四档 `unknown`；`render` 把缺失读作 `unknown`；
报告出一条不同措辞的声明（说「无从确认」，不说「你跳过了」），
并给出拿到确定答案的办法（重跑一次采集）。D4 的验收标准补上这一档。

`FilterResult.memory_status` 的类型排除 `unknown` —— 那一档是**记录的缺失**，
不是**观察的结果**，当场观察不可能得到「不知道」。

### 教训

**两条都是「我加了一道检查，然后没检查这道检查看得见什么」。**

- 指纹那条：加了检查、加了测试、加了变异，而测试用例恰好落在判据成立的那一半，
  于是三层防线一起放行
- `unknown` 那条：我在 ADR-15 里亲手写下一条边界，理由用的是被这次改动否定掉的
  旧行为。**决策记录里的一句猜测，比留在代码里更难被质疑** —— ADR-14 的教训，
  隔了三条记录又踩一次

共同点是：**新加的守卫要问一句「它看不见什么」，而不是「它抓到了什么」。**
抓到了什么由已有的用例回答，那是自证；看不见什么得主动去找，
而最省事的找法是**拿新加的字段本身去试**。

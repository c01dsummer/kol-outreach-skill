# ADR-15 记忆读不出来时不产出名单；那一份记忆绝不被覆盖

> ℹ️ **本条「教训」第 3 点指出的流程缺口由 ADR-16 补**（给 `2-CHANGE.md` 加
> 「需求冲突」和「产品取舍」两类）。ADR-16 与那处流程改动另一条改动合入；它合入
> 之前，分类表仍是五类。原文留着 —— 它是这条缺口被发现时的样子。
>
> ⚠️ **「边界」一节里「`memory_status` 缺失时按 `ok` 处理」那一条已被 ADR-18 推翻。**
> 理由写的是「那时去重是无条件跑的」—— 过滤这一步确实无条件跑，但**本条 ADR
> 修的正是它遇到坏文件会静默失效**，所以「跑过」不等于「生效」。缺失现在读作
> `unknown`。（追加不删改：原文留着，因为它错在哪本身是有用的信息。）

- 类型：**事实证伪**（D4 的假设「退化为空记忆是安全的」与 P4 矛盾）。

- 冲击的需求：**P4**（红线）· D4 · P5
- 结论：**采纳**。D4 的验收标准改写，两处止血，加一个显式逃生口

### 触发它的事实

四条各自正确的需求，串成一条没人看的路径：

1. **S3** 定下 contacted 由用户手动标记 —— 于是 `docs/business-requirements.md`
   和 `skill/references/memory.md` 都写着「**直接改 JSON**」。
   这个产品要求一个非程序员用手编辑一份 JSON
2. **D4** 规定「记忆文件损坏时退化为空记忆并告警，不中断任务」
3. **P4** 是红线，而它的**全部执行力**来自那份记忆
4. **P5** 要求交付时声明数据边界，但记忆状态从来不在交付物里

跑一遍这条路（截断 `memory/creators.json` 模拟一次写到一半的中断，
或者一个多余的逗号）：

- `filterByMemory` 一个人都不滤，**打扰过、甚至已拉黑的人全部重进名单**
- 交付物上 `filtered_contacted` 是 `0` —— 和「确实没人联系过」同一个值
- SKILL 要求交付时报的那行统计变成「0 人此前推荐过已过滤，0 人已标记联系过」，
  读起来就是一次干净的首轮采集
- 随后 `render` 调 `recordRecommendations`，它 `loadMemory()` 拿到空对象、
  `saveMemory()` 盖回去 —— **contacted 与 blocked 被永久抹掉，`first_seen` 一并重置**。
  `memory/` 不进 git，这是唯一一份副本；原本还能手工修的截断文件，
  被一份合法 JSON 盖掉之后连修的机会都没有。而按 S3，这份数据只有用户自己知道
- 警告打印的是「原文件未覆盖」。这句话在 `filterByMemory` 那条路上是真的，
  在 `render` 这条路上**是假的**，而且它打印了两次

`loadMemory` 里这两行返回的是**字节相同的值**：文件不存在（第一次跑，确实没人）、
文件读不出来（可能有一百个人，我读不出来）。两个不同的真相，一个值 ——
`process/README.md` 总纲说的「把第三档压进否」。

### 六道防线为什么一道都没拦住

| 防线 | 为什么绕过去了 |
|---|---|
| 类型 | 空 `creators` 是 `MemoryFile` 的合法值 |
| 纪律 lint | 没有兜底表达式，是一个 `return` 字面量 |
| 测试 | P4 的用例开头先写一份**合法**记忆再测。损坏路径在套件里不存在 |
| 变异 | M-P4-a/b 锚在过滤逻辑上。逻辑没错，错的是喂给它的东西 |
| 审计 | 按编号逐条数，D4 那行是「测试· 变异·」—— 一个测试都没有，而总判定是 ✓ |
| 交付物 | `meta.json` 没有任何记忆状态字段 |

**计量单位是「每条需求有没有测试」，所以交点上的测试不属于任何一条需求 ——
写了不加分，不写不扣分。** 靠提醒守不住这个，只能靠让交点在计量里有位置。

### 结论与边界

**止血（不进 trade-off，判据 2 直接给了答案）：**

- 记忆读不出来时 `recordRecommendations` 不写回，返回 `written: false` 和原因。
  不写回是**缩范围**（这一轮的推荐记录丢了，而且说出来），覆盖是**降标准**
  （文件看起来完整，其中最要紧的部分是假的）
- `saveMemory` 改成写临时文件再 `rename`。原来的直接盖写是非原子的 ——
  **这个模块既制造这个故障又吞掉它**

**裁决（红线赢，不需要讨论）：**

- `loadMemory` / `filterByMemory` 在读不出来时**抛**，`collect` 以退出码 `2` 结束，
  不产出名单。理由是 `docs/CONVENTIONS.md` 第 3 条的前半句：让错误往上抛。
  为什么不能走后半句（返回一个能表达「我没有资格回答」的东西）—— **名单没有第三态**：
  CSV 里每一行就是「这个人可以发信」，一份标注着「可能不该联系」的可联系名单
  是个自相矛盾的对象
- 中止是**便宜**的：`persist()` 跑在 `finalize()` 之前，采集结果与预算状态都已落盘。
  在这里中止一个 API 请求都不损失，`--resume` 时关键词全在 `done` 里，
  直接走回这一步。**这一条是 A 能当默认的全部理由** —— 不查它就会误以为
  中止会卡死流水线

**收场（这一半是产品取舍，由用户定，我最初擅自替他定了 b）：**

- `--ignore-memory`：必须用户显式打出来才继续。它不让重复打扰的风险消失，
  只是把它**从一个静默默认变成一次显式决定** —— 红线要挡的从来不是
  「这件事绝不许发生」，是「这件事不许在用户不知情的时候发生」
- 那一批的 `memory_status` 是 `unreadable_ignored`（**不得伪装成 `absent`**），
  报告与 `meta.json` 各带一条声明。两件事分开报：这一批可能重复打扰（去重没跑）、
  下一批可能重复推荐（这一批没记下）—— 后果不同，不能合成一句

**边界：**

- `TaskState.memory_status` 缺失时按 `ok` 处理。这只可能来自本次改动之前的
  `collect`，那时去重是无条件跑的 —— 是关于**本仓库自己历史**的判断，
  不是对数据的兜底
- `render` 里「写回在报告之前」是有语义的顺序，但变异只跑 `scripts/test.ts`，
  入口里的接线没有变异守得住（与 ADR-13 同一个处境）。声明的**判定**在
  `lib/report.ts`，由 M-P5-b / M-P5-c 守；**接线**由自检的
  「render 记忆读不出来时不覆盖原文件」那三条断言守
- **没做**：把 `docs/requirements.json` 里那个从 2026-08-25 起就没递增过的
  `version` 字段变成能被机器校验的东西。这次顺手把它改成 2，但**没有任何检查
  会发现下次忘记改** —— 和 ADR-13 驳回缓存版本号时说的是同一件事，仍然待决

### 教训

**需求冲突不是某条需求写错了，是几条各自正确的需求串成了一条没人负责的路径。**

D4 想要的**性质**是「记忆不可用不该让整个任务失败」。它写下的是
「退化为空记忆」—— 那是一个**实现方式**，而且在所有满足那个性质的方案里，
它是唯一一个会破红线的。`process/1-REQUIREMENTS.md` 早就写着「需求文档里不要有
实现方式」，这次是那条纪律第一次具体化：**需求里夹带的实现方式，会替下游把一个
本来有三种解法的问题，锁死成跟红线冲突的那一种。**

三条可操作的：

1. **写需求时只需要检查它与红线的交点。** 红线只有五条，这是 O(5) 不是 O(n²)，
   而且红线是全序最高的，交点的结论已经确定 —— 只需要把它写下来
2. **裁决和收场是两个问题。** 红线预先裁决了「什么不能发生」，但「那么该怎么办」
   经常还剩一个真正的产品取舍。压力解除的那一刻最容易把它顺手做掉
3. **`2-CHANGE.md` 的五分类装不下这一类。** ADR-11 当时自己标了「产品取舍」，
   也不在五类里。这两类都该补进去，并写明：**产品取舍默认需要用户，其余默认不需要**

# ADR-06 首次完整跑通 Skill 暴露的四个采集缺陷

- 2026-08-26 · 按 SKILL.md 走完 Phase 01–06 时
- 类型：**事实证伪**
- 触发它的事实：真实跑一遍便携榨汁机的建联任务，四个只有真跑才会暴露的问题：
  1. **`offset` 按固定步长递增。** 写的是 `page * 20`，而 API 某页返回不足 20 条时，
     下一页就会**跳过数据**。旧项目 `tikhub-kol-sourcing` 用的是 `offset += items.length`，
     是对的
  2. **没用 API 的 `has_more`。** 靠「本页新增 0 人」推断关键词是否耗尽 —— 不准，
     且要多发一次请求才知道
  3. **profile 补全无 try/catch。** 64 人里任何一个 404，整轮采集全挂
  4. **达标判断数错了对象。** 用采集总数（64）比目标（50），但过粉丝闸门后只剩 36 ——
     既没达标，又因为提前停止导致 7 个关键词只跑了 1 个
- 冲击的需求：D6（断点续跑）· F2（四维关键词）
- 结论：**采纳**（全部修复）
- 理由：第 4 条最严重，它让**关键词策略整体失效** —— 竞品词一个词就吃掉全部配额，
  场景词、人群词、整个 IG 一条都没跑到。而四维各有各的价值正是这套策略的核心。
  修法不只是改判据，还把顺序执行改成**轮转**：先给每个关键词各抓一页，再回头抓第二页。
  这样同样的预算下，每个维度都保证有产出。
  改轮转又引入一个回归：per-keyword 的 offset 只在内存里，续跑时全部从第 0 页重来，
  **重复抓也重复付费**，违反 D6。已把 offsets 持久化进 `task.json`。
  该回归是**脚本自检抓到的**，不是测试 —— 单测不会构造「预算中途耗尽再续跑」这个序列。
- 连带改动：`scripts/lib/types.ts`（新增 `SearchPage`、`TaskState.offsets`）·
  `scripts/providers/tikhub.ts`（search 返回分页信息）· `scripts/collect.ts`（轮转 +
  达标判据 + 错误恢复）· `skill/references/providers/_interface.md`
- 教训：**「达标」这类判据最容易数错对象。** 采集数、过滤后数、去重后数、
  写进名单数是四个不同的量，用错一个就会在完全正常的日志下产出错误行为。
  凡是写 `if (x >= target)`，都要回答一句：**x 和 target 是同一种东西吗？**

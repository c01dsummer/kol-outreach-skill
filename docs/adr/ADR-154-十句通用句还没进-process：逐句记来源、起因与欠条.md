## 二、十句

### 第 1 句：改 process/ 配一条决策记录写明来源，不与代码改动混在一条

来源：`0-process.md` 第 17 行（通-30「提议」的中段）：

```text
……通用层今天没有任何检查读它，所以三条：改通用层的 PR 必须配一条决策记录，写明这条纪律从哪个项目的哪件事里提出来；通用层改动不得与代码改动混在同一条 PR；加一条 lint，通用层出现产品词表里的词即红 —— 词表由业务层维护，通用层只规定「有这张表且检查读它」。……
```

起因：提案 §3 表（第 210 行）「用在哪」写的是「沉淀到 `process/` 的入口纪律」。提案 §0 第 1 条（第 30–31 行）：教训进 `process/` 的样本里，真正先记后搬的 12 个延迟 4–25 天，每次都是人想起来；§5 P7（第 261 行）定的是「搬 = 人批：需求所有者另开一条只改 `process/` 的 PR，其记录写明来源记录号与批准 URL」。这条线上每一句都配这样一条记录，就是本条。

落到：`process/2-CHANGE.md`「文档同步规则」表「改本目录里的任何一份」那一行（第 248 行），接在「至少要看」那一格末尾。

不搬：第三截「加一条 lint」—— 提案 §3「已被主干超越、不搬的」（第 219–220 行）与 §6 表都列了产品词 lint（ADR-77 撤过这一类，`docs/SYNC.md` 判为读）。同一行前面那半句「通用层里不许出现任何产品专有的名字」，`process/README.md` 第 28–30 行已经有了。

已有的近亲：`process/README.md` 第 31–32 行「某个项目自己的实例与经过,写在它自己的决策记录里,通用层不指回去」—— 新句照这个写：记录放在项目里，`process/` 不指回去。`process/6-INTEGRATE.md` 第 50 行「一个改动只回答一个『怎么证明它对了』的问题」管的是证据，没说通用层与代码要分开。

### 第 2 句：「结论：采纳」不等于采纳，要指到人拍板的痕迹

来源：`0-process.md` 第 100 行（通-26「提议」，条目在第 97–103 行）：

```text
新增一条决策记录是自动档 —— 它是记录，不是尺子。但「结论：采纳」不等于采纳：记录的是需要人批的结论（触及尺子、红线、通用层、架构）时，记录里必须能指到人批的痕迹 —— PR 里人类身份的批准，或人类身份的提交。指不到的「采纳」按提案读，下游不得引用它当依据。模板加一栏：「- 批准痕迹：<PR 里的批准或提交>；没有就写「提案」」。……
```

起因：提案 §3 表（第 209 行）「用在哪」：机器起草的草案怎么写结论。§6 表末行（第 302 行）把「让例程……给记录写『结论：采纳』」判为不做，理由就是这一句。本仓库照它写过：ADR-151 头部「结论」一栏写了裁决在项目线程的哪一处、「GitHub 上的人批痕迹是合入本条那条 PR 上需求所有者的批准」；ADR-153 与本条的结论都写了人批痕迹是合入本条那条 PR。

落到：`process/2-CHANGE.md`「第四步:结论只有三种,都要落纸」（第 152–163 行），接在第 160–162 行那段引用之后。

不搬：「模板加一栏『批准痕迹』」（ADR-151 第五节末条点名不搬）；开头「新增一条决策记录是自动档」用的是第 3 句的分档，第 3 句在后面才搬，这一句不先用它；原文后半引 `2-CHANGE.md`、`6-INTEGRATE.md` 行号的那几句（点名了文件与行）。

已有的近亲：`process/2-CHANGE.md` 第 152–158 行三种结论，没说哪一种要指到谁拍的板；`process/6-INTEGRATE.md` 第 210 行「合并者不能是写档的那一方」管的是评审发现的去向，不是记录的结论。

### 第 3 句：改动按碰的是什么分三档：自动、提议、人批

来源：`0-process.md` 第 10 行（通-20「提议」，条目在第 7–13 行）：

```text
……改动分三档：自动 —— 自动化执行者可直接改、直接合，仍过检查链；提议 —— 可以改、可以开 PR，合并前必须有独立复核，复核记录进 PR；人批 —— 执行者只能写提案（决策记录草案、提案文档），改动本身由人做或由人明确授权后做。被量的默认自动，但触及守红线模块（……本仓库这张表自 ADR-78 起人维护……）的普通代码升为提议。自动化执行者可以做的正面清单：修实现让现有测试变绿（不动测试）；新增测试、变异、属性、不变量、运行时断言；把一条散文假设登记进假设登记表（标「未验证」）；把一条判据的可观测结果与例子补具体（不改义务本身）；写决策记录草案、提案、复核意见；执行预定义的回滚（限被量的改动）；在参数层影子模式下运行候选规则并记录对比数据（`7-EVOLVE.md`）。放宽方向的改动一律不在自动档（`2-CHANGE.md`）。
```

起因：提案 §3 表（第 208 行）「用在哪」：§5 每条实践的「档」。提案 §5 表前那句（第 251 行）注明「档」借的是这套分法，「那是未采纳的提案，这里只当设计判据用，不是仓库规则」；ADR-151 第一节照它给 P1–P7 分了档，表下第 23 行写着「这套分法本身进不进 `process/`，按第五节另记」—— 本仓库已经在按这三档裁决，`process/` 里却没有这三档。

落到：`process/README.md`「什么时候不走流程」（第 259–265 行），接在「直接做」那两段之后。

不搬：「守红线模块升为提议」那句（点名了本仓库的锚点表、ADR-78 与 `docs/ARCHITECTURE.md` 行号）；正面清单里的「假设登记表」与「参数层影子模式」两项（`process/` 里没有假设登记表，影子模式在原提案新篇 `7-EVOLVE.md` 里，都依赖原提案的新东西）；同一行前面「尺子 / 被量的 / 尺子的尺子」的逐项举例里点名本仓库的那几样。

已有的近亲：`process/README.md` 第 261–265 行「直接做」与「流程只在改动触及需求登记表任何一条时启动」—— 三档不推翻它，「直接做」的那些落在自动档；`process/2-CHANGE.md`「第三步:谁来裁决」（第 108–150 行）管的是需求变更谁拍板，不管流程文档与闸门；`process/4-VERIFY.md` 第 256 行「红线改动必须过一次独立复核」是提议档的一例。

### 第 4 句：新字段在旧数据里缺着，读作「我不知道」

来源：`0-process.md` 第 24 行（通-40「提议」）：

```text
（行 118 之后追加）这一句对字段的生命周期也成立：状态文件、交付物、登记表新增一个字段时，旧数据里没有它。缺失只能读作第三档「无从确认」，不得读作 `false` / `0` / `ok` / 「未发生」；用旧数据续跑时缺字段不算不兼容，读取方要显式区分「字段不存在」与「字段存在且值为否」。新增字段的那条改动里必须写出这条读取规则，并有一条测试拿一份缺该字段的旧数据喂进去。
```

落到：`process/README.md`「这套东西的一条总纲」（第 107–126 行），插在第 122–124 行那段与第 126 行之间。

已有的近亲：总纲第 122–124 行「压进"否"就是把"没测量"说成"测量结果是零"」。那句管没测量，这句管旧数据里没有这一栏 —— 是它在字段生命周期上的展开；是不是赘述，在那一句的 PR 上读。

### 第 6 句：让机器替人改东西之前先画回路，逐段标闭合、半开、开路

来源：`0-process.md` 第 259 行（通-31「提议」）：

```text
任何「自演化」先画一张框图：目标（需求 / 红线 / 成本上限）→ 控制器（人或自动化执行者）→ 被控对象（代码 + 判断层文本 + 外部供应商）→ 输出（交付物、成本）→ 传感器 → 回到控制器。每一段传感器逐个标闭合 / 半开 / 开路：闭合 = 系统自己读得到；半开 = 靠人手工回填、稀疏且不及时；开路 = 系统里不存在。判据只有一句：没有传感器的目标不能成为自动演化的目标 —— 控制器凭空改不是演化，是漂移。逻辑正确性与成本这两条回路通常最先闭合；以业务效果为目标的回路要先建传感器，那是产品决策，不是工程步骤。自动修改代码不等于自演化。
```

起因：提案 §3 表（第 211 行）「用在哪」：§4 的回路图。提案 §4（第 224–242 行）照这张图画了本仓库的过程层：秒数、进程内耗时、按族启动数、runner 型号那一段半开，欠条「响了没还」与「教训」栏两段开路；§3「与今天问题的交集」（第 199 行起）指出原提案九条全以产品指标为被控量，还拿「逻辑正确性与成本这两条回路通常最先闭合」一句把成本回路当成已闭合略过了 —— 而 CI 时长正是那条回路，提案 §0 第 2 条（第 32–33 行起）数到 12 条记录里头部写明由人发问的四条。

落到：`process/README.md`「第二层 · 可执行的部分」末尾，第 218 行之后、第 220 行「第三层」标题之前，新起一个小节（ADR-151 第五节）。第 7 到 10 句依次接在这个小节里。

不搬：「逻辑正确性与成本这两条回路通常最先闭合」（提案 §3 指它恰好略过了没闭合的那条）；目标、被控对象括号里的「外部供应商」「交付物」这类举例，换成换个项目也读得懂的；「半开」改用提案 §4 的定义 —— 机器打印、人读、不跨运行（ADR-151 第五节），不用原文的「靠人手工回填、稀疏且不及时」。

已有的近亲：没有。`process/README.md` 第二层「能变成检查就变成检查」（第 157 行）讲的是一条纪律往哪一层搬，不讲反馈有没有闭合。

### 第 7 句：每个传感器写明怎么失效，失效时控制者停手

来源：`0-process.md` 第 266 行（通-32「提议」的第 3 条）：

```text
……（3）每个传感器有失效形态 —— 读不到、样本不足、口径变了（软件或配置版本变了）—— 失效时控制器停手，可机器守。
```

起因：提案 §3 表（第 212 行）「用在哪」：传感器的「无从确认」态。那一格点了两处：ADR-121「缺计时不补零」（第 28 行）是现成的一例；ADR-145 只有「失效形态」那一半 —— 两次基线计数不同时单报「启动数不确定」，可这一态在 PR 上照样判红，退不退成只报数由需求所有者定、「本条不自动退」（ADR-145 第二十一节第 3 小节，第 622 行），「控制器停手」那一步是人做的。

落到：同一小节，接在第 6 句之后。

不搬：通-32 的第 1、2 条（三态表示：总纲已有；传感器与控制器不同源：原文的落法全是业务判定的抽检）；「可机器守」—— 守不守得住看各项目，写进通用层就成了一句承诺；同条「每个传感器登记七样」那张表。

已有的近亲：`process/README.md` 总纲（第 111–124 行）的三档与「把第三档压进前两档」；这一句是它落在传感器上的样子。

### 第 8 句：预期的变化小于分得出的最小差时，只记录、不决策

来源：`0-process.md` 第 273 行（通-33「提议」中的一句）：

```text
……预期效应量低于最小可分辨差时，这个闭环只记录、不决策 —— 要明说，不能给人「窗口攒够就能动」的印象。……
```

起因：提案 §3 表（第 213 行）「用在哪」：墙钟只报数不判红。提案 §2.3（第 170 行起）用主干 301 次成功运行回测，墙钟够做一行只报数的传感器、不够判红；§6 表第一行（第 291 行）引 ADR-145 第二节「噪声底的 p99.9 是 37.8 秒，真劣化最小 83 秒，空隙只有 1.17 倍」，把秒数判红判为不做。ADR-151 的 P1 照这个只报一行（`.github/workflows/check.yml`「墙钟对比（只报数）」）。

## 一、按条数分配不平秒数

ADR-200 按条数分：主干 `d153df5` 上 2,179 条变异三份各 726～727 条。可一条变异的代价差得很多。取主干最近 5 跑（run 43599870587、43602914312、43606643519、43611515154、43677636843）三份变异 job 日志里的成本报告（`MUTATION_COST_JSON`，每种配置的基线与变异实测毫秒）：

- 自检变异 339 条，平均每条约 **10.2 秒**；需求测试变异 1,831 条，平均每条约 **1.6 秒**。
- 三份条数一样，变异那一步的墙钟却差到最重一份比平均高 9%～33%（`92ef770` 那一跑三份是 516、426、223 秒）。按 CPU 秒合计差到 1.36 倍。

## 二、估重与分法

一条变异的估重：**自检 6、需求测试 1**（10.2 ÷ 1.6 ≈ 6.4，取整）。用估重而不用实测秒数：秒数随 runner 型号与并发变（同一份代码在不同 runner 上差到 ×1.6，ADR-145 第三十一节），拿它判红，同一个提交重跑就可能换结论；估重只看清单，同一棵树永远算出同一个数。ADR-200 第四节说过的「秒数写进仓库」那一路也就不必走。

分法照 ADR-200，只把「条数」换成「估重」：同配置成摞，摞按估重从重到轻发给眼下最轻的那一份（`shardPlan`）。拿上面 5 跑的成本报告回放（每种配置的实测秒数不变，只换分法）：

| 分法 | 5 跑里最重一份比平均高 |
|---|---|
| 按条数（现行） | 9%～45% |
| 按条数 × 启动数 | 16%～26% |
| **按估重（自检 6、需求测试 1）** | **9%～17%** |

`d153df5` 上按估重分出来是 1,292 / 1,291 / 1,291。闸门量的就是这个分法：变异一步与闸门共用 `shardKey`、`shardPlan`、`mutationWeight`，不会量一个变异一步不用的分法。

## 三、三道线

需求所有者 05:41Z 选的（选择卡原文：最重一份超平均 25% 红；一个 PR 让变异总量涨超 5% 红，提交信息写理由可豁免；最重一份预计超 14 分钟红，无豁免）：

1. **三份均衡**：最重一份比平均高过 25% 就红。不设豁免。按估重分时，只有一摞重到比其余两份都重才会越线 —— 即某一种配置的变异太多；改法是把那组用例拆开或删重复的变异。
2. **一次涨幅**：一个 PR 让估重总量比 PR 基线涨过 5% 就红。基线与体量闸门同一个（`resolveBaseline`：PR 上是合并用的主干头，主干上是上一版）。可在这条分支自己的提交信息末段写 `mutation-growth-ok: <理由>` 豁免（只认 trailer 块，见 `trailer.ts`；键用 ASCII，因为 trailer 的键只认 `[\w.-]`）；只写键没写理由不算豁免，还判红。最近约 40 个合进主干的 PR 里涨得最多的一次 +2.1%（#449），十月一次加 91 条那个约 +6%。
3. **上限**：最重一份预计超过 14 分钟就红。不设豁免。折算：变异一步按份摊下来每单位估重约 0.30～0.32 秒（5 跑），取宽一点 0.35，14 × 60 ÷ 0.35 = **2,400**。`d153df5` 上最重一份 1,292，约 7.5 分钟。这一道守的是一次涨一点、涨很多次：十月（16 → 24 分钟）和这一周（估重 +11%）都是这么涨的，跟上一次比永远过不了第 2 道线。到线时要么删变异，要么由需求所有者决定加一台 runner（改 `SHARD_COUNT` 与 `check.yml`）。

PR 上越线就红；**主干上只报数**，同体量闸门与启动数闸门：CI 跑在推送之后，主干上判红只会让主干变红。问不出在不在主干上、接线对不上（第四节）是数据错，主干上也红；PR 基线那份清单读不出来，PR 上红，不当成没涨。

每跑都先打一行报数：每份估重、最重一份比平均高多少、预计几分钟、总量与比基线涨了多少。

放在检查链第三步、紧跟体量闸门：两道都只看这次改了什么，不起验证者，约 2 秒；越线时后面的几十分钟不白跑。

## 四、顺手守住的接线

`check.yml` 里有几处与代码对不上不会红（ADR-200 第 92 行那张欠条）。本条让闸门入口一起核，对不上就红（主干上也红）：

- 份数：matrix 是 `shard: [1, 2, 3]`、`MUTATE_SHARD` 的分母是 3、上传的分份启动数文件名是 `-of-3.json`，三处都与 `SHARD_COUNT` 对得上（`shardWiringFaults`）；
- `chain` 那个 job 跑的那一串恰是 `package.json` 的 `check` 去掉 `mutate` 与 `launches` 两步（`chainWiringFaults`）；
- 变异那几份写着 `MUTATE_JOBS: '6'`（`CI_MUTATE_JOBS`）。

没守的：构件名 `mutation-launches-*` 与 `selfcheck-launches` 的上传与取回对不对得上（对不上时最后一步读不到文件、闸门红，不会悄悄放行）；`check` 那个 job 只跑 `npm run launches` 这一点。

# ADR-132 独立自检按依赖族拆进程，与变异共用编译缓存

- 日期：2026-10-02 起，逐块追记到 2026-11-04
- 类型：成本超预期
- 触发它的事实：#263 合入后的四次自然成功 CI 里，最后那一遍完整 `selfcheck` 占整个 `Run npm run check` 步骤的 26%–29%；本机串行跑这一步只用满一个核（四跑的表在原文第一节）
- 冲击的需求：无。不改任何已有断言、变异、需求登记或检查强度；新增的是检查链自己的判定及其测试与变异
- 结论：**采纳方案甲＋方案丙，已落地。** 不带 `--only` 的完整、非变异自检默认按依赖族拆成多个子进程同时跑，父进程合并各子进程交回的结果后照旧收尾；带时间窗口的组所在的族等其余各族全部交回后再一族一族单独跑（第十节）。独立自检与变异那一步共用同一份编译缓存。方案乙（与变异步骤同时跑）与「复用变异基线结果」不做
- 理由：独立自检是串行的单核工作，而 CI 和本机都有四个核闲着；在不改断言、不碰变异判定的前提下，按进程拆开是唯一不需要重写自检运行方式的并行化
- 连带改动（现状）：`scripts/check/group-rule.ts`（`families`、`shardJobs`、`mergeShards`、`readShardReport`、`shardOrder`）、`scripts/check/selfcheck.ts`（`runShards` 派工、子进程回报、`shardChild` 判别、名单 `TIME_WINDOW_GROUPS`）、`scripts/check/tsx-cmd.ts`（`compileCacheDir`，编译缓存目录只此一份）、`scripts/check/mutate.ts`（用那一份）、`scripts/test.ts` 与 `scripts/check/mutations.json`（`M-H42-k`…`M-H42-ao` 等）、`docs/ARCHITECTURE.md`（锚点表与顺序契约表）

> 本文件只写现在定的是什么。节号沿用原文，好让老引用照旧对得上；空着的节号与没收进来的追记是实测、方案比较、复核与更正的过程，原文在 `docs/adr/历史/` 下的同名文件里（ADR-211）。

## 一、计时的口径

本条的计时照 ADR-99 第一节：给 CPU 时间、给多次与区间，单次的数写明是单次。CI 上取日志里 `> tsx scripts/check/mutate.ts`、`> tsx scripts/check/selfcheck.ts`、`> tsx scripts/check/audit.ts` 三行的时间戳之差，整个 check 步骤取 `Run npm run check` 那一步的起止；这些都是单次墙钟，CI 日志里没有这一步的 CPU。CI 机器每跑都可能换，不同运行的秒数不直接相减，只拿同一跑里自检与变异两步的比值看方向。

拆之前的规模（2026-10-02，树 `557b3e5`）：本机串行完整自检墙钟中位 348.9 s（346.0–349.8），CPU 中位 352.7 s（347.9–354.2），CPU ≈ 墙钟。ADR-97 第三节「调度已经到顶，并行没有红利」说的是变异那一步，不管独立自检这一步。

## 二、组与组之间共享什么，决定怎么拆

- **同一进程里真正跨组共享的运行态只在族内。** 族按 `needs` 连通（不分方向）划分：族内的组共享模块级变量或上一组落在 `tmp` 里的产出，必须同一个进程、按登记顺序跑；共用同一个前置组的两组也在同一族，拆开的话前置组要在两个进程里各跑一遍，两份运行态互不相通。2026-10-02 拆的时候，这样的族有五个：

  | 族 | 共享什么 |
  |---|---|
  | collect 链（`collect`、`enrich`、`render`、`regress`、`memory`） | 模块级 `dir`（collect 写，enrich、render、regress、memory 读）与 `rendered`（render 写，regress、memory 读）；另有文件系统边 render←enrich（ADR-99 第二节） |
  | render-input 族 | 完成计数对象 |
  | config-entry 族 | 完成记录对象 |
  | task-list 族 | 惰性创建的共用夹具与完成记录 |
  | review-cli-entry 族 | 阳性对照结果与完成标记（ADR-131） |

  其余各组之间只共享失败计数、认领集合与「执行过哪些脚本」，拆进程后各进程各一份，由父进程合并。逐组明细（当时 65 组的依赖、共享、资源与串行耗时）是那一天的快照，在历史文件第二节；今天「哪组读了别组写的什么」由 `share-rule.ts` 按语法树扫（ADR-134），不靠这张表。
- **文件系统与系统资源上没有跨进程冲突。** 每个进程自己 `mkdtemp`；在仓库 `output/` 下建的都是唯一临时目录；没有固定端口、固定文件名或家目录写入；`jobs-resource` 的文件描述符耗尽限在它自己的子 shell 里。
- **真正的风险是 CPU 争抢下判红取决于时刻的组。** `claims-restoration-entry` 等子进程起停有几秒的窗口；`mutation-cost-entry` 在被测入口 close 的那一刻就判、没有宽限（ADR-133 第一节）。这两组的处置见第十节。
- **不在一个进程里用异步并发跑多组。** `mutation-maintenance-entry` 临时改写本进程的 `process.env`，若干组往本进程的 `exit` 上挂清理，同进程并发就会互相踩；那条路还要把所有 `spawnSync` 改成异步，等于重写自检。

## 四、变异步骤的自检基线不能与完整自检互相代替

- **不能拿完整自检代替子集基线。** 基线证的是「这个子集单独跑是绿的」，施变后红了才能归给变异；完整自检全绿推不出子集单独全绿（ADR-99 第二节 render←enrich 就是只在单跑子集时暴露的边）。
- **不能拿基线代替完整自检。** 有些组没有任何变异指向，只有完整自检会跑；入口认领只在完整、非变异、全绿的一跑里写出（`claimsPublishable`）；「每个可执行文件都有出处」只在完整跑里判。
- 「让完整自检跳过基线里证过的组、再把基线的认领并进来」不做：要改「子集跑不写认领」（ADR-99 第五节）与「变异跑不碰认领」两条约定，完整自检从此依赖变异步骤先跑过，单独 `npm run selfcheck` 和检查链里那一次就成了两种东西。

## 五、方案甲的约定（现行）

- 「子集跑既不删也不写入口认领」（ADR-99 第五节）照旧：子进程仍是子集跑、仍不写；由父进程在**全部子进程全绿、开跑与收尾指纹一致**时写一次合并后的认领。认领判定 `claimsPublishable` 不变，只多一个合并步骤。
- **出处移到父进程**：「每个可执行文件都有出处」用各子进程上报的并集判，子进程里不判，也不说「这一跑没验『每个可执行文件都有出处』」。
- **输出**：各子进程的输出按族整段转发，不交错；`judgeRun` 认的末行汇总只由父进程打，子进程收尾不打汇总、只在有失败时设退出码，由父进程拿退出码与回报对账（`mergeShards`）。子进程的判别是 `selfcheck.ts` 里的 `shardChild`：交到了回报落点、又带着 `--only` 的那一跑。带上 `--only` 那一半，是因为只认落点的话，一次继承了落点、`SELFCHECK_JOBS` 又写错的完整跑也会被当成子进程，失败汇总被吞；判别摆在两段收尾的最前面（写成「是子集跑且不是子进程」，子进程会掉进孤儿检查那一支）；它只是一个合取，没抽进规则模块。它两处分支没有常驻断言，现挂在 ADR-158「拆进程子进程判别两处分支没有常驻断言」。
- 变异步骤里的自检验证者不受影响：它们本来就带 `--only`，走单进程子集跑。
- 合并与分配是判定，按 `docs/CONVENTIONS.md` 第 10 条放在 `group-rule.ts`，配需求测试与变异。
- 子进程崩溃沿用「进程级失败带记号」的规矩（`verifier-rule.ts`），不当成断言红。

方案乙（独立自检与变异步骤同时跑）不做：两者省下的量级相近，而乙的争抢落在变异判定上，误红会算到变异头上；还要额外守住「1 个 worker 时变异直接改工作区源码」那条路。方案丙（独立自检带上编译缓存）就是 ADR-97 第八节那张欠条要的事，随甲一起做了。方案的实测与比较在历史文件第三、五节。

## 七、落地后的现状

- **判定**（`group-rule.ts`）：
  - `families`：按 `needs` 连通把组并成族；族内按登记顺序，族按首个成员的登记位置排。校验与 `wanted` 同一套（重复 id、缺失依赖、自指、成环当场抛）；自检入口不分跑法、开跑前先调它一次，所以登记坏了每一种跑法都在开跑前停下（第九节）。
  - `shardJobs`：只有完整、非变异的那一跑才拆；个数的读法与 `MUTATE_JOBS` 同一份（`jobsWanted`），`SELFCHECK_JOBS` 写错当场拒绝，族比核少按族数收口。
  - `mergeShards`：各子进程的断言失败数相加；另把进程级问题各算一处失败 —— 子进程没起来（带上 Node 交回的原因）、没交回结果、退出码与它报的失败数对不上、它跑的组与派给它的族对不上（没跑与多跑两侧都有断言）、某组没派出去或派了两次。认领与出处取并集，各组子进程的当前目录也一并交回（ADR-212）。
  - `readShardReport`：子进程写回的那一份读不出来（写了一半、缺一栏、失败数不是非负整数）就按没交回算。
  - `shardOrder`：见第十节。
- **入口**（`selfcheck.ts` 的 `runShards`）：完整、非变异跑时本进程一组也不跑，按族排成队列，最多起 K 个子进程，谁空了领下一族 —— 派工用动态队列，不用手写或实测的耗时权重（写死的耗时表会烂，ADR-77）；「全部交回」等的是各子进程 close，孙进程不在等待之内；子进程用现有的 `--only` 跑一整族，跑完写回报；各族输出先落盘，再按族的登记顺序整段转出。合并之后把失败数、认领、出处与各组子进程的当前目录并进本进程，才核当前目录（ADR-212），后面的孤儿检查、汇总、`--brief` 那一条和入口认领照旧走。回报落点经环境变量 `SELFCHECK_SHARD_REPORT` 交给子进程，子进程读完就从自己的环境里摘掉。打开某一族日志与起子进程在同一个 `try` 里，打不开时那一族报成「没起来」（ADR-158 第五节）。`SELFCHECK_JOBS=1` 照旧单进程。
- **编译缓存**：目录定义在 `tsx-cmd.ts` 的 `compileCacheDir`，变异与独立自检共用；单独 `npm run selfcheck`、缓存不存在时行为不变。
- **入口那一半没有变异守着**：「全部交回 → 合并 → 才收尾」的先后、名单 `TIME_WINDOW_GROUPS` 少写一组、把单独跑的那段并回队列，都只有完整、非变异的拆进程跑够得到，而那一跑开头就删入口认领，需求测试里没有这样的夹具。原因不是笼统的「自己验自己」：那道体检只拦写了 `by`、又不是 `test` 的变异（`verifier-rule.ts` 的 `selfVerifying`），由需求测试起真入口来验的变异指着 `selfcheck.ts` 不被拦（先例 `M-H42-j`、`M-H42-ae`…`M-H42-ai`）。`docs/ARCHITECTURE.md` 顺序契约表那两行照实写了。
- **效果**：本机交替三对（2026-10-02），完整自检墙钟中位 384.3 s → 123.3 s，CPU 中位 403.3 s → 388.5 s，两组范围都不重叠。CI 上三次自然成功（#266 首次与最终提交、合入后主干，2026-10-03）独立自检 86–113 s，同一跑里自检／变异之比从合入前的 0.37–0.43 降到 0.152–0.157；这是墙钟的方向，不是 CI 上精确省下的秒数（原文第八节）。

## 九、合入后复核定下的几条（2026-10-07 起）

需求所有者要求对 #265–#267 做一次合入后复核，六条发现都出在 #266，都不是正确性错误，各登了欠条。现状：

- **复核发现一**（拆进程后正确性依赖 `needs` 写全，没有机器核）：扫得见的那一半由 ADR-134 还上 —— 一组读了别族写下的模块级变量或 `tmp` 下的固定路径、却没在 `needs` 里声明写方时，`npm test` 当场红。扫不见的那一半（拿 `tmp` 当当前目录按相对路径读写、拼出来的路径、`process.env`）从 ADR-134 一路重挂，现挂在 ADR-222「其余看不见的通道与记当前目录的回调仍没有守着」；其中当前目录那一种，完整自检收尾时由 `judgeCwds` 补核（ADR-212）。
- **复核发现二**（「多跑」那一侧没有断言）：已补断言与 `M-H42-aj`。
- **复核发现三**（顺序契约表那一行漏列守护变异）：「独立自检拆进程」那一行最后一栏逐条列出守合并与读回报判定的变异：本记录按下面的判据判过的十一条 `M-H42-*`，加 ADR-212 补的 `M-H212-g`。算不算守这一半，按后果判：施加之后，有没有一种子进程结果会让父进程拿着与实际交回不符的合并结果去判孤儿、打汇总、写入口认领。`M-H42-q`、`M-H42-ad`、`M-H42-z`、`M-H42-aj` 按这个判据不列，ADR-212 那条 PR 也没列 `M-H212-h`。第十节那一行特意以「拆进程整跑的派工先后」起头，不与这一行同以「独立自检拆进程」起头：列候选的命令按这个开头取行。这一行全不全没有机器核，挂在本文件末尾。列候选的命令在历史文件第九节「复核发现三」已还那一块。
- **复核发现四**：子进程不再打末尾汇总、不再说「没验出处」（第五节）；诊断里少的空格已补；子进程红行进 stdout 那一条没改，挂在末尾。
- **复核发现五**（父进程先走、`openSync` 在 `try` 外、等子进程没上限、几处信号下退出钩子的说法）：父进程先走**不会假绿，也不留错的证据**：父进程以信号或未捕获异常结束、退出码非零，子进程都是子集跑、不删也不写入口认领，回报目录删了之后写不回去；Ctrl-C 打到整个前台进程组、留下临时目录，`SELFCHECK_JOBS=1` 时也一样，不是拆进程带来的。`openSync` 与信号说法已在 ADR-158 第四、五节改掉（经 tsx 起时，挨 `SIGHUP`、信号落在壳上而真进程卡在同步等里时壳补的 `SIGKILL`、摘过自己装的处理，这三种退出钩子不跑；摘过处理那一种的实测在历史文件第九节，ADR-158 第四节的表里没有）；父进程先走那张现挂在 ADR-158「拆进程跑时父进程先走子进程没人收」；等子进程没上限挂在本文件末尾。三种停法的比较（父进程接管打断、子进程自查父进程两种做了原型实测，子进程自成一组没做原型、按构造判）在历史文件第九节，取舍是都不做：最便宜的乙也只把孤儿从「跑完手上那一族」缩到「那一组」，定性不变，还要加一条两头都没有变异守着的父子约定。
- **复核发现六**（`mutation-cost-entry` 判活对僵尸也成立）：裁决与修法见 ADR-133，判定在 `jobs-rule.ts`。那里核实了：变异那一步没有任何路由执行这一组，所以「CI 上变异那一步在满负载下跑过它的基线」这条推论不成立；它的判红是 close 那一刻立即算，不是「约 1 秒窗口」。
- **族漏并一条依赖边的真后果**（`M-H42-k`）：用它的组照样沿 `--only` 的依赖闭包把前置组拉进自己的子进程再跑一遍，同一组在两个或更多进程里各跑一遍，拆进程的完整自检合并时只有「多跑」看得出来；没有哪个子进程因此读到初始值（2026-10 用真入口整跑核过）。该分开的两族并成一族，合并时什么都不报，只是少并行；两种毛病都由 `h-group` 里核族划分结果的那条断言先抓。
- **登记坏了的后果**（`M-H42-l`、`M-H42-m`）：悬空依赖与重复 id 在每一种跑法里都在开跑前由族划分那一句停下（缺失依赖点出是哪一组缺了哪个，重复 id 只说有重复）。拿掉这道之后照样红，只是红得晚、红在别处：拆进程跑每族一句「没交回结果」；不拆进程的整跑只红在「自检选择」那一组起真入口做的子集跑上 —— 这一组哪天不再起真入口点名跑组，这两条变异在不拆进程的整跑里就成了静默的。需求测试先红，与这两条变异无关。
- **入口先后那条理由的更正**（「自己验自己」只拦指名自检来验的变异，由需求测试起真入口来验的不被拦）：见第七节「入口那一半没有变异守着」。
- **改已发编号变异的 `why`**：需求所有者定了 `M-H42-k`、`M-H42-l`、`M-H42-m` 三条的 `why` 一并改成真后果，只就这三条作数、不另立一般规则。依据：变异编号没有「不改含义」的规矩（那句写在需求与判据编号上）；`why` 不在变异的核心正文里、不进路由比较；三条的 `req`、`file`、`find`、`replace`、`by`、`kills` 一个字没动。

## 十、带时间窗口的两组挪到最后单独跑（2026-10-15）

2026-10-15 主干一跑（[run 38685385694](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/38685385694) 第一次，树 `6c80ed4`）独立自检红在 `claims-restoration-entry` 夹具记号那一条，同一提交重跑全绿；按形状推断是时间窗口误红，没有直接证据，也排除不了僵尸。照原来写好的修法做，窗口一个字不改：

- `group-rule.ts` 的 `shardOrder`：名单里的组所在的族不进并行队列，其余各族照旧谁空了领下一族，全部交回之后，这几族再按登记顺序一族一族单独跑；一族里只要有一组在名单里就整族挪；名单里点了没登记的组当场抛。需求测试在 `h-group`，变异 `M-H42-ak`…`M-H42-ao`；断言与实现出自同一个上下文（ADR-04）。

## 还开着的欠条

> ⚠️ 欠条「自检父进程等子进程没有上限」：父进程等子进程这一层没有上限，拆进程前后一样；一个自检子进程卡在别处，父进程就一直等，CI 的 job 也没写 `timeout-minutes`。不在拆进程这一层补：秒数随负载与机器变，猜一个写进代码就是把「不知道」伪装成「知道」，写紧了会在负载下误红；到点要收的正是卡在同步等里的子进程，收它只能走留盘的硬杀 · 来源：历史文件第 342 行 · 档：登记 · 重启条件：本机或 CI 上真见到自检卡住不结束时；那时先比较两条路：整条检查链一处上限（CI job 的 `timeout-minutes`），或给每个子进程定秒数

> ⚠️ 欠条「拆进程跑时子进程的红行只转到父进程 stdout」：子进程的 stdout 与 stderr 写进同一份日志、整段转到父进程的 stdout，红行（`✗ …`）也在 stdout；只读 stderr 的人看不到，单进程跑时它们在 stderr。没改：CI 与终端都把两股并在一起看，族内各行按真实先后排；分开转的话族内红行会排到这一族所有 stdout 行之后、丢掉上下文；要分开看用 `SELFCHECK_JOBS=1` · 来源：历史文件第 346 行 · 档：登记 · 重启条件：检查链或 CI 改成单独保存或解析完整自检的 stderr 时，或有人报告因此漏看了红行时

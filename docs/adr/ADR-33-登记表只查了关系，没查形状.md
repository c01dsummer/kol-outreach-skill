# ADR-33 登记表只查了关系，没查形状

> ⚠️ 这张欠条已还：`shapeProblems`、它的测试与 M-H4-f 随登记表判定切片（#39）进了主干；
> `spec-sync.ts` 随「判据与指纹」切片接上 `validateRegistry`，形状不过当场拦下，
> 不再把解析结果强转后渲染

- 日期 · 2026-08-28 · PR #5 第十四轮自动评审，成立
- 类型：**事实证伪**
- 冲击的需求：登记表完整性（检查链自身）
- 结论：**采纳**，形状先过，再查关系

### 事实

`validateRegistry` 查的全是**关系**：编号唯一、分类声明过、交点指向真实存在的
编号、决策记录存在。每一处 `.trim()`、`.length`、`for...of` 都**假定字段在、
类型对** —— 而登记表是 `JSON.parse` 出来的，`Req` 那个接口运行时一个字段都不拦。

缺 `why` / `ruling` / `text` 会当场抛 TypeError，吵是吵了点，至少不是静默的。
**真正危险的是只被渲染、不被任何关系检查碰的字段**：

- `deprecated.since` —— 评审指出的那一个
- `pri` —— **同一类，评审没指出**

两者都会被 `renderTables` 原样写成 `undefined` 进生成的表格，`--write` 存下，
而一致性检查比的是**生成结果和生成结果** —— 于是全绿。

### 判据换成「渲染实际读哪些字段」

不是「我想得到哪些字段该在」。渲染读什么，就校验什么 —— 这是个能穷举的集合，
而「我想到的」不是。按这个判据走，`pri` 是和 `since` 一起掉出来的，
不需要再想一遍。

### 教训

**和 ADR-19 是同一条**：`memory.ts` 早就有 `shapeProblem` 了，
因为记忆文件是手改的、显然不可信。登记表也是 `JSON.parse` 出来的，
只是它「看起来是我们自己维护的」—— 于是我没给它同样的待遇。

**数据可不可信，看它怎么进来的，不看它归谁维护。**

# ADR-50 崩溃持久性从「承诺」降为「尽力而为」

- 日期 · 2026-08-28 · 用户裁决
- 类型：**产品取舍**（不是事实证伪 —— 没有人发现新缺陷，是承诺该有多大的问题）
- 冲击的需求：D4
- 结论：**收窄 D4 的措辞，代码保留**

### 起因

D4 里有一句「『写了』不等于『落到盘上了』」。写下之后，自动评审就按这句话逐条检查 ——
而「断电不丢」在文件系统层面是一长串动作，漏一环就不算数。于是连着三轮：

| 轮次 | 补了什么 | 下一轮发现 |
|---|---|---|
| 十二 | 刷文件 + 刷目录 | 刷文件的失败被吞了 |
| 十三 | 拆成抛 / 吞两个 | 新建目录的上层没刷 |
| 十四 | 逐层刷新建的目录 | —— |

**每一轮的发现都成立，每一轮的修法也都对。** 让这条线停不下来的不是评审，
是**我自己写下的那句承诺**：当初不写，前三轮的意见根本不成立。

### 裁决

三条路摆给用户：继续补 / 把代码删回去 / **代码留着、把承诺改小**。用户选第三条。

- **代码保留** —— 已经写好也验过，留着有益无害，只是不再是一条要被追着查的承诺
- **D4 改成**：整体替换与「不留截断文件」照旧是**保证**；
  主机断电时这次写回留不留得住**明确不保证**，并写清代价 ——
  丢的是这一轮的推荐记录，下次跑会重新记上，**文件本身不会坏**

### 为什么这样不算偷懒

这个 PR 一路的规矩是「需求不许写它没做到的事」（ADR-44）。那条规矩有两个方向的解法：
**把事做到**，或者**把话收回来**。前十四轮我一直在用前一个，这一次用后一个。

区别在于代价的量级：真正的崩溃持久性是数据库级的工程（每一环都不能漏，
而且很多环受平台限制根本做不到），而这是个跑在运营电脑上的本地命令行工具；
它保护的那件事 —— 「谁被联系过」—— 真正的威胁是手改改坏了，不是断电，
而前者这个 PR 已经修了十几轮。

**文档说少了不要紧，说多了才是问题。**

### 教训

**一句写进需求的话，会自己产生工作量。**

我当初加那句是为了诚实（承认「写了不等于落盘」）。但需求文档不是笔记本 ——
写进去的每一句都会被人拿去检查，而检查是对的。

**想说明一件事，和把它定成一条要被守住的承诺，是两回事。**
前者写在注释或决策记录里，后者才写进验收标准。

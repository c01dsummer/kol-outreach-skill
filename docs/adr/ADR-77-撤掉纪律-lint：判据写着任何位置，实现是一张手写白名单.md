# ADR-77 撤掉纪律 lint：判据写着「任何位置」，实现是一张手写白名单

- 2026-09-18 · 按 Bitter Lesson 原则重整检查链，逐道评定里的第三道
- 类型：缩范围（撤一道闸门）＋ **改一条红线判据的形状**（不改它要什么）
- 冲击的需求：**P1.b（红线）** —— 判据从「不得出现这种写法」改成「三态不得被压平」
- 结论：**撤 lint，把 P1.b 换成结果约束**

## 这条判据一直在说大话

P1.b 原文逐字是：

> 任何位置不得出现 `?? 0` / `|| ''` 形式的数据兜底；纪律 lint 对 scripts/ 全量扫描，命中即失败。

「任何位置」「全量扫描」。而实现是 `lint-rule.ts` 里一张**手写的敏感字段表** ——
扫到一行，先问这行里有没有表上的字段名，没有就放行。所以它的真实覆盖是
「表上那几十个名字」，不是「任何位置」。

这不是理论风险，两次都真的发生了，而且两次都落在红线上：

- **`score` 不在表上**（ADR-71）。`(b.score ?? 0) - (a.score ?? 0)` 判绿判了很久 ——
  「还没算过分」和「0 分」被压成同一个值，交付表上谁在前全看排序算法
- **`null` 不在兜底值表上**。`?? null` 不被当成兜底，于是「未查询」被写成
  「查过，没有」这条路一直开着

**一张要靠人记得往里加名字的表，漏项是它的常态，不是意外。**
而判据正文写着「任何位置」—— 检查说了假话，比没有检查更坏。

## 换的是材料，不是要求

P1 要的东西一个字没减：**「未查询」「查过为空」「值就是 0」必须分得出来。**
换掉的是拿什么去守它。

三种材料，按强弱排：

1. **结构性**（「写不出来」）—— 改形状，让坏状态表达不出来
2. **验证性**（「查得出来」）—— 直接断言结果
3. **指令性**（「别这么写」）—— 扫源码、写告诫

lint 是第三档。**而这个仓库自己最成功的一次 P1 修复用的是第一档**：
ADR-71 那个 bug 的最终修法不是给表里补上 `score`，是把 `tierOf` 改成
**分数由调用方传进来、不从 `c.score` 读** —— `scripts/lib/score.ts` 的注释原话是
「传进来之后**结构上就不存在「拿不到分」这一态**——靠结构保证，不靠运行时兜底」。

那一处从此不可能再犯，而且不需要任何人记得往表里加名字。

## 新判据与它的认领

P1.b 改成：

> 「未查询」「查过为空」「查到的值就是 0」三态不得被压平：同一个字段的这三种状态，
> 在交付表的取值、排序与入池判定上，任意两者不得给出同一个结果。

认领它的是新夹具「三态不得被压平：取值、排序、入池三处各验一次」，三条轴各一组断言：

| 轴 | 断言 | 压平了会怎样 |
|---|---|---|
| 取值 | `cell(undefined) / cell(null) / cell(0)` → `未查询` / `` / `0` 三个不同的格子 | 交付表上看不出这人查没查过 |
| 排序 | 没算过分的排在 0 分之后，不与它混同 | 名单顺序把两类人混在一起 |
| 入池 | 粉丝数未查询 → 放行；确实是 0 → 挡掉，**结论相反** | 不知道的人被静默筛掉 |

**三处各验一次，因为压平可以发生在任何一处**，三处用的是三套代码。

## 账

- 删 `lint.ts` ＋ `lint-rule.ts` 共 **130 行**
- 删 **9 条**变异（`M-P1-i` 到 `M-P1-p`、`M-P1-v`）—— 它们守的全是「别把 lint 弄瞎」：
  白名单拿掉一项、扫描不进子目录、`lib/` 整片排除、豁免不写理由也放行。
  **harness 守 harness**
- P1 名下**剩 13 条**变异，一条没动，守的全是真行为：「把未知粉丝数当作符合区间给分」
  「合并时把未知当 0 相加」「把 bio 未取到兜底成空串」。**这些本来就是结果级的三态断言**
- **19 处 `p1-ok:` 标记**（产品代码里 16 处）改成 `P1 例外：` —— 理由原样留着，
  但不再假装有个工具在读它。闸门没了，一个指向不存在的工具的标记就是假引用

## 老实说，什么缩了

**旧 lint 会对着源码报出「这一行有兜底写法」，新判据不会。**
一处新写的 `?? 0`，只要还没把三态压平到那三处之一，没有东西会在写下的那一刻指出来。

这是真的缩。换来的是两样：判据不再说大话（它现在描述的正是它查的）；
以及不再漏没被谁枚举到的字段 —— 结果查得住 `score`，写法查不住。

⚠️ **「1087 次 CI 零真红」这一条我没有复核** —— 它要读 1087 次运行的日志，
出处是 2026-09-18 那次逐道归因。本条其余的数都是自己跑命令核的。

> ⚠️ 欠条：**三条轴之外的压平点没人守。** 新判据点名的是取值、排序、入池三处，
> 因为今天的产出物只经过这三处。哪天多出第四处（比如新增一张分表、一种导出格式、
> 或者一条把三态读进去再写回去的路径），它压平三态时**三条轴一条都不会红**。
> 这和旧 lint 漏 `score` 是同一个形状的坏法，只是换了一层：旧的漏字段，新的漏路径。
> 路径比字段少得多、而且加一条路径是显式的改动，所以这一层更薄 —— 但不是没有。
> · 重启条件：**下一条往产出物里加一条新路径的 PR**（新的 sheet、新的导出、
> 新的排序或分层入口）—— 那时要么给它补一条轴，要么说明为什么它碰不到三态。

## 什么条件下重开这个讨论

- **同一类坏法在半年内又出现两次**，而且两次都是「写下的那一刻没人吭声、
  等到产出物坏了才发现」—— 那说明第三档（扫写法）的即时反馈是有价值的，
  重新装一道，但**这次要么表由代码生成，要么判据正文别再写「任何位置」**
- **敏感字段的类型形状真的做成不可默认时** —— 那时第一档接管，连结果断言都可以再薄一层。
  ⚠️ 实测过：`number & { brand }` 这种**不管用**，`(x ?? 0) - (y ?? 0)` 照样编译通过；
  要挡住得用不是 `number` 子类型的不透明类型，代价是 145 处使用点全要显式解包。
  本条没做，量过才说不做

**谁去数**：新判据坏了会在 `npm test` 里红。上面那条「半年内两次」靠开 PR 的人自己记 ——
没有机器在数，这是有意的。

# ADR-74 硬杀那一刀落在 tsx 壳上，worker 和验证者都活着

- 2026-09-14 · 还 ADR-72 那张「硬来只杀 worker、不杀验证者那一组」的欠条时，量出来的
- 类型:既有缺陷 —— **让收尾说了假话**
- 冲击的需求:无编号需求（检查链自己）。冲击的是「这一跑收干净了」这句承诺
- 结论:**采纳** —— 把号传上来、按组收掉；`hardStopPlan` 那一整段判定搬进 `jobs-rule.ts`

## 欠条说的那件事是真的，但它把严重程度说小了

ADR-72 那张欠条逐字是「硬来那一步只杀 worker 自己，不杀它底下验证者那一组」。
还它的时候先去量，量出来的比它写的更难看：**那一刀连 worker 自己都没杀到。**

`mutate.ts` 起 worker 走的是 `tsxCommand(…)`，而 tsx 的 cli 会**再分一个进程**出来跑脚本。
所以派工进程手上那个 `kid` 是**壳**，不是 worker。用和入口逐字同形状的 `spawn`
（`stdio: ['pipe','pipe','inherit']`，无 `detached`）各跑一次：

| 发什么 | 壳 | 真 worker | `close` 事件 |
|---|---|---|---|
| SIGTERM | 死 | **死**（tsx 会转发） | 来了 |
| SIGKILL | 死 | **活着**（心跳 21 → 33 → 45，一直在长） | **永远不来** |

两条推论，都比欠条上写的更要紧：

- **硬来那一步在最要紧的那种情形下近乎空操作。** SIGKILL 转发不了，于是真 worker
  活着接着跑**被改过的源码**；而 `close` 不来意味着 `live.delete` 不跑，死壳留在表里，
  对一个已经 `exit` 的子进程再调 `kill` 实测交回 `false`、一个信号都不发。
- **「先把 worker 全杀了，集合就冻住了」这个论证不成立。** 三份独立设计都拿它当中心理由，
  实测全部落空。真正让集合近似冻住的是**派工协议本身**：一条一派，任何时刻一个 worker
  手上至多一个没消化的编号；派工进程一进硬来就不再转事件循环，新编号出不去了。

## 为什么只能把号传上来

拓扑两层，两层的组不一样（`mutate.ts` 两处 `spawn`）：worker 无 `detached`，跟派工同一组；
验证者有 `detached`，自成一组。验证者那个 `detached` **去不掉** —— 「见齐就停」靠
`process.kill(-验证者pid)` 连 tsx 壳底下那个真跑脚本的进程一起收，不自成一组就没有那个负号。

于是派工进程手上没有任何一个现成的号能打到验证者那一组：杀 worker 那一组会打到自己，
杀 worker 自己够不到孙子。**只剩把号传上来这一条。**

ADR-72 里把「让 worker 自成一组」按「够不到验证者」否掉了 —— **那个理由对的是另一个问题**。
对「够不够得到 worker 自己」这一问，它反而是唯一成立的那条。那条驳回要重写，
否则下一个人会引一条站不住的驳回（记成下面的欠条）。

## 走文件，不走已经有的那根管子

**硬来那一步是同步的，而管道不是。** 它从三处进来 —— `error` 事件、`noStdio`、
建目录那一圈的外层 catch —— 其中后两条发生在派工进程**一次事件循环都还没转过**的时候。
那时管道里就算躺着一行号，也还没变成「派工进程知道」。文件不挑这个。

顺带量了那三条路上的余量：本仓库这棵树 `cpSync` 一份 **27 ms**，而 worker 从起来到
跑得动验证者要 **约 1.1 s**。缺省并行度（本机 4）下建目录一圈约 110 ms，**余量约 10 倍**，
所以那几条路上今天确实没有验证者可漏。但那是余量不是结构：交叉点约在 **40 个 worker**，
`--jobs=64` 或者慢一点的盘就翻过来。

**经命令行参数告诉 worker，不经环境变量。** 环境变量会继承下去：worker 起验证者时
`env: { ...process.env }` 原样带过去，而验证者可能又是一个 `mutate`（自检把它当工具起）。
那样每一层都要「记得掐掉」，漏一层的症状是两个进程抢写同一份号文件。
命令行参数天生不继承 —— 验证者的 argv 是新的，看不见它。**没有一处要记得掐。**

## 硬来那几步的次序，以及哪一段承重

```
① 每个还活着的 worker 壳一刀   ② 每个读得出号的验证者组一刀   ③ 号读不动的各出一句话   ④ 删隔离目录
```

**② 必须在 ④ 之前，这是唯一真正承重的一段。** 验证者的 cwd 就是那个 worker 目录：
先删后杀的话，刀落下之前它还能往一棵已经被删掉的树里写，盘上重新长出半成品，
而删那一句已经成功返回、诊断根本不打 —— **静默**。倒过来至多剩「一次已经交给内核的写」，
撞上时删会抛 `ENOTEMPTY`，被现成那个 catch 接住打诊断 —— **响**的。

**① 与 ② 的先后买不到任何东西**，理由见上面那条被推翻的论证。排在前面只是保持
今天的承诺顺序，不是因为它冻住了集合。

**这一段整个搬进 `jobs-rule.ts`**，有两个各自独立的理由：一是入口里的接线缺省那个验证者
够不到（`process/4-VERIFY.md`）；二是**顺序契约登记不了** —— 留在 `mutate.ts` 的话，
契约位置只能写那个文件，而指着它的变异不写 `by` 只会「存活」，写了 `by: "selfcheck"`
又被 `selfVerifying` 当场拦下（`mutate.ts` 是自检的工具种子）。这正是**主干 `090e0ee` 上那
348 条变异里，指着 `mutate.ts` 的一条都没有**的原因（本条改完 364 条，仍然一条都没有）。

## 算号那一格的每一道拒，各挡什么

这是整条改动里最危险的一格 —— 它算出来的东西会被当成信号的目标。实测支撑：

| 拒 | 挡的坏法 |
|---|---|
| 末尾没有换行 | 写到一半的 `12345` 被截成 `1234` —— 杀错一整组，不响 |
| 往返核对 | `Number` 认 `0x10`／`1e3`／`007`／`''`，实测 16／1000／7／0 |
| `n <= 1` | `0` 打的是**调用者自己这一组**（而 `-0 === 0`）；`1` 是**发给发得出的每一个进程** |
| `n === 自己那一组` | 真正的自杀向量 |

**「超过 PID_MAX 就拒」那一条有意不加**：实测本机 `pid_max` 是 32768，而 systemd 常设
4194304 —— 写死哪个都错。越界的号发出去只会拿到 ESRCH，而那一支本来就被吞掉。

自保守卫比的是**组号**不是 pid：`'getpgrp' in process` 实测是 `false`，只能读 `/proc/self/stat`；
而实测 shell 底下 `pgid(15262) ≠ pid(15286)`，**比 pid 那一条永远不命中**，配它的负片也是假负片。

## 实测：改之前与改之后

```
改之前（只杀 worker）：心跳 21 → 33 → 45   还在长
改之后（真判定＋真执行）：
  计划：kid → group(-15306) → sweep
  执行完：心跳 14 → 14              停了
```

端到端也验过一次：真跑 `--jobs=2`，号文件 `w0.<派工pid>.verifier` 如期出现、里面是真的验证者号；
给派工进程发 SIGTERM，9 秒后隔离目录收掉、两个验证者都没了、`mutate` 相关进程剩 0 个。

## 三段窗口，照实写

- **窗口一（号还没到）**：从起验证者那句返回，到写号那句返回。中间只隔装两个监听器。
  派工若在这一段里硬来，读到的是「没有文件」，这一次照旧漏。**大小没量过，也不写一个没量过的数。**
- **窗口二（下一个编号已经在路上）**：至多一个编号（一条一派，手上不会有第二个）。
- **窗口三（死号）**：号写下之后、验证者已结束而抹号还没发生。读到死号时 `process.kill`
  答 ESRCH 被吞掉，**除非那个号已经被系统回收给了别人**，那一刀就落在不相干的组上，而且不响。
  温和那条路上原本会留整 5 秒（宽限期）的死号 —— 已经压掉：worker 一进来就先装抹号的处理函数，
  排在那个会退掉进程的处理函数之前。

**刀发出去就走，不等那一组真停下。** 从发出到真停下之间，已经交给内核的那一次写照样落盘 ——
`mutate-restore.ts` 上写着同一句，这里不能有第二种说法。

> ⚠️ 欠条：**真 worker 在硬杀之后仍然活着，本条没修。** 边界：它拿不到新编号（stdin 的写端
> 随派工退出而关），手上那一条的验证者已被第 ② 步收掉，于是它几乎立刻从等待里回来、还原、
> 写结论行拿到 EPIPE 死掉。残量是一个卡在别处（不是卡在等验证者）的 worker 会一直活着。
> 两条修法各带代价：让 worker 也 `detached` 再按组杀（代价：终端里 Ctrl-C 打的前台组从此
> 不含 worker，温和那条路从「本来就收到」退化成全靠转发），或者让号文件同时带上 worker 自己的号
> （代价：正文从一个数变成两个生命周期不同的数）· 重启条件：下一条碰 `hardStop` 或 `stopJobs` 的 PR

## 第一轮评审揪出两处「注释说不许，代码就那么干了」

两处形状一样，都是**把「量到了但读不懂」压进「量出来是零」**：

| 在哪 | 头一版怎么写的 | 后果 |
|---|---|---|
| 写号那一句 | 把异常吞掉，而紧挨着的注释写着「不许留下孤儿」 | 验证者在跑、号文件不存在，派工读到 ENOENT 当成「压根没起」——**静默过继** |
| 算号那一步 | 号在却认不出（写了一半、不是个号）时既不出刀也不吭声 | 同上，而且这边照样删目录、照样报「收干净了」 |

改法：

- **写号失败就就地把那一组收掉。** 手上有号，用同一道判定算（同样的往返核对与自保守卫）；
  这一条于是没有结论 —— 而**没有结论不是通过**（`process/README.md` 总纲），
  下游当作「跑不起来」报出来，带着现场。
- **三种状态三条路**：没有号文件（没起验证者）不吭声；读不动（别的 errno）出一句话；
  **号在却认不得**也出一句话。第三种正是头一版漏掉的那一格，而它恰恰是本文自己
  在那段注释里骂过的形状。

值得单记的是**它是怎么藏住的**：这两处的注释里都写着正确的那句话，代码却是反的。
**一段说明意图的注释，会让写它的人以为意图已经实现了** —— 道理写得越清楚，
越难在同一屏里看见代码没照着做。


> ⚠️ 欠条：**收的只有一层。** 收的是验证者自己那一组；验证者若再 `detached` 分出去孙子，
> 那个孙子逃出这一组，谁也收不到。判据拦不住这种写法 —— 和 `verifier-rule.ts` 头上那句
> 「写的人绕得过去，不是机器判错」同一处境 · 重启条件：闭包里真出现第一个这么写的验证者时

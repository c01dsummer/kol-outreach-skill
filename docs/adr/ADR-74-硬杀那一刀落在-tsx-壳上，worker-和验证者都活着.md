# ADR-74 硬杀那一刀落在 tsx 壳上，worker 和验证者都活着

- 2026-09-14 · 还 ADR-72 那张「硬来只杀 worker、不杀验证者那一组」的欠条时，量出来的
- 类型:既有缺陷 —— **让收尾说了假话**
- 冲击的需求:无编号需求（检查链自己）。冲击的是「这一跑收干净了」这句承诺
- 结论:**采纳** —— 把号传上来、按组收掉；`hardStopPlan` 那一整段判定搬进 `jobs-rule.ts`

## 欠条说的那件事是真的，但它把严重程度说小了

ADR-72 那张欠条逐字是「硬来那一步只杀 worker 自己，不杀它底下验证者那一组」。
还它的时候先去量，量出来的比它写的更难看：**那一刀连 worker 自己都没杀到。**

`mutate.ts` 起 worker 走的是 `tsxCommand(…)`，而 tsx 的 cli 会**再分一个进程**出来跑脚本。
所以派工进程手上那个 `kid` 是**壳**，不是 worker。用和入口逐字同形状的 `spawn`
（`stdio: ['pipe','pipe','inherit']`，无 `detached`）各跑一次：

| 发什么 | 壳 | 真 worker | `close` 事件 |
|---|---|---|---|
| SIGTERM | 死 | **死**（tsx 会转发） | 来了 |
| SIGKILL | 死 | **活着**（心跳 21 → 33 → 45，一直在长） | **永远不来** |

两条推论，都比欠条上写的更要紧：

- **硬来那一步在最要紧的那种情形下近乎空操作。** SIGKILL 转发不了，于是真 worker
  活着接着跑**被改过的源码**；而 `close` 不来意味着 `live.delete` 不跑，死壳留在表里，
  对一个已经 `exit` 的子进程再调 `kill` 实测交回 `false`、一个信号都不发。
- **「先把 worker 全杀了，集合就冻住了」这个论证不成立。** 三份独立设计都拿它当中心理由，
  实测全部落空。真正让集合近似冻住的是**派工协议本身**：一条一派，任何时刻一个 worker
  手上至多一个没消化的编号；派工进程一进硬来就不再转事件循环，新编号出不去了。

## 为什么只能把号传上来

拓扑两层，两层的组不一样（`mutate.ts` 两处 `spawn`）：worker 无 `detached`，跟派工同一组；
验证者有 `detached`，自成一组。验证者那个 `detached` **去不掉** —— 「见齐就停」靠
`process.kill(-验证者pid)` 连 tsx 壳底下那个真跑脚本的进程一起收，不自成一组就没有那个负号。

于是派工进程手上没有任何一个现成的号能打到验证者那一组：杀 worker 那一组会打到自己，
杀 worker 自己够不到孙子。**只剩把号传上来这一条。**

ADR-72 里把「让 worker 自成一组」按「够不到验证者」否掉了 —— **那个理由对的是另一个问题**。
对「够不够得到 worker 自己」这一问，它反而是唯一成立的那条。那条驳回要重写，
否则下一个人会引一条站不住的驳回（记成下面的欠条）。

## 走文件，不走已经有的那根管子

**硬来那一步是同步的，而管道不是。** 它从三处进来 —— `error` 事件、`noStdio`、
建目录那一圈的外层 catch —— 其中后两条发生在派工进程**一次事件循环都还没转过**的时候。
那时管道里就算躺着一行号，也还没变成「派工进程知道」。文件不挑这个。

顺带量了那三条路上的余量：本仓库这棵树 `cpSync` 一份 **27 ms**，而 worker 从起来到
跑得动验证者要 **约 1.1 s**。缺省并行度（本机 4）下建目录一圈约 110 ms，**余量约 10 倍**，
所以那几条路上今天确实没有验证者可漏。但那是余量不是结构：交叉点约在 **40 个 worker**，
`--jobs=64` 或者慢一点的盘就翻过来。

**经命令行参数告诉 worker，不经环境变量。** 环境变量会继承下去：worker 起验证者时
`env: { ...process.env }` 原样带过去，而验证者可能又是一个 `mutate`（自检把它当工具起）。
那样每一层都要「记得掐掉」，漏一层的症状是两个进程抢写同一份号文件。
命令行参数天生不继承 —— 验证者的 argv 是新的，看不见它。**没有一处要记得掐。**

## 硬来那几步的次序，以及哪一段承重

```
① 每个还活着的 worker 壳一刀   ② 每个读得出号的验证者组一刀   ③ 号读不动的各出一句话   ④ 删隔离目录
```

**② 必须在 ④ 之前，这是唯一真正承重的一段。** 验证者的 cwd 就是那个 worker 目录：
先删后杀的话，刀落下之前它还能往一棵已经被删掉的树里写，盘上重新长出半成品，
而删那一句已经成功返回、诊断根本不打 —— **静默**。倒过来至多剩「一次已经交给内核的写」，
撞上时删会抛 `ENOTEMPTY`，被现成那个 catch 接住打诊断 —— **响**的。

**① 与 ② 的先后买不到任何东西**，理由见上面那条被推翻的论证。排在前面只是保持
今天的承诺顺序，不是因为它冻住了集合。

**这一段整个搬进 `jobs-rule.ts`**，有两个各自独立的理由：一是入口里的接线缺省那个验证者
够不到（`process/4-VERIFY.md`）；二是**顺序契约登记不了** —— 留在 `mutate.ts` 的话，
契约位置只能写那个文件，而指着它的变异不写 `by` 只会「存活」，写了 `by: "selfcheck"`
又被 `selfVerifying` 当场拦下（`mutate.ts` 是自检的工具种子）。这正是**主干 `090e0ee` 上那
348 条变异里，指着 `mutate.ts` 的一条都没有**的原因（本条改完 364 条，仍然一条都没有）。

## 算号那一格的每一道拒，各挡什么

这是整条改动里最危险的一格 —— 它算出来的东西会被当成信号的目标。实测支撑：

| 拒 | 挡的坏法 |
|---|---|
| 末尾没有换行 | 写到一半的 `12345` 被截成 `1234` —— 杀错一整组，不响 |
| 往返核对 | `Number` 认 `0x10`／`1e3`／`007`／`''`，实测 16／1000／7／0 |
| `n <= 1` | `0` 打的是**调用者自己这一组**（而 `-0 === 0`）；`1` 是**发给发得出的每一个进程** |
| `n === 自己那一组` | 真正的自杀向量 |

**「超过 PID_MAX 就拒」那一条有意不加**：实测本机 `pid_max` 是 32768，而 systemd 常设
4194304 —— 写死哪个都错。越界的号发出去只会拿到 ESRCH，而那一支本来就被吞掉。

自保守卫比的是**组号**不是 pid：`'getpgrp' in process` 实测是 `false`，只能读 `/proc/self/stat`；
而实测 shell 底下 `pgid(15262) ≠ pid(15286)`，**比 pid 那一条永远不命中**，配它的负片也是假负片。

## 实测：改之前与改之后

```
改之前（只杀 worker）：心跳 21 → 33 → 45   还在长
改之后（真判定＋真执行）：
  计划：kid → group(-15306) → sweep
  执行完：心跳 14 → 14              停了
```

端到端也验过一次：真跑 `--jobs=2`，号文件 `w0.<派工pid>.verifier` 如期出现、里面是真的验证者号；
给派工进程发 SIGTERM，9 秒后隔离目录收掉、两个验证者都没了、`mutate` 相关进程剩 0 个。

## 三段窗口，照实写

- **窗口一（号还没到）**：从起验证者那句返回，到写号那句返回。中间只隔装两个监听器。
  派工若在这一段里硬来，读到的是「没有文件」，这一次照旧漏。**大小没量过，也不写一个没量过的数。**
- **窗口二（下一个编号已经在路上）**：至多一个编号（一条一派，手上不会有第二个）。
- **窗口三（死号）**：号写下之后、验证者已结束而抹号还没发生。读到死号时 `process.kill`
  答 ESRCH 被吞掉，**除非那个号已经被系统回收给了别人**，那一刀就落在不相干的组上，而且不响。
  温和那条路上原本会留整 5 秒（宽限期）的死号 —— 已经压掉：worker 一进来就先装抹号的处理函数，
  排在那个会退掉进程的处理函数之前。

**刀发出去就走，不等那一组真停下。** 从发出到真停下之间，已经交给内核的那一次写照样落盘 ——
`mutate-restore.ts` 上写着同一句，这里不能有第二种说法。

> ⚠️ 欠条：**真 worker 在硬杀之后仍然活着，本条没修。** 边界：它拿不到新编号（stdin 的写端
> 随派工退出而关），手上那一条的验证者已被第 ② 步收掉，于是它几乎立刻从等待里回来、还原、
> 写结论行拿到 EPIPE 死掉。残量是一个卡在别处（不是卡在等验证者）的 worker 会一直活着。
> 两条修法各带代价：让 worker 也 `detached` 再按组杀（代价：终端里 Ctrl-C 打的前台组从此
> 不含 worker，温和那条路从「本来就收到」退化成全靠转发），或者让号文件同时带上 worker 自己的号
> （代价：正文从一个数变成两个生命周期不同的数）· 重启条件：下一条碰 `hardStop` 或 `stopJobs` 的 PR

> ⚠️ 欠条：**ADR-72 里那条「让 worker 自成一组」的驳回，理由站不住。** 它按「够不到验证者」
> 否掉，而那个理由对的是另一个问题；对「够不够得到 worker 自己」它反而是唯一成立的那条。
> 只追加不删改，所以不回去改那一段 · 重启条件：下一条碰 ADR-72 那张欠条、或者动 worker
> 起法的 PR

> ⚠️ 欠条：**fd 到顶那一次硬来，号一个都读不出来。** 那时正是要开文件的时候而 fd 没了。
> 挡住的只是「不吭声」（读不动会出一句话），没挡住漏。实际暴露面是「`--jobs=` 派得很多
> **且** fd 到顶」· 重启条件：下一条把缺省并行度提到 40 以上、或者动 `hardStop` 读号那一段的 PR

> 同一处境 · 重启条件：下一条要让这套东西在非 Linux 上跑的 PR

## 第一轮评审揪出两处「注释说不许，代码就那么干了」

两处形状一样，都是**把「量到了但读不懂」压进「量出来是零」**：

| 在哪 | 头一版怎么写的 | 后果 |
|---|---|---|
| 写号那一句 | 把异常吞掉，而紧挨着的注释写着「不许留下孤儿」 | 验证者在跑、号文件不存在，派工读到 ENOENT 当成「压根没起」——**静默过继** |
| 算号那一步 | 号在却认不出（写了一半、不是个号）时既不出刀也不吭声 | 同上，而且这边照样删目录、照样报「收干净了」 |

改法：

- **写号失败就就地把那一组收掉。** 手上有号，用同一道判定算（同样的往返核对与自保守卫）；
  这一条于是没有结论 —— 而**没有结论不是通过**（`process/README.md` 总纲），
  下游当作「跑不起来」报出来，带着现场。
- **三种状态三条路**：没有号文件（没起验证者）不吭声；读不动（别的 errno）出一句话；
  **号在却认不得**也出一句话。第三种正是头一版漏掉的那一格，而它恰恰是本文自己
  在那段注释里骂过的形状。

值得单记的是**它是怎么藏住的**：这两处的注释里都写着正确的那句话，代码却是反的。
**一段说明意图的注释，会让写它的人以为意图已经实现了** —— 道理写得越清楚，
越难在同一屏里看见代码没照着做。

## 第五轮评审三条，两条是这一段自己在最坏的一格上放行

三条都标 Mandatory，核过都成立。

**一、抹号那两步都失败时，它一声不响地接着跑。** `forgetVerifier` 先写空作废、再删；
两句各自 `catch` 掉。可**两句都失败**（只读、盘满）时，文件里留着的还是一个**合法的号** ——
而这个 worker 紧接着就去接下一条，那个号迟早被系统回收分给别人，下一次硬来就对着
无关的一组开刀。**那正是这一整段注释逐字要挡的「死号」那一格，而它自己在最坏的一格上放行。**
改成两步都没成就把在途变异还原掉、就地停。四格逐个注入跑过：

```
作废成 删成 → 继续    作废成 删败 → 继续（文件成空的，硬来读到「认不得」，出话不发刀）
作废败 删成 → 继续    作废败 删败 → **停下**
```

（「删败」不含「文件本来就不在」—— 实测 `rmSync(不存在的路径, { force: true })` 不抛。）

**二、硬来里出那句话的写没有兜。** `writeFileSync(2, …)` 抛出去（stderr 成了坏 fd、
管道那头先走）会把它**后面的收目录和显式退出整段掀掉**。讽刺的是紧挨着的 `rmSync`
那一支兜了，理由还逐字写着「比让异常冒上去盖掉上面那句真正的诊断强」—— 上面那句自己没兜。

第三条是并发，登记在下面。

> ⚠️ 欠条：**两个派工同时跑，后来的那个把先来的那份号文件抹掉。** `dispatch` 开头把
> 共享的那个根目录整棵删掉，而各 worker 的目录叫 `w0`、`w1`…… 两跑同名。实测：先在
> `w0` 里放一个标记，另起一个 `--jobs=2` 的跑，25 秒后标记没了。于是先来那个派工硬来时
> 读到 ENOENT —— 判定把它当成「没号」，**一声不响**放过，它底下的验证者那一组就留着了
> （#116 第五轮评审指出）。**号文件名里带派工 pid 挡不住这一格**：被删掉的是它上面那一层。
> 根因比本条早 —— 那一句整删和 `w<i>` 同名都是主干上就有的，两跑本来就会互相拆掉对方的
> 隔离树（同一次实测），本条只是往这个已经坏了的场景里又添了一格**不响**的；按
> `6-INTEGRATE.md:240` 归**既有缺陷**。正确的修法是把整个作业目录按派工 pid 分开，
> 连 `beaconPathOf` 的形状一起变，动到判定、单测与 `M-H40-*`，按 `:235` 是扩范围 ·

## 硬来那一刀有了自检夹具（还第 198 行，2026-11-12）

**做了什么。** 第 198 行那张欠条：入口里真发那一刀的那一句（`hardStop` 照 `hardStopPlan` 给读得出号的验证者组发 SIGKILL 的那一句）删掉，单测与变异照样全绿；夹具当时已经造出来、两头验过，因为体量没进那条 PR。这一片照第 174–191 行的语料与驱动写成自检组 `jobs-hard-stop`：

- **语料**：两条变异、`--jobs=2`。验证者分出一个孙子（不 `detached`、不接管道），孙子隔一小会往自己那份心跳文件追加一个字节，文件名带孙子自己的号；验证者自己挂住不退。两者都有上限，坏掉时不把整份检查挂住；上限比驱动最长的等待还长，否则量的时候孙子已经自己停了，删掉那一刀也照绿。
- **驱动**：一个 `.cjs`，写进这一跑的临时目录，自检同步起它。等两份号文件（`w<i>.<派工pid>.verifier`，里面是个合法的号）与两份心跳都有了，从号文件的名字里拿派工进程的号，读 `/proc/<派工>/task/<派工>/children` 拿到 worker 壳，再读各个壳的子进程表拿到壳底下真跑的 worker；先把真 worker 冻住（SIGSTOP），再把壳全部 SIGKILL，然后给派工发 SIGTERM；等它退出，量一次心跳、隔一会再量一次，再按 `/proc/<pid>/stat` 里的组号数一遍记下的验证者组里还活着的进程（僵尸不算：被杀的验证者父进程是冻住的 worker，收不了尸），看隔离目录在不在。驱动边等边记下读到的每个验证者号；最后不论结果，都给这些组补一刀 SIGKILL、把冻住的真 worker 杀掉，没等到派工退出就收场的那一跑，再按 `/proc` 的进程树把派工底下的进程逐个 SIGKILL，红的那一跑也不留孤儿。
- **三条具名断言**：验证者那一组被收掉、孙子的心跳停了（两样都看：那几组没有活着的进程，心跳也不长了。CodeRabbit 第二轮指出初稿只看心跳，孙子停了而验证者活着也会绿）；隔离目录收干净了；以退出码 1 收场。号文件或心跳没齐、派工底下不是恰好两个壳且各带一个真 worker、量心跳的那两次读不到或哪一次量到的不是两份、数验证者组时读 `/proc` 出了「进程刚好没了」以外的错、从心跳齐了到量完拖过了驱动定的上限，都按夹具没造对报，带夹具记号（读不到时退回空表的话，两次都量成零，「心跳停了」白白成立）；读不到子进程表（Linux 之外、内核没开）明着降级、不判 —— 开跑之前先探自检本进程的那一份，探不到就不起派工，起了之后才读不到的由驱动降级。驱动要的环境从标准输入交过去，不放进命令行（CodeRabbit 指出：命令行谁都列得出来，环境里有继承来的令牌）。
- 每一跑的心跳文件都是新的：临时目录是这一跑建的，文件名又带孙子的号（第 188–189 行那个坑）。

**让真 worker 动不了是承重的。** 实测：驱动不杀壳、不冻 worker，同时把入口那一刀删掉，这一组照绿 —— SIGTERM 经壳转发给 worker，worker 自己的打断处理就把验证者那一组收了，轮不到硬来那一刀。初稿只杀壳：真 worker 收不到转发、管道没关，`close` 不来，宽限期到点走硬来。可它还活着：验证者那一组被收掉之后，它从等待里回来、还原副本、抹号（第 122–127 行那张欠条写的正是这一段），正赶上硬来递归删隔离目录，新写的文件让删抛出来、目录留下。初稿在 nobody 身份的整跑里（自检拆成四个子进程并行）撞上过一次：「隔离目录收干净了」红。日志只留了末几行，没留下删目录时那句话，所以是哪一种写撞上的，是按形状推的。那是入口那张欠条的残量，不该由这一组替它判红。现在先冻住真 worker 再杀壳：冻住的 worker 什么也不做，宽限期到点硬来，删目录时没人跟它抢。冻住而不杀：杀了它管道就关，派工那边「收到 SIGTERM」与「worker 没了」谁先到说不准，走的未必是硬来那一条。

**怎么验的。** 本地把 `hardStop` 里发那一刀的那一句换成空的，只跑这一组：「心跳停了」那条红，派工退出之后心跳还在长，另两条绿；原样绿。验证者两种起法各试了一遍（照今天经 tsx；`runTest` 临时改成直接拿当前 node 起），结论一样；改成冻住之后两种起法又各试了一遍。只冻不杀壳、删掉那一刀，同样红。加上数组里活着的进程之后又试了一遍：原样绿；删掉那一刀、或改成正 pid 只杀组长，都红；删掉那一刀、同时让孙子几秒后自己停，心跳不长了，只有数进程那一半红，正是 CodeRabbit 说的那种情形；裸 node 起验证者，原样绿、删掉那一刀红。worker 照旧只经 tsx 起（`tsxCommand`），这一组只走那一种。这些改动都没留下。本机连跑与几份并发同跑都绿；跑完用 `ps` 列过进程表（僵尸也列得出，ADR-133 第一节），没有这一组起的进程留下。另把驱动临时改成等不齐、按夹具没造对收场跑了一次：带夹具记号红，同样没留下进程。

**没有负片。** `mutate.ts` 在验证基础设施闭包里：指名自检的变异被「自己验自己」拦下；指名需求测试的施得上，可需求测试走不到派工 —— 真起 `mutate.ts` 的只有 `h-worker-output-contract`，它起的是单个 worker（`--worker`），不经派工，硬来那一步走不到。理由与 ADR-70 末尾同日那一节同，余额合挂在那一节末的欠条上。

**已知边界。**
- 孙子若 `detached`，这一组也会红：那是第 201 行那张欠条说的情形，不是入口坏了。
- 真入口上硬来时，活着的 worker 照旧会去还原、抹号，赶上删目录就留下目录（第 122–127 行那张欠条的残量，初稿夹具在整跑里撞上过，见上）。这一组把真 worker 冻住，不替那张欠条判红，也就验不到它。
- 红绿取决于时刻：派工退出之后隔一下才量，那一刀发出到孙子真停若拖过了这一下，会误红；心跳的上限先到会误绿，所以拖过驱动定的上限的那一跑不判。这一组没进 `TIME_WINDOW_GROUPS`，登在 ADR-70 末节那张欠条里。

## 作业目录按派工进程分开（还第 237 行，2026-11-13）

**做了什么。** 第 237 行那张：`dispatch` 开头整删作业根 `.check-cache/mutate-jobs`，worker 目录又都叫 `w0`、`w1`……同一棵树上两跑同时开，后来的那个把先来的那份连号文件一起抹掉；先来的那个硬来时读到 ENOENT，当成「没号」一声不响放过，它底下的验证者那一组就留着了。现在：
- 每一跑的作业目录是作业根底下以派工进程号命名的一层（`jobs-rule.ts` 的 `jobsRunDir`），worker 副本、号文件（`beaconPathOf`，现在是 `<那一层>/w<i>.verifier`，名字里不再带派工进程的号 —— 那一层已经带了）、正常基线的副本与启动数日志都在这一层里。
- 开工前（派工与正常基线两处）只清自己这一层，再清**进程已不在**的那几层（判定 `staleRunDirs`：名字是一个正整数、那个进程问得出已不在；问不出来的算在；名字不是号的不碰）。原先「下一跑开头整删」顺带收掉被硬杀那一跑的半成品，各删各的之后这件事要另判，不然那一层永远没人收。
- 收尾（正常跑完、硬来、正常基线被打断或跑完）删自己这一层，作业根空了一并删掉，还有别人就留着。硬来那句「半成品副本留在……」改成指向这一层，后半句改成「以后哪一跑开头见这个进程已不在就会清掉」。

第 237 行写的修法是「整个作业目录按派工 pid 分开（`JOBS_DIR/<pid>/w<i>`），连 `beaconPathOf` 的形状一起变，动到判定、单测与 `M-H40-*`」，照做了；清「已不在的那几层」是那句修法没写、分开之后自然多出来的一件。

**变异。** `M-H40-m` 原先守「号文件名里带派工进程的号」，那一格挪到了 `jobsRunDir`：改成点它，把那一层换回作业根本身（两跑共用一处），`kills` 加上新单测「两跑的作业目录不一样」，原有那条「两跑的路径不一样」照旧点名。新加两条：`M-H40-y`（不问进程还在不在就清）、`M-H40-z`（不认名字就清）。三条在本地逐条施加（`mutate --worker`）都 `caught`。

**入口那一半由自检夹具守，没有负片。** 新组 `mutate-jobs-per-run`：在玩具树的作业根底下先摆三样 —— 自检自己这个进程号的一层（整跑期间都在，站「另一跑还在用」，里面放一份隔离副本里的记号和一份号文件）、一个已退出进程号的一层（站「被硬杀的那一跑留下的」）、一个名字不是号的 `w0`（站旧布局）——再真起一跑 `--jobs=2` 派工。断言：照常跑完；第一样原样留着；第二样清掉；第三样不碰；这一跑自己那一层收干净、作业根因为还有别人而留着。实测会红：开工前换回整删作业根（三条红）；收尾换成整删作业根（三条红）。入口在自检的验证基础设施闭包里，指名自检的变异被「自己验自己」拦下；`by: test` 不被拦，但需求测试不在有别的跑的作业根上起派工，所以没配负片，同本文第 198 行那一节的处境。

`jobs-hard-stop` 那一组的驱动原先从作业根底下的 `w<i>.<派工pid>.verifier` 认号与派工进程，改成从 `<派工进程号>/w<i>.verifier` 认。**更正第 198 行那一节「驱动」那一条的形状说明**：号文件现在是 `<派工进程号>/w<i>.verifier`，派工进程的号从层名拿；那一节原文没动。

**没有新闸门**，是把一句整删换成各删各的，不写撤除条件。

**已知边界，照实记。**
- 号被系统回收给一个不相干的进程时，那一层会一直留着（只占盘，不误删）。
- 共用同一棵树、却不在同一个进程号空间里的两跑（比如一跑在容器里、一跑在宿主上）会把对方那一层当成「已不在」清掉 —— 本条要堵的那一格在这种布置下还开着。
- 旧布局留下的东西（升级之前的 `w0`、`baseline-0`、号文件、启动数日志）不清，作业根因此可能一直不空；它们不进 worker 副本（`copyIntoWorker` 整个跳过 `.check-cache`），只占盘。
- 本条只管派工那条路的作业目录。串行那条路（只派一个时）是在主树上改写源文件、跑完还原的，两跑同时开时那一格本条没碰；两跑共用的产出位置（启动数摘要、认领文件等）也没碰。

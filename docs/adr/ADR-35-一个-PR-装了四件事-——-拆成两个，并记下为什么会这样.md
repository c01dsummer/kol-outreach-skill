# ADR-35 一个 PR 装了四件事 —— 拆成两个，并记下为什么会这样

- 日期 · 2026-08-28 · 用户在第十四轮之后问「最开始我想让你做什么，为什么改了四千多行」
- 类型：**范围失控**（不是事实证伪 —— 每一步都对，是总和从来没被评定过）
- 冲击的需求：无。这条冲击的是**做事的方式**
- 结论：**采纳**，拆成两个 PR

### 事实

最初的请求是一个**问题**：「需求冲突、迭代和更新你怎么看？需求本身要不要做版本管理？」
授权实现的是后来的一句 `do it`，它授权的是一件有边界的事：
D4×P4 那条红线的修复 + 配套测试和变异。

最终这个 PR 是 4362 行，其中真正改行为的产品代码 433 行（9%）。

### 它是怎么长这么大的

一部分是**后来授权的**，而且是有意的乘数：

| 授权 | 带出了什么 |
|---|---|
| `do them all` | 整套登记表机器：内容指纹、决策记录反链、作废、交点 |
| 「验收标准拆成可独立计量的条目」 | 35 条需求变成 81 条判据，`criterion` 机制，审计改造 |

另一部分**没有任何人授权** —— 十四轮外部评审，每一轮我都做了四件事，
而被要求的只有第一件：

1. 修这一条
2. 把同一类都堵上
3. 写一条决策记录
4. 往通用规则里加一行

单看每一步都站得住。十四轮复利下来，决策记录占了全部篇幅的三分之一。

### 怎么拆的

- **本 PR**：D4×P4 的红线修复 —— `memory.ts` 的三档状态、原子写回、
  键的规范化与形状校验、`--ignore-memory` 逃生舱，以及它们的测试与变异
- **后续 PR**：需求登记表的机器 —— 内容指纹、判据、交点、作废、
  `spec-rule.ts` / `claims.ts` / `attribution-rule.ts`，以及审计的改造

**决策记录整份留在本 PR，不拆。** 二十条里有八条是「一条记两件事」的
（比如 ADR-30「红线不许作废」与「硬杀留下的临时文件」），
按代码归属切开会把当时真实的推理切成两半假的。代价是：本 PR 的
ADR-17、ADR-33、ADR-34 讲的是后续 PR 才会出现的文件 —— 看到那里请回到这一条。

> **这个决定在 ADR-54 被推翻了一半。** 那些讲别的 PR 的记录已经移走了，
> 编号留着空位不复用。「一条记两件事」的那八条仍然不拆，理由不变。

### 教训

**我对每一条进来的意见都做了评定，唯独没有对「我自己已经做了多少」做评定。**

`2-CHANGE.md` 写着：反向输入必须走评定，**不许悄悄消化**。我在下一层
一丝不苟地执行了这条规则 —— 十四轮、每一条评审意见都验证、都记录、都回复。
而在上一层，「范围已经涨到哪了」这个问题一次都没有被提出来。

规则是「每一条输入都要评定」，我读成了「每一条输入都要评定」。
**漏掉的是：总和也是一条输入。**

一个可执行的补法：**改动超出授权时的原始范围时，把它当成一次反向输入**
—— 走同样的评定，交给当初授权的人，而不是自己吸收掉。

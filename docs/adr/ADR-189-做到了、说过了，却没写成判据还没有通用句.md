## 给 process/ 的候选句

```
实现已经做到、也已经对用户说出口的对外行为，在说出口的那一次就写成带编号、可失败的判据；
不要等到测试要冻结期待值、找公开出处时，才回头照现行实现补写。
```

拟放在：`process/1-REQUIREMENTS.md`「什么时候需求算写完了」。这三条都是需求登记表在当时被当成写完了、其实漏了已经兑现的行为，管的是需求什么时候算写完，放那一节最近。

来源：
- ADR-183 第 7 行：collect 的收尾标签与退出码怎么对应，原先只散在说明文字里，没有判据，照现行实现补写 D6.x 与对照表，行为不改。
- ADR-184 第 7 行：新建任务缺预算时按 2 美元写进 task.json，现行实现早就这么做，照现行实现补写 D13.t，行为不改。
- ADR-185 第 7 行：记忆读不出来时原文件不被改动，现行实现做到了、也对用户说过，登记表只有半句，照现行实现补写 D4.s，行为不改。

## 要搬、要拒

- 要搬：需求所有者另开一条 PR 改 `process/`，同一条 PR 在本条末尾追加一块，头一行写成
  `> ⚠️ 上文那张「process/ 里没有这句通用话」欠条已还：搬进了 process/<文件>「<节>」，批准它的是 #<号>`。
- 要拒：在本条末尾追加一块，头一行以 `> ⚠️ 驳回：` 开头（「驳回」后面直接接冒号，不加括注），写为什么（比如 `process/` 哪一句已经说了），
  不写重启条件；也可以在这条 PR 上直接追加，再合。关掉 PR 不合不算驳回，下一跑照样为这一类起草。驳回以后，欠条括号里出现这条记录「这一类」
  以外的编号之前（那张欠条写在驳回前还是驳回后都算），例程不再为它起草；是不是驳回以后才添的，起草时写进「驳回过」，由需求所有者判。

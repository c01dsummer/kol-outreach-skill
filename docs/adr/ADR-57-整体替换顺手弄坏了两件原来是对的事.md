# ADR-57 整体替换顺手弄坏了两件原来是对的事

- 日期 · 2026-08-31 · 外部评审（两条，都属实）
- 类型：**事实证伪**
- 冲击的需求：D4
- 结论：**采纳两条**

### 事实

两条都不是「新功能没做」，是**这个改动把原来对的行为改坏了**，
而且两条的坏法都是静默的。

**一、目标是软链时，改名换掉的是链接本身。**

`memory/creators.json` 是一条指向别处的软链时（用户把它放在同步目录、
或者多个工作副本共用一份），`statSync` 跟着链接看到了终点的权限位，
而 `renameSync(tmp, file)` 换掉的是**链接**。第一次写回之后：

| | 换成整体替换之前 | 之后 |
|---|---|---|
| 链接还在吗 | ✅ 还是链接 | ❌ 变成普通文件 |
| 真正那份 | ✅ 写进去了 | ❌ 停在旧内容 |
| 交付物怎么说 | 已记入 | **也说已记入** |

真正那份记忆从此不再更新，而每一次都报成功。**静默地停止记录**，
正是这条需求存在的理由要防的那一种 —— 由它自己引入。

改成整体替换之前，这里是一次普通的 `writeFileSync`，它跟着链接写到终点。
**所以这不是补一个新能力，是把顺手弄坏的行为还回去。**

**二、新文件停在了临时文件那一档最严的权限。**

临时文件建的时候就给 `0600`（ADR-42：不能先按 umask 建再收紧，
完整内容在那段窗口里是别人读得到的）。然后只有目标已存在时才 `chmod`
回它原来的权限位 —— **目标不存在时没有任何一步把它调回去**，于是新文件
是 `0600`。而同一个函数上方的注释写着「目标不存在时保持 umask 默认：
新文件该多严是产品决定，不在这里替它定」。

实测：umask 022 下，新文件 `600`，默认应为 `644`。

这个函数写的不只是记忆，还有 `task.json`、名单、增强结果。
**一个临时文件的实现细节，替产品决定了所有新建文件的权限。**

### 修法

- 写之前顺着软链找到终点（`followLinks`），临时文件建在终点那一层，
  改名也改在那一层。不用 `realpathSync` —— 它要求终点存在，
  而**终点不存在时该写的正是那个终点**，不是把链接换掉。
  解不出来时（不是 EINVAL / ENOENT）**抛，不猜** —— 和 `isAbsence` 同一条规矩。
- `chmod` 从「只在目标存在时做」改成**总是做**：已有的带回原权限，
  新的还原成 `0666 & ~umask`。

两条各配一条变异（`M-D4-x` / `M-D4-w`）。权限那一行现在担着两件事，
所以 `M-D4-m` 与 `M-D4-w` 分别打它的两半，不是重复。

### 教训

**「换一个更强的实现」和「保持原有行为」是两件事，而后者没人会替你检查。**

从 `writeFileSync` 换到「临时文件 + 改名」，收益是原子性，
代价是这个操作的**每一个副作用都变了**：它作用在哪个 inode 上、
新文件的权限从哪来、目标是链接时会发生什么。这些原先不用想，
因为 `writeFileSync` 的语义就是对的。

需求、测试、变异守的都是「新实现该做到什么」，**没有一条守着
「旧实现已经做到、不该丢的那些」**。所以两条都不是被检查链发现的。

判据，写给下一次换实现的人：**先列出旧实现的语义清单，逐条问新的还成不成立。**
对文件写入至少是这四条：写在哪个 inode、权限从哪来、目标是链接时怎么办、
中途失败留下什么。

这也是 ADR-56 那条的放大版：那次是「契约只兑现在一部分路径」，
这次是「替换只保住了一部分语义」。**两次都是我知道那个性质、
却只在当时看着的那条路上兑现了它。**

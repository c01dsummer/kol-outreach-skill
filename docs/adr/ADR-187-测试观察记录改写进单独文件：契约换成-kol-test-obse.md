## 一、改了什么

记录不再写进 stderr。设了环境变量 `KOL_TEST_OBSERVER_EVENTS` 时，入口一启动就以追加方式打开它指的文件，就绪、预留、命中、未命中四种记录一条一行写进去，行首没有前缀；stdout 和 stderr 一个字节都不因此多写。没设或值为空时与没有这一节完全相同。

原来两样东西各自开关：开关管预留事件，控制文件 `.kol-save-fault.json` 放着就注入。现在注入也只在设了记录文件时生效 —— 命中与未命中记录要有地方写，而平时误放一个控制文件，collect 就会以保存失败收尾，这也是 ADR-186 第三节第二段担心的那一面。

新加一条：记录文件打不开或写不进时，入口在 stderr 说出是哪个文件、以 1 退出。启动时打不开的什么输入都没读；中途写不进的停在那一句，还没发出的请求都不再发。写的是 `reserved` 记录时，那一次请求也就没发；collect、enrich 的这笔预留已经存进任务账，`task.json` 里留着它，下次续跑照「恢复未结项」处理，和预留之后被杀一样（probe 的预留只在本进程里，退出就没了；`rejected` 记录写不进时，账上没有因这一次多出未结预留）。`SP-200`、`SP-N200`、`SP-NS` 的命中记录在那次请求之后才写，写不进时它已经发出去了，停下的是之后的。未命中记录在退出时写，那一跑可能一次请求都没发（例如参数不对就退出），它不说明发过请求。

## 三、实现怎么对上原文

ADR-186 第二节那张表照旧成立，只有下面几行换了：

| 原文 | 实现 |
|---|---|
| 「入口一启动就打开这个文件：不存在就新建，已存在就接着往后写，不清空」 | `obsReady` 是三个入口 import 之后的第一句，在那里以 `'a'` 打开、写就绪记录；已存在的文件最后一行没有以换行结束时，先补一个换行再写（「每条记录占一整行」），读不出最后一个字节就当以换行结束 |
| 「每条记录占一整行，是一个单行 JSON 对象，以换行结束」 | 每条记录拼成一整段字节，同步写到写完为止；入口出错会立刻 `process.exit`，排队没写出去的会丢，所以不用异步写 |
| 「打不开或写不进去时……以 1 退出」 | 打开与每一次写都包在同一处：stderr 说出变量名、文件路径与原因，`process.exit(1)`；在 `exit` 事件里写未命中记录时失败也走这一处，Node 在退出途中再调 `process.exit(1)` 照样以 1 收尾 |
| 「也只在设了 `KOL_TEST_OBSERVER_EVENTS` 时生效」 | collect 读控制文件排在 `obsReady` 之后，没打开记录文件就不读 |

ADR-186 第二节那张表最后一行说的 fd 2 不阻塞、写回 EAGAIN 时等着整行写完，那是写管道才有的事；记录写进普通文件，那一段连同它的一例自检、两条变异一起撤下。

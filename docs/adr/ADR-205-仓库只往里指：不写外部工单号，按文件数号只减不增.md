## 一、规矩在本仓库是哪几个字

`process/` 不写本仓库的字眼（`docs/SYNC.md`「一条判别规则」），具体是什么记在这里：

- **外部任务工具**：Linear，一个团队，卡号前缀 `KOL`。
- **工单号**：`KOL-` 接数字，不分大小写 —— Linear 给的分支名是小写的（`kol-` 接数字再接标题），旧记录里引过好几个这样的分支名。不带数字的 `KOL` 不算，那是产品名里的词。
- **指向一张卡的链接**：linear.app 上路径里带 `/issue/` 的。指向项目页的（`AGENTS.md`「开工前按顺序读」表里接手任务那一行、ADR-181 第四节）是路由，不算。
- **仓库里的文字**：受控文件全部，不分目录。`skill/` 本来就一个号都没有；决策记录、`docs/`、`scripts/`、工作流都算。
- **不受这条管的**：PR 标题与正文、分支名本身、提交信息。Linear 的 GitHub 联动靠它们把 PR 挂到卡上；提交信息不要求写，也不禁止 —— 它是改动的来历，不是仓库里的文字。但新写的文字里**引**一个带号的分支名，那个号就成了仓库里的文字。

不分大小写以后，第一片合入时的主干 `ed355e6` 上数到 427 处（大写 392 处之外，多出的 35 处都是旧决策记录里引的小写分支名），28 个不同的号。ADR-204 的对照表里 27 个；缺的那一个只出现在一个小写分支名里（ADR-79「并行准备的 #402 欠条登记」那句），同一句已经写明那是哪条 PR、改的是哪份记录，不用再对照。

## 二、检查怎么判

`npm run ticket-refs`，检查链里排在体量闸门（`npm run size`）与变异负载闸门（`npm run shard-load`）之后：

1. 起点与体量闸门同一个判定（`size-rule.ts` 的 `resolveBaseline`）：分支上是与主干的共同祖先，主干上是上一版。浅克隆、找不到主干、没有共同祖先 —— 无从判断，以 1 结束；主干上只有一个提交 —— 不适用，以 0 结束。
2. 用 `git grep -o -i` 从仓库根数两边：基线那个提交的树，与工作区里的受控文件（没提交的改动也算）。每处一行，同一行两个号算两个。卡片链接只数网址里会出现的字符（字母、数字与 `_./#?=&%-`），链接末尾带着的号随链接算一处；链接后面紧跟中文标点再写的号单算。颜色关掉，本机配了总是上色也不影响。
3. 逐本账比：**比基线多就红**；基线上没有的文件（新文件、改了名的文件）按零个算。少了的列出来，不红。一份文件一本账，只有一个例外：决策记录的主文件与 `docs/adr/历史/` 下的同名历史文件**合一本账**。ADR-211 拆记录时把旧正文一字不改地搬进历史文件，号跟着搬过去、也不能删；合在一本账上，搬家不算多，搬完再往哪一份里添号才算。
4. 主干上只报数不判定，与体量闸门同一个理由：CI 跑在推送之后，判红只会让主干变红。
5. 退出码只设在进程上、不当场退出（同 ADR-202「退出码只设不退」）：多了的文件一长串时，接在管道上的输出不会被截掉。

为什么按文件记数、不按 diff 的新增行：决策记录追加不删改，旧记录里的号删不掉、也不该逼人删；按 diff 判，往旧记录末尾追加一块、块里引了一句带号的旧话，就分不清是新写的还是抄的。按文件数，「那份文件里的号变多了」是一个不用解释的事实，需求所有者 06:48Z 那句「旧adr也要防止它们后续继续追加卡号」正是这个。代价：改名一份带号的文件会红（新路径按零个算）—— 这时一并把号撤掉，正是规矩要的。拆记录不在这个代价里，见第 3 步。

## 三、认不出的

本条只认上面两种写法。下面这些认不出，读的人要知道闸门绿了不等于没有：

- 不带号、只说「卡片」「那张卡」的话：没有号可数。仓库里还有这类句子（例如 `scripts/check/selfcheck.ts` 里「与卡片「复现步骤与实测结果」一致」），本条不改，读的时候知道它指向仓库外。
- 号的变体：字母与数字之间隔了别的字、换成下划线、空格或全角横线；`linear.app` 以外的写法。
- 一份文件里把一个号换成另一个号：个数没变。
- `git` 当成二进制的文件（`.gitattributes` 标了的，或混进一个空字节的），`-I` 跳过它们。
- 没 `git add` 的新文件、只在暂存区里的改动：提交之后就数得到，CI 上数的是提交。
- 主干上直推：只报数（同体量闸门，那是分支保护的活）。
- 基线上已有的号：留着。对照见 ADR-204。

第二、三条记成末尾两张欠条；其余的要么提交后就数得到，要么是有意不管。

## 四、它替代什么、什么时候撤

**替代的是「跑」，不替代「读」**（`process/README.md` 第二层「一道闸门该不该建」）。它做的是数一个数、和起点比：同一棵树永远同一个结论，判据是一条命令。它认的写法是一张手写的正则，这一点和「替代读的那些不要建」说的「一张手写的名单、映射或正则」形状一样，所以说清楚为什么不算：要守的是这个仓库里**一个工具、一个团队**的号，写法是 Linear 定的，集合是闭的、今天就列得全；号的变体和别的工具不在它守的范围里，第三节写明了，报数那一行也只说「认得出的」。哪天集合不再是闭的（第二个团队、第二个工具），就是末尾那张欠条响的时候。

**同类判过、不算一例**：「要守的是一整类，落地成手写清单」那一类（ADR-71、ADR-77、ADR-180、ADR-192 记过四次）说的是清单盖不住那一类、明天会漏。本条清单盖住的就是今天整个集合，漏的只有变体，变体写在第三节。

> **什么条件下退成只报数**：连续 8 周里，PR 上它变红的每一次，改法都不是撤掉一个号（只是改了它、或绕开它），即它一次真问题都没拦到

> **什么条件下整个撤掉**：项目不再用外部任务工具；或仓库里认得出的号数到零 —— 那时换成「一处都不许有」，按文件记账这一套整个撤掉

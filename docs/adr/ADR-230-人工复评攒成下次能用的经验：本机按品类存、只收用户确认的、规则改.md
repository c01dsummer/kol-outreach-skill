## 一、这次做什么：规矩和实现一起落地

选择题第 1 题原先推荐先只写规矩、实现另开一件，理由是经验写错了会带偏后面每一个同品类任务，先把边界写成需求批下来再动手。需求所有者看到「多数条款暂时没有代码可测」后问为什么，听完解释回「一起吧」：规矩与实现在同一条改动里，判据尽量都由真实调用的代码和测试认领。

所以本条既立 D31，也让 Agent 真的读写经验库：语义筛选前读同品类那一份，报告里说清读了什么；用户在复评表里与 Agent 判得不一样时，报告提示可以沉淀成经验，Agent 按分歧起草，用户在对话里明确收下才写进库。

## 二、D31 写了什么（对照选择题第 2–10 题，外加几处）

选择题第 1 题定的是这次做多大（见第一节），第 11 题定的是工单怎么关，都不进需求正文。

1. **存在哪**（第 2 题）：本机 `memory/lessons/<品类名>.json`，每个品类一个文件；品类名不能指到别处，换到 Windows 上也要建得成（不许路径分隔符、以点开头或结尾、控制字符、首尾空白、`< > : " | ? *`、`CON`、`NUL` 这类保留设备名，不超过 80 个字）（D31.a）；仓库的忽略规则把这些文件挡在 git 之外（D31.b）；写经验不往 `skill/` 写任何东西（D31.c）。选择题写的是「`memory/` 下」，实现时多开了一层 `lessons/`：品类名由用户的产品定，直接放在 `memory/` 下，一个叫 creators 的品类就会撞上已联系名单 `memory/creators.json`。共享与否跟着 D4（跨任务记忆那一条）走，本条不另写 —— D4 以后改成多人共享时，不用连带改 D31。D4 若改成把 `memory/` 做成一条指向共享目录的符号链接，D31.b 那组测试只抄忽略规则、不建链接，要跟着补一种造法：今天的忽略规则写的是 `memory/`（带斜杠只挡目录），挡不住同名的符号链接（ADR-72 有一张欠条专管这件事）。
2. **一条经验长什么样**（第 4 题）：五项缺一不收 —— 局面、教训、证据（任务、平台、账号、复评轮次、人工怎么答、Agent 怎么判）、归因（「能归到这一条」或「混杂」）、规则版本（D31.d）。归因可以写「混杂」，借的是 harness2 经验库的做法（ADR-157 第一节引过）：一个偶然的例子不能当规律。规则版本与写入时间由写入命令在写入那一刻自己填，草稿里带了整条不收（D31.e）：不许起草的一方替这条经验报版本。
3. **只记局面和判断**（第 7 题）：局面写成以后还认得出的情境形状、不写某一次的具体事实，也不收能直接照抄进开发信或评审理由的现成句子（D31.f）。Agent 会照着现成句子抄，下一个任务的产出就成了模板；两样都要读句子本身才判得出，放在同一条豁免里由人看。
4. **谁批**（第 5 题）：写入命令不带 `--confirmed-by-user` 一律不写，以 2 退出（D31.g）；Agent 只起草，用户在对话里明确收下后才替用户带上这个开关（D31.h）。机器核不了用户真说过没有，这个开关只防 Agent 顺手就写。
5. **规则版本三种状态**（第 6 题，来自 2026-10-22 pstack 研究页那条「值得做」的建议）：版本是写入那一刻 `skill/` 全部内容的指纹，读不出来记「未知」（D31.i）；读的时候每条落在且只落在「同一版本」「写于规则改动之前」「版本未知」三种之一（D31.j）；后两种读的命令照常读出、每条标出状态（D31.k），数据边界逐条列出、写明状态（D31.v），不为此停下问用户（D31.o）。指纹取整个 `skill/`，不只取语义筛选那几份：改了哪份会影响判断说不清，宁可多标几条「写于规则改动之前」，也不漏标。
6. **同品类怎么认**（第 3 题）：读只读与本任务品类名同名那一份，没有就照常以 0 结束（D31.l）；有命令列出已有品类名（D31.m），起名前先看、能沿用就沿用（D31.n），不为此追问用户（D31.o，与上一条「版本对不上不问」同是对话里不问的事，放在一条）。不多问一句，是因为开工前要问的事正在另一件需求里压到三件以内。
7. **什么时候起草**（第 9 题）：人工复评表与 Agent 判断有分歧时，重出的报告在分歧那一段后面提示可以沉淀成经验、确认后才写入（D31.p）；Agent 交付这份报告时主动在对话里按分歧附上草稿，不等用户开口要（D31.x）；不为攒经验去要复评表或回填（D31.q，与 S3 相接）。选择题写的是「下次重出报告附一段草稿」，实现时草稿不进报告文件、由 Agent 在交付时附在对话里：起草要读分歧账号的内容、写局面和教训，是判断，render 是机械的一步，写不出也不该写。附在对话里仍是主动给，不是第 9 题放弃的「只在用户明说时起草」（复核指出初稿写成了等用户开口，已改）。
8. **管到哪**（第 8 题）：不改评分、分层与采用建议的规则，评审正本相同时读没读经验，同一个任务交出的名单完全一样（D31.r）；经验的命令不读写已联系、拉黑、已回复三个标记，跑完 `memory/creators.json` 一字不变（D31.s）。分层由语义判断决定（F6），经验改了 Agent 的判断，分层结果当然会跟着变；D31.r 禁的是绕过判断直接动规则。
9. **读不出来怎么办**（第 10 题）：读的命令照常以 0 结束，数据边界写明没读到及原因、不当成空的（D31.t）；读的时候不动原文件，往里写的时候拒绝写入（D31.u），免得只剩新一条的文件把原来的经验盖掉。这与「已联系名单读不出来就不出名单」（D4.e）不同：经验库只是参考，缺了不会让已联系过的人再进名单；已联系名单缺了会。

另外几处不在选择题里：

- **共享与同时写入跟着 D4 走**（需求正文末句）：执行稿原有的一句，免得两条需求各写一遍「不共享」，D4 一改就要连带改。复核实测同时跑六个写入只留下五条，与已联系名单同样不加锁；Skill 写明一条一条写。
- **交付时说清读了哪几条**（D31.v）：执行稿原有的一项，「读了」指读进来的全部，不只是用上的。
- **四种「没读到」分开写**（D31.w）：「这次没有读」「没有这一品类」「有这一份但零条」「读了什么的记录本身读不出来」，是红线 P1（「没查」与「查了为空」要分得开）推出来的。

### 怎么做的

- **读的输出里，状态与序号由命令算出、盖在经验自带的同名键上**：经验库是可手改的文件，一条经验里多写一个 `state` 不能冒充现行状态（复核实测过）。
- **经验库文件认 `version: 1`**，别的版本号整份算读不出来：以后换了写法的文件不能被按旧写法读歪。
- **`skill/` 本身是一条符号链接时跟着链接走**：装到用户机器上常这样，只记链接指向会把改过的规则算成同一版本（复核实测过）。
- **读与报告是两个进程，靠任务目录里一份读取记录接上。** Agent 在语义筛选前跑 `lessons read`，它在任务目录写 `lessons-read.json`（读了哪个品类、哪个文件、三态之一、每条的序号、状态、局面）；render 读这份记录写进 `meta.json` 的 `lessons`，报告的数据边界照它出一句。没有这份记录就是没读过，不写成「没有经验」。render 不自己去读经验库：读经验是语义筛选前的事，render 在后面，那时经验库可能已经变了。
- **经验库文件**是 `{"version": 1, "lessons": [...]}`，追加写，原子替换。读的时候查重复的键（与 D27 同一个道理：解析之后就看不见了）、逐条查五项，有一处不对整份算读不出来。
- **退出码**沿用 ADR-193 那张表：0 做完（含没有、读不出来）；2 输入问题（品类名不合规、不是任务目录、没带确认开关、草稿不收、经验库读不出来时要写）；6 保存失败。
- **报告的提示**只在分歧那一段有账号时出，一句话，不列草稿。

### 一条判据装几件事

每条判据按 `process/1-REQUIREMENTS.md`「拆到多细」核过：会被不同代码路径分别做到、分别弄坏的，都拆开了。命令能守的一半与只有 Agent 能守的一半分开（确认开关 D31.g 与真有确认 D31.h；列名 D31.m 与沿用 D31.n；报告提示 D31.p 与交付时附草稿 D31.x；五项齐不齐 D31.d 与局面写没写成形状 D31.f）；读的命令标状态 D31.k 与数据边界列状态 D31.v 分开（两个进程，复核指出）；写入时填版本 D31.e 与版本怎么算 D31.i 分开；读不出来时读 D31.t 与写 D31.u 分开。留成一条的：D31.a 文件放哪与品类名合不合规是同一个「这一品类的文件在哪」；D31.d 五项缺一不收是同一道「收不收」的关；D31.l 只读同名一份与没有同名时照常以 0 结束是同一次「挑哪一份」的两个结果；D31.t 照常结束与写明没读到的原因是读失败那一个分支里的同一步。D31.f 的两样要靠人读，两个人判未必一样，随回归办法（ADR-159）由人看。

## 三、不要什么

- **经验库不进 `skill/`、不进仓库。** 三个理由：
  - 经验里有用户自己的客户、品类和账号，装了这个 Skill 的别人不该读到；
  - `skill/` 是发给所有用户的规则文字，改它要走 ADR-159 的回归办法、由需求所有者合入；经验库是每个用户自己攒、自己批的，节奏完全不同，混在一起，每收一条经验就成了一次 Skill 改动；
  - 经验写的是「上次这样判错了」，它的证据（哪个任务、哪个账号）只在用户本机的任务目录里，进了仓库就成了指不回证据的孤句。
- **不自动写入**：理由同第二节第 4 条。
- **不改打分**：经验一旦能调权重，打分规则就随库悄悄漂移，规则版本记录也对不上（第 8 题放弃的那一项）。
- **不存现成句子**：见第二节第 3 条。
- **不用 git 取规则版本**：用户机器上的 Skill 多半是拷过去的目录，不是仓库；问 git 在那里只会全是「未知」。

## 四、与红线、范围的交点

只查与红线的交点（`process/1-REQUIREMENTS.md`「和红线的交点必须查」），结论写进 D31 的判据文字，不登记成两条需求之间的交点：这几处都是 D31 单方面让步，没有哪两条需求在同一处要相反的东西。

- **P1（缺失的数据不得用默认值填充）**：经验库读不出来不当成空的（D31.t），也不覆盖原文件（D31.u）；没有那一份（新品类）就是没有（D31.l）；四种「没读到」分开写（D31.w）；`skill/` 读不出来时版本记「未知」，不拿一个看着正常的指纹顶上（D31.i）。
- **P4（已联系、已拉黑的不得再进名单）**：经验的命令不读写这三个标记（D31.s），读没读经验名单都一样（D31.r）；用户在复评表里填「采纳」也不让已联系的人回到名单（这一半本来就由 `memory.md` 那一段管着）。
- **P5（交付必须声明数据边界）**：读了哪几条、哪几条版本对不上、没读到的原因，都写进数据边界（D31.k、D31.t、D31.v、D31.w）。
- **S3（不主动索要回填）**：不为攒经验去要复评表或回填（D31.q）；报告里那句提示只在已有分歧时出，是告诉用户能做什么，不是向用户要东西。
- P2（开发信不得有未证实信息）、P3（不超预算）不相接：经验不进开发信原句（D31.f），经验的命令不开账、不发请求。

## 五、测试认领

24 条判据里 18 条由需求测试认领，6 条（D31.f、D31.h、D31.n、D31.o、D31.q、D31.x）发生在对话里或要读句子本身才判得出，登记成豁免（`scripts/check/mutations.json` 的 `exemptions`），守它们的是 `skill/references/semantic-fit.md`「复评经验」一节与真实任务回归（末尾欠条）。

- `d31-store-outside-repo`（D31.b）：把本仓库的忽略规则原样抄进一个玩具仓库，在 `memory/` 与 `memory/lessons/` 下放已联系名单和几份经验库文件（含中文、带空格的品类名）、在别处放同名对照文件，问 git 哪些文件算已跟踪或没被忽略的新文件，由 git 答。问的时候把 `HOME`、`XDG_CONFIG_HOME` 指进临时目录、不读系统与用户级配置：不然本机另有一份挡 `memory/` 的用户级忽略文件时，仓库那一行删了这条照样绿（复核实测过）。
- `d31-lessons-lib`（D31.a、D31.d、D31.i、D31.j、D31.v、D31.w）：品类名收拒表、五项缺任一项、`skill/` 指纹对改字节、加文件、改名、改符号链接、`skill/` 本身是链接时的反应、三态、数据边界那一句的六种写法、任务目录里读取记录的读法。经验库与 `skill/` 都注入到临时目录。

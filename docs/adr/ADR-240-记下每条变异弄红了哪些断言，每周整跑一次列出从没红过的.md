# ADR-240 记下每条变异弄红了哪些断言，每周整跑一次列出从没红过的

- 日期 · 2026-11-23
- 类型：不属于反向输入的五类 —— 改的是检查链自己（还 ADR-70 两张欠条）
- 触发它的事实：变异集证的是「每条变异都被抓到」，反过来那一句 —— 每条有名字的断言都至少被一条变异弄红过 —— 没人查，一条永远为真的断言发现不了（ADR-70 欠条「没有东西查哪条断言从没被负片弄红过」）。要查就得记下每一次运行红过哪些断言，而「见齐就停」（点名的断言都红了就停掉验证者）会让停下之后的断言没跑到（ADR-70 欠条「攒具名断言清册与见齐就停互斥」）。需求所有者在回访台账 2026-11-23 那一块（ADR-152，#536）把前一张标了接受
- 冲击的需求：无
- 决定人与时间：需求所有者丸子 —— 2026-11-23 13:53（北京时间）在项目线程的选择卡「记录『每条断言有没有被弄红过』用哪种办法？」上选了丙「平时照常，每周整跑一次」。三个选项与实测在 Linear 项目文档「查出永远不会变红的测试断言：三种记法和实测代价」
- 结论：采纳。人批痕迹：上面那张选择卡；需求所有者合入本条
- 理由：清单只报不拦，一周一份够用；变异测试工具的成熟做法也是这样分的（第二节）；每条改动不多花时间、不碰变异负载闸门
- 连带改动：新加 `scripts/check/never-red-rule.ts`（判定）、`scripts/check/never-red.ts`（入口，`npm run never-red`）、`.github/workflows/never-red.yml`（每周一的整跑）· `scripts/check/mutate.ts`（每条变异算红过哪些、写记录、`MUTATE_NO_EARLY_STOP=1` 关掉见齐就停）· `scripts/check/jobs-rule.ts`（汇报行带上红过哪些，`parseReport` 逐项验）· `scripts/check/verifier-rule.ts`（自检的工具表加 `never-red`）· `scripts/test.ts`（新组 `h-never-red`）· `scripts/check/selfcheck.ts`（新组 `mutation-reds-entry`）· `scripts/check/mutations.json`（M-H240-a 到 ba）· `package.json`（`never-red` 命令）· `docs/REVISIT.md`（回访 PR 正文加 (e) 一段）· `docs/ARCHITECTURE.md`（两行锚点、`output/` 那一行、变异一步一段）· `docs/GLOSSARY.md`（「见齐就停」「从没红过的断言」）· `AGENTS.md`（命令一行）· ADR-70 两张欠条挪进历史文件 · `docs/adr/README.md` 索引
- 同类：ADR-145（变异一步顺手写一份记录、另一个入口读，同一个形状：启动数）

## 要用到的事实，各找谁要

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 一次运行里哪几条有名字的断言红了 | 验证者自己打的失败行（`✗ <名字>` 或 `✗ <名字>：…`），认法与 `kills` 同一条（`killsMatched`）；名字只认按语法树从验证者源码收的清册（`labelsOf`） | 机器 |
| 那一次的红算不算断言的功劳 | 判定四态（`judgeRun`）：只认「抓到」「红错了地方」两档 | 机器 |
| 每条断言属于哪一组、每条变异跑了哪几组 | `groupOfLabel` 按语法树认的组；变异的选组来自 `executionRoutes`，变异一步随记录写下 | 机器 |
| 这一跑停没停、停了几条 | 变异一步自己：开关 `MUTATE_NO_EARLY_STOP`；每条的「主动停下」由入口记（`Ran.stopped`） | 机器 |
| 记录是不是这份变异目录的整跑 | 变异目录 `scripts/check/mutations.json` 的编号，与记录逐条对 | 机器 |
| 关不关提前停各花多少时间、清单多长 | 实跑：2026-11-23 在主干 c8401a59 上整跑一遍、自检那 352 条停与不停各跑一遍（Linear 文档里那张表，原始记录在项目文件 `never-red-assertions/2026-11-23-实测/`） | 人 |
| 业界怎么做 | Stryker 配置文档 `disableBail` 一节与测试三态的定义；PIT 的 `fullMutationMatrix`；MuTalk 的「红了第一条就停」开关 | 人 |

## 一、做了什么

1. **每条变异记下红过哪些断言。** 变异一步跑完一条，用 `creditedReds` 从验证者的输出里认出这一次红过的有名字的断言：一行以 `✗ ` 开头、后面正好是清册里的一个名字，或名字接全角冒号；只有判「抓到」「红错了地方」的那两档算数 —— 判「跑不起来」的那一次出过进程级或夹具级的失败，红不是断言的功劳。认出来的随结论带回（派工跑时写进汇报行，`parseReport` 逐项验），收尾**在判结论之前**写进 `output/mutation-reds/reds.json`（分份跑时 `reds-k-of-n.json`），所以有变异没被抓到的那一跑也留下记录。每条记 `id`、验证者、选了哪几组、停没停、红过哪些；整份记这一跑验的提交、开没开提前停、第几份。开跑先删上一跑的，删不掉以 1 退出。
2. **开关：`MUTATE_NO_EARLY_STOP=1` 关掉见齐就停。** 没写照常停；写 `1` 每一条都跑到底；别的值读不出来，以 1 退出、一条不施（`earlyStopWanted`）。关了提前停的那一跑判结论走普通那条路（要退出码与汇总），启动数的账照旧按「会停」记，所以这一跑不拿去比启动数。
3. **`npm run never-red` 出清单。** 读那几份记录，`readRedsPart` 逐字段验，`mergeParts` 拼回一跑并核它就是这份变异目录的整跑（缺一份、几份的提交或开关对不上、同一条记两次、目录里有的没记、记了目录里没有的，一律拒，以 1 退出、不出清单 —— 少一条就会把那一条弄红过的断言算成没红过，而清单上看不出来）。对着两个验证者的清册，`neverRed` 列出从没红过的，分「没有负片跑到」（它那一组没有任何变异选，再多变异也弄不红它）与「跑到了，没红过」两段；头上照实说这份记录有没有提前停、停了几条；末尾一行 `NEVER_RED_JSON` 给每周回访读。**只报不拦**：列出几条都以 0 退出，不接进 `npm run check`。
4. **每周一整跑一次。** `.github/workflows/never-red.yml`：周日 20:00 UTC（周一北京时间 04:00，赶在 08:50 的回访之前），分三份、关掉提前停跑全部变异，各传一份记录，再起 `never-red` 出清单，写进这一跑的 Summary 和日志。不是必需检查，不挡任何合并。变异基线取这个提交的上一版（定时触发的事件里没有可用的基线）。
5. **回访把数带给需求所有者。** `docs/REVISIT.md` 新加 (e)：读本周那一跑「清单」job 日志里的 `NEVER_RED_JSON`，把两个验证者的清册条数、从没红过几条（其中没有负片跑到几条）、比上一跑多了还是少了写进回访 PR 正文。只报数。

平时每次检查（本地与 CI）照常见齐就停，同样写记录 —— 本地想看一眼可以 `npm run mutate` 之后跑 `npm run never-red`，头上会说这份会多报。

## 二、为什么是这个分法

需求所有者在三个选项里选的（Linear 文档里有全文）：甲，照现在的跑法顺手记（不多花时间，自检那一半多报约 25 条且分不出是哪些）；乙，每次检查都不提前停（每次都准，变异那一步本机多约 21%，顶红变异负载闸门，还得先处理 6 条跑到底会改判的变异）；丙，平时照常、每周整跑一次。

业界同一件事的做法：Stryker 默认「一条测试红了就停」（bail），`disableBail` 默认关，文档说打开后「多得多的测试会拿到『抓到过』状态」，「适合在测试视图里找一个都没抓到过的测试」，并给每条测试记三态 —— 抓到过、跑到了没抓到、没跑到；PIT 的 `fullMutationMatrix` 默认关，打开后一条测试红了还接着跑；MuTalk 的「红了第一条就停」默认开。三家都是平时提前停，要完整的「哪条测试抓到过什么」时专门关掉去跑。丙照这个分法；清单的两段就是 Stryker 后两态。

实测（2026-11-23，主干 c8401a59，本机 4 核）：

- 见齐就停只发生在自检那 352 条变异上；需求测试那 2683 条只跑选中的组、组里有收尾，本来就跑到底。
- 有名字的断言：需求测试清册 4759 条，从没红过 1502 条（没有变异跑到 135 条）；自检清册 830 条，不停时从没红过 369 条（没有变异跑到 255 条），提前停时 394 条 —— 多报的 25 条就是停下之后没跑到的。
- 自检那 352 条：验证者累计用时 2168 秒 → 3470 秒；墙钟 820 秒 → 1136 秒。整个变异一步墙钟 1527 秒，不停时约多 316 秒。
- 6 条自检变异（M-D13-a、M-D13-n、M-D6-at、M-D26-b、M-D26-k、M-D6-br）跑到底以后，后面冒出带「夹具没造对」或「进程出错」记号的失败，改判「跑不起来」。

## 三、关上的欠条

- ADR-70「没有东西查哪条断言从没被负片弄红过」：已还（第一节）。它写的「改法已想清」—— 跑变异时把每一次弄红的具名断言记下来，跑完报从没被弄红过的 —— 就是第一节第 1、3 条。
- ADR-70「攒具名断言清册与见齐就停互斥」：已还。它说「提前停的要另算，怎么办没想清」；现在的答案是第二节那个分法：平时停下的那几条照记、清单头上标明会多报，准的那份由每周不停的整跑出。

两张都照 `process/6-INTEGRATE.md`「登记怎么做」第 3 条，连同还上那一行挪进 ADR-70 的历史文件。

## 四、碰到的欠条

按 `process/6-INTEGRATE.md`「登记怎么做」第 5 条，只写碰响了的：

- ADR-70「见齐就停的那一次只对停下之前的输出负责」：条件是「下一条要改判定四态或记号语义的改动」，本条没改判定四态和记号，不响。但它说的事第一次有了数：上面那 6 条变异，见齐就停时判抓到，跑到底判跑不起来。每周那一跑会把它们照实报红（「不提前停的整跑」那几份 job 红），回访照 (e) 写出来。这 6 条怎么处理是另一件事，本条不动。
- ADR-89「下一条往 `mutations.json` 加变异时看一眼盖的是不是没人盖过的地方」（按行号指的那张）：响了。看过：53 条盖的都是新判定 `never-red-rule.ts` 与汇报行新带的那一项，以前没有变异。条件是事件触发，照旧挂着。
- ADR-158「判定的返回字段有没有断言消费」那一路：新判定交回的字段各有一条会被测试打红的变异改到它的值（字段断言闸门绿），不欠。

## 五、证不了的

- 入口那一半（`mutate.ts` 真的记、真的写、关了提前停真的不停；`never-red.ts` 真的读、真的拒）只由自检组 `mutation-reds-entry` 守：两个入口都在验证基础设施闭包里，指名自检的变异施不上去，本条没配指名需求测试的那种。
- 每周那个工作流没有任何检查跑它：第一次真跑要等合入后的那个周一，或者合入后手动点一次（`workflow_dispatch`）。它跑不起来时回访 (e) 那一段写 `无从确认`。
- 清单里「跑到了，没红过」的那些是不是真的什么也没查到，要人逐条看：有的是正例（比如「区间内放行」），没有变异去弄坏「该放的没放」；有的断言名字是拼出来的、不在清册里，压根不在这份清单的范围。
- 清单只管**有名字**的断言（清册里那些）；没起名字、只在失败时说一句话的不在范围内。

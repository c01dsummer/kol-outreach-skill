# ADR-180 报告的 HTML 在输出处转义每个取值，读入校验另登记

- 日期：2026-10-24 · 读 Anthropic 那篇形式化验证文章时，照它「一条通用性质套到全部入口」的思路，在仓库外把报告渲染扫了一遍；需求所有者 2026-10-24 在项目线程里选了「两条都开」，本条是其中补转义的那条
- 类型：需求有歧义（补充），连同一处既有缺陷。报告该不该转义取值，登记表只在 D15.h、U9.i、U11.j 里各管几类字段时写过，没有一条管全部取值；按 `process/2-CHANGE.md` 分类表，这一类是补写清楚、不走评定，补成 U12。没转义的那几处主干上不合本条也一样在
- 触发它的事实：把本条那条 PR 的 `scripts/test.ts` 放到主干 `a878b88` 上跑 `npx tsx scripts/test.ts --only=u12-report-escape`，红在一条断言：夹具里的取值逐个换成金丝雀以后，两种视图里共 58 处让金丝雀的原字符进了报告，落在 19 个字段上（三个创作者的同名字段算一个）：创作者的平台、粉丝数、作品数、层级、分数，主账号与关联账号的活跃状态与受众风险等级，交付 meta 的平台列表、总人数、三层人数、有邮箱人数、跨平台人数、高风险人数、公开指标已测账号数。代码位置在 `scripts/lib/report.ts`（树 `a878b88`）第 103、104、258、259、261、262、265、270、296–298、426、430–437 行：这些取值直接拼进模板，没过转义。创作者自己写的文字（昵称、简介、草稿等）原先就都转义了
- 冲击的需求：新增 U12（U12.a、U12.b）。U2、D15.h、U9.i、U11.j 的含义不变
- 结论：**采纳。** 上面那几处一律在输出处转义。原先直接插进模板的取值，先照模板插值的规矩转成文字再转义：缺值时照旧印出原样，不悄悄变成空白
- 理由：报告读的名单与增强结果是从盘上反序列化进来的，也就是外部输入（`process/4-VERIFY.md`「判据的失效方式」）。render 读 `creators.json` 时只查是不是数组；增强结果里没有样本的账号，活跃状态与风险等级照盘上存的那份带进来，不重算。层级、分数与 meta 里那几项人数是 render 自己算的，今天进不来坏值，但输出处不该靠这一点。今天外人也用不上这几处：供应商正常返回数字，盘上文件只由流水线写。所以这是几条没写下来的前提，不是一个能被利用的漏洞。在输出处统一转义只改一个文件，不靠每条读入路径各自都校验对
- 连带改动：`scripts/lib/report.ts`；`scripts/test.ts` 新增一组 `u12-report-escape`；`scripts/check/mutations.json` 新增 M-U12-a 至 M-U12-d，另有三条既有变异 M-U6-a、M-P1-ad、M-U10-b 的 `find` 落在改过的那几行上，跟着改成转义后的写法，各自施的那一刀不变；`docs/requirements.json` 与由它生成的 `docs/SPEC.md`；`docs/ARCHITECTURE.md` 锚点表里 `scripts/lib/report.ts` 那一行加 U12；`skill/references/output-format.md` 的相关需求一行加 U12；本索引一行；`scripts/check/launches.json` 重写

## 一、测试怎么判

夹具是三个创作者加一份交付 meta，当作盘上读进来的 JSON 写在测试里：有报价、已测的受众风险（含依据）、人工评审与多平台人工作答、待重评的关联平台 Agent 判断、没有样本的关联账号、不可用的样本与指标、费用账问题、记忆没写回。

- **U12.a**：夹具里每个取值（字符串、数、布尔、`null`）逐个换成金丝雀 `x"y'z<q-u12>&w`，字符串另试一次末尾追加；每一份都用公共单层视图和生产用的双筛选视图各渲染一次。报告里出现金丝雀里任何一段原字符（`x"y`、`y'z`、`<q-u12`、`&w`）就记一处漏。渲染被拒（抛出）不算漏：没有报告，也就没有被改写的标记。
- **U12.b**：账号、昵称、简介、开发信草稿、产品名、关键词这六个自由文本换成金丝雀，两种视图里都要出现手写的「转义一次」写法。它挡的是把取值删掉、截断或转义两次也能让 U12.a 变绿的那几种写法。

什么能在事实不成立时也让它通过：渲染全被拒，U12.a 就是空的绿，所以先断言原夹具两种视图都照常渲染，U12.b 也要求那六个字段真的渲染出来；只转义尖括号、不转义引号，金丝雀里带着两种引号；夹具里没有的字段扫不到，见第二节第三张欠条。

四条负片都只跑这一组：M-U12-a 去掉平台样式类的转义（属性里）、M-U12-b 去掉粉丝数的转义（正文里）、M-U12-c 去掉副标题平台列表的转义（交付 meta）、M-U12-d 把账号转义两次。

## 二、不修在本条的

> ⚠️ 欠条：读入这一头没核取值。render 读 creators.json 时不核平台是不是 tiktok 或 instagram；TikHub 解析粉丝数、作品数的几处（scripts/providers/tikhub.ts 第 224、228、260、262、383、386 行，树 a878b88）不核是不是数，不是数时照原样进名单与三份交付。读入时拒收还是报告上显示未知，由需求所有者定 · 重启条件：需求所有者定下不是数的粉丝数、作品数怎么处理时；或下次改动碰到这几处解析、或 render 读名单的那一步时

> ⚠️ 欠条：U12 只管转义，管不住链接的协议：主页链接的取值换成 javascript: 开头的串，照样进报告里那个链接的 href。今天主页链接是采集时用账号名拼出来的 · 重启条件：主页链接改为取自供应商返回时；或下次改动碰到主页链接的生成或渲染时

> ⚠️ 欠条：U12.a 的测试只换夹具里有的字段，判据说的是每个取值，测试守的只是夹具里那些；报告以后新展示的字段，要有人补进夹具才扫得到 · 重启条件：下次改动给报告加展示字段时

## 一、为什么三份各跑一遍全部基线

变异前要先用没改过的代码把那一组测试跑一遍，确认它本来是绿的（子集基线）；同一种配置只跑一次，同配置的变异都拿它作对照。
ADR-197 按清单顺序轮流发：主干 `1914cad` 上三份各碰到 156、157、161 种配置（共 200 种），几乎每一份都要全部基线，于是三份各跑一遍。
基线与启动数还都按整份做，所以三份写下的启动数文件一样，最后一步取第 1 份那个就行 —— 这是当时不拆的原因（ADR-197 第四节）。

## 二、做法

**按配置成摞分。** `shardOf(items, keyOf, k, n)`：`keyOf` 交回这一条的子集配置键（与基线去重用的是同一个键：验证者加排好序的选组），同键的整摞落在同一份；整跑的（没有子集基线）各自成一摞。摞按条数从多到少排（一样多的按在清单里第一次出现的先后），逐摞发给眼下条数最少的那一份（一样少的给编号小的），交回的照清单原顺序。每一份各自算，算出来的分法一样，几份合起来就是整份。

按条数配而不是按秒数：拿 #470 合入前本机那一跑的成本报告（每种配置的基线与变异实测秒数，`ci-duration/2026-11-14-KOL-1/br-step-mutate.log`）回放，198 种配置照条数这样分，三份的实测秒数是 1,176、1,194、1,118（相差不到 7%，最大的比理想值多 2.7%）；照轮流发、每份再各付全部基线，每份是 1,459。按秒数配要一份各配置的历史耗时进仓库或随跑传递，换来的不到 3%，不值。

**每份只做自己的。** 开跑前的体检（归因、标签、接线、ORDER 绑定、维护比较）照旧按整份；子集基线、启动数、成本报告的组合都只按这一份的变异算。一条变异和它的基线永远在同一份里，「先过基线再施变」在每一份内照旧成立。

**启动数拼回整份。** 分份时变异一步写 `output/mutation-launches/launches-k-of-n.json`（记录里多一个 `shard: { index, count }`），开跑先删旧的整份文件和所有分份文件。最后一步 `npm run launches` 有整份的 `launches.json` 就读它；没有就读目录里的分份文件，交给 `joinLaunchParts` 拼：几份的配置互不相交，`tally`、`findings`、`baselines`、`again` 直接拼起来，再照 `launchFindings`、`launchTally` 的顺序排（findings 全跑的按 id 在前，其余按配置键、同一配置里照原顺序；tally 按配置键），`baselines`、`again` 照第 1 到第 n 份的顺序拼，拼好的不带 `shard`。拼出来的与整份跑写的一个字不差，所以闸门与摘要的判法一行没改。少一份、多一份、同一份两次、份数说法不一、不是同一提交或同一棵树写的、各段形状不对，都拼不起来：先打一行「✗ 分份的启动数文件：…拼不起来：原因」，再当没有文件交给闸门，闸门照旧红。

**CI 上派 6 个 worker。** `check.yml` 的变异 job 加 `MUTATE_JOBS: '6'`。本地不写，照旧按核数。ADR-197 第四节本机量过：4 核上派 6 个，变异 768 秒对 902 秒，user+sys 几乎不变 —— 4 个 worker 时有核在等子进程起来。

`check.yml`：三份各上传自己的 `launches-k-of-3.json`（构件名 `mutation-launches-k`），最后那个 job 用 `pattern: mutation-launches-*`、`merge-multiple: true` 一起取回到 `output/mutation-launches/`。

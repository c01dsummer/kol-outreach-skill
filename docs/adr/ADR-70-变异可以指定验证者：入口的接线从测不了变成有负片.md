**几个词。** **验证者**：一条变异施上去之后跑来看它红不红的那个程序，今天两种 —— 需求测试（`test`）与脚本自检（`selfcheck`）。**接线**：入口脚本里把判定、IO 与打印连起来的那几行，本身不装判定，但删了改了照样会坏事。**具名断言**：起了名字的那一条断言，失败时打一行 `✗ <名字>`；没起名字、只在失败时说一句话的叫**散文诊断**。**清册**：从验证者源码里静态收出来的具名断言名单。**见齐就停**：`kills` 点名的断言都红了，就当场停掉验证者，不跑完。

## 触发它的事实

清点 #19–#70 这 52 条 PR 的评审：42 条有评审，160 条线程，约 161 条发现。分档是本改动 126、既有缺陷 10、登记 13、扩范围 5、驳回 7。当场修的 126 条里最大的一类是同一个形状，论证永远是「把这一行删掉／改坏，整套测试仍然全绿」，每一次核实都成立。

当时查出来的三处事实：变异的验证者写死成 `scripts/test.ts`；`mitigation` 字段全仓只出现在一行类型声明里，没有任何代码读它；`selfcheck.ts` 里一次 `criterion(` 也没有。第一条是这一整类问题的唯一原因：变异改入口脚本 → 没有任何断言会红 → 只能判「存活」→ 入口里的东西在机制上不可能有负片。第三条最刺眼：自检一跑打出几十行 `✓`，正是评审反复在要的那些，**全都存在、全都在跑、全都没有任何东西证明它们不是空的，审计里也看不见**。

## 为什么这不是纪律问题

写一条单元断言拿到三样东西：一个认领、一条负片、审计表里一行；写一条自检断言只拿到一行 `✓`。激励梯度整个指向单元层，而单元层在结构上看不见接线。`docs/CONVENTIONS.md` 第 10 条底下这件事按实例记过六次，记到第六次还在犯，要改的不是那条纪律，是画界的那个机制。

**这条路 ADR-62 已经堵过一次，不重开。** ADR-62 否掉了把第 10 条做成静态查形状的 lint（三条判据都是假阳性），本条不重提那条路。要掀掉的是那里一句隐含前提：「带 shebang 的是入口……也就没有可变异的东西」。入口里那一行接线有语义，只是工具跑的不是它 —— 一个是被测对象的性质，一个是工具的实现限制。够得着之后，第 10 条就不必再靠自觉：**不用管判定在哪，只管它有没有负片。**

## 结论：给变异加两个字段

```json
{ "id": "M-D6-bi", "req": "D6.r", "by": "selfcheck",
  "kills": ["<点名的具名断言>"],
  "file": "scripts/collect.ts", "find": "…", "replace": "…", "why": "…" }
```

**今天的形状**（`mutate-rule.ts` 的 `VERIFIERS` 与 `wiringFault`）：

- **`by`** 是 `test` 或 `selfcheck`。`test` 跑 `scripts/test.ts`，汇总行认 `N 个失败`；`selfcheck` 跑自检，汇总行认 `✗ 脚本自检：N 项失败`，另认两种记号：**进程记号** `（进程）`（被测脚本没起来、被信号杀掉之类进程级的失败）与**夹具记号** `（夹具）`（夹具自己没造对）。每个验证者各自声明它起名字用的调用：需求测试是 `eq`、`ok`，自检是 `endPath`、`named`。
- **`kills`** 是一组具名断言的名字，点名的**每一条**都要在输出里见到 `✗ <名字>` 才算被抓到。
- **`by` 与 `kills` 同进同出。** 开跑前 `wiringFault` 逐条查，四种不合格各有说法：`unknown-verifier`（点了没有的验证者）、`missing-kills`（写了 `by` 没写 `kills`，空名单也算 —— 「每一条都红」对空名单恒真）、`kills-without-by`、`kills-not-list`（老写法的字符串会被逐个字符遍历）。
- **现状是全员都写。** 变异目录里今天每条都带 `by` 与 `kills`，`by` 只有 `test` 与 `selfcheck` 两种；条数与分布看 `scripts/check/mutations.json` 本身（`npm run mutate -- --brief` 逐条列出）。原文把 `by` 写成可选、缺省 `test`，`kills` 只要求自检那几条写；后来全员补齐（原文「它挡不住什么」第四类那条「`kills` 推广到全部变异」的出路就此成真），以代码为准。全员都写是目录的现状，不是代码的规定：接线判定今天仍放行两样都不写的（缺省跑需求测试、不点名，有汇总行的失败就算抓到，见下面判法第 3 步的附注），也没有检查拦新加的不写；只写 `kills` 不写 `by` 报 `kills-without-by`。

**`kills` 是必需的，两个理由各堵一个洞。** 一、堵假阳性：入口里的变异很容易把脚本弄崩，崩了退出码也非零，不点名就会被误判成「被抓到」（ADR-62 第三条取舍要拦的那种事）。二、堵散文那个洞：夹具被删 → 那条变异不再被抓到 → 检查链红。**负片本身就是可执行的 mitigation。**

**`mitigation` 现状。** 豁免与变异同在 `scripts/check/mutations.json`，豁免在它的 `exemptions` 数组里。拿得到负片的豁免删掉了它，拿不到的留着：今天的豁免是 P3.e、S1.b、P2.a、P2.d、P1.b 五条，各带范围（`scope`）、`why` 与 `mitigation`。P2.a 那条 `mitigation` 是「不要编造品牌信息」那句缓解的唯一出处，永远拿不到可执行负片。

**怎么判一次运行**（`judgeRun(退出码, 输出, 验证者, kills, atStop)`，四态是 `survived`／`caught`／`elsewhere`／`crashed`）：

1. 退出码 0 → 存活。
2. 主动停下的那一次（交了 `atStop`，即开枪那一刻已经收到的输出）：点名的都见齐、且没有任何记号 → 抓到；否则判崩。判的是开枪那一刻它说过的话，不是最终输出（ADR-72）。
3. 没有退出码（被信号杀掉）或没打出汇总行 → 判崩。
   - 接着：没写 `kills` 的（今天目录里没有，代码仍允许）→ 到这里就算抓到，不查记号，也不见齐就停。
4. 输出里有进程记号或夹具记号 → 整次判崩：这一次里有一条夹具压根没测到它要测的东西，整份证据不算数。代价是保守的假阴性。
5. 点名的都红了 → 抓到；有没红的 → 红错了地方（`elsewhere`）。

三个判据只此一份：`allKilled`（见没见齐，入口靠它决定什么时候杀，判定靠它给抓到）、`notAssertion`（两种记号合成一句）、`complete`（收到的字节里哪一段已经成行，两股流各自截 —— **半行不算**：`✗ 某条夹具` 是 `✗ 某条夹具又长了一截` 的前缀）。

**判崩时留证据。** `crashEvidence` 交回退出码（或「被信号杀掉」）、是不是主动停的、以及验证者打出的失败行，最多 15 行：带记号的一行不截，截掉几行报个数；一条成形的失败行都没有时退回原始输出的末尾，标 `raw`，入口用 `┆` 打出来。

**开跑前的体检**（`mutate.ts`，先后就是这个顺序，一条不过就不开跑）：编号不重复 → 没有挂空的需求号 → `--brief` 要打的每一段不夹带实现原文（`briefLeaks`）→ 锚点在目标文件里恰好命中一处（`anchorMatches`）→ **接线**（`wiringFault`）→ **自己验自己**（`selfVerifying`）→ **清册**（`labelFaults`）。原文说的「入口那三道体检」就是最后这三道，由粗到细：接线不对是这条变异没法跑；自己验自己是整份证据不算数；点不着夹具是证据算数但功劳记错了人。

**施加照字面。** `applyMutation` 把 `replace` 原样落盘，`$$`、`$&`、`` $` ``、`$'` 一个也不展开（见「施加照字面」一节）。

## 两处接缝，现在就写下来

**一、首次失败即停和 `kills` 会打架，除非停的条件对。** 一条入口变异常同时弄红好几条夹具；停在没点名的那条上，`kills` 匹配不到，一条真被抓到的变异会被判成没抓到。所以停的条件是**点名的那些都已经红了**，不是第一条红。今天「停不停」由 `stopsEarly(验证者, kills, 选组)` 一处说了算：有 `kills`、而且不是「需求测试 ＋ 选了组」那种跑法（选组跑的需求测试有 `finally` 收尾，停了会留下现场；ADR-145 第一节）。停的是验证者**整组**进程（见「见齐就停停的是整组」一节）。

**二、验证者跑的东西里不许有变异改的那个文件。** 自检自己会起 `mutate --brief` 和几个检查脚本；改的正是这些文件之一，就成了自己验自己，结论是脏的。判据是 `verifier-rule.ts` 的 `selfVerifying(变异, 闭包)`：`by` 不是 `test`、且目标文件在**验证基础设施闭包**里，就拦。闭包从种子递归收 `import`：种子是 `selfcheck.ts`、自检工具表 `SELFCHECK_TOOLS` 里的各个检查入口（名单以那张表为准）、`check/fake-fetch.ts` 与 `check/launch-preload.ts`；抽边的 `importsOf` 认单引号的 `from '相对路径'` 与副作用 `import '相对路径'`。闭包多大随仓库动（原文写的 13 个是当时的树），要看就在仓库里调 `infraClosure` 现算。需求测试另有两条断言盯着：真闭包里一个产品入口都没有（名单从 `package.json` 的产品命令读，不从闭包取）；真闭包里没有抽边认不得的引用写法。

## 它挡不住什么

按 `1-REQUIREMENTS.md`「允许写做不到，不允许写应该可以」，把边界写清。四类：

### 一、判据拆分

一个编号管着两件能各自坏掉的事，测试只跑了一半却认领整条，审计照样报已覆盖。「这两半会不会被不同的代码路径独立弄坏」机器答不了，要读语义。原文设想过一张候选表：同一判据底下两条变异的 `kills` 不相交，就列为候选。

**现状。** 那张表只用**声明值**不相交：`kills` 是下界（「这几条必须红」，不是「只有这几条会红」），声明值不相交推不出杀伤集不相交；要拿真杀伤集得有一个跑完并记全部失败的模式，而见齐就停走的是相反方向，两者互斥。它不当硬失败，也不是常设的报告。P3.b 该不该拆判过，结论是**不拆**：拆判据那一版写出来过，新增变异数是零，全部产出是审计一格读数的变化（ADR-89 判掉的「给缺口装一块仪表盘」）；「拆分的目的是让漏掉一半变得看得见，不是让条目变多」。

### 二、断言太松

不是没测，是判定本身放得太宽（`.+` 接受空白；拿整个 stderr 搜一个词；stderr 为空返回 `''` 而调用点做真值判断）。变异只抓得到有人想到去变异的那种松，写负片的和写松断言的是同一个盲点。能沉淀的只有一条纪律：**每条断言同时钉一个正例和一个该被拒的反例。**这一条留在第三层，本条之后没有新信号。

### 三、文档、注释与代码对不上

代码全对、检查全绿，旁边那句话在撒谎，还带着「检查全绿」的背书。已经在查的是「需求正文里出现的每个 `ADR-nn` 必须出现在 `adr` 栏」；没人做过的是**可数的断言**（句子里有个数或量词，而那个数数得出来）。本条不碰。

### 四、`kills` 只硬化第三拍，不创造它

`4-VERIFY.md` 第三拍要每条新测试配一个变异，当场确认它会红。`kills` 抓得到「配了但配得不准」（变异在，可它红的是别的断言）；抓不到「压根没配」。diff 级启发式按 ADR-62 的标准过不了关（改名、重构、拆断言全是假阳性）。`kills` 已推广到全部变异，「没有任何变异点过名的断言」那张表算得出来了，但它是下界，仍只能是候选，没有人做成检查 —— 见欠条「没有东西查哪条断言从没被负片弄红过」。

## 落地 2：`by` ＋ `kills`，切成五步

原文把落地 2 写成一条 PR，开工时切成五步，每步回答一个「怎么证明它对了」：1 隔离判据（自己验自己）；2 `by` ＋ `kills` 与两种记号；3 隔离判据接进 `mutate.ts`；4 清册与审计那一栏；5 见齐就停与两条真负片。闸门自己走「最后一块砖」（`6-INTEGRATE.md`）：判定、测试、负片先合，接线留到最后。

**清册**（第 4 步，`labelsOf`）按语法树静态收，不拿某一次跑出来打了什么当清册（见齐就停会让一次运行只走到一部分夹具）；只收声明调用的**第一个实参是字面量**的那些（转发、带插值的模板串定不下来就不收 —— 清册小了是拦住，大了是放行）；重名**只在被 `kills` 点到时才拦**，不做全局唯一。顺带买到：**派生诊断进不了清册** —— 自检那几十句 `✗ <散文>` 是夹具的后果、不是夹具的名字，收进来的话 `kills` 就能点着一句崩溃之后照打的话。

**审计那一栏**（第 4 步后一半）：判据级的负片在报告里露面（`判据 6(负片 3)/6` 这种写法）；「变异」那一格从入口抽进判定模块；需求级豁免那一路补了断言与负片。原文这一步加过一道「豁免与负片互斥」的硬失败，同一条 PR 里又撤了：豁免带范围、变异只有需求号，按需求号相交会逼人删掉另一半唯一的缓解记录。那道闸至今没建，见欠条「豁免与负片的互斥闸没建」。

### 5b

`M-P3-b` 是第二条 `by: selfcheck` 的变异，点名一条新起的具名断言（断点记到了中止那一刻）。为此加了 `named(名字, 成立与否, 原因)`，名字进自检的声明表；只改了 P3.b 那一段，其余几十处诊断仍是散文，指着它们的接线仍写不出 `kills`，要用时逐处改成具名。头两次写的变异都从断言底下滑了过去（循环里每页都落过一次断点），实测找到真正弄得红它的那一处才落。

### 5c 第一片

## 零请求观察器与外层断网

**它回答什么。** 一次运行里，真实入口进程有没有经 `fetch` 发请求、发了哪些、每一次拿到的是脚本里预定的哪一个响应。请求不出本机：观察器按**响应脚本**（`kol-test-observer-script/v1`，按方法、路径与查询键匹配规则，同一条规则第 n 次命中答第 n 个响应）作答，不回落真网络；入口还跑在外层断网（bubblewrap 的 `--unshare-net`）的沙箱里，断网不靠换掉 `fetch`。这一套给独立黑盒测试包用（今天在 `scripts/independent-blackbox-tests/`，ADR-195 改的名；那是冻结包，改字节要需求所有者批，ADR-204）。

### 对作者公开的协议

现行的是**修复轮 1 修订后的 v1**：历史文件第 3223 行起的 v1 与第 3408 行起的修订合起来读，修订列出的条目整条替换同号条目。要点：

1. 先认证一次断网（`certifyIsolation`），认证不成立就不能起任何入口；手上的认证对象必须是认证交回的那个。
2. 逐次运行用 `runObserved`，入口是 `probe`、`collect`、`enrich`、`render` 四个真实入口之一，或观察器自带的对照夹具 `control`（只用作 render 的阳性）。入口进程的环境从空表起，只有白名单那几项（今天的白名单含 `KOL_TEST_OBSERVER_EVENTS`），不读 `.env`；沙箱里看得见、写得了的只有 `cwd` 与证据目录。
3. 只断言零请求的那一跑，脚本可以一条规则也不写；这时入口发了请求，是脚本外的请求，判**设施故障**，不是语义红。想让不该发的请求判成语义红，就在脚本里写上那条请求。没有规则命中或命中的已用完：记下、不答、叫停入口，判观察器故障。
4. 事件写进 `events.jsonl`：`armed` 打头（入口进程自己写，记脚本与预加载的哈希、加载顺序、环境变量名），每个请求答之前写 `request`，读正文写 `body`，设施问题写 `fault`。`fault` 可能由别的线程写、可能排在 `close` 之后，不论在哪一行都算。
5. 观察成立要求：`armed` 打头且属于本次运行、加载顺序对、入口只看得见 `lo`、环境只有白名单、请求序号连续且结局与脚本一致、没有 `fault`、`close` 收尾。
6. render 的零请求要有阳性对照（`control` 那一跑），证明这套观察看得见请求。
7. 零请求判定（`zeroVerdict`）有四档：`pass`（通过，只有这一档算零请求断言成立）、`red`（目标那一跑观察到请求）、`facility`（设施故障）、`fixture`（夹具失格，例如没给阳性对照、阳性一次请求也没观察到、两跑不在同一份断网认证下或装的不是同一份预加载）；后两档既不算过也不算红。**先看设施故障、后看请求**：设施故障那一档带 `side`（目标那一跑还是对照那一跑）与 `cause`；脚本外的请求、请求之后被信号打死，都判设施故障，不判红。
8. 入口只许在**主线程**用 `fetch`；起线程、起子进程、用 `net`／`dns` 连网，都是设施故障。

## 变异残留：对着目录查锚点

变异施加在真实源文件上，`mutate` 被打断或跑到一半提交，树上会躺着一条。检查链第一步 `npm run anchors`（`scripts/check/anchors.ts`）对着变异目录查：

- **第一片：判定。** `anchorFaults` 对每条变异判五种对不上的：读不到（`unreadable`）、没还原（`residue`，目标文件里是 `replace` 而不是 `find`）、锚点不唯一（`ambiguous`）、分不开（`unclear`）、锚点失效（`stale`）；还标出被同文件另一条带出来的（连带）。
- **第二片：入口要用的判定。** `anchorCatalog` 判目录是不是一组齐全的变异（不是数组、空的、缺字段的整份不算 —— 没得核不是核过了）；`anchorVerdict` 先问编号唯一（重名时只报重名，与 `mutate.ts` 那道检查用同一个 `duplicateIds`），再判五种。
- **第三片：入口。** 读目录与目标文件，逐条说人话，有一条就以 1 退出；不起验证者、不碰 git 以外的东西，提交之前可以单跑。叫人先用 `git diff HEAD` 看那个文件，没还原的只撤那一处，看出来是自己改了代码的改变异集。这条纪律写进了 `process/4-VERIFY.md`「变异测试 · 做法」末尾。

**这道闸门替代的是「跑」**：锚点失效原先要等变异那一步跑到才报，没还原的原先没有任何一步报。

> **什么条件下整个撤掉**：`mutate.ts` 的每条路都把变异施加在隔离目录里、不再改写真实源文件（`runOne` 里写的不再是 `m.file`）时。那时树上不会躺着变异，这一步只剩「锚点失效」一种，`mutate.ts` 开跑前那道体检已经报。

## 变异残留：暂存区

工作树完好、变异却 `git add` 进了暂存区，下一次提交会把它带进去。

- **第四片：判定。** `stagedResidue(目录, 读工作树, 读暂存区, 读 HEAD)`：工作树上已报的（按编号）不再看暂存区；其余的对暂存区再判一遍，交没还原（`unrestored`）与分不开（`unclear`）；HEAD 上已是同一种的不交（改完还没 `git add` 时暂存区就是旧代码，必然像没还原）。HEAD 里没有这个文件的（新文件），分不开的改交第三种「认不准」（`unconfirmed`）：暂存了一版旧稿与真暂存了删一段的变异长得一样，分不开；没还原的照交。同一文件里一条躺在暂存区、把同文件别的条带成没还原或分不开的，那几条照交，只是不标是被它连带的。前提是编号唯一，重名时入口不调它。
- **第五片：入口。** `anchors.ts` 在编号不重复时用一次 `git cat-file` 读每个目标文件的暂存区与 HEAD 版本（不挑文件）。没还原、分不开的逐条点名，以 1 退出；认不准的单起一行 ⚠ 点名、叫人先 `git diff --cached` 看，不报错，可也不说「暂存区也查过」。读不到 git 时由 `notARepo` 认 git 的原话（入口按 `LC_ALL=C` 起 git）：只有「往上找仓库没找到」那一句放过（✓ 那一行说「不是 git 仓库，暂存区没查」），`GIT_DIR` 指错、属主不符、`.git` 坏了、没装 git 都以 1 退出并带出 git 的第一行原话，不静默放过。

## 硬退出收口（2026-11-12）

硬退出会截掉紧挨着它的那句诊断（输出是管道时 `console.error` 是异步的）。

- `mutate.ts` 里所有硬退出收成 `exitWith(code, ...lines): never`，退出前要说的话交给它、由它同步写满 fd 2 再退；被打断与起不来时走 `hardStop`（杀干净、收目录、再 `exitWith`），要说的那句也交给它头一个写。
- `sync-write.ts` 的 `writeAllSync`：一截一截写；`EAGAIN` 停 1 毫秒接着写，连着停够上限就放弃；`EPIPE` 当场放弃。诊断写不出去也照样退出 —— 那一步的承诺是退出码。`--brief` 那份清单是主产物，不设上限，写不出去以 1 退出。
- `exitRace` 按语法树认 `process.exit(…)`、`process['exit'](…)`（带 `globalThis.` 的也认），注释与字符串里的不算。
- `exitFaults(源码, 收口函数, 引入的名字)` 查一个入口收没收口：收口函数之外的硬退出报 `outside`；会退出的那一句之前、同一段语句里有 `console.` 调用的报 `async-before`。需求测试对真 `mutate.ts` 跑它。

**这道闸门替代的是「跑」**：原先靠一句注释纪律顶着，要等一次真截断撞在管道上才看得见。

> **什么条件下整个撤掉**：变异一步不再需要被打断时当场退出（比如改由外层进程管杀与收目录），那时 `mutate.ts` 里一处硬退出都不该有，`exitRace` 就够了，`exitFaults` 与对真 `mutate.ts` 那条断言一起撤。

## 教训

**一个证据机制的边界，会变成注意力的边界。** 变异只跑单元测试 → 单元层每一处都有人守 → 接线层没有激励 → 同一个形状的缺陷反复出现、每次都靠评审器指出。**纪律填不平机制的洼地，只会一直记录人掉进去。** 推论：看见一条纪律被反复违反，先问「有没有一个检查在管它」，再问「那个检查够得着它吗」。

**一条写着重启条件的欠条，挡不住作者在别的步骤里凭直觉重新发明它**；**条件挂在错的文件上，它就不会响**（P3.b「断点在不在」那一格是判定层换了跑法才失效的，条件却挂在 `collect.ts` 上）。

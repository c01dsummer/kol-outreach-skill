# ADR-72 变异跑改成有界并行，隔离到目录而不是进程

- 2026-09-09 · 起因是「`npm run check` 太慢」这个请求，先量再改
- 类型：扩范围（新跑法）—— 主体是「一次跑几条」；**另修掉它暴露出来的一处判定缺陷**
- 冲击的需求：无。变异集、归因、退出码逐条不动。**判定改了一处**：`judgeRun` 在
  「主动停掉」那一档改判开枪那一刻的快照 —— 方向是**收紧一处假红**，见末节
- 结论：**并行的单位是目录**；派法是**一条一派**；**派出去却没有结论回来的算硬失败**

## 先量出来的事实

在一台 4 核 Linux（Node v22.22.2）上量，不是推断：

| | 耗时 | 占比 |
|---|---|---|
| `npm run mutate`（293 条，串行） | 649.3 秒 | 整条 check 的九成 |
| `npm run selfcheck` | 36.0 秒 | |
| 其余 8 步合计 | 约 6 秒 | |

再往一次验证者跑里拆（临时插桩量的，最终对比用的是不带插桩的入口）：
一次完整 `scripts/test.ts` 约 1.9 秒，其中

- **起进程加装载模块约 1.15 秒**（node 自身约 0.04、tsx 那一层约 0.42、把四十来个模块
  过一遍加载钩子约 0.7）
- **它自己再起一个子进程验「真挨一刀」那一段约 0.5 秒**
- 四十六组断言加两次源码树指纹合计约 0.25 秒

也就是说，**一次跑里真正在断言的部分只占一成三**，其余是起进程和装模块。
这一条决定了方向：把每一次跑压快，天花板很低；能拿掉的是「一次只跑一条」。

## 为什么隔离到目录，不是到进程

一条变异是**真的改写一份源文件**，跑完再还回去。两条变异同时改同一棵树，
验证者跑的就是「两处改动叠在一起」那棵树，而报告仍按条归因 ——
那不是变慢，是**每一条的绿或红都不算数**。

所以每个 worker 拿一份自己的源码树（`.check-cache/mutate-jobs/w<i>`，`node_modules`
用符号链接，那份没人改）。改的、还的、它那一跑写下的覆盖记录，全在自己那份里。
真正的工作区从头到尾没有被动过 —— 这比原来更严，不是更松。

顺带一个后果：`scripts/test.ts` 往临时目录写的那几个夹具文件名里本来就带着进程号，
并行之后仍然互不相撞；自检那边用的是 `mkdtemp`，同理。

## 为什么一条一派，不是先切好再发

先按条数切成 N 份最省事，**但切不平**：指名了验证者的那两条跑的是自检，
一次 35 秒，而缺省那个验证者一次 1.5 秒。原型上量过：293 条切 6 份轮流发，
两份落在 186 秒，另外四份 154 秒 —— 32 秒的空转，正是那两条自检的代价。

要靠静态切法摊平，就得先知道每条要跑多久。**那个数今天没有人量过**，
猜一个写进代码，就是把「不知道」伪装成「知道」（`process/README.md` 总纲）。
一条一派不需要那个数：谁先空出来谁接下一条。代价是每条要回一句话。

## 派出去却没有结论回来的，算硬失败

worker 崩了、被杀了、汇报行被截断 —— 这几种在输出上长得都一样：**那一条没有结论**。
把它当成「跑过了、没事」正是总纲里那个头号事故（把第三档压进「是」）。
所以派出去的编号逐个核回来，少一个就报「没有结论」并以非零退出。
判定在 `scripts/check/jobs-rule.ts`，负片是 `M-H36-e`。

同一条道理管着汇报行怎么读：结论那个词不认得就是认不出，**不猜、不兜底成「被抓到」**
（`M-H36-d`）。

## 打断怎么办

派工那一侧自己不改任何源文件，所以它没有现场可还；它欠的是另一样东西 ——
那几个 worker 各自攥着一处改写和一个正在跑的验证者。派工进程直接退掉，
那些改写和那些验证者就被过继出去接着跑，谁也没在看着。

⚠️ **本条里 worker 并不自成一组**（`spawn` 没有 `detached`），自成一组的是它们各自
起的那个**验证者**。所以拓扑分两种情形：终端上按 Ctrl-C 打的是整个前台进程组，
worker 直接就收到了；而只发给派工进程那一个 pid 的信号（`kill <派工 pid>`）才需要转发。
两种情形下**验证者那一组都收不到**，得由它自己的 worker 去停 —— 这也是下面那条
「都收完了再走」为什么必要。（本段第一版把 worker 说成自成一组，与实现不符，
#109 第四轮评审指出。）

所以打断时先把那一刀转发给每个 worker（它们各自走原来那条 `onInterrupt`：
停掉手上的验证者、还原、非零退出），**都收完了再删目录、再退出**；
宽限期到了还没收完就硬来 —— 等不到的那种不能变成「Ctrl-C 按了没反应」。
判定在 `mutate-restore.ts` 的 `stopJobs`，四条负片 `M-H37-a`～`d`。

实测（不是推断）：4 核上跑到一半，分别按 Ctrl-C 的形状（整个前台进程组挨
SIGINT）和直接 SIGTERM 各来一次，两次都是 —— 工作区受跟踪文件一个字没变、
`.check-cache/mutate-jobs` 已清、`scripts/test.ts` 与 `mutate.ts` 一个残留进程都没有。
串行那条路（`MUTATE_JOBS=1`）同样各来一次，结果相同。

## 收益

同一台机器（4 核 Linux · Node v22.22.2）、同一个 Node、同一份输入，各预热 1 次再量 3 次，
三轮串行跑不互相争抢。**口径**：步骤清单从 `package.json` 的 `check` 那一行读出来逐步计时，
`check` 报的是各步之和（不含最外层那一次 npm 自身约 0.2 秒的开销，两边同样不含）；
real／user／sys 三个都记 —— 改了并行度之后墙钟变短而 CPU 时间不变是正常的，
只报墙钟会把「换了一批资源」说成「省下了工作」。

| | 变异条数 | check 均值 | mutate 均值 | mutate 区间 | 标准差 |
|---|---|---|---|---|---|
| 基线 `793f7ce` | 293 | 689.141s | 644.204s | 642.512–645.877 | 1.374 |
| 本条 | 302 | 273.062s | 227.823s | 227.307–228.108 | 0.366 |

mutate 2.83 倍、check 2.52 倍。**变异条数从 293 涨到 302**（本条新增 9 条负片守新判定，
跑的活更多），所以另给一组按条归一的：每条墙钟 2.199s → 0.754s（**2.91 倍**）。

六轮全部退出码 0；六轮跑完受跟踪文件的工作区内容指纹、HEAD、git 状态都与跑前一致，
隔离目录无残留，无残留进程。基线那一跑的 293 条结论与当时那棵树逐条对过 ——
**没有一条结论不一致**，多出来的正好是新增的那 9 条。

⚠️ **上面这一整节量的是 `793f7ce`／293 条那棵树，不是现在这棵。** 主干此后走了 50 多个
提交、变异集涨到 340 条以上，秒数和倍数都不能代表当前的树。**逐条比对那一条尤其要重来** ——
它正是本条的中心验收问题，而现在手上那份证据是旧树的。干净的重量与重新逐条比对
放在叠在本条上面的下一条，**在那之前这一节只能当历史读**。

并行效率：mutate 那一步 776.1 CPU 秒 ／ 227.8 秒墙钟 ＝ 3.41 核同时在忙，4 核机器上是 85%。

⚠️ 这些秒数只在这台机器上成立。**倍数可以跨机器参考，秒数不行。**

## 它买不到什么，以及没验过的边界

- **CPU 时间一点没省。** 省的是墙钟。核越少收益越小；单核机器上 `jobsWanted`
  直接给 1，走的还是原来那条串行路径，一个额外进程都不起
- **内存换时间**：同时活着的 node 进程从 2 个变成 2N 个
- **报告的行序变成「跑完的先后」**，不再是清单顺序（串行那条路仍是清单顺序）。
  每行自带编号，归因不受影响
- **磁盘**：每个 worker 一份源码树的副本（本仓库约 1.9 MiB），跑完删掉
- **Windows 没验过**，和 ADR-69 第二块欠条同一处境：那边 `detached` 给的不是进程组。
  本条新增的转发用的是「给那个子进程本身发信号」，不是进程组，所以这一层在 Windows
  上讲得通；但 worker 自己那条 `onInterrupt` 里的 `process.kill(-pid)` 仍然落空 ——
  **那笔账还欠着，本条没有还**
- **没量过的**：多核机器上到底几个 worker 最划算。本条给的默认值是机器核数，
  那是个合理的起点，不是量出来的最优

## 它踩出来的一处判定缺陷 —— 主干上本来就有，修在本条

并行唯一改变的是**机器忙不忙**，而这一条正是靠这个触发的。

`M-D6-j`（`by: selfcheck`，点名四条夹具）会时不时被判成「跑不起来」，
而它其实**被抓到了** —— 四条点名的夹具全红了。机制：见齐就停那一刀杀的是验证者
**整组**，自检自己正跑着的子进程被一起杀掉，临死前补打一句
`✗ …（进程）：预期以退出码 0 结束，实际是 null`，而这个记号在 `judgeRun` 里一票否决。
**那一句是我们自己那一刀打出来的，不是这条变异的罪证。**

**不是本条引入的**（实测，在主干上、串行、只跑这一条变异）：

| 主干 · 串行 | 8 次里红几次 |
|---|---|
| 机器空闲 | 0 |
| 3 核被占满 | **5** |

主干平时串行跑、机器空着，所以它一直没露头。**并行是暴露它，不是造成它。**

按 `6-INTEGRATE.md` 的路由，既有缺陷本该从主干单开一条。放在本条的理由是：
**它正是本条引入的可靠性回归** —— 合进去之后 CI 会三次里红一次，而 CI 机器核少、
负载高，恰恰是它最容易犯的场景。明知会坏还推，比越一次路由更糟。

改法：`judgeRun` 在「主动停掉」那一档判的是**我们动手那一刻它说过的话**，不是最终输出。
开枪之前就有的记号照旧一票否决（那时还没动手，记号是真的）；开枪之后才冒出来的
不算这条变异的账。「停没停」与「停的那一刻它说过什么」**合成一个形参** ——
拆成布尔加一份快照的话，两者对不上是表示得出来的状态，而对不上的症状是
判定悄悄换了一份输入。

验过：同样负载条件下重跑 **8 次全绿**；CI 上两趟独立全跑也都绿；
负片 `M-H27-a`／`b`／`c` 跟着新形状重新对上，新增 `M-H27-e` 守新判定 ——
逐条应用实测，它只弄红新加的那两条断言。

⚠️ **代价说清楚**：这一档从此对「开枪之后的输出」不设防。理由是那一段本来就由我们
自己制造，但它同时意味着 —— 万一将来有别的东西也在那个窗口里写进输出，判定看不见。
真正的护栏仍然是开枪**之前**那一段，两条既有断言钉着它。

## 起 worker 失败：为什么要单独接 `error` 事件

派工循环里建目录（`cpSync` / `symlinkSync`）抛出来的是同步异常，一个 `try/catch` 就够；
**而 `spawn` 起不来不是这么报的**。实测（Node v22.22.2，#109 第五轮评审指出）：

| 问的 | 实测 |
|---|---|
| `spawn` 失败会同步抛吗 | **不会** —— `try/catch` 接不到 |
| 事件顺序 | `error` → `close`（`close` 还会再来一次） |
| 没装 `error` 监听器 | **未捕获异常，进程当场死** |

所以 EAGAIN／EMFILE／可执行文件不在这几种，效果是派工进程崩掉，而已经起来的 worker
和隔离目录**全留下** —— 和「建目录抛错」是同一个洞的两半，只堵一半等于没堵。
接上 `error` 之后走同一条硬来路径；`hardStop` 里就 `process.exit`，
所以紧跟着那个 `close` 不会再结算一次。

⚠️ **这条路没有夹具。** 入口在验证基础设施闭包里，指着它的变异会被「自己验自己」拦下；
而 `spawn` 失败要靠资源耗尽（EAGAIN／EMFILE）才造得出来，夹具控制不了。
与本条另外几处入口代码同一处境 —— 上面那张「哪一半有证据」的表说的是同一件事。

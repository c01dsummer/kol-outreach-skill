## 一、换掉的是什么，为什么模型是零

P3 说的是**供应商真正收了几次钱**。代码里没有任何变量装着它，所以 9 月 5 日的做法是把它放进一个
状态机当变量，再穷举。那个状态机的每个动作「对应实现里一处真实位置」是人写下的一句话；
代码改了，那句话不会红。按 `process/README.md` 第二层的判据，它替代的是「读 `collect.ts` 找落盘点」——
正是模型再强一档自己会做得更好的事。

而模型唯一独有的产出（崩溃续跑之后供应商多收一次的那条反例）**可以在真实入口上执行出来**：
让测试用的假 fetch 记一本供应商侧的账，在真实 `collect.ts` 收到第 n 个 200、还没来得及落盘的那一瞬间
把进程 SIGKILL 掉，再 `--resume`，数账。账本就是那个「代码里没有变量装着」的量，现在由一个外部观测者
在请求真正出去的那一刻写下。

ADR-81 的三问，对留下的东西逐条答：

- **哑**。三处都是。把 `charge()` 挪到 `fetch` 之后，最终计数、退出码、断点文件一个字都不变，只有
  提交那一刻的计数从 1 变 0，没有任何测试看得见。崩溃窗口更哑：多花的那一次不出现在任何输出、任何
  文件里，用户看到的是一次正常续跑，它只出现在下个月的账单上。删掉循环里的 `persist()`，`main()`
  末尾那次照样把数写对，主干今天全绿。
- **模型代替不了**。它能替的是「读」——一眼看出补 profile 循环里没有 `persist`，所以旧资产里替它读代码的
  状态机与映射表全砍。它替不了的是「跑」：几千个响应序列上真实 `get()` 在提交那一刻的计数、真实入口被
  SIGKILL 之后 `task.json` 里留下的数 —— 这两个结果不随模型变，而写代码的那个模型照样会在重构时把
  `charge` 挪到 `fetch` 后面、把 `persist` 挪出循环。
- **发生过一半**。试点撞出两处真实的 P3 洞（`--budget 3.0.0` 让闸门整条不存在；`requests` 为 `null`
  整本账退回零），已修，记在 ADR-95。「先发再记」的重排在现场没有记录；「崩溃后多收」只在被砍的模型里
  出过反例。本条把后者变成在真实代码上跑出来的事实。

三样资产都是验证，按 ADR-85 属涨的一档，**不写死亡条件**（见「为什么没有死亡条件」）。

## 二、对照套件（`scripts/test.ts`）：oracle 只从需求推

真实的 `Budget`、真实的 `TikHub`，换掉的只有 `globalThis.fetch` 与 `globalThis.setTimeout` 的**返回值**，
不换调用位置：`tikhub.ts` 在调用那一刻才取全局 `fetch`，`sleep` 在调用那一刻才取 `setTimeout`。
假 fetch 按序列服务状态码，并在每次被调用那一刻记下 `budget.count`。

oracle 只从 P3.a（「`charge()` 在 spent + 本次开销 > limit 时抛 `BudgetExceeded` 且不增加计数」）与
`skill/references/providers/tikhub.md` 的计费列（200 计费、非 200 不计费、402 停）推出，**不含重试策略**：
文档说非 200 可重试三次，代码只重试 429 —— 两处不一致，oracle 不替它选边（见欠条）。

四条性质，对 tiktok 搜索这条单次 `get()` 路径，字母表 {200, 402, 429, 500}、长度 ≤ 4、
(上限, 起始计数) ∈ {(0,0),(1,0),(1,1),(2,0),(2,1)}：

1. 每次提交那一刻本地计数 = 起始 + 1，且 ≤ 上限（非 200 退款回起始，所以每次 attempt 前的闸门看到的都是起始）
2. 抛 `BudgetExceeded` ⇔ 起始 + 1 > 上限；此时提交 0 次、计数 = 起始
3. 正常返回 ⇔ 最后一个被服务的响应是 200；此时计数 = 起始 + 1；被服务的响应里 200 之后没有别的
4. 提交次数 ≤ 4，且至少有一例观测到 4 次（证明「重试耗尽」那条分支真的被走到）

两条与方法无关的通用不变量，扫六个公开方法（search × 2 平台、profile × 2、recentPosts × 2），
长度 ≤ 2：每次提交那一刻计数 = 起始 + 此前被服务的 200 数 + 1 且 ≤ 上限；返回或抛出时计数 = 起始 +
被服务的 200 数。它不需要知道某方法内部发几次逻辑请求，所以 IG reels 空→users 回退（两次 `get`）与
IG profile V3 失败→V2（两级端点）都进对照面，不再写成 ASSUMED。**只报观测到的每方法最大提交数，
不判**「IG profile 最多 8 次」—— 长度 2 量不到 8，不冒充量出来的数。

上限折算的次数**不许用 `Math.floor(limit / 0.001)` 算**：闸门是浮点比较，0.001–1.000 之间有 44 个上限
比 floor 少放行一次（例如 0.010 只放 9 次，第 10 次 9 × 0.001 + 0.001 = 0.010000000000000002 > 0.01），
多买的 0 个，方向对 P3 安全。测试与轨迹里的上限全部取自逐次算过的安全集合（0.001、0.002、0.004、0.005）。

## 三、三条崩溃续跑轨迹（`scripts/check/selfcheck.ts`）：期望等式怎么算出来的

`scripts/check/fake-fetch.ts` 加两个 env 旋钮，未设时严格无副作用：

- `FAKE_FETCH_LEDGER=<绝对路径>`：每次响应之前同步追加一行「状态码 ⇥ pathname」
- `FAKE_FETCH_KILL_AFTER_OK=n`：第 n 个 200 响应，先追加账本行，再 `process.kill(process.pid, 'SIGKILL')`

杀点落在假 fetch 内部 —— 响应已服务、尚未返回，此时 `tikhub.ts` 的 `charge()` 已经做完（内存计数已含本次），
入口的 `persist()` 还没跑（它在 `await` 返回之后）。这就是落盘窗口。旋钮只传给崩溃那一次 spawn，
续跑进程不带它，天然一次性。

**实测过的两条事实**（tsx 4.23.12，Node 22，本仓库的 `tsx-cmd.ts` 起法）：被杀的是 tsx 壳底下真正跑脚本的
孙进程，壳把信号译成 128 + 9，`spawnSync` 交回 `status: 137, signal: null`；杀之前写到 stderr 的提醒行与
`appendFileSync` 的账本行都留住了。所以自检对崩溃那一跑写 `expect: { status: 137 }`，走既有的 `runBoth`。

每条轨迹一个独立 cwd（`tmp` 下的子目录，带空的 `memory/`）：自检在别处把 `tmp/memory/creators.json`
截坏之后不恢复，共用 cwd 的续跑会以退出码 2 收场而不是 3。产品名各不相同：`taskDir` 是分钟级时间戳，
被杀那一跑打不出目录名，自检按产品名前缀在 `output/` 下找，断言恰好一个。夹具**只数账本里以 `200` 开头的行**：
假 fetch 每进程第 7 次调用回 429，三条轨迹每进程 ≤ 4 次，碰不到；碰到也只是多一行 429。

三条的期望值都是「上限折算的次数 + 落盘窗口内已计费的次数」，逐行走出来的：

**A · 搜索循环**。`--config`：两个 tiktok 词，`target_count` 500，`budget_usd` 0.002，`KILL_AFTER_OK` 2。
第一跑：开头存 `task.json`（requests 0）；kw0 过闸门→200（账本 1）→循环末尾 `persist`（盘 1）；
kw1 过闸门（内存 2）→第 2 个 200（账本 2）→杀。盘上 1，内存 2，窗口 1。
第二跑 `--resume`：Budget(0.002, 1) 还买得起 1 次 → kw0 第二页 200（账本 3）→persist（盘 2）；kw1 闸门抛 →
退出码 3。**账本 200 行数 = 3 = 2 + 1**。前提：罐头 `has_more: 1`，kw0 不进 done，续跑才会再搜它。

**B · 补 profile 循环**。`--config`：一个 tiktok 词，`target_count` 1，`budget_usd` 0.004，`KILL_AFTER_OK` 3。
第一跑：kw0 200（账本 1）→persist（盘 1）；下一轮开头 qualified() = 3 ≥ 1 → 达标 → `run()` 末尾 persist（盘仍 1）；
进补 profile：三人都 needsProfile（罐头搜索结果没有 signature，bio 是 undefined）；第 1 人 200（账本 2），
第 2 人 200（账本 3）→杀。**这个循环里没有任何 `persist()`**：盘上 1，内存 3，窗口 2。
第二跑：Budget(0.004, 1)；达标不搜索；补全结果上次一个都没落盘，三人重补：200、200、200（账本 4、5、6），
第 3 次 3 × 0.001 + 0.001 > 0.004 为假（浮点算过），放行 → 退出码 0。**账本 200 行数 = 6 = 4 + 2**。
选 0.004 而不是 0.003，是为了在 M-P3-b（断点永远写 0）下续跑的退出码也不变，否则那条变异会以进程记号被判成跑不起来。

**C · enrich 每账号**。复制「collect 完整流程」跑完并把 `fit` 全设 ✅ 之后的目录（连 `creators.raw.json`），
`task.json` 改 `budget_usd` 0.002、`requests` 0，删 `enrichment.json`，`KILL_AFTER_OK` 2。
五个可抓账号（IG 那个私密号被 profile 罐头的 `is_private: false` 盖过，照常抓）。第一跑：账号 1 200（账本 1）
→`assess` 末尾 persist（盘 1，`enrichment.json` 一个账号）；账号 2 200（账本 2）→杀。窗口 1。
第二跑同一条命令（enrich 没有 `--resume`，靠 `enrichment.json` 跳过已查的）：账号 1 零请求；账号 2 200（账本 3）→persist（盘 2）；
账号 3 闸门抛 → 末尾 persist → 退出码 3。**账本 200 行数 = 3 = 2 + 1**。

三条各配两条具名断言（`named()`，进变异清册）：崩溃那一跑「盘上 = 账本 200 数 − 窗口」，续跑「账本 200 数 = 上限 + 窗口」。
每条轨迹还打印一行**抽取列**（盘上的数、账本 200 数、非 200 数、两个进程各打了几行「💰 已用」），只打印不判定 ——
提醒行数是 F7.a 那张欠条的原料，交给会读的那一侧。

## 四、结论与等级

词表沿用试点的七级，其中 `PROPERTY_TESTED` 按无模型重写：**在显式有界、可枚举的输入域上逐个跑真实实现，
oracle 只从需求与契约推出、不 import 实现**。`MODEL_CHECKED` 与 `MODEL_ONLY` 两档随模型一起归零；
`PROVED_IMPLEMENTATION` 一条都没有 —— 写下来免得被读成有。

| 结论 | 需求 | 等级 | 机制 |
|---|---|---|---|
| tiktok 搜索单次 `get()`：提交前必已记账、被拒不发不计、200 之后不再提交、最多提交 4 次且耗尽分支被走到 | P3 · P3.a | `PROPERTY_TESTED`（字母表 4 个、长度 ≤ 4、上限 ≤ 2） | 对照套件；负片 M-P3-c 以「提交那一刻计数 = 起始」红，M-P3-e 以性质 2 红 |
| 六个公开方法（含 IG 两种回退）：每次提交时计数 = 起始 + 此前 200 数 + 1 且 ≤ 上限；返回时计数 = 起始 + 200 数 | P3 · P3.a | `PROPERTY_TESTED`（长度 ≤ 2） | 同一夹具的通用不变量；只报每方法最大提交数 |
| 被预算拒绝的那一次不增加计数、不发出 | P3.a | `UNIT_TESTED` + `PROPERTY_TESTED` | `test.ts` 固定样例（已在主干）+ 对照性质 2；负片 M-P3-a、M-P3-e |
| 续跑用盘上的 `requests` 初始化，spent 不归零；坏取值在花钱之前被拦下 | D6.a | `UNIT_TESTED`（续跑那半是自检端到端） | 已在主干（ADR-95；续跑从零起算那条负片 M-D6-m 与断点文件名那条 M-D6-n 随 #132 进的，本条的 enrich 落盘负片因此让号到 M-D6-o）；负片 M-D6-l、M-D6-m、M-P3-b |
| 50%／80% 各提醒一次 —— **每个进程内** | F7.a | `UNIT_TESTED` | 已在主干；跨进程的「每任务一次」不裁，抽取列每次印出提醒行数 |
| 预算用尽 → 落盘断点 → 退出码 3 | P3.b | `UNIT_TESTED`（自检端到端） | 已在主干；负片 M-P3-b |
| 不存在「已向供应商提交付费请求而本地无记录」的状态 —— **不成立**，三个窗口各一条反例在真实代码上执行出来 | P3 · D6.a | `UNIT_TESTED`（端到端固定夹具，反例） | 轨迹 A/B/C 崩溃那一跑的断言；负片 M-P3-f、M-D6-o、M-P3-b |
| 崩溃续跑之后供应商收的钱可以超过上限，超出量 = 落盘窗口内已计费的次数 —— **不成立**，反例执行出来 | P3 | `UNIT_TESTED`（反例） | 轨迹 A/B/C 续跑的断言（3 = 2 + 1、6 = 4 + 2、3 = 2 + 1） |
| 这三个窗口之外没有别的交错让供应商账超过本地账 | P3 | **无法证明** | 记录里三行推理：唯一让账本超过盘上的转移是收费之后、落盘之前死掉；charge 与 send 之间死掉是少记不是多收；连崩两次只叠加次数不改变窗口。不写「应该没问题」 |
| 非 200 供应商不计费 | P3 | `ASSUMED` | 只在 tikhub.md 里；假设为假时每次逻辑请求最多多收 3 次（429 重试），IG profile 两级端点再乘二。变成结论只能拿账单核 |
| 同一时刻只有一个进程写 `task.json`；probe 的花销进账；断电后这次写回留得住 | D4 · P3 · F1 | `ASSUMED`（前两条已知为假） | 并发 D4 已撤回承诺（ADR-66）；probe 不落盘是 ARCHITECTURE 写明的代价；ADR-50 不作保证 |
| 浮点让 44 个上限少买一次，多买 0 个 | P3 | `ASSUMED`（方向安全） | 实算过；不写成不变量 |

## 五、四条负片各杀在哪

- **M-P3-c**（`providers/tikhub.ts`：把 `charge()` 挪到 `fetch` 之后）。最终计数一模一样，只有对照套件在提交那一刻
  读到的计数是起始而不是起始 + 1 —— 这是整套资产里唯一守「顺序」的负片，主干今天没有任何东西抓它
  （既有测试把 `get()` 整个换掉，自检比的两边都来自 `Budget.count`）。
- **M-P3-e**（`lib/budget.ts`：记完账再比「已花是否超」）。被拒的那一次也记进账：上限 0.005 放行 5 次、抛，计数 6 ——
  `test.ts` 既有断言「抛出时不增加计数」红（6 ≠ 5），对照性质 2 也红。**为什么不是字面上的「把 `requests += n` 挪到判断之前」**：
  那种形状会让 F7 套件（`new Budget(0.010)` 连打 9 次、没有 try）在第 9 次未捕获抛出，整份测试打不出汇总，
  按 4-VERIFY「验证者崩了不算抓到」判成跑不起来。
- **M-P3-f**（`by: "selfcheck"`，`collect.ts` 删掉搜索循环末尾那次 `persist()`，find 串带上下文，首次匹配唯一）。
  轨迹 A 崩溃那一跑盘上停在 0（0 ≠ 2 − 1），续跑从 0 起做两次（4 ≠ 3）：两条具名断言都红，退出码 137 与 3 不变，
  无进程记号。主干今天删掉它全绿 —— `main()` 末尾那次 `persist` 把数写对了，只有在两次落盘之间把进程杀掉才观察得到。
- **M-D6-o**（`by: "selfcheck"`，`enrich.ts` 删掉 `assess()` 末尾那次 `persist()`）。轨迹 C 同形：0 ≠ 1、4 ≠ 3。
  落盘节奏第一次有负片。
- 既有 **M-P3-b**（断点永远写 0）的 `kills` 加进轨迹 B 崩溃那一跑的断言（盘上 0 ≠ 3 − 2）——
  B 在被杀前已经走过 `run()` 末尾的 `persist`，M-P3-f 杀不到它；这是 B 的第三拍，零成本。

ADR-89 末尾那张欠条响了（「下一条要往 `mutations.json` 加变异的改动 —— 顺手看一眼它盖的是不是从来没人盖过的地方」）：
四条里三条盖的是从来没人盖过的地方（`charge` 与 `fetch` 的先后、两处循环内的落盘节奏），一条（M-P3-e）盖的是
既有断言「抛出时不增加计数」原本抓不到的形状。答完，那张欠条的条件按原样留着，下一条加变异的人再答。

## 没做的，写在明处

> ⚠️ 欠条：**崩溃与续跑之后供应商收的钱可以超过已确认的上限。** 三条轨迹今天都是正面断言这个缺口
> （账本 = 上限 + 窗口）。这不是一处写错，是这个架构的性质：任何把落盘和发请求分成两步的实现都有这个窗口。
> P3 的两条判据只说了 `charge()` 与退出码，D6.a 说「spent 连续不归零」也没说崩溃 —— 登记表没有决定崩溃时该怎样，
> 这里不替它裁决。要把它变成保证得改协议：先写「打算发一次请求」再发，或者按供应商账单对账。
> · 重启条件：**有人要把崩溃安全变成保证**，或 `docs/requirements.json` 里 P3 多出一条对崩溃续跑的判据 ——
> 那一刻三条轨迹续跑的期望从「= 上限 + 窗口」翻成「≤ 上限」，本条销掉（怎么核见「什么条件下重开这个讨论」）。

> ⚠️ 欠条：**补 profile 那个循环整段不落盘，窗口是整份候选名单。** 轨迹 B 把它量成「多收 2 次」（三人里两人）；
> 名单有多长窗口就有多大。修法是在那个循环里加 `persist()`，那时 B 崩溃那一跑的断言会红（盘上不再是 1），去还本条。
> · 重启条件：**轨迹 B 的「盘上 = 账本 − 2」那条断言红了**，或者有人认为这是产品缺陷而不是可接受的已知缺口。

> ⚠️ 欠条：**F7.a 的「一次」是每个进程一次还是每个任务一次，登记表没有定义。** 提醒集合是进程内的，续跑新建一个
> 实例就空了；轨迹 A 的续跑起点已在 50% 之上，第一次放行的 charge 会把 50% 与 80% 一起打出来。按任务算的话
> F7.a 与 D6.a 就是一条交点，登记表里没有。抽取列每次印出两个进程的提醒行数，机器不裁。
> · 重启条件：**抽取列印出的提醒行数被当成问题提出来时**，或下次有人碰 `lib/budget.ts` 的提醒逻辑 —— 走 2-CHANGE 定义「一次」。

> ⚠️ 欠条：**预算用尽且记忆读不出来时退的是 2，不是 3。** 那条路径先 `persist()` 保住断点，再因为 P4 无法保证而中止
> （ADR-15），退 2 是有意的；但 P3.b 的措辞是无条件的「以退出码 3 结束」，登记表里没有 P3 × D4 这条交点。两侧都是红线，
> 实现者不许自选一条违反。建议把 P3.b 收成「没有更高优先的中止理由时」。**已知假响源**：这条裁决若落成 P3 的第三条判据，
> 下面那条重开命令会响，而崩溃语义没变 —— 那时人读一眼，期望不改。
> · 重启条件：**下次改 `collect.ts` 的收尾分支**，或有人按 P3.b 的字面写检查。

> ⚠️ 欠条：**「非 200 供应商不计费」是承重的假设，只活在 tikhub.md 里。** 假设为假时每次逻辑请求最多多收 3 次
> （429 重试 attempt 0 到 3），IG profile V3→V2 再乘二。没有需求、没有测试，也没法有 —— 只能拿账单核。
> · 重启条件：**拿到一份可核对的真实账单时**，或供应商改计费口径时。

> ⚠️ 欠条：**probe 的花销不写盘；两个进程同时对着一个任务目录跑时后写的会盖掉先写的。** 前者是 ARCHITECTURE 写明的
> 「probe 不落盘」的代价：F1 向用户要的是一个预算上限，而 probe 那些请求不进任何账。后者是 `collect` 与 `enrich`
> 都把计数整体赋值回 `task.json`；D4 已就记忆文件撤回并发承诺（ADR-66），`requests` 不在那条撤回里也不在任何保证里。
> 两个写方各从盘上 0 起花满上限时，供应商收 2 × 上限。
> · 重启条件：**Agent 被允许并行跑 `collect` 与 `enrich` 时**，或有人要把 P3 的上限说成整个任务的而不是每个进程的。

> ⚠️ 欠条：**重试契约以谁为准，需求侧没说。** tikhub.md 写「非 200 可安全重试、同一端点连续失败 3 次就停」且「429 从 150ms
> 调到 300ms」，代码只重试 429、其它非 200 立刻抛、间隔翻倍封顶 1000ms。对照 oracle 刻意不含策略，只钉「提交 ≤ 4 次」；
> 下一个「按文档修 oracle」的人会让对照红 —— 那是需求侧的事，不是对照坏了。
> · 重启条件：**下次有人改 `tikhub.ts` 的重试分支或 tikhub.md 的状态表** —— 两处只能留一个说法，走 2-CHANGE。

> ⚠️ 欠条：**「三个窗口之外没有别的交错会多收」只有三行推理，没有证明。** 砍掉穷举之后，崩在 charged 相位、连崩两次这两类
> 交错没有机器见证；方向对 P3 安全（少记不多收）是手推的。按「无法证明」记，不写「应该没问题」。
> · 重启条件：**有人在真实入口上找到第四种让账本超过盘上的走法时** —— 加一条轨迹，不是加回模型。

> ⚠️ 欠条：**`Budget.affordable` 是死代码，且与 `charge()` 在 44 个上限上相差 1。** 它按 `Math.floor(remaining / 0.001)` 算，
> `charge()` 按浮点比较放行；`new Budget(0.010).affordable` 说 10，`charge()` 只放 9 次。仓库里没有任何调用方。
> · 重启条件：**下次有人调用它**，或改 `lib/budget.ts` 的计价 —— 要么删掉，要么改成逐次比较。

## 为什么没有死亡条件

ADR-85 逐道判过：`test` 与 `selfcheck` 的假 fetch 端到端那一半属「验证，涨的一档」，**不该有**；
「硬编一条『产品入口不再需要密钥或网络时』，那是句永远不成立的话」。本条留下的三样全在那一档。
一条测试因重构而多余（比如花钱那一步在结构上并进 `Budget`），是重构那条 diff 里的一行红字（ADR-79 的形状，响的），
不是闸门的死法。写下「判过、不该有」，免得下一个人当成漏了去补一份不会响的条件。
整套没有豁免通道、不拦路、不加链步，也就没有「退成只报数」的形状可写。

## 什么条件下重开这个讨论

- **登记表对崩溃续跑有了裁决**：P3 多出一条判据，或 P3.b / D6.a / F7.a 的原文改动。那一刻三条轨迹续跑的期望按新文本重推
  （从「= 上限 + 窗口」改成「≤ 上限」），第一张欠条销掉。在那之前它们每次都要能红：SIGKILL 没杀死（退出码不是 137）、
  账本没写上、续跑没多买，三种都是红，不是跳过。
- **有人要加回模型**：只在「真实入口上跑不出来的交错」被找到时 —— 那时先加轨迹，轨迹加不出来再谈模型。

**谁去数**：没有机器在数（同 ADR-85 的处境）。下面这条命令落在仓库内，基线钉在 `eb1a0ad`（P3 两条判据；
P3.b、D6.a、F7.a 三段原文的 sha256 前 16 位），在 `origin/main` 2e5d22a（ADR-95 并入之后）上四个值逐个核过相同：

```bash
node -e '
const fs=require("fs"),crypto=require("crypto");
const rs=JSON.parse(fs.readFileSync("docs/requirements.json","utf8")).requirements;
const pick=id=>rs.flatMap(r=>[r,...(r.accept||[])]).find(x=>x.id===id);
const h=t=>crypto.createHash("sha256").update(t,"utf8").digest("hex").slice(0,16);
const BASE={P3_accept:2,"P3.b":"e4ae884ad1d80193","D6.a":"361ea72adf0855cf","F7.a":"1c0031d3239d283b"};
const fired=[];
if (pick("P3").accept.length!==BASE.P3_accept) fired.push(`P3.accept ${BASE.P3_accept}→${pick("P3").accept.length}`);
for (const id of ["P3.b","D6.a","F7.a"]) { const x=pick(id); if (!x||h(x.text)!==BASE[id]) fired.push(id+(x?" 原文变了":" 没了")); }
console.log(fired.length?"重开："+fired.join("；"):"未响"); process.exit(fired.length?1:0)
'
```

按 ADR-85 的三句自问：扫的范围与条件写的范围是同一个（只有那四样，不是 git 历史、不是整份登记表）；仓库里既有的
`spec-rule` 内容指纹判的是整册，口径比这宽、用途不同，两者不会给出矛盾答案；答不准时**偏宽** ——
三段原文改一个标点也响、P3 少一条也响，响了要人读一眼。**偏窄的那一面**：崩溃续跑的新判据若挂在 D6、F7 或新需求名下，
不响；这是它主要的漏，写在这儿。这条命令是新判据，不是引用既有代码的判据。

## 教训

**穷举得再全，也只证明抄本自洽。** 9 月 5 日那套资产在模型里找到的每一条反例都是真的 ——
但「模型和代码是一回事」这句话没有任何东西在跑，只有一张要人回来核的表。ADR-78 撤掉架构锚点表撤的正是这个形状，
而我在同一个仓库里又建了一张。

第二条：**要证明的量代码里没有，就在真实执行里造一个观测者，不要在模型里造一个变量。** 供应商收了几次钱，
假 fetch 在请求出去那一刻写一行账，比任何状态机里的 `billed` 都更接近事实。

第三条：**负片的形状要先走一遍验证者。** 「先记账再判断」照字面挪一行，会让一条不相干的套件未捕获抛出，
整份测试判成跑不起来 —— 抓到了也不算抓到。

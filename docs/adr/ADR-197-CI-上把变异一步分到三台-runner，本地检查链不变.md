# ADR-197 CI 上把变异一步分到三台 runner，本地检查链不变

- 日期 · 2026-11-14 · Linear KOL-1（恢复 CI 耗时）
- 类型：检查链在 CI 上的跑法。不动任何需求、判据、断言或变异的判定；本地 `npm run check` 一步不改
- 触发它的事实：KOL-1 关单标准第 3 条（需求所有者丸子 2026-11-14 12:02 CST 定）要 Linux CI 完整检查连跑 5 次的中位数不超过 18 分钟。同一天在 #470 第一个提交上实测现状：主干 `5f68c8b` 在 5 台 runner 上各跑一遍，job 耗时 19:35、24:35、28:24、29:04、29:09，中位 28:24（CI run 43555465585）
- 决定人与时间：做法由 KOL-1 线程提出；多花 runner 分钟数这一取舍，需求所有者丸子 2026-11-14 05:25Z 在 KOL-1 线程的决策卡上选「分到 3 台并行（推荐）」（卡上问「CI 提速是否接受多花 runner 分钟数，把变异分到 3 台机器并行？」；另两个选项是分到 2 台、不加机器只改代码）
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 连带改动：`scripts/check/jobs-rule.ts`（新增 `shardWanted`、`shardOf`）· `scripts/check/mutate.ts`（认 `MUTATE_SHARD`）· `.github/workflows/check.yml`（拆成三种 job）· `scripts/test.ts` 组 `h-jobs` 加 17 条断言 · `scripts/check/selfcheck.ts` 新组 `mutate-shard`（入口接线）· `scripts/check/mutations.json` 加 `M-H197-a`～`k` · `README.md`、`docs/ARCHITECTURE.md` 各一句 · `scripts/check/launches.json` 回写

## 一、时间花在哪

EPYC 7763 那台（29:09）逐步：`npm test` 143 秒，变异 1,382 秒，自检 193 秒，其余九步合计约 15 秒。变异占八成。
本机（4 核 Xeon 2.3 GHz，nobody 用户，`/var/tmp` 下的副本）同一主干：`npm test` 119 秒，变异 902 秒（user 1,999 + sys 487 秒），自检 168 秒。
变异 1,987 条、198 种配置；单台 4 核上变异一步的 CPU 已经用到 2.75～3.3 核。

ADR-97 第三节量过：单机上的派工离理想下界只差 2.7%，靠排序与派工省不出时间。要在一周内省下 10 分钟，只剩两条路：
砍每条变异的成本（改验证者、改夹具，逐组去省，每一处都要另证没减弱），或者多用几台机器。本条走后一条。

## 二、做法

**`MUTATE_SHARD=k/n`**：变异清单按出现顺序轮流发成 n 份（第 i 条归第 `i % n + 1` 份），这一跑只施变、派工第 k 份。
轮流发而不切连续几段：同一种验证者配置的变异在清单里挨着写，贵的一段一段，切连续几段会让某一份全是贵的。
开跑前那几道体检（归因、标签、接线、ORDER 绑定、维护比较）、子集基线与启动数，**仍按整份清单做**：
每一份写下的 `output/mutation-launches/launches.json` 都一样，启动数闸门读哪一份都是整份的数。
没写或写空就是整份（1/1）；写了读不出来（不是 `k/n`、k 不在 1～n）以 1 退出、一条变异也不施 —— 悄悄按整份跑等于几台各跑一遍全量，悄悄跑错一份是有几条谁也没跑。
验证者里再起的 `mutate`（玩具树）不带这个变量：`verifierEnv` 把它摘掉，玩具树一律整份。

**`check.yml` 拆成三种 job**：

| job | 跑什么 |
|---|---|
| `chain` | `anchors` `size` `spec` `skill` `adr` `typecheck` `compile` `test` `selfcheck` `audit`，顺序同 `npm run check`；把自检写的按族启动计数交出去 |
| `mutate`（3 份） | `compile` 之后 `MUTATE_SHARD=k/3 npm run mutate`；第 1 份把启动数文件交出去 |
| `check` | 等前两种都绿，取回两份计数，跑 `npm run launches`（检查链最后一步），再跑墙钟对比 |

合起来跑的步骤与本地 `npm run check` 相同，哪一份红、哪一步红，这一跑就红。最后那个 job 仍叫 `check`。
本地不写 `MUTATE_SHARD`，`npm run check` 照旧一条链跑完。

## 三、实测

**改前**：上面那 5 次，中位 28:24。

**改后**：在 #470 上加一个临时提交，让三种 job 各按 5 组跑（每组一份 `chain`、三份 `mutate`、一个 `check`），量完撤掉。
每一组的耗时 = 它那几个干活的 job 里最长的那个 + 最后那个 job。

- CI run 43560599550（`856404c`，全部 25 个 job 绿）：5 组 11:20、11:22、11:02、11:25、10:45，**中位 11:20**；整个 run 05:14:54 → 05:26:29。
- 更早一跑 CI run 43558035192（`42f6170`）：5 组都不超过 11:12；那一跑最后那个 job 红在启动数摘要（改了 `scripts/` 的 `.ts`，树内摘要还没回写），计时不受影响。

两跑里最长的都是某一份变异（7～11 分钟），`chain` 5:20～6:05。关单标准第 3 条要的是合入后主干上连跑 5 次的中位数，这里只是合入前的预估；合入后的那 5 次记在 KOL-1 卡上。

**本地 `npm run check` 不变**：本机同一台（4 核 Xeon 2.3 GHz），主干 `5f68c8b` 与本条 `8b770e0` 各计时跑一遍检查链的 12 步（整份，不写 `MUTATE_SHARD`），每步记墙钟与 CPU 时间（user+sys）：

| 步 | 主干 墙钟 / CPU | 本条 墙钟 / CPU |
|---|---|---|
| `npm test` | 119 / 129 秒 | 119 / 129 秒 |
| 变异 | 902 / 2,486 秒 | 908 / 2,525 秒 |
| 自检 | 168 / 306 秒 | 172 / 318 秒 |
| 其余九步合计 | 约 10 / 16 秒 | 约 11 / 17 秒 |

每个版本只跑了一遍，没有多次的区间；本地这条路的代码在不写 `MUTATE_SHARD` 时只多一次读变量、整份照旧（第二节），这组数只用来看有没有明显变慢，不当精确对比。
本条那一跑最后一步启动数红（同上，摘要还没回写），回写之后整条 `npm run check` 绿；其余 11 步两跑都绿。
（日志：项目共享盘 `ci-duration/2026-11-14-KOL-1/`。）

CI 那边只有墙钟：GitHub 的 job 记录不给 CPU 时间。KOL-1 关单标准第 3 条判的就是墙钟中位数，抗抢占的量在这里拿不到，用多组的区间（10:45～11:25）代替。

**runner 分钟数**：改前每跑一台 19:35～29:09；改后 `chain` 约 6 分钟 + 3 份变异各 7～11 分钟 + 最后那个 job 不到半分钟，合计约 32～34 分钟，每跑多四五分钟到十来分钟。

## 四、代价与没做的

- 每一份都跑全部 198 种子集基线（本机约 3 分钟墙钟），三份重复付了两遍。只让第 1 份跑全部、其余份只跑自己用得到的那几种能再省一点，
  但那要动基线与启动数的分工，本条不做；重启条件见第五节欠条。
- 本机试过 `MUTATE_JOBS=6`（4 核上派 6 个 worker）：变异 768 秒对 902 秒，user+sys 几乎不变。说明 4 个 worker 时有空等。本条不改缺省派工数，记在这里供以后用。
- 「防止性能回退」不在 KOL-1 范围（关单标准第 6 条）：墙钟对比照旧只报数。
- 墙钟对比那一步的字节一个没动，但它读的东西变了：它现在跑在最后那个 job 里，打出的 CPU 型号是那台 runner 的，不是跑变异的那几台；「摊到每条」除的仍是整份变异条数，分子却成了这一跑的墙钟（三份并行）。合入后头几跑与改前主干的中位数比会显著变小（约四成），那是拆开的效果，不是代码变快了。`check.yml` 那一步上方的注释写明了这一点。

# ADR-197 CI 上把变异一步分到三台 runner，本地检查链不变

- 日期 · 2026-11-14 · Linear KOL-1（恢复 CI 耗时）
- 类型：检查链在 CI 上的跑法。不动任何需求、判据、断言或变异的判定；本地 `npm run check` 一步不改
- 触发它的事实：KOL-1 关单标准第 3 条（需求所有者丸子 2026-11-14 12:02 CST 定）要 Linux CI 完整检查连跑 5 次的中位数不超过 18 分钟。同一天在 #470 第一个提交上实测现状：主干 `5f68c8b` 在 5 台 runner 上各跑一遍，job 耗时 19:35、24:35、28:24、29:04、29:09，中位 28:24（CI run 43555465585）
- 决定人与时间：做法由 KOL-1 线程提出；多花 runner 分钟数这一取舍在同一线程的决策卡上请丸子定（推荐「分到 3 台并行」），答复补记在本条末尾
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 连带改动：`scripts/check/jobs-rule.ts`（新增 `shardWanted`、`shardOf`）· `scripts/check/mutate.ts`（认 `MUTATE_SHARD`）· `.github/workflows/check.yml`（拆成三种 job）· `scripts/test.ts` 组 `h-jobs` 加 15 条断言 · `scripts/check/mutations.json` 加 `M-H188-a`～`f` · `scripts/check/launches.json` 回写

## 一、时间花在哪

EPYC 7763 那台（29:09）逐步：`npm test` 143 秒，变异 1,382 秒，自检 193 秒，其余八步合计约 15 秒。变异占八成。
本机（4 核 Xeon 2.3 GHz，nobody 用户，`/var/tmp` 下的副本）同一主干：`npm test` 119 秒，变异 902 秒（user 1,999 + sys 487 秒），自检 168 秒。
变异 1,987 条、198 种配置；单台 4 核上变异一步的 CPU 已经用到 2.75～3.3 核。

ADR-97 第三节量过：单机上的派工离理想下界只差 2.7%，靠排序与派工省不出时间。要在一周内省下 10 分钟，只剩两条路：
砍每条变异的成本（改验证者、改夹具，逐组去省，每一处都要另证没减弱），或者多用几台机器。本条走后一条。

## 二、做法

**`MUTATE_SHARD=k/n`**：变异清单按出现顺序轮流发成 n 份（第 i 条归第 `i % n + 1` 份），这一跑只施变、派工第 k 份。
轮流发而不切连续几段：同一种验证者配置的变异在清单里挨着写，贵的一段一段，切连续几段会让某一份全是贵的。
开跑前那几道体检（归因、标签、接线、ORDER 绑定、维护比较）、子集基线与启动数，**仍按整份清单做**：
每一份写下的 `output/mutation-launches/launches.json` 都一样，启动数闸门读哪一份都是整份的数。
没写或写空就是整份（1/1）；写了读不出来（不是 `k/n`、k 不在 1～n）以 1 退出、一条变异也不施 —— 悄悄按整份跑等于几台各跑一遍全量，悄悄跑错一份是有几条谁也没跑。
验证者里再起的 `mutate`（玩具树）不带这个变量：`verifierEnv` 把它摘掉，玩具树一律整份。

**`check.yml` 拆成三种 job**：

| job | 跑什么 |
|---|---|
| `chain` | `anchors` `size` `spec` `skill` `adr` `typecheck` `compile` `test` `selfcheck` `audit`，顺序同 `npm run check`；把自检写的按族启动计数交出去 |
| `mutate`（3 份） | `compile` 之后 `MUTATE_SHARD=k/3 npm run mutate`；第 1 份把启动数文件交出去 |
| `check` | 等前两种都绿，取回两份计数，跑 `npm run launches`（检查链最后一步），再跑墙钟对比 |

合起来跑的步骤与本地 `npm run check` 相同，哪一份红、哪一步红，这一跑就红。最后那个 job 仍叫 `check`。
本地不写 `MUTATE_SHARD`，`npm run check` 照旧一条链跑完。

## 三、实测

**改前**：上面那 5 次，中位 28:24。

**改后**（#470 的 `42f6170`，即本条的实现加一个临时提交：三种 job 各按 5 组跑，CI run 43558035192）：
`chain` 5 次 5:20～6:05；`mutate` 15 份 7:19～10:53；整个 run 04:43:16 → 04:54:30。
每一组的耗时 = 它那几个 job 里最长的那个 + 最后那个 job（11～18 秒），5 组都不超过 11:12。
那一跑最后那个 job 红在启动数摘要（改了 `scripts/` 的 `.ts`，树内摘要还没回写），见第五节；计时不受影响。
回写之后的那一跑记在第六节。

**本地 `npm run check` 不变**：本机同一台、同一口径，主干 `5f68c8b` 与本条 `8b770e0` 各跑一次完整检查（整份，不写 `MUTATE_SHARD`）：
变异 902 秒 / 908 秒，user+sys 2,486 / 2,525 秒；`npm test` 119 / 119 秒；自检 168 / 172 秒。都完整成功。
（日志：项目共享盘 `ci-duration/2026-11-14-KOL-1/`。）

**runner 分钟数**：改前每跑一台约 25～29 分钟；改后 `chain` 约 6 分钟 + 3 份变异各 7～11 分钟 + 最后那个 job 不到半分钟，合计约 32～34 分钟。

## 四、代价与没做的

- 每一份都跑全部 198 种子集基线（本机约 3 分钟 CPU 墙钟），三份重复付了两遍。只让第 1 份跑全部、其余份只跑自己用得到的那几种能再省一点，
  但那要动基线与启动数的分工，本条不做；重启条件见第五节欠条。
- 本机试过 `MUTATE_JOBS=6`（4 核上派 6 个 worker）：变异 768 秒对 902 秒，user+sys 几乎不变。说明 4 个 worker 时有空等。本条不改缺省派工数，记在这里供以后用。
- 「防止性能回退」不在 KOL-1 范围（关单标准第 6 条）：墙钟对比照旧只报数。

## 五、欠条清点

> ⚠️ 欠条（档：登记）：CI 上三份变异各跑一遍全部子集基线，两份是重复的；只让一份跑全量、其余份只跑自己用得到的配置要改基线与启动数的分工 · 重启条件：CI 中位数又超过 18 分钟时，或下一条改子集基线那一段（`mutate.ts`「同一组选跑配置只做一次正常代码基线」）的改动

> ⚠️ 欠条（档：登记）：`check.yml` 里三种 job 怎么拼成与 `npm run check` 相同的一条链，检查链里没有测试或变异守着 —— `chain` 那一行少写一步、`mutate` 的份数与 `MUTATE_SHARD` 的分母对不上，都不会有任何东西红 · 重启条件：下一条改 `check.yml` 里这三种 job 的改动，或 `package.json` 的 `check` 那一串增删一步时

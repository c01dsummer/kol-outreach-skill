# ADR-87 替代跑的建、替代读的不建：把这条判据搬进流程档

## 起点：拦住我的是一句人问的话，不是流程档

ADR-86 那一轮，欠条台账原本要做成「拿这次改动的文件清单去匹配欠条的重启条件」。
那是一张路由表，靠一张手写的符号索引活着，正是 ADR-77 撤掉纪律 lint 的形状。

**它没落地，是因为有人在代码写出来之前问了一句「我们在 bitter lesson 的原则吗」。**
不是因为 `process/` 拦了我。

反过来看更难受：`process/README.md` 第二层写着

> **所以：每一条你真正在乎的纪律，能变成检查就变成检查。**

**没有任何限定。** 我在乎欠条被忘掉，于是我去把它变成检查 ——
完全照着那句话做的。**那句话当时正在把我推向错的一侧。**

## 判据一直堵在决策记录层

斜率判据（涨的留、跌的标死亡条件、不动的永远留）散在哪儿 —— **数钉在本条的基线
`e00efd7` 上**，那棵树不会再动（`REVIEW.md` 给的两条出路之一；另一条是只写命令不写输出）：

```bash
git -c core.quotePath=false grep -c '斜率\|涨的\|跌的\|会变强' e00efd7 -- .
```

| 在哪 | 在 `e00efd7` 上的出现次数 |
|---|---|
| ADR-85 | 13 |
| ADR-76 | 3 |
| ADR-86 / ADR-81 | 各 2 |
| ADR-78 / ADR-79 | 各 1 |
| **`process/README.md`** | **1，而且只是叙述** |

**这张表在本条合入的那一刻就不再代表现状了** —— 本条正是来改它的。
它钉的是「搬之前长什么样」，不是「今天长什么样」。

那唯一一处写的是「每一道撤的时候都摆出了判据：边际价值的斜率、……」——
**它在讲 2026-09-18 那天发生了什么，不是在给下一个人一条判据。**

按 `docs/SYNC.md` 那条判别规则，换个产品也成立的规则写在 `docs/` 就是写错地方；
这一条连 `docs/` 都没到，还在 `docs/adr/` 里。而 `process/README.md` 自己写着
「给一条纪律找到判据，就把它搬下来」——**判据有了，在上面那几份记录里反复用过，没搬。**

## 搬下去的不是口号

「涨的留、跌的撤」落到手上分不出哪个是哪个。真正能用的是这个问题：

> **这道闸门替代的是「跑」，还是「读」？**

分不清时再问一句：**判据写不写得成一条命令？** 写不成、要靠一张手写的表去逼近，
那就是「读」。

本仓库刚好有一正一反两个实例，都来自 ADR-86 那一轮：

| | 它替代什么 | 判 |
|---|---|---|
| `⚠️ 欠条` 块里没写重启条件 | **跑** —— 定出块的范围，看块内有没有那四个字加冒号 | 建了 |
| 这次改动踩到了哪几条欠条 | **读** —— 要读懂条件说的是什么 | 撤了 |

而「撤了」那一侧不是靠推理判的，是实测：一条写着「下一条往 `SELFCHECK_TOOLS`
里加东西的 PR」的欠条，照字面做那件事，`git diff` 的 ± 行里那个词出现 **0** 次；
历史上也已经漏报过一次（`ADR-70:351` 的第二条腿「落地 4 开工」就是提交 `6fad02e`，
那次 diff 里 `mutatedCrit` 命中 0 次）。

## 两种失败不对称，这才是「拿不准时不建」的理由

一道替代「跑」的闸门坏了，**它当场报错**。
一张替代「读」的表漏了，**它报绿**。

而后者的漏会随时间变多：表是写下它那一天的仓库的样子，仓库不会停在那一天。
ADR-77 记的那张敏感字段表漏过 `plays`、后来又漏了 `score` 和 `null` ——
同一张表，漏的东西越来越多。**那不是那张表写得不好，是这个形状必然的结局。**

## 这一条自己落在第三层

「它替代的是跑还是读」要人判，没有机器能替人判。所以这一条也写进了
`process/README.md` 第三层那张表 —— 连同它判错时的症状：**一张表报绿，
而报绿不会自己暴露。**

这是 ADR-85 那个动作的又一次应用：**把「这一条机器管不了」写下来**，
否则下一个人会当成漏了，然后去给它补一道检查 —— 而补出来的又会是一张表。

## 动了哪三处

- `process/README.md` 第二层：在那句没有限定的话后面加一节，写清楚例外那一类
- `process/README.md` 第三层那张表：加一行
- `process/4-VERIFY.md`「判据的失效方式」开头：加一条指针。那一节问的是**已经决定要建**
  的检查强不强，该不该建是它前面那个问题，两者容易混

## 没做的

- **没有把「读/跑」这条判据做成任何检查。** 它自己就是「读」那一类 ——
  给它建一道闸门会当场违反它说的事。
- **没有回头重判已有的那几道闸门。** 今天这几道都是按同一把尺子撤过、留过的
  （ADR-76 到 ADR-81、ADR-85），重判一遍是另一件事。
  ⚠️ 欠条：**没有逐道回核「它替代的是跑还是读」。**
  重启条件：下一条要新建或者要撤一道闸门的改动 —— 那一刻顺手把同批的也过一遍。
- **`process/README.md` 里对本仓库决策记录的点名式引用又多了一处上下文。**
  那几段（往上撤那一节）本来就逐个点了 ADR 编号，而 `process/` 是跨项目复用的。
  本条新写的那一节没有引任何编号，但旧的那几处没动。
  ⚠️ 欠条：**流程档里点名了本仓库的决策记录编号。**
  重启条件：下一次这份流程档真的被复制到另一个项目时，或者下一条要动
  `process/README.md` 那一节的改动。

> ⚠️ 上文第 102–104 行那张欠条（流程档里点名了本仓库的决策记录编号）的条件在本块所在 PR 上响了：那条 PR 在 `process/README.md`「往上撤那个方向也正当」一节末尾加了一段，定死亡条件的写法。那一节在本条（#122，`55ad729`）之后没人改过（`git log -L183,205:process/README.md 979499c`，即本块所在 PR 的基线，只列得出本条之前 2026-09-18 的三个提交），本块所在 PR 是头一条。

> · 重启条件不变：下一次这份流程档真的被复制到另一个项目时，或者下一条要动 `process/README.md` 那一节的改动 —— 从本块所在 PR 合入起重新起算

## 一、问题与今天的树

拆进程之后，`needs` 连通的族是派工单位（ADR-132、`group-rule.ts` 的 `families`）：同一族在同一个进程里按登记顺序跑；不同族各在各的进程里，各有一份模块级变量、各有一个 `tmp`。一组读了别族的组写下的东西，拆进程跑时读到的就是初始值；被 `if (dir) { … }` 守着的那一节会整节静默跳过，自检照样全绿。拆进程之前，同样的漏写只影响 `--only` 选跑。

按第二节的规则扫，扫得见的通道里今天没有这种组；看不见的通道没核。规则在 `5e4e43c` 与 `fad416d` 上报出的只涉及一处：`tmp/jobs-cwd.txt`，`jobs` 与 `jobs-resource` 两族都提到它（`fad416d` 这一次是本条作者复跑的；条数按下一段的命令在第五节第 2 步落地时钉树再写）。这一处是良性的：`seedJobs` 把这个路径写进玩具验证者，验证者每跑一遍往里追加一行当前目录；`jobs` 先删、后读；`jobs-resource` 只经 `seedJobs` 提到这条路径，随后改写了玩具验证者（新的那份不再追加），而且起 worker 之前就耗尽描述符，验证者一次不跑 —— 既不追加也不读。它仍会报，是因为规则把提到 `tmp` 下的固定路径算作又读又写，有意保守（第二节）；回应办法见第五节第 3 步。

报了几组、几对，属于可算的数，不写进散文（ADR-73、ADR-82）：第五节第 2 步合入后，在那棵树上跑 `git show <被扫的树>:scripts/check/selfcheck.ts | npx tsx -e "<读 stdin，调 scanShares，打印 faults 与 problems>"`，两棵树（被扫的、规则所在的）各钉一个提交，数字写进那一步的落地记录。

## 二、规则扫什么、判什么

**扫。** 每组连同它提到的顶层函数，读写了哪些东西：

- **状态** = 顶层声明的非函数绑定。组里给它赋值（含解构赋值的目标、for-of／for-in 的循环变量）、`++`／`--`、`delete`、改它（或它的别名）的属性、调它会改自己的方法（`add`、`push`…），算写；其余提到它，算读。名字按编译器的符号表认，组里同名的局部变量不是那个顶层绑定。
- **`tmp` 下的固定路径** = 顶层 `const x = join(tmp, '字面量', …)`，以及组里直接写的 `join(tmp, '字面量', …)`。谁写谁读源码里看不出（多半是子进程在写），提到就算又读又写；一条路径是另一条的上级目录，也算碰到同一处。
- **经由顶层函数**：组里提到一个顶层函数（调用，或当实参传），它及它再提到的顶层函数读写的东西，都记到这一组头上。

**判。** 写方与读方是两组时：

- `family`：两组不在同一族。完整跑拆进程时，读方拿不到写方那一份。
- `closure`：同一族，读方只读不写，它的 `needs` 闭包里却没有写方。`--only` 点它时写方不跑。自己也写这份状态的组（惰性建夹具那种）、碰同一路径的组，不在这一类里判 —— 看不出谁靠谁。
- `merged`：组里读了子进程交回、父进程合并的那几样（`failed`、`claimed`、`covered`，类型钉在 `ShardReport` 的字段上）。拆进程后一组只看得见本进程那一份；这几样各进程各写一份、由合并收回，写不算共享。

`closure` 放进本次，是因为只有它抓得到这一种：本条作者在 `fad416d` 的副本里只把 `enrich` 的 `needs` 从 `['collect']` 改成 `[]`：`render` 的 `needs` 仍把 `collect` 与 `enrich` 连在同一族里，`family` 不报；除第一节那一处良性报告外，只多出 `closure dir: collect → enrich`。而 `--only` 是公开入口，选跑 `enrich` 时那一节会静默跳过。另取一份副本只把 `regress` 的 `needs` 改成 `[]`，多出 `dir` 与 `rendered` 两条 `family`。

设计阶段的第一版原型把解构赋值与循环变量的目标当成「读」，漏报过：把 `collect` 那句 `dir = JSON.parse(…).dir` 改写成 `({ dir } = JSON.parse(…))`、再拿掉 `regress` 的 `needs`，原型只报 `rendered` 那一条。定稿规则两条都报（本条作者在 `fad416d` 上复跑过这一例）。

**规则有意保守。** 两族各自建、各自用同一处，也会报：`tmp` 下同名的落点、跨族的惰性夹具都属于这种。**报出来之后的回应是给每组各自的路径或状态，不补一条假依赖。** 假 `needs` 会把两族并成一族，静默降低拆进程的并行度，而没有机器分得出真边与假边。规则头注、测试注释与本条三处写同一句话。

**扫描绿只说明「扫得见的组间共享都在 `needs` 里」**，读真源码那条断言就叫这个名字。看不见的通道：

- 拿 `tmp` 当当前目录起的子进程，按相对路径读写的文件（`memory/creators.json` 那一类）；
- 拼出来的路径（模板串、变量；`join(tmp, 非字面量)` 静默放过，不进 `problems`）；
- 经由实参或返回值交出去之后再被改的对象（`Object.assign(S, …)`、`S.get(k)!.add(…)` 都记成读）；
- 对象方法、条件表达式里的函数体；
- `process.env`、`globalThis`、import 进来的模块的状态；
- 顶层收尾段读组写下的东西。

「拆进程绿、单进程红」那一类，扫描同样看不见。这些仍只有真跑证得了（ADR-99 第二节），记作第七节第一张欠条。

## 三、比较过的做法

**甲（采纳）静态扫描。** 怎么做见第二节。好处：在 `npm test` 里就红，结果跟跑法无关，也覆盖选跑；判定全部在规则模块里，设计阶段的变异用真 `mutate.ts` 跑过、都被抓到（条数以第五节第 2、4 步落地为准）；`selfcheck.ts` 只为那一处良性报告改一个落点。代价：看不见的通道（第二节）；规则保守，今天就有一处良性报告；它是第三份识别 `group(…)` 的语法树扫描（另两份在 `mutate-rule.ts`：`routeLayout` 与按标签归组那一段），与 `routeLayout` 的口径已有一处不同（第六节）。

**乙（驳回）运行时格子。** 把跨组状态迁进 `group-rule` 管的格子，读的那一刻核对 `needs` 闭包、以及写方是否已在本进程跑完。它还能抓登记顺序错。驳回的理由：

- 不走格子的新状态照样静默。这等于把「记得写 `needs`」换成「记得走格子」，还是靠自觉。
- `selfcheck.ts` 要改几十行，格子读写的先后落在入口里：指着 `selfcheck.ts` 的 `by: selfcheck` 变异会被「自己验自己」拦下（`verifier-rule.ts` 的 `selfVerifying`）；`by: test` 的负片守得住（先例 `M-H42-j`，从 `scripts/test.ts` 起真自检跑子集），但每条负片都是一次真跑，代价落在 `npm test` 上。甲的负片只把源码文本喂给判定，不起进程。
- `group-rule.ts` 会从判定模块变成执行器（`docs/CONVENTIONS.md` 第 10 条）。

**丙（已知缺口）痕迹核，或两种跑法对照。** 完整跑结束时逐组核标签、判据与心跳；或者拿拆进程跑与 `SELFCHECK_JOBS=1` 单进程跑比对入口认领与 ✓ 行。好处是从后果一侧核，扫描看不见的通道也抓得到。本次不做：已有失败的那一跑不核；回报协议要改；对照法要多跑一整遍完整自检，正是 ADR-132 刚省下的那一块；入口一侧同样没有变异守着。它是第七节第一张欠条的两种还法。

**不动 `process/`。** `docs/SYNC.md`「新增一道闸门」那一行要求同步「`process/` 里那条纪律」。这一条纪律（自检组跨组共享要写进 `needs`）是本产品自检结构专有的，该落在 `docs/ARCHITECTURE.md` 的分组合同里（「自检以 `group(id, needs, callback)` 登记同步回调」那一段）—— 那一段今天还没写这一句，第五节第 4 步补上；通用的那一半，`process/4-VERIFY.md`（每个判定模块要有变异指向它）与 `process/6-INTEGRATE.md`（闸门走「最后一块砖」）已经写着。

## 四、同主题的两张旧欠条，本次不还

- ADR-131 末尾「跨组读取运行结果的组，没有机器检查保证被读的组登记在前」。它的重启条件是新增读取他组运行结果的依赖边，或调整 `review-cli-entry` 各组的登记顺序；本条及第五节的三条 PR 都不加依赖边、不调顺序，没有触发。同一份读写配对加上登记顺序就能判「纯读方登记在写方之前」，那是扩范围，要不要另开由需求所有者定。
- ADR-99 第九节「登记完成后不校验这张图」。它的重启条件是往 `REGISTERED` 里加组或改 `needs`；第五节三条 PR 都不碰 `selfcheck.ts` 的 `REGISTERED` 与任何组的 `needs`，没有触发。规则读这张图走的是 `group-rule.ts` 的 `families` 与 `wanted`，重复 id、缺失依赖在那里照旧当场抛。

## 六、已知代价与边界

- **有人把扫描绿当成 `needs` 写全。** 缓解只有措辞：断言名、规则头注、`docs/ARCHITECTURE.md` 与本条四处都写「扫得见的」，并列出看不见的通道。
- **第三份 `group(…)` 扫描，口径已经不一。** `routeLayout` 接受 `await group(…)`（`mutate-rule.ts`），规则把它报成扫不了。往失败那一侧偏，会大声红；但两份判定会漂。记作第七节第二张欠条。
- **`selfcheck.ts` 的登记本身坏掉时，读真源码那组会让整个 `test.ts` 进程抛出，不是带名字地红。** 重复 id、缺失依赖时 `families` 会抛，`test.ts` 的 `group` 不接异常。这是大声的，而且那时自检与变异也会硬失败；但排在后面的测试组跑不了。第五节第 4 步可以在这一组里包一层，把异常变成断言失败。
- **`merged` 只用类型钉住一半。** `ShardReport` 新增合并字段时，规则不会跟着收；漏收的后果是到处报 `family`，往大声那一侧失败。
- **独立性。** 判定、测试、变异与本条出自同一个工作流，不是独立作者；新测试与实现实际由谁写，在各自的落地记录里如实记（`process/4-VERIFY.md`「标出干净的那些」）。

## 七、欠条

「复核发现一」本身的欠条在 ADR-132 第九节，本条不另登一张同题的（ADR-131「复核发现三」记过同一组欠条重复登记的问题）。下面两张是这条裁决新带出来的。第一张只记扫描看不见的那一半：第五节第 4 步合入之前，以 ADR-132 那张为准；那一步还掉扫得见的一半之后，由第一张接着挂，所以它的重启条件把 ADR-132 那张的「新增组、改 `needs`」也收了进来。

> ⚠️ 欠条：第二节列出的那些通道，扫描看不见；扫描绿只说明扫得见的组间共享都在 `needs` 里。还法是第三节丙的两种之一（完整跑结束时的痕迹核，或把拆进程跑与单进程跑的对照接进检查链）。找候选（只找候选，不是判定）：`git grep -nE "join\(tmp, [^'\"]" -- scripts/check/selfcheck.ts`、`git grep -nE ", tmp[,)]" -- scripts/check/selfcheck.ts` · 重启条件：新增或改动的自检组（含改它的 `needs`）用到第二节任一看不见的通道时；或者拆进程跑与单进程跑的入口认领、✓ 行出现差异时

> ⚠️ 欠条：第五节第 2 步合入后，`share-rule.ts` 是第三份识别 `group(…)` 的语法树扫描，它与 `mutate-rule.ts` 的 `routeLayout` 在 `await group(…)` 上口径不同（前者报扫不了，后者接受） · 重启条件：下一条改动碰 `mutate-rule.ts` 的 `routeLayout`，或 `share-rule.ts` 的组识别时

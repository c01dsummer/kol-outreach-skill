# ADR-65 三条分支合回一条：按「谁的版本更新」取产品代码，按「谁有那台机器」取检查链

- 日期 · 2026-09-02 · 用户：「把三个分支重整为一个新分支，要求最大限度的包含三个分支的所有功能」
- 类型：**产品取舍**（ADR-35 / ADR-54 拆开的东西，这次合回来）
- 冲击的需求：D1 · D4 · D6（文本没变，形状变了：验收标准拆成了判据）
- 结论：**采纳**，新分支 `claude/consolidated-z23u9v`

## 事实

三条分支在 ADR-54 之后各自压成了一个提交，落在当前主干上：

| 分支 | 装的是什么 | 相对主干 |
|---|---|---|
| `requirement-conflict-perspective`（原 PR #5） | 第一、二层：读侧红线、一个写入方被打断 | 1 个提交 |
| `durable-persistence-machinery` | 第三层：改名前的比对、刷盘 —— **叠在上一条之上** | 2 个提交 |
| `requirements-registry-machinery` | 需求登记表的机器：判据、交点、作废、内容指纹、运行时认领、归属校验 | 1 个提交 |

前两条是一条线，第三条是另一条线，而第三条**带着拆分前的旧版产品代码**
（`memory.ts`、`collect.ts`、`render.ts`、`types.ts`、`report.ts`、`pipeline.ts`、
`skill/` 的两份文档）—— 和前两条重叠 92%，但是十六轮评审之前的版本。

## 怎么合的

以并发那条（含前两层）为底，把登记表那条合进来。三方基线是主干，冲突 18 个文件，
按三条规矩解：

1. **产品代码取版本更新的那一边。** 登记表分支上的那些改动是前两层的早期形态，
   每一处都被后来的修复盖过了。`memory.ts`、`collect.ts`、`render.ts`、`types.ts`、
   `report.ts`、`skill/references/*`、以及三条两边都有的决策记录（ADR-18 / 22 / 32，
   前两层那边是就地更正过的版本）—— 全部取并发分支。
2. **检查链取有那台机器的那一边，其余取并集。** `audit.ts`、`spec-sync.ts`、`mutate.ts`、
   `spec-rule.ts`、`claims.ts`、`attribution-rule.ts` 只有登记表分支改过，自动合入；
   `test.ts` 以并发分支为底，搬进登记表分支独有的：三个模块的导入、`criterion` /
   `tension` 两个认领函数（顶掉前两层里只做计数的 `crossing`）、两个 harness 套件、
   六处红线判据的认领、末尾把认领落成 `.check-cache/test-claims.json` 那一块。
   `mutations.json` 按 id 取并集，同 id 的取并发分支的锚点（六条锚点两边不同，
   都是同一处代码的新旧两版）。
3. **`requirements.json` 取登记表的结构、装并发分支的文本。** 判据是登记表分支照着
   十六轮之前的验收标准拆的；D1、D4、D6 此后都改过，D4 从几百字改到 1600 字。
   按 `process/1-REQUIREMENTS.md` 的粒度重拆：D1 两条、D6 四条、D4 十六条。
   拆完逐句核对，并发分支那段文本的每一句都落在某一条判据里。内容指纹由
   `spec-sync --write` 重算。

## 没合进来的

- **`M-P4-j`**（登记表分支）：它守的是「记忆的键里带空白也收下」，锚在
  `if (/\s/.test(raw))` 上。前两层后来把这条判定并进了 `keyProblem` 的 handle 形状
  校验，那一行已经不存在，同一件事由 `M-P4-l` 守着。不再另立一条。
- 登记表分支上那些旧版产品代码 —— 见上，不是功能，是同一功能的旧版本。

## 合完之后仍然成立的

- **第三层还没做完。** ADR-55 记的两条 P1（三步协议第二步没有比对；五个写入方只有
  两个入事务）原样带进来了，D4 的判据也照旧声称「改名前要再确认一次」。
  合并不改变这件事的真假 —— 它只是把三条线放到了同一棵树上。
- 登记表的机器现在守着的是**新文本**拆出来的判据：81 条变成 88 条，红线那 10 条的
  认领一条不少，审计绿。

## 顺带记一件事，不是这次的题目

主干的 `mutate` 有一个偶发：整套跑下来偶尔有**一条**变异被判「跑不起来」，
每次是不同的一条（本轮先后见过 M-H9-c、M-P1-c、M-D8-a、M-H4-d、M-P1-a），
而单独按 `mutate.ts` 一模一样的 `execSync` + `judgeRun` 路径各跑三次全是「被抓到」，
重跑整套也过。出现率约百分之一，与本次改动无关 —— 它会随机把 CI 弄红，值得单独查。

## 教训

**「最大限度包含所有功能」的判据不是「两边的行都留下」，是「每个功能取它最新的那一版」。**
三条分支里同一段代码有两个版本时，留下旧的那一版不是多保留了一个功能，
是把一条已经修掉的缺陷重新装回去。所以合并的第一步是先分清：哪些文件是
**两个功能**，哪些文件是**一个功能的两版**。分清之后，前者取并集，后者取新的，
冲突就只剩机械活。

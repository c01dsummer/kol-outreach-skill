# ADR-31 代码注释也是副本；删字段和改承诺一样要走同步表

- 日期 · 2026-08-28 · PR #5 第十三轮自动评审，两条都成立
- 类型：**事实证伪**（两条都是「改完了没同步到剩下的副本」）
- 冲击的需求：P3（预算承诺）· 登记表的字段描述

### 一、那句承诺的第五份副本，在脚本自己的文件头里

`scripts/collect.ts` 的文件头写着「修好后续跑零花费」。

ADR-23 的追记把同步规则改成了点名的清单，ADR-28 又往清单里补进了
`requirements.json`。但清单列的全是**文档** —— 而**代码注释也是副本**，
并且它离实现最近，最容易被下一个人当成权威。

顺带发现同一个文件里还有一句「中止一个请求都不损失，修好文件 `--resume`
直接走到这一步」：前半句是真的（中止不浪费已花掉的请求），
后半句会被读成「续跑直接就到这一步了」。改成明确区分
「不浪费」和「续跑不花钱」这两件不同的事。

**清单补上：那个脚本自己的文件头与块注释。**

### 二、删掉一个字段，也要走同步表

ADR-30 把 `updated_at` 从 `requirements.json` 里删了，改了 `spec-sync.ts`，
**没改描述这个文件有哪些字段的两处文档**：`AGENTS.md` 和 `docs/SYNC.md`
的文档地图，两处都还写着「`content_hash` 与 `updated_at` 是派生字段」。

按那两份文档做事的人，会去找一个已经不存在的字段。

同步表原先只有「改承诺」这一行。**「增删登记表的字段」是另一类触发，
之前根本不在表上** —— 补了一行：类型与校验、读写、
以及**描述这个文件有哪些字段的文档**。

### 连带改动

`scripts/collect.ts` · `AGENTS.md` · `docs/SYNC.md`（两处：文档地图 + 两行触发规则）

### 教训

**同步表的行，是靠踩出来的。**

这张表现在有三条与「同一件事在多处有副本」相关的行，而它们分别是在
第 23、27、31 条决策记录时补上的 —— 每一条都是因为漏了一处才知道该有那一行。

这不算失败：**一张能自己长出来的表，好过一张一开始就想全的表** ——
后者不存在。但它有个前提，就是每次漏掉都要**回头补表，而不只是补那一处**。
这三次都补了表，所以下一次漏的会是新的地方，不会是同一个地方。

值得单独记的是这一条的形状：**清单只列了文档，而代码注释也是副本。**
写清单时我下意识把「文档」和「代码」当成两类东西，
而对「同一句话有几份副本」这个问题，注释和文档没有区别。

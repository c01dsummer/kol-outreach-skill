# ADR-68 PR #73 / #74 推迟的欠条：起 tsx 的坑有三处，不是两处

> ⚠️ 欠条：`npm run mutate` 起测试子进程那个坑**有三处，不是两处** —— `scripts/check/mutate.ts`
> 已修（PR #73），还剩 `scripts/check/selfcheck.ts` 的 `spawnSync('npx', …)` 与
> `scripts/test.ts` 里那处直接指 `node_modules/.bin/tsx` 的调用。后者在 Windows 上同样起不来：
> libuv 只按**文件名段**找扩展名（`.bin` 里那个点不算），无扩展名就只试 `tsx.com` / `tsx.exe`，
> 而 npm 在 Windows 生成的是 `tsx.cmd` / `tsx.ps1` / `tsx`(sh shim) · 重启条件：PR #74 已合入 ——
> 三处抽一份共用的「怎么起 tsx」一起改（同一份证据，按 `6-INTEGRATE.md` 的切分判据是一个改动）

> ⚠️ 欠条：Windows 上 `scripts/check/mutate-restore.ts` 里 `killTest` 那一刀**落空**，失败还被
> `catch` 吞掉 —— `process.kill(-pid)` 的负号是 POSIX 的进程组语义，配的是入口那边的
> `detached: true`；而 Node 文档写明 `detached` 在 Windows 上给的是**一个自己的控制台窗口，
> 不是进程组**，那个组号没有对应的组可落。**落空的只是「把它停下来」那一半**：`onInterrupt` 是
> 先杀、再还原、才退出，`killTest` 失败也照常返回，源文件是还得回去的；停不下来的是子进程 ——
> 它活着，跑的是被改过的源码，而父进程已经还原完、退出了 · 重启条件：PR #73 已合入 ——
> 要碰 `mutate-restore.ts` 的杀进程策略（Windows 上得换成 `taskkill /T` 之类），是另一份证据

> ⚠️ 欠条：`scripts/check/mutations.json` 里 **M-H14-e 的 `why`** 说反了 —— 它写着变异运行
> 「也会清掉、**写脏**那份覆盖记录，普通运行留下的证据被**顶替**」，而实测只会**被清掉**：
> 该变异自己会被断言抓到、`fail` 不为零，写盘资格那一半仍要求 `fail === 0`。这段 `why` 会被
> `npm run mutate -- --brief` 直接打给**写测试的那个上下文**（`4-VERIFY.md` 的准入读物），
> 误导面比一段注释更宽 · 重启条件：PR #74 已合入

> ⚠️ 欠条：`scripts/check/mutate.ts` 里引 Node 文档那句「`.cmd` 那一节写着**不推荐，见 DEP0190**」
> **没有标版本**。本仓库钉的是 Node **v22**，而那句「not recommended」只在 **v24+** 文档里；
> DEP0190 在 v22 是 **Documentation-only（v22.15.0 起）**，不是运行时弃用（实测 `{ shell: true }`
> 不发任何警告），运行时弃用要到 v24。**结论不受影响** —— DEP0190 正文那句「不转义、只用空格拼、
> 会导致 shell 注入」在 v22 文档里确实在 · 重启条件：下次有改动碰到 `mutate.ts` 那段注释，
> 或本仓库把 Node 升到 v24

> ⚠️ 欠条：**本条取的编号 68 与「号一旦用过就不复用，包括那些活在别的分支上、还没合进来的」
> 相抵触** —— 这句话两处都写着：`docs/adr/README.md` 的前言，和 `process/6-INTEGRATE.md`
> 「决策记录先于实现合」那节（第二处是评审指出的）。另一个会话的 #75 比本条早取了 68，按字面，
> 68 已经算「用过」。本条先让过号（改成 69），随后按作者裁决改回 68；记在这里是因为
> **裁决不改变那句话说的事**：合约的用意（一个号永远只指一条记录）现在要靠 #75 让号才保得住 ·
> 重启条件：#75 改号；若它带着 68 先合进主干，则以主干为准重排本条

### 为什么单开一条记录

按 `6-INTEGRATE.md`「登记怎么做：欠条 PR」，合入后作者开的第一条 PR 就是欠条 PR，
把「不修在本 PR 的发现」里的每一条各写一行。那份索引只是目录，不是登记处 ——
留在 PR 描述里的东西，接手的会话翻不到。

**这一条要装的不止 #74 那三条。** #73 合入之后按这条规矩本该先开欠条 PR，
而当时接着开的是 #74（补一条没赶上合并的更正），于是 #73 索引里的两条从未落到主干上：
一条是 `selfcheck.ts` 起 tsx —— 第一块把它和 #74 查出来的第三处并成了一条；
另一条是 Windows 上那一刀落空 —— 第二块，**是评审在本 PR 上点出来的，我自己没想起来**。

被指出的这些事在主干上都没有现成的记录可以追加，所以按「都没有的，另开一条」新开这一条
只装欠条的记录。最后一块是本 PR 自己长出来的（编号撞车），一并记在这里。

### 共同点值得记一句

**第一、二块是判据落在实例上而不是类上。** #73 修了 `mutate.ts` 一处就收工，而同一个坑当时
已经有第二处（`selfcheck.ts`），第三处（`test.ts`）是后来查 Node 在 Windows 上怎么找可执行
文件时才发现的；同一份 Windows 证据里「杀不掉」那半条，也是写进 #73 的描述之后就停在那儿。
ADR-45 正文骂过同一件事（「一次只修一处就是又一次『只修实例』」），
`4-VERIFY.md` 把它一般化成「判据要落在那个类上」——**而我在读着 ADR-45 干活的时候又踩了一次**。

**第三、四块都是把没核过的说法写进记录。** 一条是变异集的 `why`（主干上早就写着，这次才被实测
推翻），一条是我自己引 Node 文档时没核版本。`docs/CONVENTIONS.md` 第 11 条说的「描述保证的
那句话，没有任何检查看着」，这两条各是一个新实例。

**第五块不同类：它是流程本身没有闸门。** 编号唯一性没有任何前置检查，撞车要等合进主干之后
`npm run adr` 才红。**这道缺口和 ADR-34 那条欠条不是同一个形状**（评审指出，我原先写成同一个）：
ADR-34 缺的是「所有消费者之前的一个统一阶段」，那道闸站在同一棵树里就建得起来；而这里
`adr-sync` 看得见的只有当前这棵树加主干（`readdirSync` 加 `git show <base>:<路径>`），
别的分支上占着的号它**看不见** —— 同一棵树里加多少道闸都挡不住，要挡住得有跨分支的占号或协调。

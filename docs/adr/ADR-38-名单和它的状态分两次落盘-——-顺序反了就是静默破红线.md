# ADR-38 名单和它的状态分两次落盘 —— 顺序反了就是静默破红线

- 日期 · 2026-08-28 · PR #5 拆分后第三轮自动评审。**两条里只采纳一条**
- 类型：**事实证伪**（一条成立，一条前提不成立）
- 冲击的需求：P4 · P5 · D4
- 结论：**采纳一条**（落盘顺序），**驳回一条**（写回时机），理由见下

### 采纳：状态要先于名单落盘

`collect.ts` 末尾原先是 `saveCreators` 再 `saveTask`。两次独立的
`writeFileSync`，中间被打断是可能的，而两种顺序的失败后果**不对称**：

| 顺序 | 被打断之后 | 后果 |
|---|---|---|
| 名单在前（原先） | `creators.json` 已是未去重的新名单，`task.json` 还留着上一轮的 `ok` | render 从 `task.json` 读状态，**压掉警告**，把打扰过、已拉黑的人当成已去重交付 —— 静默破 P4 与 P5 |
| 状态在前（现在） | `task.json` 说「没去重」，`creators.json` 还是上一轮去重过的旧名单 | 报告多报一次警告，用户重跑一次 |

多报要用户重跑一次，少报是把人重新打扰一遍。**答不上来时报警告，不报「已去重」。**

值得记的是：**同一个文件里正确的顺序早就有** —— `persist()` 一直是
`saveTask` 在前。是末尾这段偏离了它。加功能时我照着「先写主产物、再写元数据」
的直觉写，而没有回头看这个文件自己是怎么做的。

守它的东西：**没有。** 这是入口脚本里两次落盘的先后，而变异只跑
`scripts/test.ts`，入口接线没有变异守得住 —— 与已登记的另一处入口接线同样处境。
按先例**显式登记成缺口**，不在单元测试里伪造一个认领。

### 驳回：写回记忆的时机

另一条说：`recordRecommendations` 跑在 `meta.json` / `report.html` 之前，
若后两者写失败（磁盘满），人已被记成「推荐过」，而**用户从没拿到一份完整交付**，
下一个任务却会把这些人滤掉。

**前提不成立。** `render.ts` 的落盘顺序是：

```
saveCreators(40) → CSV(44) → xlsx(50) → recordRecommendations(80) → meta(137) → report(138)
```

CSV 与 xlsx 在写回**之前**就已落盘，中间没有任何 `process.exit`、`throw` 或
`return`。也就是说走到写回时，名单**已经在用户手上**了 —— 缺的是
`meta.json` 与 `report.html`。那条记忆记的「这些人为这个产品推荐过」是**真的**。

而且写回按任务编号分段（`filter(r => !(task && r.task === task))`），
同一个任务重跑 render 会替换掉自己那一段，是幂等的。

反过来说，把写回推迟到交付物全部落盘之后，会让 `meta.json` 没法报告写回的
**真实**结果 —— 只能报一个预测。那正是 D4.j 要求的反面（「交付物必须带出失败
原因原文」），也正是 ADR-22 记过的那条：**不许替下一步打包票。**

### 教训

**「两件事要一起落盘」做不到的时候，问的不是怎么做到，是哪个先。**

原子性拿不到时还有一件事可做：**让打断之后剩下的那个状态是安全的那一个。**
顺序不是实现细节，它就是这条约束本身。

> **上面这一节只对了一半，见 ADR-41。** 我只分析了 `ok` → `unreadable_ignored`
> 这个方向，就断言「状态先写是安全的那一个」。反方向
> （`unreadable_ignored` → `ok`）恰恰相反，而**哪个顺序都不安全**。
> 「让剩下的状态是安全的那一个」这句话是对的，「所以状态先写」是错的。

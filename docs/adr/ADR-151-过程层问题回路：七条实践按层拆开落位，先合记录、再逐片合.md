## 三、落位时改了形的地方

提案原文与仓库现行规矩对不上的，按下面改；需求所有者一并选了「按推荐」。

1. **被引表挂在只读入口上，不挂 `npm run audit`。** `scripts/check/audit.ts` 在处理任何参数之前先读两份覆盖记录（第 121、140 行，`693eb5e`），读不到就以 1 退出；照原文挂在 `audit` 上，`docs/adr/README.md` 里那句「新开记录前跑 `--cites`」在没跑过需求测试与自检的检出里照做不了。所以 P5 的前置入口挪到最前，`--cites` 只挂在它上面；`npm run audit` 默认输出末尾那一行分布照原文保留，由同一个判定模块算。
2. **P6 的规则正文写进 `docs/adr/README.md`，不写进 `REVIEW.md`。** `REVIEW.md` 卷首是「只做转发，不装规则」；原文让它「加一句路由：评审器首轮列 ≤ 3 条……」，那是一条规则。`REVIEW.md` 只在表里加一行指过去，三个评审器的转发都不用动。
3. **P1 的取数逻辑内联在 `check.yml` 里**，照原文零新文件。这一步本跑那一侧只算得到这一步为止，比提案 §2.3 的口径（`run_started_at → updated_at`）少末尾的 `lscpu`；这个差写在那条 PR 里。
4. **P3 的第一条死亡条件改写**，随 ADR-145 那一节由需求所有者批：原文「任一 CI 报出『启动数不确定』」是数 CI 运行，ADR-85 说这个仓库不留逐次运行的结果、这一族条件核不了；改成「ADR-145 末尾追加过一块，记下某一跑报出『启动数不确定』」。
5. **作者 ≠ 合并者。** 除回访 PR 外，每片由执行者开草稿 PR、需求所有者合；回访 PR 前四周以需求所有者账号提交，只追加台账一个文件，按 `process/6-INTEGRATE.md`「什么不走这套」直接合（与欠条 PR 同一条路），P7 上线前再看。

## 四、各条的边界与死亡条件

1. **P1、P2、P6、P7 不是闸门，按 ADR-85 不设死亡条件**：它们永不判红、没有豁免通道，只报数或只递原料。
   P1 的撤除钉一个仓库内事实：`process/6-INTEGRATE.md`「改验证成本时」那节的「前后实跑」义务被删时，同一条改动删掉 `check.yml` 那一步。
2. 例程永不改 `process/`、`scripts/`、`docs/requirements.json`、`.github/workflows/check.yml`；不给记录写「采纳」、不标欠条已还、不判死亡条件（ADR-80、ADR-86）。
3. 没有任何一条按秒数判红，与 ADR-97 第四节、ADR-145 第二节不冲突。
4. P4 / P5 共用两条：

> **什么条件下整个撤掉**：非浅克隆下 `git log --since=8.weeks -- 'docs/adr/ADR-*-回访台账*.md'` 为空 —— 例程停了。

> **什么条件下停候选表、只留心跳行**：八周内台账里没有一块写着「上周结果：已合入」。

5. P3 的两条随 ADR-145 那一节批，不在这里重复。
6. 这套东西本身不看缺口数降没降（提案 §7：缺口变多是可见性提高），看三个一条 grep 得到的数：台账里 `已合入` 的块数；`^- 同类：` 头部行的累计数与其中 N ≥ 3 变成欠条的条数；「process/ 里没有这句」类欠条的已还条数。

> **什么条件下整个撤掉**：上面三个数八周都不动。

## 五、提案 §3 那十句通用句

提案 §3 从 self-evolution 分支（tip `37e3c8d`）挑出的十句，改 `process/`、一律人批，不在本条第二节那条线上：另开一条记录写明每句的来源、起因与欠条，先合；之后一句一条只改 `process/` 的 PR，引那条记录的句号。同一次裁决里需求所有者对这十句选了：

- 十句共用一条记录、逐句一张欠条，不是一句一条记录

- 「每一步 48 小时内能合入」不把数写进 `process/`，只写「很快能合；迟迟合不进，多半是装着第二个证据问题」

# ADR-71 score 不在敏感字段表上，红线那条「任何位置」没落地

- 2026-09-09 · PR #91 合入后清点欠条时发现（逐条核对评审回复里说过的话有没有真落成记录）
- 类型:接受为已知缺口
- 冲击的需求:**P1.b（红线）**;改法会牵到 U1 / U5 的展示与排序
- 结论:**接受为已知缺口,本条不修** —— 补一个字段名是一行,补完之后那两处当场判红,
  而「拿不到分该怎么办」是产品语义决定,不该由作者顺手定

## 触发它的事实

P1.b 逐字是:

> 任何位置不得出现 `?? 0` / `|| ''` 形式的数据兜底;纪律 lint 对 scripts/ 全量扫描,命中即失败。

而实测(`npx tsx -e` 直接喂真判定,不是推断):

```
"  const s = c.score ?? 0"                   -> clean
"  const s = c.followers ?? 0"               -> violation
"  return (b.score ?? 0) - (a.score ?? 0)"   -> clean
```

原因在 `scripts/check/lint-rule.ts` 的 `judgeLine`:先用 `FALLBACK` 认出 `?? 0` 的形状,
**再要求这一行里出现 `SENSITIVE` 表上的某个字段名**。表上有 `followers`、`plays`、
`fake_follower_score`……**没有 `score`**。于是这两处既不报违规,也不需要 `// p1-ok:` 具名豁免 ——
红线说的是「任何位置」,闸门查的是「表上那些名字出现的位置」,两者今天对不上。

活着的两处:

| 位置 | 写法 | 拿不到分时会怎样 |
|---|---|---|
| `scripts/lib/score.ts:35`（`tierOf` 里） | `const s = c.score ?? 0` | 当 0 分算,分层直接落到 C 档 —— 而「没打过分」和「打了 0 分」是两回事 |
| `scripts/lib/rows.ts:109` | `(b.score ?? 0) - (a.score ?? 0)` | 没分的排在最后,与「0 分」并列,交付表上看不出区别 |

两处都没有变异守着(`score.ts` / `rows.ts` 名下现有七条变异,`M-F6-a` 只盖 `tierOf` 的
`fit === '❌'` 那一行)。

**最刺眼的是那张表自己的注释**:「这些字段的值会进入过滤、评分、分层 —— 兜底就是静默改变决策」。
而 `score` 正是 `tierOf` 做**分层**时读的那个值。按表自己写的准入标准,它本来就该在表上。

## 理由:为什么不在这一条里修

`SENSITIVE` 加一个 `'score'` 是一行。加完之后 `npm run lint` 当场把上面两处判红,
于是必须当场回答「拿不到分该给什么」——

- `tierOf`:今天默默当 0 分。要改成显式的第三态(有分 / 无分 / 不适用),得动 `Creator`
  的字段语义,而 `tier` 是交付物上的一列;
- `rows.ts`:排序要有一个「没分」的位置,那是 U1 / U5 的展示决定。

**这不是顺手能带的,也不该由作者一个人定。** 按 `2-CHANGE.md`,不改设计、登记在案、
写明重启条件。

## 重启条件

下一条要动 `lint-rule.ts` 的 `SENSITIVE` 表、或要动 `tierOf` / `rows.ts` 排序的改动;
或定期清点时一并处理。改法已想清:表里加 `'score'` → 两处判红 → 先定「没分」这一态怎么表达,再连同变异一起补。

**那条新断言要有自己的负片:一条把 `'score'` 从表里删掉的变异。**
现有三条都盖不住它 —— `M-P1-i` 删的是 `'plays'`、`M-P1-j` 动的是 `FALLBACK` 那条正则、
`M-P1-k` 动的是 `p1-ok` 那一支;`'score'` 从表上消失,三条一条都不会红。
按 `4-VERIFY.md`,每条断言都要有一条变异证明它会红。
(这一句头一版写成「表本身有 `M-P1-i`／`j`／`k` 守着,新增字段名不需要新负片」,
**与下一节自己写的话直接打架** —— 那节逐字说着「它们守的是『表上的名字会不会被判出来』,
不是『该在表上的名字在不在表上』」。#92 评审指出,已改准。)

## 教训:同一形状的第二次

`docs/CONVENTIONS.md` 第 10 条记着「第五次」——**同一张表漏了 `plays`,漏了多久没人知道**,
后来抽出 `lint-rule.ts` 才拿到测试与 `M-P1-i`／`j`／`k`。那一次补的是**测试**,
补不了的是**表本身的完整性**:表是人手维护的,漏一个名字是静默的,
而 `M-P1-i`／`j`／`k` 守的是「表上的名字会不会被判出来」,不是「该在表上的名字在不在表上」。

这是同一形状的第二次。**第三次发生时,该问的不是「再补一个名字」,而是这张表能不能从别处派生** ——
比如从 `Creator` 里参与过滤／评分／分层的字段生成,让漏项在编译期或检查期显形。
今天没有这样的来源,所以先记在这儿。

> 顺带:这一条是被**清点**发现的,不是被使用发现的。它从初次提交(`aa40ee0`)起就在,
> 中间没有任何一次改动碰过它 —— 一条 P0 红线在两处静默失效,靠的是有人回头逐条对账才浮出来。

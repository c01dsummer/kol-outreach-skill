# ADR-71 score 不在敏感字段表上，红线那条「任何位置」没落地

- 2026-09-09 · PR #91 合入后清点欠条时发现（逐条核对评审回复里说过的话有没有真落成记录）
- 类型:既有缺陷 —— **让检查说了假话**
- 冲击的需求:**P1.b（红线）**
- 结论:**立刻修**,走 `6-INTEGRATE.md` 的「主干红了」:从主干开一条 PR 就地修、立刻合,
  #92 等它合了再把主干合进来。**实现与本记录在同一条 PR（#93）里** ——
  记录跟着实现走,否则主干上会先出现一句指向不存在的记录的注释（#93 评审指出）
- ⚠️ 本记录第一版把结论写成「接受为已知缺口,本条不修」,理由是「拿不到分该怎么办是
  产品语义决定」。**两处都错**,#92 第三轮评审指出,见下面「第一版错在哪」

## 触发它的事实

P1.b 逐字是:

> 任何位置不得出现 `?? 0` / `|| ''` 形式的数据兜底;纪律 lint 对 scripts/ 全量扫描,命中即失败。

而实测(`npx tsx -e` 直接喂真判定,不是推断):

```
"  const s = c.score ?? 0"                   -> clean
"  const s = c.followers ?? 0"               -> violation
"  return (b.score ?? 0) - (a.score ?? 0)"   -> clean
```

原因在 `scripts/check/lint-rule.ts` 的 `judgeLine`:先用 `FALLBACK` 认出 `?? 0` 的形状,
**再要求这一行里出现 `SENSITIVE` 表上的某个字段名**。表上有 `followers`、`plays`、
`fake_follower_score`……**没有 `score`**。于是这两处既不报违规,也不需要 `// p1-ok:` 具名豁免 ——
红线说的是「任何位置」,闸门查的是「表上那些名字出现的位置」,两者今天对不上。

活着的两处:

| 位置 | 写法 | 拿不到分时会怎样 |
|---|---|---|
| `scripts/lib/score.ts:35`（`tierOf` 里） | `const s = c.score ?? 0` | 当 0 分算,分层直接落到 C 档 —— 而「没打过分」和「打了 0 分」是两回事 |
| `scripts/lib/rows.ts:109` | `(b.score ?? 0) - (a.score ?? 0)` | 没分的排在最后,与「0 分」并列,交付表上看不出区别 |

两处都没有变异守着(`score.ts` / `rows.ts` 名下现有七条变异,`M-F6-a` 只盖 `tierOf` 的
`fit === '❌'` 那一行)。

**最刺眼的是那张表自己的注释**:「这些字段的值会进入过滤、评分、分层 —— 兜底就是静默改变决策」。
而 `score` 正是 `tierOf` 做**分层**时读的那个值。按表自己写的准入标准,它本来就该在表上。

## 修起来比第一版以为的小得多

`SENSITIVE` 加一个 `'score'` 是一行。加完之后 `npm run lint` 当场把上面两处判红,
而 `tierOf` 那一处**在生产路径上根本走不到**:

```
scripts/lib/score.ts:11       export function scoreCreator(c: Creator): number   ← 必返回数字
scripts/lib/pipeline.ts:172      c.score = scoreCreator(c)
scripts/lib/pipeline.ts:173      c.tier  = tierOf(c)     ← tierOf 唯一的生产调用点
```

全仓 `tierOf` 只有这一个生产调用点(另有 3 处在 `scripts/test.ts`),而 `c.score`
就在**它上一行**被赋成了一个 `number`。所以那条兜底是一处**纯粹的防御性默认值** ——
`docs/CONVENTIONS.md` 第 1 条那一类,删掉它在生产行为上是 no-op。

`rows.ts` 那一处同理:`sortForOutput` 的两个调用点拿到的都是排过序的 `kept`。
它上面那段注释已经为 `tier` 缺失写了显式的「排末位」,`score` 照同一形状写即可 ——
**「没分」和「0 分」要分得开**,这不是展示决定,是同一条 P1。

## 第一版错在哪

结论与理由是分开的两个错,而理由那个更要紧:

**「拿不到分该怎么办是产品语义决定」这个前提,我没查调用图就写下了。** 查完发现
那一态不会发生,于是没有决定要做,只剩一处该删的防御性默认值。这跟 #92 里已经
改过两次的错是同一形状 —— **拿印象当查证**,而它这次把一条该立刻修的既有缺陷
挡在了「登记」档后面。

结论那个错跟着它:`6-INTEGRATE.md` 的「既有缺陷」一档写明,**会让检查说假话的走
「主干红了」**,不是登记。`npm run lint` 今天报绿而 P1.b 写着「任何位置」,
正是「检查说假话」。

## 改法

表里加 `'score'` → 两处判红 → 就地删掉那两处兜底 → 配断言与负片。

**那条新断言要有自己的负片:一条把 `'score'` 从表里删掉的变异。**
现有三条都盖不住它 —— `M-P1-i` 删的是 `'plays'`、`M-P1-j` 动的是 `FALLBACK` 那条正则、
`M-P1-k` 动的是 `p1-ok` 那一支;`'score'` 从表上消失,三条一条都不会红。
按 `4-VERIFY.md`,每条断言都要有一条变异证明它会红。
(这一句头一版写成「表本身有 `M-P1-i`／`j`／`k` 守着,新增字段名不需要新负片」,
**与下一节自己写的话直接打架** —— 那节逐字说着「它们守的是『表上的名字会不会被判出来』,
不是『该在表上的名字在不在表上』」。#92 评审指出,已改准。)

## 教训:同一形状的第二次

`docs/CONVENTIONS.md` 第 10 条记着「第五次」——**同一张表漏了 `plays`,漏了多久没人知道**,
后来抽出 `lint-rule.ts` 才拿到测试与 `M-P1-i`／`j`／`k`。那一次补的是**测试**,
补不了的是**表本身的完整性**:表是人手维护的,漏一个名字是静默的,
而 `M-P1-i`／`j`／`k` 守的是「表上的名字会不会被判出来」,不是「该在表上的名字在不在表上」。

这是同一形状的第二次。**第三次发生时,该问的不是「再补一个名字」,而是这张表能不能从别处派生** ——
比如从 `Creator` 里参与过滤／评分／分层的字段生成,让漏项在编译期或检查期显形。
今天没有这样的来源,所以先记在这儿。

> 顺带:这一条是被**清点**发现的,不是被使用发现的。它从初次提交(`aa40ee0`)起就在,
> 中间没有任何一次改动碰过它 —— 一条 P0 红线在两处静默失效,靠的是有人回头逐条对账才浮出来。

## 这次修撞出来的两处「需求沉默」

都不是本记录的主题,但它们是被这一条修**逼出来**的 —— 删掉兜底之后，
必须回答「那该怎么办」，而需求两处都没说。

### 一、没算过分的人排在哪:`U1.b` 沉默

`U1.b` 逐字是「行序满足 A→B→C 且同层分数递减」,对「没有分数的记录排哪儿」一个字没有。

**「不表态」这条路走不通**:比较器必须是全序。让缺分的一律返回 0(表示无意见)会做出一个
**非传递**的比较器 —— 没分的 ≡ 50 分的、没分的 ≡ 10 分的,而 50 > 10,排序结果由实现定,
正是那段注释自己警告过的坑。所以实现被迫选一个。

本条选的是**排本层末位**,理由是同一个函数里 `tier` 缺失早就这么处理(「未分层的排末位」),
跟着既有先例走,不另立一套。

按 `2-CHANGE.md` 的分类,这是「需求有歧义 → 补充,不走评定」还是「产品取舍 → 要人拍板」?
**我判前者**,依据是那一档的判据写着「选哪种**决定用户看到什么**」——
而今天 `sortForOutput` 的两个调用点拿到的都是 `rankCreators` 排过的 `kept`,
每个人都刚被赋过分,**这一态在生产路径上不可达**,用户看不到任何区别。
⚠️ 但这条判断是作者做的,需求所有者可以推翻 · 重启条件:需求所有者确认(写进 `U1` 的判据),
或 `sortForOutput` 开始接到没打过分的人 —— 那一刻它就真的决定用户看到什么了

### 二、分层阈值本身没有需求条目

`tierOf` 的 60 / 40 两条阈值,全仓找不到一条需求管它:`F6` 只说「语义判断为否定时……不得因
分数高而进入 A 级」,`U1` 只管排序。于是本条新加的 `M-F5-b`(分层用的不是刚算出来的那个分)
只能挂在 `F5` 名下 —— 沿用 `M-F5-a` 的既有用法,而 `F5` 的正文讲的是「增强层缺失时优雅降级」。
**编号和它守的东西对不上**,与 #91 里 `M-D6-f`／`g`／`h` 那笔账是同一种。
⚠️ 重启条件:下一条要动分层阈值、或要动 `F5`／`F6` 需求文本的改动

> 顺带记一笔:这一支原先**一条断言都没有** —— 把 `tierOf` 的分数分层整支改成永远返回 `C`,
> 整个测试套照样全绿(#93 评审指出)。本条补了三个跨阈值的语料(实测 30 / 45 / 60)。

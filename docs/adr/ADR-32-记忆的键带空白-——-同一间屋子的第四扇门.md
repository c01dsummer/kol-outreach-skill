# ADR-32 记忆的键带空白 —— 同一间屋子的第四扇门

- 日期 · 2026-08-28 · PR #5 第十四轮自动评审，成立
- 类型：**事实证伪**（P1，静默破红线）
- 冲击的需求：P4（不重复打扰）· D1（身份规范化）
- 结论：**采纳**，带空白的键判为读不出来

### 事实

`tiktok:alice ` 这个键，现有的每一关都过得去：分隔符恰好一个、两边非空、
平台也在支持范围内。而查询侧生成的是 `tiktok:alice` —— 永远差那一个空格。

跑出来的结果：一个 contacted **且** blocked 的人重新进名单，
状态报「读到了」，过滤条数报 0 —— 与「确实没人联系过」完全同值。
**用户看不出任何异常。**

### 这是第四扇门

同一间屋子已经修过三次：

| | 门 | 记在 |
|---|---|---|
| 一 | 键的大小写没规范化（`tiktok:Alice`） | ADR-22 |
| 二 | 只要求「有个冒号」，平台拼错、多一个分隔符都收 | ADR-25 |
| 三 | 权限错误被 `existsSync` 压成「文件不存在」 | ADR-26 |
| 四 | 键里带空白 | 本条 |

四次都是同一个形状：**存储侧接受了一个查询侧永远生成不出来的键**，
而它静默地等价于「这个人没被联系过」。

### 这条规则是个判断，不是推导

前三扇门的判据都能从代码里推出来（查询侧就是那么生成的）。这一条不行 ——
「用户名不允许空白」是关于 `PLATFORMS` 里那两家平台的**外部事实**，
代码里推不出来。所以它绑在那个枚举上：**平台集合变了，这条得跟着重看。**

判断有可能错，所以选了错得起的那一边：误判会大声中止（还有
`--ignore-memory` 兜底），漏判是静默地破红线。红线不参与取舍。

### 教训

**「我已经修过这里了」不是「这里修好了」。**

三扇门都关上之后，我把「键的形状」当成了一件做完的事。而实际做完的是
三个**具体的**形状问题 —— 那不等于回答了「查询侧生成不出来的键还有哪些」。

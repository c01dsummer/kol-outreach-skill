# ADR-92 未查询的粉丝数排在已查到的前面：只改先后，不加分

## 裁决

需求所有者 2026-09-19：**粉丝数未查询的人，排在粉丝数确实是 0 的人前面。**

落成判据 `P1.h`：同一层、同一分数时，粉丝数未查询的排在已查到的前面。
**只改先后，不改分数也不改分层。**

## 一、这句话有两种落地，选了哪一种

| | 做法 | 后果 |
|---|---|---|
| 加分 | 给「未查询」一个分值 | 他整体上移，**可能跨档** —— C 变 B |
| **排序** | 分数不动，打平时让他站前面 | 同档同分内部换位，**档位不动** |

**选了排序。** 给分等于替他编一个他可能并没有的实力：那个分值从哪来？
没有依据，只能拍一个，而拍出来的数会把人推进他不该进的档。
「不知道」的正确待遇不是「当他强」，是**「让人先看见他」** —— 排序正好只做这件事。

顺带：这也保住了 `scoreCreator` 的一条既有性质 —— 未查询的维度**不折算成任何具体值**。
加分会当场破掉它。

## 二、规则写成「未查询 vs 已查到」，不是「未查询 vs 恰好是 0」

裁决的原话是拿 0 说的，但落到比较器上，只跟 0 比是个很怪的特例。
写成「已查到」更一般，而且理由更硬：

> **已查到的那位是量过了、仍然没拿到粉丝分 —— 我们确定他不够。
> 未查询的那位可能够。**

这条更一般的规则有一个副作用，写在这里：同层同分、一个未查询一个已查到 5 万，
未查询的也会排前面。发生条件很窄（已知 5 万本来就多拿分，要打平得靠别的项凑齐），
而且结果说得通 —— 他没拿粉丝分还能打平，底子不差。
**需求所有者知情并接受这个推广。**

## 三、测试为什么要正序逆序各排一次

打平时排序是稳定的：比较器返回 0，结果就跟着输入顺序走。
**只写一个方向的断言，一半的错误实现照样绿** —— 包括「这一条根本没生效」。
所以同一对输入正序逆序各排一次，两次都要求同一个结论。

这个手法不是本条发明的：ADR-88 里那个隔离上下文独立用了同一招，
理由一字不差。

第三条断言管另一个方向：**这一条只在打平时说话**，不许越过分数插队 ——
越得过去就等于偷偷加了分，而那正是第一节判掉的做法。

## 四、动了哪几处

| | |
|---|---|
| `scripts/lib/rows.ts` | 排序比较器加第三级。全仓只有这一处排序，名单与分 sheet 都走它 |
| `docs/requirements.json` ＋ `docs/SPEC.md` | 新判据 `P1.h`（`SPEC.md` 由 `spec-sync` 回写） |
| `skill/references/output-format.md` | 那句「先按 tier，同层按 score 降序」**会变得不完整** —— 读者据此预测不了打平时谁在前。补上第三级 |
| `scripts/test.ts` | 三条断言，认领 `P1.h` |
| `scripts/check/mutations.json` | 负片 `M-P1-m`：把第三级去掉 |

**`U1` 没动。** 它的判据说「行序满足 A→B→C 且同层分数递减」——
加一条打平时的次序，这句话仍然成立，不是改它的含义。

## 五、ADR-88 那张「评分侧与采集解析侧没有判据」的欠条

重启条件是「下一条要动 `docs/requirements.json` 里 P1 的改动」，本条踩到了。
**只还了一部分，把账说清楚：**

- **排序侧**：本条新增 `P1.h`，有认领、有负片。
- **评分侧**：仍然没有自己的判据编号。但**行为本身有变异守着** ——
  `M-P1-b` 指的就是评分里那行「粉丝数未查询时不给分、也不当作 0」，
  它记在 `P1` 名下而不是某条判据名下。隔离上下文要的是给它一个编号，本条没给：
  裁决把出口改在了排序侧，评分侧一个字没动。
- **采集解析侧**：ADR-90 补了测试，**不是判据**。

⚠️ 欠条：**评分侧「未查询不折算成具体值」只有变异守着，没有自己的判据编号。**
重启条件：下一条要动 `scripts/lib/score.ts` 里那几条「未查询不给分」的改动，
或者下一次有人要给这条性质做拆分计量时。

## 六、没做的

- **没有回头看别的排序键有没有同一个毛病。** 本条只处理了粉丝数这一个字段。
  作品数、播放数同样是三态，它们在排序上有没有被压平，本条没查。
  ⚠️ 欠条：**只审了粉丝数这一个排序字段。**
  重启条件：下一条要动排序比较器的改动。
- **没有给这条规则做端到端验证。** 它在单元层有三条断言和一条负片，
  但「产出的 CSV／xlsx 里真的是这个顺序」没有在自检里跑过一遍。
  ⚠️ 欠条：**排序的新规则没有端到端跑过。**
  重启条件：下一条要动交付物产出那一段的改动。

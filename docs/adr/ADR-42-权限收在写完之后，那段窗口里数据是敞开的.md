# ADR-42 权限收在写完之后，那段窗口里数据是敞开的

- 日期 · 2026-08-28 · PR #5 拆分后第七轮自动评审，成立
- 类型：**事实证伪**，证伪的又是**我上一轮刚给出的修法**
- 冲击的需求：D4
- 结论：**采纳**，临时文件建的时候就给最严的权限

### 事实

ADR-40 的修法是「写完临时文件，chmod 成目标的权限，再改名」。
顺序错了：`writeFileSync` 按 umask 建文件（通常 0644），**完整的联系历史
在那一刻就已经躺在一个别人读得到的文件里了**，chmod 是事后才收的。

而且硬杀正好落在这两步之间时，那份 0644 的副本会留在盘上，
直到下次写回时被清掉。

### 修法

临时文件**建的时候**就给 0600 —— 它没有任何人需要读，比目标只严不松。
建完再 chmod 到目标该有的权限。

两步都要：建文件时的 `mode` 会被 umask 削（目标本来是 0666、umask 是 022 的话，
只靠建文件那一步会把它悄悄收严），chmod 不会。

### 一个变异当场活了

改完跑检查，**M-D4-m 存活**了。它删掉的是 chmod 那一步，而我的用例
恰好把目标也设成 0600 —— 临时文件既然按 0600 建，删不删 chmod 结果一样，
**那条测试证明不了任何事**。

把用例改成 0640（一个不等于临时文件那一档的权限），变异当场被抓到。

这正是变异测试存在的理由：它不是在测代码，是在测**测试**。
「建得严」和「事后调回目标」是两件事，而我原来的断言把它们压成了一件。

### 教训

**修一个安全问题时，问题本身会挪位置。**

ADR-40 问的是「最后落到目标上的权限对不对」，答对了。
这一轮问的是「中途有没有一瞬间是敞开的」—— 同一份数据、同一段代码，
换一个时刻去看就是另一个答案。

**「结果正确」不等于「过程中每一刻都正确」**，而涉及敏感数据时，
后者才是要问的那个。

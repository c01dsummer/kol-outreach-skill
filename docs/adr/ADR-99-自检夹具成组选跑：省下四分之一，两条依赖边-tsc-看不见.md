# ADR-99 自检夹具成组选跑：省下四分之一，两条依赖边 tsc 看不见

- 日期 · 2026-09-21 · ADR-97 第六节记的那条主修。起因是用户问「`npm run check` 时长
  又劣化了…这次的『劣化』是不是应该的」，那一轮的结论是「工作量该付、乘数不该付」
- 类型：**既有缺陷**（检查链自身的成本结构）。不触及需求登记表 —— 检查链的成本不是编号需求
- 触发它的事实：见第一节（交替配对实测，命令在那一节）
- 冲击的需求：无。冲击的是**检查链自己跑得起跑不起**
- 结论：**① 24 组夹具「先登记、后按依赖闭包派跑」，`--only` 选跑；② 依赖图里有两条边
  `tsc` 看不见，只有真跑子集才发现得了；③ 子集跑要收三处口，否则 `survived` 这一态
  对每一条负片都不可达；④ ADR-97 第六节那个估算错了单位也错了量级，本条一并订正；
  ⑤ **这条链省下的是 CPU，不是墙钟** —— 本条头一版报的「墙钟省 28%」是假的精度，
  第一节连同「钉了树为什么还不够」一起记下来**
- 理由：一条负片要证的只有「它点名的那 1–3 条夹具会红」，而今天它要付整段前缀

## 一、省下多少 —— 以及「省下多少秒」这个问法本身是错的

头一版这一节写的是「本机 603 s → 432 s，省 171 s（−28%）」，每个数都照
`REVIEW.md` 钉了一棵不会再动的树，还注明了同机、串行、空载，并且找了 CI 作第二组
对照。**那一版是错的，而且错得值得单独记下来：它形式上完全合规。**

独立复核问的是「换 revision 要不要用干净工作树」。顺着查下去撞见的不是它说的那件事，
是另一件更大的：**墙钟不是树的函数。** 同一棵 `7c4fd39`、同一台机器、同样 389 条变异，
`time npm run check` 先后跑出 **603 s、663 s、706 s、788 s**。树决定要干多少活，
不决定这台机器什么时候肯干。

### 真正测出来的

交替跑 —— 本条 → 主干 → 本条 → 主干，同机串行、背靠背，让机器漂移落进配对里：

| 树 | 变异数 | 墙钟 | **CPU（user + sys）** |
|---|---|---|---|
| `7c4fd39`（主干） | 389 | 706.0 s · 663.3 s | **1538.9 s · 1651.2 s** |
| `2be5e1d`（本条） | 395 | 680.6 s · 476.6 s | **1202.0 s · 1259.2 s** |

**墙钟没有结论。** 两对配对分别是 −25 s（−3.6%）与 −187 s（−28.1%）；本条自己两跑
就差 204 秒。一个数落在 −4% 到 −28% 之间，它不是测量结果。

**CPU 有结论。** 两组**完全不重叠** —— 本条最差的一跑（1259.2 s）仍比主干最好的一跑
（1538.9 s）少 **280 秒**。均值 1595.0 s → 1230.6 s，**省 364 s，−22.9%**，
而且跑的变异还多了 6 条。

一条旁证把解释钉死：`2be5e1d` 第一跑是四跑里 CPU 最省的（1202.0 s），墙钟却是第二慢
的（680.6 s）。**它干的活最少，等核等得最久。**

订正提交之后本条又跑了一次（`a28484e`，与 `2be5e1d` 只差几份 `.md`）：CPU **1288.4 s**，
墙钟 488.4 s。本条三跑落在 1202.0–1288.4（跨 86 s），整段在主干两跑之下 —— 最差的本条
仍比最好的主干少 250 秒。这一跑不在配对实验里，只作旁证。

第二轮复核的修补落地之后，在 `6607ecb` 上又跑了一次：**CPU 1372.3 s**、墙钟 481.4 s。

**这是单样本，按本节自己的规矩它不构成区间** —— 一次量不出速率。但它能证一件**不需要
区间**的事：那一版多跑 **397** 条变异（多了 `M-H43-c`／`M-H43-d`）、多一批断言，而 CPU
仍比主干两跑里最省的那一跑（1538.9 s）少 167 秒。**多干了活还更便宜** —— 这是个不等式，
一个样本就够；「省了百分之多少」是个速率，一个样本不够。两者别混着用。

### 为什么该看 CPU

这台箱子名义 4 核，而四跑的 `(user+sys)/real` 落在 **1.8–2.6**：派出去 4 个 worker，
实际拿到不足 3 个核。`--only` 砍掉的是**工作量**；工作量要乘以「你能拿到几个核」才变成
墙钟，而那个系数不归这条改动管，也不归这棵树管。**这条改动只买得到 CPU 那一项。**

CI 上同样抖，所以头一版那句「CI 那一组是最硬的证据，因为它不是我跑的」也不成立：

| CI 上 `check` 那一步 | 树 | |
|---|---|---|
| 615 s | `7c4fd39` | 主干 |
| 479 s | `25813f4` | 本条 |
| 340 s | `2be5e1d` | 本条 —— **与上一行只差几份 `.md`** |

同样的代码差了 139 秒（29%）。GitHub 的 runner 一样被邻居抢。方向与量级和本机那组
一致，**只能当旁证，不能当精度**。

### 串行 Σ 那个数仍然站得住

自检负片的串行实付 **737.4 s → 145.2 s（省 592 s）**。它是 `mutate` 逐条报的时长求和，
19 条各自成样本，不是一次墙钟 —— 抢 CPU 会同时抬高两边的每一条，抬不出「前缀没被砍掉」
这个结论。四条点名负片的逐条实测同理：`M-P5-o` 58.0→3.2 s · `M-D6-t` 56.8→2.6 s ·
`M-F9-a` 44.8→7.3 s · `M-D6-w` 51.6→2.6 s。

592 s 与实测省下的 364 s CPU **不该相等**：592 是逐条**墙钟**之和，4 个 worker 同时在
跑，每条自己的墙钟里含着等核的时间，所以它高估了真正砍掉的 CPU。364 < 592 正是应该的
方向 —— 反过来才说明哪里算错了。

### 量它的命令 —— 给区间，不要给一个数

```
git checkout <上表任一棵树>
for i in 1 2 3; do
  { time npm run check >/dev/null; } 2>"/tmp/t$i" \
    || { echo "第 $i 跑红了 —— 这一跑不算数，别写进表里"; cat "/tmp/t$i"; continue; }
  grep -E '^(real|user|sys)' "/tmp/t$i"
done
```

> 这条命令头一版写的是 `{ time npm run check; } 2>&1 | grep -E '…'`，**它自己就犯了
> 这一节讲的毛病**：管道的退出码来自 `grep`，而 `npm run check` 红了 `time` 照样打
> real/user/sys —— 一次失败的检查会被当成一个有效样本收进表里（实测
> `{ time sh -c 'exit 7'; } 2>&1 | grep -E '^(real|user|sys)'` 退出码是 0）。
> 评审指出。**一次红跑的时长不是测量**，它量的是「跑到炸为止花了多久」。

> **写给下一个在这里写时间数的人。** `REVIEW.md` 那条「可算的数要么钉一棵不会再动的
> 树、要么只写命令」是为**树的函数**写的 —— 行数、变异数、判据数，钉住树就复现得出来。
> **时间不是树的函数。** 我钉了树、写明了同机串行空载、还拿第二台机器对照过，
> 交出的仍然是假的精度：我报的 −28% 恰好是观测区间最好的那一端，而那个区间
> 从 −4% 到 −28%，跨了七倍。
> 计时只有三条出路：**给抗抢占的量（CPU 时间）、给多次与区间、或者只写命令。**

## 二、依赖图：两条边 `tsc` 看不见

把 24 个小节机械包进 `group()` 后跑 `tsc --noEmit`，收 82 条 TS2304：24 条是预期的
`group` 未定义，另 58 条是跨节绑定，共 **14** 个名字。**十二个是无状态的**（十个纯函数
与两个常量 `bothTmp`／`q`），外提到模块作用域即可；**两个是真运行态**：
`dir`（collect 那一跑的产出目录）、`rendered`（render 那一跑的产出）。

> 这两个数头一版写的是「12 个名字、十个无状态」，第二轮复核核出来是 14／12。
> 数它的命令钉在 `2ad4c02` 这棵不会再动的树上：
> `git show 2ad4c02 -- scripts/check/selfcheck.ts | grep -cE "^\+(const|let) "` → 14。
> `2ad4c02` 的提交信息同错，照 ADR-73 不改旧提交，以本节为准。

于是我写下的依赖表是（**这一版是错的，下面两条各推翻它一处**）：`enrich←collect`、
`render←collect`、`regress←{collect,render}`、`memory←{collect,render}`，
并声称「其余 20 节互不依赖」。

**表里那条 `render←collect` 少了一半，那句声称也不成立。** 独立复核真跑
`{collect, render}` 子集，当场红两条：

```
✗ HTML 缺少公开指标或其边界声明（违反 U7/P5）
✗ HTML 缺少 KOL 活跃状态（违反 D10/U7）
```

`render` 真的需要 `enrich` —— 它读 `enrich` 落下的 `enrichment.json`。两者之间
**一个名字都不共享**，所以 `tsc` 的 82 条里没有它。真正的那条边是
`render←{collect, enrich}`，写在 `group('render', ['collect', 'enrich'], …)` 上。
**依赖只此一份**（第三节），这里不另抄一张表 —— 抄一张就是两份，迟早有一份先烂
（ADR-77 撤掉的那张手写敏感字段表正是这么烂的）。

第二条同族的：`bothTmp` 被我列进「十个无状态、外提即可」的名单，而外提的只是那行
路径常量，造目录与写语料还留在原处 —— 用它的地方会拿到 ENOENT，那会打出带（进程）
记号的失败，`notAssertion` 一票否决，整次判「跑不起来」。整段一起搬才对 —— 搬完之后
那 20 组的 `needs` 才真的是空的，那句声称这才补成真话。

> **`tsc` 抓得到名字级的耦合，抓不到文件系统级的。** 各节都往同一个 `tmp` 下写东西，
> 而那种耦合没有名字。**只有真跑每个子集才证得了。** 这条改动的依赖表因此是
> 「跑出来的」，不是「推出来的」。

## 三、先登记，后派跑

一组要不要跑，取决于后面有没有别的组 `needs` 它 —— 边登记边跑的话，第三组执行的
那一刻还不知道第八组会不会点它，于是只能另外维护一张手写的依赖表，而手写清单会烂
（ADR-77 撤掉的那张手写敏感字段表就是先例）。登记完再派，依赖只写在 `group(...)`
的第二个实参上，只此一份。

## 四、`--only` 收组 id，不收夹具名

头一版的理由是「收组 id 要让 `mutate` 多维护一份手写映射」。**那个理由是假的** ——
`mutate` 每跑一次本来就在读验证者源码扫清册，ADR-77 碰不着它。

> ⚠️ 「同一趟语法树多收两个字段就够」是当初用来驳成本论的说法，**落地没这么做** ——
> `groupOfLabel` 自己又 `createSourceFile` 了一遍，调用侧也是两趟。代价仍然远低于
> 运行期 import typescript，所以结论不变；但那句描述留着就是第二份不准的副本，
> 在这里订正，欠条见第九节。

真正的代价在另一侧：收夹具名要让 `selfcheck` 在**运行期** import typescript 扫自己的
源码，实测每跑约 +0.65 s，乘 19 条负片约 **+12.4 s** —— 占这条改动目标的一成。
所以翻译放在 `mutate` 那边。

**任何一条点名的夹具落不进某一组，就整跑。** 宁可多跑，不可漏验 —— 漏掉的表现是
「跑完、没红」，一条本该被抓到的变异会被判成没人抓得住。

## 五、子集跑要收的三处口

**没收之前，每个子集跑都剩一条 `✗`（孤儿检查），而那不是「多一条红」：**
`failed` 一涨退出码就非零，`judgeRun` 第一句 `exitCode === 0` 走不到，于是
**`survived` 这一态对每一条负片都不可达** —— 「这条变异没人抓得住」这个最要紧的
信号被静默换成 `elsewhere`。

- **孤儿检查在子集跑里不判、不计 `failed`**，照 `noShell` 的先例显式打一句
  「这一跑没验『每个可执行文件都有出处』」
- **成功支那句「N 个可执行文件都有出处」**在子集里同样不成立，换成说得准的
- **入口认领既不删也不写**：`claimed` 只装这一跑跑到的那几条判据，写回去等于拿残缺的
  记录盖掉完整的，而审计读的就是这份文件

## 六、老实说，什么缩了

`notAssertion` 的一票否决看的是「这一次运行的输出」。点名的负片走 `judgeRun` 的
`atStop` 那条路，所以**今天它看的已经只是「跑到那条夹具为止」的前缀**；`--only`
把这个前缀从约 50 s 缩到约 1–21 s。

缩掉的是「这条变异顺手把别处弄崩了」这种发现（ADR-70／#139 两轮评审才补上的）。
这是真的缩。换来的是那 171 秒。照 ADR-77：写出来，不假装没缩。

## 七、ADR-97 第六节的两处订正

- **单位**：那里写的「Σ 676.8 s → 约 20–40 s」是**串行 Σ**，不是实付。本条实测给的是
  CPU 1595.0 s → 1230.6 s（省 364 s，−22.9%）。这个单位错误是本条从第六节继承的，
  一并改口 —— 而本条头一版改成「墙钟 603→432」，**换了个错的单位**，见第一节
- **量级**：「约 20–40 s」把依赖闭包当成了空集，也没算到有几节自己就很贵
  （`memory` 12.0 s、`f9` 10.2 s、`collect-resume` 9.5 s）。实测的子集 Σ 是 **145.2 s**
- 第二节末那行「乘 347 条」与「selfcheck ×18」是当期陈述、已经过期（`7c4fd39` 上是
  370 与 19）。ADR-98 第六节已经更正过一次，本条不再重复记数 —— 要当下的数就跑一遍链

## 八、缺口与欠条

- **`--only` 点得着的只有一半小节。** 24 组里 12 组一个具名夹具都没有（`labelsOf`
  只认 `named(...)`／`endPath(...)` 的字面量），于是点不着。它们不是「不跑」——
  不点名时照样全跑，而且 `collect` 正是靠 `needs` 被别人拖进来的
- **`mutate` 不检查 `find` 在目标文件里是否唯一**，出现两次时静默只改第一处。
  这条在本条改动里真的发作过一次（见提交历史），登记在 `scripts/check/mutate.ts` 名下

  > ⚠️ 欠条：`mutate` 的前置体检不问锚点唯一不唯一，静默只改第一处 —— 错改的那处
  > 恰好有测试守着时，会报「被抓到」而要验的东西一个字没动 · 重启条件：下一条改动
  > 碰到 `mutate.ts` 里 `wiringFault`／`labelFault` 那几道前置体检

- **`mutate` 仍然不打那个乘法。** 每个验证者被几条变异用、每条跑多久，两个数它都手上
  有，却从不相乘给人看。这一条要在 `Ran` 上加字段并穿过 worker 的进程边界
  （`parseReport` 逐字段严格校验），连测试与负片是独立的一件事

  > ⚠️ 欠条：`mutate` 不打「每给一个验证者加一秒要乘以多少条」这个乘法 ·
  > 重启条件：下一条改动碰到 `jobs-rule.ts` 的 `Ran` 或 `parseReport`

- **缺省验证者那一族一点没动。** 本条之后它占串行总量的九成：370 条各跑一整遍
  `test.ts`，而它们一条 `kills` 都没有，`stopIfSeen` 第一句就 `kills === undefined`
  返回 —— 那里没有前缀可砍，因为根本没有「停」这回事

  > ⚠️ 欠条：给 `test.ts` 也切子集的路子没做，而它才是大头 · 重启条件：下一条专门
  > 碰检查链时长的改动

## 九、第二轮独立复核（ADR-24）：修了八条，登记五条

这条改动动的是守 P5.i（红线）的验证者本身，所以按 ADR-24 起了第二轮四路独立复核。
复核跑的是 `2be5e1d` 那棵树，交回 15 条存活、7 条驳回，**而且驳回了自己人** —— 同一件事（空的 `--only=`）被两个
维度报成缺陷、被第三个维度驳回。下面是我逐条复现之后的裁定。

### 修了的

- **新模块 `group-rule.ts` 没进 `docs/ARCHITECTURE.md` 的锚点表。** 三个维度各自独立
  撞上同一条。机械核过：分支上 `scripts/` 底下唯一缺表的就是它，主干 `7c4fd39` 一个
  不漏 —— **本条开了这张表的第一个洞**。那张表自己写着「当索引读，别当证据读」，所以
  后果只是索引缺一行；但免责的是**怎么读**，不是可以不登记（`AGENTS.md` 与
  `docs/SYNC.md` 都明写这道同步，ADR-78 起没有机器核）。已补，并机械核过表补满了。

- **`--only=`（等号后面空着）跑零组、打绿、退出 0。** 这是三个维度打起来的那一条。
  驳回方说得没错：屏幕上确实印着 `[只跑 ]（其余 24 组没跑）` 与 `只跑 0 组`，而且
  `M-H42-d` 的 `why` 明写抛错会掩盖意图。**我仍判它是缺陷**，理由在触发路径：
  `--only=$IDS` 而 `IDS` 没设时没人在看屏幕，看的是退出码；而那句汇总的**形状**与
  一次合法的子集全绿一模一样，只有括号里的数字不同。`group-rule.ts` 开头我自己写着
  「什么也不验、还以退出码 0 结束 —— 那正是本仓库反复栽的那种假绿」，这条原则对空集
  一样成立。修在**入口**，判定一个字没动 —— `parseOnly` 仍把空数组与 `undefined`
  分开，`M-H42-d` 杀在返回值上、不受影响，只订正了它的 `why`。
  实测：修前 `exit=0`，修后 `exit=1` 并说出「点了零个组」。

- **`--only` 点错组名时临时目录漏在盘上。** `wanted` 在 `runGroups` 里抛，而那时目录
  已经建好、语料已经写盘，收尾那句 `rmSync(tmp)` 一行都不跑。复核给的补法（把校验
  提到建目录之前）**不成立** —— 登记表要到 24 句 `group(...)` 跑完才满，提前校验会把
  `--only=probe` 也判成点了不存在的组。改成照 `mutate.ts` 里 `restoreClaims` 的先例

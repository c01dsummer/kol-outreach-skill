# ADR-136 校准版本改由命令按内容算出，原地改校准的流程保留

- 日期 · 2026-10-09 · 语义复评批次 A 开工前的设计审计（批次 A 的范围见 ADR-135）
- 类型：**发现更优解**（改需求 D20；是否夹带扩范围单独查过，见第三节）
- 触发它的事实：评审过不过期只比版本字符串 —— `statusOf` 在评审记下的品牌校准版本与任务当前版本相等时就标已评（`scripts/lib/review-projection.ts:30-33`），
  version 只要求是非空字符串（`scripts/lib/brand-calibration.ts:13`）。Skill 说明照实写着「内容改了而版本没换，旧评审仍显示为已评」（`skill/references/product-intake.md:66`）。
  ADR-130:244 当时只把这条边界写进说明，不另加内容指纹
- 冲击的需求：D20（新增两条判据与 D20 × P1 交点；D20.a、D20.d、D20.e 不变）；D21（D21.p 的比较规则不变）
- 结论：采纳。本条不改代码与需求登记表；新判据与交点由 ADR-135 施工顺序第 2 步那条实现 PR 在第一个提交登记；
  第 2 步落地前，现行 D20（版本只校验结构）、D21.p 与 `skill/references/product-intake.md:66` 继续生效，内容哈希版本与 `calibration version` 不得称为已上线（ADR-135 第五节分步启用说明）
- 理由：不碰红线；不缩范围、不降标准，补上「按旧校准做的判断显示为已评」这一个可信缺口；可逆。逐条见第二节
- 连带改动：本记录；`docs/adr/README.md` 索引（`npm run adr -- --write`）。Skill 与架构文档的同步在实现 PR 里做，至少含第六节所列，完整清单按 `docs/SYNC.md` 触发表逐行过；ADR-130 本次不追加

## 一、决定

1. **新命令 `calibration version`。** 读任务目录 task.json 的 `brand_calibration`，对除 version 外的全部内容按规范化 JSON（规则见下）计算 SHA256，
   写回 version，格式是 `sha256:` 加 64 位小写十六进制。
   - 只改 `brand_calibration.version`；brand_calibration 的其余字段与它们的顺序原样不动。
     写盘照 `saveCostCheckpoint` 的形状：盘上重读、只换这一个字段再保存（`scripts/lib/task.ts:41-46`）；
     保存时 `saveTask` 照例刷新 `updated_at`（`scripts/lib/task.ts:36`），task.json 的其余字段不变。
   - 任务没有 brand_calibration 时不生成校准、不生成版本、不写盘，如实说明这个任务没有品牌校准。
   - brand_calibration 不合 D20.a 时以退出码 2 拒绝，不写盘。
   - 四组偏好与 sources 都是有序数组，调换顺序也算内容变了。
   - 规范化：UTF-8、无 BOM、无多余空白；对象键递归按 Unicode 码点排序（不用 JS 默认的 UTF-16 码元序）；数组保持原顺序；
     实现带固定测试向量，其中含一对两种排序结果不同的键（如 U+FF5E 与 U+1F600）。
   - 规范化 JSON 与内容哈希是批次 A 的同一份实现；ADR-135 D30 草案里的 `calibration generate` 生成校准时用同一算法，不另写一份。
   - 命令不加锁。与同一任务的 collect、enrich、render 同时运行时，互不覆盖不保证（同 D4、ADR-66），由 Skill 要求串行运行；
     B1 引入任务锁时另开 ADR 处理（ADR-135 第二节）。
2. **入口复算。** version 是这种格式时，collect、enrich、render 在 D20.e 的同一时机按内容复算 ——
   与 D20.e 的结构校验同处（`scripts/collect.ts:88`、`scripts/enrich.ts:73`、`scripts/render.ts:43-51`），先于费用预留、外部请求和任何写入。
   不一致以退出码 2 拒绝，指出 `brand_calibration.version` 与复算值不符。
   - 复算写在这三个入口各自的流程里，**不放进** `brandCalibrationProblems`：人工反馈模板命令也调用它（`scripts/lib/feedback-template-task.ts:33`），
     而 D26.b 与 `docs/ARCHITECTURE.md:193` 只要求那里做结构校验。D26.b 不变。
   - 不是这种格式的手写版本照旧只校验结构（向后兼容）。已建好的任务不受影响。
3. **原地改校准的流程保留。** 任务建好后改 task.json 的 brand_calibration（`skill/references/product-intake.md:66` 后半句）照旧可以做；
   改完运行 `calibration version` 换 version，不再手写。旧评审按 D21.p 标待重评。
   改了内容却忘了运行命令：version 是哈希格式的，下一次 collect、enrich、render 以 2 拒绝并指出来 —— 这正是本条要补上的；
   version 仍是手写标签的，与今天一样识别不出（第五节）。
4. **Skill 流程只变两处。**
   - 新任务建好后、进入 Phase 04 评审之前，把 version 换成内容哈希：绑定了发布包的由 `calibration generate` 写（ADR-135），其余运行一次 `calibration version`。
   - 原地改完校准后用命令换 version（上一条）。两处运行命令时都不与同一任务的 collect、enrich、render 同时进行（第 1 条）。
   - 建任务前 Phase 02 小样确认里，collect 配置的 version 仍是手写标签（`skill/SKILL.md:66`、`skill/references/product-intake.md:66` 前半句）。

## 二、理由（四条判据依次问）

1. **触碰红线吗？** 不碰。
   - P1：没有 brand_calibration 的任务不补校准、不补版本，复算只核对已有内容（交点写在第四节）。
   - P2：version 只标识内容，不改变 kind 的含义，也不授予脚本核实产品事实的能力（`docs/ARCHITECTURE.md:161-162`）。
   - P3：复算是纯本地计算，排在费用预留之前，不新增付费请求。P4、P5 无关。
2. **缩范围还是降标准？** 都不是。今天「已评」可能是按旧校准评的，展示说的是假话；本条落地后，哈希版本的任务不再这样。
3. **覆盖还是可信？** 可信。按旧校准做的判断不再冒充当前判断；手写版本的任务覆盖不变，也不变差。
4. **可逆吗？** 可逆。手写版本仍被接受，命令可以不用；撤掉命令与复算后，已写进 task.json 的哈希 version
   在旧代码下只是一个合 D20.a 的非空字符串，任务照常可用。

## 三、是否夹带扩范围

新增的只有一条命令和一次复算。命令只写 version 一个字段；复算只在 version 已是哈希格式时发生。
不新增付费请求，不新增输出文件，不改评审正本格式，不改 D21.p 的比较规则，不改人工反馈模板命令（D26）。
rubric、案例与 Skill 指令的依赖**不**顺带做，见第五节。结论：没有夹带。

## 四、D20 新判据与交点草案（实现 PR 的第一个提交照抄进 `requirements.json`）

字母写作 D20.f、D20.g，登记时按下一个空字母。登记时 D20 的 adr 数组追加 ADR-136。

- **D20.f** `calibration version` 先按 D20.a 校验，不合规以退出码 2 拒绝且不写盘；合规时对 brand_calibration 除 version 外的内容
  按第一节第 1 条的规范化规则计算 SHA256，写成 `sha256:` 加 64 位小写十六进制的 version，brand_calibration 的其余字段及数组顺序不变；
  brand_calibration 缺席时不生成校准或版本、不写 task.json。写入成功以 0 退出；保存失败以 1 退出，盘上 task.json 保持原字节；
  task.json 中除 brand_calibration.version 与 updated_at 外的字段不变；诊断进 stderr。
  brand_calibration 缺席时的退出码与提示写法、成功时 stdout 的内容，由实现 PR 在登记时写死。
- **D20.g** version 为 `sha256:` 加 64 位小写十六进制时，collect、enrich、render 在 D20.e 的同一时机按内容复算；
  不一致时指出 `brand_calibration.version`，以退出码 2 在费用预留、外部请求和任务或交付物写入前拒绝，续跑及改额时盘上 task.json 保持原字节；
  version 为其他非空字符串时只按 D20.a 校验结构。人工反馈模板命令不复算（D26.b 不变）。
- **D20 × P1**（写在 D20 一侧，adr 填 ADR-136）：「P1 优先：brand_calibration 缺席的任务不生成校准或版本，版本保持缺席；
  复算只核对已有内容，不补出缺失的字段，也不以复算值改写不一致的版本。」
- 与 P2 无交点：version 不改变 kind 的含义（第二节）。与 P3 无交点：不新增付费请求。与 P4、P5 无关。

## 五、代价与已知边界

- **第一次换哈希会让已有评审全部待重评。** D21.p 比的是字符串，已有评审的任务把手写 version 换成哈希时，
  内容没变也会全部标待重评。所以 Skill 只要求新任务在 Phase 04 之前换；已有评审的旧任务不要求换。
- **任何内容改动都换 version。** 改错字、调换偏好或来源的顺序，也会让全部旧评审标待重评；
  手写标签时运营可以选择不换，按内容算以后没有这个选择，重评量只会持平或上升。
- **手写版本的任务仍有 ADR-130:244 那条边界。** 内容改了而手写版本没换，旧评审仍显示为已评。
- **v1 的 version 只覆盖 task.json 里的校准内容。** rubric、案例与 Skill 指令的变化在 v1 不触发待重评；
  发布包里供 Agent 读的案例（ADR-137 第一节第 4 条）也一样，发布包将来若带 rubric 同理。要到 v2 的分项依赖才覆盖；B1、B2 是否排期见 ADR-135。

第 2 步落地后，本条补上 ADR-130:244 记下的那条边界（对哈希格式的版本）。ADR-130:244 写的是那一次 Skill 对齐的范围（「本次只把这条边界写进说明」），
本条不推翻它，也不改它的原句；本次不在它末尾追加，第 2 步落地时按 `docs/SYNC.md:34` 追加更正（见第六节）。

## 2026-10-10：第 2 步切成两片；登记时补定的几处

**切法。** 需求所有者 2026-10-10 定：ADR-135 第四节第 2 步切成两片，串行。

- **2a**：规范化 JSON 与内容哈希（新模块 `scripts/lib/content-hash.ts`），collect、enrich、render 的入口复算（第一节第 2 条）。登记 D20.f–D20.j 与 D20 × P1。
- **2b**：`calibration version` 命令（第一节第 1 条），Skill 运行命令的两处流程（第一节第 4 条），README、入口表与字段所有权，ADR-130 末尾的更正（第六节）。命令的判据在 2b 按下一个空字母登记。2a 合入后开 2b；ADR-135 第四节第 2 步的落地块在 2b 合入时追加。

理由：两片要的证据不同（单元向量加入口夹具，对命令夹具）；2a 在主干上不改任何现有行为 —— 命令出来之前没有哪个任务的 version 是哈希格式；整步的源码新增按先例估在 350–550 行，切开后各在线内。2a 合入后、2b 合入前，哈希版本只能手写，Skill 不提它，也不得称内容哈希版本已上线（ADR-135 第五节）。

**判据拆开登记。** 第四节草案的 D20.f、D20.g 各装着几件能被不同代码路径分别弄坏的事，按 `process/1-REQUIREMENTS.md`「拆到多细」拆开。2a 登记五条：D20.f 哈希的定义，D20.g 不一致时拒绝，D20.h 一致时放行，D20.i 非哈希版本只校验结构，D20.j 人工反馈模板命令不复算。字母从 f 起：D20 只发出过 a、d、e，b、c 从未用过，拿来登记读起来像回收旧号。

**规范化 JSON 补定。** 第一节第 1 条只定了编码、空白与键序。标量照 ECMAScript `JSON.stringify` 写：字符串的转义、数字的最短往返写法、`true`／`false`／`null`。JSON 写不出的值照它的结果写 —— 解析时溢出成无穷大的数字写成 `null` —— 不另加分支。D20.a 不拒绝未列出的键，它们也进哈希（D20.f 写明）。

**只在结构合 D20.a 时复算。** 结构不合规时只报 D20.a 的问题，不另算哈希（D20 × P1）。复算出的问题与结构问题进同一份清单，所以 enrich、render 与同文件的任务列表问题照旧两类均报（`docs/ARCHITECTURE.md:422`）。

**不一致时报出复算值。** 提示里给出按当前内容复算的值。把它贴进 version 不会让旧评审变成已评：D21.p 比的是评审记下的版本与任务当前版本，换了值，旧评审照样待重评。2b 之前，这也是手写哈希版本的唯一改法。

**第六节的同步清单分到两片。** 2a 只改 `docs/ARCHITECTURE.md` 的锚点表、`:161-162` 与顺序契约那一行，以及 `skill/references/product-intake.md:66`「只校验结构」那半句的限定；其余各处随 2b。

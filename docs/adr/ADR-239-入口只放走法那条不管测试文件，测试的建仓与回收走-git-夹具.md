## 二、业界怎么分

- **git 自己的测试**（`t/test-lib.sh`）：隔开本机设置这件事只在这一份共用脚本里做 —— 清掉继承来的 `GIT_` 开头的环境变量（留着一张白名单，比如调试输出、测试开关那几样）、不读系统配置、把 `HOME` 指到每个测试脚本自己的临时目录，测试通过就删掉那个目录（失败时留着给人看）。各个测试脚本不各写一份。共用的还有一批比较、判断的小函数（比如比两份文件），但每条测试该看到什么，写在测试脚本自己身上。
- **《xUnit Test Patterns》**（Meszaros）：建夹具的步骤抽成共用的「建造方法」「测试工具方法」，常用的比较也可以抽成「自定义断言」；为的是每个测试读起来只剩「准备了什么、该看到什么」，测试本身就是一份说明书。

两边分法一致：**准备与收尾抽出去共用，具体的期望留在测试里**。本仓库还多一条硬限制，比业界更紧：变异点名「该红的是哪几条断言」，认的是两份验证者（`scripts/test.ts`、`scripts/check/selfcheck.ts`）本文件里字面写着的断言名字，扫描不跟进它们引的模块（`mutate.ts` 的 `inventoryOf`、`mutate-rule.ts` 的 `labelsOf`；ADR-120 第 146 行说的「字面声明、单源码标签扫描」）。所以连「自定义断言」也不能抽走：断言调用连同名字必须留在这两份文件里。

## 三、定下的

1. **第 10 条不管测试文件。** 它说的「入口」是被测的代码。测试文件（以 `field-use-rule.ts` 的 `isVerifierFile` 为准）是验证者：它对不对靠变异来验，不靠再写一层测试，所以「有语义就该能被测、能被测就不该待在入口里」那条判据到这里停住。不归第 10 条管不等于什么都行：照样受 `process/4-VERIFY.md` 与体量闸门管。写进 `docs/CONVENTIONS.md` 第 10 条末尾，CodeRabbit 按约定评审时读得到。换个项目也成立的那一半（准备收尾共用、具体的期望留在测试里）该进 `process/4-VERIFY.md`，但 `process/2-CHANGE.md`「文档同步规则」要求改流程纪律的 PR 不与代码改动混在一起，所以另开一条只改 `process/` 的 PR，来源指本条。
2. **测试里该共用的是建仓、删仓、提交身份、环境。** 这几样漏一样不会红，只会悄悄读到本机配置、留下垃圾。测试要在临时目录里建 git 仓库、或起一个会在那里问 git 的进程时，从 git 夹具模块拿（`withToyRepo`、`toyRepoAt`、`fixtureEnv`），不自己拼。
3. **留在组里的**：具名断言（必须留在两份验证者本文件里，见第二节）；只有这一组用的观察手段 —— 这一组的预加载探针、目录字节快照、起入口的编排。它们只有一处用，抽出去不省事，反倒让读测试的人多跳一个文件。
4. **旧组改到哪组搬哪组。** 测试与自检里还有十几处自己包一层 `fixtureGit` 加提交身份、自己开临时目录的（树 c8401a5：`scripts/test.ts` 里调 `fixtureGit`／`fixtureGitOrThrow` 26 处（本条改完 25 处），其中一部分是夹具模块自己的测试，`selfcheck.ts` 14 处）。它们的环境已经经夹具隔开，缺的只是建删与身份那一层的共用；不专门去搬，哪条改动改到那一组就顺手搬（与拆大决策记录「改到哪份拆哪份」同一个办法）。

## 四、这一组改了什么

- 独占临时根改由 `withToyRepo` 开（它的 `more('owner')`：原先是系统临时目录底下的 `kol-fixture-git-env-…`，现在是 `kol-toy-…/owner-…`，深一层），跑完或抛错整个删掉；`withToyRepo` 自己那个空的玩具仓库目录没用上，跟着一起删。三个诱饵仓库与两次入口的临时目录照旧建在这个根底下、名字不变，诱饵仓库经 `toyRepoAt` 建：带提交身份（命令行 `-c` 给，另关了提交签名）、不读本机配置。原先自己 `mkdtempSync`、自己 `try … finally` 删，自己包一层 `fixtureGit` 并在诱饵仓库里写一份提交身份配置。
- 删完再看临时根还在不在、在就抛错，这一句留着，但只在正常走完时查：组里抛错时由 `withToyRepo` 删、原样往外抛，不再另查（原先抛错时也查）。
- 起自检入口的环境改从 `fixtureEnv({})` 拿：去掉继承来的全部 `GIT_` 开头的变量，再不读系统与用户的配置文件（原先手写 `GIT_CONFIG_NOSYSTEM`、`GIT_CONFIG_GLOBAL` 两项）。要灌进去的六项污染照旧在这份环境之上另加，`NODE_OPTIONS`、`MUTATING` 照旧删。
- **新加：跑测试的进程身上本来带着六项之一时，这一组先从本进程环境里拿掉、跑完放回。** git 夹具正是 `M-H64` 改的地方；跑测试的进程身上若带着其中一项（比如在 git 钩子里跑，git 会设 `GIT_INDEX_FILE`），施变后它会经测试自己建诱饵、起入口时漏出去。独立复核两轮都造出过：第一轮，起入口的环境不再删六项时，`GIT_INDEX_FILE` 那条变异下整组抛错、生产代码写进了外面那份索引文件；第二轮，起入口时再删一遍之后点名的那条照常红，但测试自己建诱饵时仍把一份索引写进了外面那个文件（改前也是这样，原先建诱饵同样经 `fixtureGit`）。现在两处都不漏。
- 诱饵仓库关掉后台维护（`gc.auto=0`、`maintenance.auto=false`）那两句保留：快照前要仓库静止（ADR-120「CI 的夹具维护竞态修正」）。
- 十二条具名断言、预加载探针、快照、起入口那一段一个字没改。

改后对照：这一组单跑 12 条全绿；把 git 夹具里去掉 `GIT_` 变量那一行依次改成放过 `M-H64-a`～`f` 各自那一项（六条变异原样手工施上，跑完复原），每一次都是点名的那条「Git 建历史隔离：不继承 …」红，`GIT_DIR` 那一次另加「继承 GIT_DIR 不改诱饵任何 Git 文件」红。跑测试的进程身上带着 `GIT_INDEX_FILE`（指向测试外一个还不存在的文件）再施 `M-H64-c`、带着 `GIT_WORK_TREE`（指向测试外一个空目录）再施 `M-H64-b`，都是点名的那条红，外面那个文件没建出来、那个目录仍是空的；不施变时带着 `GIT_INDEX_FILE` 跑，12 条全绿。

## 五、拦不住的

- 第三节第 2 条没有机器查：测试里自己拼 git 环境、自己开临时目录建仓，不会红。按字面去搜「`GIT_CONFIG_NOSYSTEM`」「`mkdtempSync` 后接 `git init`」这类写法是猜，搜不全也会误报，不做。靠评审读第 10 条。
- 测试自己建诱饵仓库也经 git 夹具，而 `M-H64` 改的正是夹具。上面那一条只挡跑测试的进程身上带着的那六项；被测的夹具若漏的是别的变量，测试自己建仓同样会漏，这一组只观察六项，看不到。

# ADR-152 回访台账：例程每周往这里追加一块，人合每一块

- 日期 · 2026-10-14 · 按 ADR-151 落 P4（第二节第 4 片）
- 类型：需求有歧义（补「定期清点」由谁、何时触发；不改重启条件的三种写法）
- 触发它的事实：`process/6-INTEGRATE.md`「登记怎么做」第 4 条把「定期清点」列为重启条件三种之一；主干上没有任何按日历的触发（`.github/workflows/` 下只有 `check.yml`，其中没有 `schedule`，`aa96ce0`）；ADR-151 转引提案 §0 第 1 条：「定期清点」在决策记录里发生过 16 次，没有一次是定期的
- 冲击的需求：无
- 结论：**采纳**。P4 的采纳在 ADR-151 第一节（需求所有者 2026-10-14 选了「全按推荐」）；本条只落那份裁决定下的形状。GitHub 上的人批痕迹是需求所有者合入本条那条 PR
- 理由：「定期清点」要有一个按日历发生的触发，它的产出又不能落进一张会漂的表。台账是一条只追加的决策记录：每一块由人合，人判（接受、拒绝）也进块；接手的会话由 `AGENTS.md` 路由表点名来读最新一块。例程只递原料，判断留给人（ADR-151 第四节第 2 条）
- 连带改动：`docs/REVISIT.md`（新，例程的说明书）、`docs/SYNC.md` 文档地图一行、`AGENTS.md` 路由表一行、索引

## 一、一块的格式

每次回访往本条末尾追加一块，按时间往下排；前面的块一个字不改（`process/2-CHANGE.md`「新内容加在哪」）。没有候选也写一块。

```markdown
## <YYYY-MM-DD> · 本跑 <主干提交前 7 位>

- 上周结果：<token> · 提出 <N> · 接受 <M> · 拒绝 <K>

| id | 候选 | 值 | 人判 |
|---|---|---|---|
| <YYYY-MM-DD>#1 | <一句：是什么、在哪> | <值 / 没查到 / 无从确认> | |
```

- **上周结果**：四个 token 之一，原样写：`已合入` / `所有者关闭` / `例程关闭` / `无从确认`。怎么判，见 `docs/REVISIT.md`「每次开始」。
- **提出 · 接受 · 拒绝**：说的都是**上一块**：它的候选有几行，需求所有者在它的「人判」栏填了几个「接受」、几个「拒绝」。
  上一块没合入，三个数都写「无从确认」。
- **候选表**：一行一条。id 是本块日期加序号，后面的 PR 引一条候选就引这个 id。
  「值」只有三态：查到的值本身、`没查到`（查了，没有）、`无从确认`（查不了，原因跟在后面）—— 缺的值不留空，也不写成 0。
  「人判」只由需求所有者在合并前填「接受」或「拒绝」，不填就是没判。
  没有候选就只写一行 `| — | 无候选 | | |`。
- 候选从哪来、每块最多几条：`docs/REVISIT.md`。

## 二、怎么读

- 签收了几块：`grep -c '^- 上周结果：已合入' <本文件>`。
- 什么条件下整个撤掉、什么条件下停候选表只留心跳行：ADR-151 第四节第 4 条，这里不重复。
- 例程能写什么、不能写什么：`docs/REVISIT.md`「能写什么」。

第一块从本条末尾往下接。

## 一、数什么

**单位。** 验证者进程（`selfcheck.ts` 或 `test.ts` 那个进程本身）经 `spawn`、`spawnSync`、`execFile`、`execFileSync`、`exec`、`execSync`、`fork`（含 promisify 版）**直接**起的子进程，**不含 git**；`sh -c`、`node -e` 都算，孙进程不单独算。本记录说的「启动」都是这个单位。

**在哪数。** 变异一步的正常基线（每种选组配置在没施变的源码上本来就跑的那一次），不加任何启动。

**每条变异付几次 `paid(m)`**，在 m 所在配置的正常基线里数：

1. **会提前停的变异**：m 的 `kills`（它点名的断言标签）里每条**末次打印**时验证者已经起了几次，取最大的。取末次不取首次：循环里多次打印的标签，往首次之后加启动，下界不变、成本却变了。
2. **某条 `kills` 标签在基线里一次也没打印**：见齐就停永远凑不齐，记为**整个配置的启动数**。
3. **全跑变异**（没有选组）：拿不到计数，**按超线判红**。
4. **不提前停的配置**：按规则二判，乘数是配置的启动数与落到它的变异条数。

**「停不停」与见齐就停共用一个谓词** `stopsEarly(verifier, kills, only)`（有 `kills`，且不是「需求测试 ＋ 选了组」）：`mutate.ts` 的 `stopIfSeen` 与判定都调它（那个调用点施不了变异，只能靠读）。

**一行打印归到哪条标签。** 去掉记号后的正文，归到**最长的**那条声明标签 `L`：等于 `L`，或以 `L：`、`L（` 开头（一条标签可能是另一条的前缀）。

**为什么数得准。** 同一棵树上逐次相同，CI 与本机逐项相同（第十三节第 5 小节）；第四十四节那 10 跑是主干上连着的 10 个提交，计数要用到的四样文件一字不差，跑在四种 CPU 上，都打「相同」。秒数做不到。

**限定。**

- **只数直接子进程**：整棵子树随 tsx 的转换缓存变。**git 不算**：单价差两个量级。
- **确定性只对同步起进程、按程序顺序打印的组成立。** 所以超线时只对那种配置**再跑一次基线**确认；两次计数都有而且不同，报「启动数不确定」，不报超线（第十三节第 3 小节）。
- **标签不拼随跑变的东西。** 同一配置两次正常基线的打印要逐字相同，所以断言标签不拼玩具仓库这一跑的提交号之类，写成固定的名字；拼了，重跑确认时就报「不确定」（2026-11-14 照这条改过四条）。

## 二、两条线

交接文档量了 11 个提交（各是哪个提交，见历史文件第二节那张表）：正常时自检单条最多 46、需求测试最大 48；劣化那一轮从 #294 的 61 涨到 169，需求测试到 390。**50**：60 会漏掉 #294 那一步，40 会让 ADR-131 决定不拆的 `feedback-template` 尾部（45–46）触发。**100**：正常 48、劣化 390，两边都有余量。秒数规则回测过六种，最好的也漏掉 #294。

> ⚠️ **`feedback-template` 离线只差 4 次，拆组救不了它**（两条汇总断言汇总全组）：一旦超线，只剩第三节第 2 种改法，或由需求所有者改常量。

## 三、不设豁免

超线只有三种改法：

1. 拆组（ADR-131、ADR-144；本记录自己拆过 `h-launch-preload-edge`、`h-launch-summary-deep`）；
2. 把覆盖整个矩阵的一条断言改成每个用例各一条（`process/4-VERIFY.md` 本来的要求）；
3. 把真入口用例移出需求测试组（ADR-120），通常移到自检。

**少写变异不是改法**，失败信息与本记录都这么写；机器看不出来（第七节第 6 条）。**真要调高 50 或 100**：改 `launch-rule.ts` 的 `LAUNCH_LIMIT`、写决策记录、由需求所有者批。不设豁免：写代码和批豁免是同一方时，出口的价格是零，豁免还会被当先例引（ADR-64）。

## 四、PR 上判红，主干上只报数

PR 的 CI 跑在合并提交上、没有合并队列，两条各自在线内的 PR 合起来可能超线。所以照体量闸门：HEAD 就在主干上时，超线只报数。这只让主干自己那一跑不红：之后每条 PR 的合并提交照样红，直到拆组的那一条合进去；按 `process/6-INTEGRATE.md`「主干红了」先开拆组的那一条。

**主干上也红的两种**：这一跑量没量成（文件缺了、对不上树、形状不对、某种配置缺计数，第二十一节）；摘要现算时 `tally` 有一项认不得（第四十四节）。

## 五、取代哪几处，为什么

与本条相左的只有 ADR-97 第四节；ADR-99、120、121 里相近的话说的是各自的范围，末尾追加的是说明、不是取代；只说秒数的文档与注释已改准（秒数照旧不判）。对 ADR-97 第四节的四条理由：

1. **秒数只在那台机器上成立**：启动数是树的函数；本条不管单次启动多贵（第七节第 2 条）。
2. **核不了的死亡条件比没有更糟**：本条的都对着仓库核得了。
3. **体量闸门当不了先例**：判据数得出来这一半正适用；「豁免全自批」那一半成立，所以不设豁免。
4. **闸门自身的成本是乘性的**：本条不加启动，判定的变异全部 `by: test`、每条 0 次启动。

数一个数是该建的「替代跑的」；「这段前缀该不该付」是不建的「替代读的」，所以只数、不判。

**数据缺失不放行。** 没先跑变异一步、计数文件的树身份对不上、某种配置的计数缺了，判定一律**报错**，不当成通过；不然删掉数据文件就等于关掉闸门。计数在任何情况下都不记成 0，只能是「未知」，而「未知」是红的。

## 六、死亡条件

> **什么条件下退成只报数**：主干上的计数报出「启动数不确定」时 —— 同一棵树、同一种配置的两次正常基线计数不同（第一节末）。那时启动数不再是树的函数，本条的前提没了，判红会变成按运气红。

> **什么条件下整个撤掉**：变异按点名的用例路由（不再按整组），或需求测试的选组也能提前停，成为现实时。前一种让规则一要拦的那段前缀不存在，后一种让规则二要拦的乘数不存在；两种都能对着代码核（`group-rule.ts` 的选组单位、`stopsEarly`）。

不写「连续 N 次运行」（ADR-85），也不写「豁免占比」。主干上报了不确定时闸门打一行「死亡条件响了」，退不退由需求所有者定。自检玩具 `s-drift` 故意造的不确定不算。

## 七、不覆盖的

绿灯不说明：

1. **进程内变慢**：组内 0 次启动的配置本条不管，第二十七节那一行只报数（变异总量与分份均衡后来由 ADR-203 另判）。
2. **单次启动变贵**：换加载方式、丢编译缓存，次数不变。
3. **嵌套启动只算 1 次**。
4. **每条都在线内、整组中等程度地胀**：单条上限抓不到；树内摘要（第三十五节）让它进 diff，由人读。
5. **变异以外的耗时**：能数的那一块由第三十一节那一行只报数。
6. **少写变异**：没有东西会报。

第 1、5 条各有一行只报数，代码与文档里叫「第七节末第一行」「第七节末第二行」：第一行是进程内耗时（第二十七节），第二行是有启动但没有变异的组（第三十一节）。两行都不改退出码、不进闸门。

## 八、怎么落地

照「闸门自身走最后一块砖」：判定、测试、变异先合，最后才接进检查链，一片合了再开下一片。判定 #303；计数只报数 #306、#309；接进检查链 #311；两行只报数 #312、#313；树内摘要 #333–#335，升红 #346。

## 九、判定模块的接口

判定都在 `scripts/check/launch-rule.ts`，纯函数，计数由别处数好交进来：`LAUNCH_LIMIT`（`paid: 50`、`product: 100`）；`printLabel`（一行归哪条标签）；`paidLaunches`（付几次）；`launchFindings`（两条规则的判定，交回 `paid`、`product`、`full-run`、`missing`，后加 `unsteady`）；`launchReport`（报错文本，末尾附三种改法与「少写变异不是改法。不设豁免；上限只能改常量、写决策记录、由需求所有者批」，只有 `unsteady` 时不附）。后加的见第十三、二十一、二十七、三十一、三十五、四十四节，另有 `joinLaunchParts`（ADR-200）。

`launchFindings` 的规矩，逐条可测：

- `stopsEarly` 为真且有选组：`paid > 50` 报 `paid`，等于 50 不报。
- `stopsEarly` 为假：按配置归拢，`基线 total × 条数 > 100` 时报一条 `product`，`ids` 按 id 排；等于 100 不报。
- 没有选组的变异各报一条 `full-run`。
- 有选组变异却没有基线的配置，报一条 `missing`、带全部 id，不再判两条规则；没有变异落到的基线不判。
- 顺序：`full-run` 按 id 最前，其余按配置键（`jobs-rule.ts` 的 `configurationKey`），同一配置里 `paid` 按 id。本记录说的「排」都是 JS 字符串的 `<`，不是 `localeCompare`。

## 十、测试怎么写

1. **测试先于实现**：断言由不读实现函数体的上下文照本记录写、期望值手推；先红后绿，再逐条施变。读物越过清单时照 ADR-81 第 98 行写成偏离，合入即接受；那张欠条按每偏离一次都响来读。
2. **判定的断言直接写成 `eq('…', …)`、`ok('…', …)`，不包一层**：变异点名用的清册（`VERIFIERS.test.declares`）只认直接传给它们的字面量首参，包一层（如 `same(label, …)`）就点不着，`mutate --brief` 报夹具立不住。不往 `declares` 里加包装。
3. **判定的变异全部 `by: test`**；入口与 `mutate.ts`、`selfcheck.ts` 的接线只由自检守（欠条「启动数闸门入口的映射与吞错没有变异」）。
4. **让组变重的断言另成一组**：落到不提前停的选组的变异，每条付一遍整组。

## 十三、数的那一侧：计数预加载与日志

变异一步只报数，不改结论与退出码；判红在第二十一节。

### 1. 计数预加载

`scripts/check/launch-preload.ts`，经 `NODE_OPTIONS` 的 `--import` 加载；tsx 壳里没有转换，所以它只 `import` `node:` 内建。

- 只认环境变量 `LAUNCH_COUNT`（日志路径、验证者脚本、原来的 `NODE_OPTIONS`），只在验证者进程本身的主线程里启用；启用后删掉它、还原 `NODE_OPTIONS`，子进程什么也不继承。
- 包住七个函数与两个 promisify 版；名字、返回值、抛出的东西都与原来一样。被包住的调用里再调到的不记。调用那一刻先记、再调原函数，起没起来都算。
- 日志每行一个 JSON：`L`（一次启动，记 `api`、`file`、`shell`）；`O`（写完的一整行 ✓／✗，两股各自切，半行不记）；`E`（在 `exit` 事件里写的收尾，之后不再记）。写错一律吞掉，读的一侧会认不得。
- **git 的口径**：`api` 是 `spawn`、`spawnSync`、`execFile`、`execFileSync` 之一、没有 `shell`、`file` 的末段是 `git` 或 `git.exe`，不算；`exec`、`execSync` 与带 `shell` 的起的是 shell，算。

### 2. 变异一步怎么接

- **只在正常基线那一跑注入**（路径只认 `verifier-rule.ts` 的 `LAUNCH_PRELOAD`），变异运行不注入。日志在 `.check-cache/mutate-jobs/` 下，读不出来算缺计数。
- **开跑先删**旧的 `output/mutation-launches/launches.json`（`--brief` 与 worker 以外，排在变异集体检之前）；**删不掉就以 1 退出**，打一行为什么、要先挪走。
- 全部正常基线绿了以后：`launchFindings` 判一遍；`launchRecheck` 列出的配置（有 `paid` 或 `product`）各**再跑一次基线**（不进成本报告），`settleLaunches` 确认，`launchTally` 汇总。
- 输出在「子集选跑」那行后面：`tallyLine`；有发现时一行「检查链最后一步的启动数闸门会照下面这些判（变异一步只报数）：」与缩进四格的报告；`MUTATION_LAUNCHES_JSON ` 接单行 JSON（`schema` 为 `mutation-launches/v1`，含 `head`、`source`、`tally`、`findings`）。同一份另写 `output/mutation-launches/launches.json`，外加 `baselines` 与 `again`（重跑没拿到计数记 `null`）；分份跑时写 `launches-k-of-n.json`（ADR-200）。
- 数的那一段（判定、重跑、汇总）抛错只打一行「启动数没数成（…）」，机器段与文件都没有，变异照常跑。只是写文件失败的，另打一行「启动数文件没写成（…）」，只报数那几行与机器段照打。
- 一种选组配置都没有（没有正常基线可跑）时也照样判一遍（只可能有全跑的发现）、照样打、照样写文件。

### 3. 读日志与确认

- `parseLaunchLog`（`launch-count.ts`）把日志读成 `{total, prints}`（不含 git）；形状不对、收尾行缺了或数对不上，就是 `undefined`，不是 0。
- `launchDrift` 交两次计数第一处出入；`settleLaunches` 只在两次都有计数**而且不同**时，把那种配置的超线换成一条 `unsteady`；有一次没有计数，超线照原样报。`unsteady` 报「✗ 配置 的启动数不确定：同一棵树上两次正常基线不一样（出入），不按超线报」与一行「先查这种配置两次起的进程为什么不一样」。
- `tallyLine`：「启动数（只报数）：n 种配置有计数；会提前停的最多付 x 次（…）；不提前停的启动×条数最多 y（…）」。

### 4. 接线证明

需求测试组 `h-launch-preload`、`h-launch-preload-edge` 真起玩具，核预加载记得对、不改验证者的行为；自检组 `launch-count-entry`（不进任何变异的路由）在玩具仓库上跑真 `mutate` 与 `launches`，核各种发现与最后一步那几行。

2b（2026-10-12）：CI 与本机在同一棵树上 `tally` 136 项逐项相同；有无预加载，136 种配置里 135 种行序列与退出码相同；差的那一种是 `h-mutation-maintenance` 一个标签拼了随跑变的提交号（2026-11-14 已改成固定名字，见第一节「限定」）。

## 二十一、检查链最后一步：启动数闸门

### 1. 判定放在哪

- **入口 `launches.ts`（`npm run launches`）是检查链最后一步**，不起验证者、不重跑：读启动数文件（没有整份时拼分份的，ADR-200），算源码身份，判在不在主干上，交给纯函数 `launchGate(record, source, trunk)`，照交回的 `{red, lines}` 打，红就以 1 退出。
- **不重判**：源码身份对得上，文件里的发现就是这棵树的。
- **源码身份**与变异一步用同一个函数：`claims.ts` 的 `mutationSourceIdentity()`（`scripts/` 下 `.ts`、`mutations.json`、依赖锁）。
- **在不在主干上**同体量闸门：`size-rule.ts` 的 `resolveBaseline`。`not-applicable` 算在主干上；`cannot-answer`（比如浅克隆）交原因，按 PR 判。

### 2. 先核数据，缺了不放行

依次核，第一条不过就报，红，**在主干上也红**：1. 没有文件、读不出、不是 JSON 对象；2. `schema` 不是 `mutation-launches/v1`；3. `source` 不是字符串；4. 当前树的身份取不到；5. `source` 与当前树不同；6. `tally` 或 `findings` 不是数组，或有一条发现的 `kind` 不在五种里。不核 `head`；只核到发现的种类（缺字段会让报告抛错、不放行，那张欠条现由 ADR-200 承接）。

### 3. 有发现时

- 没有发现：一行，绿。
- 有发现：先原样打 `launchReport`（重跑没拿到计数的配置另打一行）；判词：不在主干上，红；无从判断，红；**在主干上有 `missing`，红**（计数缺了是未知、不是超线）；在主干上没有 `missing`，只报数，另打「主干红了」那一行（全是不确定时不打），有不确定时再打死亡条件响了那一行。
- **「不确定」在 PR 上也红**，不附拆组的改法。`full-run` 在主干上与超线一样只报数；新加一条全跑变异在 PR 上就红。

### 4. 逐字的输出

数据不过：`✗ 启动数闸门：无从判断 —— 原因` 与一行叫人先跑 `npm run mutate`。原因按第 2 小节的六条依次是：「没有启动数文件，或读不出来、不是一个 JSON 对象」「启动数文件的 schema 不是 mutation-launches/v1」「启动数文件里没有源码身份（变异一步没取到）」「当前树的源码身份取不到」「启动数文件是另一棵树上写的（源码身份对不上）」「启动数文件的 tally 或 findings 不是数组，或有一条发现的种类认不得」；`--write` 不写时的原因也用这六句。没有发现：`✓ 启动数闸门：N 种配置有计数，都在线内`。有发现：报告各行、`  配置键 重跑那次没拿到计数，超线照第一次报（第五节末）`、`✗ 启动数闸门：n 条发现，不设豁免（ADR-145）`；无从判断时末行换成 `✗ 启动数闸门：n 条发现；无从判断 HEAD 在不在主干上（原因），按 PR 判红`；在主干上末行换成 `启动数闸门：HEAD 就在主干上，只报数不判红（ADR-145 第四节）` 与上面说的两行；在主干上有 `missing` 时那几行不打，末行是 `✗ 启动数闸门：n 条发现，其中 m 种配置没有启动计数：HEAD 就在主干上也红，计数缺了不放行（ADR-145 第五节末）`。闸门那几行之前先打第三十一节、第三十五节那两行。

## 二十七、第七节末第一行：进程内耗时（只报数）

### 2. 怎么算、怎么打

- 变异一步收尾，「按验证者记账」之后、结论之前打，有变异没被抓到时也打。只算第一次正常基线整跑 0 次的选组配置。
- **单位**：这一跑所有实测经过时间（成本观测里 `reported`、有限非负）的单条中位数；每种配置的数是落到它的实测耗时之和 ÷ 单位。同一跑里除以同一个数，两跑之间才比得了。
- 文本「进程内耗时（组内不起进程的 N 种配置、M 条变异，只报数）：合计 X 个单位；单位是……中位数 Y 秒；最多的：…」，一位小数用 `toFixed(1)`，合计先求和再取；前五从大到小，并列按配置键。
- 数不出来时打三句之一（没有计数；没有实测耗时或单位是 0；那些配置没有实测耗时），不报 0。不判红。

### 3. 接口

`inProcessLine(baselines, mutations)`，`mutations` 是成本观测里的变异那一张（`jobs-rule.ts` 的 `CostMutation`）；交回不带缩进的一行。

## 三十一、第七节末第二行：有启动但没有变异的组（只报数）

需求所有者 2026-10-13 定「整跑时顺便数」：不多跑、不加启动、不改退出码、不进闸门。

### 1. 数什么

自检登记的组里，不在任何一条 `by: selfcheck` 变异路由（`executionRoutes`）的 `executes` 里的组。完整、非变异、拆进程的自检整跑里，每族的子进程带计数预加载起，读成那一族的启动数（读不成记 `null`）；族里有一组有变异落到，就分不开，只数组数。需求测试一侧、父进程那条 `mutate --brief`、单进程整跑不数。

### 2. 自检那一侧：数、写

完整、非变异的跑（拆不拆都算）开头删旧文件，**删不掉不红、不停**（与变异一步那一份正相反：这一行只报数，最后一步还要按树身份认）；子集跑、变异跑不碰这个文件。各族零失败才写 `output/selfcheck-launches/families.json`（路径与 schema 是 `launch-rule.ts` 的 `SELFCHECK_LAUNCHES_FILE`、`SELFCHECK_LAUNCHES_SCHEMA`，即 `selfcheck-launches/v1`）：`{"schema","source","families":[{"groups":[…],"launches":n 或 null}]}`，`source` 是 `mutationSourceIdentity()`；写不成只打一行，不计失败。

### 3. 最后一步：读、打

`launches.ts` 在闸门之前先打这一行，读到什么都不改退出码。文件、树身份、路由（由 `mutations.json` 现算）交给纯函数 `idleGroupsLine(file, source, routes)`；读不出交 `undefined`。

### 4. 这一行怎么算、怎么打

文件形状不对、不是这棵树上数的、算不出路由，各打一句数不出来的话。其余打「有启动但没有变异的组（自检，只报数）：整族没有变异落到、起过进程的 N 族、M 组共起 X 次，不含 git；最多的：…；…按族分不开的 K 组不在其内；…没拿到计数的 J 族不在其内」：「最多的」前五、并列按族名，只在 N 大于 0 时打；最后一段只在 J 大于 0 时打。不判红。

### 5. CI 里打出 runner 的 CPU

`check.yml` 最后一步 `lscpu`，`if: always()` 与 `continue-on-error`：红了也照跑、读不到也不红，排在最后好让只取日志末尾时也看得见。同一份代码在不同型号上一起变快变慢，是机器的事，不是代码的事。

## 三十五、树内的启动数摘要

### 1. 补的是什么

`output/` 不进仓库，在线内的涨不在 diff 里。所以每种配置的数落进 `scripts/check/launches.json`、随 PR 的 diff 走：对不对得上由机器比，涨了值不值由人读。

### 2. 文件长什么样

- 一种配置一行，从启动数文件的 `tally` 派生：`config`、`launches`、`stopping`（会提前停的条数）、`running`（不提前停的条数）、`maxPaid`（付得最多的一条 `{"id","paid"}`，并列取 id 小的，没有是 `null`）。另有 `findings`（原样、原顺序、只重排键）与 `schema`（`mutation-launch-summary/v1`）。**不带 `head` 与源码身份**，免得每条改了 `.ts` 的 PR 都撞同一行。
- **序列化逐字定死**（`--write` 写的就是这样）：顶层 `configs`、`findings`、`schema` 依次、两格缩进；`configs` 按 `config` 排，每项压成一行、四格缩进；压成一行时键按 `<` 排（递归到嵌套里），不加空白，字符串照 `JSON.stringify` 转义；末尾一个换行。
- 冲突时不手挑：合进主干、重跑变异、再 `--write`。

### 3. 谁写

`npm run launches -- --write`：照第二十一节第 2 小节六条核启动数文件，再核 `tally` 每项（对象、`config` 非空不重复、几个数是非负安全整数）。都过就写、打「启动数摘要已写回 scripts/check/launches.json：N 种配置」、以 0 退出；不过、或写不进，不写，打「✗ 启动数摘要没写：…」、以 1 退出。带 `--write` 只做这一件事。写之前要在这棵树上跑过变异；写它不改源码身份。

### 4. 怎么比，打什么

在第三十一节那行之后、闸门之前打一行。**相同就是逐字节相同**：树内文件照 UTF-8 读（BOM 不去），与现算的全文逐字比。依次判：

1. 这一跑现算不出来：`启动数摘要（只报数）：这一跑现算不出来（原因），不比`
2. 树内没有或读不出来：不在主干上（含无从判断）是第四十四节的乙，红；在主干上打 `启动数摘要（只报数）：树内没有 scripts/check/launches.json，不比`
3. 相同：`启动数摘要（只报数）：树内 scripts/check/launches.json 与这一跑现算的相同，N 种配置`
4. 不同、不在主干上（含无从判断）：第四十四节的丙，红
5. 不同、在主干上：`启动数摘要（只报数）：树内 scripts/check/launches.json 已过期（差别），下一条 PR 须 npm run launches -- --write`

**差别**：按 `config` 对上两边（树内那项只取五个键再压成一行比），写成「变了 a 种、多了 b 种、少了 c 种：前五种配置键」，`findings` 不同末尾接「；findings 也不同」；都一样时「配置与 findings 都一样，差在别处，不是 --write 写的」；树内文件认不得（含带 BOM 的）时「认不得树内的文件」。

### 5. 升红

已升（第四十四节）。数法：从 #335 合入起，主干第一父链上 push 那一跑连着 10 跑都打第 3 句，中间一跑没打就重数，只改文档的也算。

### 6. 死亡条件

> **什么条件下退成只写文件、不核相等**：本记录末尾追加过一块，记下下面两件事之一：真树上某一跑报出「启动数不确定」；或 CI 上某一跑打出树内摘要与现算的不同，而这棵树与另一棵在 CI 上打过相同的树，`scripts/` 下的 `.ts`、`scripts/check/mutations.json`、`package-lock.json` 与 `scripts/check/launches.json` 都一字不差，两跑的 `findings` 里也都没有 `missing`。那时这份数不再是这几样文件的函数，判红会变成按运气红。

> **什么条件下整个撤掉**：第六节第二条成真（变异按点名的用例路由，文件退化为一配置一条；或需求测试的选组也能提前停）。撤第六节的那条改动，同时删掉本节的文件与比对。

拆分以后，「本记录末尾」指历史文件末尾（ADR-211 第一节）。那一块记下两跑的提交号与树（PR 上那一跑测的是合并提交，PR 关掉以后取不回来，所以 PR 上的跑另记 PR 的头与当时主干的提交号，好重建它）；核两棵树 `A`、`B` 用这条命令，以 0 退出就是一字不差：

## 四十七、仓库的行尾规范（2026-10-23，#371）

`.gitattributes` 两行：`* text=auto eol=lf`，后面留着 `scripts/check/launches.json text eol=lf`（后面的说了算）。

- git 判成文本的文件，入库存 LF、检出写 LF，`eol=lf` 压过 `core.autocrlf`，Windows 上也一样。
- 例外：判成二进制的（带孤立 CR 或 NUL）原样不动；已经以 CRLF 入库或经合并带进来的，`text=auto` 不转（`launches.json` 那一行是 `text`，没有这个例外）。开了 `core.safecrlf=true` 的人 `git add` CRLF 新文件会被拒。
- 已检出成 CRLF 的旧工作区不会自己变；先保存本地改动，再重新检出一次。只在 Linux 上模拟过，没在真的 Windows 上跑过；`scripts/test.ts` 的行尾夹具自建临时仓库，不受影响。
- 行尾规范只管入库与检出，不改摘要的比法（照旧逐字节；树内是 CRLF 时摘要那一行打「差在别处」，PR 上红），也没有把别的已入库文件归一化。
- 那条 PR 登记的两张欠条：行尾夹具注释那张已在 #404 还上；入库 CRLF 样本那张见下一节。

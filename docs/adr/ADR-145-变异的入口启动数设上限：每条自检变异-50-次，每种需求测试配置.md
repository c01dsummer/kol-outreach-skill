# ADR-145 变异的入口启动数设上限：每条自检变异 50 次，每种需求测试配置启动乘条数 100，不设豁免

- 日期 · 2026-10-12 · 需求所有者在 #302（ADR-144）那条线程上批的
- 类型：**产品取舍**（需求所有者裁决）；与 ADR-97 第四节「不加成本闸门」的四条理由相左，逐条回应在第五节；ADR-99、ADR-120、ADR-121 里几句相近的话说的是各自的范围，与本条不冲突（第五节）
- 触发它的事实：#294 到 #301 这条功能线让 main 上 `npm run check` 从 16:37 涨到 30:42，几乎全部来自两种配置：一条自检变异要先付它点名的断言之前那一大段无关前缀，一个不提前停的需求测试组每加一次启动就乘以全组条数（ADR-144 开头三条）。同一机制这是第四次（ADR-97、ADR-120、ADR-131、ADR-144），前三次都是事后拆组。启动数在同一棵树上逐次相同（第一节末），秒数在不同 runner 上差 ×0.6–×1.6
- 冲击的需求：无。管的是检查链自己
- 结论：采纳。**规则一**：每条会提前停的变异（今天就是自检变异），在它点名的断言出结果之前要付的入口启动不超过 50 次。**规则二**：每种不提前停的配置（今天就是需求测试的选组配置），配置内启动数 × 选它的变异条数不超过 100。超线就红，**不设豁免**；PR 上判红，主干上只报数。分三片落地（第八节），本条这条 PR 是第一片：判定模块、它的测试与变异。没有入口，没有一项检查的结论因它而变；变异那一步多跑 18 条 `by: test` 的变异、多一种配置（`h-launch-rule`，组内 0 次启动）
- 理由：第一到第五节
- 连带改动：`scripts/check/launch-rule.ts`（新）；`scripts/check/mutate-rule.ts` 多一个 `stopsEarly`，`scripts/check/mutate.ts` 的 `stopIfSeen` 改用它；`scripts/test.ts` 新组 `h-launch-rule`；`scripts/check/mutations.json`；`docs/ARCHITECTURE.md` 锚点表；ADR-97、ADR-99、ADR-120、ADR-121 末尾的说明，ADR-129 末尾的重审条件修正；本记录及生成的索引

## 一、数什么

**单位。** 验证者进程（`selfcheck.ts` 或 `test.ts` 那个进程本身）经 `spawn`、`spawnSync`、`execFile`、`execFileSync`、`exec`、`execSync`、`fork`（含 `exec`、`execFile` 的 promisify 版）**直接**起的子进程，**不含 git**。`sh -c`、`node -e` 都算，不只是 `process.execPath`。孙进程不单独算（第七节第 3 条）。本记录里说的「启动」都是这个单位。

**在哪数。** 变异一步的正常基线：每种选组配置本来就在没施变的源码上跑一次，不提前停，保留全部输出。数就在这一跑里数，**不加任何启动**。全跑的变异没有这一跑（`mutate.ts` 把它们记进「整跑」就跳过），见下面第三条。

**每条变异的付费启动 `paid(m)`**，在 m 所在配置的正常基线里数：

1. **会提前停的变异**：m 的 `kills` 里每条标签**末次打印**时，验证者已经起了几次；取其中最大的。取末次（上界）不取首次（下界）：两种都确定，但下界有盲区 —— 在循环里打印多次的标签，往首次打印之后加启动不改变下界，真实成本却变了。交接文档在 `05de0f1` 上量过，两种取法判出的超线集合相同，所以上界不多报。
2. **某条 `kills` 标签在基线里一次也没打印**（标签清单认得它，但这一跑没走到那个分支）：见齐就停永远凑不齐，变异会跑到底，`paid(m)` 记为**整个配置的启动数**。不记 0，不跳过。
3. **全跑变异**（没有选组）：拿不到计数，**按超线判红**，报错写明「全跑变异没有基线计数，按规则视为超线」。不记 0、不跳过、不排除。今天 0 条（`mutate` 的「整跑 0 条」）。另一种做法是给全跑配置补一次整跑基线，那要多花启动，不选。
4. **不提前停的配置**：配置里每条变异都跑完全程，按配置判规则二，乘数是这个配置的启动数与选它的变异条数。

**「停不停」与见齐就停共用一个谓词。** `mutate.ts` 的 `stopIfSeen` 开头那个条件（有 `kills`，且不是「需求测试 ＋ 选了组」）抽进 `mutate-rule.ts` 成为 `stopsEarly(verifier, kills, only)`，`stopIfSeen` 与判定模块都调它。不这么做，判定模块立的是一条自己管不到的规矩：将来改了停法，账面上的「会停」与实际不停各说各的。

**一行打印归到哪条标签。** 一行 `✓`／`✗` 去掉记号后的正文，归到**最长的**那条声明标签 `L`：正文等于 `L`，或以 `L：`、`L（` 开头。最后这一种是 `runBoth` 打的 `✓ L（按预期以退出码 N 结束）`。这与判变异被抓到的 `killsMatched` 不同（它只认 `L` 与 `L：`，而且只看 `✗`），所以不复用它。取最长的，是因为一条标签可能是另一条的前缀，归错了就是把一条的成本记到另一条头上。

**为什么数得准。** 交接文档第 5.2 节的实测：`05de0f1` 上 115 种配置各跑 5 次（3 轮、worker 目录复用顺序不同），路由启动数、每组启动数、启动序列、每条标签首次打印时的启动数、1171 条变异的 `paid`，5 次完全相同；另 9 个历史提交重跑的配置逐次相同；同一组在不同配置里的启动数完全一致。ADR-144 第三节在 `bf4e708` 上量的二十种配置也都只跑一次就与路由对得上。秒数做不到这一点：同一份代码在不同 runner 上差 ×0.6–×1.6，正常与劣化之间的空隙最好也只有 1.17 倍。

**限定。**

- **只数直接子进程。** 整棵子树不确定：`resume-progress` 两次分别是 347 与 340，差值正好是 tsx 的 esbuild 服务进程数，取决于转换缓存。
- **git 不算。** 否则 `h-mutation-maintenance`、`h-check-rules` 这类按 git 子进程算的组会排到最前，而 git 的单价与入口启动差两个量级。
- **只在一种环境里验证过**（Linux、Node 22.22.0、4 核、root 下去掉 DAC 能力）。CI 上是否逐条相同，是第二片的验收（第八节）。
- **确定性只对今天的树成立。** 今天组内的启动全是同步等，标签按程序顺序打印。将来要是有组异步起子进程、标签按完成顺序打印，计数可能随时序变。所以超线时只对超线的那个配置**再跑一次基线**确认；两次不同，报「配置 X 的启动数不确定」，不报「超线」。这一条连同比对两次计数的函数都在第二片接线时做。

## 三、不设豁免

超线只有三种改法：

1. 拆组（ADR-131、ADR-144 的做法）；
2. 把覆盖整个矩阵的一条断言改成每个用例各一条 —— 这本来就是 `process/4-VERIFY.md` 的要求；
3. 把真入口用例移出需求测试组（ADR-120 第 51–55 行的做法），通常移到自检。

**少写变异不是改法。** 规则二按「启动 × 条数」判，条数直接降乘积；规则一下，根本不写那条会超线的变异也就过了。失败信息与本记录都把它列为不接受的改法；它在机器上看不出来（第七节第 6 条）。

**真要调高 50 或 100**：改 `launch-rule.ts` 里的常量、写决策记录、由需求所有者批。

**为什么不设豁免。** 体量闸门在 #7 一条 PR 上问了 15 次「能不能拆」，15 次都由写代码的同一方自己写理由放行（ADR-64）；豁免本来就写在作者自己的提交信息里，此后主干上带 `size-ok:` 的提交又有 85 个（`git log origin/main --format=%B | grep -c '^size-ok:'`，按 `81a0e02`）。写代码和批豁免是同一方时，出口的价格是零。豁免还会被当先例引用：#290 的 `size-ok:` 理由写着「同 #253 的先例」，而 #253 正是 review-cli-entry 那次劣化。需求所有者在「超线必须写说明」（交接文档第 5.8 节方案丙）与「超线就红」之间选了后者。

## 四、PR 上判红，主干上只报数

PR 的 CI 跑在合并提交上，没有合并队列。两条各自在线内的 PR 干净合并后，可能一起超线：一条往某组前段加启动，另一条加一条点名该组靠后标签的变异；或者一条往需求测试组加启动，另一条往同一组加变异。所以照体量闸门（`size.ts` 的 `onTrunk`）：HEAD 就在主干上时只报数、不判红。

**这只让主干自己那一跑不红，不让在途的 PR 不红。** 这条规则看的是整棵树的状态，不是一条 PR 的增量：主干一旦超线，之后每条 PR 的合并提交里都带着那一组，照样红，直到一条拆组的 PR 合进去。这是不设豁免的代价，写明而不绕：主干上的计数一报超线，就按 `process/6-INTEGRATE.md`「主干红了」的优先级处理 —— 先开拆组的那一条，其余在途 PR 等它合了再把主干合进来。

## 五、取代哪几处，为什么

按字面重读之后（第十二节第 4 条），与本条相左的只有 ADR-97 第四节。别的几句相近的话说的是各自那条改动的范围，或者只说秒数，与本条不冲突。各自末尾追加的是说明，不是取代，原文都不改：

| 位置 | 原文说的是什么 | 与本条 |
|---|---|---|
| ADR-97 第四节 | 拒「一条改动允许让链慢多少秒／最多加几条自检负片」那种闸门，给了四条理由 | 四条理由对按成本判通过一般成立，本条逐条回应（下面）。结论②的两种闸门本条都不加：不按秒数，也不限一条改动加几条负片；规则二里的条数只是启动数的乘数 |
| ADR-97 第五节「处置是压单条负片的成本，不是给改动配额」 | | 照旧成立：本条不按一条 PR 让成本涨了多少判，只限每条变异的成本 |
| ADR-99 第 416 行 | 秒数账单「只是参考数：不拿它判任何事」 | 不冲突：启动数不在那张账上，账单照旧只是参考数 |
| ADR-99 第 541 行末句 | 「这里只引用现有约定，不新增性能阈值或增长闸门」 | 不冲突：「这里」指那张欠条自己 |
| ADR-120 第 26 行 | 主语是「解释」：解释不改实际执行、正常源码基线这几样 | 不冲突。第二片要在正常基线那一跑里注入计数预加载，那一跑的环境变了；接线证明里核同一配置有无预加载，✓／✗ 行序列与退出码逐行相同 |
| ADR-120 第 35 行、ADR-121 第 25 行与第 48 行 | 那两条改动交付的报告与 `started` 字段只提供原料，缺了只表示成本未知，不改变旧变异判定 | 不冲突：本条的计数是另一份（第二片的预加载），缺了由本条判红（本节末「数据缺失不放行」）；`started` 与秒数成本照旧缺了只表示未知 |

只说秒数的几处同样不冲突，只是表述要对齐，在接进检查链那一片改：ADR-120 第 23 行、ADR-121 第 14 行、ADR-129 第 48 行；`docs/ARCHITECTURE.md` 里「报告只提供评审原料，不增加性能通过判定」「成本观测不重复启动基线、不参与归因或认领资格」「不设硬秒数闸门」三句；`docs/SYNC.md`「改变变异配置使用、基线复用或经过时间报告」那一行；`process/6-INTEGRATE.md`「不设跨机器通用的秒数闸门」那句；`jobs-rule.ts`「配置成本观测（纯汇总；不决定检查通过）」与 `mutate.ts` 账单头上「只是参考数，不拿它判任何事」两处注释。按句引、不按行号，因为同一片里加减行就会挪（ADR-64 第 251–252 行）。在它们说的那件事真变了之前改，文档说的就不是当时的行为。

**逐条对 ADR-97 第四节的四条理由：**

1. **秒数只在那台机器上成立（ADR-75）。** 对启动数不成立：第一节的实测逐次相同；ADR-99 第 101–104 行本来就把「行数、变异数、判据数」归为树的函数。**另一半照旧成立**：删掉 `NODE_COMPILE_CACHE`、把 `jobsWanted` 改成恒为 1，仍然一条都不会红 —— 本条不管单次启动有多贵（第七节第 2 条）。
2. **核不了的死亡条件比没有更糟（ADR-85）。** 本条的两条死亡条件都对着仓库核得了，见第六节。
3. **体量闸门当不了先例。** 前半句「判据是行数，数得出来、和机器无关」现在正好适用于启动数；后半句「豁免全部自批」成立，所以本条不设豁免。
4. **闸门自身的成本是乘性的。** 本条不加启动；判定模块的变异全部 `by: test`、在进程内验证，每条 0 次启动。ADR-97 担心的「最贵的 `by: "selfcheck"` 那一族」不会出现：变异的基础设施本来就不能由 selfcheck 验证（`verifier-rule.ts` 的 `selfVerifying`）。

**对 bitter lesson（ADR-97 当时的约束）。** 数一个数属于该建的「替代跑的」；「这段前缀该不该付」属于不建的「替代读的」，所以本条只数、不判前缀必不必要。50 与 100 是人放进去的知识，与体量闸门的 `BUDGET` 一样。真正符合它的结构解，是把每条变异路由到它点名的用例而不是整组，被组内共享状态（ADR-131）与运行时成本（ADR-99）挡着；它写成撤掉的条件。

**数据缺失不放行。** 没先跑变异一步、计数文件的树身份对不上、某种配置的计数缺了，判定一律**报错**，不当成通过。不这样，删掉数据文件就等于关掉闸门。计数在任何情况下都不记成 0，只能是「未知」，而「未知」是红的。

## 六、死亡条件

> **什么条件下退成只报数**：主干上的计数报出「启动数不确定」时 —— 同一棵树、同一种配置的两次正常基线计数不同（第一节末）。那时启动数不再是树的函数，本条的前提没了，判红会变成按运气红。

> **什么条件下整个撤掉**：变异按点名的用例路由（不再按整组），或需求测试的选组也能提前停，成为现实时。前一种让规则一要拦的那段前缀不存在，后一种让规则二要拦的乘数不存在；两种都能对着代码核（`group-rule.ts` 的选组单位、`stopsEarly`）。

不写「连续 N 次运行」（没有东西能数，ADR-85），也不写「豁免占比」（本条没有豁免）。

## 七、不覆盖的

绿灯不说明下面这些：

1. **进程内变慢。** #300 合入那一跑里约 23% 的变异耗时在组内 0 次启动的配置里（`h-mutate`、`h-group`、`h-spec`、`h-jobs`），本条对它们什么也不说。
2. **单次启动变贵。** 换加载方式、丢编译缓存、更重的入口，次数不变。
3. **嵌套启动只算 1 次。** 控制脚本、`sh -c` 包着的启动；`h-selfcheck-shard-entry` 记 2 次，底下实际 31 个进程。
4. **每条都在线内、整组中等程度地胀。** review-cli-entry（13 条 × ≤ 39）那种，单条上限抓不到。四次劣化里 ADR-131 那次本条封不住。
5. **变异以外的耗时**：正常基线本身、独立自检的关键路径。
6. **少写变异。** 一般验收判据少一条负片，审计只对红线与检查模块强制「有测试、有变异」，没有东西会报。

第二片会加两行只报数：组内不起进程的配置的自归一计时，与「有启动但没有变异的组」的启动数。它们不判红。

// scripts/check/mutate-rule.ts
/** 见齐就停的条件：有 kills，且不是「需求测试 ＋ 选了组」。verifier 是 VERIFIERS 里的那一项（VERIFIERS.test、VERIFIERS.selfcheck） */

`launchFindings` 的规矩，逐条可测：

- `stopsEarly` 为真且 `only` 有值的变异，按规则一：`paidLaunches(kills, 它那种配置的基线, 那个验证者的声明标签) > 50` 时报 `paid`。等于 50 不报。
- `stopsEarly` 为假的变异（需求测试 ＋ 选了组），按配置归拢：`基线的 total × 这种配置的变异条数 > 100` 时，这种配置报一条 `product`，`ids` 按 id 排。等于 100 不报。

- git 不在计数里是计数那一侧的事：判定模块拿到的 `total` 与 `launched` 已经不含 git。

## 十三、第二片：接上计数，只报数（2026-10-12）

第二片把计数接进变异一步：每条 PR 与主干上的 `mutate` 都打出每种配置的启动数，以及照第三片的判法会报什么；`mutate` 的退出码不因它变。第八节第 2 条列的事情里，**第七节末那两行只报数挪出这一片**：「有启动但没有变异的组」不在任何一次正常基线里（没有变异路由到它就不跑），要数它得多跑或者按调用点把启动归到组，两样都不是这一片的事；组内不起进程的配置的自归一计时要拿每条变异的耗时去配计数，是成本报告那一侧的改动。两行都只报数、不挡闸门，另开一条 PR，不排在第三片前面。

**这一片按体量拆成两条 PR**，同样一条合了再开下一条。第 1 到第 4 小节合在一条里，源码一类要四百出头（线是 350），测试一类连同变异清单（一条变异约十行）要六七百行（线是 450）：

- **2b，预加载与接线**：`launch-preload.ts` 与 `h-launch-preload`、它的变异，第 2 小节（变异一步的接线、输出与文件）、自检组 `launch-count-entry`、自检闭包的种子、`ARCHITECTURE.md` 的计量语义与 `SYNC.md` 那一行，以及第 5 小节的验收。切法是「起不起进程」：2a 全在进程内、组内 0 次启动，2b 是真起进程的那几样。

### 1. 数的那一侧

**预加载 `scripts/check/launch-preload.ts`**，经 `NODE_OPTIONS` 的 `--import` 加载。它也在 tsx 的壳里加载，那里没有 tsx 的转换，靠 Node 自己去掉类型，所以它只 `import` `node:` 内建。

- **只认一个环境变量 `LAUNCH_COUNT`**，值是 JSON：`{"log": 日志路径, "target": 验证者脚本, "options": 原来的 NODE_OPTIONS}`；原来没有 `NODE_OPTIONS` 就不写 `options`。只在 `process.argv[1]` 与 `target` 的真实路径相同的那个进程的主线程里启用：tsx 壳里不启用；验证者进程里的 worker 线程（tsx 冷缓存时从那里起 esbuild）也会加载它，不启用，那里起的进程不计（交接文档第 5.5 节「数不到的情况」）。启用后删掉 `LAUNCH_COUNT`，把 `NODE_OPTIONS` 还原成 `options`（没有 `options` 就删掉），验证者起的子进程什么也不继承。
- **包住七个函数**（`spawn`、`spawnSync`、`execFile`、`execFileSync`、`exec`、`execSync`、`fork`）与 `exec`、`execFile` 的 `util.promisify.custom`，然后调 `module.syncBuiltinESMExports()`，让具名导入也拿到包过的。包过的函数名字、返回值、抛出的东西都与原来一样。**深度保护**：在一次被包住的调用里面再调到的不记（`exec` 内部走 `execFile`，只记一次）。
- **记的是调用次数**：调用那一刻先记、再调原函数；进程起没起来都算一次。
- **日志**：每行一个 JSON，按验证者进程里发生的先后追加。
  - `{"t":"L","api":"spawnSync","file":"git"}`：一次启动。`api` 是七个名字之一（promisify 版记成它的原名），`file` 是第一个参数转成的字符串；选项里 `shell` 为真时多一个 `"shell":true`。
  - `{"t":"O","line":"  ✓ 甲"}`：往 stdout 或 stderr 写完的一整行（不含换行），去掉行首空白后以 `✓ ` 或 `✗ ` 开头的才记。两股各自按换行切，没写完的半行不记（与 `mutate` 见齐就停只认整行一致）。
  - `{"t":"E","launches":L 行数,"prints":O 行数}`：在 `exit` 事件里写，**之后什么也不再记**。验证者自己挂在 `exit` 上、排在它后面打的行不算打印过 —— 点名那条的标签要是只在那里打，付费按整个配置算，偏大，不偏小。
- **只用加载时拿到的 fs 函数**（需求测试里有几处会临时换掉 `fs.*`）；写日志出错一律吞掉，不打扰验证者。少写的那一行会让 `E` 的两个数对不上，读的一侧判认不得。

**读日志的纯函数在 `scripts/check/launch-count.ts`**（下面第 3 小节）。**git 的口径**：`api` 是 `spawn`、`spawnSync`、`execFile`、`execFileSync` 之一，没有 `shell`，`file` 按 `/` 与 `\` 切开后的末段是 `git` 或 `git.exe`，这一次是 git，不算。`exec`、`execSync` 与带 `shell` 的，验证者直接起的是 shell，算 —— 第一节「`sh -c` 都算」，与交接文档附录 D 的工具按可执行文件名归类的结果相同。今天两个验证者里没有一处 `exec`、`execSync` 或 `shell`。

### 2. 变异一步怎么接

- **只在正常基线那一跑注入**，变异运行不注入。日志写在 `.check-cache/mutate-jobs/` 下、一种配置一份，那一跑一结束就读，随这个目录一起删。
- 全部正常基线都绿了以后：`launchFindings` 判一遍；`launchRecheck` 列出的配置（有 `paid` 或 `product` 的）各**再跑一次正常基线**，同样注入；`settleLaunches` 拿第二次的计数确认；`launchTally` 汇总。没有发现时不多跑任何东西。有基线没绿时 `mutate` 本来就以 1 退出，不报计数。
- **输出**，都在「子集选跑 … 条」那一行后面：
  1. `tallyLine` 那一行；
  2. 有发现时，一行「照第三片的判法会报下面这些（这一片只报数，不判红）：」，后面是 `launchReport` 的每一行，各缩进四格；
  3. 一行 `MUTATION_LAUNCHES_JSON ` 接单行 JSON：`{"schema":"mutation-launches/v1","head":…,"source":…,"tally":[…],"findings":[…]}`。`head` 是维护比较的那个 head 提交；`source` 是成本报告里那份 `sourceIdentity`（取不到时是 `null`）。CI 日志里留下这一行，第 5 小节拿它与本机对照；
  4. 文件 `output/mutation-launches/launches.json`：上面那个对象，外加 `baselines`（每种配置第一次的计数）与 `again`（重跑的，没拿到计数的记 `null`）。第三片的判定读这个文件、先核 `source` 与当时的树对不对得上。
- **退出码不因它变**。它不改任何一条变异的结论，也不改成本报告；`mutate.ts` 账单头上那句「只是参考数」与 `jobs-rule.ts` 的那句注释留到第三片（第五节）。

## 一、触发它的事实

ADR-112 第七节登记的欠条，正文原文：

> probe 与 collect 都不校验 `tasks` 的形状 —— 缺 `tasks`、`tasks` 不是数组、元素为 `null` 时 probe 以退出码 1 结束并带
> `TypeError` 与堆栈（ADR-108 说配置问题退出 2）；元素是空对象时 probe 退出 0，还按 Reels 发出一次不带关键词的付费请求

它的重启条件是「本条合入后另开一条 PR，先补需求（校验 `SearchTask` 已有的必填字段，不补默认值），collect 与 probe 共用一处校验」。
这里不照抄那一行的原样写法，免得欠条台账把它又数一遍。它说的「本条」（#172，F3.c–F3.e）已经合入，条件满足。

现象不止欠条写的那几种。`SearchTask` 的类型写着 `keyword`、`dimension`、`platform` 三个必填字段，
但任务配置与 `task.json` 都是从盘上读进来的原样 JSON，类型只在编译期成立：

- `platform` 写错大小写（`TikTok`）或缺席时，任务不报错，改走 Instagram Reels 付费；
- `dimension` 写错（`brand`、`Competitor`）时，任务照常付费采集，评分按原值比较，静默拿不到竞品词、场景词的加分；
- `keyword` 缺席或是空串时，发出不带关键词的付费搜索（请求参数里空串那一项被丢掉）；只有空白时，带着一串空白去付费搜索。

## 二、需求所有者的裁决（2026-09-24）

设计时有两处不能从现有条文推出、会改变用户拿到什么的，带着推荐问了需求所有者，原话「1.直接报错 2.按建议」。

**1. `tasks` 是空数组（一个任务都没有）：算不合规，直接报错。**

- 推荐原是「不算」：类型允许空数组；欠条口径只说「已有的必填字段」；空列表零请求、不花钱，「跑完了」也是真话。
- 需求所有者裁成**算不合规**。于是 D16 正文写「至少有一个任务才能开跑」，D16.a 写「缺席、不是数组或是空数组」；
  空列表与缺席、不是数组同一类处理：报错指出是 `tasks` 本身，不点名任何一个任务。

**2. 旧版本写下的、不合规的 `task.json`，续跑时：整张表校验，与新建用同一套规则。**

- 选项有三个：(A) 整表校验；(B) 只校验还会被请求的任务；(C) 旧目录豁免。推荐 A，需求所有者答「按建议」。
- 代价：已经付过费、`task.json` 里写着不合规取值的旧任务目录，续跑会以退出码 2 停下，要手改 `task.json` 或新建任务。
  这对旧目录是缩范围，所以要需求所有者点头；已点头。

## 三、由现有需求推得出的（不找人）

| 定了什么 | 依据 |
|---|---|
| `tasks` 缺席或不是数组，算不合规 | `TaskState.tasks` 的类型就是任务数组；欠条原文点名了这两种 |
| `null`、数组、原始值这类元素，算不合规 | 欠条原文点名了 `null`；`igRouteProblems` 的说明把这一判交给了「别处」 |
| `keyword` 用 `textProblem` 的口径，不修剪 | 必填文字字段只有一个判据（ADR-46 追记二）。空串等于欠条说的「不带关键词」。原词要原样保留：D15.k、U8.k |
| `dimension` 只认 F2 的四个值，区分大小写 | F2.a；评分按原值比较 |
| `platform` 只认两个值，区分大小写 | `PLATFORMS` 的说明：运行时列表与类型同源，否则校验放行一个查询侧永远匹配不到的值（ADR-25）；先例是 D15.j 只认 `"hashtag"`、把 `"Hashtag"` 判为不合规 |
| 完全相同的两个任务合规 | U8.a、D6.h |
| 整份拒绝，不跳过坏任务 | 跳过等于降覆盖，要人拍板（`process/2-CHANGE.md`）；这里不选它 |
| 跨任务报全 | `igRouteProblems` 的先例：好坏相间时每个坏任务都报 |
| 同一任务几个字段都报 | 没有先例可引。`igRouteProblems` 每个任务只报一句，是因为它那几条判定前后依赖；本条三个字段互相独立，少报就是用户拿到的信息变少（`process/2-CHANGE.md`）。判据只要求「指出几个」，不规定分几句 |
| 形状不合规时，路线问题一并报 | D15.j 要求任一不合规时指出第几个任务、哪一条不合规；已合入的判据不改含义。两条同时满足不难，不是冲突 |
| 退出码 2 | ADR-108 的退出码表：配置问题退 2 |
| `ig_route`、`as_hashtag` 不归 D16 判 | `ig_route` 归 D15.j；`as_hashtag` 不在欠条口径（「已有的必填字段」）之内 |
| pri 定 P1 | 最近的同类是同为任务配置校验的 D15.j，D15 是 P1 |
| 报错里不加「改好再续跑」 | 那是一句新承诺，要按 `docs/SYNC.md` 把全表过一遍；报错已经写明了文件、任务和字段 |

## 四、需求与拆法

新开 D16。D 类是「数据 —— 结构、取值、约束」；现有条目都不合适：D15 管发现来源，F2.a 只管维度有哪几个值，F3 管先试探、后确认。
已合入的判据不改：D15.j、F3.c、F3.d 一字不动。F3.c、F3.d 的括号里已经写了「配置读不出或不合规」，任务列表不合规属于这一类，
入口接线那条 PR 的新夹具认领它们，不改变含义。

按 `process/1-REQUIREMENTS.md` 的拆分判据，每条判据都至少有一条变异能单独把它弄坏：

- **a–e：判定的五个分支** —— 列表本身（含空数组）、非对象项、`keyword`、`dimension`、`platform`；
- **f、g、h：报全与不误报** —— 跨任务报全、同一任务几个字段都报、合规的任务（包括完全相同的两个）不点名；
- **i：校验不改写任务列表**；
- **j、k（collect）与 l、m（probe）：入口** —— 每个入口拆成「拒绝」（退出码 2、零请求、不落盘，由拒绝发生在哪一步决定）
  与「报错内容」（写出每一处问题、collect 写出文件名、路线问题一并写出，由报错那一句决定）。先例：F3.c 与 F3.d 分开。
  k、m 写了成立条件：几处输入同时出错时，入口只报最先检查的那一处（collect 先查预算），「写出每一处」只在预算合规时成立；
  「拒绝」那两条不用带条件，哪一处先错都是退出码 2、零请求。
- collect 的新建、续跑、带 `--budget` 的续跑不拆开：它们共用同一个调用点；续跑专有的风险（续跑改额时跳过校验、续跑的进度行抢在校验之前）留给入口接线那条 PR 各配一条自检负片 —— 那条 PR 之前 D16.j–m 没有认领，审计看得见。

交点只声明与 P1 的一处：三个字段缺席时不补默认值，也不从别的字段推断。区分大小写的依据是 D15.j 的先例与 `PLATFORMS` 的说明，不拿 P1 当依据。
不声明与 P3 的交点：「在任何预留与请求之前、零请求」已写进 D16.j、D16.l 的原文，由入口接线那条 PR 的自检负片来守；单元测试证不了「请求之前」。

本条 PR 只落判定（a–i 与 P1 交点）。j–m 在入口接线那条 PR 之前没有认领，审计把它们标成看得见的缺口，不是硬失败。

## 六、判定落地（本条 PR）

- 顺序：需求 → 桩（`taskListProblems` 的说明与签名，先交回空数组）→ 测试 → 实现 → 变异。
- 测试由没读过实现的上下文照需求原文与签名说明写成（读物写在测试那个提交的说明里），写完之后再由另一个独立上下文
  专挑「只坏一条判据的偷懒实现能不能全绿」，改到那一轮挑出的都补上：
  - 缺席、读到 `null`、读到字符串 `"缺席"`、读到 `7` 在同一处各调一次互相对照 —— 「缺席写明缺席」不能被规则描述里本来就有的字、
    也不能被拿哨兵值顶替缺席的写法满足（P1：没有与读到某个值是两个可区分的值）；
  - 好坏相间的长列表跨两位数序号、同值重复的非对象项、同一个对象引用出现两次，挡住「只报前几处」「按值找序号」这类写法；
  - 每一次调用前后给传入值拍形状照，挡住「顺手改写」。
- 对着桩：点名与报错那一侧都红 —— 但这只因为桩一句话都不交回，证明不了这些断言分辨得出句子写的是什么。
  合规一侧（交回空数组）与不改写传入值，桩本来就满足。这两类的红都由变异重演：
  - 判不判、报不报全：`M-D16-a`…`n`，外加空数组判合规的 `o`（对应需求所有者那一项裁决）、缺 dimension 放行的 `p`；
  - 合规一侧：`M-D16-e`、`h`、`m`，以及把路线也判了的 `q`（写着 `ig_route` 的合规任务被多点名一句）；不改写：`M-D16-n`；
  - 报错内容：缺席写成 null（`r`）、写成字符串「缺席」（`s`）、读到的 null 写成缺席（`t`）、序号从 0 数（`u`）、
    按值找序号（`v`）、读到的字符串不带引号（`w`）。
- 实现之后按 D16.a–i 与交点逐条核过测试覆盖，没有要补的断言；开 PR 前的独立复核指出缺 `p`、`q` 与报错内容那几条变异，已补。
- 变异 `M-D16-a`…`w` 都在判定层，不写 `by`，由 `test.ts` 守；逐条打进代码，D16 的断言都有红，别的 suite 不受影响。
- 按 JSON 写法写出读到的值有一个边：JSON 里写 `1e400` 这种读进来已经不是有限数的，写出来是 `null`，`-0` 写成 `0`。
  这种输入照样被拒、任务与字段照样点名，不为它多写分支。

> ⚠️ 欠条：交点「P1 优先」只在判定这一半有断言撑着（校验不补、不推断，缺席照样点名）。另一半在入口 ——
> collect（新建、续跑）与 probe 要是先把任务「规范化」（按 `ig_route` 补上 instagram、补一个默认维度）再交给校验，
> 判定层的测试看不见，而 `tension('D16', 'P1')` 的认领照样让审计把整个交点报成已守住。
> 要两份入口夹具（缺 `platform` 却写了 `ig_route: "hashtag"`；缺 `dimension`），断言退出码 2、零请求、stderr 点名那个任务的字段并写明缺席 ·
> 重启条件：D16 入口接线那条 PR（D16.j、D16.l 的入口组）

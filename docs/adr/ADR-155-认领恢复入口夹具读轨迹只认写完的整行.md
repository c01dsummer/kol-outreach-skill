# ADR-155 认领恢复入口夹具读轨迹只认写完的整行

- 日期：2026-10-22 · #357 合入后主干那一跑红了，需求所有者转来通知，本条是它的裁决
- 类型：既有缺陷（响的误红）。走 `process/6-INTEGRATE.md`「主干红了」：主干上 CI 是红的（第二节）
- 触发它的事实：[run 39742162920](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/39742162920)（第一次，树 `6453d9f`）的独立自检红在一行：「认领恢复入口夹具（夹具）：[fixture-error] interrupted-空原件被改写 command/observer/PID qualification failed：夹具记下 owned interruption trace malformed」。后半句是 ADR-132 第十节补的诊断，这次头一回把红在哪一支写了出来：受控中断那一侧的控制器串读轨迹失败（读不出与解析不了都落到这一句）
- 冲击的需求：无。只改夹具读轨迹的方式，具名断言的标签与判法一个字不改
- 结论：**采纳。** `claims-restoration-entry` 里读轨迹的两处（宿主的 `trace`、控制器串的 `rows`）都只解析最后一个换行之前的那段；宿主等进程收完之后再读一遍，判与留档都用这一份，那时进程都结束了、末尾还有一截没写完，照样判红；收尾核进程的那一处照旧要求整份写完
- 理由：轨迹是好几个进程同时往一份文件里追加的，读的那一刻别的进程正在写，读到的最后一截可能只写了一半；那是「还没写完」，不是「写坏了」（本机复现过，第一节第 4 条）。CI 上那一次是不是这样，是推断：宿主读到的每一份都解析得了，控制器那一次读坏是一时的（第一节第 3 条）；一时读坏的两种来源里，本机打得出 CI 那一句的是半行（第一节第 5 条），另一种没有排除。仓库里边收边看的读者本来就只认整行（`scripts/check/mutate-rule.ts` 的 `complete`，ADR-70；`scripts/check/launch-preload.ts`，ADR-145）
- 连带改动：ADR-132 末尾追加一块（第 486 行那张欠条响了）。索引一行。`docs/SYNC.md`「查到新事实」那一行的另两项：`docs/data-source-strategy.md` 与 `docs/SPEC.md`「尚未确定的」一节都与检查链夹具无关，不适用。检查跑什么、按什么顺序跑都没变，`process/6-INTEGRATE.md`「改验证成本时」两段都不适用：这一组每次完整检查只在独立自检里跑一遍（`docs/ARCHITECTURE.md` 第 245 行），变异那一步执行它的路由是 0 条（ADR-132 第 469 行，树 `6c80ed4` 上算的，本条没在 `6453d9f` 上重算），本条不加启动、不加等待，只改读到的那段怎么解析（第五节末条）；没有给前后实跑
- 教训：读一份别的进程还在往里追加的文件，最后一截先当成可能没写完；只有写的人都结束了，半截才是坏。往大里说是 ADR-133 那一句：拿一个代理量（这里是「整份解析得了」代「轨迹没写坏」）判一件事，先核两者在边界态（这里是「正在写」）上会不会分叉
- 同类：ADR-70、ADR-133（至少第 3 次；查的范围：--cites 前十、正文所引、grep，树 6453d9f）

本条的实测都在同一类容器里：Linux 6.18 x86_64、4 核、ext4、Node 22.22.0。复现、注入与单跑这一组以 root 跑，完整检查以 `nobody` 在新克隆上跑。下面给的都是次数，不是比率。行号凡没另说的，都是树 `6453d9f` 上 `scripts/check/selfcheck.ts` 的。

## 一、事实与证据

**1. 同一棵树在别处是绿的。** 主干 `6453d9f` 与 #357 的头 `d5f4bd6` 是同一棵树（`git rev-parse 6453d9f^{tree} d5f4bd6^{tree}` 两行相同）。那条 PR 上的 CI（run 39717135097）是绿的，本条作者以 `nobody` 在新克隆上对 `d5f4bd6` 跑的完整检查也以 0 结束。所以这次红不是 #357 改的那几行文档必然导致的。「只改了文档」本身说明不了这一点：这一组把 `docs/`、`process/` 整份拷进它的玩具仓库（第 7575–7576 行，ADR-132 第 457 行已说过）；能说明的是同一棵树在别处是绿的。

**2. 谁在什么时候读轨迹。** `git grep -n "owned interruption trace malformed" 6453d9f -- scripts/` 只列出控制器串里 `rows` 的 `catch`（第 7824–7825 行）：读文件出错、有一行解析不了，都记这一句、抛出。控制器读轨迹在两段：找协调进程那段至多 2 秒（第 7831 行），每隔 10 ms 读一次（第 7846 行）；发完信号以后先等协调进程与验证者都没了，至多 4 秒，这段每隔 10 ms 只问进程在不在、不读轨迹（第 7851 行），等完读最后一次（第 7852 行），这一次读坏了没有下一次。宿主的 `trace`（第 7652–7655 行）是同一种读法，解析不了就抛「owned claim restoration trace unavailable or malformed」；宿主在命令结束后每隔 10 ms 读一次，至多 4.5 秒（第 7887–7890 行），等完另读一次只为留档，不解析（第 7891 行）。

**3. 宿主读到的都解析得了：控制器那一次读坏是一时的。** CI 那一句是宿主等完以后判的，「夹具记下」后面是它把轨迹里 `fixture-fault` 那几行的原因拼出来的（第 7904 行）。宿主等的时候每一次读都整份解析，有一行解析不了它自己就抛上一条那句，走不到这一句。所以宿主最后读到的那一份，连同控制器读坏以后记下的那一行 `fixture-fault`，每一行都解析得了；轨迹只往后追加，控制器读到的坏东西要是留在了文件里，宿主也会读到。控制器那一次读坏是一时的，来源有两种：赶上别的进程一次追加的前半截（下一条），或者 `readFileSync` 那一下本身出错。后一种没有排除，本机的复现与注入只打出了前一种。

**4. 别的进程正在追加时，读的人能读到半行。** 下面这段起 4 个写进程，各往同一份文件追加 400 行 JSON（每行几百到一千多字节，一次 `appendFileSync` 写一整行），另一个进程不停地整份读、逐行解析，写完为止：

```js
// writer.cjs <file> <n> <size>
const fs = require('node:fs'); const [file, n, size] = [process.argv[2], +process.argv[3], +process.argv[4]];
for (let i = 0; i < n; i++) fs.appendFileSync(file, JSON.stringify({ pid: process.pid, i, pad: 'x'.repeat(size + (i * 37) % 900) }) + '\n');
// reader.cjs <file>：起 4 个 writer.cjs <file> 400 300，写完之前 setImmediate 循环：
//   整份 readFileSync，按 \n 切，最后一截非空且解析不了记「末尾半行」，中间哪一行解析不了记「中间坏行」
```

跑了 6 轮，4 轮读到过末尾半行，每轮 1 到 3 次；中间坏行 6 轮都是 0：几个进程的追加没有插进彼此中间，读的人只是可能赶上某一次追加的前半截。CI 的 runner 上没有这样量过。

**5. 在原代码上注入半行，打出的就是 CI 那一句。** 在 `6453d9f` 的副本上，让某一次读到的内容去掉最后 7 个字节（模拟赶上一次追加的前半截），单跑这一组：

| 注入在哪一次读 | 结果 |
|---|---|
| 控制器找协调进程那段的头一次读 | 红：「…qualification failed：夹具记下 owned interruption trace malformed；夹具记下 owned interruption window expired」 |
| 控制器发完信号、等完以后的最后一次读 | 红：「…qualification failed：夹具记下 owned interruption trace malformed」 |
| 宿主在命令结束后的头一次读 | 红：「owned claim restoration trace unavailable or malformed」 |

注入在第一个受控中断的场景就生效，所以场景名是「interrupted-相同原字节」，不是 CI 上的「空原件被改写」。CI 那一行只有「trace malformed」、没有「window expired」：控制器要是在找协调进程那段就抛了，协调进程没人杀，验证者等满 3 秒（第 7804 行）会再记一句「window expired」（上表第一行）。所以 CI 上那一次多半是撞在最后那次读上。正常情形下（等的那段以两者都没了为出口）那一刻协调进程与验证者都已经没了；按代码读，还会往轨迹里写的是它们上面那几层带同一份预加载的进程：子进程退出时记一行 `owned-child-exit`（第 7605 行），自己退出时记一行 `owned-exit`（第 7595 行）。这是推断，没有直接证据。

**6. 第十节那一次。** ADR-132 第十节记的 [run 38685385694](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/38685385694)（2026-10-15）也红在这一组、同一个场景，那时还没有后半句诊断，原因判不了。本条不改那一节的判断；两次落在同一个场景是不是巧合，没查。

## 二、档、路由与为什么改夹具

**档：既有缺陷。** 这种读法随这一组在 #223 进主干（`git log -S"owned interruption trace malformed" -- scripts/check/selfcheck.ts` 最早的那条），不是 #357 引入的；按 `6-INTEGRATE.md`，合入之后才到的意见没有「本改动」档。

**走「主干红了」。** 与 ADR-133 那一条不同，这次是主干上的 CI 红了，主干不可发布，所以就地修。不回滚：同一棵树在 #357 上与本地完整检查都是绿的（第一节第 1 条），这次红不是它必然导致的；回滚它也去不掉这一组读轨迹的毛病。

**按 `4-VERIFY.md`「测试失败时」：为什么改的是夹具。** 改的不是哪条断言的期望，是夹具读轨迹的方式：把「读到一截解析不了的」从「轨迹写坏了」收窄成「写的人都结束了，还是解析不了」。该红的照旧红（第四节）。

## 四、改了什么，怎么证的

- `scripts/check/selfcheck.ts`，只动 `claims-restoration-entry` 一组，四处：
  - 宿主的 `trace` 拆成读文件与 `lines` 两步，`lines` 只解析最后一个换行之前的那段；
  - 控制器串的 `rows` 同样只解析最后一个换行之前的那段；
  - `call` 等进程收完之后再读一遍轨迹，判与留档都用这一份；进程都结束了、末尾还有一截没写完，并进「qualification failed」那一句，后半句写「进程都已结束，轨迹末尾还有一截没写完」；
  - 收尾核进程的那一处（读 `trace.jsonl` 与留档的 `*.trace.jsonl`，记下见过的进程号）照旧严格：改前它整份解析，半截在末尾就抛；改后 `lines` 会跳过末尾半截，所以这里写成显式判断：那时写的人该都结束了，末尾还有一截没写完就算坏、留下夹具目录，与改前一样红在「认领恢复入口资源收尾」，读不出时的报错也与改前同一句。
- **改前红、改后绿。** 第一节第 5 条的三种注入合在一起，加到改后的副本上，单跑这一组是绿的；改后不注入单跑，也是绿的。
- **该红的照旧红。** 改后的副本里，让控制器退出时最后往轨迹追加一截不带换行的半行，单跑这一组红两条：「…qualification failed：进程都已结束，轨迹末尾还有一截没写完」，与「认领恢复入口资源收尾」（收尾那一处读到半截，留下夹具目录）。半截后面要是还有别的进程接着写，它就落在中间、成了一行解析不了的，照旧红「owned claim restoration trace unavailable or malformed」（先试的就是这种写法，打出的是这一句）。
- 单跑这一组：`npx tsx scripts/check/selfcheck.ts --only=claims-restoration-entry`。以上注入都在本机副本上做，不进仓库。完整检查的结果在本条所在 PR 的正文里。

## 五、已知代价与边界

- **没有变异守着。** 指着 `selfcheck.ts` 的变异，写 `by: selfcheck` 的会被 `scripts/check/verifier-rule.ts` 的 `selfVerifying` 拦下；写 `by: test` 的不拦（ADR-132 第 373 行那块更正），可需求测试里没有点这一组的（`git grep -n claims-restoration-entry 6453d9f -- scripts/test.ts` 什么也不打），那样的变异没有谁去杀。有人把这几处改回整份解析，或去掉「等完再读一遍」、收尾那一处的严格读，单元断言与变异都不会红，只有赶上半行时才看得见；第四节那几种注入是手工的。
- **控制器找协调进程那段晚一拍。** 那段赶上半截时，那一行要等下一次读（10 ms 以后）才算数，都在那 2 秒之内。发完信号以后那最后一次读没有下一次，它跳过末尾半截只会少看见一行；那一次判的是协调进程自己记的两种行，`owned-exit` 要有、`owned-uncaught` 要没有。少看见 `owned-exit` 就判红；少看见 `owned-uncaught` 才会把红判成绿，而协调进程先记 `owned-uncaught`、后记 `owned-exit`（都是它自己同步写的，第 7595–7596 行注册），读到了后者，前者早就写完了。正常情形下等的那段以协调进程被收走（0 号信号得到 `ESRCH`）为出口，那时它记的行都已写完。
- **宿主那一次读之后才写的行照旧看不见。** 宿主判「进程都结束了」是在读完之后；读的那一刻还活着、读完以后写了一行再退出的进程，那一行不在判的那一份里。改前判用的是等的时候最后一次读到的那一份、留档另读一次；改后判与留档共用等完以后的那一次，这个窗口比改前窄了，没有消失。
- **只管这一组。** 同一种读法（整份按行 `JSON.parse`，有一行解析不了就算坏）在 `selfcheck.ts` 别的组里还有几处，本条没逐处核它们读的时候还有没有别的进程在写，见第八节。
- **成本。** 每次 `call` 读轨迹的次数没变（原来只为留档的那一次读，改成判与留档共用），多一次整份解析；进程启动数不变。本条不说变快了。

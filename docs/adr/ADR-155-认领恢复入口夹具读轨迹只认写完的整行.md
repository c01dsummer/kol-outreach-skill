# ADR-155 认领恢复入口夹具读轨迹只认写完的整行

- 日期：2026-10-22 · #357 合入后主干那一跑红了，需求所有者转来通知，本条是它的裁决
- 类型：既有缺陷（响的误红）。走 `process/6-INTEGRATE.md`「主干红了」：主干上 CI 是红的（第二节）
- 触发它的事实：[run 39742162920](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/39742162920)（第一次，树 `6453d9f`）的独立自检红在一行：「认领恢复入口夹具（夹具）：[fixture-error] interrupted-空原件被改写 command/observer/PID qualification failed：夹具记下 owned interruption trace malformed」。后半句是 ADR-132 第十节补的诊断，这次头一回把红在哪一支写了出来：受控中断那一侧的控制器串读轨迹、逐行 `JSON.parse` 时失败
- 冲击的需求：无。只改夹具读轨迹的方式，具名断言的标签与判法一个字不改
- 结论：**采纳。** `claims-restoration-entry` 里读轨迹的两处（宿主的 `trace`、控制器串的 `rows`）都只解析最后一个换行之前的那段；宿主等进程收完之后再读一遍，判与留档都用这一份；那时进程都结束了、末尾还有一截没写完，照样判红
- 理由：轨迹是好几个进程同时往一份文件里追加的。读的那一刻别的进程正在写，读到的最后一截可能只写了一半；那是「还没写完」，不是「写坏了」。仓库里边收边看的读者本来就只认整行（`scripts/check/mutate-rule.ts` 的 `complete`，ADR-70；`scripts/check/launch-preload.ts`，ADR-145）
- 连带改动：ADR-132 末尾追加一块（第 486 行那张欠条响了；第十节那次的红法与这次是同一个场景）。索引一行
- 教训：读一份别的进程还在往里追加的文件，最后一截先当成可能没写完；只有写的人都结束了，半截才是坏

本条的实测都在同一类容器里：Linux 6.18 x86_64、4 核、ext4、Node 22.22.0、root。下面给的都是次数，不是比率。

## 一、事实与证据

**1. 同一棵树在别处是绿的。** 主干 `6453d9f` 与 #357 的头 `d5f4bd6` 是同一棵树（`git rev-parse 6453d9f^{tree} d5f4bd6^{tree}` 两行相同）。那条 PR 上的 CI（run 39717135097）是绿的，本条作者以 `nobody` 在新克隆上对 `d5f4bd6` 跑的完整检查也以 0 结束。所以红的不是 #357 改的那几行文档。

**2. 那半句只有一处会写。** `git grep -n "owned interruption trace malformed" 6453d9f -- scripts/` 只列出控制器串里 `rows` 的 `catch`。控制器每 10 ms 把整份轨迹读一遍、逐行 `JSON.parse`，有一行解析不了就记这一句、抛出。宿主的 `trace` 是同一种读法，解析不了就抛「owned claim restoration trace unavailable or malformed」。

**3. 别的进程正在追加时，读的人能读到半行。** 下面这段起 4 个写进程，各往同一份文件追加 400 行 JSON（每行几百到一千多字节，一次 `appendFileSync` 写一整行），另一个进程不停地整份读、逐行解析，写完为止：

```js
// writer.cjs <file> <n> <size>
const fs = require('node:fs'); const [file, n, size] = [process.argv[2], +process.argv[3], +process.argv[4]];
for (let i = 0; i < n; i++) fs.appendFileSync(file, JSON.stringify({ pid: process.pid, i, pad: 'x'.repeat(size + (i * 37) % 900) }) + '\n');
// reader.cjs <file>：起 4 个 writer.cjs <file> 400 300，写完之前 setImmediate 循环：
//   整份 readFileSync，按 \n 切，最后一截非空且解析不了记「末尾半行」，中间哪一行解析不了记「中间坏行」
```

跑了 6 轮，4 轮读到过末尾半行，每轮 1 到 3 次；中间坏行 6 轮都是 0：几个进程的追加没有插进彼此中间，读的人只是可能赶上某一次追加的前半截。CI 的 runner 上没有这样量过；本条按第 2 条的诊断与这里的复现推断 CI 上是同一回事。

**4. 在原代码上注入半行，打出的就是 CI 那一句。** 在 `6453d9f` 的副本上，让控制器某一次读到的内容去掉最后 7 个字节（模拟赶上一次追加的前半截），单跑这一组：

| 注入在哪一次读 | 结果 |
|---|---|
| 控制器找协调进程的头一次读 | 红：「…qualification failed：夹具记下 owned interruption trace malformed；夹具记下 owned interruption window expired」 |
| 控制器发完信号、等收完之后的最后一次读 | 红：「…qualification failed：夹具记下 owned interruption trace malformed」 |
| 宿主在命令结束后的头一次读 | 红：「owned claim restoration trace unavailable or malformed」 |

注入在第一个受控中断的场景就生效，所以场景名是「interrupted-相同原字节」，不是 CI 上的「空原件被改写」。CI 那一行只有「trace malformed」、没有「window expired」：控制器要是在找协调进程时就抛了，协调进程没人杀，验证者等满 3 秒会再记一句「window expired」（上表第一行）。所以 CI 上那一次多半是撞在最后那次读上 —— 发完信号以后，协调进程和它的子进程陆续退出、各写一行退出记录，正是追加最密的时候。这是推断，没有直接证据。

**5. 第十节那一次。** ADR-132 第十节记的 [run 38685385694](https://github.com/c01dsummer/kol-outreach-skill/actions/runs/38685385694)（2026-10-15）也红在这一组、同一个场景，那时还没有后半句诊断，原因判不了。本条不改那一节的判断；两次落在同一个场景是不是巧合，没查。

## 二、档、路由与为什么改夹具

**档：既有缺陷。** 这种读法随这一组在 #223 进主干（`git log -S"owned interruption trace malformed" -- scripts/check/selfcheck.ts` 最早的那条），不是 #357 引入的；按 `6-INTEGRATE.md`，合入之后才到的意见没有「本改动」档。

**走「主干红了」。** 与 ADR-133 那一条不同，这次是主干上的 CI 红了，主干不可发布，所以就地修。不回滚：#357 只改了文档，同一棵树在别处是绿的（第一节第 1 条），回滚它不改变这一组的行为。

**按 `4-VERIFY.md`「测试失败时」：为什么改的是夹具。** 改的不是哪条断言的期望，是夹具读轨迹的方式：把「读到一截解析不了的」从「轨迹写坏了」收窄成「写的人都结束了，还是解析不了」。负片照旧红（第四节）。

## 三、比较过的做法

| | 做法 | 去向 |
|---|---|---|
| 甲 | 两处读都只认整行；宿主等完再读一遍，判与留档用这一份，写的人都结束了末尾还有半截就判红 | **采纳** |
| 乙 | 只认整行，但不加「等完再读一遍」与「末尾半截判红」 | 不采纳：宿主最后一次轮询恰好赶上半截时，那一行会被跳过，而它可能就是一条「夹具记下」的故障；原先这种情形是红的，乙会让它绿 |
| 丙 | 解析不了就重读几次 | 不采纳：重读几次、隔多久是一个新的时间窗口，而这一组已经是带时间窗口的组（ADR-132 第十节） |
| 丁 | 让写的人改成先写临时文件再改名，或加文件锁 | 不采纳：写的人散在三段预加载、验证者与控制器里，改动面大，锁要所有写的人都配合 |
| 戊 | 宿主改为引用 `mutate-rule.ts` 的 `complete` | 不采纳：控制器是单独起的 CJS 串，引用不到，两处总要各写一份；宿主多一条到 `mutate-rule.ts` 的引用，变异的路由会不会跟着变，没核 |

## 四、改了什么，怎么证的

- `scripts/check/selfcheck.ts`，只动 `claims-restoration-entry` 一组：宿主的 `trace` 拆成读文件与 `lines` 两步，`lines` 只解析最后一个换行之前的那段；`call` 等进程收完之后再读一遍轨迹，判与留档都用这一份；进程都结束了、末尾还有一截没写完，并进「qualification failed」那一句，后半句写「进程都已结束，轨迹末尾还有一截没写完」。控制器串的 `rows` 同样只解析最后一个换行之前的那段。
- **改前红、改后绿。** 第一节第 4 条的三种注入合在一起，加到改后的副本上，单跑这一组是绿的；改后不注入单跑一次，也是绿的。
- **该红的照旧红。** 改后的副本里，让控制器退出时最后往轨迹追加一截不带换行的半行，单跑这一组是红的：「…qualification failed：进程都已结束，轨迹末尾还有一截没写完」。半截后面要是还有别的进程接着写，它就落在中间、成了一行解析不了的，照旧红「owned claim restoration trace unavailable or malformed」（先试的就是这种写法，打出的是这一句）。
- 以上注入都在本机副本上做，不进仓库。完整检查的结果在本条所在 PR 的正文里。

## 五、已知代价与边界

- **没有变异守着。** 改动在 `selfcheck.ts` 里，属于验证基础设施闭包，指着它的变异造不出来（同 ADR-133 第五节「接线不会有变异守着」）。有人把两处改回整份解析，或去掉「等完再读一遍」，单元断言与变异都不会红，只有赶上半行时才看得见；第四节那几种注入是手工的。
- **控制器晚一拍看见那一行。** 赶上半截时，那一行要等下一次读（10 ms 以后）才算数，都在它 2 秒、4 秒的等待之内。
- **宿主那一次读之后才写的行照旧看不见。** 宿主判「进程都结束了」是在读完之后；读的那一刻还活着、读完以后写了一行再退出的进程，那一行不在判的那一份里。改前也是这样，本条没收窄它。
- **只管这一组。** 同一种读法（整份按行 `JSON.parse`，有一行解析不了就算坏）在 `selfcheck.ts` 别的组里还有几处，本条没逐处核它们读的时候还有没有别的进程在写，见第六节。

## 六、欠条

> ⚠️ 欠条（档：登记）：`selfcheck.ts` 别的组里还有几处整份按行 `JSON.parse`、一行解析不了就算坏的读法（树 `6453d9f` 上第 1521、1922、7254、8027、8061、8847 行），本条没逐处核读的时候还有没有别的进程在追加；其中第 8061 行 `mutation-cost-entry` 的 driver 是边等进程边读观察文件的形状 · 重启条件：其中哪一处在任何机器上红出 JSON 解析一类的错时，先核那一刻有没有别的进程在写，有就照本条只认整行

> ⚠️ 欠条（重挂 ADR-132 第 486 行 · 档：登记）：本条只去掉了「读到半行」这一种来源；这两组单独跑时照样可能因为别的来源红（时间窗口、僵尸，ADR-132 第十节「范围」、ADR-133） · 重启条件：本条合入之后，CI 上独立自检里这两组之一再红时，先看「qualification failed」后半句指到哪一支

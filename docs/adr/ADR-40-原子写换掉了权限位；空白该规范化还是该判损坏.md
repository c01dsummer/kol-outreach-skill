# ADR-40 原子写换掉了权限位；空白该规范化还是该判损坏

- 日期 · 2026-08-28 · PR #5 拆分后第五轮自动评审，两条都成立
- 类型：**事实证伪**
- 冲击的需求：D4 · D6
- 结论：**采纳**，但两条用的是**相反**的处理方式

### 一、写回悄悄放开了权限

```
写回前: 600
写回后: 644
```

`writeFileSync` 按 umask 建临时文件（通常 0644），`renameSync` 把这个更宽松的
权限**一并装到目标上**。用户特意 `chmod 600` 过的记忆 —— 它记着谁联系过、
备注写了什么 —— 每成功写回一次就被放开一次。

这是 write-then-rename 自带的一格：rename 换掉的是整个 inode，权限跟着新文件走。
修法是把目标原有的权限位读出来、装到临时文件上，再改名。

**文件不存在时保持默认**：新文件该多严是产品决定，不在修 bug 时顺手改。

### 二、product 的首尾空白：规范化，不是判损坏

`" Foo "` 存着、`"Foo"` 查，精确相等匹配不上，「已推荐过」整条失效，
人被重新推荐一次。

**这条和 handle 的形状（ADR-37）看起来是同一类，处理却相反 —— 因为数据的来源不同：**

| | handle | product |
|---|---|---|
| 从哪来 | 提供方 API，形状受平台约束 | **用户的任务配置**，想写什么写什么 |
| 判成损坏的风险 | 几乎没有 —— 越界只可能来自手改 | **真实存在** —— 配置里带个空格，我们自己写下的记忆就被判读不出来 |
| 所以 | **拒绝** | **规范化** |

判据不是「这个字符串好不好看」，是**「这个值是谁产生的，我把它判成坏数据会不会
伤到自己」**。handle 越界只可能来自手改；product 带空格完全可能是用户配置本来
就那样，而那时候拒绝等于自伤。

纯空白（`"   "`）仍然算损坏 —— trim 之后是空的，回到 ADR-37 已经处理过的那一格。

### 教训

**同一个形状的两个问题，可以有相反的正确答案。**

上一轮刚学会「先去仓库里找证据」，这一轮差点把它用成「凡是越界一律拒绝」。
真正决定拒绝还是规范化的，不是那个值长什么样，是**它从哪来、以及判错了谁受伤**。

### 追记 · 「文件不存在时保持默认」那句 `catch` 断言了单一原因

- 第十五轮自查（五类自查第 1 类）

`writeFileAtomic` 读目标权限位那一处写着 `catch { /* 新文件 */ }` —— 读不到权限位时
一律当成新文件，把用户设过的权限换成 0600。方向与上面第一节相反（那次是放开，这次是收紧），
性质相同：**一个 `catch` 只认一种原因。** 改成只把「不存在」当新文件，
其余抛出来 —— 与 ADR-26 的 `isAbsence` 同一条规矩。

- 教训：**「达标即停」这个判断跑在什么之前，决定了它保护什么。** 跑在每次请求之前，它保护的是预算；
  跑在「每个任务都问过一遍」之后，它保护的才是策略。ADR-06 的教训是「凡是写 `if (x >= target)`
  都要问 x 和 target 是不是同一种东西」，本条在它后面补一句：**还要问这个判断跑在什么之前。**

  因为它引用的那次修复是真的

## 一、事实：轮转保证的是「页」，不是「每个词被问过」

`scripts/collect.ts` 的 `run()`：

```
for round in 0..MAX_PAGES:
  for i in state.tasks（task.json 的顺序）:
    if exhausted(i): continue
    if qualified() >= target_count: stopped = 'target'; break   ← 每一次请求之前
    search(task[i], offset)
```

那句达标判断跑在**每一次**搜索请求之前，第一轮也不例外。所以轮转保证的是
「一个词不连翻四页」，**不是「每个词都被问过一遍」**：第一轮里排在前面的任务只要把目标填满，
内层 `break` 之后外层也 `break`，后面的任务一个请求都不发。而 `qualified()` 是一个**跨平台的总数**，
`TaskState` 里没有任何按平台或按维度的配额。

task.json 的顺序由 Agent 写，没有任何文档说它有意义 —— 而本仓库几处**任务清单形状**的样例
（`skill/references/keyword-strategy.md` 的试探结果样例、`scripts/check/selfcheck.ts` 的夹具）
都把 TikTok 排在前、Instagram 排在后。**于是最常见的受害者正是整个 IG。**

⚠️ **不写成「每一个例子」。** `skill/SKILL.md` 那段续跑对话里的「剩余关键词」把
`#travelessentials(IG)` 列在首位 —— 它展示的是剩余进度而不是任务清单，但一样能被抄，
所以这里不用全称（#128 第一轮评审指出，头一版写的是「每一个能抄的例子」，那句为假）。

两个把它放大的结构性事实（都已记在 `skill/references/providers/tikhub.md`，不是新发现）：
TikTok 视频搜索每页 20 条、有 `offset` 与 `has_more`，一个词最多四页；
**IG 的 Reels 搜索没有分页游标**，一个词只有一页（约 12 条，同一作者多条还会合并成一个人），
`offset > 0` 直接返回空。所以即便顺序公平，IG 的上限也只是「每词一页 × IG 词数」，
第二轮起只剩 TikTok 在跑。

```js
/**
 * 复现用假 fetch：按真实产量建模 —— TikTok 每页 20 条、每条不同作者、都带粉丝数；
 * IG Reels 每词 12 条、每条不同作者、不带粉丝数（与实测一致）。
 * handle 由 keyword+offset 派生，保证跨页、跨词不撞。
 *
 * 写成 .mjs 而不是 .ts：`--import` 的预加载由 node 自己处理，轮不到 tsx，

 * 但照这条记录重跑的人不在那个钉子底下 —— 纯 JS 没这个问题。

const q = (u, k) => new URL(u).searchParams.get(k) ?? ''
const slug = s => s.toLowerCase().replace(/[^a-z0-9]+/g, '')
const log = []
globalThis.fetch = async input => {
  const url = String(input)
  let body
  if (url.includes('fetch_video_search_result')) {
    const kw = q(url, 'keyword'), off = Number(q(url, 'offset') || 0)
    log.push(`TT ${kw} offset=${off}`)
    body = { data: { aweme_list: [], has_more: 1, search_item_list: Array.from({ length: 20 }, (_, i) => ({
      aweme_info: { desc: `${kw} video ${off + i}`, statistics: { play_count: 5000, digg_count: 100 },
        author: { unique_id: `tt_${slug(kw)}_${off + i}`, nickname: 'x', follower_count: 20000, aweme_count: 0 } } })) } }
  } else if (url.includes('instagram/v2/search_reels')) {
    const kw = q(url, 'keyword')
    log.push(`IG ${kw}`)
    body = { data: { data: { count: 12, items: Array.from({ length: 12 }, (_, i) => ({
      caption: { text: `${kw} reel ${i}` }, play_count: 3000, like_count: 50,
      user: { id: String(i), username: `ig_${slug(kw)}_${i}`, full_name: 'y', is_verified: false, is_private: false } })) } } }
  } else if (url.includes('tiktok/web/fetch_user_profile')) {
    body = { data: { userInfo: { user: { uniqueId: q(url, 'uniqueId'), nickname: 'x', signature: 'hi', verified: false, bioLink: { link: 'https://example.com' } },
      stats: { followerCount: 20000, videoCount: 50 } } } }
  } else if (url.includes('fetch_user_info_by_username')) {
    body = { data: { username: q(url, 'username'), full_name: 'y', biography: 'hi', bio_links: [{ url: 'https://example.com' }],
      follower_count: 20000, following_count: 100, media_count: null, is_private: false, is_verified: false } }
  } else {
    body = { data: {} }
  }
  return new Response(JSON.stringify(body), { status: 200, headers: { 'content-type': 'application/json' } })
}
process.on('exit', () => { console.error(`[fake] 搜索请求顺序:\n  ` + log.join('\n  ')) })
```

## 二、四条把「少」推向「零」的连带成因

都用同一套夹具跑过。**它们各自独立**，第一页保证只修掉第一条与第二条的一半。

1. **达标停下之后 `--resume` 救不回 IG。** 续跑从第 0 轮第 0 个任务重来，那句判断在第一个请求之前
   就成立；`keywordsResumeWillRun` 返回空，于是收尾那句话说「续跑不产生新的请求」，
   而 stdout 的 `pending_keywords` 里明明还列着两个 IG 词。`collect` 只接受 `--budget`，
   **没有抬高 `target_count` 的参数**；手改 task.json 抬高之后，多出来的额度先被排在前面的
   TikTok 词翻第二、三页吃掉，IG 照样轮不到（实测目标 50→100 后续跑，TikTok 60→100，IG 仍 0）。
   而 `SKILL.md` 写着「人不够，再多找点」也走 `--resume` —— 这条路在达标停下时什么都不做
   ⚠️ **这一条只在「补全没把人筛掉」那种情形下成立，本节第 3 条讲的正是它不成立的那种** ——
   `qualified()` 在补全把真实粉丝数写回之后会掉回目标以下，续跑照样去抓。见第十三节。
2. **预算续跑循环让 TikTok 越翻越深，IG 永远不再被看。** 页数上限是**每次运行**的轮数，
   计数只在内存里；预算中途用尽时翻满四页的 TikTok 词不会被标 `done`，续跑后从 `offsets`
   接着再翻四页。IG 词在第一页之后就进了 `done`，永远跳过。实测两个 TikTok ＋ 一个 IG、
   预算只够 8 次，用尽后续跑：一个 TikTok 词累计八页，IG 零次新请求。
   这同时违反 `SKILL.md` 写的「单关键词页数上限 4 页」
3. **IG 的人按「粉丝数未知」计入达标，补 profile 之后才被闸门筛掉 —— 那时循环早停了。**
   P1.g 要求入池时未知放行，这没错；但采集期的 `qualified()` 因此对 IG 偏乐观。
   实测 IG 排前面、目标 50、假 profile 让 IG 粉丝数落在下限之下：`stopped=target`，
   累加器里 IG 24 人，交付物里 IG 0 人，总数还低于目标。
   **今天 TikTok 在前的配置走不到这条**（IG 根本没被数进去）；**第一页保证落地之后它会真的发生** ——
   处置在第六节
4. **免费额度下 IG 端点返回 402，一个 402 让整轮以出错退出，而报错不点名平台。**
   `tikhub.md` 记着 IG 端点不吃 free credit；402 不重试直接抛，入口转成 `stopped='error'` 退 1。
   TikTok 在前时，第一轮 TikTok 跑完、第一个 IG 请求就把整轮打断：profile 一个没补、
   关键词一个没标完，而 stderr 只说「余额不足」。`probe` 遇 402 也直接 `break`，
   后面的 IG 词连一行试探结果都没有。**这条与调度无关，第一次用的人最容易撞上**

| **F9.b** | 预算不够给每个任务抓第一页时，按 P3 停下（退 3、存断点），从未查询的任务如实列出，**不得为了抓齐第一页超出预算** | 同上 |
| **F9.c** | 续跑时，没抓过第一页的任务会被查询，即使当前已经达标；已抓过第一页的任务在达标后不再查询。**「续跑会去抓哪些」只此一份判定**，调度与「续跑要不要花钱」那句话共用它 | `lib` 的纯函数 → 单元断言 |
| **F9.d** | 第一页之后的分页仍按达标判断停止 | 同上 |
| **F9.e** | 任务目录里没有分页记录表时，读作「无从确认哪些任务查过」：不发请求，续跑那句话如实说明；**不得读作「都没查过」去发请求，也不得读作「都查过了」** | 入口 → 自检 ＋ 负片 |

F9.c 的后半句是结构要求，同 `needsProfile` 的先例（ADR-25）：补全循环和账单各写一份表达式时，
**先改的那边不会报错**。F9.d 是范围边界，按 ADR-67 它必须可失败 ——
一条把 IG 也翻到第二页、或者达标后继续翻页的实现让它红。
F9.e 是三态在 `task.json` 上的落点：**「没有那个键」和「没有那张表」是两件事。**

### 与红线的交点，以及三条连带的判据

| 交点 | 裁决（红线在场，结论已定，只是写下来） |
|---|---|
| **F9 × P3**（不超预算） | P3 赢。第一页保证在**达标判断**之前生效，不在**预算**之前；预算不够时照旧退 3 存断点，没抓到的按 P5 如实列出 |
| **F9 × P1**（不填默认值） | 不设任何默认的平台配额。用户没说，就只有「每个任务一页」这条机械保证；IG 占多少由 Agent 出了几个 IG 词决定，那是判断层的事。同 `docs/CONVENTIONS.md` 第 7 条对预算的处理 |
| **F9 × D6** | 续跑会去抓的 ＝ 没抓过第一页的任务 ∪（未达标时）其余未完成的任务。**D6.c 据此退役** —— 它现在的判据是「那一刻还差不差人」，而 F9.c 让第一页不受这个判断约束，于是这句为假。判据不改含义、不回收复用（ADR-67 第二节连「改窄」都算改含义），所以退役、用下一个字母。⚠️ 本行原先引的是 D6.c 的旧正文（「达标提前停下时那些词一个都没碰过，续跑一个都不会去抓」）——**那句不用等 F9 就已经是假的**，已按第十三节改掉 |
| **F9 × F1**（只问三个问题） | 不新增必问项 |

三条连带的判据，与 F9 同一批但各自独立：

- **P5.i（红线）**：`meta.json` 与 HTML 报告必须列出任务里**从未发出过搜索请求**的关键词与平台；
  「未查询」「查了 0 命中」「命中 N 人」「无从确认」四态可分，从未查询的平台不得从「平台」那一行
  静默消失；未查询的行不得带出 `0%` 这类看起来像测量值的数（渲染口径同 P1.e）
- **U3.b**：关键词表按**关键词×平台**列出任务里的每一个，包括 0 命中的与从未查询的；
  「找到」按搜索命中数计，另列「入围」，两个数不得合并
- **D6.g / D6.h**：前者接替退役的 D6.c；后者是「单关键词页数上限跨运行有效」（第二节第 2 条）

**为什么 P5.i 落在 P5 而不是 U3**：U3 管「表里有什么」，P5 管「用户会不会据此做出错误决定」。
IG 从报告里消失，运营的结论是「这个品类 IG 没人」，下次预算就不投 —— 代价由用户承担且不可逆。
**为什么不并进 P1.e**：P1.e 说的是交付表里**人**的字段，落在 `rows.ts` 的 `cell` 上；
关键词表落在另一条路径上，会独立坏掉。这正是 ADR-77 末尾那张欠条说的「三条轴之外的压平点没人守」——
关键词表就是第四处，本条给它补一条轴，但登记在 P5 名下（它是「数据边界」，不是「字段取值」）。

## 四、五处结果承诺，本条当场撤回

按 `docs/CONVENTIONS.md` 第 11 条「描述保证的那句话，没有任何检查看着」，**搜关键词不搜整句、搜全仓不只搜文档**：

```bash
git -c core.quotePath=false grep -n \
  -e '整个 IG 一' -e '每个维度都保证有产出' -e '不让第一个关键词吃掉全部配额' -e '再多找点' \
  825fd2d -- .
```

⚠️ **树钉死、范围是整个仓库**：`825fd2d` 是本条动手之前的那一棵，撤回的对象在那棵树上都还在；
`-- .` 就是全仓，不是只有文档。头一版写着「搜全仓」而命令限在 `skill docs scripts README.md`，
那两件对不上（#128 第三轮评审指出）。这一版两条命中清单我都跑过，逐行相同 ——
**但对不上的时候，改的是命令而不是那句话**，否则下一个人按窄清单核就核不出「全仓」这个结论。

命中里有五处在说一句不成立的话，本条都改成事实：`skill/SKILL.md` 的 Phase 03 那条与续跑那段、
`docs/business-requirements.md` 的「采集必须轮转」那段、`scripts/collect.ts` 的 `run()` 函数头注释、
以及 ADR-06「理由」里那句（记录只追加，所以在**末尾**追一块、开头留一行指针）。
`docs/ARCHITECTURE.md` 锚点表里 `collect.ts` 那一行**本身成立**（第一个词确实每轮只拿一页），
漏说的是「排在后面的任务可能一次都不被查」—— 那一处是**补充**，不是撤回。

同一条命令还会命中 ADR-08 与自检里的「再多找点」，那两处说的是
「`--resume` 在 render 之后不会把已采集的人清掉」—— 那一半今天仍然成立，不在撤回范围里。

**先撤回、后重申，理由与 ADR-66 同**：撤回是响的（读的人知道这里没有保证），
挂着是静默的（读的人以为有）。落地之后再改成新的保证，而且**措辞只说请求、不说产出** ——
一页可以 0 个不同作者、可以被兜底成商家号、可以补完 profile 全被筛掉。
写「每个维度才真的有产出」又会是一句没人看着的承诺。

没有任何测试或变异守着那几句话。**在 `825fd2d` 上，验证资产只有三个**：单元测试 `scripts/test.ts`、
变异集 `scripts/check/mutations.json`（数据，断言在跑它的 `mutate.ts` 里）、自检 `scripts/check/selfcheck.ts`——
`git show 825fd2d:package.json` 里 `test` / `mutate` / `selfcheck` 三条脚本的入口就是它们。带断言的源文件只有两个，
同一棵树上这条列得出来（⚠️ `\b` 不能省：少了它 `searchTikTok(` 也会命中，多列一个文件）：

```bash
git grep -lE '\b(ok|criterion)\(' 825fd2d -- scripts
```

所以下面这条扫的就是全部，退 1、无输出：

```bash
git grep -e 轮转 -e 各抓一页 825fd2d -- \
  scripts/test.ts scripts/check/mutations.json scripts/check/selfcheck.ts
```

（头一版只写了关键词、没写树也没写路径，照字面跑扫的是整个工作区、二十多行命中 —— 第十三节。
⚠️ 这条**不该**改成 `-- .`：断言说的就是「这三个验证资产里不命中」，扫全仓会把文档也算进来，
反而证不出这句话 —— #137 评审建议扫全仓，那一条没照做，改的是把范围写进散文。）
变异集里唯一碰那句达标判断的是 `M-D6-e`，它守的是相反的那件事。

## 五、登记表的条目不在本条 PR 里 —— 实测它过不了审计

变更文档原先把「ADR ＋ 登记表 ＋ 撤回措辞」放在同一条 PR 里，理由是「先把编号固定下来」。
**动手之前先把那个组合跑了一遍，它过不了。**

把 F9、P5.i、U3.b、D6.g、D6.h 加进 `docs/requirements.json`、退役 D6.c、回写 `docs/SPEC.md`，
不改任何代码与测试，然后跑整条检查链。**审计硬失败**，逐条如下 ——
判定都在 `scripts/check/spec-rule.ts`，**指那两个函数而不抄一个数**：函数是正本，数会漂。

- **P5.i 是红线的验收判据但没有认领** —— 判定在 `scripts/check/spec-rule.ts` 的
  `requirementVerdict`：`r.cat` 是红线时，每一条没认领也没豁免的判据都 `hard++`
- **F9 × P3 是有红线的交点但没有测试认领** —— 判定在同一份文件的 `tensionVerdict`：
  交点里有红线、而没有任何测试认领它，就判硬失败（**不抄它返回的那个字面值** ——
  那同样是会随代码漂的数，#128 第二轮评审指出）

（另有一处不是硬失败但值得记：`spec` 会先拦下「F9 的 adr 指向不存在的决策记录」——
**登记表引用的记录必须先存在**。这一条反而支持「决策记录先合」。）

这两处都不是可以顺手补掉的：

- 认领 P5.i 的测试要断言「报告列出了从未查询的关键词」，而那个行为还不存在 → 测试会红。

**结论：登记表的每一条跟着它的实现与测试一起进主干。** 这不是把纪律放松，是按
`process/6-INTEGRATE.md`「按验收证据切」得到的结果 —— 登记表条目的证据就是认领它的那条测试，

它不改任何行为，所以没有机器证据可给，而这正是它能独立成一条的理由（`6-INTEGRATE.md`「决策记录先于实现合」）。

### 追记 · 第二轮评审：我修第三条的时候，又犯了第三条

第一轮那三条修完之后，评审复核第三条（「算出来的数要么钉树、要么只写命令」），**没通过**。
两点，都成立：

**一、我新补的那条旁证是假的。** 为了说明「这张表不是某一棵树的偶然产物」，我写了

**我是拿另一个区间跑出来的结果推广过去的** —— 本条早几版对齐主干时跑过
`d7e20d7..73eef5f` 那一段，那一段确实为空，于是把结论搬到了 `7469901..825fd2d` 上，

**这两点合起来是一条更窄的教训**：ADR-73 说「判据落纸那一刻先拿它量一遍这条记录自己」。
我照做了一半 —— 量的是**被讲的那件事**，没量**为了修它而新写的那几句**。
**修一条「不许写没核过的数」的发现时，最容易新写一个没核过的数**，因为注意力在「把它修好」上。

## 九、第三轮评审：三条，头一条又是一句没核过的宽慰话

三条全部成立，都在本条 PR 里修了（`6-INTEGRATE.md` 的**本改动**档，第三轮）。

**一（Major）·「TikTok 词跳过了还能续」是假的。** `skill/SKILL.md` Phase 03 那条里我写着
「IG 一词只有一页，跳过了续跑也补不回来；TikTok 词跳过了还能续」。后半句没有依据 ——
而**这条记录自己的第二节第 1 条**就写着：达标停下之后 `--resume` 一个关键词搜索请求都不发。
那件事不分平台。

这一轮把两种停法各跑了一遍（夹具与命令同第一节，树钉在 `e04e736`）：

| 怎么停的 | 续跑发出的第一个搜索请求 | 被跳过的那些词 |
|---|---|---|
| 达标（`stopped=target`） | 没有，一个都不发 | 一个都没碰，`pending_keywords` 仍列着全部任务 |

⚠️ **第一行同样只是一种情形** —— 那次跑里补全没把人筛掉。筛掉之后续跑照样搜，
而且「`pending_keywords` 仍列着全部任务」这一格本身也误导：它列的是**不在 `done` 里**的词，
搜过一页的也在里面（第一行那次就有三个词搜过并贡献了全部产出）。见第十三节。
| 预算用尽（`stopped=budget`，追加 `--budget` 续跑） | 排在第 0 位那个词的**下一页** | 仍然没碰 —— 那一页就够重新达标 |

⚠️ **第二行只是预算停法的一种情形**（差一点就达标），我当时当成了全部 —— 见第十节。

两种停法都不保证补得回来，原因还不一样：达标那种一个请求都不发；预算那种会发，
但仍从第 0 个任务按 task.json 的顺序排队，`offsets` 让前面那些词接着往深处翻
（同第二节第 2 条那个机制，只是单次续跑里就看得见）。**顺序在两种停法下都决定谁被查到** ——
这让「把 IG 写在最前面」这条临时办法的理由更硬，不是更软。
修法：假的那半句删掉，两种停法各写一句，`SKILL.md` 续跑那一段补上预算那种的口径。

**同一条 PR 里第四次犯 ADR-73 那个形状**（前三次：第一轮的全称量词、第一轮那句
「一个请求都不会发」、第二轮那条推广来的 `git diff`）。四次唯一的共同点是
**写下来的那句话没有被它自己那条命令量过**。这一次与第一轮第三条还共着更窄的一层：
**两句都是「它还能怎么恢复」的宽慰话** —— 那次是「续跑不发请求」，这次是「TikTok 还能续」。
手里握着坏消息落笔时会本能地配一句「不过……」，而那半句最容易没人去核。
判据加一格：**写下「还能 X」「X 能补回来」之前先把 X 跑一遍**；跑不动就只写坏消息。

## 十、第四轮评审一条：我把那句话过度纠正到了另一头

第三轮删掉「TikTok 词跳过了还能续」之后，我在 `SKILL.md` 写下的是「**跳过的词续跑补不回来，两个平台都一样**」。
**这句也是假的**，只是错的方向反过来了。

跑了一次「目标还远」的预算停（夹具同第一节，树钉 `53f903b`）：3 个 TikTok ＋ 3 个 Instagram、
`target_count` 500、预算只够两次搜索。追加 `--budget` 续跑之后，**三个 IG 词全被查到了**，
一路跑到 `stopped=done`。所以预算那种停法下跳过的词**可能补得回来**，取决于轮到它之前会不会重新达标 ——
第九节那张表的第二行是「差一点就达标」那一种，我当成了全部。代价是实的：
**「补不回来」会让人放弃追加预算**，而那恰是那种情形下唯一管用的一步（评审点的就是这个）。
改法：两种停法分开写，预算那种写成「可能补得回来」并给出判断依据（`collected` 与目标的差）。
⚠️ 当时那句依据把 stdout 的键名写成了 `target_count`，而 summary 里叫 `target` —— 第十三节改掉了。

**第五次，而且第九节刚写下的判据漏了它** —— 那条是「宽慰句先跑一遍」，而这一句是宽慰话的反面。
真正的共同形状是**全称句**：第一轮那条「每一个能抄的例子」、这一条「两个平台都一样」，
坏消息那一侧的全称同样没人核。判据放宽成：**出现「都」「一定」「一个也不」这类全称，
就把它覆盖的情形逐个跑一遍**；跑不全就写成「看情况，判断依据是 X」。

## 十一、第五轮评审两条：一条是我上一轮的修里新埋的，一条谁都没跑过

**一 · 第十节的修里又埋了一个全称，这次在好消息那一侧。** 把「补不回来」改成「可能补得回来」时，
我顺手写了「**离目标还远时后面的词都会被查到**」—— 同样是没跑遍的全称：追加的预算不够，它照样跑不到。

两处都改成「补得回来不保证」，后面跟判断依据。

**二 · 第一节那条复现命令在别人机器上跑不起来。** 原文是
`NODE_OPTIONS="--import /abs/path/fake-fetch.ts"`，而 `--import` 的预加载由 node 自己处理、
轮不到 `tsx`；node 能不能直接吃 `.ts` 取决于版本与 flag，而读记录的人那台机器没钉版本
（仓库自己在 CI 里钉了 22 —— 这句头一版写成「本仓库没钉」，见第十三节）。
**我这台是 22.22，所以我跑得通** —— 于是「写下的命令我跑过一遍」这条判据第一次不够用：
它保证的是这棵树、这台机器上跑得通，**不保证读记录的人跑得通**。
夹具改写成纯 JS 的 `.mjs` 抄进第一节，四行换完之后重跑过一遍、逐格未变。

判据再加一格：**命令写进记录之前，先问它依赖了什么本机没钉住的东西**
（node 版本、全局装的工具、环境变量）。**自己跑得通不等于别人跑得通。**

## 十二、第六轮评审两条：我用一个核不了的版本号，去修「别人跑不起来」

这两条在 #133 上（#128 合得早了四分钟，第十一节那两条是在它后面的一条 PR 里补的）。

评审指出它把**两件事混成了一件**：22.6 引入的是带 flag 的 type stripping，不加 flag 能用是更晚的事。
**而我根本核不了这句** —— 我只有一台机器、一个版本（跑得通那个），另外那些版本我一个都试不了。
第十一节刚立的判据是「先问它依赖了什么本机没钉住的东西」，**我照做了一半**：
我发现了「依赖 node 版本」这件事，却接着自己编了一个版本号去描述它。

改法不是换一个更准的版本号，是**把版本号整个拿掉**：记录只说这条命令依赖什么
（`--import` 的预加载轮不到 `tsx`；node 吃不吃 `.ts` 取决于版本和 flag），
具体从哪个版本起以 node 官方文档为准。**纯 JS 把整个问题绕开了 —— 那才是换 `.mjs` 的理由。**
⚠️ 本节上面为说清错在哪仍然转述了一次版本（「22.6 引入的是带 flag 的」）—— 那是**引它来说明它错**，
不是拿它当依据；而头一版在同一节写了「本条不转述」，自相矛盾（第十三节）。
判据再窄一格：**核不了的事实不要替它找一个具体的数**，说清依赖是什么就够了。

**二 ·「顺序是今天唯一决定哪些词会被查到的东西」，那个「唯一」是假的。**
目标人数和预算同样决定 —— 它们决定砍在第几个，顺序决定被砍掉的是谁。
`SKILL.md` 那一处已改成后面这个说法。第九节里「顺序在两种停法下都决定谁被查到」是它的松散祖先，
那句本身不假（顺序确实在两种停法下都排队），留在原地不改。

**又是全称。** 第一轮「每一个能抄的例子」、第四轮「两个平台都一样」、第五轮「后面的词都会被查到」、
这一轮「唯一决定」—— **四次了，而且每次都在不同的位置、不同的方向**。
第十一节那条判据（出现全称就逐条跑）是对的，问题是**我总在写别的东西时顺手写下一个新的**。

## 十三、自查一轮：这条记录最核心的那句话，本身就是假的

#133 合入之后我自己派了一轮对抗式复核（六个维度并行找、每条发现再由三个不同视角去推翻它）。
它推翻了三条我以为成立的，也留下了二十多条。**其中最重的那条推翻的是这条记录的立论之一。**

### 「达标停下之后 `--resume` 一个关键词搜索都不发」—— 假的

这句话我从 #128 一路辩护到第六轮，还拿它当过「把 IG 排前面」的理由。它只在**一种**情形下成立。

**机制就写在这条记录自己的第二节第 3 条里**：达标判断跑在 profile 补全**之前**，
用的是补全前的粉丝数（未知一律放行，P1）；而 `enrichProfiles()` 跑在 `run()` 之后、
把真实粉丝数写回累加器。被闸门筛掉的人一多，`qualified()` 就掉回目标以下 ——
续跑的第一次判断因此不再成立，照常从第 0 个任务开始搜。

**我写下了机制，也写下了与机制矛盾的结论，两段隔着不到一屏。**

实测（夹具同第一节，只把 IG profile 的 `follower_count` 改成 800，低于 `FOLLOWER_MIN`；
3 个 IG 词在前 ＋ 2 个 TikTok 词在后，`target_count` 30，树钉 `origin/main`）：

|---|---|---|---|
| 首轮 | `target` | **0** | 3 个 IG 词 |
| 原样 `--resume`（目标一字未改） | `target` | **40** | 2 个 TikTok 词 —— 被跳过的词整词补回 |

**脚本自己一直是对的**：首轮 stderr 打的就是「还有 2 个关键词 没跑完，续跑会继续发请求、继续花钱」

`SKILL.md` 同一份文件里也早写着「照 stderr 说的转述，别自己下结论」—— **是我后加的散文跟它对着干。**

代价是真金白银、而且方向搞反了：照旧版那三句，Agent 会告诉用户「`--resume` 办不到，只能重新
`--config`」，让他为一次本来续跑就能拿到的补采**把已经付过的请求再付一遍**。

改的地方（同一句话的六份副本，`docs/SYNC.md` 那条走查链上每一站）：

**实现一行都没动** —— 它从来就是对的。

**它们没有到期**，而且都要等有人拿真实品类跑过才知道。

**这条修掉的是「零」，修不掉「少」。** 用户最早报的是「IG 召回很少、甚至会没有」——
「没有」今天有了机械保证，「很少」没有：一个 IG 关键词只有一页（约 12 条），
补完 profile 还可能被粉丝闸门全筛掉。要 IG 多，得多出几个 IG 关键词，
那是判断层的事 —— 本条不设任何默认的平台配额（F9 × P1 的裁定）。

## 十五、盘上先记实话：独立复核推翻了「不必加字段」，三轮下来的形状比结论更值钱

第五节那张表写着「`task.json` 记每任务的查询状态／页数／命中数，`collect` 写它」。
头一版实现推翻了它，理由写得很自信：F9 已经把这份记录建好了 —— `offsets` 的取值本身
就是四态（整张表缺失＝无从确认／有表没这个键＝未查询／值为 0＝查了没返回／值为 N＝返回 N 条），
而 `offsets[i]` 在数值上就等于累计返回条数，**因为 ADR-06 第 1 条把 offset 定成了
`offset += items.length`**；再存一份就是同一个数存两遍，这仓库最忌那种。

**ADR-24 要求的独立复核把它推翻了**，两处反例都当场跑过。

### 甲 · 第一轮复核：`offsets` 兼不了那两个职

**一 · `offsets` 只在 `search()` 正常返回之后才写，而任务循环没有 try。**
于是「请求发出去、钱扣了、在写它之前抛了」这一整类路径全都塌回「没查过」：
供应商换了响应结构（200 已返回、`charge()` 已计费且不退，`pickList` 认不出抛出）、
IG 兜底撞上预算、进程被杀。盘上于是对着一个**已经付过钱**的关键词记着「没问过」——
续跑照原样再买一次同样的第一页。

**二 · `offsets[i]` 不等于累计返回条数。** IG 的兜底路径（reels 解析不出人就改搜账号名）
把第一次请求的条数整个丢掉，只交回第二次的。实测：reels 返回 8 条、两次都计了费，
而盘上记着「拿回 0 条」，读作「这个词一条内容都没有」。

**所以回到第五节的原计划：三个事实三张表。**
`offsets` 只答「下一页从哪儿接」；`answered` 答「让供应商应答过几次」（**写在 finally 里**，
取预算计数器的增量 —— 它在 `charge()` 里加、非 200 时 `refund()`，数的正是真发出去且付了钱的那些）；
`found` 答「累计拿回几条」。**第五节是对的，推翻它是错的。**

⚠️ `answered` 的取舍写下来：402／429 退避耗尽那几次会 `refund()`，不计入 —— 钱没花、
也没拿回任何东西，而续跑会照常重试它，读作「还没查过」既如实也可行动。

**复核还挖出一个结构性缺口：provider 从来没有假 HTTP 层** —— `TikHub.search()`
未被任何测试直接调用过，所以 `pickList` 抛出、IG 兜底、IG 不走 offset 这几条路
在整条检查链里一次都没跑过。上面两个 blocking 就长在这几条路上。本条补了一组
provider 契约测试，把那几条路各走一遍。

### 乙 · 第二轮复核：9 条里 8 条是第一轮的修自己引入的

这一小节的标题就是本轮最该记住的事实。第一轮挖出 6 个根因、全部采纳并重做；
第二轮 15 条并成 9 条，**其中 8 条是那次重做新开的洞**。落在本条范围内的两条 blocking：

**`state.answered ??= {}` 把「无从确认」当场抹成「都没问过」。** 甲引入了两张新表，
而 `run()` 开头无条件把它们建了出来 —— **而那正是紧挨着的十行注释里自己写下的警告**
（「`??=` 会把整张表缺失抹成表在、都没查过」），写完警告，两行之后对新表做了一遍。
实测、且不可逆：同一个旧目录，不续跑直接读是「无从确认」（对的），**续跑一次（零次搜索）
之后变成「都没问过」、条数挂着一个 0**，而那个目录 `requests=7`、钱早就花了。
一句诚实的「无从确认」退化成一句肯定的假话，**比修之前更糟**。

修法不是「别建表」那么简单 —— 分页记录表在的时候，它本来就证明了哪些任务问过。
所以：**照它如实补 `answered`，而 `found` 记 `null`**（＝这个数注定不全，
升级前抓了几页无从得知），此后再抓几页也不许把它凑成一个偏小的数。
连分页记录表都没有的，两张表都不建。

**IG 兜底把 `BudgetExceeded` 吞成正常返回，关键词被永久烧进 `done`。**
甲为了「别丢掉已付的那一页」加的那个 catch —— 而 IG 的 reels 页恒 `has_more: false`，
于是入口把任务推进 `done`：退出码 0、还说「续跑不产生新的请求」，而预算已经见底，
追加预算续跑时它再也不会被碰。**把可重试变成了不可重试。**
改回照常抛：走到兜底就说明 reels 一个人都没解析出来，交回它并不保住任何人；
丢的只是条数，而那个数由 `found` 如实记成「无从确认」。这就是登记表里 `D6 × P3` 那条裁决。

⚠️ 同一轮还有一条 blocking 不在本条范围内（断言 grep 的字符串在静态文案与样式表里恒存在，
关键词表整个为空时照样绿）—— 那是报告那一半的事，跟着它走。

### 丙 · 第三轮复核：两条 blocking，都长在第二轮的修上

第二轮的修法是「按分页记录照实迁移」。第三轮独立复核（另一个没写这段代码的上下文）
当场把它推翻，两条都复现过。

**一 · `offsets` 为空时，迁移照样建出 `answered: {}`。** 迁移的条件是
「`answered` 缺、`offsets` 在」，而补哪几个任务只看 `offsets` 的键和 `done`。
**`offsets` 是空对象、`done` 是空数组时，`state.answered = {}` 照样落盘** ——
而那恰恰是 D6.i 立项的那条路：上一版里「请求发出去、200 计了费、`pickList` 认不出抛了」，
`offsets` 那个键从头到尾没被写过。实测：

```
旧目录（旧版 + force-schema）：{'done': [], 'offsets': {}, 'answered': 缺, 'requests': 1}
本改动续跑（零次搜索）：      {'done': [], 'offsets': {}, 'answered': {},  'requests': 1}
```

`answered: {}` 是一句**肯定**的话（「这个任务从未发出过搜索请求」），而同一份文件里
`requests: 1` 证明反面。不可逆。**而且在这个子情形里，第二轮的修法和它自己那条
「必须被抓到」的负片逐字等价** —— 迁移夹具能抓住那条负片，只是因为夹具的旧目录
`offsets` 非空。`offsets` 为空的那一半，修法和 bug 行为相同，没有任何东西在看。

**二 · `answered` 有、`found` 无（＝问过、条数没记下）在下一页成功时被凑成一个数。**
`null`（注定不全）永不消退是对的，但 `undefined` 被 `?? 0` 当成从零开始数 ——
而 `types.ts` 自己的注释写着「有 `answered` 没有 `found` ＝问过、条数没记下，
渲染成『未知』，不许写 0」。实测：

```
第一跑（供应商换了结构，退出码 1）：{'offsets': {}, 'answered': {'0': 1}, 'found': {}}
续跑（结构认得回来了，退出码 0）：  {'offsets': {'0': 12}, 'answered': {'0': 5}, 'found': {'0': 12}}
                                     ↑ 12 看起来像测量值，真值是 12 加上第一次那笔已付费的未知条数
```

同一条路在 IG 上更常见：兜底撞预算 → 付过一次、条数无从得知，追加预算续跑之后
第一轮那几条永远算不进来，而盘上没有任何记号。

**修法：把迁移整个撤掉，两张表改成只在任务目录新建时建。**
缺表 ⟺ 上一版留下的目录 ⟺ 无从确认，**此后也不长出来**（`??=` 都不许）。
代价明写进判据 D6.j：那种目录升级之后一直说「无从确认」。
宁可一直说无从确认，不说一句肯定的假话 —— 第二轮那条 blocking 的教训正是
「一句诚实的无从确认退化成肯定的假话，比修之前更糟」，而第二轮的修法又踩了一次。
第二条改在 finally 里：付了钱、而 `page` 还是 `undefined`（抛在记数之前）时
当场把条数记成 `null`。

**同一轮还有四条 major，三条采纳：**

- **`found` 今天恒等于 `offsets`，而 D6.i 给出的分表理由是假的。** 那句理由写的是
  「IG 兜底那条路上游标只记最后一个端点」—— D6.k 把兜底改成两次相加之后，那个反例
  就不存在了。复核实测把 `found` 的累加整条换成直接抄游标，**整条检查链全绿**。
  真正的理由是另一个：游标只在 `search()` 正常返回之后才写，而 `found` 还要记
  「付了钱、没数上」那一次。判据正文与代码注释都按这个改了，假理由撤掉。
- **D6.i 一条里塞了四件能各自坏掉的事**，而且「记在 finally 里」是实现方式 ——
  `1-REQUIREMENTS.md` 明令判据不写实现。拆成 D6.i（发出过几次付费请求）与
  D6.l（累计拿回几条），实现方式从判据正文里撤掉。
- **D6.k 最重的那一半没有任何检查量它**：`done`、退出码 0、那句「续跑不产生新的请求」
  全在入口那一层，而 provider 契约测试只调得到 `search()`。补了一个端到端夹具
  （reels 返回条目但一条都解析不出人 ＋ 额度只够一次请求），三样逐一断言。
  ⚠️ 顺带逼出自检这一层的一个坑：**退出码对不上打的是进程记号，而记号是一票否决**
  （`judgeRun` 的 `notAssertion`）—— 于是指着这条行为的负片会被判「跑不起来」而不是
  「被抓到」，功劳记错了人。`runBoth` 因此多一个 `asClaim`：退出码本身就是判据点名的
  东西时，对不上算一条具名断言红。
- **没采纳的那条**：`answered` 取预算计数器的增量，于是「连接根本没成功」（`fetch` 自己抛，
  `get()` 先 charge 后 fetch、不为此退费）也被记成一次。判据正文因此从「让供应商
  **应答过**几次」改成「**发出过几次付费请求**」—— 这样记录是如实的。
  ⚠️ 真正的缺口在更底下：连接没成功时供应商多半没计费，而 `budget.count` 和主干上的
  `requests` 都照记不误，两个数一起偏大。那是既有行为，不在本条范围 ·
  重启条件：下一条碰 `Budget` 的计费口径、或者有人报账单和 `requests` 对不上

**同一轮的第二个上下文跑的是重型版**（`4-VERIFY.md`：清空上下文、**只读判据**重写一遍测试、
再与现有测试比对）。它先凭判据列出 24 条「必须被量到的行为」，然后逐条找对应的证据 ——
在 `b6e7633` 上构造出**四个整条检查链全绿的反例**，其中三个是上面已经修掉的那些。
剩下两条本条也一并修了：

- **「402／429 退了费的不计入」在入口那一侧完全没人看管。** provider 那一侧是守住的
  （`refund()` 的记账语义有一组穷举序列的性质测试，删掉 `refund()` 当场红三条），
  但入口算 `paid` 的那一行没有。实测把它换成 `Math.max(budget.count - paidBefore, 1)`：
  `npm test` 与 `npm run selfcheck` 双绿，而盘上一个**一分钱没花**的词从此
  「发出过 1 次付费请求」，并且因为它是抛出去的，条数还被永久钉成 `null` ——
  D6.i 与 D6.l 同时被违反，整条链一个字不说。补了一个 402 端到端夹具与负片 `M-D6-w`。
- **`scripts/test.ts` 那一行 `criterion('D6.i')` 不只是「多认了一句」。**
  provider 契约那一组**一次都没打开过 `task.json`**，而 D6.i 说的正是「`task.json` 必须记下…」。
  更重的是 `spec-rule.ts` 的那道闸：「只由自检认领的判据必须有一条 `by:"selfcheck"` 的负片」
  这条硬失败，**只要单元那边也认领了就整条跳过**。复核用对照实验证明：删掉 `M-D6-p`
  之后审计对 D6.i **一个字都没有**；再删掉那行认领，缺口立刻现形。
  也就是说那一行的实际作用是**给 D6.i 常年免掉一道结构性闸门**。已撤掉。

⚠️ 它还留下两条 minor，都记在这里：`paidbutlost` 夹具原本写的 `pstate.offsets?.[0] === undefined`
在整张 `offsets` 表缺失时也为真，两种情况分不开（已收紧成先判表在不在）；
以及「三者不恒等」在正常路径上其实只由 `null` 撑着 —— `offsets[i] = offset + raw_count`
与 `found[i] += raw_count` 加的是同一个 `raw_count`，真正让它们分开的只有
「付了钱没走到记数那一步」和「旧目录缺表」。判据正文已经按这个改过。

### 丁 · 两处就地更正（这条记录自己说过的假话）

**一 · SIGKILL 不在 D6.i 覆盖内。** 甲把「进程被杀」和「换了响应结构」「兜底撞预算」
列在同一类，然后说三张表解决了这一类。**前两者成立，SIGKILL 不成立** ——
实测（`FAKE_FETCH_KILL_AFTER_OK=1` ＋ 账本）：账本里有一行 200，而盘上
`{'answered': {}, 'requests': 0}`。那个窗口是 `M-P3-f`／ADR-96 登记过的落盘窗口，
本条一个字都没动它。判据正文没说大话，甲这段散文说了。

**二 · 本条并没有消除「续跑再买一次同样的第一页」。** 调度仍然只看 `offsets`，
而付过钱抛了的那个键仍然不写 —— 丙那条实测里第二跑就把同一个第一页又买了一次
（`requests` 1 → 8）。判据没承诺这件事，**本条记的是「盘上看得出它问过」，
不是「续跑不会再买」**。下一个人容易把这两句读成一句。

### 戊 · 这几轮真正的教训

不是「再仔细一点」。四轮下来的形状是稳定的：

- 一轮修 N 个洞，同时开出约 N 个新洞，而整条检查链每一轮都全绿
- 新洞的位置**高度集中在修法本身**：新加的字段、新加的 catch、新加的断言
- 抓住它们的从来不是检查链，是**没写这段代码的那个上下文**

`process/4-VERIFY.md` 说变异测试抓不到同源污染，ADR-24 据此要求独立复核。
这几轮是那句话最贵的一次实证：**变异全被抓到、审计通过的每一个版本，都带着 blocking。**
第三轮尤其干净地演示了它：第二轮的修法在一个子情形里和它自己那条负片逐字等价，
而夹具恰好没造到那个子情形 —— 检查链于是照绿。

前者不靠后者也立得住（付过钱的词在盘上看得出问过），后者要靠前者才有料可读。

⚠️ **还欠着**：`U3.a` 至今没有认领（本条之前就欠着）；`D6.h`（单关键词页数上限跨运行有效）；
`F9 × F1` 的测试认领；以及「三态靠字段存不存在来表达」这个更根本的形状 ——
任何一次 JSON round-trip、任何一个默认值填充都会毁掉它，乙和丙那两条 blocking 都是证据 ·
重启条件：下一条给 `TaskState` 加字段、或者再碰这三张表的改动

## 十六、报告也说实话：关键词表从任务列表出发，四态分得开（P5.i／U3.b／U3.c）

上一节把三张表记在了盘上，但**写了没人读**。这一节是读的那一半：报告里
「查了没人」和「一次都没查」今天长得一模一样，而那正是用户最早报的那件事最贵的一半 ——
IG 一次没被查时，报告看起来和「IG 真的没人」毫无分别。

**装了什么**（本条 PR）：

- `scripts/lib/pipeline.ts`：`taskQueryStatus`（这个任务问过没有，**读 `answered`**）、
  `keywordRows`（关键词×平台一行，从**任务列表**出发）、`taskPlatforms`
- `scripts/render.ts`：`meta.keywords` 与 `meta.platforms` 都改成从任务列表派生
- `scripts/lib/report.ts`：关键词表加平台列、「找到」与「入围」分列、四态说人话；
  **命中率那一列整列撤掉** —— 它是两种单位相除，也正是 P5.i 逐字点名的那个 `0%` 的出处
- `scripts/lib/types.ts`／`scripts/collect.ts`／`scripts/lib/identity.ts`：
  `Creator.source_tasks` —— 归人按任务下标，见下面甲
- 登记表：P5.i（红线判据）＋ U3.b ＋ U3.c；U3.a 退役；交点 `U3 × P5`
- 退役：`keywordStats`（它从交付名单出发，那正是这条要修的东西）

### 甲 · 归人按任务下标，不按（关键词, 平台）

独立复核挖出来的：creator 与 task 是**多对多**，而头一版按（关键词, 平台）归人。
那个二元组**比行粗** —— 行的身份还带 dimension 与 as_hashtag，所以同词同平台的
两个任务会数到同一批人。实测：第二行 `status` 是 `unqueried` 却带着第一行的入围数，
等于把**别人的测量结果**安在一个从没发过请求的行上，**比印 0 更糟**。

改法：`Creator.source_tasks`（任务下标的数组）。全局去重命中已有的人时把这个任务
追加进他的来源；跨平台合并时取并集 —— 漏了后面那一笔，次记录那一侧的关键词
就再也归不到他。⚠️ **各行入围相加可以大于名单总人数**，一个人可以被多个词搜到。

⚠️ `source_keyword` 保留不动（CSV 的一列、记忆里的字段）；`source_tasks` 只是
另加一份归因用的。本条之前采的人没有它 —— 那种目录的关键词表本来就判无从确认。

### 乙 · 两条 HTML 断言是空转的，而整条检查链全绿

复核逐条核断言时发现：`includes('未查询')` 命中的是**同一个提交里新写的那句说明文案**，
`includes('instagram')` 命中的是样式表里的类名 `.pf.instagram{`。
关键词表整个为空时它们照样绿 —— 实测 `renderHtml([], { keywords: [] })` 两条都命中。
**那两条什么都没测，而整条检查链 403/403 全绿。**

第一次修只改了 `scripts/test.ts`（切到 `<tbody>` 再断言），**自检那一层没跟着改** ——
同一个「改了一处没改另一处」的形状，第二轮复核又逮到一次。现在两头都切表体，
另加一条**反证**：把表体挖空，那几个字必须不再命中。切在 `</table>` 上不够 ——
那句说明文案在 `<h2>` 与 `<table>` 之间，断言照样恒真。

### 丙 · U3.a 被证伪却没退役

它逐字要求「找到**人数**」与「命中率」，而本条把「找到」换成供应商返回的条目数、
并撤掉了命中率那一列（两种单位相除无意义）。按 ADR-67 退役、由 U3.c 接替 ——
判据不改含义、不回收编号。

### 丁 · 两轮独立复核：6 条 blocking，一半能构造出「全链全绿的反例」

ADR-24 这次起了**两个**没写这段代码的上下文：一个逐条找空转断言与三态被压平的路径，
一个跑重型版（只读判据重写测试再比对）。两边并出 6 条 blocking，每一条我都自己复现过。
**其中四条的反例是「把实现改坏、整条检查链仍然 371/371 全绿」** —— 同源污染的标准形状。

**一 · 归人的两个维护点一个字都没被量。** `collect.ts` 里「同一个人被第二个词搜到就把
那个任务追加进他的来源」这一笔，和 `identity.ts` 里跨平台合并时的来源并集 ——
**它们的存在理由都写在自己的注释里**（「漏了这一笔，后面那个词会被报成『找到 N 条、
一个都没入围』」），而全仓 `source_tasks` 在测试里只出现在一个 fixture 的赋值上。
删掉任一处，整条链全绿；端到端实测那一行从「入围 3」变成「入围 0」。

⚠️ 顺带把 `collect.ts` 那段搬进 `pipeline.ts` 的 `mergePage` —— **不是为了好看，是为了
验证者便宜**。留在入口脚本里，指着它的负片只能靠整跑一遍自检来验，而那是本仓库最贵的
一种验证者；搬出来之后缺省那个验证者就够得到。判据一个字没改。

**二 · 「入围／语义通过」两列的内容没有任何断言。** `criterion('U3.c')` 名下九条断言
全是 `includes('<th>找到</th>')` 这种**表头存在性** —— 而 U3.c 说的是「**每一行**列出」。
复核把「入围」那一列的接线换成 `countText(k.found)`（两个单位不同的数当场合并成一个，
正是 U3.b 逐字禁的），**全链全绿**。四态也只有两态被钉住：把「未知」印成 0、
把「查了 0 命中」印成「—」，两个改法都全绿。
现在四态放进**同一次**渲染、三列逐格钉死，五条负片指着 `report.ts`。

**三 · 上一条 PR 建的目录，走到本条的 render 每一行都印「入围 0」。**
`answered`／`found` 是上一条加的，`source_tasks` 是本条加的 —— 两条按验收证据切开、
分两个合并单元按序合，**中间那个窗口里建的目录就是「表在、人身上没有下标」**。
`keywordRows` 只拿 `status==='unknown'` 判无从确认，于是这种目录每一行都印
「找到 40 / 入围 0」，而名单里实际有 3 个人。**一个确定为假的 0，印在真测量值旁边** ——
P5.i 是红线判据，它逐字禁的就是这个形状。
而 `types.ts` 与 `pipeline.ts` 的注释当时声称这不可能（「那种目录的人身上没有任务下标，
关键词表本来就判无从确认」）—— **那句话只对早于 `answered` 的目录成立**。
改法：归人算不算得准是**整张名单**的属性 —— 只要有一个人没带来源任务，整张表的入围
一律报「无从确认」。

**四 · `found === null` 把一个确知的入围数抹成「无从确认」。** 那条等价（「条数不全
⇔ 归人不全」）的理由指向迁移，**而迁移已经被上一条 PR 整个撤掉**。今天 `found[i] = null`
只发生在「这一页付了钱、抛在记条数之前」：那一页一个人都没入库，前几页采到的人身上
下标一个不少。实测：一个贡献了名单五分之三的方向被印成「什么都不知道」。
**而单元测试把这个错误行为当成正确断言下来了** —— 误解写进实现，同一个误解写进断言。

**五 · P5.i 的单元认领，替入口接线免掉了 `by:"selfcheck"` 那道硬失败。**
`spec-rule.ts` 那道闸的判定是「**只由自检认领**才查」，单元这边也认领了就整条跳过。
而 P5.i 最要紧的那一半（`render.ts` 的 `platforms` 接线）单元根本够不到。
对照实验：删掉唯一指着它的负片 `M-P5-o`，审计**一个字都没有**。
**这正是上一条 PR 在 D6.i 上刚认定的 blocking，本条镜像地重犯了一次。**
改法同上一条：拆 —— `P5.j` 专管「平台不得静默消失」，只由自检认领，那道闸于是管得着它。

**六 · 提交把 `node_modules` 符号链接提交进了仓库。** `.gitignore` 写的是 `node_modules/`
（带斜杠只匹配目录），挡不住 worktree 里那条同名符号链接，`git add -A` 就把它收了进去 ——
任何别的检出（含 CI）会拿到一条指向作者机器绝对路径的死链。
去掉，并把 `.gitignore` 那一行的斜杠删掉，免得下一个人再踩。

### 戊 · 同一轮采纳的 major 与 minor

- **未查询的行不再印 0。** P5.i 逐字：「未查询的行不得带出看起来像测量值的数」——
  而它原本印「入围 0 / 语义通过 0」，同一张表里信息更多的「无从确认」那一行反倒印「—」，
  口径是反的。现在两者都印「—」，靠「找到」那一格的「未查询」／「无从确认」区分。
  交点 `U3 × P5` 的裁决也跟着改写成一条真裁决（原文是一句分工说明，没有任何事实能让它为假）。
- **`answered` 是 `null` 时不再当场抛。** 盘上那个值是反序列化进来的外部输入，
  只判 `undefined` 的话 `i in null` 会抛 —— 而抛的位置在 render **写完名单、写回记忆之后**，
  交付物互相矛盾。
- **判据拆分。** P5.i 原本一条里塞了五件能各自坏掉的事，U3.b 三件 ——
  同一轮复核在上一条 PR 上刚因为同样的理由把 D6.i 拆成 D6.i 与 D6.l。
  本条拆出 P5.j；U3.b 的「两个数不得合并」并进 U3.c（那一条本来就管列）。
  U3.b 的判据文本也去掉了「任务下标」这个实现说法，改成行为版本。
- **`skill/references/output-format.md` 跟着改了。** `docs/SYNC.md` 那一行逐字点名了它，
  而它还写着「每个词找到多少**人**、语义**命中率**多少」、`meta.json` 的例子里没有
  `status` 与 `shortlisted` —— Agent 照它转述会把「找到 40 条」说成「找到 40 人」。
- **`skill/SKILL.md` 里「P5.i 要补的洞」那句改了** —— 落地的 P5.i 只覆盖 `meta.json`
  与 HTML，`collect` 的 stdout 仍然分不出「没跑完」与「没跑过」。留着会让下一个人以为补上了。
- **自检 ghost 夹具那条断言绑紧了**：原先「表体里有一行、表体里有 gig」两件事不要求同行，
  今天只有 gig 是未查询所以还成立，多一个未查询的词就恒真。

⚠️ **没采纳一条**：U3.a 的退役理由被指「说大了」（「两个数单位不同、相除无意义」只对
`fit_pass / found` 成立，新表里「入围」与「语义通过」同单位）。这条对 —— 判据正文已按它
改成「命中率那一列随之撤掉，那是本条的范围决定，不是被迫的结论」。

### 己 · #140 评审一条 Major：同一个形状还藏在另外两条路上

丁之三（「上一条 PR 建的目录，每一行都印入围 0」）的修法是「整张名单只要有一个人没带
来源任务，入围一律报无从确认」。**评审指出那个判断在两条路上会被提前抹掉：**

- `mergePage` 里，累加器中本条落地之前采的人（`loadRawCreators` 从 `creators.raw.json`
  读回来的）被第二个任务再搜到时，`(seen.source_tasks ??= []).push(i)` 会**凭空给他补一个
  `[i]`** —— 等于替他打包票说「他只来自这个任务」。`attributable` 于是翻真，整张表又开始
  印确定为假的 0。
- `mergeCrossPlatform` 里，`[...(c.source_tasks ?? []), ...(other.source_tasks ?? [])]`
  把**无从确认的那一边当成空集**：合出来的人看着归得清，实际少了一半来源。

两处的共同点：**把「不知道」当成「空」**，而这条 PR 自己的判据逐字禁的就是这件事。
改成「他已经带着才追加」「两边都在才取并集，否则整个报无从确认」，各配一条负片
（`M-U3-j`／`M-U3-k`）。

⚠️ 同轮还有一条 minor 也是真的：`skill/references/output-format.md` 里那个 `unqueried`
的例子写着 `shortlisted: 0, fit_pass: 0` —— 而实现发出来的是 `null`。**我自己刚写的文档，
和我自己刚写的实现对不上**，同一个「两处副本改了一处」的形状。

### 己 · 这两轮的形状

和上一条 PR 一模一样：**一轮修 N 个洞、同时开出约 N 个新洞，而整条检查链每一轮都全绿。**
本条最刺眼的两处都是「上一轮刚认定的 blocking，这一轮镜像地重犯」——
认领过宽替判据免掉硬失败（五），以及一条判据里塞太多件事（戊）。
`process/4-VERIFY.md` 说变异测试抓不到同源污染；四条「全链全绿的反例」是它最直接的证据。

⚠️ **还欠着**：`D6.h` · `F9 × F1` 的测试认领 · 「三态靠字段存不存在来表达」这个更根本的形状 ·

重启条件：下一条碰关键词表、或者碰 `collect` 的收尾输出

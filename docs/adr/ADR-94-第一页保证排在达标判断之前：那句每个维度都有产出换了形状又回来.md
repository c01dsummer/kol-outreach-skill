# ADR-94 第一页保证排在达标判断之前：那句「每个维度都有产出」换了形状又回来

- 日期 · 2026-09-19 起（用户按 `skill/SKILL.md` 真实跑建联任务，发现 Instagram 召回很少、甚至一个人都没有），三片落地到 2026-09-20，此后在末尾逐条记欠条到 2026-11-08
- 类型：三件事，分开标。① 「轮转保证每个维度都有产出」不成立 —— 事实证伪，需求必须改，不谈取舍；② 两个平台各分多少人 —— 产品取舍，要人拍板（第六节）；③ 「没查过」在交付物里看不出来 —— 红线判据缺口（P5 名下原先没有这一条）
- 触发它的事实：采集的达标判断跑在每一次搜索请求之前，排在任务列表后面的关键词（常见的是整个 IG）可能一次都不被问（第一节）
- 冲击的需求：新增 F9（五条判据、与 P3、P1、D6、F1 四个交点）· P5 加 P5.i、P5.j · U3 加 U3.b、U3.c，退役 U3.a · D6 退役 D6.c、加 D6.g，另加 D6.h（落在 ADR-100）与 D6.i、D6.j、D6.k、D6.l 和交点 `D6 × P3`（D6.i 后来由 ADR-108 退役、D6.s 接手）· 交点 `U3 × P5`。各条的正文以 `docs/requirements.json` 为准
- 决定人与时间：用户 2026-09-19 指示把本条开出来，即采纳「第一页保证」作底线；2026-09-20 指示先做第一页保证、后做报告。其余见「需求所有者定过的」
- 结论：采纳，已落地。达标判断不再砍掉一页都没抓过的任务；盘上分开记「下一页从哪接」「发出过几次付费请求」「累计拿回几条」；报告的关键词表从任务列表出发，「未查询」「查了 0 命中」「命中 N 条」「无从确认」四态分得开。本条保证的是「问过」，不保证任何平台的人数；预算先用尽时连「问过」也不保证
- 理由：用户拿到的信息变多（IG 真的被查了，没查到的会被告知），代价是可能多花钱：原先达标时还有几个任务一页没查，就多发几次搜索请求，多少看那一跑；页数上限和预算闸门一字不动，预算先用尽就照 F9.b 停下、如实列出没查的（当时的估算只在历史文件第六节）。今天 IG 一次没查时，报告和「IG 查了没人」长得一模一样，运营据此不再投 IG —— 那正是 P5 要防的代价。只改 `skill/` 让 Agent 把 IG 排前面，等于把一条保证放回散文（第六节丁）
- 连带改动（现状）：`scripts/lib/pipeline.ts`（`firstPagePending`、`keywordsResumeWillRun`、`taskQueryStatus`、`keywordRows`、`taskPlatforms`、`mergePage`）、`scripts/collect.ts`、`scripts/lib/types.ts`（`TaskState` 的 `offsets`、`answered`、`found`，`Creator.source_tasks`）、`scripts/lib/identity.ts`、`scripts/render.ts`、`scripts/lib/report.ts`、`scripts/providers/tikhub.ts`（IG 兜底）；`skill/SKILL.md`、`skill/references/output-format.md`、`docs/business-requirements.md`、`docs/ARCHITECTURE.md` 顺序契约表；ADR-06 末尾追记与开头指针；`.gitignore` 的 `node_modules`
- 教训：「达标即停」这个判断跑在什么之前，决定了它保护什么：跑在每次请求之前，保护的是预算；跑在「每个任务都问过一遍」之后，保护的才是策略。ADR-06 的教训是「凡是写 `if (x >= target)` 都要问 x 和 target 是不是同一种东西」，本条补一句：还要问这个判断跑在什么之前。另一半与 ADR-66 同形：一句描述保证的话，被一个形状不同的同类 bug 绕过之后，比代码更难发现自己在撒谎，因为它引用的那次修复是真的

## 一、出了什么事：达标判断跑在每一次请求之前

改之前，`scripts/collect.ts` 的调度是「每轮把任务列表走一遍，每个任务抓一页」，而「已经够人了就停」那句判断跑在每一次搜索请求之前，第一轮也不例外。所以轮转保证的只是「一个词不连翻四页」，不是「每个词都被问过一遍」：排在前面的任务只要把目标填满，后面的任务一个请求都不发。达标数是跨平台的总数，没有按平台或按维度的配额。

任务的先后由 Agent 写，当时仓库里几处任务清单形状的样例都把 TikTok 排在前、Instagram 排在后，于是最常见的受害者正是整个 IG。用假 fetch 按真实产量建模（树 `825fd2d`，夹具与命令原样在历史文件第一节）：4 个 TikTok 词在前、2 个 IG 词在后、目标 50 时，IG 一次请求都没发，`stopped` 是 `target`；同一批词把 IG 排最前，IG 就被问到了。

当时还有一条放大它的事实：IG 的 Reels 搜索我们只取一页，第二轮起只剩 TikTok 在跑。这一条已经不成立 —— ADR-101 证实 Reels 能翻页，ADR-111 起 IG 顺着续页令牌在同一次运行内翻页（D6.u），单个任务仍受 4 页上限。一页的条数也不是固定的「约 12 条」，条目数与去重作者数要分开读。

## 二、四条连带成因，现在各在哪

1. 达标停下之后 `--resume` 救不回没问过的词 —— 由 F9.c 与 D6.g 修掉：续跑会去抓一页都没抓过的任务，即使已经达标。
2. 页数上限只按「每次运行」计，预算续跑让 TikTok 越翻越深 —— 由 D6.h 修掉（ADR-100）：上限跨运行累计。
3. IG 的人粉丝数未知时按 P1 放行、计进达标数，补完资料之后才被粉丝闸门筛掉，那时循环早停了 —— 不改停止规则，「接受并声明」（第六节）。
4. 免费额度下 IG 端点返回 402，整轮出错退出 —— 与调度无关，不归本条；402 的收尾与退出码后来由 ADR-183、ADR-193 定（今天 402 退 5）。

## 三、F9：第一页保证要什么，与红线的交点

F9 的正文与五条判据（F9.a 到 F9.e）以 `docs/requirements.json` 为准，要点：

- 以达标收尾时，任务列表里每一个关键词×平台都至少发出过一次搜索请求，换任何顺序都成立（F9.a）。
- 预算不够给每个任务抓第一页时，按 P3 停下、存断点，没问到的如实列出，不为抓齐第一页超出预算（F9.b）。
- 「续跑会去抓哪些」只此一份判定，调度与「续跑要不要花钱」那句话共用（F9.c）。第一页之后的分页仍按达标判断停止（F9.d）。
- 任务目录里整张分页记录表都没有时，读作「无从确认哪些任务查过」：不发请求，不得读作「都没查过」，也不得读作「都查过了」（F9.e）。

四个交点的裁决：`F9 × P3` P3 赢，第一页保证在达标判断之前生效，不在预算之前；`F9 × P1` 不设任何默认的平台配额，IG 占多少由 Agent 出了几个 IG 词决定；`F9 × D6` 续跑会去抓的 ＝ 没抓过第一页的任务 ∪（未达标时）其余未完成的任务，D6.c 据此退役、由 D6.g 接替；`F9 × F1` 不新增必问项。

连带的红线判据落在 P5 而不落在 U3：U3 管「表里有什么」，P5 管「用户会不会据此做出错误决定」。IG 从报告里消失，运营的结论是「这个品类 IG 没人」，下次就不投 —— 代价由用户承担且不可逆。也不并进 P1.e：P1.e 管交付表里人的字段，关键词表走另一条路径，会独立坏掉。现行的是 P5.i（四态分开、未查询的行不带出像测量值的数）与 P5.j（平台从任务列表出发，不得消失），见第十六节。

## 四、描述保证的话只说请求、不说产出

ADR-06 与另外四处（`skill/SKILL.md` 两处、`docs/business-requirements.md`「采集必须轮转」那段、`scripts/collect.ts` 的 `run()` 函数头）写过「每个维度都保证有产出」这类结果承诺，本条当场撤回成事实，落地之后再重申（第十四节）。重申的措辞只说请求、不说产出：一页可以 0 个不同作者、可以被兜底成商家号、可以补完资料全被筛掉；写「每个维度才真的有产出」又是一句没人看着的承诺。先撤回、后重申，理由同 ADR-66：撤回是响的，挂着是静默的。

## 五、登记表的条目跟着实现与测试一起进主干

本条第一版试过把新判据和决策记录一起写进登记表，审计硬失败：红线判据与带红线的交点没有测试认领（判定在 `scripts/check/spec-rule.ts` 的 `requirementVerdict`、`tensionVerdict`），而认领它们的测试要断言还不存在的行为。所以登记表的每一条跟着它的实现与测试进主干，决策记录与撤回措辞先合。这件事已经做完：F9、P5.i、P5.j、U3.b、U3.c、D6.g、D6.h 都在登记表里、各有测试认领，D6.c、U3.a 已退役。

| | 选项 | 处置 |
|---|---|---|
| 甲 | 每个任务保证一页，不加任何参数 | **采纳**，作底线。修掉的是「零」，修不掉「少」 |
| 乙 | 甲 ＋ 第一轮按平台交错排请求 | **不做**。只在预算小到连「任务数」次搜索都不够时才多修一点，代价是调度多一层规则 |

| 丁 | 只改 `skill/`：IG 排前面、多出 IG 词、达标时报未跑的词 | **作为单独的修法驳回**：它把保证放回散文。其中「多出 IG 词」「报未跑的词」是判断层的补充，照做；预算可能不够时把最在意的平台排在前面，仍是 `SKILL.md` 里的建议（预算先用尽时顺序照样决定谁被砍掉） |

甲的代价写明：交付物会超过目标，最多「每个词一页」；花费可能变多，多发几次看那一跑（同理由一行）；页数上限不变。`skill/references/product-intake.md` 里「要找多少人」因此是「至少这么多」。

「达标对 IG 偏乐观」（第二节第 3 条）取「接受并声明」：不改停止规则，靠「找到 / 入围」分开与收尾那句话说实话。驳回「停止判断把粉丝未知当作尚未合格」—— 那是把偏乐观换成系统性偏悲观，而用户要的是 N 个人，不是 N 个 TikTok 人。

一次性升级边界接受：本条落地前以达标停下的旧目录，IG 任务没有分页记录，落地后续跑会给它们补发第一页，与那次运行末尾说的「续跑不产生新的请求」不一致；方向正对、只发生一次。整张分页记录表都没有的更老目录按 F9.e 处理：无从确认，不发请求。

## 八、第一轮评审：一条撤回假承诺的记录里写下新的假承诺

`SKILL.md` 里不写「以达标停下的那些任务，`--resume` 一个请求都不会发」：`collect` 跑完搜索还会补资料，那是付费端点（ADR-22、ADR-25 那段）。现行的说法见第十三节。判据落纸那一刻，先拿它量一遍这条记录自己（ADR-73），特别是它引用过的每一条规矩。

## 九、第三轮评审：写「还能补回来」之前先跑一遍

写下「还能 X」「X 能补回来」这类宽慰话之前，先把 X 跑一遍；跑不动就只写坏消息。同一轮新写下的每一条命令，写完之后都原样跑一次（第八轮的教训：修「不许写没核过的数」时最容易新写一个没核过的数）。这条判据没有机器守着，欠条见末尾。

## 十、第四轮评审：全称句逐个跑

出现「都」「一定」「一个也不」这类全称，就把它覆盖的情形逐个跑一遍；跑不全就写成「看情况，判断依据是 X」。按这条定下的续跑事实：预算停下时，跳过的词补不补得回来不保证，看 `collected` 与目标（stdout 里叫 `target`）差多少、追加的预算够不够。`skill/SKILL.md` 里原先那句说法 #155 删了，今天它让 Agent 按 stderr 的待查关键词、待补资料和费用状态转述。

## 十一、第五轮评审：命令写进记录之前，先问它依赖了什么本机没钉住的东西

node 版本、全局装的工具、环境变量都算。自己跑得通不等于别人跑得通。复现夹具因此写成纯 JS 的 `.mjs`：`--import` 的预加载由 node 自己处理，轮不到 tsx。CI 钉的是 node 22，读记录的人那台机器没钉。

## 十二、第六轮评审：核不了的事实不替它找一个具体的数

说清依赖是什么就够了，从哪个版本起以官方文档为准。「顺序是唯一决定哪些词会被查到的东西」也不成立：目标人数和预算决定砍在第几个，顺序决定被砍掉的是谁。

## 十三、达标停下之后续跑会不会搜：看补完资料之后还够不够

达标判断用的是补资料之前的粉丝数（未知一律放行，P1）；`enrichProfiles()` 跑在搜索之后，把真实粉丝数写回。被粉丝闸门筛掉的人一多，达标数就掉回目标以下，续跑照常去搜；预算够时被跳过的词整词补回（那次实测见历史文件第十三节），不够时照 F9.b 用尽即停、如实列出没查的。所以没有「达标停下之后续跑一个关键词搜索都不发」这回事；要不要花钱，照 stderr 说的转述（`keywordsResumeWillRun` 按那一刻的达标数重算），Agent 不自己下结论。照错的说法，Agent 会让用户为一次续跑就能拿到的补采把已经付过的请求再付一遍。

`pending_keywords` 是「不在 `done` 里的词」，不是「没跑过的词」：搜过一页、没到页数上限的也在里面。转述时只说「还没跑完」。`collect` 的 stdout 至今分不出「没跑完」与「没跑过」，P5.i 只补了 `meta.json` 与 HTML 报告那一半（欠条现挂在 ADR-193）。

## 十四、第一页保证怎么落的地

- 「哪些任务一页都没抓过」只此一份：`scripts/lib/pipeline.ts` 的 `firstPagePending`，调度与「续跑要不要花钱」那句话共用（F9.c）。它交回三态：`null` ＝ 无从确认，`[]` ＝ 没有欠着的，`[i, …]` ＝ 这几个欠着。头一版另写过一个 `pagingUnknown` 回答「整张表在不在」，与它是同一个判断的两份，删了。
- `scripts/collect.ts` 达标之后不是一律停：用 `continue` 不用 `break`，否则排在后面、一页都没抓过的任务跟着被砍掉。「无从确认就不抓」那道闸放在达标判断之前，未达标那条路也走得到；无从确认时不 `??= {}`，否则收尾那句话会说「还有 N 个关键词要抓」而调度一个都不抓。
- `TaskState.offsets` 可选，三态：整张表缺失 ＝ 无从确认（旧目录）、有表没这个键 ＝ 一页都没抓过、有值 ＝ 抓过。
- 证据：单元断言（`scripts/test.ts`）认领 D6.g、F9.c、F9.d、F9.e 与交点 `F9 × P3`、`F9 × P1`、`F9 × D6`；自检端到端认领 F9.a、F9.b、F9.d、F9.e；负片在 `M-F9-*` 名下。条数不写在这里，数它用 `npx tsx scripts/check/mutate.ts --brief | grep -c 'M-F9-'`，覆盖看 `npm run audit`。
- 第四节撤回的五处按「只说请求、不说产出」重申；`docs/ARCHITECTURE.md` 顺序契约表加了两行。

和原文第五节那张落地顺序表（只在历史文件里）不一样的三处：实际先落的是第一页保证（用户 2026-09-20 指示），报告那一半后落；判定是一个纯函数不是两个；D6.h 另落（ADR-100）。原文第五节那张硬失败清单漏了一条：`F9 × P1` 同样是带红线的交点（一头是红线就算），落地时三个都有测试认领。`F9 × F1` 两头都不是红线，是软缺口，至今没有测试认领（欠条现挂在 ADR-156）。

这条修掉的是「零」，修不掉「少」。要 IG 多，得多出 IG 词，那是判断层的事；多出几个词也不保证新增人数（两个词的首页零成本量过一次没有交集，但不能外推，ADR-101 第十五节）。

## 十五、盘上记实话：三个事实三张表

### 甲 · `offsets` 兼不了别的职

`offsets` 只答「下一页从哪儿接」。它只在 `search()` 正常返回之后才写，任务循环里「请求发出去、钱扣了、在写它之前抛了」（供应商换了响应结构、IG 兜底撞上预算）这类路径会塌回「没查过」；IG 兜底（Reels 解析不出人就改搜账号名）原先还把第一次请求的条数整个丢掉。所以另记两张表：`answered`（发出过几次付费请求，在 `finally` 里按预算计数器的增量记；`finally` 只改内存、不落盘，此刻 `offsets` 还没更新、人也还没入库，落盘会留下自相矛盾的断点，负片 `M-P3-f`）与 `found`（累计拿回几条）。402、429 退避耗尽那几次退了费，不计入。IG 兜底两次请求的条数相加（D6.k）。

provider 原先没有假 HTTP 层，`pickList` 抛出、IG 兜底、IG 不走 offset 这几条路在检查链里一次都没跑过；需求测试里有一组 provider 契约测试（罐头 fetch）把它们各走一遍。

`answered` 的那条判据 D6.i 后来由 ADR-108 退役，搜索请求痕迹的口径现行的是 D6.s；`answered` 这张表仍在。

### 乙 · 不许凭空建表；兜底撞预算照常抛

`??=` 会把「无从确认」当场抹成「都没问过」，而且不可逆：一句诚实的「无从确认」退化成一句肯定的假话，比修之前更糟。IG 兜底撞上 `BudgetExceeded` 必须照常抛：吞成正常返回的话，任务以退出码 0 进 `done`，追加预算续跑时再也不会被碰 —— 把可重试变成不可重试。这就是交点 `D6 × P3` 的裁决。

### 丙 · 不迁移，两张表只在任务目录新建时建

缺表 ⟺ 上一版留下的目录 ⟺ 无从确认，此后也不长出来，`??=` 都不许（D6.j）。按分页记录自动迁移试过一版，独立复核推翻了：`offsets` 为空时迁移照样建出 `answered: {}`，而同一份文件里 `requests: 1` 证明反面。代价写明：那种目录升级之后一直说「无从确认」。付了钱、却在记下条数之前抛了的那一次，`found` 记 `null`（注定不全），此后永远是 `null`，不许从 0 凑出一个偏小的数（D6.l）。402 退费那一路在入口一侧也有端到端夹具与负片 `M-D6-w`。

一条判据只由自检认领时，`spec-rule.ts` 要求它有一条 `by: "selfcheck"` 的负片；单元那边也认领了，这道闸就整条跳过。所以单元测试不替只在入口证得了的判据挂认领（D6.i 当时就是这样被免掉了那道闸；第十六节丁之五在 P5.i 上又犯了一次）。

### 丁 · 本条没承诺的两件

- 进程被 SIGKILL 不在这三张表的覆盖内，那个落盘窗口是 ADR-96 登记的。
- 本条记的是「盘上看得出它问过」，不是「续跑不会再买同一页」。

## 十六、报告也说实话：关键词表从任务列表出发，四态分得开

- `taskQueryStatus` 读 `answered` 判这个任务问过没有；`keywordRows` 从任务列表出发，一个关键词×平台一行；`render.ts` 的 `meta.keywords` 与 `meta.platforms` 都从任务列表派生（P5.j）。
- 关键词表加平台列，「找到」（供应商返回的条目数）与「入围」分列，四态说人话；命中率那一列整列撤掉（U3.c 接替 U3.a，这是本条的范围决定）。从交付名单出发的 `keywordStats` 退役。
- 未查询的行和无从确认的行，入围与语义通过都印「无从确认」，照 P5.i、U3.b 原文；两种行靠「找到」那一格的「未查询」「无从确认」区分（交点 `U3 × P5`：P5 赢，行照样在，数不印出来）。原先这两格印「—」，ADR-218 起改。
- `keywordRows` 读到 `answered` 是 `null` 时读作无从确认、不抛（盘上那个值是外部输入）；ADR-139 起 render 在导出之前就以 2 拒绝整表为 `null` 的断点（D19.b）。
- `skill/references/output-format.md` 跟着改：「找到 40 条」不说成「找到 40 人」。

### 甲 · 归人按任务下标

creator 与 task 是多对多。按（关键词, 平台）归人比行粗，同词同平台的两个任务会数到同一批人，把别人的测量结果安在一个从没发过请求的行上。所以 `Creator.source_tasks` 记任务下标：去重命中已有的人时把这个任务追加进他的来源，跨平台合并时取并集。各行入围相加可以大于名单总人数。`source_keyword` 照旧保留。

### 乙 · 断言要切到表体再量

`includes('未查询')` 这类断言要切到 `<tbody>` 再量，否则会命中说明文案或样式表类名，关键词表整个为空时照样绿；另配一条反证：把表体挖空，那几个字必须不再命中。单元测试与自检两头都这样。

### 丙 · U3.a 退役

它逐字要求「找到人数」与「命中率」，与本条的「找到」不是一个量。按 ADR-67 退役、由 U3.c 接替，编号不回收。

### 丁 · 两轮独立复核的六条 blocking，落成的规定

- 归人的两个维护点（`mergePage` 里追加来源、`identity.ts` 里合并取并集）各有断言与负片；`collect.ts` 那段搬进了 `pipeline.ts` 的 `mergePage`，让缺省验证者够得到。
- 「入围」「语义通过」两列逐格钉死，四态放进同一次渲染。
- 名单里只要有一个人没带来源任务，整张表的入围一律报「无从确认」（U3.b）。
- `found === null` 不把一个确知的入围数抹成「无从确认」：`null` 只说条数不全，不说归人不全。
- 只能由入口证的部分单独成一条判据（P5.j），只由自检认领，那道 `by: "selfcheck"` 的闸才管得着它。
- worktree 里的 `node_modules` 符号链接不许提交；`.gitignore` 写 `node_modules`（不带斜杠）。

### 戊 · 判据一条只装一件能单独坏掉的事

P5.i 原本塞了五件、U3.b 三件，拆出 P5.j，U3.b 的「两个数不得合并」并进 U3.c。`SKILL.md` 写明 P5.i 只补了 `meta.json` 与 HTML 报告那一半，`collect` 的 stdout 仍分不出「没跑完」与「没跑过」。

### 己 · 「不知道」不当成「空」

`mergePage` 里，本条之前采的人（身上没有 `source_tasks`）被第二个任务再搜到时，不给他凭空补一个 `[i]`：已经带着来源才追加。跨平台合并时两边都带着来源才取并集，否则整个报无从确认。负片 `M-U3-j`、`M-U3-k`。

- 教训：**「达标即停」这个判断跑在什么之前，决定了它保护什么。** 跑在每次请求之前，它保护的是预算；
  跑在「每个任务都问过一遍」之后，它保护的才是策略。ADR-06 的教训是「凡是写 `if (x >= target)`
  都要问 x 和 target 是不是同一种东西」，本条在它后面补一句：**还要问这个判断跑在什么之前。**

  因为它引用的那次修复是真的

## 一、事实：轮转保证的是「页」，不是「每个词被问过」

`scripts/collect.ts` 的 `run()`：

```
for round in 0..MAX_PAGES:
  for i in state.tasks（task.json 的顺序）:
    if exhausted(i): continue
    if qualified() >= target_count: stopped = 'target'; break   ← 每一次请求之前
    search(task[i], offset)
```

那句达标判断跑在**每一次**搜索请求之前，第一轮也不例外。所以轮转保证的是
「一个词不连翻四页」，**不是「每个词都被问过一遍」**：第一轮里排在前面的任务只要把目标填满，
内层 `break` 之后外层也 `break`，后面的任务一个请求都不发。而 `qualified()` 是一个**跨平台的总数**，
`TaskState` 里没有任何按平台或按维度的配额。

task.json 的顺序由 Agent 写，没有任何文档说它有意义 —— 而本仓库几处**任务清单形状**的样例
（`skill/references/keyword-strategy.md` 的试探结果样例、`scripts/check/selfcheck.ts` 的夹具）
都把 TikTok 排在前、Instagram 排在后。**于是最常见的受害者正是整个 IG。**

⚠️ **不写成「每一个例子」。** `skill/SKILL.md` 那段续跑对话里的「剩余关键词」把
`#travelessentials(IG)` 列在首位 —— 它展示的是剩余进度而不是任务清单，但一样能被抄，
所以这里不用全称（#128 第一轮评审指出，头一版写的是「每一个能抄的例子」，那句为假）。

两个把它放大的结构性事实（都已记在 `skill/references/providers/tikhub.md`，不是新发现）：
TikTok 视频搜索每页 20 条、有 `offset` 与 `has_more`，一个词最多四页；
**IG 的 Reels 搜索没有分页游标**，一个词只有一页（约 12 条，同一作者多条还会合并成一个人），
`offset > 0` 直接返回空。所以即便顺序公平，IG 的上限也只是「每词一页 × IG 词数」，
第二轮起只剩 TikTok 在跑。

```js
/**
 * 复现用假 fetch：按真实产量建模 —— TikTok 每页 20 条、每条不同作者、都带粉丝数；
 * IG Reels 每词 12 条、每条不同作者、不带粉丝数（与实测一致）。
 * handle 由 keyword+offset 派生，保证跨页、跨词不撞。
 *
 * 写成 .mjs 而不是 .ts：`--import` 的预加载由 node 自己处理，轮不到 tsx，

 * 但照这条记录重跑的人不在那个钉子底下 —— 纯 JS 没这个问题。

const q = (u, k) => new URL(u).searchParams.get(k) ?? ''
const slug = s => s.toLowerCase().replace(/[^a-z0-9]+/g, '')
const log = []
globalThis.fetch = async input => {
  const url = String(input)
  let body
  if (url.includes('fetch_video_search_result')) {
    const kw = q(url, 'keyword'), off = Number(q(url, 'offset') || 0)
    log.push(`TT ${kw} offset=${off}`)
    body = { data: { aweme_list: [], has_more: 1, search_item_list: Array.from({ length: 20 }, (_, i) => ({
      aweme_info: { desc: `${kw} video ${off + i}`, statistics: { play_count: 5000, digg_count: 100 },
        author: { unique_id: `tt_${slug(kw)}_${off + i}`, nickname: 'x', follower_count: 20000, aweme_count: 0 } } })) } }
  } else if (url.includes('instagram/v2/search_reels')) {
    const kw = q(url, 'keyword')
    log.push(`IG ${kw}`)
    body = { data: { data: { count: 12, items: Array.from({ length: 12 }, (_, i) => ({
      caption: { text: `${kw} reel ${i}` }, play_count: 3000, like_count: 50,
      user: { id: String(i), username: `ig_${slug(kw)}_${i}`, full_name: 'y', is_verified: false, is_private: false } })) } } }
  } else if (url.includes('tiktok/web/fetch_user_profile')) {
    body = { data: { userInfo: { user: { uniqueId: q(url, 'uniqueId'), nickname: 'x', signature: 'hi', verified: false, bioLink: { link: 'https://example.com' } },
      stats: { followerCount: 20000, videoCount: 50 } } } }
  } else if (url.includes('fetch_user_info_by_username')) {
    body = { data: { username: q(url, 'username'), full_name: 'y', biography: 'hi', bio_links: [{ url: 'https://example.com' }],
      follower_count: 20000, following_count: 100, media_count: null, is_private: false, is_verified: false } }
  } else {
    body = { data: {} }
  }
  return new Response(JSON.stringify(body), { status: 200, headers: { 'content-type': 'application/json' } })
}
process.on('exit', () => { console.error(`[fake] 搜索请求顺序:\n  ` + log.join('\n  ')) })
```

## 二、四条把「少」推向「零」的连带成因

都用同一套夹具跑过。**它们各自独立**，第一页保证只修掉第一条与第二条的一半。

1. **达标停下之后 `--resume` 救不回 IG。** 续跑从第 0 轮第 0 个任务重来，那句判断在第一个请求之前
   就成立；`keywordsResumeWillRun` 返回空，于是收尾那句话说「续跑不产生新的请求」，
   而 stdout 的 `pending_keywords` 里明明还列着两个 IG 词。`collect` 只接受 `--budget`，
   **没有抬高 `target_count` 的参数**；手改 task.json 抬高之后，多出来的额度先被排在前面的
   TikTok 词翻第二、三页吃掉，IG 照样轮不到（实测目标 50→100 后续跑，TikTok 60→100，IG 仍 0）。
   而 `SKILL.md` 写着「人不够，再多找点」也走 `--resume` —— 这条路在达标停下时什么都不做
   ⚠️ **这一条只在「补全没把人筛掉」那种情形下成立，本节第 3 条讲的正是它不成立的那种** ——
   `qualified()` 在补全把真实粉丝数写回之后会掉回目标以下，续跑照样去抓。见第十三节。
2. **预算续跑循环让 TikTok 越翻越深，IG 永远不再被看。** 页数上限是**每次运行**的轮数，
   计数只在内存里；预算中途用尽时翻满四页的 TikTok 词不会被标 `done`，续跑后从 `offsets`
   接着再翻四页。IG 词在第一页之后就进了 `done`，永远跳过。实测两个 TikTok ＋ 一个 IG、
   预算只够 8 次，用尽后续跑：一个 TikTok 词累计八页，IG 零次新请求。
   这同时违反 `SKILL.md` 写的「单关键词页数上限 4 页」
3. **IG 的人按「粉丝数未知」计入达标，补 profile 之后才被闸门筛掉 —— 那时循环早停了。**
   P1.g 要求入池时未知放行，这没错；但采集期的 `qualified()` 因此对 IG 偏乐观。
   实测 IG 排前面、目标 50、假 profile 让 IG 粉丝数落在下限之下：`stopped=target`，
   累加器里 IG 24 人，交付物里 IG 0 人，总数还低于目标。
   **今天 TikTok 在前的配置走不到这条**（IG 根本没被数进去）；**第一页保证落地之后它会真的发生** ——
   处置在第六节
4. **免费额度下 IG 端点返回 402，一个 402 让整轮以出错退出，而报错不点名平台。**
   `tikhub.md` 记着 IG 端点不吃 free credit；402 不重试直接抛，入口转成 `stopped='error'` 退 1。
   TikTok 在前时，第一轮 TikTok 跑完、第一个 IG 请求就把整轮打断：profile 一个没补、
   关键词一个没标完，而 stderr 只说「余额不足」。`probe` 遇 402 也直接 `break`，
   后面的 IG 词连一行试探结果都没有。**这条与调度无关，第一次用的人最容易撞上**

| **F9.b** | 预算不够给每个任务抓第一页时，按 P3 停下（退 3、存断点），从未查询的任务如实列出，**不得为了抓齐第一页超出预算** | 同上 |
| **F9.c** | 续跑时，没抓过第一页的任务会被查询，即使当前已经达标；已抓过第一页的任务在达标后不再查询。**「续跑会去抓哪些」只此一份判定**，调度与「续跑要不要花钱」那句话共用它 | `lib` 的纯函数 → 单元断言 |
| **F9.d** | 第一页之后的分页仍按达标判断停止 | 同上 |
| **F9.e** | 任务目录里没有分页记录表时，读作「无从确认哪些任务查过」：不发请求，续跑那句话如实说明；**不得读作「都没查过」去发请求，也不得读作「都查过了」** | 入口 → 自检 ＋ 负片 |

F9.c 的后半句是结构要求，同 `needsProfile` 的先例（ADR-25）：补全循环和账单各写一份表达式时，
**先改的那边不会报错**。F9.d 是范围边界，按 ADR-67 它必须可失败 ——
一条把 IG 也翻到第二页、或者达标后继续翻页的实现让它红。
F9.e 是三态在 `task.json` 上的落点：**「没有那个键」和「没有那张表」是两件事。**

### 与红线的交点，以及三条连带的判据

| 交点 | 裁决（红线在场，结论已定，只是写下来） |
|---|---|
| **F9 × P3**（不超预算） | P3 赢。第一页保证在**达标判断**之前生效，不在**预算**之前；预算不够时照旧退 3 存断点，没抓到的按 P5 如实列出 |
| **F9 × P1**（不填默认值） | 不设任何默认的平台配额。用户没说，就只有「每个任务一页」这条机械保证；IG 占多少由 Agent 出了几个 IG 词决定，那是判断层的事。同 `docs/CONVENTIONS.md` 第 7 条对预算的处理 |
| **F9 × D6** | 续跑会去抓的 ＝ 没抓过第一页的任务 ∪（未达标时）其余未完成的任务。**D6.c 据此退役** —— 它现在的判据是「那一刻还差不差人」，而 F9.c 让第一页不受这个判断约束，于是这句为假。判据不改含义、不回收复用（ADR-67 第二节连「改窄」都算改含义），所以退役、用下一个字母。⚠️ 本行原先引的是 D6.c 的旧正文（「达标提前停下时那些词一个都没碰过，续跑一个都不会去抓」）——**那句不用等 F9 就已经是假的**，已按第十三节改掉 |
| **F9 × F1**（只问三个问题） | 不新增必问项 |

三条连带的判据，与 F9 同一批但各自独立：

- **P5.i（红线）**：`meta.json` 与 HTML 报告必须列出任务里**从未发出过搜索请求**的关键词与平台；
  「未查询」「查了 0 命中」「命中 N 人」「无从确认」四态可分，从未查询的平台不得从「平台」那一行
  静默消失；未查询的行不得带出 `0%` 这类看起来像测量值的数（渲染口径同 P1.e）
- **U3.b**：关键词表按**关键词×平台**列出任务里的每一个，包括 0 命中的与从未查询的；
  「找到」按搜索命中数计，另列「入围」，两个数不得合并
- **D6.g / D6.h**：前者接替退役的 D6.c；后者是「单关键词页数上限跨运行有效」（第二节第 2 条）

**为什么 P5.i 落在 P5 而不是 U3**：U3 管「表里有什么」，P5 管「用户会不会据此做出错误决定」。
IG 从报告里消失，运营的结论是「这个品类 IG 没人」，下次预算就不投 —— 代价由用户承担且不可逆。
**为什么不并进 P1.e**：P1.e 说的是交付表里**人**的字段，落在 `rows.ts` 的 `cell` 上；
关键词表落在另一条路径上，会独立坏掉。这正是 ADR-77 末尾那张欠条说的「三条轴之外的压平点没人守」——
关键词表就是第四处，本条给它补一条轴，但登记在 P5 名下（它是「数据边界」，不是「字段取值」）。

## 四、五处结果承诺，本条当场撤回

按 `docs/CONVENTIONS.md` 第 11 条「描述保证的那句话，没有任何检查看着」，**搜关键词不搜整句、搜全仓不只搜文档**：

```bash
git -c core.quotePath=false grep -n \
  -e '整个 IG 一' -e '每个维度都保证有产出' -e '不让第一个关键词吃掉全部配额' -e '再多找点' \
  825fd2d -- .
```

⚠️ **树钉死、范围是整个仓库**：`825fd2d` 是本条动手之前的那一棵，撤回的对象在那棵树上都还在；
`-- .` 就是全仓，不是只有文档。头一版写着「搜全仓」而命令限在 `skill docs scripts README.md`，
那两件对不上（#128 第三轮评审指出）。这一版两条命中清单我都跑过，逐行相同 ——
**但对不上的时候，改的是命令而不是那句话**，否则下一个人按窄清单核就核不出「全仓」这个结论。

命中里有五处在说一句不成立的话，本条都改成事实：`skill/SKILL.md` 的 Phase 03 那条与续跑那段、
`docs/business-requirements.md` 的「采集必须轮转」那段、`scripts/collect.ts` 的 `run()` 函数头注释、
以及 ADR-06「理由」里那句（记录只追加，所以在**末尾**追一块、开头留一行指针）。
`docs/ARCHITECTURE.md` 锚点表里 `collect.ts` 那一行**本身成立**（第一个词确实每轮只拿一页），
漏说的是「排在后面的任务可能一次都不被查」—— 那一处是**补充**，不是撤回。

同一条命令还会命中 ADR-08 与自检里的「再多找点」，那两处说的是
「`--resume` 在 render 之后不会把已采集的人清掉」—— 那一半今天仍然成立，不在撤回范围里。

**先撤回、后重申，理由与 ADR-66 同**：撤回是响的（读的人知道这里没有保证），
挂着是静默的（读的人以为有）。落地之后再改成新的保证，而且**措辞只说请求、不说产出** ——
一页可以 0 个不同作者、可以被兜底成商家号、可以补完 profile 全被筛掉。
写「每个维度才真的有产出」又会是一句没人看着的承诺。

没有任何测试或变异守着那几句话。**本仓库的验证资产只有三个**：单元测试 `scripts/test.ts`、
变异集 `scripts/check/mutations.json`、自检 `scripts/check/selfcheck.ts`
（`package.json` 里 `test` / `mutate` / `selfcheck` 三条脚本各自的入口；全仓带断言的文件也只有前后两个）。
所以下面这条扫的就是全部，退 1、无输出：

```bash
git grep -e 轮转 -e 各抓一页 825fd2d -- \
  scripts/test.ts scripts/check/mutations.json scripts/check/selfcheck.ts
```

（头一版只写了关键词、没写树也没写路径，照字面跑扫的是整个工作区、二十多行命中 —— 第十三节。
⚠️ 这条**不该**改成 `-- .`：断言说的就是「这三个验证资产里不命中」，扫全仓会把文档也算进来，
反而证不出这句话 —— #137 评审建议扫全仓，那一条没照做，改的是把范围写进散文。）
变异集里唯一碰那句达标判断的是 `M-D6-e`，它守的是相反的那件事。

## 五、登记表的条目不在本条 PR 里 —— 实测它过不了审计

变更文档原先把「ADR ＋ 登记表 ＋ 撤回措辞」放在同一条 PR 里，理由是「先把编号固定下来」。
**动手之前先把那个组合跑了一遍，它过不了。**

把 F9、P5.i、U3.b、D6.g、D6.h 加进 `docs/requirements.json`、退役 D6.c、回写 `docs/SPEC.md`，
不改任何代码与测试，然后跑整条检查链。**审计硬失败**，逐条如下 ——
判定都在 `scripts/check/spec-rule.ts`，**指那两个函数而不抄一个数**：函数是正本，数会漂。

- **P5.i 是红线的验收判据但没有认领** —— 判定在 `scripts/check/spec-rule.ts` 的
  `requirementVerdict`：`r.cat` 是红线时，每一条没认领也没豁免的判据都 `hard++`

  交点里有红线、而没有任何测试认领它，就判硬失败（**不抄它返回的那个字面值** ——
  那同样是会随代码漂的数，#128 第二轮评审指出）

（另有一处不是硬失败但值得记：`spec` 会先拦下「F9 的 adr 指向不存在的决策记录」——
**登记表引用的记录必须先存在**。这一条反而支持「决策记录先合」。）

这两处都不是可以顺手补掉的：

- 认领 P5.i 的测试要断言「报告列出了从未查询的关键词」，而那个行为还不存在 → 测试会红。

**结论：登记表的每一条跟着它的实现与测试一起进主干。** 这不是把纪律放松，是按
`process/6-INTEGRATE.md`「按验收证据切」得到的结果 —— 登记表条目的证据就是认领它的那条测试，

它不改任何行为，所以没有机器证据可给，而这正是它能独立成一条的理由（`6-INTEGRATE.md`「决策记录先于实现合」）。

### 追记 · 第二轮评审：我修第三条的时候，又犯了第三条

第一轮那三条修完之后，评审复核第三条（「算出来的数要么钉树、要么只写命令」），**没通过**。
两点，都成立：

**一、我新补的那条旁证是假的。** 为了说明「这张表不是某一棵树的偶然产物」，我写了
「`git diff 7469901..825fd2d -- scripts/collect.ts scripts/lib/pipeline.ts scripts/providers` 为空」。
那条命令**有输出**。真实情况是：`scripts/collect.ts` 逐字未动，而 `scripts/lib/pipeline.ts`
与 `scripts/providers/tikhub.ts` 在这段区间里都变过（都只改了注释）。

**我是拿另一个区间跑出来的结果推广过去的** —— 本条早几版对齐主干时跑过
`d7e20d7..73eef5f` 那一段，那一段确实为空，于是把结论搬到了 `7469901..825fd2d` 上，
**没有对着写下来的这条命令自己跑一遍**。

这是**同一条 PR 里第三次**犯 ADR-73 那个形状。前两次是第一轮评审指出的（全称量词、没钉树），
这一次发生在**修第三条的过程里** —— 而第三条讲的正是这件事。
改法：只留直接观察（四棵树各跑过一遍、逐格一致）＋一条真跑得出来的单文件命令，
把那句推广出来的断言撤掉并在原地记明它假在哪。

**二、`hard: 1` 也是抄来的数。** 第五节我把「两处硬失败」这个计数去掉了，却在引
`tensionVerdict` 时抄了它返回的那个字面值。**源码里的字面值同样会漂** ——
改成只说判定条件，不抄值。

**这两点合起来是一条更窄的教训**：ADR-73 说「判据落纸那一刻先拿它量一遍这条记录自己」。
我照做了一半 —— 量的是**被讲的那件事**，没量**为了修它而新写的那几句**。
**修一条「不许写没核过的数」的发现时，最容易新写一个没核过的数**，因为注意力在「把它修好」上。
判据要再窄一格：**这一轮新写下的每一条命令，都要在写完之后原样跑一次**，
不能靠「我刚才跑过类似的」。

### 「达标停下之后 `--resume` 一个关键词搜索都不发」—— 假的

这句话我从 #128 一路辩护到第六轮，还拿它当过「把 IG 排前面」的理由。它只在**一种**情形下成立。

**机制就写在这条记录自己的第二节第 3 条里**：达标判断跑在 profile 补全**之前**，
用的是补全前的粉丝数（未知一律放行，P1）；而 `enrichProfiles()` 跑在 `run()` 之后、
把真实粉丝数写回累加器。被闸门筛掉的人一多，`qualified()` 就掉回目标以下 ——
续跑的第一次判断因此不再成立，照常从第 0 个任务开始搜。

**我写下了机制，也写下了与机制矛盾的结论，两段隔着不到一屏。**

实测（夹具同第一节，只把 IG profile 的 `follower_count` 改成 800，低于 `FOLLOWER_MIN`；
3 个 IG 词在前 ＋ 2 个 TikTok 词在后，`target_count` 30，树钉 `origin/main`）：

| | `stopped` | `collected` | 发出的搜索 |
|---|---|---|---|
| 首轮 | `target` | **0** | 3 个 IG 词 |
| 原样 `--resume`（目标一字未改） | `target` | **40** | 2 个 TikTok 词 —— 被跳过的词整词补回 |

**脚本自己一直是对的**：首轮 stderr 打的就是「还有 2 个关键词 没跑完，续跑会继续发请求、继续花钱」
（`keywordsResumeWillRun` 按**那一刻**的 `qualified()` 重算）。
`SKILL.md` 同一份文件里也早写着「照 stderr 说的转述，别自己下结论」—— **是我后加的散文跟它对着干。**

代价是真金白银、而且方向搞反了：照旧版那三句，Agent 会告诉用户「`--resume` 办不到，只能重新
`--config`」，让他为一次本来续跑就能拿到的补采**把已经付过的请求再付一遍**。

改的地方（同一句话的六份副本，`docs/SYNC.md` 那条走查链上每一站）：
`skill/SKILL.md` 两处 · `scripts/collect.ts` 的 `run()` 注释 · `scripts/lib/pipeline.ts` 的
`resumeCostLine` 注释 · `scripts/test.ts` 与 `scripts/check/selfcheck.ts` 的两处注释 ·
**`docs/requirements.json` 的 D6.c 判据正文**（登记表是唯一真相来源，而它里面那句解释是假的；
判据要什么没变，改的是它后半句那个假的理由，`SPEC.md` 已按 `spec-sync --write` 回写）。
**实现一行都没动** —— 它从来就是对的。

### 同一轮里的其余几条

- **`pending_keywords` 不是「没跑过的词」**，是「不在 `done` 里的词」：搜过一页、没到页数上限的也在里面。
  第一节表格第一行那次跑，三个 TikTok 词搜过并贡献了全部 60 人，却和没碰过的词一起列着。
  `SKILL.md` 原先让 Agent 照它说「这些方向没查过」—— 会让用户为已经付过钱的词再付一次。
  改成只说「还没跑完」，并点名这正是 P5.i 要补的洞
- **「本仓库没钉 node 版本」是假的**：`.github/workflows/check.yml` 是 `node-version: '22'`，
  而 `scripts/check/tsx-cmd.ts` 与 ADR-69 都写着「本仓库钉的是 Node v22」。

### 教训：判据不是越窄越好，是得有人替你跑

这条记录前后收了五次判据（钉树 → 新写的命令要跑 → 全称要逐条跑 → 先问依赖了什么没钉住的 →
核不了的事实不要编数）。**五条判据没有一条拦住这一轮的头条**，因为它们都在问「这句话核过没有」，
而这一句我**以为**核过了：我跑过达标停下之后的续跑，只是那次的夹具恰好让补全不筛人。

真正管用的不是第六条判据，是**让别人跑**：这一轮的头条是派出去的复核跑出来的，
用的是这条记录自己第二节第 3 条给的配方 —— 那个配方我写下来了，却从没拿它去量第 1 条。
**自己写的反例，要拿去打自己的结论。**

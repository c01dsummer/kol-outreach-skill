# ADR-191 迁移旧评审时账号规范化不了就拒绝，不再跳过后清掉草稿

- 日期 · 2026-11-10
- 类型：既有缺陷。`agent-review.json` 缺席的旧任务第一次跑 render（或 collect、enrich）时，`migrateLegacyAgentReviews` 把 `creators.json` 里带 fit、fit_reason、outreach_draft 的旧记录迁成正本；平台账号规范化不了的那几条它直接跳过，紧接着的投影按正本重建名单，正本里没有这几个账号，就把它们的这三个字段清掉，再写回 `creators.json`。旧草稿从此在哪里都没有了，入口照样以 0 结束。新增判据 D21.s，按改需求逐条评定，见第二节
- 触发它的事实：#444（ADR-190 第 5 片）CodeRabbit 第 6 轮提的 Major，当时以超出那片范围驳回；需求所有者 2026-11-10 11:38Z 在项目线程里答「另开pr修」。对着主干 `abb3664` 的 `prepareTaskReviews` 喂三条旧记录（handle 含 `-`、平台写成 youtube、handle 为空，各带 outreach_draft），三条都不报错，迁出的正本里没有它们，投影出来的 outreach_draft 全是空
- 冲击的需求：D21（新增 D21.s）
- 结论：采纳。人批痕迹：需求所有者合入本条那条 PR
- 理由：迁移是旧任务唯一一次把这些判断搬进正本的机会，跳过等于删除，而用户看不到任何提示。拒绝而不是原样留着：正本的键就是规范化后的平台账号，留一条没有键的评审，后面的投影、合并、导出都要为它另开一条路；拒绝时什么都还没写，用户改正那条的 platform 或 handle 再跑就迁得进去
- 连带改动：`scripts/lib/review-projection.ts`（迁移那一圈：规范化不了的旧记录攒起来，一圈走完以 `ReviewInputError` 一并抛出）· `scripts/lib/task-reviews.ts`（接住它，每条前面加上正本文件路径与「缺席」）· `docs/requirements.json` 新增 D21.s、D21 的 adr 加 ADR-191、`docs/SPEC.md` 照它生成 · `scripts/test.ts` 组 `d21-task-reviews` 加一个用例块 · `scripts/check/mutations.json` 新增 M-D21-ak–ap，M-D21-j、m、ae、ah、aj 的锚点照新代码改写 · `scripts/check/launches.json` 照完整检查写回 · `skill/references/outreach-draft.md` 迁移那一句补上 render 以 2 结束时怎么办 · ADR-130 末尾一块补充（它第 73 行「不迁移该非法身份的 fit」在正本缺席、记录带旧判断时已变成拒绝）

## 一、决定

`agent-review.json` 缺席时，按 D21.j 本该迁入的旧记录 —— 带 fit、fit_reason 或 outreach_draft，没有新评审字段，`review_status` 缺席或为「未评」—— 只要有一条的平台账号规范化不了，迁移就整体拒绝：一条也不迁、什么文件都不写，以 `ReviewInputError` 交给入口，render、collect、enrich 照它们对评审输入错误的原有处理以 2 结束。错误里逐条写出正本文件路径、是 `creators.json` 第几条、platform 与 handle 的 JSON 原值、带着哪几个字段、规范化为什么失败，以及「改正这条的 platform、handle，或删掉这几个字段后再跑」（D21.s）。

几条坏记录一次报完，不是碰到第一条就抛：用户改一条跑一次、再报下一条，旧任务要来回好几趟。

不在本条范围里、照旧的：

- 没带这三个字段的坏账号照常跳过 —— 它们没有要迁的判断，投影也清不掉什么。
- 带新评审字段、或 `review_status` 不是「未评」的记录本来就不迁（D21.j），坏不坏都照旧跳过；`skill/references/outreach-draft.md` 那一句对这种情形早就说了「render 迁不回这些人」、让用户先找回原正本。
- 正本在场时不迁移，旧记录的坏账号不读。

## 二、按改需求逐条评定

- 红线：P1–P5 都不涉及。拒绝发生在投影与写回之前；render 不花钱，collect、enrich 在准备评审时就拒绝，排在开账与请求之前（它们对评审输入错误本来就是这个次序）
- 缩范围还是降标准：收窄的是能跑通的旧任务。被拒的那种原先以 0 结束，但代价是悄悄丢掉用户写过的草稿；改成拒绝是需求所有者「另开pr修」那句话的落地，拒绝而不是别的修法是本条替他选的，合入即拍板
- 覆盖还是可信：可信上升 —— 「render 把旧评审迁成正本」从此对每一条带判断的旧记录都为真，做不到时会说
- 可逆：可逆。被拒时 `creators.json`、`agent-review.json` 原样不动，改了那条记录重跑即可

## 三、怎么验

- 先红：`cb8d41d` 只加了判据与测试，迁移照旧。三种坏账号（handle 含无效字符、平台不认、handle 为空）的「拒绝」与「指出」六条断言红；「不落盘」三条与「没有旧判断字段的坏账号照常准备」绿 —— 前者在旧代码上不报错也就不写，后者说的是不多拒，旧代码本来如此，它们靠变异证明能红（见下）。红的那一版断言名由模板拼出，「旧判断」与「handle」之间没有空格；之后改成逐字写死的名字（变异的 `kills` 是静态扫出来的，拼出来的名字扫不到），并加了带新评审字段、`review_status` 已评、正本在场三个照常准备的用例。
- 变异（都由 `d21-task-reviews` 抓）：M-D21-ak 去掉那句 `throw`（三条「拒绝」红）；M-D21-al 去掉「没带这三个字段就跳过」（没有旧判断字段的坏账号也被拒）；M-D21-am 不说第几条、M-D21-an 不说正本路径（各让三条「指出」红）；M-D21-ao 在迁移之前先写出一份正本（三条「不落盘」红）；M-D21-ap 碰到第一条就抛（「两条旧判断都规范化不了时一次报完」红）。M-D21-j、m、ae、ah、aj 的意思没变，只是锚点跟着新代码改了写法。M-D21-ao 是欠条清点时发现「不落盘」三条没有任何变异能让它们红才补的，M-D21-ap 与它守的那条断言是独立复核指出「一次报完」没人验才补的；完整变异一步对这十一条连同其余全部跑过，红的断言与 `kills` 逐字一致。
- 入口实跑（测试只到 `prepareTaskReviews`，这一步补的是 Skill 那句话说的入口行为）：建一个没有 `agent-review.json` 的旧任务，`creators.json` 两条，第 2 条 handle 为 `bad-name`、带 fit 与 outreach_draft。render、`collect --resume`、enrich 各跑一次，都以 2 结束，stderr 写出正本路径、第 2 条、原值、字段、原因与怎么改，三个文件的 sha1 前后相同、没有新文件。把 handle 改成 `bad_name` 再跑 render，以 0 结束，正本里 `tiktok:bad_name` 的 outreach_draft 是原来那句。

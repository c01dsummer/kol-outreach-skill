## 二、实现怎么对上原文

| 原文 | 实现 |
|---|---|
| 就绪行「读取任何输入（命令行参数、配置、`task.json`）之前」 | 三个入口 import 之后的第一句 `obsReady(...)`；collect 读注入文件排在它后面 |
| 预留行「每一次预算预留尝试写一行，成没成都写」 | 三个入口的预留都经 `Budget.reserve`，那里一处写：成了的在保存回调之后、返回去发请求之前；被拒的在抛出的那一刻 |
| `scope` | 看入口，不看账：collect、enrich 是 `task`，probe 是 `process`。账坏了的时候账上的 `scope` 读不出，按入口才总写得出 |
| `attempt_id` | 预留之后账上那笔未结预留的序号；只在 `task` 且 `reserved` 时写 |
| 五种原因 | 抛出点当场标上：根预算与账上上限对不上（账本身认得、合起来不可用）→ `root-conflict`；账缺席、坏、版本认不得 → `ledger-unavailable`；账上有未结预留 → `pending`；额度不够付这一次 → `budget`；这次预留存不进、或本跑早先已有保存失败 → `save-failed` |
| SP-R、SP-200、SP-N200、SP-NS | `Budget` 每次调保存回调时说明这是哪一次：预留之后是 SP-R；结算之后按结果分，HTTP 200 是 SP-200，别的 HTTP 状态是 SP-N200，没拿到状态是 SP-NS。collect 的回调先问注入、再写盘 |
| SP-BUD「注入时作者文件和 `task.json` 都不写」 | collect 收尾那次 `stopped === 'budget'` 的保存先问注入，抛出时两样都还没写 |
| 「和磁盘写失败走同一条路」 | 注入就是在保存的位置抛一个错：前四个点经 `Budget` 记成 persistence-failed、锁住本运行，与真的写盘失败同一个 catch；SP-BUD 与那次保存真失败一样从 `main().catch` 退 1 |
| 未命中记录「退出时如果注入一直没生效」 | 读到注入文件就挂 `process.on('exit')`，`process.exit` 的各条路都经过它 |
| 「只写 stderr」 | 同步写 fd 2、整行写完才回：入口出错会立刻 `process.exit`，排队没写出去的会丢；预留行因此在那次请求发出之前已经整行进了 fd 2。fd 2 是不阻塞的管道、读的一方慢了时，写会回 EAGAIN 或只写进一截，这时歇一毫秒接着写剩下的。带前缀的行之间的次序就是调用的次序；与 `console.error` 的行之间只在 stderr 没塞满时如此（塞满时那些行排在 Node 自己的队列里晚一步出去），原文也没许诺 |

两样都关着时，`obs.ts` 除了看一眼 `.kol-save-fault.json` 在不在，什么也不做；`Budget` 多出的那一步也只是算单价、问序号，不碰盘、不改账。

注入只让选中的那一次保存不写。前四个点命中之后，collect 照真实保存失败的老路再做一次收尾保存（作者文件与 `task.json`），那一次没被选中、照常写，所以盘上的 `task.json` 会带着那笔没写成的预留或终态。命中行的 `not_written` 说的是那一次保存，不是说盘上从此不变；真实的写盘失败若只坏那一次，盘上也是这样。冻结套件 G3-14 那几例本来就容许这一点（`g3.ts` 里「pending 可有可无」）。

## 三、为什么不登需求登记表

登记表里的判据说的是用户拿到什么。这份契约在平时一个字节都不改变用户拿到的东西，它是给测试看的接口，和 ADR-70 的观察器同一类，只是一半长在入口里。需求方逐字确认的是对外文档里的原文，验收的对象是那段原文，不是一条新编号。

控制文件放进去，collect 会照它让一次保存失败。这是对外可见的行为，所以原文写明了「平时使用不需要、也不应该放这个文件」，README 也说了一句。哪天评审认为这一面也该有一条判据守着，就走 `process/2-CHANGE.md` 补登，不在这里替它定。

变异因此记在 `harness` 名下，这是把它撑宽了用：`scripts/check/mutate.ts` 第 167 行说这个名下守的是检查链本身，而这些变异改的是入口与 `scripts/lib/` 的产品代码。记在任何一条真实需求名下都是顶替，那条需求的认领会凭空多出几条。代价是审计按需求数变异时数不到它们，它们只在变异一步里被抓或存活。哪天补登，跟着改记到新编号名下。

## 四、做不到字面的几处

> ⚠️ 欠条：原文「入口给人看的提示从不以那个前缀开头」只在提示不以用户给的文字开头时成立。现在有几句提示是把用户给的东西放在行首的，比如 probe 配置出错时那句以配置路径开头，collect 出错时 `main().catch` 原样打出的报错。用户真把路径起名成以那个前缀开头，那一行也会以它开头，按前缀剥掉的就多了一行。正常使用碰不到；测试观察用的路径都是观察器自己起的 · 来源：本条作者自记 · 档：登记 · 重启条件：下次有改动碰到这几处报错的写法，或同一缺口被点名，先到为准

> ⚠️ 欠条：原文「每一次预算预留尝试写一行」有两种尝试写不全。一种是价目里没有的端点，算不出单价就不写这一行（预留照样抛 `unknown-price`）。另一种是运行时缺精确 JSON、尝试序号到顶，这时写成 `ledger-unavailable`，那是五种里最近的一种，字面并不贴。这两种都只在实现有缺陷或运行时不对时出现，调用方现在走不到。还有一处是原因的边界：账本身认得、而根上 `budget_usd` 缺席或读不出时，也报 `root-conflict`；原文「根预算与账上的上限冲突」说的是两边都有值，这一种算不算冲突，原文没说，续跑走不走得到这里也没核 · 来源：本条作者自记 · 档：登记 · 重启条件：下次有改动碰到 `scripts/lib/budget.ts` 的 `reserve` 或价目表，或同一缺口被点名，先到为准

被信号硬杀的那一跑不经过 `exit`，没有未命中记录。原文说的是「退出时」，硬杀不算退出，不另登。

## 六、怎么验

测试先于实现，由另一个上下文写：它只读了确认的原文、对外文档与自检夹具，没读入口与 `scripts/lib/` 的函数体，写成两个自检组，起真实入口、喂假 fetch，对着实现缺席先看红。哪些断言先红、哪些在缺席时就绿（关着时什么都不写、未命中与文件不合格时退出码不变、probe 与 enrich 不理控制文件），见本条那条 PR 的正文。每一条可观察的行为配一条指向自检的变异。

独立复核指出三处空档，交回同一个写测试的上下文补：只比行数挡不住「响应处理完才写 reserved 行」，补了一例让假 fetch 在第一个 200 交还之前把入口杀掉；文件不合格时只有 `not-json` 一例判了 null，补成每一例逐字段判；就绪行原来只在配置路径不存在时判，那时命令行参数已经读过，补了三个入口不带任何参数的一例。这一轮写测试的上下文对「读不出的字段」的读法是：`point` 不在五个里、`occurrence` 不是正整数，都算读不出；`point` 读不出时 `seen` 没有保存点可数，原文没定，它不判，实现写 `null`。

开 PR 后评审第一轮指出：fd 2 是管道时，进程里一碰 `process.stderr` Node 就把它设成不阻塞，读的一方慢了、管道满着，同步写就抛 EAGAIN；预留存好之后那一句抛出去，请求就不发了，账上留一笔没结的预留。本机复现过（管道满着时 `writeSync` 回 EAGAIN）。照 `process/README.md` 回应评审的做法先写测试看它红，这一例是写实现的上下文写的：预加载换掉 `fs.writeSync`，每条带前缀的行头一次回 EAGAIN、第二次只写进 10 个字节，同一目录再跑一次，要求 stdout、stderr、退出码与顺顺当当的那一跑逐字相同 —— 对着未修的代码，入口在就绪行那一句以 1 崩掉；修成整行写完才回之后绿。配两条变异：M-H186-aj（回 EAGAIN 不等）、M-H186-ak（只写进一截也当写完）；记录改写进文件之后，这两条与这一例由 ADR-187 撤下。

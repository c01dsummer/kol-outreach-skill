## 一、要用到的事实，各找谁要（`process/3-BUILD.md` 第 8 条）

| 要用到的事实 | 找谁要 | 给机器读的还是给人看的 |
|---|---|---|
| 一个文件碰没碰起子进程的模块 | TypeScript 的语法树：模块名这个字符串字面量在不在；`require`、`import()`、`getBuiltinModule` 的实参是不是字面量；`execve`、`binding` 这两个名字出现没有 | 机器（编译器的语法树，不建类型检查的程序） |
| 一个导入是不是纯类型的 | 语法树上那条语句的 `type` 修饰 | 机器 |
| 仓库里有哪些文件 | `git ls-files -z`（受控文件加没被忽略的新文件，空字符分隔，路径不加引号） | 机器 |
| 基线 | 体量闸门的 `resolveBaseline` | 机器 |
| 基线那份登记表 | `git ls-tree -z` 答有没有，`git cat-file blob` 读内容 | 机器 |
| 哪些文件可以一直碰、为什么 | 登记表的「登记」一节，理由由评审读 | 项目定格式、由闸门校验格式的标记；理由对不对是人判的 |

## 二、检查怎么判

`npm run child-process-use`，检查链里排在外部工单号闸门之后：

1. 认三类：模块名（`'child_process'`、`'node:child_process'` 字面量出现在任何位置，纯类型导入除外）；动态取模块（实参不是字面量，`pathToFileURL(…)` 的结果除外）；进程内部的口（`execve`、`binding` 这两个名字出现在任何位置：属性访问、按名字导入、解构；与 `process[不是字面量]`）。宁可多报：主干上 `scripts/worker-output-contract-test.ts` 里回执对象的 `binding` 字段也被记了，那份文件挪的时候优先给字段改名；进「登记」是按文件放行、不分类别，之后那份文件真去导入模块也不会再响。
2. 登记表两节：「登记」可以一直碰，每个文件写理由；「待挪」现在碰着，等通用启动函数与 git 入口有了挪过去，只有名字。
3. 判红：不在两节里的文件碰了；「待挪」比基线多了；「待挪」里的文件已经一处都不碰还挂着；登记表里的文件不在仓库里；登记表形状不对。基线那份读不出、解析不了，或基线上有这道闸门却没有登记表，无从判断，以 1 结束。
4. 「登记」比基线多出的行不红，单独列出来给评审看。
5. 基线上还没有这道闸门（就是本条这条 PR）：待挪不比基线，登记表整份列给评审看。
6. 主干上只报不判，与体量闸门同一个理由。

本条合入时：「登记」4 个（本闸门的判定、计数预加载、零请求观察器的预加载、缓存入口的父进程），「待挪」27 个（原有 26 个加本闸门的入口；入口自己调 git，等 git 入口有了一起挪）。从此新文件不能直接碰。

## 三、认不出的

下面这些是独立复核实测过、语法树这一层认不出的（都要故意绕才用得上；起 git 的那一部分要靠运行时拒绝兜，见第四节，不在本条）：

- 写在字符串里的代码：落成文件再去跑（例：几份 `-data.ts` 把整段源码放在字符串里，跑它们的那几份测试在「待挪」里），或当场执行（`eval`、`new Function`、`new Worker(…, { eval: true })`）。
- 换了形状的动态取模块：`require` 外面套括号、类型断言或 `!`；`process['getBuiltinModule']`；`registerHooks`；改名导入的 `createRequire`、`getBuiltinModule`；先声明后赋值；把 `require` 存进别的变量、放进对象或参数默认值；`.call`、`.apply`、`Reflect.apply`；`module['require']`；`Module._load`；自己定义一个同名的 `pathToFileURL`；`process` 换个名字再取下标。
- 不被扫的文件被一句字面量加载带进来：扩展名不在扫描之列的（`require('./x.txt')`）、被忽略的目录、子模块、目录软链底下的文件；第三方包（今天依赖里只有 esbuild、tsx、typescript）。
- 一条 PR 同时把登记表与判定文件改名，基线上两样都找不到，闸门按「还没有这道闸门」只列不判；同时删掉、或只删登记表，是红的。读的人看到那句「基线上还没有这道闸门」要警觉。
- 主干上「只报不判」有例外：登记表坏了照样以 1 结束；主干若丢了登记表，补回它的那条 PR 自己也会被「先合主干」挡住，要需求所有者直接在主干上修。
- 分支上一个提交都还没有时，起点判法（体量闸门的 `resolveBaseline`）把它当成在主干上，只报不判。

> ⚠️ 欠条「入口里几处出错的分支没有变异」：入口在 `git ls-files` 出错时以 1 结束，入口上「在不在主干」的翻译只有一种走法被测到；复核另加的变异里这两处存活（前一处坏了是放行方向）。基线登记表算哪一种（git 出错、读不出、解析不了）与读工作区文件出错算不算「已删」，已按 CodeRabbit 的意见挪进判定文件、各有变异 · 来源：第二轮独立复核 · 档：登记 · 重启条件：下一条改 `scripts/check/child-process-use.ts` 的 PR（第三片把它挪进 git 入口时就会改）

> ⚠️ 已还：ADR-217「入口里几处出错的分支没有变异」 · 还在 ADR-220 那条 PR，见它的第三节（入口那组测试加两条，变异 `M-H220-p`、`M-H220-q`）

- 「待挪」不等于调 git 的全部文件：`scripts/check/revisit-due.ts` 经 `revisit-rule.ts` 的 `cliGit` 起 git，`scripts/independent-blackbox-tests-wiring.ts` 经 `observer-run.ts` 起 node，自己都不碰模块。所以「待挪」清空不等于再没有文件起 git。
- 模块对象从登记过的文件经 `any` 或参数递出来；别的会起进程的内建模块（`node:cluster` 的 `fork`）；拿到子进程对象后碰未公开的内部方法。
- 扩展名不是 `.ts` `.mts` `.cts` `.tsx` `.js` `.mjs` `.cjs` `.jsx` 的文件（`.sh`、工作流 yaml 里的 `git`）。
- 软链或 `PATH` 里改了名的 git、`git-upload-pack` 这类 git 自带程序、大小写不敏感的文件系统上写成 `GIT`：这一类只有运行时拒绝认得出（见第四节，不在本条）。

## 四、本条不定的

本条只定一件事：碰起子进程那个模块的，只许登记过的文件，「待挪」只减不增。同属「调 git 只走一个入口」的另两件，各自定案时另立 ADR，本条不预先定它们怎么做：

- 运行时拒绝：起子进程那一刻认出起的是 git 就拒绝。第三节里语法树认不出、又起 git 的那几类，只有它兜得住。
- git 入口：调 git 统一经一个模块。

## 五、它替代什么、什么时候撤

**替代的是「跑」，不替代「读」**（`process/README.md` 第二层「一道闸门该不该建」）。它做的是在语法树上认几样东西、和登记表与起点比：同一棵树永远同一个结论，判据是一条命令。它认的三类是一张手写的名单，形状像「替代读的那些不要建」说的手写名单；不算的理由是：它不判「这一处起的是不是 git」那种要读懂意思的事（第一版设计就是那样，复核找出十类漏网），只判「碰没碰这个模块」，名单盖住的是今天整个集合，漏的变体写在第三节，靠第二片的运行时拒绝兜一层。

> **什么条件下退成只报数**：「待挪」清空以后，连续十条改过 `scripts/` 的 PR 里这道闸门一次都没红过、也没有一条新「登记」—— 口已经收住、没人再往外伸手。

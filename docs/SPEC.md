## 这个产品是什么

一个 AI Agent Skill。运营用自然语言说自己卖什么，Agent 完成从产品理解到可发信名单的
全过程，产出带个性化英文开发信草稿的分层名单。

**不是**采集工具，**不是** SaaS 的命令行版本。是一个替运营做完
「找谁、为什么是他、第一句话说什么」的助手。

背景、痛点排序、成功指标、数据源选型见 `docs/business-requirements.md` 与
`docs/data-source-strategy.md` —— 那两份是调研与论证，本文档是结论。

## 红线为什么是这五条

红线的判据是两条同时成立：**违反的代价由用户承担**，且**不可逆**。

| 编号 | 代价由谁承担 | 为什么不可逆 |
|---|---|---|
| **P1** 不得用默认值填充缺失数据 | 用户基于假数据做投放决策 | 他不会回头重查，错误一路传到预算分配 |
| **P2** 开发信不得含未证实的产品信息 | 用户的信誉，可能的法律风险 | **邮件发出去收不回来** |
| **P3** 未经确认不得超预算 | 用户的钱 | 花掉了就是花掉了 |
| **P4** 已联系/屏蔽的人不得再进名单 | 用户在该创作者处的信誉 | 打扰过就是打扰过 |
| **P5** 交付必须声明数据边界 | 用户以为数据完整，据此压预算 | 预算已投，回不来 |

对照一下**不是**红线的：召回率低是重要需求，但用户会换个词再搜一次；
IG 侧字段解析不准是缺陷，但改完重跑就好。这两条的代价都由团队承担，且可逆。

> 五条已经是上限。再多就需要查表，而**需要查表的红线就失去了「不用想就知道不能碰」的作用**。

# 术语表

> 这个仓库一路做下来起了很多自己的名字：编号的写法、自造的词、普通词的特定意思。
> 它们多半只在某一份决策记录或流程文档里定义过一次，之后到处用。这张表把它们收在一处，
> **每条一句白话、一个例子**，给读不懂的人查，也给要写给需求所有者看的人抄解释。
>
> - **新造一个词、一种编号写法，或者改了一个词的意思，在同一条 PR 里改这张表。**
>   没有检查盯着，靠写的人和评审的人（ADR-207：写给人看的文字用白话、立这张表）。
> - 这里只解释词，**不定规矩**：每个词的完整规则在「出处」那份文件里，两边说得不一样时以出处为准。
> - 写给需求所有者看的东西（消息、选择卡、任务卡、PR 标题与正文开头）里出现这些词，
>   要当场用白话说出来，见 `AGENTS.md`「汇报纪律」。照抄本表的「白话」一栏即可。
> - 本表不写外部任务工具（任务卡）的卡号：任务卡可以引仓库，仓库不引任务卡。

## 一、编号怎么读

| 写法 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 需求编号 `P1`…`P5` | 五条**红线**：绝对不许违反的需求，不参与任何取舍 | `P2` = 开发信草稿里不许有没从产品页证实过的信息，不知道的留空等人填 | `docs/requirements.json`、`docs/SPEC.md` |
| 需求编号的字母 | 第一个字母是类别：`P` 红线，`S` 明确不做的事（范围），`D` 数据（结构、取值），`F` 流程（六个阶段怎么走），`U` 产出物（报告、表格） | `S1` 是一条「不做什么」，`U9` 管名单报告怎么排 | `docs/requirements.json` 的 `categories` |
| 判据编号 `P2.c` | 需求后面加点和小写字母，是这条需求底下的**第几条验收条款**（a 是第一条） | `P2.c` = 「不许编造」这条需求的第三条验收条款 | `docs/requirements.json` 每条需求的 `accept` |
| `ADR-145` | 第 145 份**决策记录**（每拍一次板留一份，放在 `docs/adr/`，只追加不改）。新写时后面跟一句它定了什么 | 「ADR-145（变异的启动次数上限）」 | `docs/adr/README.md` |
| `ADR-70:3025`、`ADR-70 第 3025 行` | 那份决策记录的第几行。**旧写法，不再新写**：文件一改行号就悄悄指错，光看它也不知道指的是什么。新写的改成「哪份记录的哪一节、讲的什么」 | 旧欠条常用这种写法指自己登记在哪 | `AGENTS.md`「汇报纪律」第 5 条 |
| `ADR-145 第三十五节` | 那份决策记录里的第几节（`## 三十五、…` 那个标题）。新写时后面跟一句这一节讲什么 | 「ADR-145 第三十五节（启动数摘要文件怎么写回）」 | — |
| 变异名 `M-P2-c1` | 一条**变异**（见下）的名字：`M-` 后面是它守的需求或判据编号，最后是同一组里的序号 | `M-P2-c1` 故意破坏 `P2.c` 那条验收条款要的行为 | `scripts/check/mutations.json` |
| 变异名 `M-H62-aq` | `H` 开头的变异守的不是产品需求，是**检查链自己**（harness）；`H` 后面的数字通常是登记它的那份决策记录 | `M-H202-*` 守的是 `ADR-202` 那个出资料包的命令 | 同上，这类变异的 `req` 写 `harness` |
| 需求测试组名 `h-launch-rule` | 需求测试（`scripts/test.ts`）里一组断言的名字；`h-` 开头的组测检查链自己 | `h-admission` 测出资料包的命令 | `scripts/test.ts` |
| 自检组名 `launch-count-entry` | **自检**（见下）里一组夹具的名字 | — | `scripts/check/selfcheck.ts` |
| 提交号 `055fc60` | git 提交的前 7 位，指仓库在某一刻的样子（「一棵树」） | 「数字量自主干 `055fc60`」 | — |
| `#484` | GitHub 上第 484 号 PR | — | — |
| 档的那一行 `档：驳回 · 理由：…` | 回复评审意见时第一行的固定写法，说这条意见归哪一类、怎么处理（见下「档」） | `档：本改动 · 去向：a1b2c3d` | `process/6-INTEGRATE.md`「五档路由」 |

## 二、需求与拍板

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 红线 | 绝对不许违反的五条需求 `P1`–`P5`，遇到冲突时别的需求让它 | 预算没经用户同意不许超（`P3`） | `docs/SPEC.md` |
| 判据 | **验收条款**：一条需求底下可以逐条检查的细则 | 「交付表里『未查询』显示成 `未查询`，『查过为空』显示成空白」是 `P1.e` 这条判据 | `process/1-REQUIREMENTS.md` |
| 需求所有者 | 拍板的人，也就是仓库主人 | 「需求所有者合入本条那条 PR」= 他点了合并 | `process/README.md` |
| 人批 / 人批痕迹 | 必须由人拍板的改动；「痕迹」是能指得到他拍过板的东西，通常是他合了那条 PR | — | `process/README.md`、`process/2-CHANGE.md` |
| 交点 | 两条需求撞上了；裁决写在让步的那一方 | 「找得全」和「不超预算」撞上时，前者让 | `docs/requirements.json` 的 `tension` |
| 认领 | 一条测试在代码里写明「我验的是这条判据」（`criterion('P2.c')`），审计据此数每条判据有没有测试 | — | `docs/SYNC.md` 触发表 |
| 作废 | 一条需求不再要了；编号留着、不再给别的需求用 | — | `docs/SYNC.md` 触发表 |
| 反向输入 | 干活时撞见需求本身有错、或者做起来代价远超当初设想，要回头改需求 | — | `process/2-CHANGE.md` |
| 已知缺口 | 知道做不到、明着写出来的地方，不假装做到了 | 「测试和实现是同一个 Claude 写的」登记在 `ADR-04`（同源写成的已知缺口） | `AGENTS.md`「目前已知的缺口」 |

## 三、测试与检查

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 检查链 | `npm run check` 依次跑的那一串检查；任何一步红，PR 就不该合 | 变异锚点 → 体量 → 需求一致性 → … → 启动数 | `AGENTS.md`「检查命令」 |
| 闸门 | 检查链里**会变红、挡住合并**的一步。和「只提醒」相对 | 体量闸门、启动数闸门 | `process/5-DESIGN.md` |
| 只提醒 / 只报数 | 列出来给人看，但不让检查变红 | 「欠条点名提醒」只列、不拦 | `ADR-196`（改到欠条点名的文件时提醒） |
| 变异 | 故意往代码里改坏一处，看测试能不能发现；发现不了说明测试没盖住那里 | 把「未查询」悄悄改成 `0`，测试该红 | `process/4-VERIFY.md` |
| 抓到 / 存活 | 变异让该红的测试红了叫「抓到」；没红叫「存活」，说明那条测试是假的，要修测试 | — | 同上 |
| 验证者 | 跑一条变异时用来判它被没被抓到的那个程序。缺省是需求测试，也可以指定自检 | 变异里写 `by: "selfcheck"` 就改由自检来验 | 同上 |
| 基线 | 不加任何变异时先跑一遍验证者，必须是绿的，否则之后的红不算数 | — | 同上 |
| 锚点 | 变异要改的那一段原文（`find`）；「锚点失效」= 代码改了，那段原文找不到了 | — | `scripts/check/mutations.json` 开头说明 |
| 需求测试 | `scripts/test.ts` 里按需求编号组织的测试 | — | `process/4-VERIFY.md` |
| 自检 | 检查链给自己做的测试：在临时目录里真的起那几个检查脚本，看它们该红时红、该绿时绿 | — | `scripts/check/selfcheck.ts` |
| 夹具 | 测试用的假数据或假环境 | 一个只有三个文件的玩具仓库 | `process/4-VERIFY.md` |
| 负片 | 故意造的反例，用来证明某道检查真的会报红 | — | 同上 |
| 链路审计 | `npm run audit`：逐条数需求和判据有没有测试、有没有变异守着，缺了就报 | — | `AGENTS.md`「审计命令」 |
| 启动数 | 跑变异时程序被启动的次数。启动越多检查越慢，所以定了上限，超了就红 | 每条自检变异最多 50 次 | `ADR-145`（启动次数上限） |
| 体量闸门 / `size-ok:` | 一条 PR 新增的行数分类计，超线就红；要超必须在提交信息最后一段写 `size-ok: <类别> <理由>` 具名豁免 | — | `process/6-INTEGRATE.md`「体量」 |
| 派工 / worker / 分份 | 变异多，要并行跑：派工是决定下一条交给谁跑；worker 是同时干活的那几个进程；分份是 CI 上拆到几台机器各跑一份 | — | `ADR-197`、`ADR-200`（CI 上把变异拆到几台机器跑） |
| 死亡条件 | 一道检查**该撤掉**的条件，立它的时候就写下 | 「要是覆盖从来没真红过，它守的就不是会漂的那部分」 | `process/5-DESIGN.md` |
| 同源污染 | 测试和实现由同一个 Claude 写，测试会跟着实现一起错 | — | `ADR-04`（测试与实现同一上下文写成，登记为已知缺口） |
| 准入读物包 | 给写测试的那个 Claude 的一包资料：有需求和函数签名，**故意没有实现代码**，免得同源污染 | `npm run admission -- P2 <目录>` | `ADR-202`（出资料包的命令） |
| 独立复核 | 让一个没参与写这条改动的人（或 Claude）从头读一遍再评 | 红线改动必须过一次 | `process/4-VERIFY.md` |
| 顺序契约 | 代码里有几处「必须先做 A 再做 B」，对调就会出错；每一处都要有变异守着 | 先保存名单，再写「已去重」的声明 | `docs/ARCHITECTURE.md` |

## 四、评审与登记

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 档 / 五档路由 | 评审意见的分类，决定这条意见怎么处理：**本改动**（这条 PR 自己的错，本次修）、**扩范围**（要的是新功能，另开 PR）、**既有缺陷**（老毛病，另开 PR 修）、**登记**（不是错，记下来以后再说）、**驳回**（意见不成立，写理由） | `档：登记 · 重启条件：…` | `process/6-INTEGRATE.md`「五档路由」 |
| 第几轮 / 从第三轮起只登记 | 评审器每看一次新推上去的代码算一轮；第三轮起不挡合并的意见只登记、不再改本 PR，免得没完没了 | — | `process/6-INTEGRATE.md` |
| 欠条 | 「这里有个问题，知道了但先不修」的登记，写在决策记录末尾的 `⚠️ 欠条` 块里，必须带「重启条件」 | — | 同上「登记怎么做」 |
| 重启条件 | 欠条上写的「什么情况下必须回来修」 | 「下一次有人改 `pipeline.ts` 的排序时」 | 同上 |
| 还欠条 | 把一张欠条要求的事做掉 | — | — |
| 欠条 PR | PR 合入以后，另开一条只往决策记录里补登欠条的 PR | — | 同上 |
| 台账 / 欠条台账 | 把所有欠条和它们的重启条件抽成一张清单（`npm run adr-ledger`），只抽不判 | — | `ADR-86`（欠条台账只抽不判） |
| 欠条清点 | 开 PR 前让几个 Claude 各自对着台账找「这条改动碰到了哪几张欠条的条件」 | — | 本项目的 PR 例行做法 |
| 欠条点名提醒 | `npm run debt-touch`：这条分支改到的文件被哪几张开着的欠条点了名，只列不拦 | — | `ADR-196`（改到欠条点名的文件时提醒） |
| 更正块 `⚠️` | 决策记录不许改原文，后来发现说错了，就在末尾追加一个 `⚠️` 开头的块写更正 | — | `process/2-CHANGE.md`「新内容加在哪」 |
| 同类 | 几份决策记录揭示的是同一种会再犯的错法；攒够三次要考虑写成一条通用的规矩 | — | `docs/adr/README.md`「同类」 |
| 回访 | 每周一自动跑的例行检查，照 `docs/REVISIT.md` 做，往 `ADR-152`（回访台账）追加一块记录，由人合 | — | `docs/REVISIT.md` |
| 候选句 | 回访时发现某一类问题还没有通用规矩，起草的那一句候选规矩，等人定要不要 | — | `docs/REVISIT.md` |
| 合并者核对去向 | 合并之前，合并的人看每条评审意见是不是都有了去向（修了、另开了、登记了、驳回了） | — | `process/6-INTEGRATE.md` |
| 第一片、第二片 | 一件事拆成几条 PR 依次合，每条叫一片 | 「准入读物包第一片只有判定，第二片接上命令」 | — |
| 工作线 | 任务卡上把同一件大事的几张卡挂在一张父卡下面，那张父卡叫工作线 | — | 任务卡约定 |

## 五、普通词在这里的特定意思

| 词 | 在这里指 | 例子 |
|---|---|---|
| 兜底 | 数据缺了就悄悄填个默认值（`?? 0`、`\|\| ''`）。这里是**禁止的**（`P1.b`） | 「粉丝数没查到就当 0」就是兜底 |
| 口径 | 一个数怎么算、一个词怎么定义的那套约定 | 「报价口径」= 报价按什么算 |
| 收口 | 一件事最后收尾、把各种出口统一处理掉的那一步 | 「硬退出收口」= 程序被强制退出时的收尾 |
| 落地 / 落位 | 真的写进仓库并合进主干了；「落位」是放到它该在的那份文件里 | — |
| 主干 | `main` 分支 | — |
| 一棵树 | 仓库在某个提交时的全部文件 | 「同一棵树上谁跑都是同一个包」 |
| 漂 / 漂移 | 两处本该说同一件事的文字，改了一处没改另一处，慢慢说得不一样了 | — |

# 术语表

> 这个仓库一路做下来起了很多自己的名字：编号的写法、自造的词、普通词的特定意思。
> 它们多半只在某一份决策记录或流程文档里定义过一次，之后到处用。这张表把它们收在一处，
> **每条一句白话、一个例子**，给读不懂的人查，也给要写给需求所有者看的人抄解释。
>
> - 这里只解释词，**不定规矩**：每个词的完整规则在「出处」那份文件里，两边说得不一样时以出处为准。
> - 什么时候要改这张表、写给需求所有者看时怎么用它，规则在 `AGENTS.md`「汇报纪律」第 4、5 条和 `docs/SYNC.md` 触发表里「新造一个词」那一行；为什么这么定见 ADR-207（写给人看的文字用白话、立这张表）。

## 一、编号怎么读

| 写法 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 需求编号 `P1`…`P5` | 五条**红线**：绝对不许违反的需求，不参与任何取舍 | `P2` = 开发信草稿里不许有没从产品页证实过的信息，不知道的留空等人填 | `docs/requirements.json`、`docs/SPEC.md` |
| 需求编号的字母 | 第一个字母是类别：`P` 红线，`S` 明确不做的事（范围），`D` 数据（结构、取值），`F` 流程（六个阶段怎么走），`U` 产出物（报告、表格） | `S1` 是一条「不做什么」，`U9` 管名单报告怎么排 | `docs/requirements.json` 的 `categories` |
| 判据编号 `P2.c` | 需求后面加点和小写字母，是这条需求底下**一条验收条款的固定代号**。字母一旦用过就不换，作废的留空，所以不能当「第几条」数 | `P2.c` = 「不许编造」这条需求底下代号 c 的那条验收条款；预算那条红线现存的从 `P3.c` 起 | `docs/requirements.json` 每条需求的 `accept` |
| `ADR-145` | 编号 145 的那份**决策记录**（每拍一次板留一份，放在 `docs/adr/`；编号有空号，不等于第几份）。新写时后面跟一句它定了什么 | 「ADR-145（变异的启动次数上限）」 | `docs/adr/README.md` |
| `ADR-72:600`、`ADR-72 第 600 行` | 那份决策记录的第几行。**旧写法，不再新写**：文件一改行号就悄悄指错，光看它也不知道指的是什么。新写的改成「哪份记录的哪一节、讲的什么」。例外是工具按固定格式读的那几处（见下一行），在换成不会变的名字之前照旧写，旁边加一句白话 | 旧欠条常用这种写法指自己登记在哪 | `AGENTS.md`「汇报纪律」第 5 条 |
| `⚠️ 已还：ADR-N 第 M 行`（还有「已重挂」「收尾」） | 欠条关上的三种写法：已还 = 修好了；已重挂 = 改挂到另一张上，以那张为准；收尾 = 不修了、写明理由。指回原欠条的那个行号是给工具认的。**旧写法，只用于没拆过的记录和历史文件里的老欠条**；拆过的记录，主文件里的欠条只能按名字关：`⚠️ 已还：ADR-N「短名字」`（见下面「欠条短名字」） | `npm run debt-touch` 靠这几个词判断哪张欠条已经关上 | `process/6-INTEGRATE.md`「登记怎么做」、`scripts/check/debt-touch-rule.ts` |
| `ADR-145 第三十五节` | 那份决策记录里的第几节（`## 三十五、…` 那个标题）。新写时后面跟一句这一节讲什么 | 「ADR-145 第三十五节（启动数摘要文件怎么写回）」 | — |
| 变异名 `M-P2-c1` | 一条**变异**（见下）的名字：`M-` 后面通常是它守的需求或判据编号，最后是同一组里的序号。不一致时以它的 `req` 栏为准 | `M-P2-c1` 故意破坏 `P2.c` 那条验收条款要的行为 | `scripts/check/mutations.json` |
| 变异名 `M-H62-aq` | `H` 开头的变异守的不是产品需求，是**检查链自己**（harness）。`H` 后面是这一组的组号：1–70 是早年按顺序编的组号，**和决策记录编号无关**；186 起的新组借用了登记它的那份决策记录的编号 | `M-H62-aq` 守的是预编译父进程的收尾，跟 ADR-62 无关；`M-H202-*` 守的是 ADR-202 那个出资料包的命令 | 同上，这类变异的 `req` 写 `harness` |
| 需求测试组名 `h-launch-rule` | 需求测试（`scripts/test.ts`）里一组断言的名字；`h-` 开头的组测检查链自己 | `h-admission` 测出资料包的命令 | `scripts/test.ts` |
| 自检组名 `launch-count-entry` | **自检**（见下）里一组夹具的名字 | — | `scripts/check/selfcheck.ts` |
| 提交号 `055fc60` | git 提交的前 7 位，指仓库在某一刻的样子（「一棵树」） | 「数字量自主干 `055fc60`」 | — |
| `#484` | GitHub 上第 484 号 PR | — | — |
| 档的那一行 `档：驳回 · 理由：…` | 回复评审意见时第一行的固定写法，说这条意见归哪一类、怎么处理（见下「档」） | `档：本改动 · 去向：a1b2c3d` | `process/6-INTEGRATE.md`「五档路由」 |

## 二、需求与拍板

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 红线 | 绝对不许违反的五条需求 `P1`–`P5`，遇到冲突时别的需求让它 | 预算没经用户同意不许超（`P3`） | `docs/SPEC.md` |
| 判据 | **验收条款**：一条需求底下可以逐条检查的细则 | 「交付表里『未查询』显示成 `未查询`，『查过为空』显示成空白」是 `P1.e` 这条判据 | `process/1-REQUIREMENTS.md` |
| 需求所有者 | 拍板的人，也就是仓库主人 | 「需求所有者合入本条那条 PR」= 他点了合并 | `process/2-CHANGE.md`；本仓库指谁见 `AGENTS.md`「汇报纪律」 |
| 自动档 / 提议档 / 人批档 | 改动按谁能拍板分三档：自动档执行者直接做；提议档执行者只写提案；人批档必须由人拍板。「人批痕迹」是能指得到他拍过板的东西，通常是他合了那条 PR | — | `process/README.md`、`process/2-CHANGE.md` |
| 交点 | 两条需求撞上了；裁决写在让步的那一方 | 「找得全」和「不超预算」撞上时，前者让 | `docs/requirements.json` 的 `tension` |
| 认领 | 一条测试在代码里写明「我验的是这条判据」（`criterion('P2.c')`），审计据此数每条判据有没有测试 | — | `docs/SYNC.md` 触发表 |
| 作废 | 一条需求不再要了；编号留着、不再给别的需求用 | — | `docs/SYNC.md` 触发表 |
| 反向输入 | 干活时撞见需求本身有错、或者做起来代价远超当初设想，要回头改需求 | — | `process/2-CHANGE.md` |
| 三态 | 一个值有三种不同的「空」，不许混：**未查询**（没去查）、**查过为空**（查了，没有）、**值就是 0** | 粉丝数没查和粉丝数是 0 是两回事（`P1`，缺的数据不许填默认值） | `docs/requirements.json` 的 `P1` |
| 正本 / 副本 | 一件事只在一处定义，那一处叫正本；别处复述的都是副本，正本改了副本要跟着改 | 需求编号的正本是 `docs/requirements.json`，`docs/SPEC.md` 的表是它的副本 | `docs/SYNC.md` |
| 已知缺口 | 知道做不到、明着写出来的地方，不假装做到了 | 「测试和实现是同一个 Claude 写的」登记在 `ADR-04`（同源写成的已知缺口） | `AGENTS.md`「目前已知的缺口」 |

## 三、测试与检查

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 检查链 | `npm run check` 依次跑的那一串检查；任何一步红，PR 就不该合 | 变异锚点 → 体量 → 需求一致性 → … → 启动数 | `AGENTS.md`「本项目的具体信息」 |
| 闸门 | 检查链里**会变红、挡住合并**的一步。和「只提醒」相对 | 体量闸门、启动数闸门 | `process/README.md`「往上撤那个方向也正当」 |
| 只提醒 / 只报数 | 列出来给人看，但不让检查变红 | 「欠条点名提醒」只列、不拦 | `ADR-196`（改到欠条点名的文件时提醒） |
| 变异 | 故意往代码里改坏一处，看测试能不能发现；发现不了说明测试没盖住那里 | 把「未查询」悄悄改成 `0`，测试该红 | `process/4-VERIFY.md` |
| 抓到 / 存活 | 变异让该红的测试红了叫「抓到」；没红叫「存活」，意思是验证者没发现这次改动。存活不一定是测试的错：先分清是测试漏了，还是这处改动本来就不改变可见行为（等价变异），见 ADR-02（变异存活时先分清是测试漏了，还是变异等价）| — | 同上 |
| 验证者 | 跑一条变异时用来判它有没有被抓到的那个程序。缺省是需求测试，也可以指定自检 | 变异里写 `by: "selfcheck"` 就改由自检来验 | 同上 |
| 基线 | 不加任何变异时先跑一遍验证者，必须是绿的，否则之后的红不算数 | — | 同上 |
| 锚点 | 一词两义：① 变异要改的那一段原文（`find`），「锚点失效」= 代码改了、那段原文找不到了；② 「模块锚点表」是 `docs/ARCHITECTURE.md` 里登记每个脚本模块管什么的那张表 | 「新增模块请在锚点表里登记」说的是 ② | `scripts/check/mutations.json` 开头说明；`docs/ARCHITECTURE.md`「模块锚点表」 |
| 需求测试 | `scripts/test.ts` 里按需求编号组织的测试 | — | `process/4-VERIFY.md` |
| 自检 | 在临时目录里用假数据把真的入口脚本（采集、补全、导出，以及检查脚本自己）从头跑一遍，看结果对不对。很多产品验收条款是由自检来验的，不只是检查链自己 | 用假的数据源把采集从头跑到尾，看名单里每个人的来源记没记对 | `scripts/check/selfcheck.ts` 文件头 |
| 夹具 | 测试用的假数据或假环境 | 一个只有三个文件的玩具仓库 | `process/4-VERIFY.md` |
| 负片 | 故意造的反例，用来证明某道检查真的会报红 | — | 同上 |
| 链路审计 | `npm run audit`：逐条数需求和判据有没有测试、有没有变异守着，缺了就报 | — | `AGENTS.md`「本项目的具体信息」 |
| 启动数 | 跑变异时程序被启动的次数。启动越多检查越慢，所以定了上限，超了就红 | 每条自检变异最多 50 次 | `ADR-145`（启动次数上限） |
| 字段断言闸门 | 检查脚本里一个判定的返回值这次新加了字段，却没有一条会被测试打红的变异改到给它赋值的地方、也没写「字段不入断言：<理由>」，就红。字段按声明所在的行认（那一行是不是这次新加的，问 git），赋值处问 TypeScript；不读测试源码 | `npm run fields` | `ADR-198` |
| 外部工单号闸门 | 数仓库里每个文件写了几个外部任务工具（本项目是 Linear）的卡号、几条指向一张卡的链接，比 PR 起点多了就红；旧决策记录里已有的留着，只许减不许加 | `npm run ticket-refs` | `ADR-205`（仓库只往里指，不写外部工单号） |
| 起子进程接口闸门 | 起子进程的那个内建模块（`child_process`）只许登记表里的文件碰：「登记」一节写着可以一直碰的文件与理由，「待挪」一节是等着挪进通用启动函数或 git 入口的文件，只许减不许加（ADR-223 起清空）；别的文件碰了就红。另有「测试文件」一节：只给测试用的模块（git 夹具、自检记当前目录那一处、起进程的替身）只许这一节里的文件提到。是「调 git 只走一个入口」的第一片 | `npm run child-process-use` | `ADR-217`、`scripts/check/child-process-registry.json` |
| 通用启动函数（起进程的） | 文件要起进程都经它，不直接碰起子进程的模块（登记表「登记」一节里的文件还直接碰，见那张表）：用法和 Node 的同名函数一样，但只认（程序, 参数数组, 选项）一种写法，并且多两件事 —— 要起的是 git、选项要经 shell，都当场抛错。例：`spawnSync('git', …)` 经它调会直接报错，读 git 要走 git 入口 | — | `ADR-219`、`scripts/check/start-process.ts` |
| git 夹具 | 测试在系统临时目录里建玩具仓库、造提交时起 git 用的模块：能写，但只在临时目录底下、不在本仓库里起，子命令、配置键、环境变量各一张白名单，不合就抛错。与 git 入口分开：入口只答读本仓库的那几问。例：自检给变异派工造一段两个提交的历史经它 | `scripts/check/git-fixture.ts` | `ADR-222` |
| 起进程的替身 | 测试要看「交没交给 Node、交了什么」时，经它把起子进程模块上的函数暂时换成替身或探子，跑完一定换回；不把原函数交给测试。只许测试文件用。例：测通用启动函数「起 git 当场抛错、一次也没交给 Node」时，换上只记次数的替身 | `scripts/check/child-process-stand-in.ts` | `ADR-223` |
| git 入口 | 读本仓库的 git 都经它，不直接碰起子进程的模块：只答它表里列出的那几问（每一问是一串参数的形状，旁边写着谁要问），不在表里的当场抛错、不起 git；每次都带同一组固定配置（中文路径不转义、改名检测开着）。怎么读 git 的答案仍归各判定模块。有同步、异步两版，异步那版给不能同步等子进程的变异派工。例：体量闸门问 `diff --numstat -z <起点> <终点>` 经它，问 `diff --stat` 就抛错 | `scripts/check/git-entry.ts` | `ADR-220`、`ADR-221`、`ADR-217` 第四节 |
| 体量闸门 / `size-ok:` | 一条 PR 新增的行数分类计，超线就红；要超必须在提交信息最后一段写 `size-ok: <类别> <理由>` 具名豁免 | — | `process/6-INTEGRATE.md`「体量」 |
| 派工 / worker / 分份 | 变异多，要并行跑：派工是决定下一条交给谁跑；worker 是同时干活的那几个进程；分份是 CI 上拆到几台机器各跑一份 | — | `ADR-197`、`ADR-200`（CI 上把变异拆到几台机器跑） |
| 死亡条件 | 一道检查**该撤掉**的条件，立它的时候就写下 | 「要是覆盖从来没真红过，它守的就不是会漂的那部分」 | `process/README.md`「往上撤那个方向也正当」 |
| 同源污染 | 测试和实现由同一个 Claude 写，测试会跟着实现一起错 | — | `ADR-04`（测试与实现同一上下文写成，登记为已知缺口） |
| 准入读物包 | 给写测试的那个 Claude 的一包资料：有需求和函数签名，**故意没有实现代码**，免得同源污染 | `npm run admission -- P2 <目录>` | `ADR-202`（出资料包的命令） |
| 独立复核 | 让一个没参与写这条改动的人（或 Claude）从头读一遍再评 | 红线改动必须过一次 | `process/4-VERIFY.md` |
| 第二层 / 第三层 | 一条规矩靠什么守：第二层是有机器检查守着的；第三层是只能靠人自觉的 | 「不写行号」今天在第三层 | `process/README.md`「跨工具：什么是真的可移植」 |
| 硬失败 | 审计里会让检查变红的那一类缺口（相对于只报出来、不变红的缺口） | 红线判据没有任何测试认领 = 硬失败 | `docs/SYNC.md` 触发表 |
| 判定模块 / 纯判定 | 检查链里只做「判断」、不读写文件也不起进程的那部分代码，好测、必须有变异守着；读写文件、起进程的那部分叫入口 | `admission-rule.ts` 是判定，`admission.ts` 是入口 | `ADR-62`（判定模块必须有变异） |
| 选组 / 全跑 | 跑变异时只跑和它有关的那几组测试叫选组；整套测试都跑叫全跑 | — | `process/4-VERIFY.md`「只跑验证者的一部分时」 |
| 顺序契约 | 代码里有几处「必须先做 A 再做 B」，对调就会出错；每一处都要有变异守着 | 先保存名单，再写「已去重」的声明 | `docs/ARCHITECTURE.md` |
| 权威（某件事实的） | 本来就负责回答这件事的那个工具，它给的是确切答案：编译器和语言服务、git 专门给机器读的输出、真跑一遍的结果。和「从给人看的文字里推」相对 | 「改了哪些文件」的权威是 git 给机器读的文件名清单（`--name-only -z`），不是 diff 正文 | `process/3-BUILD.md` 第 8 条、`docs/CONVENTIONS.md` 第 13 条 |
| 找谁要的表（事实来源表） | 写代码前列的一张表：这个功能要用到哪些事实、各找哪个权威要、拿到的是给机器读的还是给人看的。先过独立复核再写代码。本仓库写在决策记录的「要用到的事实，各找谁要」那一节；不写代码的只写一句「不列：理由」；从 ADR-224 起的新记录缺了就红 | 「这次新加了哪几行 → 每个文件的 `git diff -U0` 块头」 | `process/3-BUILD.md` 第 8 条 · `docs/CONVENTIONS.md` 第 13 条 · `scripts/check/adr-fact-table.ts` |
| 解除表（同一处连着两轮的） | 同一处连着两轮被评审挑中、停手改了设计以后，在决策记录里写的一张固定格式的表：哪一处、旧做法最后一轮是哪个提交、新做法写在哪。写了的那一处，那一轮和之前的不再算，之后又连着两轮落回来再拦 | 「`scripts/check/x-rule.ts#keyOf` · 0a1b2c3 · 本记录第二节」 | `process/6-INTEGRATE.md`「同一处连着两轮被挑出毛病」· ADR-225 · `scripts/check/same-spot-rule.ts` |
| 评审的一轮（起轮） | 同一个版本上的全部行内评审意见算一轮；回复不算意见。同步主干的合并、空提交不起轮，锚在它们上面的意见算进下面最近那个起轮的版本；没有意见的版本不算一轮。锚在已被推掉的版本上的单独成一轮（链外）。与「第几轮」数法不同：「第几轮」数同一版代码上的全部评审意见、把开 PR 前的复核算第一轮；这里只数挂在行上的意见、不含开 PR 前的复核，同一条 PR 两种数法的轮数可能不一样 | 「#471 的 106 个提交里，有意见的 23 个版本是 23 轮」 | `process/6-INTEGRATE.md`「先定义『一轮』」· ADR-225 第二节 |

## 四、评审与登记

| 词 | 白话 | 例子 | 出处 |
|---|---|---|---|
| 档 / 五档路由 | 「档」在这里有三种意思，看上下文：① 评审意见的分类（最常见，下面说的是这种）；② 改动的自动档、提议档、人批档（见第二节）；③ 名单排序里的「一档」（同一层同一分数里再分先后）。评审意见的分类，决定这条意见怎么处理：**本改动**（这条 PR 自己的错，本次修）、**扩范围**（要的是新功能，另开 PR）、**既有缺陷**（老毛病，另开 PR 修）、**登记**（不是错，记下来以后再说）、**驳回**（意见不成立，写理由） | `档：登记 · 重启条件：…` | `process/6-INTEGRATE.md`「五档路由」 |
| 第几轮 / 从第三轮起只登记 | 同一版代码上收到的全部评审意见（人和机器都算）算一轮；开 PR 前的复核是第一轮；只为同步主干的提交不起新的一轮。第三轮起不挡合并的意见只登记、不再改本 PR，免得没完没了 | — | `process/6-INTEGRATE.md`「先定义一轮」 |
| 阻塞项 | 不处理完就不能合的评审意见：这条 PR 自己引入的正确性错、触碰红线的、安全问题。不管第几轮都要处理 | — | `process/6-INTEGRATE.md`「从第三轮起只登记，阻塞项除外」 |
| 欠条 | 「这里有个问题，知道了但先不修」的登记，写在决策记录的 `⚠️ 欠条` 块里，必须带「重启条件」 | — | 同上「登记怎么做」 |

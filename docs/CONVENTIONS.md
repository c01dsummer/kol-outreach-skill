# 在这里是错的通用做法

> 写代码前扫一眼。**你的默认做法在这里大概率是错的。**
>
> 这份清单不是风格偏好，是**会直接违反红线的**通用最佳实践。
> 能变成检查的已经变成了检查（见每条末尾），剩下的靠读这份文档。

---

## 1. 防御性默认值 —— 违反 P1

```ts
followers: a?.follower_count ?? 0      // ✗
bio: u?.signature ?? ''                // ✗
```

看起来专业，实际是**把「不知道」伪装成「知道」**。

具体会发生什么：TikHub 某次没返回 `follower_count`，我们记成 0，
`passesFollowerGate` 判定不合格，这个真实创作者从名单里**凭空消失，且没有任何人知道**。
用户不会发现 —— 他看到的是一份看起来正常的名单。

正确做法是**在类型层面就分开**：

```ts
followers?: number        // undefined = 没查到，不是 0
email?: string | null     // undefined = 没查 / null = 查了没有 / string = 有
```

`strict` 会强制每个使用点显式处理，写不出 `?? 0` 也编译不过。

> **检查**：`npm run lint` 扫描敏感字段上的兜底写法。
> 确有必要时在该行加 `// p1-ok: <理由>`，理由必填。

---

## 2. 优雅降级 —— 一半对，一半错

这条要分清，因为**本项目同时要求降级、又禁止降级**：

| | 做法 | 判定 |
|---|---|---|
| **能力降级** | 不运行公开指标或没有外部增强 → 主流程照常走完，并**说明少了什么** | ✅ 这是 F5，必须做 |
| **数据降级** | 拿不到粉丝数 → 用估算值 / 用上次的值 / 用 0 顶上 | ❌ 违反 P1 |

判别办法一句话：

> **少做一件事是健康的；把一件事做得看起来完整但其中有假的，不可接受。**

这正是 `process/2-CHANGE.md` 的「缩范围 vs 降标准」。压力永远推向后者，
因为降标准在演示时看不出来。

---

## 3. `catch` 后返回空数组 —— 违反 P1

```ts
try { return await search(kw) } catch { return [] }    // ✗
```

「请求失败」和「这个关键词确实没人」被合并成同一个值。
用户会据此毙掉一个本来不错的关键词。

要么让错误往上抛，要么返回一个能表达「我没有资格回答」的东西。

---

## 4. DRY 到底 —— 两个平台的字段不是一回事

TikTok 的 `followerCount` 和 Instagram 的 `follower_count` 看起来该合并处理，
但它们的**缺失含义不同**：TikTok 视频搜索的 author 对象本来就常常不带 bio
（所以必须补 profile），IG hashtag 结果里的 owner 则通常带。

合并成一个"通用解析器"之后，改一处会误伤另一处。
适配层里两个平台**分开写**，靠 `_interface.md` 的契约保证输出一致，
而不是靠共用代码。

---

## 5. 封装内部细节 —— 溯源信息必须穿透到界面

`source_keyword`、`source_dimension`、`fit_reason` 这些"内部实现细节"
**必须出现在 CSV 和报告里**。

运营要回答的问题是「为什么这个人排在前面」。答不上来，他就不会信这份名单，
而一份不被信任的名单等于没做。

这条同样适用于成本：花了多少、剩多少，必须全程可见（P3）。

---

## 6. 空值合并成布尔 —— 把三档压成两档

```ts
if (!creator.email) { /* 没邮箱 */ }        // ✗ undefined 和 null 混为一谈
```

`undefined`（没查过）和 `null`（查过，没有）在这里是两件事：
前者应该去补 profile，后者不该再花钱。

`process/README.md` 的总纲说的就是这件事 —— **第三档不许被压掉**。

---

## 7. 有默认值的配置项 —— 预算不许有默认值

一般配置项给个合理默认值是好习惯。**预算不行。**

不同人的预算和任务规模差异太大，任何拍脑袋的数字都会误伤。
必须由用户在 Phase 01 设定；用户不给才按 $2 走，**并明确告知这是假设值**。

对照 P3：花的是用户的钱，代价由他承担，且花掉不可逆。

---

## 8. 「修一下测试让它绿」—— 默认驳回

变异存活时，修的是**测试**不是变异；测试失败时，先假设**代码**错了。

改测试让它变绿和修好代码让它变绿，**在 CI 上长得一模一样**。
确实需要改测试的，写进 `DECISIONS.md`。

见 `process/4-VERIFY.md`。

---

## 9. 「我跑过了」≠「我跑过那条路径」

probe / collect 需要密钥和网络，在开发环境里**等于从未被测试过**。

所以有 `npm run selfcheck` —— 用假 fetch 把每个可执行文件从头执行到尾。
新增可执行文件时**同时加进自检**，否则审计会报它没被执行过。

---

## 10. 入口脚本里放决策逻辑 —— 它就永远测不到

`scripts/*.ts` 是入口（读参数、落盘、打印、退出码），`scripts/lib/*.ts` 才放逻辑。
**检查脚本同样分这两层**：`scripts/check/lint.ts` 走文件树、打印、退出码，
判定在 `scripts/check/lint-rule.ts`。

判据只有一句：**这段代码的顺序错了会不会出错？**

会，它就有语义；有语义就该能被测；能被测就不该待在入口脚本里。
合并要在粉丝闸门之前（否则「两平台各 3000」的人被提前丢掉）、
降权要在分层之后（否则降完立刻被覆盖）—— 这些都是语义，都在 `lib/pipeline.ts`。

这条踩过五次。前三次是变异存活（M-P2-a、M-U5-a），第四次是 ADR-08 那个
数据丢失 bug：`filterByMemory`、`saveCreators`、`loadCreators` 三个函数各自都对，
错的是入口脚本里把它们组合起来的方式。**单元测试永远看不到这类 bug，
因为它不在任何一个单元里。**

第五次是这条纪律 lint 自己：判定与走法混在同一个入口文件里，于是 P1 唯一
机器可执行的那一半，自己既没有测试也没有变异 —— 敏感字段表漏了 `plays`，
漏了多久没人知道。抽出 `lint-rule.ts` 之后才拿到测试与 M-P1-i/j/k。
**这一次的教训比前四次多一层：检查自己也是被检查对象。**

---

## 11. 关于第三层

`process/README.md` 说得很清楚：有些纪律机器查不了。本项目里主要是这几条：

- **P2 的判断那一半**（草稿里的产品事实是否真来自产品页）—— 见 ADR-01
- **写测试时不读实现** —— 目前违反了，见 ADR-04
- **一个任务 = 一个能一次读完的 diff**

**不要假装这一层是被保证的。** 它们显式留在审计报告里。

---

## 12. 把公开异常分数命名为“假粉率” —— 违反 P5

近期播放、互动和关注比只能告诉我们“这个账号相对同行有异常”，看不到全部粉丝是谁，
更看不到订单与转化。把启发式风险写成 `fake_follower_rate=37%`，会把方法没有测量过的
东西包装成精确事实。

本项目只输出 `audience_quality_risk` 与逐条依据。即使未来第三方返回百分比，也必须保留
供应商、时间、样本和方法口径；在没有独立验证前不得单独删除创作者或声称带货差。

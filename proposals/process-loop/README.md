## 0. 结论先行

1. **记录这一环是全套里最硬的，识别、回访、沉淀三环都是空的或靠人。** 决策记录一条一文件、欠条块没写重启条件当场红、
   「教训」栏可选 —— 这些都在；但「写下之后再把它拿出来」没有任何触发器：`process/6-INTEGRATE.md` 说重启条件是
   三种之一（碰到那个文件 / 同一缺口再被点名 / 定期清点），ADR-64 的欠条自述「**三种没有一种是自动的** —— 全靠下一个人恰好记得」；
   「定期清点」在决策记录里实际发生过 16 次，15 次是作者在 PR 流程里顺手做的，1 次是需求所有者的 main 审计，**没有一次是定期的**；
   「教训」栏在仓库里**没有任何读者**（代码、索引、流程文档各 0 处读它）；教训进 `process/` 的样本里，真正「先记后搬」的 12 个
   延迟 4–25 天，每次都是人想起来。
2. **CI 时长这条线是上面那句的实证。** 12 条决策记录（ADR-72/75/97/99/120/121/126/129/131/132/144/145），
   头部写明由用户或需求所有者提问、要求或裁决的四条（97、99 二阶、132、145），其余八条头部没写谁提的 —— 两条提了请求（72、75），六条连请求也没提（§2.1）；**这 12 条没有一条有「教训」栏**。
   2026-10-11 到 10-12 #294 到 #301 这条功能线合入，主干检查 #296 合入后 16:37、#300 后 23:04、#301 后 30:42（ADR-144 头部），每一跑的日志里都打着 `resume-progress` 那一行成本数
   （362 → 1283 → 1662 秒），**有数；当时是否有人比过，无从确认**。按主干 301 次成功运行回测，一条「本跑 vs 前五跑中位，超三成就报一行」的只报数传感器
   在五段人记下的劣化上全部命中，其中三段早于人（约 3 小时、约 1 天、2 天），噪声约 1.7%；它判不出是哪条改动、也抓不到两成以内的小步，
   但「不靠人提醒」这一点它够（§2.3）。ADR-145 把「发现」写成了树的函数（启动数），三片已全部合入：第三片 #311 把启动数闸门接在检查链最后一步，
   PR 上判红、主干只报数、计数缺了主干也红，不设豁免（ADR-145 §二十一、§二十五）；#312、#313 又加了两行只报数（进程内耗时、有启动但没有变异的组）。
   秒数那一半仍归人 —— `process/6-INTEGRATE.md` 随 #311 写明「检查链要是已经数了、判了,作者不必再证;作者补的是机器没数的那部分,主要是秒数」。
   而就在 10-13，需求所有者又问了一次「CI 为什么一会二十分钟、一会十几分钟」，答案（runner 型号不同）是人比了 9 跑推出来的，
   处置是 CI 末尾加一步 `lscpu` 打出型号、只报数（ADR-145 §三十一第 5 小节）—— 时长线上又一次由人发问、机器只多打一行。
3. **self-evolution 分支的材料三分之二已过时或与主干后来的决定相撞，剩下的三分之一正是这件事缺的句子。**
   它从未开过 PR；形式化那块次日被 ADR-96「零模型」否定，治理那块撞 ADR-79/81，
   控制论九条全部以产品指标为被控量、**没有一个传感器量检查链自身**，还把「成本回路」当成「通常最先闭合」略过了。
   可以原样搬的：三档分权（写草案、登记、复核意见可自动；改 `process/` 一律人批）、「没有传感器的目标不能成为自动演化的目标」、
   「效应量低于可分辨差时只记录不决策」、「没有跨运行台账，迟滞／冷却／振荡检测不可执行」、「缺失读作无从确认」、
   「改通用层的 PR 必须配一条决策记录，写明这条纪律从哪个项目的哪件事里提出来」（§3）。
4. **推荐七条实践（§5），每条都过了三个独立反驳镜头（合规 / 有效性 / 成本），六条按反驳降过档。** 共同形状：
   机器只做「跑」—— 数、比、抽取、按日历触发；「读」—— 这是不是同一类、值不值、能不能进 `process/` —— 一律递给仓库里**已经定义好的读者**
   （评审器、合并者、下一条欠条 PR、需求所有者），不是「有人想起来」；产出只落既有形状（审计 stdout、`⚠️` 欠条块、一条专用台账记录），
   不落热文件、不建会漂的表；改 `process/` 永远由人另开一条 PR 并写明来源。
   第一条 PR 零风险：`npm run audit -- --cites` 在 stdout 列出每条记录被引几次、有没有教训栏（§7）。
5. **明确不做的 12 件**（§6，按表的行序）：秒数判红、机器追加的持久台账、用 `upload-artifact` 上传成本 JSON、每合入一条记录起会话／每日日报、给模板加必填「同类」栏、
   产品词 lint／路径↔重启条件匹配／相似记录路由表、往索引生成区加列、用中文 trailer 当成功信号、散落新记号块、把说明书放 `.github/`、手写首条样本、让例程改 `process/` 或替人下结论（含自判死亡条件）。

### 2.2 立场怎么从「不建」走到「建」

ADR-97 §四的四条理由（秒数只在那台机器上成立；核不了的死亡条件比没有更糟；体量闸门的豁免全是自批；闸门自身成本是乘性的）
在 ADR-145 §五被逐条回应：启动数是树的函数、两条死亡条件对着仓库核得了、不设豁免、判定在进程内 0 次启动。
对 bitter lesson 的用法也写清了：**「数一个数属于该建的『替代跑的』；『这段前缀该不该付』属于不建的『替代读的』，所以本条只数、不判前缀必不必要」**。

今天（`3985048`）机器已经能报什么：每跑变异末尾的账单与成本 JSON（只在日志）；每配置的启动数、`launches.json`、超线重跑确认（`output/` 下，不进树）；
检查链最后一步照 `launches.json` **判红**（PR 上；主干只报数，缺计数主干也红，#311）；变异一步收尾的「进程内耗时」一行（组内不起进程的配置，以本跑单条变异耗时的中位数为单位，#312）；
最后一步的「有启动但没有变异的组」一行（按族，`output/selfcheck-launches/families.json`，#313）；CI 日志末尾的 runner 型号（`lscpu`）。后三样只报数。
还不能报什么（ADR-145 §七，按 `3985048` 重读）：单次启动变贵、嵌套启动、整组中等程度地胀（ADR-131 那次封不住）、少写变异；
进程内变慢与变异以外的耗时各有了一行**单跑的数**，两跑之间比不比仍靠人（§二十八第 3 条自己记了两跑单位差 1.7 倍、合计差一成五，「这只是两个样本」）；
以及 —— **秒数仍无跨运行比对、无持久历史**；runner 型号也只在日志里，五个样本是人从五份日志里抄出来的（§三十四末）。

### 2.3 用主干 301 次成功运行回测：墙钟作「只报数」传感器够不够

数据：GitHub Actions 公开 API，`/actions/runs?branch=main&status=completed`，306 次（301 成功、5 取消），时长取 `run_started_at → updated_at`；
2026-10-02（#261）之前主干不取消排队，第二跑要等第一跑，所以按串行模型估排队并扣掉（14 次抽样逐步骤核过，估 754 秒 / 实测 756 秒）。

| 传感器 | 台阶命中 | 噪声/回声 | 与人的对照 |
|---|---|---|---|
| (a) 本跑 vs 前 5 次成功跑中位，超 +30% 报 | 9 个台阶全部首报 | 纯噪声 5/301（≈1.7%）；同台阶回声 14 次 | S6（09-23，8:50→31:42）比第一条提速 PR 早 2 天；S8（10-01）早约 1 天；S9（10-12）早 1 个 PR；S5（09-20）人早一天 |
| (b) 近 10 次中位 vs 再前 10 次中位，超 +20% 报 | 滞后 4 跑到 1.5 天，**完全漏掉 S8**，S9 报在修完之后 | 无纯噪声 | 比人慢 |
| (c) 连续上涨 N 次 | N=3 命中 5、噪声 12；N≥4 基本失效 | 高 | runner 噪声 ±30% 让单调上涨几乎不连续 |

抓不到的：#294（+36 秒，ADR-145 自己也说「淹在噪声里」）、#299（×1.21），以及所有两成以内的小步。
**结论：墙钟够「只报一行数」用（一条「本跑 X，前 5 跑中位 Y，×1.NN」代价为零），不够归因、不够判红** —— 与 ADR-97/145 的立场不冲突。
更稳的量按序：启动数（树的函数，但只能从 #309 接线之后往前看）、变异条数（零噪声、`git show <sha>:scripts/check/mutations.json` 可回放，但单调递增分不出贵的一条）、
逐配置的基线秒数与变异合计秒数（比总墙钟敏感，仍乘 runner 系数）。

## 4. 回路图：今天断在哪

```
 目标：检查链跑得起、问题不复发、通用纪律随经验长
      │
      ▼
 控制器：人（需求所有者 / 作者 / 评审器）────改────▶ 被控对象：检查链配置、测试分组、process/、docs/
      ▲                                                        │
      │   传感器 A  检查链红绿、audit 硬失败 ◀───────────────────┤ 闭合
      │   传感器 B  启动数 → 最后一步判红 ◀──────────────────────┤ 闭合（#311 起，PR 上红）：只量启动数
      │   传感器 B′ 秒数 / 进程内耗时 / 按族启动数 / CPU ◀───────┤ 半开：机器打印、人读、不跨运行（#312/#313 后仍如此）
      │   传感器 C  欠条「响了没还」◀──────────────────────────┤ 开路：靠人重读
      │   传感器 D  「教训」栏 / 同类第几次 ◀───────────────────┤ 开路：0 个读者
      └───传感器 E  需求所有者问一句话 ◀────────────────────────┘ 闭合，但只有一个提问者
```

断开的是 B′ 的「跨运行」那一半、C 与 D 的整段。B 里启动数那一段 #311 起闭合了，但它只量启动数；秒数、进程内耗时、按族启动数、runner 型号（B′）仍是一跑一个数、人比。
回访目前还没有自动触发；10-13 那次「CI 为什么一会二十分钟、一会十几分钟」又是 E 响的。
按通-31 的判据，B′/C/D 在闭合之前，任何「自动改纪律 / 改阈值 / 改分组」都处于熔断态：机器只能记录、比数、递原料和起草，不能改尺子。

**P3 的死亡条件**（随 ADR-145 追加节一起由需求所有者批）：

> **什么条件下退成只写文件、不核相等**：任一 CI 报出「启动数不确定」，或某条没碰 `mutations.json` / `scripts/test.ts` / `scripts/check/selfcheck.ts` 的 PR，其现算与树内文件不等。

> **什么条件下整个撤掉**：ADR-145 §六第二条成真（变异按点名的用例路由，文件退化为一配置一条）。

**几条反驳里改掉的东西，值得单独说：**

- **读者必须是仓库里已经定义的角色。** 三位裁判的共同盲点是「把『比』交给机器后，把『读』原样递回同一个人」。改形后：P1 的读者是「改验证成本时，评审要看到实际变化」那条既有义务的评审/合并者（#311 后那一节写明「作者补的是机器没数的那部分,主要是秒数」，P1 补的就是它）；P5 的读者是下一条欠条 PR（正文须引台账 id）；P4 用 `AGENTS.md` 一行让接手的会话必读台账。
- **死亡条件只能是 git 内一条命令可核的事实。** 「连续 N 次运行里 X 没发生」这一族在本仓库核不了（ADR-85），所以 P4 用「八周内台账无块」与「八周内无 `已合入` token」，其余几条按 ADR-85 写明「不是闸门、不设」。
- **新写入点不落热文件。** 决策记录末尾与索引是最热的写入点之一（反驳上下文量过「近 7 天 26 个文件被 ≥ 2 条 PR 碰」，口径没留下，本文复现不出；按「`3985048` 前 7 天内被 ≥ 2 条合入 PR 碰过的文件」重算是 63 个（`git log --first-parent 3985048 --since='2026-10-06T21:36:37+08:00' --format= --name-only | grep . | sort | uniq -d | wc -l`），其中 27 个是决策记录（把末尾的 `wc -l` 换成 `grep -c 'docs/adr/ADR-'`）、索引 `docs/adr/README.md` 被 14 条 PR 碰（`--name-only` 之后直接接 `grep -cx 'docs/adr/README.md'`）；`mutations.json`、`ARCHITECTURE.md`、`test.ts` 更热，但本提案不往那里写），索引生成区两条并行 PR 同改一行会干净合并后主干红（反驳上下文在临时仓库复现过）。所以 P2 落 stdout 不落索引，P5 只写一条专用台账记录。
- **单一人类身份。** Routine 以所有者账号提交会让作者 = 合并者（`6-INTEGRATE.md`「合并者不能是写档的那一方」那条）；先以快车道形状（只追加一个文件、直接合）跑四周，P7 上线前再决定要不要机器人账号 —— 这是 §7 的裁决项之一。
- **「本可抓到什么」按核过的日期改写。** P1 在 PR 侧对 S6/S8/S9 分别早 2 天、约 1 天、约 3 小时，前提是评审者读那一行；×1.33 和 ×1.43 落在 docs-only 噪声的 p90（×1.46）以内，单跑分不出噪声，有效提前量比回测少一跑。P2 对 CI 线零提前量（ADR-120、131 都不引 ADR-97），它守的是「教训记了没被应用」这一类的候选池。P5 对劣化晚于人，收益只在长期挂着的条件（ADR-129 那条重审条件自 09-29 起恒真，10-05 的第一个周一就会列出，早于 ADR-144 一周）。

**与主干已有物的关系：** P1/P3 补 ADR-145 §七「不覆盖的」里启动数盲的几条（§七末那两行只报数已随 #312、#313 落下，P1 补的是它们之上的跨运行比对），不碰「不设秒数闸门」那句；P2 给 `2-CHANGE.md` 的「教训」栏第一个结构读者，不改模板；P4/P5 给 `6-INTEGRATE.md`「定期清点」补触发器、不改清单，不与 ADR-80（拒绝给闸门装自动清点器）冲突 —— 机器只触发与递原料，不判死亡条件；P6 是 incident.io「Related incidents」在建立时匹配、人当场接受/拒绝的同形；P7 给 `SYNC.md`「如果换个产品也成立，那它写错地方了 —— 移到 `process/` 去」补触发器，判据不动。

## 7. 落地顺序、要裁的事、怎么验收

**第一条 PR 的顺序**（每条只回答一个证据问题，48 小时内能合）：

1. **P2** `--cites`：零 CI 改动、零文件写、零判定。证据问题：「被引最多的 10 条里几条有教训栏？」（本文在 `3985048` 上按同一口径算过一次：ADR-70、78、89、77、99、132、87、97、22、94，其中 **7 条没有**，有的只是 70、22、94；被引 ≥ 3 的 97/139。`f4b314e` 上同一批十条、92/138）
2. **P1** 时长对比一行：验收 = runner 上算出的前 5 次中位与本文 §2.3 的口径一致；PR 上的 notice 在合并者按 UI 合并时在视线里。
3. **P4** 契约：说明书 + 空台账记录 + SYNC 文档地图一行 + `AGENTS.md` 一行；claude.ai 建 Routine，prompt 只一句转发。
4. **P5** 首跑（前提：§5 P5 (b) 那个不读覆盖记录的抽取入口已合）：手动 Run now 一次，只做 (b) 欠条 diff + 「定期清点」日龄两段，追加台账第一块（含「能否读 Actions 接口」「squash 后块是否完整落树」两项三态）。证据问题：「四周里由台账候选引出的欠条 PR 有几条？」对照今天 16 次清点 0 次由定期发起。
5. **P3** 启动数摘要落树：先在 ADR-145 追加一节由需求所有者批；K 条 PR 后决定要不要升红。
6. **P6** 评审时同类提示：样本 = 下一条新记录的评审线程。证据问题：「四周内评审器提的候选被作者接受几条、拒绝几条？」
7. **P7** 候选句已知缺口记录：所有者先人工过一遍 §1.1 那 19 类；首条样本选「教训记了没被应用」（8 条、`process/` 无已搬、不撞 ADR-145 已合入的那几片）。

**只有需求所有者能裁的（各附建议）：**

1. `check.yml` 加 `actions: read`（仍只读）换 `GITHUB_TOKEN` 配额？建议接受；否则 P1 用未登录 curl、首周看 403 率。

### A.2 一次教训怎么变成通用规则，且不靠人记得

| 实践 | 形状 | 对本仓库的映射 |
|---|---|---|
| Google ;login: 2017「Postmortem Action Items」（读到） | 反模式「Thinking Only of the Current Incident (Missing Patterns)」：「We rarely repeat incidents, but we sometimes have incidents that rhyme」；缓解是「Review postmortems for similar incidents」；AI 按「风险 of unmitigated recurrence」定级并跟踪关闭时间 | 决策记录的「教训」栏旁加一行「同类第几次 / 相似记录」，候选由机器递、人接受或拒绝；ADR-145 手写的「这是第四次」应是机器先说 |
| AWS COE → ORR（读到） | COE「preventing the reoccurrence … in the workload where it happened」；ORR「distills the learnings … into curated questions」去挡其它 workload —— **本地修复与通用清单是两种产物** | `docs/adr/` 对应 COE，`process/` 对应 ORR；晋升候选由「同一机制第 N 次」计数触发，晋升本身人批 |
| Rust 周会（读到） | 每周四；议程由 `prioritization-agenda` 工具从标签生成，人只读 | 「定期清点」改成日历触发、议程由脚本生成 |
| Linux regzbot（读到） | 每周日晚发报告；修复提交带 `Closes:`/`Link:` 指向报告即自动闭环；Linus 看周报 | 欠条带 ID，提交/PR 引用 ID 即「已还」，没被引用的持续出现在周报里 |

**对「自动沉淀放哪一档」的结论：** 自动档只放不当规则读的观测记录（跨运行的成本序列、台账）；提议档放教训候选、欠条重启建议、决策记录草案，以 PR 或只读报告出现；
人批档放 `process/` 的每一句、任何「以后一律 X」的规则、删或降权既有教训。这与 self-evolution 提案的通-20 三档、与 `process/README.md`「替代读的不建」一致。

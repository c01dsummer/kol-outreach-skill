### 通-20 · 分权原则：尺子 / 被量的 / 尺子的尺子，三档（自动 / 提议 / 人批）与正面清单
- **目标文件**：process/README.md · §「什么时候不走流程」（行 180–187）
- **现状**：「改文案、调间距、重命名变量、修 bug、补测试 —— **直接做**。流程只在**改动触及需求登记表任何一条**时启动。」
- **提议**：「直接做」的边界不按文件类型划，按**这件东西是尺子还是被量的**划。被量的：普通代码、给自动化执行者的指令文本、配置、模型对实现的映射。尺子：需求文本、判据与结构化子句、词汇表里的 oracle、测试的期望值、变异集、模型不变量、假设登记表。尺子的尺子：红线、本目录的流程文档、审计判定、闸门代码与 CI 配置本身。**一次改动只碰一类；碰了尺子的改动，验证它的不能是同一个上下文。** 改动分三档：**自动** —— 自动化执行者可直接改、直接合，仍过检查链；**提议** —— 可以改、可以开 PR，合并前必须有独立复核，复核记录进 PR；**人批** —— 执行者只能写提案（决策记录草案、提案文档），改动本身由人做或由人明确授权后做。被量的默认自动，但触及守红线模块（架构文档锚点表里标注服务红线的模块）的普通代码升为提议。自动化执行者可以做的正面清单：修实现让现有测试变绿（不动测试）；新增测试、变异、属性、不变量、运行时断言；把一条散文假设登记进假设登记表（标「未验证」）；把一条判据的可观测结果与例子补具体（不改义务本身）；写决策记录草案、提案、复核意见；执行预定义的回滚（限被量的改动）；在参数层影子模式下运行候选规则并记录对比数据（`7-EVOLVE.md`）。放宽方向的改动一律不在自动档（`2-CHANGE.md`）。
- **为什么**：最要防的模式是「修改代码 → 验证失败 → 自动放宽尺子 → 通过」，它的危险在于同一执行者同一上下文同时握着被量的与尺子；今天改守红线的检查链、零复核、作者自合仍算「直接做」→ 依据见 9-evidence.md §B（B18）、§I「关于测试与同源」

### 通-01 · 判据可选的结构化子句形式与字段集
- **目标文件**：process/1-REQUIREMENTS.md · §「一条需求长什么样」（行 33–55）与 §「验收标准是一组判据」（行 57–88）
- **现状**：判据只有两个字段 ——「{ "id": "D3.a", "text": "怎么算满足了 —— 必须是可以被判定的,不是形容词" }」
- **提议**：判据的 `text` 一字不动，旁边**可以**挂一个结构化的行为规格 `ears`（EARS 句型），二选一：`{ clauses: [...] }` 或显式的 `{ none: { verify: 'human' | 'unmeasured', why } }`。每条子句：`id` 形如 `{判据编号}/{正整数}`，稳定、不回收（R5）；`while`（状态，全部成立）、`when`（事件，至多一个）、`if`（条件；与 `when` 同现时是守卫）、`where`（功能开关）、`unless`（例外：任一成立则本子句不适用）、`shall` / `shall_not`（义务与禁止的响应，至少一个非空）、`outcome`（响应之后必须成立的可观测结果，可带期望值）、`examples`（边界值绑定，测试应使用，不参与计量）、`boundary_of`（本子句是与哪条需求交点上的让步边界，登记表里必须有对应 `tension`，R9）、`note`（唯一的自由文本，过实现泄漏检查，点名的决策记录必须在 `adr[]`，R4）。句型由字段推出（`when` 至多一个；四者皆无即无条件句型；R1），不存 `kind`。每一格里出现的词都必须是词汇表术语（词汇表的要求见「验收标准」节的「可判定」条）。**故意不存的**：「这条子句由什么验」（由术语的 oracle 推出）；达到的证据等级（由检查写进覆盖记录）；范围边界「不保证」（回需求 `text`）。这套字段只回答「在什么前提、对什么事件、要求什么可观测结果」，写不出来的那一格就是没想清楚的那一格；它不能证明需求是对的，也看不见两条各自合规的需求在交点上打架 —— 交点仍由 `tension` 负责。
- **为什么**：一句话判据装着两条义务、测试只覆盖一半而审计报 ✓；「不可失败」判据混在判据里；登记表没有「这条判据由什么守」的信息 → 依据见 9-evidence.md §B（B1、B19）、§I「关于需求与 EARS」；实例见 8-p3-pilot.md §D.2
- **承接**：业-01、业-02、业-04、业-05、业-11、业-12、业-13、业-14、业-33、业-55；码-01、码-02
- **落地**：H 第 2 步 · 裁决 J10、J11、J38 · 档：人批（process/ 改动）
### 通-02 · 术语表：每个术语带 oracle 种类，human / none 显式
- **目标文件**：process/1-REQUIREMENTS.md · §「验收标准」（行 175–182）「可判定」一条
- **现状**：「**可判定** —— 两个人分别看,结论一样」
- **提议**：「可判定」里机器守得住的那一半是词汇表：登记表根级维护一张术语表，子句里的每个词都必须是其中一条。每条术语有 `kind`（state / event / condition / response / outcome / feature / quantity）、人话定义 `def`（过实现泄漏检查，R4）、首次登记日期 `since`（含义变了换 id，旧 id 进退役清单）、至少一个 `oracle`（R3）。oracle 是机器判定这个词成立与否时去读的那个东西：`invoke`（怎么触发，只有 event 允许）、`call`（调哪个模块的哪个导出，期望返回 / 抛出 / 不变）、`exit_code`、`stdout_json`、`stderr_match`、`file_json`、`file_text`、`source_grep`、`call_count`、`fixture`（只有夹具能观测的量）、`model`（只在模型里存在的量）、`human`（显式承认只能靠人，带 `who` 与 `mitigation`）、`none`（显式承认还没决定怎么观察，带 `why`）。event 只允许 `invoke`，其余只允许观测类；`human` / `none` / `model` 必须带理由，审计单列，红线判据用到的术语不许是 `none`。「unknown」有三个落处，不许混：说的是范围 → 需求 `text`；说的是整条判据 → `ears.none`；说的是某个术语 → `oracle: none`。要一起写明界线：机器只能保证「每个术语都有人写了 oracle」，写的 oracle 是不是真可判定、oracle 里的谓词说的是「大于什么」，仍要人看。改词汇表的档：新增术语是**提议**；把一个术语的 oracle 从机器类改成 `human` / `none` 是放宽，**人批**；反向（从 `human` / `none` 改成机器类）是**提议**；登记表的形状校验要看 oracle 改动的方向。放宽清单（`2-CHANGE.md`）说的「只能提议」是上限，这里定得更严的人批以本行为准。
- **为什么**：「句式合规但不可判定」只能靠词汇表 + oracle 挡；可判定性本身是语义性质，机器判不了 → 依据见 9-evidence.md §B（B1）、§I「关于需求与 EARS」；实例见 8-p3-pilot.md §D.2
- **承接**：业-01、业-06；码-01、码-03
- **落地**：H 第 2 步 · 裁决 J46 · 档：人批（process/ 改动）

### 通-04 · 「句式合规但不可判定」的机器识别规则
- **目标文件**：process/1-REQUIREMENTS.md · §「验收标准」（行 175–182）
- **现状**：「**可失败** —— 存在一种明确的情况会让它不通过。永远通不过和永远通得过一样没用」
- **提议**：对结构化子句，机器只守这几条：**R2** 每一格引用的词必须在词汇表里存在且 kind 与槽位匹配（`while` 只收 state，`when` 只收 event……）；**R3** 每个术语的 oracle 非空，`human` / `none` / `model` 带理由；**R6** 迁移闸开到「红线」档之后，红线判据必须有子句或显式 `none`，且 `none` 的红线判据必须同时出现在变异集的豁免表里；**R11** 只有真跑入口才观测得到的 oracle（`exit_code` / `stdout_json` / `fixture`）不得由单元测试认领，只能由脚本自检认领。迁移闸 `ears_policy.require ∈ { none, redline, all }`：`none` 时孤儿术语（没有任何子句引用）只警告，`redline` 起变红（R8）—— 先装术语后挂子句的迁移期不能因此红。这几条能挡住「安全地处理」「合理地快」「适当地去重」这类没有定义的词：它们进不了词汇表，进了就得写 oracle，写成 `human` / `none` 的在审计里单列并对红线施压。机器**做不到**的一起写明：判断一个写了 oracle 的术语是否真可判定；判断谓词的内容。含糊词表这类检查在存量判据上从不红，只约束新写的术语，不能拿它当可判定性的保证。
- **为什么**：判据的可判定性差三个量级，EARS 化时它们会暴露为「不可失败」或「无 oracle」 → 依据见 9-evidence.md §B（B1）、§I「关于需求与 EARS」

- **落地**：H 第 2 步 · 裁决 J46 · 档：人批（process/ 改动）

### 通-06 · 一条判据多义务：子句是同一路径的边界枚举，不同路径仍拆判据
- **目标文件**：process/1-REQUIREMENTS.md · §「验收标准是一组判据」「拆到多细」（行 73–80）
- **现状**：「**这两半会不会被不同的代码路径独立满足、或者独立弄坏?** 会 → 拆成两条。」
- **提议**：有了结构化子句之后这条判据不变，只多一句边界：**一条判据下的多条子句只能是同一条代码路径的边界枚举**（零成本、恰好等于上限、前提未确认……这类拒绝 / 放行分支与边界例子），不是多条义务的容器。多个能被不同路径独立弄坏的义务仍然是多条判据 —— 路径机器判不了，靠人；机器只做一件事：`shall` 里出现「and / 且 / 并 / 同时」时**警告**，不失败（R10）。子句 id 不是第三套编号：它只在判据编号后面加一个序号，认领、变异、指纹的单位仍是判据。
- **为什么**：拆分判据是「会不会被不同代码路径独立弄坏」，要读实现结构，机器做不到 → 依据见 9-evidence.md §B（B1）、§I「关于需求与 EARS」

### 通-09 · 范围边界声明算放宽；自动执行者只能指出「边界未声明」
- **目标文件**：process/1-REQUIREMENTS.md · §「红线的四条硬要求」（行 143–157）
- **现状**：「1. **不参与 trade-off。**任何变更请求只要触碰红线,直接驳回,不进入权衡」
- **提议**：（列表末尾追加第 6 条）**红线的范围边界声明也是放宽。**「本条在某某情况下当前不保证」这句话让红线覆盖的面变小，方向与删一条判据相同。自动化执行者不得起草它 —— 只能登记「边界未声明」（撞见的是什么情况、证据是什么），措辞由需求所有者起草；起草「收紧」或「拆判据」方向的决策记录不受此限。

### 通-07 · 义务指纹（含 unless / where）划分「改义务」与「补 outcome」
- **目标文件**：process/2-CHANGE.md · §「第一步:分类。类型决定处理方式」（行 19–29），「需求有歧义 → 补充」一行（行 26）

### 通-08 · 放宽 / 收紧的机器可认清单与「放宽只能提议」

### 通-18 · 结构化义务到各层守法的映射表

### 通-32 · 传感器三条纪律：三态表示、不与控制器同源、有失效形态
- **目标文件**：process/7-EVOLVE.md（新篇）· §「传感器」
- **现状**：今天没有
- **提议**：每个传感器登记七样：读哪里、测的是什么、是测量还是代理、unknown 怎么表示、延迟、噪声来源、失效形态。三条纪律：（1）**任何进入控制决策的量，来源字段必须能表达三态**；交付物里凡是数值，旁边必须有状态或分三态计数；一个裸的 `0` 不得进入任何自动决策 —— 可机器守，把「禁止默认值兜底」那类 lint 扩到读交付物的一侧。（2）**传感器与控制器不得同源**：由判定者给出的判定不能反过来自动调整它自己的判定规则，也不能自动用于改它的输入策略。机器守不住「同源」本身，能守的是结构 —— 判定字段旁边要有第二判定的落处（谁判、值、何时），每任务由人盲判固定 N 条，一致率以三态记录（未抽检 / 抽检 n 条一致 k 条），按桶跨任务累计，n 达门槛才成为决策输入；一致率未记录或未达门槛时，这个传感器不得作为任何改动的依据。「让同一个判定者再判一次」不是零成本，也不盲。（3）**每个传感器有失效形态** —— 读不到、样本不足、口径变了（软件或配置版本变了）—— 失效时控制器停手，可机器守。
- **为什么**：表现表把「0 结果 / 请求失败 / 未跑」坍缩成「无此行」，且被文档定为「下次调整策略的依据」—— 这句话本身就是同源回路 → 依据见 9-evidence.md §G「传感器」现状、§B（B16）、§I「关于控制闭环」
- **承接**：业-35、业-40、业-41、业-43、业-57；码-27、码-37
- **落地**：H 第 10、12 步 · 档：人批（process/ 改动）
### 通-33 · 状态估计：不看单点看窗口；区间、分桶、版本指纹只取影响面
- **目标文件**：process/7-EVOLVE.md（新篇）· §「状态估计」
- **现状**：今天没有
- **提议**：**不看单点，看窗口，先把数算出来。** 比例类指标用二项比例的置信区间（Wilson 区间）算最小可分辨差：两个窗口的区间不相交才算「变了」；预期效应量低于最小可分辨差时，这个闭环只记录、不决策 —— 要明说，不能给人「窗口攒够就能动」的印象。窗口按**同类别、同版本**分桶，桶内攒样本，跨桶不比。版本指纹只取影响该软目标的那几个文件，不取整棵源码树 —— 主干合并频繁时整树指纹会让窗口每天重置、永远攒不满。桶大小、一致率门槛、影子差异上限这些起点数字都是可失败的假设，写进假设登记表待校准。

### 通-34 · 控制变量表与不可控识别两问
- **目标文件**：process/7-EVOLVE.md（新篇）· §「控制变量」
- **现状**：今天没有
- **提议**：对每个软目标列一张控制变量表：变量在哪、谁能动（用户 / 人批 / 参数层可提议 / 判断层可提议）、影响面、反馈延迟。然后对每个软目标问两句：（a）它变动后，有没有传感器能分辨出结果的变化 —— 桶内区间是否可能分开；（b）变动它是否触碰任何红线或人批项。任一句答「否 / 不知道」，就把这个目标标成**当前不可控**，写进假设登记表，停止对它的自动演化 —— 这是识别「系统缺乏可控变量」的办法，替代的是盲目继续改代码。参数层的变量要集中到一个配置文件里，否则「一次只改一个变量」守不住。判断层规则（提示、知识、工作流文本）不是参数层：由判定者依据自己的判定结果改它，就是同源回路。
- **为什么**：回复率既无传感器又只有文案一个变量，按两问判为不可控；参数散在多个文件里守不住单变量 → 依据见 9-evidence.md §G「控制变量」现状、§I「关于控制闭环」

### 通-35 · 迟滞、冷却期、单变量、实验台账
- **目标文件**：process/7-EVOLVE.md（新篇）· §「稳定性」
- **现状**：今天没有
- **提议**：**迟滞**：改一个参数的触发条件与改回的触发条件不对称（例如改的触发是连续两个桶低于对照，改回的触发是连续三个桶高于），否则短期噪声会让它来回振荡。**冷却期**：任何参数层改动之后，至少一个完整桶内不得再改任何参数层变量；同一时间只允许一个在途实验。**单变量**：一次改一个变量；机器守法 = 一条 PR 只允许 diff 参数配置文件的一个键，进「改尺子」那道闸门。**实验台账**：跨任务记录「改了什么、何时、哪个桶、结果」；迟滞、冷却、振荡检测都从台账读，没有它这一节不可执行。
- **为什么**：今天只有每任务的交付物，没有跨任务记录 → 依据见 9-evidence.md §G「稳定性」现状、§I「关于控制闭环」

### 通-36 · 灰度 = 参数层的影子运行；判断层没有影子形式，只有人工盲评
- **目标文件**：process/7-EVOLVE.md（新篇）· §「灰度」
- **现状**：今天没有
- **提议**：没有多用户、没有部署的项目里，传统灰度不适用。可行的形式只有**参数层的影子运行**，且只对纯计算常量成立：候选参数与现行参数同时计算（本地纯函数，不花外部供应商的钱），候选结果写进一个**控制器不读的文件** —— 判断层文本明写不读它，lint 守判断层文本里不出现这个文件名 —— 交付物仍按现行参数产出；累积到桶满后由人看一眼再决定翻开关。改变外部请求量的参数**没有影子形式**：候选值意味着多发请求，那是花钱不是计算，只能小步改 + 人批。判断层规则没有影子形式：候选规则的「并行计算」意味着判定者对同一批对象再判一次，是成本且同会话不盲；判断层只有人工盲评。
